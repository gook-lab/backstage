관리자 화면에서 엑셀 다운로드를 누르면 30초 뒤 타임아웃이 나요. 서버가 파일을 만드는 중인지, 이미 실패했는지도 알 수 없어요. 10만 건을 내려받는 요청은 한 번의 응답 안에서 끝내기 어려워요.

이 글은 CSV와 엑셀 내보내기를 서버에서 만드는 방법을 다뤄요. 메모리에 다 올려 만드는 방식의 한계, 응답을 바로 흘려보내는 스트리밍, 파일을 따로 만들고 만료되는 링크로 내려받는 비동기 방식을 비교해요. 그다음 CSV 형식 규칙, 엑셀에서 한글이 깨지는 문제, 수식 주입, 내보내기 시점의 일관성, 권한과 감사 기록을 정리해요. 작업 상태 조회와 완료 알림은 [백그라운드 작업](/m/background-jobs) 글에서 다뤘어요.

아래 시뮬레이터에서 행 수와 생성 방식을 바꿔 보면 첫 바이트까지 걸리는 시간, 서버 최대 메모리, 게이트웨이 타임아웃 여부가 어떻게 달라지는지 바로 확인할 수 있어요. 이 글의 형식 규칙은 CSV 기준이에요. 엑셀(.xlsx) 파일은 형식 자체가 달라서, 쓰는 라이브러리가 스트리밍 쓰기를 지원하는지 따로 확인해야 해요.

## 타임아웃 증상 — 행을 다 읽은 뒤에야 첫 바이트가 나가는 구조

동기 요청으로 전체 행을 조회하고, CSV 문자열을 다 만든 뒤에 응답하면 첫 바이트는 마지막 행을 처리한 뒤에야 나가요. 행 수가 늘면 이 시간도 같이 늘어요.

RFC 9110은 504 (Gateway Timeout)를 게이트웨이나 프록시가 필요한 상위 서버에서 제때 응답을 받지 못했을 때의 상태 코드로 정의해요. 504를 받았다고 파일 생성이 실패했다는 뜻은 아니에요. 뒤에서 작업이 계속 돌고 있을 수도 있어요. 그래서 사용자가 다시 누르면 같은 내보내기가 한 번 더 돌 수 있어요.

## 메모리에 모아 응답 — 행 수에 비례해 커지는 서버 메모리

행을 배열에 모으고, 문자열로 합치고, 응답 버퍼에 다시 복사하면 같은 데이터가 여러 번 메모리에 올라가요. 시뮬레이터의 계수 3은 이 복사를 어림한 예시예요. 실제 배수는 언어와 라이브러리에 따라 달라요.

이 방식은 행 수가 늘수록 서버 한 대가 쓰는 메모리가 함께 늘어요. 내보내기가 동시에 여러 개 겹치면 그 부담이 곱해져요. 한도를 올리면 당장은 통과하지만, 전체를 붙잡는 구조는 그대로예요.

## 스트리밍 응답 — 커서로 나눠 읽으며 바로 쓰기

스트리밍은 DB에서 행을 조각으로 읽고, 조각마다 응답에 써요. 서버 메모리가 전체 행 수가 아니라 조각 하나 분량에 묶여요.

DB에서 읽는 방법은 두 가지예요. 하나는 커서예요. PostgreSQL 문서는 `DECLARE`로 만든 커서를 `WITHOUT HOLD`로 두면 그 커서는 만들어진 트랜잭션 안에서만 쓸 수 있다고 설명해요. 그래서 커서를 쓰는 동안 트랜잭션을 열어 둬야 해요. 다른 하나는 `COPY (SELECT ...) TO STDOUT`이에요. PostgreSQL 문서는 `COPY TO`가 SELECT 결과도 복사할 수 있고, `STDOUT`을 쓰면 데이터가 클라이언트와 서버 사이 연결로 전달된다고 설명해요.

HTTP 응답은 조각을 만들 때마다 보내요. 브라우저의 fetch 응답 body는 ReadableStream이에요. MDN은 Streams API가 역압 (backpressure)과 큐를 내장한다고 설명해요. 받는 쪽이 느리면 보내는 쪽도 속도를 줄여요. 서버도 같은 원칙으로, 응답 쓰기가 밀리면 DB에서 다음 조각을 읽는 것을 멈추는 편이 좋아요.

스트리밍에는 한계도 있어요. 응답 헤더는 본문보다 먼저 나가요. 그래서 중간에 실패하면 이미 나간 상태 코드는 바꿀 수 없어요. 서버가 중간 오류 뒤 응답을 정상으로 끝내 버리면 받는 쪽은 잘린 파일을 완료된 파일과 구분하기 어려워요. 오류가 나면 연결을 끊어 클라이언트가 실패로 알게 하거나, 마지막 줄에 행 수 같은 끝 표시를 두는 방법이 있어요. 이건 설계 판단이에요. 이 한계가 비동기 방식을 고르는 이유 중 하나예요.

## 비동기 파일 생성 — 접수 뒤 워커가 파일을 쓰는 흐름

비동기 방식에서 서버는 작업을 접수하고 202로 답해요. RFC 9110은 202 (Accepted)를 요청이 받아들여졌지만 처리는 아직 끝나지 않았다는 뜻으로 정의해요. 워커가 DB를 읽어 파일을 저장소에 쓰고, 끝나면 작업 상태가 완료로 바뀌어요.

워커도 행 전체를 메모리에 올릴 이유가 없어요. 조각 단위로 읽어 저장소에 쓰면 워커 메모리는 조각 크기에 묶여요. 상태를 어떻게 조회하고 완료를 어떻게 알릴지는 [백그라운드 작업](/m/background-jobs) 글에서 다뤘어요. 이 글은 파일을 어떻게 만들고 내려받는지에 집중해요.

## 다운로드 링크 — presigned URL의 만료와 권한 범위

완성된 파일은 저장소에 두고, 내려받기 링크는 만료되는 presigned URL로 줘요. AWS 문서는 presigned URL에 대상 객체, HTTP 메서드, 만료 시간이 들어간다고 설명해요. 콘솔에서 만들면 1분에서 12시간 사이로 정하고, AWS CLI나 SDK로 만들면 최대 7일까지 정할 수 있다고 설명해요. 임시 자격 증명으로 만들었다면 URL은 그 자격 증명이 끝나는 시점에 함께 끝나요.

URL을 가진 사람은 그 권한을 그대로 써요. 그래서 만료는 짧게 잡고, 메서드는 내려받기에 필요한 것만 허용하고, 객체 키는 작업마다 다르게 두는 편이 안전해요. 이건 설계 판단이에요.

만료된 링크를 받으면 같은 작업을 다시 만들거나, 파일이 아직 남아 있으면 새 링크만 발급해요. 다시 만들기 흐름은 [백그라운드 작업](/m/background-jobs) 글의 결과 파일 절과 같아요.

## 파일 이름 — Content-Disposition과 filename\* 인코딩

응답에는 `Content-Disposition: attachment`를 붙여서 브라우저가 내려받게 해요. MDN은 attachment가 응답을 내려받아 저장하게 하는 값이고, 보통 '다른 이름으로 저장' 창을 띄운다고 설명해요.

파일 이름은 두 파라미터로 줄 수 있어요. `filename`에는 ASCII 이름을 넣고, 한글 이름은 `filename*=UTF-8''...` 형태로 넣어요. `filename*`의 인코딩은 RFC 8187이 정한 ext-value 형식이에요. RFC 6266은 두 파라미터가 모두 있으면 받는 쪽이 `filename*`를 고르라고 정해요. MDN은 호환성을 위해 둘 다 넣는 편이 좋다고 권해요.

헤더 자체의 자세한 규칙은 [파일 전송](/m/file-transfer) 글에서 다뤘어요.

## CSV 형식 — RFC 4180 따옴표와 줄바꿈 규칙

RFC 4180은 CSV 파일 형식과 `text/csv` 미디어 타입을 정해요. 레코드는 CRLF로 나누고, 쉼표, 줄바꿈, 큰따옴표가 들어간 필드는 큰따옴표로 감싸요. 필드 안의 큰따옴표는 큰따옴표를 한 번 더 써서 이스케이프해요. RFC 4180의 예시는 `"aaa","b""bb","ccc"` 형태예요.

| 셀 값         | CSV 필드          | 이유                           |
| ------------- | ----------------- | ------------------------------ |
| 홍길동        | 홍길동            | 특수 문자가 없어서 그대로 써요 |
| 서울, 강남    | "서울, 강남"      | 쉼표가 있어서 감싸요           |
| 그는 "좋아요" | "그는 ""좋아요""" | 큰따옴표를 두 번 쓰고 감싸요   |

직접 문자열을 이어 붙이면 이 규칙을 빼먹기 쉬워요. 라이브러리의 CSV writer를 쓰는 편이 안전해요.

## 엑셀 한글 깨짐 — UTF-8 BOM 붙이기 기준

CSV를 엑셀에서 열면 한글이 깨져 보일 수 있어요. 이때 떠올리는 방법이 파일 맨 앞에 BOM을 붙이는 거예요.

Unicode FAQ는 BOM을 U+FEFF 문자로 정의해요. UTF-8에서는 바이트 순서를 알리는 용도가 아니라, 데이터가 UTF-8임을 알리는 서명으로 쓸 수 있다고 설명해요. UTF-8 BOM은 바이트 `EF BB BF`로 나타나요. 같은 문서는 BOM을 기대하지 않는 수신 측도 있다고 설명해요. 그래서 BOM을 붙일지는 파일을 여는 프로그램을 기준으로 정해요.

## CSV 수식 주입 — 셀 맨 앞 문자 막기

OWASP는 Excel과 LibreOffice Calc에서 `=`로 시작하는 셀이 수식으로 해석된다고 설명해요. 악의적인 수식은 파일을 여는 사람의 컴퓨터를 노리거나 다른 내용을 빼 갈 수 있어요. 사용자가 입력한 값이 그대로 CSV에 들어가면 이 위험이 생겨요.

OWASP는 `=`, `+`, `-`, `@`에 더해 탭, CR, LF로 시작하는 셀도 같은 위험으로 나열해요. 전각 문자 `＝`, `＋`, `－`, `＠`도 일부 환경에서 수식으로 해석될 수 있다고 설명해요. 음수 금액 `-3000`도 `-`로 시작해서 같은 처리 대상이에요.

대응은 두 가지가 나와요.

| 방식                      | 내용              | 주의                                                                                   |
| ------------------------- | ----------------- | -------------------------------------------------------------------------------------- |
| 작은 따옴표 앞에 붙이기   | `'=1+2`로 써요    | OWASP는 엑셀이 저장 뒤 다시 열 때 이스케이프가 사라져 수식이 살아날 수 있다고 설명해요 |
| 따옴표 안 맨 앞에 탭 넣기 | `"\t=1+2"`로 써요 | OWASP는 엑셀에서 관찰된 방식이고, 다른 스프레드시트에서는 다를 수 있다고 설명해요      |

탭을 넣으면 값 자체가 바뀌어요. 그래서 값을 그대로 다시 읽어야 하는 데이터라면 이 방식을 고르기 전에 받는 쪽을 확인해야 해요. 이건 설계 판단이에요.

## 내보내기 시점의 일관성 — 스냅샷과 페이지 사이 변경

내보내기가 여러 번 나눠 읽는 동안 데이터가 바뀌면, 같은 행이 두 번 나오거나 빠질 수 있어요. 예를 들어 OFFSET으로 페이지를 나누는 중에 앞쪽 행이 지워지면 다음 페이지의 첫 행이 한 칸 당겨져요.

PostgreSQL 문서는 REPEATABLE READ에서 트랜잭션이 보는 데이터가 첫 문장이 시작될 때의 스냅샷이라고 설명해요. 같은 트랜잭션의 SELECT들은 다른 트랜잭션이 그 뒤에 커밋한 변경을 보지 않아요. 긴 내보내기를 한 트랜잭션에 묶으면 같은 시점의 데이터를 받을 수 있어요. 대가로 그 트랜잭션은 내보내기가 끝날 때까지 열려 있어요. 이 대가는 설계 판단이에요.

트랜잭션을 길게 열기 어렵다면 페이지를 OFFSET 대신 마지막으로 받은 키 다음부터 읽는 커서 방식으로 나눠요. 앞쪽 행이 지워져도 다음 페이지가 밀리지 않아서 중복과 누락이 줄어요. 다만 읽는 동안 바뀐 행은 바뀐 값으로 나올 수 있어서, 한 시점의 스냅샷과 같지는 않아요. 자세한 설계는 [페이지네이션](/m/pagination) 글에서 다뤘어요.

## 권한과 감사 기록 — 접수 · 링크 발급 시점의 확인과 로그

권한은 두 번 확인해요. 한 번은 작업을 접수할 때이고, 한 번은 다운로드 링크를 발급할 때예요. 접수 때 있던 권한이 링크를 받을 때는 사라졌을 수 있어요. 권한 판단 자체는 [권한 설계](/m/authorization) 글을 보면 돼요.

작업에는 필터와 열 목록을 고정해서 저장해요. 워커가 나중에 실행될 때 화면의 필터가 바뀌어도 접수 당시 범위를 그대로 써요.

감사 기록에는 누가, 언제, 어떤 필터로, 몇 행을 내려받았는지 남겨요. 주민번호나 연락처 같은 열은 내보내기 열에서 빼거나 가려요. 이 기준은 [민감 정보](/m/sensitive-data) 글에서 다뤘고, 기록 구조는 [감사 이력](/m/audit-history) 글에서 다뤘어요.

## FE 체크 포인트

- 내보내기 버튼을 누르면 접수 응답을 받은 뒤 "파일을 만드는 중이에요"로 바꿔요. 완료된 뒤에만 다운로드 버튼을 보여요.
- 스트리밍 응답은 `fetch`로 받아 Blob으로 모으기보다 링크(`<a href download>`)로 열어 브라우저 다운로드에 맡기는 편이 간단해요. Blob으로 모으면 파일 크기만큼 브라우저 메모리가 다시 커져요.
- 스트리밍 다운로드는 서버가 응답을 정상으로 끝내면 잘린 파일도 완료처럼 보일 수 있어요. 끝 표시나 행 수를 서버와 맞춰 두면 확인할 수 있어요.
- 다운로드 링크의 만료 시각을 보여 주고, 지나면 다시 만들기 버튼을 열어요.
- 엑셀에서 한글이 깨지면 BOM 옵션을 서버에서 켜고 끌 수 있게 두고, 실제로 여는 프로그램에서 확인해요.

## 시뮬레이터 안내

아래 시뮬레이터에서 다음 순서로 바꿔 보세요.

1. 기본값은 10만 건, 메모리에 모아 응답, 게이트웨이 제한 30초예요. 첫 바이트가 40초 뒤에 나가서 504로 끊겨요.
2. 생성 방식을 스트리밍 응답으로 바꾸면 첫 배치 0.4초 뒤에 바이트가 나가요. 서버 메모리는 배치 하나 분량이 돼요.
3. 생성 방식을 비동기 파일 생성으로 바꾸면 202 접수는 0.2초에 끝나고, 파일은 40초 뒤에 준비돼요.
4. 셀 값을 `=1+2`로 두고 수식 주입 대응을 바꿔 보면, 보낼 CSV 필드가 어떻게 달라지는지 확인해요.

모델의 가정은 이래요. 메모리 방식은 첫 바이트를 기다리는 제한에 걸리고, 스트리밍은 바이트 사이의 공백이 제한보다 길 때만 걸린다고 봐요. 실제 게이트웨이가 어떤 시간 제한을 쓰는지는 서비스마다 달라요. 행당 처리 시간과 바이트 수는 모두 예시예요.

## 정리 — 생성 방식 · 형식 · 보안 결정

행을 전부 모아 응답하는 방식은 행 수가 늘수록 첫 바이트와 메모리가 함께 늘어서 큰 내보내기에 맞지 않아요. 응답을 바로 시작해야 하면 스트리밍으로 조각마다 써요. 파일이 크고 기다려도 되면 비동기로 만들고 만료되는 링크로 내려받아요. 형식은 RFC 4180을 따르고, 파일 이름은 filename\*로 인코딩해요. 셀 맨 앞 문자는 수식 주입을 막도록 처리하고, 권한과 감사 기록은 접수 때와 링크 발급 때 둘 다 남겨요.
