엑셀 내보내기 버튼을 누르면 프론트엔드 (FE) 화면이 로딩 상태로 멈춰 있다가 결국 타임아웃 화면을 보여 줘요. 서버가 파일을 만드는 중인지, 이미 실패했는지도 알 수 없어요. 이런 작업은 요청 하나의 응답 시간 안에 끝나지 않아요.

이 글은 FE가 오래 걸리는 요청을 어떻게 받아들이는지 정리해요. 접수 응답을 어떻게 읽고, 상태를 어떻게 조회하고, 완료 알림을 어떤 방식으로 받을지, 취소와 재시도, 결과 파일의 만료를 다뤄요. 서버 안에서 작업을 청크로 나누고 재시작 지점을 남기는 방법은 [배치 작업](/m/batch-jobs) 글에서 다뤘어요. 큐에 넣고 워커가 가져가는 구조는 [메시지 큐](/m/message-queue) 글을 보면 돼요.

## 타임아웃 증상 — 동기 요청이 게이트웨이 제한에 걸리는 순간

브라우저가 요청을 보내면 중간의 프록시나 게이트웨이가 응답을 기다려요. MDN은 504 (Gateway Timeout)을 게이트웨이나 프록시가 상위 서버에서 제때 응답을 받지 못했을 때의 상태 코드로 설명해요.

504를 받았다고 해서 서버가 실패했다는 뜻은 아니에요. 게이트웨이가 기다리기를 멈췄다는 뜻이에요. 504만으로는 뒤에서 작업이 끝났는지 알 수 없어요. 그래서 사용자가 다시 누르면 같은 작업이 한 번 더 시작될 수 있어요.

해결은 요청을 둘로 나누는 거예요. 첫 요청은 작업을 맡기고 "받았어요"만 돌려받아요. 그 뒤의 요청은 진행 상태를 짧게 조회해요. 한 번의 요청이 오래 붙잡히지 않아요.

## 접수 응답 — 202와 상태 주소로 답하기

RFC 9110은 202 (Accepted)를 요청이 처리를 위해 받아들여졌지만 처리는 끝나지 않았다는 뜻으로 정의해요. 같은 절은 이 응답을 의도적으로 결론을 미루는(noncommittal) 응답이라고 설명해요. 응답 본문은 요청의 현재 상태를 설명하고, 상태를 볼 수 있는 모니터를 가리키거나 담는 편이 좋다고 권해요.

MDN은 202 응답에는 나중에 비동기 HTTP 응답으로 처리 결과를 알릴 방법이 없다고 설명해요. 그래서 FE는 결과를 확인할 주소를 접수 응답에서 받아야 해요.

예시 응답은 이래요. 필드 이름은 설계 예시예요.

```http
HTTP/1.1 202 Accepted
Location: /exports/exp_8f2
Retry-After: 5
Content-Type: application/json

{ "id": "exp_8f2", "status": "queued" }
```

RFC 9110은 `Location`의 구체적인 뜻을 201 (Created)과 3xx 응답에 대해서만 적어요. 202에서 상태 주소를 `Location`으로 주는 방식은 RFC의 정의가 아니라 Azure 패턴이 권하는 관행이에요. Azure 패턴은 202 응답에 폴링할 주소와 간격을 담으라고 권해요.

`Retry-After`는 RFC 9110이 503과 3xx 응답에 쓰는 헤더로 정의하고, 날짜나 초 단위 숫자를 값으로 받는다고 설명해요. 202에 붙이는 것도 Azure 패턴이 권하는 방식이에요.

응답 종류별로 화면을 나눠요.

| 응답                | 뜻                               | FE 화면                                   |
| ------------------- | -------------------------------- | ----------------------------------------- |
| 201 Created         | 결과 자원이 이미 만들어졌어요    | 완료 화면으로 이동                        |
| 202 Accepted + 주소 | 접수만 됐어요                    | "요청을 받았어요. 진행 상황을 확인할게요" |
| 200 OK + 상태 본문  | 지금 상태를 알려 줘요            | 상태 값에 맞춰 문구를 바꿔요              |
| 504 Gateway Timeout | 게이트웨이가 기다리기를 멈췄어요 | 같은 작업이 있는지 먼저 확인해요          |

202에 "완료"라는 문구를 쓰면 사용자는 파일이 이미 준비됐다고 오해해요.

## 상태 머신 — queued · running · succeeded · failed · canceled 전이

Azure 패턴은 상태를 Pending, Running, Succeeded, Failed, Canceled 같은 값으로 나타내라고 예를 들어요. 이 글은 대기열에 들어간 상태를 queued라고 불러요. 실패한 작업에는 구조화된 오류 객체를 담으라고 Azure 패턴이 권해요.

| 상태      | 뜻                          | FE 화면                    | 다음 조회 |
| --------- | --------------------------- | -------------------------- | --------- |
| queued    | 접수됐고 아직 시작 전이에요 | 대기 중, 취소 가능         | 계속 조회 |
| running   | 처리 중이에요               | 진행률과 취소 버튼         | 계속 조회 |
| succeeded | 결과가 준비됐어요           | 결과 열기와 만료 시각      | 멈춤      |
| failed    | 처리가 실패로 끝났어요      | 오류 설명과 재시도         | 멈춤      |
| canceled  | 취소가 끝났어요             | 끝난 부분 표시와 다시 시작 | 멈춤      |

상태는 queued에서 running으로 가고, 그다음 succeeded나 failed로 가요. 취소는 queued나 running에서 canceled로 가요.

종료 상태 (succeeded · failed · canceled)에 들어간 뒤에는 상태가 다시 바뀌지 않아야 해요. FE가 조회를 멈추는 기준이 이 상태뿐이기 때문이에요.

## 상태 조회 — 폴링 간격과 Retry-After

Azure 패턴은 상태 조회가 성공하면 200 OK를 돌려주고, 작업이 진행 중이면 그 상태를 나타내는 리소스를 돌려준다고 설명해요. 작업이 끝나면 결과 자원으로 가는 303 See Other를 보낼 수도 있어요. Azure 패턴은 303이 원래 메서드와 상관없이 GET으로 결과를 가져오게 한다고 설명해요.

간격은 세 가지 규칙으로 정해요. 서버가 준 `Retry-After` 값이 있으면 그 값을 따르고, 없으면 지수 백오프로 간격을 늘리고, 전체 대기 시간에 상한을 둬요. 상한을 넘으면 "아직 처리 중이에요"와 나중에 다시 볼 링크를 보여 줘요.

```ts
async function waitForJob(statusUrl: string, signal: AbortSignal) {
  let delayMs = 1000;
  for (;;) {
    const res = await fetch(statusUrl, { signal });
    const job = await res.json();
    if (job.status === 'succeeded' || job.status === 'failed' || job.status === 'canceled') {
      return job;
    }
    const retryAfter = Number(res.headers.get('Retry-After'));
    delayMs = retryAfter > 0 ? retryAfter * 1000 : Math.min(delayMs * 2, 30_000);
    await new Promise((resolve) => setTimeout(resolve, delayMs));
  }
}
```

`Retry-After`가 날짜 형식이면 위 코드는 숫자로 읽히지 않아 백오프 간격을 써요. 상한을 두지 않은 예시이므로 실제 코드에는 전체 대기 시간 제한을 더해요.

조회 횟수는 작업 시간을 간격으로 나눈 올림값이에요. 예시로 45초 작업을 5초 간격으로 보면 9번 조회해요. 간격을 1초로 줄이면 45번이 돼요. 이 횟수가 사용자마다 곱해져 서버가 받는 요청 수가 돼요.

## 완료 알림 — 폴링 · 서버 전송 이벤트 (SSE) · 웹훅 · 이메일 비교

조회를 기다리지 않고 완료를 알려 받는 방법도 있어요. 서버 전송 이벤트 (SSE)는 서버가 연결을 열어 두고 이벤트를 보내는 방식이에요. MDN은 EventSource가 `text/event-stream` 형식의 이벤트를 받으려고 지속 연결을 연다고 설명해요. HTTP/2를 쓰지 않으면 브라우저당 연결 수 제한에 걸릴 수 있고, MDN은 그 값을 6으로 설명해요. SSE의 자세한 동작은 [실시간 알림](/m/realtime-delivery) 글에서 다뤘어요.

| 방식   | 결과를 받는 시점          | FE가 할 일                          | 놓쳤을 때                            | 맞는 경우                         |
| ------ | ------------------------- | ----------------------------------- | ------------------------------------ | --------------------------------- |
| 폴링   | 다음 조회 때              | 간격과 종료 조건을 구현해요         | 다음 조회에서 상태를 다시 봐요       | 짧은 작업, 화면이 열려 있을 때    |
| SSE    | 상태가 바뀌는 즉시        | 연결을 열고 이벤트를 받아요         | 재연결 뒤 상태 주소를 한 번 조회해요 | 진행률을 실시간으로 보여 줄 때    |
| 웹훅   | 서버가 알림을 받은 뒤     | FE는 직접 받지 않고 서버가 전달해요 | 서버가 다시 시도해야 해요            | 외부 시스템이 완료를 알아야 할 때 |
| 이메일 | 사용자가 메일을 여는 시점 | 화면은 없고 링크로 돌아와요         | 상태 주소로 다시 확인해요            | 화면을 닫고 오래 기다리는 작업    |

웹훅을 받는 쪽의 서명 검증과 중복 처리는 [웹훅 수신](/m/webhook-receiving) 글에서 다뤘어요.

알림은 보조 수단이에요. 알림을 받든 놓치든 상태 주소가 최종 기준이에요. 그래서 알림을 받은 뒤에도 상태를 한 번 더 조회하는 편이 안전해요.

## 취소 — 협조적 중단과 이미 끝난 부분

Azure 패턴은 상태 주소에 DELETE를 두고, 이 요청을 처리 구성 요소에 취소 지시로 넘기라고 권해요. 백엔드가 취소를 처리한 뒤 상태를 canceled로 바꿔요. 취소 요청을 보내도 서버가 멈출 때까지 상태는 바로 canceled가 되지 않아요.

그래서 FE는 취소 버튼을 누른 뒤 "취소를 요청했어요"를 보여 주고, 상태가 canceled가 되면 끝난 부분을 함께 보여 줘요. Azure 패턴은 부분 롤백이 가능한지, 보상 트랜잭션이 필요한지 미리 정하라고 권해요. 예를 들어 이미 발송된 메일은 취소로 되돌릴 수 없어요.

## 재시도 — 멱등성 키로 중복 접수 막기

Azure 패턴은 접수 요청에 `Idempotency-Key` 같은 헤더로 멱등성 키를 보내라고 권해요. 백엔드가 같은 키를 다시 받으면 두 번째 작업을 큐에 넣지 않고 기존 상태 리소스를 돌려줘요. 클라이언트는 응답이 유실됐는지 요청이 도착하지 않았는지 구별할 수 없어서 이 방식이 중요하다고 Azure 패턴은 설명해요.

504 뒤에 다시 누를 때 키를 보내지 않으면 같은 작업이 두 번 접수될 수 있어요. 키를 보내면 서버가 기존 작업을 돌려줘요. 재시도 간격은 앞의 조회와 같은 지수 백오프로 늘려요.

실패 원인이 일시적이면 같은 키로 다시 접수해요. 입력값이 잘못됐다면 새 값으로 새 작업을 만들어요.

## 결과 파일 다운로드 — 만료 시각과 다시 만들기

Azure 패턴은 상태 리소스와 저장된 결과가 저장소와 연산 자원을 쓰므로 보관 정책을 정하라고 권해요. 보관 기간은 클라이언트에 알리라고 권하고, 그 방법으로 `Expires` 헤더를 예로 들어요.

결과 파일을 직접 내려받는 주소에도 만료가 있을 수 있어요. AWS 문서는 S3 presigned URL의 만료 시간을 콘솔에서는 생성 뒤 최대 12시간, AWS CLI에서는 최대 7일로 설명해요. presigned URL 자체는 [파일 전송](/m/file-transfer) 글에서 다뤘어요.

그래서 완료 화면은 결과의 만료 시각을 보여 줘요. 만료가 지나면 다운로드 버튼 대신 "다시 만들기" 버튼을 보여 주고, 같은 작업을 새로 접수해요.

## FE 체크 포인트

- 202 응답은 "접수했어요"로 보여 주고, 결과가 준비된 뒤에만 "완료"라고 써요.
- 상태 주소를 저장해 두고, 페이지를 다시 열어도 같은 작업을 이어서 조회해요.
- `succeeded`, `failed`, `canceled`를 받으면 조회를 멈춰요.
- 504 뒤에는 바로 다시 누르지 않고, 같은 멱등성 키로 다시 접수하거나 작업 목록을 먼저 확인해요.
- 결과의 만료 시각을 보여 주고, 지나면 다시 만들기 경로를 열어요.

## 시뮬레이터 안내

아래 시뮬레이터에서 다음 순서로 바꿔 보세요.

1. 기본값에서 동기 처리는 504로 끝나요. 202 접수 방식은 조회 9번 끝에 45초에 결과를 봐요.
2. 게이트웨이 제한 시간을 60초로 올리면 동기 처리도 결과를 받아요.
3. 작업 소요 시간을 120초로 올리면 게이트웨이 제한을 60초로 두어도 동기 처리는 다시 504를 받아요. 202 접수 방식은 그대로 결과를 받아요.
4. 폴링 간격을 30초로 올리면 조회 수가 줄어요. 대신 작업이 끝난 뒤 최대 30초 늦게 결과를 봐요.

## 정리 — 접수 응답 · 상태 조회 · 알림 · 만료 기준

오래 걸리는 요청은 202로 접수하고 상태 주소로 조회해요. 상태는 정해진 순서로만 흐르고, 종료 상태에서 조회를 멈춰요. 알림은 보조 수단이고 상태 주소가 최종 기준이에요. 취소와 재시도는 멱등성 키와 함께 설계하고, 결과 파일은 만료 시각을 화면에 보여 줘요.
