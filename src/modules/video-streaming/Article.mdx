업로드한 동영상을 `video` 태그에 원본 mp4 주소로 넣으면 브라우저는 그 파일을 내려받으면서 재생해요. 데스크톱에서는 대체로 잘 돌아가요. 모바일에서 첫 화면이 늦고 중간에 자꾸 멈추는 증상은 원본 파일과 기기 네트워크가 맞지 않을 때 나와요.

이 글은 원본을 그대로 내려주는 방식의 한계부터 봐요. 그다음 트랜스코딩으로 여러 화질을 만들고, 재생 목록과 세그먼트 구조, 연결에 맞춰 화질을 고르는 적응형 비트레이트를 다뤄요. 업로드 뒤 처리 대기, 썸네일과 포스터, CDN 캐시와 서명 URL도 짧게 정리해요. 아래 시뮬레이터에서 연결과 전달 방식을 바꾸면 멈춤과 화질이 어떻게 달라지는지 볼 수 있어요.

## 증상 — 원본 mp4를 video 태그로 바로 틀 때

원본 파일의 주소를 `video` 태그의 `src`에 넣으면 브라우저는 그 파일을 기준으로 재생해요. 파일 하나가 화질 하나예요. 기기가 바뀌어도 같은 파일을 받아요.

MDN은 `preload` 속성을 어떤 데이터를 미리 불러올지에 대한 브라우저 힌트라고 설명해요. 기본값은 브라우저마다 달라요. 원본 파일이 클수록 첫 화면까지 받아야 할 양도 늘어나는 편이에요.

## 원본 그대로 내려주기 — Range 요청과 206 응답

RFC 9110은 `Range` 헤더가 붙은 GET 요청이 전체 대신 일부 범위만 요청한다고 정의해요(14.2). 범위 요청을 처리하면 서버는 206 Partial Content로 답해요(15.3.7). 서버가 범위 요청을 지원하면 `Accept-Ranges: bytes`로 알려요(14.3).

MDN도 범위 요청을 임의 접근이 가능한 미디어 플레이어가 쓰는 방식으로 소개해요. 그래서 원본 한 파일이어도 필요한 구간만 받을 수 있어요. 다만 범위 요청은 화질을 바꾸지 않아요. 구간을 나눠 받아도 파일의 비트레이트는 그대로예요.

RFC 9110은 범위 요청을 지원하는 서버도 잘못된 범위를 무시하거나 거절할 수 있다고 정해요. 요청한 범위가 파일 밖이면 416 Range Not Satisfiable로 답해요(15.5.17). 그래서 클라이언트는 응답이 206인지 확인해야 해요.

## 원본 한 파일의 한계 — 비트레이트와 네트워크 차이

원본이 8 Mbps인 영상을 예로 들어요(예시). 영상 1초를 재생하려면 8 Mbit가 필요해요. 연결이 6 Mbps면 1초 동안 6 Mbit만 와요. 받는 속도가 재생 속도보다 느리면 버퍼가 줄고, 버퍼가 비면 재생이 멈춰요.

이 계산은 원본 한 파일에서 특히 잘 드러나요. 화질을 낮출 선택지가 없으니 연결이 나빠지면 멈춤으로 나타나요. 시뮬레이터의 원본 하나 · 안정적인 연결 결과도 멈춤이 여러 번 나와요. 시뮬레이터 값은 실측이 아니라 감을 잡기 위한 예시예요.

## 트랜스코딩 — 같은 원본에서 여러 화질 만들기

트랜스코딩은 원본을 다른 비트레이트와 해상도로 다시 인코딩하는 일이에요. RFC 8216은 서버가 같은 프레젠테이션의 여러 인코딩을 Media Playlist 파일로 제공할 수 있다고 정해요(6.2.4). Apple 명세도 변형(variant)의 비트레이트는 여러 선택지 중에서 고를 수 있다고 설명해요(1.25).

여러 화질을 함께 둘 때는 조건이 있어요. RFC 8216은 Variant Stream마다 같은 내용을 담아야 하고, 같은 장면은 같은 타임스탬프를 가져야 한다고 정해요. 화질을 바꿀 때 영상이 끊기지 않게 하려는 조건이에요.

| 화질 (예시) | 비트레이트 (예시) | 쓰는 상황                                   |
| ----------- | ----------------- | ------------------------------------------- |
| 낮음        | 0.8 Mbps          | 연결이 거의 끊기는 구간이나 첫 화면         |
| 중간        | 2.5 Mbps          | 보통 모바일 연결                            |
| 높음        | 5 Mbps            | 안정적인 와이파이 연결                      |
| 원본        | 8 Mbps            | 트랜스코딩을 거치지 않은 파일 (예시 원본값) |

## 세그먼트와 재생 목록 — HLS의 m3u8과 DASH의 MPD

HLS는 재생 목록 파일 두 종류로 구조를 나눠요. 마스터 재생 목록(Master Playlist)은 Variant Stream을 `EXT-X-STREAM-INF` 태그로 나열해요. 이 태그에는 `BANDWIDTH` 속성이 있어야 해요(RFC 8216 4.3.4.2). 미디어 재생 목록(Media Playlist)은 세그먼트 하나하나의 길이를 `EXTINF`로 적어요. 세그먼트 길이는 `EXT-X-TARGETDURATION` 값을 넘으면 안 돼요.

Apple 명세는 목표 길이를 6초로 두라고 권해요(7.5). 세그먼트는 목표 길이보다 0.5초를 넘으면 안 되고(7.7), 영상 세그먼트는 IDR 프레임으로 시작해야 해요(7.4). H.264 영상의 컨테이너는 fMP4나 MPEG 전송 스트림이어야 해요(1.2).

DASH는 MPD 파일로 구조를 설명해요. DASH-IF 상호운용성 지침 V5는 MPEG DASH 명세(ISO/IEC 23009-1)에 맞춰 쓰이고, MPD 작성 지침을 따로 둬요. 아래 표는 두 방식의 파일 역할을 나란히 둔 거예요.

| 구분      | HLS                                                           | DASH                                                  |
| --------- | ------------------------------------------------------------- | ----------------------------------------------------- |
| 파일 구성 | 마스터 재생 목록(화질 목록) + 미디어 재생 목록(세그먼트 목록) | MPD 한 파일이 미디어 프레젠테이션을 설명해요          |
| 길이 정보 | `EXTINF`와 `EXT-X-TARGETDURATION`                             | 데이터와 시간 모델을 정의해요 (DASH-IF Part 2)        |
| 명세      | RFC 8216 (Apple 저작 명세 병행)                               | ISO/IEC 23009-1, DASH-IF 지침 V5 (MPD 작성은 Part 10) |

## 적응형 비트레이트 — 연결에 맞춰 화질 고르기

RFC 8216은 클라이언트가 네트워크 상태에 맞춰 Variant Stream을 바꾸라고 권해요. 다만 바꾸는 알고리즘은 이 문서의 범위 밖이라고 밝혀요. 화질을 고르는 기준은 플레이어 구현이 정하는 몫이에요.

MDN은 MSE(Media Source Extensions)가 세그먼트를 얼마나, 얼마나 자주 받을지 더 세밀하게 조절하게 해 준다고 설명해요. DASH나 HLS 같은 적응형 스트리밍 클라이언트가 그 위에 만들어질 기반이라고도 해요.

이 글의 시뮬레이터는 설명을 위해 간단한 규칙을 써요. 직전 세그먼트의 처리량을 재고, 그 80% 안에서 가장 높은 화질을 골라요. 버퍼가 6초보다 적으면 가장 낮은 화질을 골라요. 이 규칙은 HLS나 DASH의 요구 사항이 아니라 교육용 모델이에요.

처리량을 재는 시점이 늦으면 화질이 헛돌아요. 연결이 잠깐 좋아졌다가 나빠지면 화질이 바뀌는 횟수만 늘어요. 시뮬레이터에서 흔들리는 연결의 적응형 결과가 화질을 세 번 바꾸는 것도 이 때문이에요.

## 처리 대기 — 업로드 뒤 트랜스코딩 상태 보여 주기

원본 업로드가 끝나도 재생 목록과 화질별 파일은 아직 없을 수 있어요. 트랜스코딩이 끝나야 재생 목록이 생기기 때문이에요. 이 기간은 긴 작업이라서 요청 하나에 묶으면 게이트웨이 제한에 걸리기 쉬워요. [백그라운드 작업 글](/m/background-jobs)의 접수 응답(202)과 상태 주소 흐름을 그대로 써요.

FE는 처리 중이면 재생 버튼 대신 처리 중 문구를 보여 줘요. 상태 응답이 완료되고 재생 주소가 생겼을 때만 `video`의 `src`를 넣어요. 완료 전에 원본 주소로 재생을 시도하면 화면이 빈 상태로 남기 쉬워요.

## 썸네일과 포스터 — 재생 전 화면 채우기

MDN은 `poster` 속성을 영상을 내려받는 동안 보여 줄 이미지 주소라고 설명해요. 속성이 없으면 첫 프레임이 준비되기 전까지 아무것도 보이지 않고, 그다음 첫 프레임이 포스터처럼 보여요.

썸네일은 목록에서 쓰는 작은 이미지이고, 포스터는 `video` 요소 안에서 쓰는 이미지예요. 두 이미지는 같은 원본에서 만들 수 있지만 크기와 형식은 따로 정하는 편이 좋아요. 크기별 변형은 [이미지 CDN 글](/m/image-cdn)을 참고하세요.

목록에 영상이 여러 개 있으면 `preload`를 `none`이나 `metadata`로 두는 편이 좋아요. MDN은 `metadata`가 길이 같은 메타데이터만 받는다고 설명해요. `auto`는 파일 전체를 받을 수 있어서 화면에 보이지 않는 영상까지 내려받을 수 있어요.

## CDN 캐시와 서명 URL — 조각 단위로 캐시하기

CloudFront 문서는 Range GET을 이렇게 처리한다고 설명해요. 에지 캐시에 요청한 범위가 있으면 바로 그 범위를 보내요. 없으면 원본에 요청하는데, 원본이 범위 요청을 지원하면 그 범위만 받아 캐시에 저장해요. 원본이 지원하지 않으면 전체를 받아 캐시에 둬요.

세그먼트는 몇 초 분량의 작은 파일이라 캐시 단위가 작아요. 그래서 같은 화질을 여러 시청자가 받을 때 캐시를 재사용하기 쉬워요. 파일 이름에 해시를 넣고 오래 캐시하는 방법은 [이미지 CDN 글](/m/image-cdn)과 [HTTP 캐싱 글](/m/http-caching)에서 다뤄요.

CloudFront 문서는 서명 URL에 만료 날짜와 시간이 들어간다고 설명해요. 재생할 때 CloudFront는 URL의 만료 시각과 현재 시각을 비교해요. 그래서 만료 시각은 영상이 끝까지 재생될 만큼 길어야 해요. 짧은 URL로 긴 영상을 받으면 중간에 접근이 막힐 수 있어요.

## FE 체크 포인트

- 재생이 멈추면 `waiting` 이벤트가 발생해요. MDN은 일시적으로 데이터가 없어서 재생이 멈췄을 때 발생한다고 설명해요.
- `buffered`로 지금까지 받은 구간을 확인할 수 있어요. 버퍼가 얼마나 남았는지 보고 로딩 표시를 정하는 편이 좋아요.
- 이어받기 코드는 응답이 206인지, `Content-Range`가 요청한 범위와 맞는지 확인해요. 200으로 전체가 오면 기존 조각 뒤에 붙이지 않아요. [파일 전송 글](/m/file-transfer)의 Range 처리와 같은 규칙이에요.
- 재생 주소를 넣기 전에 처리 상태가 완료인지 확인해요.
- 목록에서는 `preload`를 낮추고 포스터를 같이 지정해요.

## 시뮬레이터 안내

아래 시뮬레이터에서 연결 3종과 전달 방식 3종을 바꿔 보세요. 원본 하나는 8 Mbps 한 파일이고, 고정 화질 세그먼트는 3 Mbps 6초 세그먼트예요. 적응형은 0.8 · 2.5 · 5 · 8 Mbps 중에서 골라요. 모든 수치는 예시예요. 실제 플레이어나 실제 네트워크 값이 아니에요.

표에서 5초마다 대역폭, 버퍼, 화질, 재생 상태를 볼 수 있어요. 버퍼가 0이 되는 순간 멈춤이 생기고, 버퍼가 다시 차면 재생이 이어져요.

## 정리 — 원본 전송 · 고정 화질 · 적응형 고르기

- 원본 하나는 연결과 기기가 안정적이고 화질을 하나로 정해도 될 때 골라요.
- 고정 화질 세그먼트는 연결 범위가 좁고 화질을 한 가지로 정할 수 있을 때 골라요.
- 적응형은 모바일 재생이 많을 때 골라요. 화질 목록, 재생 목록, 처리 대기 상태를 함께 설계해야 해요.
- 세그먼트 길이와 서명 URL 만료 시각은 재생 시간에 맞춰 정해요.
