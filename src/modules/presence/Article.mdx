친구 목록의 초록 점은 두 가지 실패로 틀려요. 앱을 닫았는데 점이 한참 남아 있고, 와이파이가 잠깐 끊기면 바로 꺼져요. 둘 다 서버가 "지금 접속 중인가"를 잘못 판단해서 생겨요.

이 글은 한 질문에서 출발해요. **서버는 접속 상태를 어떻게 판단해야 할까요?** 답을 찾으려면 연결 종료 이벤트가 어디까지 알려 주는지, 하트비트와 만료되는 키가 어떤 시간 차를 만드는지, 기기가 여러 개일 때 상태를 어떻게 합칠지를 차례로 봐야 해요.

글의 숫자는 설명을 위한 예시예요. 아래 시뮬레이터의 기본값과 같아요. 시뮬레이터는 120초 동안 기기 한 대 또는 두 대의 접속을 보여 주고, 실제 연결 · 서버 판단 · 화면 표시를 나란히 놓아요.

## 연결 종료 이벤트 — 종료 프레임 없는 끊김의 한계

WebSocket 연결은 종료 프레임(close frame)을 주고받으면 정상적으로 끝나요. RFC 6455는 이 종료 프레임을 연결 종료의 기본 절차로 정의해요(§5.5.1).

문제는 종료 프레임 없이 끊기는 경우예요. RFC 6455는 종료 프레임을 주고받지 않고 닫힌 연결을 종료 코드 1006 "비정상 종료"로 정의해요(§7.4.1). 전송 연결이 끊기면 종료 코드를 1006으로 본다고도 설명해요(§7.1.5).

이 말은 종료 이벤트가 정상 종료에서만 확실한 신호라는 뜻이에요. 앱 강제 종료나 와이파이 끊김에서는 종료 프레임이 오지 않을 수 있어요.

운영체제가 연결을 닫아 주면 서버가 비정상 종료(1006)로라도 알 수 있지만, 기기가 네트워크에서 그냥 사라지면 서버 쪽에는 아무 신호도 오지 않아요. 그래서 종료 이벤트는 "접속 중이 아니다"의 증거가 아니에요. "정상적으로 끝났다"는 증거일 뿐이에요.

## 접속 판단 방식 — 하트비트와 만료되는 키

종료 이벤트 대신 **하트비트**로 살아 있음을 알려 줘요. 클라이언트가 일정 간격마다 메시지를 보내고, 서버는 그때마다 키의 만료 시각을 뒤로 밀어요. 키가 만료되면 오프라인으로 봐요.

```ts
// 예시: 클라이언트가 보내는 하트비트
setInterval(() => {
  if (ws.readyState === WebSocket.OPEN) ws.send(JSON.stringify({ type: 'hb' }));
}, HB_MS);
```

이 방식에서 하트비트는 앱 메시지로 보내요. MDN은 WebSocket 인스턴스 메서드가 `close()`와 `send()`뿐이라고 정리해요. Ping 프레임은 RFC 6455에서 정의돼 있지만, 브라우저 WebSocket API로 직접 보내지는 않아요. 그래서 상태를 판단할 하트비트는 애플리케이션 메시지로 따로 둬야 해요.

서버 쪽은 Redis 같은 저장소에 만료 시간이 있는 키를 두는 방식이 자연스러워요. Redis 문서는 EXPIRE가 키의 TTL을 설정하고, 같은 키에 다시 호출하면 TTL이 새 값으로 갱신된다고 설명해요. TTL 명령은 키가 없으면 -2를 돌려줘요.

Redis는 만료된 키를 두 가지 방식으로 지워요. 키에 접근할 때 만료를 확인하는 방식과, 접근되지 않는 키를 백그라운드에서 조금씩 찾아 지우는 방식이에요. 이 때문에 키가 만료된 정확한 순간에 지워진다고 가정하면 안 돼요.

접속 여부를 만료 이벤트로 받는 방법도 있어요. 하지만 Redis keyspace notifications는 Pub/Sub 기반이라 구독자가 끊겨 있던 동안의 이벤트는 사라진다고 설명해요.

만료 이벤트도 키에 접근하거나 백그라운드에서 발견될 때 만들어져서 정확한 시각을 보장하지 않아요. 상태 판단은 키의 존재 여부를 읽는 쪽이 더 단순해요.

## 하트비트 간격과 TTL 비율 — 깜빡임 막기

하트비트 간격을 H, TTL을 T라고 해요. 키는 마지막 하트비트 뒤 T초 동안 살아 있어요. 하트비트가 T보다 자주 오면 키가 계속 살아 있어요. 하트비트가 T보다 길면 하트비트 사이에 키가 만료돼요.

| 설정           | 정상 연결 중 결과                  | 이유                                     |
| -------------- | ---------------------------------- | ---------------------------------------- |
| H 15초, T 45초 | 온라인 유지                        | 하트비트를 두 번 놓쳐도 키가 살아 있어요 |
| H 30초, T 10초 | 10~29초 사이 오프라인으로 깜빡여요 | 하트비트 사이에 키가 먼저 만료돼요       |
| H 15초, T 15초 | 하트비트 지연 한 번에 깜빡여요     | 하트비트가 조금만 늦어도 만료돼요        |

설계 판단으로는 TTL을 하트비트 간격의 여러 배로 잡아요. 예를 들어 H 15초에 T 45초처럼 세 배 정도면 하트비트 몇 번의 지연과 유실을 흡수할 수 있어요.

여러 배가 정답이라는 출처는 없어요. 네트워크 지연과 유실 정도에 맞춰 정해요.

### 표시 유예 — 짧은 끊김을 숨기는 대가

서버가 오프라인으로 판단한 뒤에도 화면에 잠시 온라인을 유지하는 시간을 표시 유예라고 불러요. 유예는 깜빡임을 줄여요. 대신 실제로 나간 사용자가 온라인으로 보이는 시간이 유예만큼 늘어요.

| 선택        | 얻는 것                      | 잃는 것                                          |
| ----------- | ---------------------------- | ------------------------------------------------ |
| 유예 없음   | 오프라인이 가장 빨리 보여요  | 짧은 끊김마다 깜빡여요                           |
| 유예 5~15초 | 짧은 끊김이 화면에 안 보여요 | 실제 종료 뒤에도 같은 시간만큼 온라인으로 보여요 |
| 유예 길게   | 긴 재연결도 흡수해요         | 상태 신뢰가 떨어져요                             |

유예는 "서버 판단"과 "화면 표시"를 나누는 설계 판단이에요. 서버 판단을 바꾸지 않고 화면에서만 기다려요.

## 짧은 끊김 — TTL 안에 묻히는 구간

와이파이가 5초 끊기는 경우를 봐요. 기기는 40초부터 신호를 못 보내고, 45초에 다시 붙어서 하트비트를 보내요. 마지막 하트비트가 35초였고 T가 10초라면 키는 45초에 만료돼요. 재연결 하트비트가 45초에 도착하면 키가 바로 되살아나요.

이 경우 서버는 한 번도 오프라인으로 보지 않아요. 실제로는 5초 동안 끊겼지만, 화면은 온라인으로 남아요. 짧은 끊김을 상태 변화로 보지 않겠다는 설계 결과예요. 시뮬레이터에서 "5초 와이파이 끊김"을 고르면 실제 연결 줄만 빈 칸이 생기고, 나머지 줄은 온라인으로 남아요.

반대로 재연결이 TTL보다 길어지면 서버가 먼저 오프라인으로 보고, 다시 붙을 때 온라인으로 돌아와요. 그 사이가 화면에 깜빡임으로 보여요. 이때 표시 유예가 깜빡임을 줄여 줘요.

## 여러 기기와 탭 — 기기마다 키

한 사용자가 휴대폰과 노트북, 탭 여러 개로 접속할 수 있어요. 키를 사용자당 하나만 두면 한 기기의 종료가 다른 기기의 상태까지 지워요.

시뮬레이터의 두 번째 기기 사건에서 기기 A가 종료하면, 사용자당 키 방식은 키를 지워요. 기기 B가 살아 있어도 서버는 잠깐 오프라인으로 봐요. 다음 하트비트가 키를 다시 만들 때까지 그 차이가 남아요.

이 차이는 하트비트 간격만큼 생겨요. 간격이 길수록 오래 틀려요.

그래서 키는 연결마다 두는 편이 좋아요. 키 이름은 사용자와 연결 id를 함께 쓰는 식으로 나눠요(예시: `presence:user:42:conn:a1`). 사용자가 온라인인지는 그 사용자의 키 중 하나라도 살아 있는지로 판단해요. 키 목록을 어떻게 모을지는 저장소 설계에 따라 달라요.

## 마지막 접속 시각 — 기록 주기

마지막 접속 시각은 키의 TTL에 담으면 안 돼요. 키는 만료되면 사라지고, 그 뒤에는 시각이 남지 않아요. 마지막 접속 시각은 키와 별도로 DB나 캐시에 기록해요.

매 하트비트마다 기록하면 쓰기가 너무 많아져요. 예를 들어 동시 접속자 10만 명이 15초마다 하트비트를 보낸다면, 기록만으로 초당 약 6,667번 쓰기가 생겨요(예시 계산).

기록 주기를 30초나 60초로 두면 쓰기가 줄어요. 대신 저장된 시각은 실제 마지막 연결보다 최대 기록 주기만큼 옛날이 될 수 있어요.

정상 종료 때는 종료 순간 한 번 더 기록해서 오차를 줄일 수 있어요. 시뮬레이터에서 강제 종료와 기록 주기를 바꾸면 "저장된 마지막 접속 오차"가 어떻게 변하는지 볼 수 있어요.

## 상태 변경 전파 — 친구 수와 보이는 목록만 구독

접속 상태가 바뀔 때마다 친구 전체에게 알리면 비용이 친구 수와 변경 수의 곱이 돼요. 예를 들어 친구 300명이 있는 사용자의 상태가 하루 20번 바뀐다면, 그 사용자 한 명에서만 6,000건이 나가요(예시 계산).

그래서 두 가지를 같이 줄여요. 화면에 보이는 친구 목록의 상태만 구독하고, 화면을 벗어나면 구독을 끊어요. 여러 변경은 짧은 시간 묶어서 한 번에 보내요. 전달 방식과 팬아웃의 자세한 비용은 [실시간 알림 — 폴링 · SSE · WebSocket](/m/realtime-delivery)과 [피드 팬아웃 — 쓰기 시점과 읽기 시점](/m/feed-fanout)에서 다뤘어요.

## 숨은 탭 — 하트비트 주기 조정

MDN의 Page Visibility API는 문서가 숨겨지면 `visibilitychange` 이벤트를 보내고, 현재 상태를 `document.visibilityState`로 알려 줘요. 숨은 탭에서 불필요한 작업을 줄일 수 있다고 설명해요.

같은 MDN 문서는 브라우저가 배경 탭의 `setTimeout()` 같은 타이머를 조절(스로틀링)한다고 설명해요. 다만 WebSocket이나 WebRTC를 쓰는 탭은 연결이 끊기지 않도록 조절되지 않는다고도 적어요. 그래서 숨은 탭에서는 타이머로 보내는 하트비트가 늦게 나갈 수 있어요.

설계로는 숨은 탭의 하트비트 주기를 보이는 탭과 다르게 두고, TTL이 그 지연을 덮을 만큼 넉넉하게 잡아요. 숨은 탭을 오프라인으로 볼지는 제품 정책이에요. 기술 문제가 아니라 사용자에게 무엇을 보여 줄지의 문제예요.

## 개인정보 — 마지막 접속 숨기기 설정

마지막 접속 시각을 숨기는 설정은 서버 응답에서 값을 빼야 해요. 화면에서만 가리면 API 응답에는 값이 그대로 남아요. 접속 여부 자체도 개인정보로 다뤄요.

이 판단은 설계 권장이에요. 응답 필드를 어떻게 빼고, 어느 권한에서 보여 줄지는 서비스 정책에 맞춰 정해요.

## FE 체크 포인트

- **네트워크 상태 API로 온라인을 판단하지 않아요.** MDN은 `navigator.onLine`이 LAN 연결도 온라인으로 볼 수 있고, Windows에서는 특정 서버 도달 여부로 정해져 방화벽이나 VPN에 따라 달라진다고 설명해요. 그래서 이 값으로 기능을 끄지 말고, 힌트로만 써요.
- **하트비트는 애플리케이션 메시지로.** 브라우저는 Ping 프레임을 직접 보내지 않으니, 상태용 하트비트는 `send()`로 보내요.
- **재연결하면 하트비트를 바로 한 번.** 끊긴 동안 키가 만료됐을 수 있어서, 다시 붙은 즉시 상태를 알려 줘야 화면이 빨리 맞아요. 재연결 간격의 백오프는 [실시간 알림 — 폴링 · SSE · WebSocket](/m/realtime-delivery)에서 다뤘어요.
- **보이는 목록만 구독.** 화면을 벗어난 친구의 상태는 받지 않아요.
- **숨은 탭은 주기를 바꾸고 기록은 유지.** 복귀할 때 상태를 한 번 다시 맞춰요.
- **읽음 위치와 혼동하지 않기.** 마지막 접속 시각은 기기 상태이고, 읽음 위치는 대화방 순번이에요. 둘은 [채팅 메시지 순서 — 서버 순번과 임시 행 교체](/m/chat-ordering)의 읽음 위치 설계처럼 따로 저장해요.

## 시뮬레이터 안내

시뮬레이터는 사건 하나를 고르고, 판단 방식과 설정을 바꿔 가며 결과를 봐요.

1. **사건 고르기**에서 정상 종료, 앱 강제 종료, 5초 와이파이 끊김, 두 번째 기기 접속 중 하나를 골라요.
2. **판단 방식**에서 하트비트 + TTL과 종료 이벤트만을 비교해요. 시뮬레이터는 강제 종료를 아무 신호 없이 끊긴 경우로 단순화해요. 그래서 종료 이벤트만이면 강제 종료 뒤 120초 안에서는 계속 온라인으로 남아요.
3. **TTL**을 하트비트 간격 이하로 두면, 정상 연결에서도 깜빡임 경고가 나와요.
4. **표시 유예**를 바꾸면 끊긴 뒤 오프라인이 보이는 시점이 늦어져요.
5. **키 단위**를 사용자당 키 하나로 바꾸고 두 번째 기기 접속을 고르면, 기기 A가 끝날 때 기기 B가 연결돼 있는데도 오프라인으로 보이는 구간이 생겨요. 표시 유예를 없음으로 두면 그 구간이 화면에 그대로 보여요.

- 종료 이벤트는 정상 종료만 알려 줘요. 강제 종료와 신호 없는 끊김은 하트비트와 만료되는 키로 판단해요.
- TTL은 하트비트 간격의 여러 배로 잡고, 표시 유예로 짧은 끊김을 화면에서 흡수해요.
- 키는 기기마다 두고, 마지막 접속 시각은 주기적으로 기록해요.
- 친구 상태는 보이는 목록만 구독해서 전파 비용을 줄여요.
