부분 환불 버튼을 만들면 프론트엔드(FE) 개발자가 먼저 걱정하는 질문이 세 가지 생겨요. 버튼을 두 번 누르면 두 번 환불되나요? 쿠폰을 쓴 주문에서 상품 하나만 취소하면 얼마를 돌려줘야 하나요? 환불 요청을 보내자마자 "환불 완료"라고 보여 줘도 되나요? 이 글은 세 질문에 대한 답을 서버 쪽에서 어떻게 정하는지 따라가요.

아래 시뮬레이터에서 쿠폰 배분과 동시 환불 두 건을 직접 돌려 볼 수 있어요. 글에서 말하는 계산과 같은 규칙을 써요.

## 환불 가능 잔액 — 결제액에서 환불 합계를 뺀 값

환불 가능 잔액은 원 결제 금액에서 이미 환불한 합계를 뺀 값이에요. 이 값을 넘는 환불은 받지 않는 것이 기본이에요.

Stripe 문서는 한 결제에 환불을 여러 번 걸 수 있지만, 환불 총액이 원래 결제 금액을 넘을 수 없다고 설명해요. 우리 서버도 같은 규칙을 적용해야 해요.

금액은 정수 원으로 저장하고 계산해요. Stripe 문서도 환불 금액을 최소 단위의 정수로 준다고 설명해요. 소수점과 반올림은 [금액 계산과 표현](/m/money-amounts) 글에서 다뤄요.

화면이 잔액을 계산해서 버튼 옆에 보여 줄 수는 있어요. 다만 최종 확인은 서버가 해요. 화면이 가진 잔액은 옛 값일 수 있어요.

## 동시 환불 한도 — 조건부 UPDATE와 행 잠금 비교

결제액 30,000원 주문에서 이미 10,000원을 환불했다고 해요. 손님이 두 탭에서 각각 15,000원과 12,000원을 요청했어요. 두 요청이 같은 옛 잔액 20,000원을 보고 시작하면 둘 다 통과해서 합계 37,000원이 나가요.

환불 한도를 쓰기 문장의 조건에 넣으면 이 틈을 막을 수 있어요. 아래 SQL은 예시 스키마예요.

```sql
UPDATE payment
SET refunded_amount = refunded_amount + $1
WHERE id = $2
  AND refunded_amount + $1 <= paid_amount;
```

PostgreSQL 문서는 UPDATE가 갱신한 행 수를 돌려준다고 설명해요. 조건에 맞는 행이 없으면 이 값이 0이에요. 앱은 0이면 한도 초과로 거절하고, 응답에 현재 환불 가능 잔액을 실어 줘요. 거부 응답의 형식은 [주문 상태 전이](/m/order-state) 글의 409 본문과 같은 방식으로 맞출 수 있어요.

읽기 커밋 격리 수준에서는 먼저 쓴 트랜잭션이 끝날 때까지 기다린 뒤 WHERE 조건을 갱신된 행에 다시 적용한다고 PostgreSQL 문서는 설명해요. 그래서 두 번째 요청은 앞선 환불이 반영된 잔액으로 판단해요.

### 대안 — 행 잠금

`SELECT ... FOR UPDATE`로 결제 행을 먼저 잠그는 방법도 있어요. PostgreSQL 문서는 이렇게 가져온 행을 다른 트랜잭션이 바꾸거나 잠그지 못하고, 현재 트랜잭션이 끝날 때까지 잠긴다고 설명해요.

이 방식에서는 외부 환불 호출을 같은 트랜잭션 안에 넣으면 락을 그 호출이 끝날 때까지 붙잡아요. 그래서 이 글에서는 한도 확인과 갱신을 한 문장으로 끝내는 조건부 UPDATE를 먼저 골라요. 이것은 설계 판단이에요. 락의 세부 동작은 [트랜잭션 · 락 · 데드락](/m/transactions) 글에서 다뤄요.

## 중복 요청 — 멱등성 키와 조건부 갱신의 역할 분담

같은 요청이 두 번 도착하는 경우와 서로 다른 두 건이 동시에 도착하는 경우는 막는 방법이 달라요. 표로 보면 이렇게 나뉘어요.

| 방어 방식   | 같은 요청 두 번 (더블 클릭) | 서로 다른 두 건이 한도를 넘는 경우 |
| ----------- | --------------------------- | ---------------------------------- |
| 방어 없음   | 두 번 환불돼요              | 한도를 넘어요                      |
| 조건부 갱신 | 한도 안이면 두 번 환불돼요  | 막아요                             |
| 멱등성 키   | 막아요                      | 한도를 넘어요                      |
| 둘 다 쓰기  | 막아요                      | 막아요                             |

멱등성 키는 같은 요청을 한 번만 처리해요. 토스페이먼츠 문서는 결제 취소 요청의 헤더에 멱등키를 추가하면 중복 취소 없이 안전하게 처리된다고 설명해요. Stripe 문서는 API v1의 모든 POST 요청이 멱등성 키를 받을 수 있고, 같은 키에 다른 파라미터를 보내면 오류를 낸다고 설명해요.

멱등성 키는 한도를 지키지 못해요. 서로 다른 두 환불은 키가 달라서 둘 다 실행돼요. 반대로 조건부 갱신은 같은 요청을 알아보지 못해요. 한도 안이면 같은 금액이 두 번 나가요.

그래서 두 방법을 같이 쓰는 편이 좋아요. 키는 같은 요청을 묶고, 조건부 갱신은 한도를 지켜요.

키를 만드는 단위도 중요해요. 화면이 누를 때마다 새 키를 만들면 더블 클릭은 막히지 않아요. 같은 환불 의도에 같은 키를 붙이는 편이 좋아요. Stripe 문서는 키를 최소 24시간이 지난 뒤 지울 수 있다고 설명해요. 재시도 기간이 그보다 길어지면 키로는 중복을 막을 수 없어요. 키 설계는 [결제 이중 결제 막기](/m/payment-idempotency) 글에서 자세히 다뤄요.

## 쿠폰 할인 배분 — 비율 · 몰아주기 · 배분 없음 비교 (예시 규칙)

상품 세 개(12,000원, 8,000원, 5,000원)에 주문 쿠폰 할인 5,000원이 적용된 주문을 예로 들어요. 결제액은 20,000원이에요. 상품 A만 취소하면 얼마를 돌려줘야 할까요? 답은 배분 방식에 따라 달라져요.

| 방식             | 상품 A에 배분된 할인 | 상품 A 환불액 | 주의                                          |
| ---------------- | -------------------- | ------------- | --------------------------------------------- |
| 비율 배분        | 2,400원              | 9,600원       | 나눗셈 끝수가 생겨요                          |
| 첫 상품 몰아주기 | 5,000원              | 7,000원       | 할인이 몰린 줄을 취소하면 환불이 줄어요       |
| 배분 없음        | 0원                  | 12,000원      | 전체 취소 환불이 결제액보다 할인액만큼 많아요 |

비율 배분에서는 줄 금액 비율대로 할인을 나눠요. 몫은 내림하고, 남은 끝수는 금액이 큰 줄부터 1원씩 주는 규칙을 예시로 써요. 이 규칙은 예시 규칙이에요. 회사 정책은 따로 정해야 해요.

몫을 줄마다 반올림만 하면 합계가 할인액과 맞지 않을 수 있어요. 예를 들어 할인 1,000원을 세 줄(1,000원씩)에 나누면 333원씩 999원이 돼요. 1원이 모자라요. 끝수를 정하지 않으면 전체 취소 때 결제액과 1원이 어긋나요. 반올림 순서는 [금액 계산과 표현](/m/money-amounts) 글의 할인과 세금 배분 항목에서 다뤄요.

배분 없음은 줄 계산을 없애요. 하지만 전체 취소 환불 합계가 결제액보다 할인액만큼 커져요. 주문 쿠폰을 환불할 때 되돌릴지도 따로 정해야 해요. 쿠폰 쪽 판단은 [쿠폰 사용과 중복 방지](/m/coupon-redemption) 글의 환불 항목을 함께 봐요.

## 부분 환불 여러 번 — 환불 행 기록과 잔액 열

한 결제를 여러 번 나눠 환불하는 경우가 흔해요. Stripe 문서도 한 결제에 환불을 여러 번 걸 수 있다고 설명해요. 그래서 환불 한 건을 행 하나로 남기는 편이 추적하기 쉬워요.

- 환불 행에는 누가, 언제, 어떤 상품을, 얼마나 환불했는지 남겨요.
- 결제 행의 환불 합계 열은 잔액을 빠르게 확인하는 값으로 둬요.
- 행 추가와 합계 갱신은 같은 트랜잭션에서 함께 해요.

진행 중인 환불을 잔액에서 미리 빼 두는 방법도 있어요. 그러면 `pending` 환불이 실패했을 때 다시 더해 줘야 해요. 이 방식은 설계 판단이에요. 실패 뒤 되돌리는 흐름은 아래 환불 실패 처리 항목에서 다뤄요.

## 비동기 환불 상태 — 접수 · 처리 중 · 최종 상태 구분

환불은 요청을 보낸 순간에 끝나지 않아요. Stripe 문서는 환불 상태로 `requires_action`, `pending`, `succeeded`, `failed`, `canceled`를 나열해요. 우리 서비스는 `pending`, `succeeded`, `failed` 세 가지를 중심으로 쓰고, 취소된 환불은 `canceled`로 따로 둬요.

| 상태        | 뜻                                                       | 화면 문구 예시                             |
| ----------- | -------------------------------------------------------- | ------------------------------------------ |
| `pending`   | 환불을 시작했고 결과를 기다려요                          | 환불을 접수했어요                          |
| `succeeded` | 환불이 성공했어요. 고객 계좌에 보이는 시점은 따로 있어요 | 환불이 완료됐어요. 반영까지 걸릴 수 있어요 |
| `failed`    | 환불이 실패했어요                                        | 환불이 실패했어요. 다음 행동을 안내해요    |
| `canceled`  | 환불이 취소됐어요                                        | 환불이 취소됐어요                          |

Stripe 문서는 카드 환불이 잔액 부족으로 `pending`에 머물 수 있다고 설명해요. 또 고객이 환불을 카드에서 확인하는 시점은 은행에 따라 약 5~10 영업일 뒤라고 영문 문서가 설명해요. `succeeded`는 고객 계좌에 도착할 것으로 예상된다는 뜻이에요. 고객이 보는 시점과 구분해야 해요.

요청 직후에는 접수 상태만 보여 줘요. "환불 완료"는 최종 상태를 받은 뒤에만 써요. Stripe 문서는 환불이 실패하면 `refund.failed` 이벤트를 보낸다고 설명해요. 최종 상태는 웹훅으로 받고, 놓쳤을 때는 조회로 맞춰요. 수신 방법은 [웹훅 수신](/m/webhook-receiving) 글에서 다뤄요.

## 주문 상태와 환불 상태 — 두 상태를 나누는 이유

주문이 "취소"가 되어도 환불은 아직 실패하거나 진행 중일 수 있어요. 주문 상태와 환불 상태를 한 칸에 섞으면 두 흐름의 판단이 서로 막혀요. 그래서 환불 상태는 환불 행이 따로 가지고, 주문 상태 전이는 [주문 상태 전이](/m/order-state) 글의 규칙을 따르는 편이 좋아요.

## 환불 실패 처리 — 재시도할 실패와 알릴 실패 구분

실패는 세 가지로 나눠 보면 처리가 쉬워져요.

| 실패 상황                               | 처리                                                                     |
| --------------------------------------- | ------------------------------------------------------------------------ |
| 응답을 받지 못함 (시간 초과 · 네트워크) | 같은 멱등성 키로 다시 보내요. 키가 같으면 중복 환불이 생기지 않아요      |
| 카드 잔액 부족으로 보류                 | `pending`으로 두고 기다려요. 최종 결과는 웹훅으로 받아요                 |
| 명확한 거절 (failed)                    | 다시 보내지 않아요. 실패를 기록하고 손님에게 알리고 다음 행동을 안내해요 |

응답을 받지 못한 경우가 가장 까다로워요. 서버가 환불을 처리했는지 알 수 없기 때문이에요. 이때 같은 키로 재시도하면 중복 환불 없이 결과만 다시 받을 수 있어요. 키를 새로 만들면 두 번 환불될 수 있어요.

환불이 실패한 뒤 주문 상태를 먼저 바꿨다면 되돌리는 보상 작업이 필요해요. 여러 단계에 걸친 되돌림은 [사가와 보상 작업](/m/saga-compensation) 글에서 다뤄요.

## FE 체크 포인트

**요청 중에는 버튼을 잠가요.** 응답을 받기 전까지 버튼을 비활성화하고, 같은 환불 의도에 같은 키를 붙여요. 응답이 늦어도 재전송이 안전해요.

**응답의 잔액으로 입력을 제한해요.** 환불 금액 입력의 최댓값을 응답의 환불 가능 잔액으로 맞춰요. 화면의 제한은 편의예요. 최종 판단은 서버가 해요.

**"환불 완료" 대신 접수 상태를 보여 줘요.** 요청 직후에는 `pending`이에요. 최종 상태는 웹훅이나 조회 결과가 바꿔 줄 때 화면에 반영해요.

**금액은 정수 원으로 받고 표시만 포맷해요.** 상품별 환불액을 보여 줄 때 합계가 결제액과 맞는지도 화면에서 확인해요.

**실패는 다음 행동과 함께 보여 줘요.** "환불이 실패했어요"만 보이면 손님이 할 일을 몰라요. 재시도 버튼이나 문의 안내를 같이 보여 주세요.

## 시뮬레이터 안내

시뮬레이터는 두 부분이에요. 위쪽에서는 상품 금액 세 개와 주문 쿠폰 할인을 정하고 배분 방식을 골라요. 상품별 환불액, 끝수 처리 결과, 전체 취소 때 결제액을 넘는 금액을 볼 수 있어요.

아래쪽에서는 이미 환불한 금액과 두 요청의 환불액을 정하고 방어 방식을 골라요. 같은 요청을 두 번 보내는 경우도 골라 볼 수 있어요. 누적 환불이 결제액을 넘는지 확인해 보세요.

수치는 감을 잡기 위한 예시예요.

## 정리 — 잔액 확인 · 조건부 갱신 · 멱등성 키 · 배분 규칙 · 비동기 상태

환불 가능 잔액은 서버가 계산하고, 조건부 갱신으로 한도를 지켜요. 같은 요청은 멱등성 키로 묶고, 서로 다른 요청은 조건부 갱신으로 걸러요. 쿠폰 배분은 회사 정책으로 정하고, 끝수 규칙은 문서에 남겨요. 환불은 요청 시점에 끝나지 않으니 `pending`을 데이터와 화면에 함께 두어요.
