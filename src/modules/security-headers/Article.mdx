배포 뒤에 인라인 스크립트와 외부 분석 스크립트가 CSP 위반으로 막히는 일이 흔해요. 로컬에서는 잘 돌던 코드인데 서버 응답 헤더 하나가 바뀌면서 실행이 멈춰요. 이 글은 그 헤더들이 무엇을 막는지, 각 헤더가 FE 코드의 어떤 동작을 바꾸는지 차례로 나눠 봐요.

아래 시뮬레이터에서 정책 문자열과 응답 헤더를 바꾸면, 페이지가 로드하려는 자원마다 허용 · 차단 · 보고만 중 무엇인지와 그 이유가 보여요. 규칙은 MDN 헤더 문서와 W3C CSP Level 3, RFC 6797을 따라요.

## CSP — 스크립트와 자원 출처를 정하는 정책

콘텐츠 보안 정책 (Content Security Policy, CSP)은 페이지가 어떤 출처의 스크립트, 이미지, 요청을 쓸 수 있는지 정하는 응답 헤더예요. OWASP는 CSP가 XSS 같은 공격을 감지하고 줄이는 데 도움을 준다고 설명해요. 정책은 `Content-Security-Policy: script-src 'self'`처럼 지시문 이름과 허용 목록으로 이루어져요.

중요한 점은 CSP가 서버를 막는 것이 아니라 **브라우저가 자원을 실행하거나 불러오는 것**을 막는다는 거예요. 그래서 서버 로그에는 아무 문제가 없어 보여도, 페이지에서는 스크립트가 실행되지 않아요.

### 인라인 스크립트 — nonce와 해시로 허용

`<script>` 태그 안에 쓴 코드를 인라인 스크립트라고 해요. MDN은 `script-src`가 없거나 `unsafe-inline`, 맞는 nonce, 맞는 해시 가운데 하나가 있어야 인라인 스크립트가 실행된다고 설명해요. 셋 가운데 하나도 없으면 막혀요.

nonce (한 번만 쓰는 값)는 스크립트 태그에 붙이는 무작위 값이에요. MDN은 nonce를 HTTP 요청마다 새로 만들어야 한다고 설명해요. 같은 nonce를 헤더와 태그에 같이 넣어야 해요. 값을 고정하면 공격자가 미리 알아낼 수 있어서 이 요구가 있어요.

해시는 인라인 스크립트 본문의 SHA-256 같은 값이에요. MDN은 해시를 만들 때 `<script>` 태그를 빼고, 대소문자와 앞뒤 공백까지 본문과 똑같이 계산해야 한다고 설명해요. 본문이 한 글자라도 바뀌면 해시가 맞지 않아 막혀요.

| 방식            | 서버가 하는 일                          | FE가 바꿔야 하는 것                     | 주의                                       |
| --------------- | --------------------------------------- | --------------------------------------- | ------------------------------------------ |
| nonce           | 요청마다 새 값을 헤더와 템플릿에 넣어요 | 인라인 스크립트 태그에 같은 값을 붙여요 | 템플릿 엔진이 값을 빠뜨리면 막혀요         |
| 해시            | 본문의 해시를 미리 계산해 헤더에 넣어요 | 본문을 고치면 해시도 다시 계산해요      | 본문이 바뀔 때마다 배포 절차에 넣어야 해요 |
| `unsafe-inline` | 아무 인라인 스크립트나 허용해요         | 바꿀 것이 없어요                        | MDN은 보안 위험으로 봐요                   |

MDN은 모든 인라인 스크립트를 허용하는 `unsafe-inline`이 보안 위험이라서, nonce나 해시를 쓰는 편을 권한다고 설명해요. 그래서 이 모듈의 시뮬레이터 기본값은 nonce와 해시를 쓰는 정책이에요.

### `'unsafe-inline'` — nonce나 해시가 있으면 무시

정책에 nonce나 해시가 함께 있으면 `'unsafe-inline'`은 무시돼요. MDN은 지시문에 nonce와 `unsafe-inline`이 함께 있으면 브라우저가 `unsafe-inline`을 무시한다고 설명해요. 해시도 같은 규칙이에요.

그래서 "정책에 `'unsafe-inline'`을 넣었는데도 막혀요"라는 상황이 생겨요. 예전 설정을 남긴 채 nonce만 추가한 정책이 대표적이에요. 이때는 `'unsafe-inline'`을 지우는 편이 맞아요. 문자열에 두 방식이 섞여 있으면 어느 쪽이 적용되는지 헷갈리기 때문이에요.

### Report-Only — 막기 전에 위반만 모으기

`Content-Security-Policy-Report-Only` 헤더는 정책을 강제하지 않고 위반만 보고해요. MDN은 이 헤더가 정책을 강제하지 않고 위반을 모니터링하게 해 준다고 설명해요. 보고를 받으려면 `report-to` 지시문이 있어야 해요. 없으면 아무 일도 일어나지 않아요. 보고를 받을 주소는 `Reporting-Endpoints` 헤더로 정해요.

새 정책을 바로 `Content-Security-Policy`로 보내면 실제 사용자 화면에서 스크립트가 멈출 수 있어요. MDN은 이 헤더가 정책을 적용하기 전에 위반을 테스트하고 고치게 해 준다고 설명해요. 그래서 먼저 Report-Only로 보내 위반 목록을 모으고, 목록에 맞춰 정책을 고친 뒤 강제 헤더로 바꾸는 순서가 안전해요. 시뮬레이터의 Report-Only 체크를 켜면 같은 자원이 "막힘" 대신 "보고만"으로 바뀌는 것을 볼 수 있어요.

## 자원 출처 — 지시문이 없을 때 넘어가는 규칙

정책에 지시문이 모두 있는 것은 아니에요. MDN은 `default-src`가 다른 fetch 지시문의 대체값이라고 설명해요. 또 `script-src`는 `script-src-elem`의 대체값이고, `img-src`가 없으면 `default-src`를 따른다고 설명해요.

이 규칙 때문에 FE가 놓치기 쉬운 상황이 생겨요. `default-src 'self'` 하나만 있는 정책에서는 이미지 CDN 주소도 막혀요. 이미지 CDN을 새로 쓰면서 `img-src`를 추가하지 않으면 그 이미지는 CSP에 막혀요. `fetch`로 분석 이벤트를 보내는 코드도 `connect-src`가 없으면 `default-src`를 따라 막혀요.

다만 CSP 지시문 이름은 요청 종류별로 나뉘어 있어서, 어떤 지시문을 고쳐야 하는지는 콘솔 오류에 적힌 이름으로 찾아야 해요. 이름을 모르면 기본 정책을 넓히기보다 해당 요청의 종류를 먼저 확인하는 편이 좋아요.

## frame-ancestors와 X-Frame-Options — 삽입 허락 우선순위

다른 사이트가 이 페이지를 `<iframe>`에 넣을 수 있는지는 두 헤더가 정해요. 하나는 CSP의 `frame-ancestors`이고, 다른 하나는 `X-Frame-Options`예요. MDN은 `X-Frame-Options: DENY`가 어떤 프레임에도 로드되지 않게 하고, `SAMEORIGIN`은 모든 상위 프레임이 같은 출처일 때만 허용한다고 설명해요.

두 헤더가 함께 오면 우선순위가 있어요. W3C CSP Level 3은 `frame-ancestors`가 강제 모드(enforce)일 때 `X-Frame-Options` 헤더를 무시한다고 정해요. Report-Only의 `frame-ancestors`는 이 규칙을 발동시키지 않아요. MDN도 `frame-ancestors`가 더 세밀한 제어를 준다고 설명해요.

| 헤더              | 허용 범위                         | 설정 위치            | 주의                                              |
| ----------------- | --------------------------------- | -------------------- | ------------------------------------------------- |
| `frame-ancestors` | 출처 목록으로 지정해요            | 응답 헤더만 가능해요 | `<meta>`에 넣으면 무시돼요 (CSP3)                 |
| `X-Frame-Options` | `DENY` 또는 `SAMEORIGIN`만 있어요 | 응답 헤더만 가능해요 | `frame-ancestors`가 있으면 강제 모드에서 무시돼요 |

FE 관점에서는 파트너 사이트가 결제창이나 위젯을 iframe으로 넣어야 할 때 이 헤더가 막는 것을 보게 돼요. 그때는 `frame-ancestors`에 파트너 출처를 넣는 것이 설계 판단이에요. 반대로 로그인 화면이나 결제 확인 화면은 삽입을 막아 클릭재킹을 줄이는 편이 좋아요. OWASP도 `frame-ancestors`를 먼저 쓰고, 안 되면 `X-Frame-Options: DENY`를 쓰라고 권해요.

## X-Content-Type-Options — 스크립트 MIME 검사

`X-Content-Type-Options: nosniff`는 브라우저가 `Content-Type`을 무시하고 내용으로 타입을 추측하지 못하게 해요. MDN은 이 헤더가 `Content-Type`을 그대로 따르게 하고, 스크립트 요청에서 MIME 타입이 자바스크립트가 아니면 실행하지 않는다고 설명해요.

FE에서 보는 장면은 이래요. 예전 빌드 파일이 CDN에서 `text/plain`으로 나가면, `nosniff`가 있는 페이지는 그 파일을 실행하지 않아요. 파일은 받았는데 실행이 안 되니 원인이 헷갈릴 수 있어요. 네트워크 탭에서 응답의 `Content-Type`을 확인하는 것이 출발점이에요.

## Strict-Transport-Security — https 강제 범위

HTTP 엄격한 전송 보안 (HSTS)은 브라우저에게 이 호스트에 HTTPS로만 접속하도록 기억하게 하는 헤더예요. RFC 6797은 HTTP로 받은 응답의 HSTS 헤더를 브라우저가 무시해야 한다고 정해요. 그래서 HSTS는 HTTPS 응답으로만 보내야 해요.

`max-age`는 기억할 시간을 초 단위로 정해요. `includeSubDomains`가 있으면 같은 규칙이 서브도메인에도 적용돼요. MDN은 `preload`를 쓰려면 `max-age`가 31536000초(1년) 이상이고 `includeSubDomains`도 있어야 한다고 설명해요. OWASP는 `max-age=63072000; includeSubDomains; preload` 형태를 예로 들면서, 잘못 설정하면 정상 사용자도 접속하지 못할 수 있으니 동작을 먼저 읽어 보라고 설명해요.

FE가 직접 HSTS를 설정하는 일은 드물어요. 하지만 `includeSubDomains`를 켜면 API 서브도메인이 HTTPS만 쓰게 되어, 그 서브도메인에 HTTP 인증서나 HTTP 전용 서비스가 남아 있으면 영향을 받아요. 시뮬레이터에서 `api.shop.example`을 http로 요청할 때 헤더 옵션에 따라 결과가 어떻게 갈리는지 보세요.

## Referrer-Policy — 교차 출처 요청의 Referer 값

`Referrer-Policy`는 요청에 실리는 `Referer` 값의 범위를 정해요. MDN은 현재 브라우저의 기본값이 `strict-origin-when-cross-origin`이라고 설명해요. 이 값에서 같은 출처 요청은 전체 주소를 보내고, 교차 출처 요청은 출처만 보내요.

| 값                                | 교차 출처 요청에 보내는 Referer (https → https)      |
| --------------------------------- | ---------------------------------------------------- |
| `no-referrer`                     | 보내지 않아요                                        |
| `origin`                          | 출처만 보내요 (`https://shop.example/`)              |
| `same-origin`                     | 보내지 않아요. 같은 출처 요청에만 전체 주소를 보내요 |
| `strict-origin-when-cross-origin` | 출처만 보내요. 기본값이에요                          |
| `unsafe-url`                      | 경로와 쿼리까지 보내요                               |

FE에서 중요한 점은 URL 쿼리에 토큰이나 쿠폰 코드를 넣어 둔 화면이에요. `unsafe-url`이면 그 값이 분석 서버로 나갈 수 있어요. 기본값을 유지하면 쿼리는 빠지고 출처만 나가요. 값을 바꾸는 결정은 개인정보와 분석 요구를 같이 보고 내려야 해요.

## 헤더 설계 — 막는 대상과 FE 동작 비교

| 헤더                                  | 막는 대상                              | FE 코드에서 보이는 증상                    |
| ------------------------------------- | -------------------------------------- | ------------------------------------------ |
| `Content-Security-Policy`             | 허용 목록 밖의 스크립트, 이미지, fetch | 인라인 스크립트 미실행, 외부 스크립트 차단 |
| `frame-ancestors` / `X-Frame-Options` | 다른 사이트의 iframe 삽입              | 파트너 위젯이 빈 칸으로 보임               |
| `X-Content-Type-Options`              | MIME 타입이 맞지 않는 스크립트         | 파일은 받았는데 실행되지 않음              |
| `Strict-Transport-Security`           | HTTP로 가는 요청                       | http 주소가 https로 바뀌어 요청됨          |
| `Referrer-Policy`                     | 요청에 실리는 Referer 범위             | 분석 서버가 받는 페이지 주소가 달라짐      |

이 표를 보면 헤더 하나가 한 종류의 동작만 바꾼다는 것을 알 수 있어요. CSP는 자원 로딩과 실행을, 삽입 헤더는 iframe 생성을, HSTS는 주소 체계를, Referrer-Policy는 요청 메타데이터를 바꿔요.

## FE 체크 포인트

**콘솔의 CSP 문구에서 지시문 이름부터 봐요.** 문구에 `script-src`나 `img-src` 같은 이름이 있으면 그 지시문의 허용 목록에 무엇이 빠졌는지 확인해요. 브라우저마다 문구가 달라서, 이름을 찾는 것이 첫 단계예요.

**인라인 스크립트가 필요한지부터 물어요.** 번들러가 만든 작은 인라인 스크립트가 있다면 nonce를 붙일지, 해시를 쓸지 정해야 해요. 해시는 본문이 바뀔 때마다 다시 계산해야 하니, 배포 파이프라인에 넣을 수 있는지 함께 봐요.

**새 외부 스크립트를 넣을 때 정책 변경이 함께 가야 해요.** 분석 도구를 추가하면 `script-src`와 `connect-src`에 호스트를 같이 넣어요. 한쪽만 넣으면 스크립트는 로드되는데 이벤트 전송이 막히는 식으로 어긋나요.

**새 정책은 Report-Only로 먼저 보내요.** 배포 전에 위반 목록을 모으고, 목록이 비면 강제 헤더로 바꿔요. 실제 사용자가 막힌 뒤에 알게 되는 일을 줄이는 방법이에요.

**CORS와 헷갈리지 않아요.** CSP는 페이지가 자원을 불러오고 실행하는 것을 정하고, CORS는 다른 출처 응답을 JS가 읽는 것을 정해요. 둘은 서로 다른 헤더예요. 응답 읽기 실패는 [CORS와 교차 출처 요청 모듈](/m/cors)에서, 쿠키 인증과 CSRF는 [인증 세션 · 토큰 모듈](/m/auth-session-token)에서 따로 다뤄요.

## 시뮬레이터 안내 — 정책 문자열과 자원 판정

시뮬레이터는 CSP 정책 문자열, Report-Only 여부, 나머지 보안 헤더, 페이지가 로드하려는 자원 목록을 받아요. 기본값은 nonce와 해시를 쓰는 정책이에요. 이때 nonce가 없는 인라인 스크립트, 외부 분석 스크립트, 분석 이벤트 전송, 파트너 iframe 삽입이 막혀요.

세 가지를 순서대로 바꿔 보세요. 먼저 "`'unsafe-inline'` 허용 (예전 방식)" 프리셋을 고르면 인라인과 외부 분석 스크립트가 통과해요. 다음으로 Report-Only를 켜면 같은 자원이 막히지 않고 "보고만"으로 바뀌어요. 마지막으로 HSTS를 켜고 다음 요청을 `http://api.shop.example/api/cart`로 바꾸면, includeSubDomains가 있을 때만 https로 바뀌는 것을 볼 수 있어요.

이 시뮬레이터는 규칙만 옮긴 모델이에요. 페이지 안의 다른 자원, `strict-dynamic` 같은 지시문, 브라우저별 세부 동작은 계산하지 않아요.

## 정리 — 정책 방식과 헤더 배포 순서

인라인 스크립트는 nonce나 해시 가운데 하나로 허용하는 편이 좋아요. 정책에 nonce나 해시가 있으면 `'unsafe-inline'`은 무시되니 문자열에서 지우는 편이 맞아요.

새 정책은 Report-Only로 먼저 보내 위반을 모은 뒤 강제 헤더로 바꿔요. 삽입 허락은 `frame-ancestors`로 정하고, `X-Frame-Options`는 오래된 브라우저를 위한 보조로만 둬요.

HSTS는 HTTPS 응답에만 보내고, `includeSubDomains`는 서브도메인이 모두 HTTPS를 쓰는지 확인한 뒤 켜요. Referrer-Policy는 기본값을 유지하고, 쿼리에 민감한 값이 있는 화면만 따로 검토해요.
