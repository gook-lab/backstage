관리자 대시보드의 차트는 점 90개만 그리면 돼요. 그런데 서버가 주문 테이블을 열 때마다 전부 훑으면 응답이 10초씩 걸리기도 해요(예시). 예를 들어 주문이 하루 5만 건이면 90일치 원본은 450만 행이에요(예시). 차트 한 번에 450만 행을 읽고 세서 숫자 90개를 만드는 셈이에요.

이 글은 그 계산을 언제 미리 해 두고, 무엇을 틀리지 않게 맞출지 다뤄요. 아래 시뮬레이터에서 기간, 버킷, 시간대, 집계 방식을 바꿔 보면 점 개수와 읽은 행 수가 어떻게 달라지는지 확인할 수 있어요.

## 증상 — 점 90개를 위해 원본 행을 전부 읽는 응답

FE에서는 차트 API가 느리다고만 보여요. 그런데 응답 본문은 점 90개 정도로 작아요. 본문이 작은데 응답이 느리다면, 시간은 전송이 아니라 DB가 원본 행을 읽고 묶는 데 쓰였을 가능성이 커요.

## 매번 원본 집계 — 읽는 행이 기간에 비례해요

가장 단순한 방법은 요청이 올 때마다 주문 테이블을 묶는 거예요.

```sql
SELECT date_trunc('day', occurred_at AT TIME ZONE 'Asia/Seoul') AS day,
       sum(amount) AS total
FROM orders
WHERE occurred_at >= now() - interval '90 days'
GROUP BY 1
ORDER BY 1;
```

이 쿼리는 조건에 맞는 주문 행을 전부 읽고, 날짜별로 묶어서 합해요. 기간이 두 배가 되면 읽는 행도 대략 두 배가 돼요. 같은 차트를 여러 사람이 열면 같은 원본을 여러 번 읽어요.

PostgreSQL 문서는 `date_trunc`가 지정한 단위보다 작은 필드를 0으로 맞춰서 시각을 잘라낸다고 설명해요. 그래서 하루 단위로 자르면 그날 0시가 나와요.

## 시간 버킷 — 시 · 일 · 주 고르기

버킷 크기는 점 개수와 읽기 비용을 같이 정해요. 점 개수는 기간을 버킷 크기로 나눈 값이에요.

| 버킷 | 90일 기준 점 개수 (예시) | 어울리는 질문               |
| ---- | ------------------------ | --------------------------- |
| 시   | 2,160                    | 하루 안의 추이, 장애 시간대 |
| 일   | 90                       | 최근 석 달 매출 추이        |
| 주   | 13                       | 분기 흐름, 장기 비교        |

점이 수천 개를 넘으면 화면에서 추이가 읽히지 않고 응답도 커져요. 큰 기간에 작은 버킷을 고르면 DB가 읽을 행 수도 함께 늘어나요.

PostgreSQL 문서는 `date_bin`이 간격과 기준점(origin)으로 입력을 묶는다고 설명해요. 같은 문서는 `date_bin`의 간격에 월 단위가 들어갈 수 없다고 설명해요. 그래서 월별 버킷은 `date_trunc`로 따로 다루는 편이 좋아요.

## 시간대 경계 — 어느 시간대의 자정인가

서울에서 3월 10일 0시 30분에 일어난 주문은 UTC로는 3월 9일 15시 30분이에요. 기준이 UTC 면 3월 9일 버킷에, 서울이면 3월 10일 버킷에 들어가요. 같은 주문이 두 차트에서 다른 날짜가 되는 셈이에요.

PostgreSQL 문서는 `date_trunc`에 시간대를 넘기면 그 시간대 기준으로 자른다고 설명해요. 문서 예시는 Australia/Sydney 기준으로 하루를 자르면 UTC로 13시가 나오는 경우를 보여 줘요. 같은 문서는 `timestamp with time zone` 값에 `AT TIME ZONE`을 붙이면 그 시간대의 벽시계 시각(시간대 없는 값)으로 바뀐다고 설명해요. 위 쿼리의 `occurred_at`이 이 형식이라면 서울 벽시계 시각으로 바꾼 뒤 날짜를 자르는 셈이에요.

MDN은 `Intl.DateTimeFormat`의 `timeZone`에 `America/New_York` 같은 IANA 시간대 이름을 쓸 수 있고, 생략하면 실행 환경의 시간대를 쓴다고 설명해요. 집계 기준을 실행 환경에 맡기면 서버를 옮길 때마다 날짜가 바뀔 수 있어요. 기준 시간대는 요청 파라미터로 받고, 응답에도 적어 둬요.

TimescaleDB 문서는 `time_bucket`이 기본으로 UTC 자정에 맞춘다고 설명해요. `timezone` 인자를 주면 버킷을 그 시간대의 자정에 다시 맞춘다고 설명해요. 같은 문서는 서머타임 전환일에 버킷에 들어가는 데이터 양이 불규칙해질 수 있다고 설명해요.

집계 날짜 기준을 어느 쪽에 둘지는 [날짜 · 시간대 · 다국어](/m/time-and-locale) 글에서 더 다뤄요.

## 미리 집계 — 롤업 테이블과 materialized view 비교

원본을 매번 세지 않으려면 날짜별 합계를 미리 저장해 둬요. 방법은 네 가지예요.

| 방법                               | 갱신하는 주체        | 장점                               | 주의                               |
| ---------------------------------- | -------------------- | ---------------------------------- | ---------------------------------- |
| 매번 원본                          | 없음                 | 읽는 시점의 원본 기준              | 읽는 행이 기간에 비례해요          |
| 일별 롤업 테이블                   | 직접 만든 배치 작업  | 응답이 날 수에 비례해요            | 갱신 뒤에 도착한 데이터가 빠져요   |
| materialized view                  | `REFRESH` 명령       | 정의한 쿼리를 기억해서 다시 채워요 | `REFRESH`는 내용을 전부 다시 써요  |
| continuous aggregate (TimescaleDB) | 정책(refresh policy) | 새 데이터를 점진적으로 반영해요    | TimescaleDB 기능이라 DB가 달라져요 |

PostgreSQL 문서는 `CREATE MATERIALIZED VIEW`가 `CREATE TABLE AS`와 비슷하지만, 쿼리를 기억해서 나중에 `REFRESH`할 수 있다고 설명해요. `REFRESH MATERIALIZED VIEW`는 내용을 전부 바꿔 써요. `CONCURRENTLY`를 붙이면 읽기를 막지 않는다고 같은 문서가 설명해요. 다만 유일 인덱스가 있어야 하고, 한 번에 한 번만 `REFRESH`가 돌 수 있어요.

TimescaleDB 문서는 materialized view가 정기적으로 갱신되지 않고, continuous aggregate는 백그라운드에서 점진적으로 갱신된다고 설명해요. 롤업 테이블을 직접 만들면 쓰기 경로가 하나 더 생겨요. 주문 취소와 환불이 들어오면 빼는 로직도 필요해요.

## 갱신 주기 — 끝난 날만 미리 집계하기

롤업은 끝난 날만 담는 편이 간단해요. 날이 끝나면 값이 바뀌지 않는다고 가정할 수 있기 때문이에요. 이 가정이 깨지는 곳이 늦은 데이터예요.

예를 들어 매일 0시 10분에 어제까지를 롤업한다고 해요(예시). 0시 10분 뒤에 도착한 어제 주문은 롤업에 없어요. 시뮬레이터의 `일별 롤업`이 이 상황이에요. 배치가 실패했을 때 재시도와 중복 실행을 막는 방법은 [배치 작업](/m/batch-jobs) 글에서 다뤄요.

## 늦은 데이터와 오늘 버킷 — 재계산 구간 두기

두 종류를 나눠서 봐요. 오늘 버킷은 아직 끝나지 않아서 계속 바뀌어요. 어제 이전 버킷은 늦게 도착한 데이터로 바뀔 수 있어요.

TimescaleDB 문서는 refresh 정책의 `end_offset`이 현재 버킷 안에 있으면 그 버킷을 물질화에서 뺀다고 설명해요. 이유로 현재 버킷은 불완전하고, 쓰기가 많아서 금방 옛 값이 된다는 점을 들어요. 오늘 버킷을 원본으로 읽는 설계는 이 이유를 그대로 따르는 거예요.

늦은 데이터는 `start_offset`으로 다뤄요. 같은 문서는 `start_offset`이 정책이 실행되는 시점을 기준으로 갱신 구간의 시작을 정한다고 설명해요. 예를 들어 3일로 두면(예시) 최근 3일을 매번 다시 계산해서 늦게 도착한 주문이 반영돼요.

| 방식                    | 늦은 주문                 | 오늘 점         | 추가 비용                    |
| ----------------------- | ------------------------- | --------------- | ---------------------------- |
| 롤업만                  | 다음 갱신 전까지 빠져요   | 빠져요          | 없어요                       |
| 롤업 + 오늘만 원본      | 과거 날짜는 여전히 빠져요 | 원본으로 맞아요 | 오늘 주문 수만큼 읽어요      |
| 롤업 + 최근 며칠 재계산 | 재계산 구간 안은 반영돼요 | 원본으로 맞아요 | 재계산 날 수만큼 다시 읽어요 |

늦은 데이터가 얼마나 늦게 오는지 모르면 재계산 구간을 정하기 어려워요. 도착 지연을 먼저 재 보고 구간을 정해요(예시: 99%가 1시간 안에 도착하면 최근 2일을 재계산).

## 점 개수 — 구간에 맞는 버킷과 다운샘플링

점이 많으면 그릴 수도 읽을 수도 없어요. 먼저 버킷을 키워서 점 개수를 줄이는 편이 좋아요. 시 단위 점 2,160개를 일 단위 90개로 바꾸는 식이에요.

이미 계산한 점을 다시 줄이는 방법도 있어요. 시 단위 점을 일 단위 평균으로 묶는 식이에요. 이 방식은 피크가 평균에 묻혀요. 스파이크를 봐야 하는 차트라면 최댓값을 같이 보내요. 어떤 집계 함수를 쓸지는 차트가 답해야 하는 질문으로 정해요.

## 빈 버킷 — 0으로 채울지 비울지

주문이 없는 날에는 원본 집계에서 그 날의 행이 아예 없어요. 그래서 `GROUP BY` 결과에도 그 날이 빠져요. 차트의 가로축이 끊기거나, 선이 엉뚱하게 이어져요.

PostgreSQL 문서는 `generate_series`가 시작과 끝, 간격으로 시계열을 만들고, `timestamp with time zone` 형식은 시간대 인자에 따라 서머타임까지 계산한다고 설명해요. 버킷 목록을 먼저 만들고 집계 결과를 `LEFT JOIN`하면, 빈 버킷도 행으로 남고 합계 칸은 `NULL`이 돼요. 0으로 채우려면 `coalesce(total, 0)`처럼 따로 바꿔요.

| 선택         | 장점                                    | 위험                                         |
| ------------ | --------------------------------------- | -------------------------------------------- |
| 0으로 채우기 | 가로축이 끊기지 않아요                  | 아직 계산되지 않은 점도 0으로 보여요         |
| 비워 두기    | 계산 전 점과 진짜 0을 나눠 볼 수 있어요 | 차트가 빈 칸을 어떻게 그리는지 확인해야 해요 |

주문이 없었던 날처럼 진짜 0이면 0으로 채워도 돼요. 오늘 점처럼 계산 전인 값은 응답에서 `null`로 주고, FE가 빈 칸으로 그리는 편이 안전해요.

## 차트 응답 형식 — 값과 기준 시각을 함께 싣기

응답에는 점 목록과 함께 점을 어떻게 만들었는지 알려 주는 값을 실어요. 아래는 예시 응답이에요.

```json
{
  "bucket": "day",
  "timeZone": "Asia/Seoul",
  "computedThrough": "2026-03-10T00:10:00+09:00",
  "points": [
    { "t": "2026-03-08T00:00:00+09:00", "v": 1240000 },
    { "t": "2026-03-09T00:00:00+09:00", "v": 1315000 },
    { "t": "2026-03-10T00:00:00+09:00", "v": null }
  ]
}
```

`bucket`과 `timeZone`은 점을 어떻게 나눴는지 알려 줘요. `computedThrough`는 롤업이 어느 시각까지 반영됐는지 알려 줘요. 오늘 점의 `v`가 `null`이면 아직 계산 전이라는 뜻이에요. `v`는 원 단위 정수로 보내요([금액 계산과 표현](/m/money-amounts) 글 참고).

끝난 날의 점은 오래 캐시해도 되지만, 오늘이 들어간 응답은 짧게 두거나 캐시하지 않는 편이 좋아요. 캐시 규칙은 [API 응답 HTTP 캐시](/m/http-caching) 글에서 이어 봐요.

## FE 체크 포인트

**차트의 점 수를 먼저 가늠해요.** 기간을 버킷 크기로 나누면 점 개수가 나와요. 점이 수백 개를 넘으면 버킷을 키우자고 BE와 먼저 이야기해요.

**`null`과 `0`을 다르게 그려요.** 계산 전인 점은 빈 칸으로, 실제 0은 0으로 그려요. 두 값을 같은 선으로 이으면 오늘 매출이 0으로 떨어진 것처럼 보여요.

**기준 시각을 화면에 적어요.** `computedThrough`를 차트 아래에 적으면, 사용자가 숫자가 언제까지의 값인지 알 수 있어요.

**기간, 버킷, 시간대가 바뀌면 다시 요청해요.** 같은 차트라도 세 값이 다르면 다른 응답이에요. 요청 파라미터로 넘기고, 캐시 키에도 같은 값을 넣어요.

## 시뮬레이터 안내

아래 시뮬레이터는 가짜 주문 90일치로 차트를 만들어요. 모든 값은 예시예요.

1. 집계 방식을 `매번 원본`으로 두고, 차트 점과 읽은 행 수를 확인해요.
2. `일별 롤업`으로 바꾸면 읽은 행이 줄고, 오늘 점이 빠져요.
3. `늦게 도착한 주문 2건 넣기`를 켜면 롤업의 원본과 다른 점이 늘어요.
4. `롤업 + 오늘만 원본`으로 바꾸면 오늘 점은 맞지만, 과거 날짜의 차이는 남아요.
5. 시간대를 UTC와 서울로 바꾸면 같은 날의 값이 어떻게 달라지는지 봐요.

버킷을 `시`로 바꾸면 집계 방식은 원본으로 바뀌어요. 이 모델은 시 단위 롤업을 만들지 않아요.

## 정리 — 원본 집계 · 시간대 · 갱신 주기 · 재계산 구간 결정

차트가 느리면 원본을 매번 세지 말고, 끝난 날을 미리 집계해요. 오늘 버킷은 원본으로 읽고, 늦게 도착한 데이터는 재계산 구간으로 다뤄요. 시간대는 요청에서 받아 IANA 이름으로 자르고, 응답에는 기준 시간대와 계산 기준 시각을 같이 실어요. 빈 버킷은 진짜 0만 0으로 채우고, 계산 전 값은 `null`로 둬요.

이어서 읽을 글은 이렇게 나뉘어요. [날짜 · 시간대 · 다국어](/m/time-and-locale)는 집계 날짜 기준을, [배치 작업](/m/batch-jobs)은 롤업 갱신 작업의 재시도와 중복 실행을 다뤄요. [목록 필터와 정렬](/m/list-filtering)은 집계 전 조건과 인덱스를, [좋아요와 조회수](/m/hot-counters)는 쓰기가 몰리는 카운터를 다뤄요.
