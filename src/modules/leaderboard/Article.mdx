이벤트 랭킹 화면에 상위 100명과 "내 순위 12,345위"를 같이 보여 달라는 요청을 받으면, 가장 먼저 드는 생각은 "내 점수보다 높은 사람을 세면 되겠다"일 거예요. 맞는 생각이에요. 다만 참가자가 100만 명이 되면 그 한 번의 COUNT가 요청마다 큰 비용이 돼요. 이 글에서는 순위를 매번 세는 비용이 어디서 생기는지, 정렬된 집합으로 그 비용을 어떻게 옮기는지, 그리고 동점과 페이지와 기간을 어떻게 다루는지 정리해요.

아래 시뮬레이터에서 참가자 수와 순위 방식, 동점 규칙을 바꾸면서 같은 점수의 사람이 어떤 순서로 서는지 직접 볼 수 있어요. 숫자는 이 시뮬레이터 안에서만 쓰는 예시예요.

## 매번 세는 순위 — 점수보다 높은 행 수 세기

가장 단순한 방법은 DB에 점수 테이블을 두고 내 점수보다 높은 행을 세는 거예요.

```sql
SELECT COUNT(*) + 1 AS my_rank
FROM scores
WHERE score > :my_score;
```

이 쿼리는 맞는 답을 줘요. 문제는 비용이에요. 이 글의 계산은 조건에 맞는 항목을 하나씩 센다고 가정해요. 그러면 내 순위가 낮을수록, 다시 말해 내 점수보다 앞선 사람이 많을수록 세는 항목도 늘어요. 100만 명 중 500,000번째인 사람은 약 50만 개를 세야 해요. 상위권 사람은 적게 세지만, 요청마다 같은 긴 범위를 다시 세는 구조라는 점은 같아요.

여기에 동점 규칙이 붙으면 조건이 두 줄이 돼요.

```sql
SELECT COUNT(*) + 1
FROM scores
WHERE score > :my_score
   OR (score = :my_score AND reached_at < :my_reached_at);
```

조건이 늘수록 인덱스를 고르기도 어려워져요. 같은 점수 안에서 도달 순서로 한 번 더 나눠야 하기 때문이에요.

윈도 함수 `rank()`로 한 번에 전체 순위를 매기는 방법도 있어요. PostgreSQL 문서는 `rank()`가 같은 값에 같은 순위를 주고 다음 순위를 건너뛴다고 설명해요. `dense_rank()`는 건너뛰지 않고, `row_number()`는 동점이어도 행마다 번호를 달아요. 다만 이 함수들은 쿼리 하나가 전체 행을 훑는 결과라서, 요청마다 호출하는 순위 API에는 맞지 않아요. 순위 목록을 주기적으로 만들어 두는 배치 용도로는 쓸 만해요.

## 정렬된 집합 — 점수 순서를 저장소에 두기

Redis의 정렬된 집합은 멤버마다 점수를 붙이고, 점수 순서를 저장소가 계속 유지해요. Redis 문서는 각 멤버가 부동소수점 점수와 짝을 이룬다고 설명해요. 점수가 바뀔 때마다 순서를 함께 갱신하기 때문에, 순위 조회는 다시 세지 않아도 돼요.

```
ZINCRBY rank:daily:2026-11-24 10 user-42
ZREVRANK rank:daily:2026-11-24 user-42
ZRANGE rank:daily:2026-11-24 0 99 REV WITHSCORES
```

복잡도는 명령 문서에 적힌 범위만 말할 수 있어요.

| 명령             | 하는 일                            | 문서의 Time complexity         |
| ---------------- | ---------------------------------- | ------------------------------ |
| `ZADD`           | 멤버와 점수를 넣어요               | 항목당 O(log(N))               |
| `ZINCRBY`        | 점수를 더해요                      | O(log(N))                      |
| `ZREVRANK`       | 높은 점수부터 세는 순위를 돌려줘요 | O(log(N))                      |
| `ZRANGE ... REV` | 높은 쪽 구간을 돌려줘요            | O(log(N)+M), M은 돌려주는 개수 |

`ZREVRANK`는 높은 점수부터 0부터 번호를 매기는 순위를 돌려줘요. 1등이 0이라는 점에 주의해서 화면에는 1을 더해 보여 주세요. Redis 문서는 `ZREVRANGE`가 6.2.0부터 deprecated이고, `ZRANGE`에 `REV` 인자를 붙여 대체할 수 있다고 설명해요. 새 코드는 `ZRANGE ... REV`로 쓰는 편이 좋아요.

정렬된 집합이 모든 경우에 맞는 답은 아니에요. 점수를 올리는 쓰기가 같은 저장소에 몰리면 그 쓰기도 로그 단계씩 들어요. 그래서 순위 저장소는 쓰기 경로에서 떼어내고, 원본 DB 위의 파생 데이터로 다루는 편이 안전해요. 이 부분은 아래 원본과 랭킹 저장소 절에서 다시 봐요.

## 동점 처리 — 먼저 도달한 사람을 점수에 섞기

Redis 문서는 점수가 같으면 멤버를 문자열 순서로 정렬한다고 설명해요. 그래서 기본 설정을 그대로 쓰면 같은 점수의 순서는 이름 순이 돼요. 먼저 도달한 사람이 뒤로 밀리는 건 공정하지 않아요. 이름 순은 기본값일 뿐이고, 어떤 규칙이 맞는지는 이벤트 규칙이 정해요.

먼저 도달한 사람을 우선하려면 도달 순서를 점수에 섞어 하나의 값으로 만들어요. 이 글의 모델은 다음처럼 인코딩해요.

```
encoded = score × SPAN + (SPAN − 1 − arrival)
```

`arrival`은 도달 순서예요. 작을수록 먼저 온 사람이에요. 같은 점수면 먼저 온 사람의 인코딩 값이 커서 높은 순위에 와요. `SPAN`은 도달 순서의 최대값보다 커야 해요. 점수는 부동소수점이라서, 두 값을 합친 결과가 정확히 표현되는 범위를 벗어나지 않는지도 확인해야 해요.

| 동점 규칙                      | 같은 점수의 순서                 | 주의                                                   |
| ------------------------------ | -------------------------------- | ------------------------------------------------------ |
| 이름 순 (Redis 기본)           | 멤버 문자열이 큰 쪽이 먼저       | 도달 순서가 순위에 반영되지 않아요                     |
| 먼저 도달한 사람 우선 (인코딩) | 도달이 빠른 쪽이 먼저            | 점수와 도달 순서를 합친 값의 범위를 확인해야 해요      |
| 시각을 점수 소수점에 붙이기    | 밀리초 단위 시각을 점수에 더해요 | 시각 단위가 크면 점수 정밀도에 걸려요. 설계 판단이에요 |

동점 규칙은 설계 판단이에요. 같은 점수가 많이 나오는 이벤트라면 먼저 도달한 사람 우선이 설명하기 쉬워요. 반대로 같은 점수가 드물다면 이름 순이라도 큰 문제가 없어요.

## 상위 N과 페이지 — 오프셋 대신 점수 커서

상위 100명은 `ZRANGE ... REV`의 앞쪽 구간이에요. 다음 페이지는 오프셋으로 건너뛰는 대신, 마지막으로 받은 사람의 (점수, 도달 순서)를 커서로 넘겨요. 순위 목록도 [페이지네이션 글](/m/pagination)에서 본 keyset과 같은 원리예요. 오프셋을 쓰면 페이지 사이에 점수가 바뀐 사람이 중복되거나 빠지기 쉬워요.

이 모델의 `pageAfter`는 커서 다음 행을 같은 정렬 기준으로 이어 읽어요. 페이지를 전부 이어 읽으면 참가자 전체가 중복 없이 한 번씩 나와요.

커서 안의 값은 FE가 해석하지 않는 불투명한 토큰으로 두세요. 정렬 기준을 BE가 바꾸면 커서 해석도 함께 바뀌어야 하기 때문이에요.

## 주기별 랭킹 — 일간 · 주간 키 분리와 만료

일간과 주간 랭킹은 같은 저장소를 쓰되 키를 나눠요. 날짜가 키에 들어가면 새 기간은 새 키에서 시작하고, 지난 기간의 키는 쓰지 않으니 만료 시간을 줘서 치워요.

```
rank:daily:2026-11-24
rank:weekly:2026-11-23
```

이 글의 주간 키는 UTC 기준 월요일 날짜로 정해요. 기간 경계를 어느 시간대로 자를지는 서비스 규칙이에요. 키가 사라지는 시간(TTL)도 설계 판단이에요. 기간이 끝난 뒤 결과를 확인하거나 정산할 시간을 남겨야 하는지에 따라 달라요.

## 원본과 랭킹 저장소 — 어긋남 감지와 재구축

점수의 원본은 DB에 있고, 랭킹 저장소는 그 파생 데이터예요. 점수를 DB에 쓰고 랭킹 저장소에 쓰는 두 단계 사이에서 장애가 나면, 둘의 값이 어긋날 수 있어요. 이 글의 모델은 어긋난 참가자를 세 종류로 나눠요.

- DB에는 있는데 랭킹 저장소에 없는 참가자
- 두 곳에 있지만 점수가 다른 참가자
- 랭킹 저장소에만 남은 참가자

어긋남이 확인되면 랭킹 저장소를 DB에서 처음부터 다시 채워요. 재구축은 비용이 크니, 평소에는 쓰기 경로에서 두 저장소를 같은 요청으로 맞추고 재구축은 장애 뒤에만 돌려요. 재구축 중에도 순위 조회가 맞게 나오도록 새 키에 채운 뒤 바꿔 끼우는 방식도 있어요. 이 부분은 서비스의 허용 지연에 따라 골라요.

## 근사 순위 — 상위 몇 %로 충분한 경우

화면이 "12,345위"처럼 정확한 숫자를 요구하지 않으면 근사가 충분할 수 있어요. 이 글의 구간별 근사는 점수를 구간으로 묶고, 구간마다 인원수만 들고 있어요. 내 구간보다 높은 구간의 인원을 더하면 순위의 아래쪽이 나와요. 같은 구간 안의 순서는 모르니 위쪽은 구간 인원만큼 더해 범위로 보여 줘요.

이 방식은 읽는 수가 구간 수에 비례해서 적어요. 대신 같은 구간 안에서는 순위가 한 자리로 나오지 않아요. "상위 5%" 같은 표시는 이 근사로 충분한 경우가 많아요. 정확한 등수가 상금과 연결되면 근사로는 부족해요.

## 점수 신뢰 — 서버가 점수를 계산하기

랭킹은 점수를 믿어야 의미가 있어요. 클라이언트가 점수 값을 보내게 하면 누구나 값을 바꿔 보낼 수 있어요. 그래서 클라이언트는 점수가 아니라 행동 이름만 보내고, 서버가 점수표로 점수를 계산해요.

```json
{ "actions": ["correct", "correct", "streak"] }
```

점수표에 없는 행동 이름이 들어오면 그 요청은 거절해야 해요. 서버 점수표에 없는 값은 점수로 쓰면 안 돼요. 음수 점수도 같은 방식으로 막을 수 있어요. 점수를 주는 행동만 서버 규칙에 있으면, 음수는 입력 자체로 들어올 수 없어요.

## FE 체크 포인트

**순위와 목록을 한 응답으로 받는지 확인하세요.** 내 순위를 따로 호출하면 두 응답 사이에 점수가 바뀌어 순위와 목록이 어긋날 수 있어요. 한 응답에 내 순위와 상위 목록을 같이 받을 수 있는지 BE에 물어보세요.

**근사 순위는 범위로 그리세요.** 구간별 근사처럼 범위로 온 순위를 "12,345위"처럼 정확한 값으로 보여 주면 틀린 정보가 돼요. "약 12,000위대"처럼 범위로 표시하세요.

**같은 점수의 순서를 화면에 설명하세요.** 손님은 왜 나보다 늦게 온 사람이 위에 있는지 궁금해해요. 동점 규칙을 짧은 안내 문구로 붙이면 문의가 줄어요.

**목록은 커서로 이어 받으세요.** 다음 페이지를 받을 때 페이지 번호를 계산하지 말고, 응답의 커서를 그대로 보내세요.

**점수는 행동으로 보내세요.** 화면이 점수를 계산해서 보내면 안 돼요. 정답 제출처럼 행동 이름과 입력만 보내고, 점수 표시는 서버 응답을 따르세요.

## 시뮬레이터 안내

아래 시뮬레이터에서 세 가지를 확인해 보세요. 첫째, 참가자를 1천 명에서 10만 명으로 늘릴 때 DB COUNT의 읽는 항목 수가 늘어나는지 보세요. 둘째, 정렬된 집합은 로그 단계로 늘어나는 점을 비교해 보세요. 셋째, 동점 규칙을 바꾸면 같은 점수 안의 줄 서기가 어떻게 달라지는지 보세요.

## 정리 — 순위 방식 · 동점 규칙 · 페이지 단위 고르기

내 순위를 매번 세면 참가자가 늘수록 비용이 커져요. 정렬된 집합은 점수 순서를 저장소에 두어서 조회를 로그 단계로 끝내요. 같은 점수의 순서는 Redis 기본 설정이 이름 순이므로, 먼저 도달한 사람을 우선하려면 도달 순서를 점수에 섞어야 해요.

상위 목록은 오프셋 대신 점수 커서로 이어 읽고, 일간 · 주간 랭킹은 키를 나눠 만료를 둬요. 원본 DB와 랭킹 저장소가 어긋나면 DB에서 다시 채우세요. 정확한 등수가 필요 없으면 구간별 근사로 범위를 보여 줄 수 있어요. 점수는 서버가 계산하는 편이 좋아요.

더 보고 싶다면 같은 키 카운터를 여러 조각으로 나누는 방법은 [핫 카운터 글](/m/hot-counters)에서, 순위 조회가 몰릴 때 캐시가 한꺼번에 비는 문제는 [캐시 스탬피드 글](/m/cache-stampede)에서 이어서 읽어 보세요.
