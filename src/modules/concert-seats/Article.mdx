티켓 오픈 시각에 수많은 사람이 같은 좌석을 동시에 눌러요. 예시로 1만 명이 같은 좌석을 누르면, 그 좌석은 누구의 것이 될까요? 화면에서는 모두 "선택했어요"가 뜨지만, 실제로 DB 에 "이 좌석은 내 것"이라고 적히는 사람은 한 명이어야 해요.

이 글은 그 한 명을 정하는 방법과, 그 방법이 무엇을 대가로 치르는지 정리해요. 아래 시뮬레이터에서 같은 상황을 직접 돌려 볼 수 있어요. 글의 규칙과 시뮬레이터의 동작은 같아요. 시뮬레이터에서 시간의 단위인 "틱"은 DB 요청 한 번을 뜻해요.

## 좌석 상태 — 선점과 확정을 나누기

좌석 예매는 보통 두 단계로 나뉘어요.

1. 선점(hold): 결제 전에 "이 사람이 이 좌석을 잠시 잡고 있어요"라고 기록해요. 보통 몇 분 안에 결제해야 한다는 시한이 붙어요.
2. 확정(confirm): 결제가 끝나면 "이 좌석은 팔렸어요"로 바꿔요.

좌석 한 칸의 상태는 세 가지로 볼 수 있어요.

```text
AVAILABLE ──(hold: holder, held_until)──▶ HELD ──(결제 확정)──▶ SOLD
    ▲                                      │
    └────────(held_until 이 지나거나 취소)──┘
```

| 상태      | 뜻                                      | 저장되는 값             |
| --------- | --------------------------------------- | ----------------------- |
| AVAILABLE | 아무도 잡고 있지 않아요                 | 없음 (또는 만료된 보류) |
| HELD      | 누군가 시한 안에 결제하려고 잡고 있어요 | holder, held_until      |
| SOLD      | 결제가 끝나 팔렸어요                    | sold 표시, 판매한 사람  |

선점과 확정을 나누면 생기는 질문이 있어요. 결제가 늦어서 보류가 풀린 뒤에 결제 콜백이 도착하면 어떻게 할까요? 이 질문은 뒤의 "보류 만료" 절에서 다뤄요.

## 같은 좌석을 두고 생기는 경쟁 — 다섯 가지 방법

경쟁은 "누가 먼저 확인하고, 누가 나중에 쓰는가"에서 생겨요. 아래 다섯 방법은 그 사이를 어떻게 막는지가 달라요.

### 읽고 나서 쓰기 — 이중 예약이 생기는 패턴

가장 자연스러운 코드는 이렇게 생겼어요.

```sql
SELECT status FROM seats WHERE id = 7;        -- 앱이 AVAILABLE 인지 확인
UPDATE seats SET status = 'HELD', holder = $u WHERE id = 7;
```

두 사용자가 같은 순서로 읽으면 둘 다 AVAILABLE 을 봐요. 그다음 둘 다 쓰면 나중 쓰기가 앞선 보류를 덮어써요. 두 사람 모두 "보류 성공"을 받았으니 이중 예약이에요. 시뮬레이터의 "읽고 나서 쓰기"에서 이 장면이 보여요.

이 패턴은 읽기와 쓰기 사이에 빈틈이 있다는 점이 문제예요. 락을 잡지 않으면 빈틈은 그대로 남아요.

### 조건부 UPDATE — 비어 있을 때만 바꾸기

확인과 변경을 한 문장에 넣으면 빈틈이 없어져요.

```sql
UPDATE seats
SET status = 'HELD', holder = $user_id, held_until = now() + interval '5 minutes'
WHERE seat_id = $seat_id
  AND (status = 'AVAILABLE' OR held_until < now());
```

앱은 영향받은 행 수를 확인해요. 1 이면 보류 성공이고, 0 이면 이미 누군가 잡았다는 뜻이라 409 Conflict 로 답해요. 이 방식은 DB 가 한 번에 판단하기 때문에 앱이 옛날 값으로 계산할 일이 없어요.

영향받은 행 수를 확인하지 않으면 실패가 조용히 지나가요. 이 방식의 절반은 행 수 확인이에요.

### UNIQUE 제약 — 예약 행을 하나만 허용하기

좌석마다 예약 행을 하나만 허용하는 방법도 있어요.

```sql
CREATE TABLE reservations (
  show_id    bigint NOT NULL,
  seat_id    bigint NOT NULL,
  holder     bigint NOT NULL,
  status     text   NOT NULL,
  held_until timestamptz,
  UNIQUE (show_id, seat_id)
);
```

PostgreSQL 문서는 UNIQUE 제약이 열 또는 열 묶음의 값이 테이블의 모든 행에서 유일하도록 보장한다고 설명해요. 두 사용자가 동시에 INSERT 하면 한 명만 통과하고, 나머지는 제약 위반 오류를 받아요. 앱은 그 오류를 409 로 바꿔요.

이 방식의 장점은 DB 가 이중 예약을 막는다는 점이에요. 앱 코드가 어떻게 짜였든 같은 좌석에 행이 두 개 생길 수 없어요. 단점은 만료된 보류를 지우는 일을 따로 해야 한다는 점이에요. 시뮬레이터는 "만료 행 지우기 → INSERT" 두 단계로 구현했어요.

### SKIP LOCKED — 아무 자리나 n 석 자동 배정

좌석을 고르지 않고 "아무 자리나 두 석"처럼 요청하면, 줄 서서 같은 자리를 기다릴 이유가 없어요. 이때 쓰는 것이 SKIP LOCKED 예요.

```sql
BEGIN;
SELECT seat_id
FROM seats
WHERE show_id = $show AND status = 'AVAILABLE'
ORDER BY seat_id
LIMIT 1
FOR UPDATE SKIP LOCKED;
-- 찾은 행을 HELD 로 바꾸고
COMMIT;
```

PostgreSQL 문서는 SKIP LOCKED 를 이렇게 설명해요. 잠글 수 없는 행은 건너뛰고, 잠글 수 있는 행만 골라요. 다른 요청이 이미 잠근 자리는 그냥 지나가니까, 많은 요청이 서로 다른 좌석을 가져가요.

문서는 같은 설명 안에서 이 방식의 대가도 밝혀요. 건너뛴 행 때문에 데이터 일관성이 떨어질 수 있어서, 일반 목적의 조회에는 맞지 않는다고 해요. 그래서 "아무 자리나" 같은 큐 성격의 배정에만 쓰는 것이 안전해요. 특정 좌석 하나를 누르는 요청에는 맞지 않아요.

### Redis SET NX PX — 메모리에서 잡고 TTL 로 풀기

Redis 를 쓰면 보류를 메모리에 두고 TTL 로 자동 만료시킬 수 있어요.

```text
SET seat:7:hold <user_token> NX PX 300000
```

Redis SET 문서는 NX 옵션이 키가 없을 때만 값을 쓴다고 설명해요. PX 는 밀리초 단위의 만료 시간을 줘요. 키가 없으면 성공(OK), 이미 있으면 실패(nil)가 돌아와요. 실패를 409 로 바꾸면 조건부 UPDATE 와 같은 모양이 돼요.

여기에는 주의할 점이 세 가지 있어요.

- Redis 는 확정 기록의 원장이 아니에요. 키는 빨리 쓰고 읽지만, 결제 결과와 판매 기록은 DB 에 남아야 해요. Redis 는 "지금 잡혀 있나"를 빠르게 답하는 용도로 두세요.
- 장애 때 쓰기가 사라질 수 있어요. Redis 공식 복제 문서는 기본 복제가 비동기이고, 장애 조치 중에는 응답을 보낸 쓰기도 설정에 따라 잃을 수 있다고 설명해요.
- 만료와 결제가 경합해요. TTL 이 지난 뒤에 결제 콜백이 도착하면, Redis 키는 사라졌어도 결제는 이미 끝났어요. 이 경합은 Redis 가 아니라 DB 의 조건으로 최종 판단해야 해요.

Redis 공식 분산 락 페이지도 같은 SET NX PX 패턴을 소개하면서, 키에 만료 시간을 두어 결국 풀리게 하라고 설명해요. 같은 페이지는 Redlock 알고리즘이 시계의 진행 속도가 비슷하다는 가정에 기대고 있다고도 밝혀요. 락이 있다고 해서 모든 경합이 사라지지는 않아요.

## 핫 로우 — 같은 행이 병목이 되는 이유

특정 좌석을 누르는 방법은 모두 같은 행을 두고 경쟁해요. SKIP LOCKED 만 잠긴 행을 비켜 가는데, 그건 "아무 자리나" 요청일 때뿐이에요. 1만 명이 같은 좌석 한 칸을 누르면, 그 한 행이 모든 요청의 공통 지점이에요. 락을 잡고 기다리는 시간이 곧 응답 시간이 돼요.

그래서 핫 로우는 DB 를 여러 대로 늘려도 잘 풀리지 않아요. 같은 행을 누가 쥐고 있는지가 병목이기 때문이에요. 대기열은 이 병목 앞에 두는 입구예요. 요청이 좌석 행에 닿는 양을 줄여서, 행이 감당할 수 있는 만큼만 들여보내요. 대기열 설계는 다음 모듈에서 더 깊이 다룰 거예요.

## 보류 만료 — 시간이 지나면 풀리는 규칙

보류에는 만료 시각이 있어야 해요. 그렇지 않으면 결제하지 않은 사람이 좌석을 영원히 붙잡아요. 시뮬레이터에서 "보류 만료 켜기"를 끄면, 결제하지 않은 보류가 끝까지 HELD 로 남는 장면을 볼 수 있어요.

만료를 처리하는 방법은 두 가지예요.

| 방법        | 어떻게 하나                               | 장점                             | 주의                                            |
| ----------- | ----------------------------------------- | -------------------------------- | ----------------------------------------------- |
| 지연 만료   | 쓰기 조건에 held_until < now() 를 넣어요  | 별도 작업이 없고 항상 정확해요   | 좌석 목록 조회 화면은 옛 값을 보여 줄 수 있어요 |
| 주기적 정리 | 백그라운드 작업이 만료된 보류를 풀어 줘요 | 화면과 집계가 실제 상태와 맞아요 | 정리 전까지 잠깐 어긋나요                       |

두 방법을 같이 쓰는 것이 보통이에요. 지연 만료가 정확성을 지키고, 주기적 정리가 화면과 집계를 맞춰요.

만료 시각 경계는 한 칸 차이로 정확히 정해 두세요. 시뮬레이터는 held_until 과 같은 틱에는 아직 잡혀 있고, 그다음 틱부터 풀리게 했어요. 테스트도 이 경계를 확인해요.

### 결제 콜백이 만료 뒤에 도착할 때

결제 콜백은 보류가 살아 있는 동안 도착한다고 보장할 수 없어요. 확정 쓰기도 같은 조건으로 확인해야 해요.

```sql
UPDATE seats
SET status = 'SOLD'
WHERE seat_id = $seat_id
  AND holder = $user_id
  AND status = 'HELD'
  AND held_until >= now();
```

영향받은 행 수가 0 이면 결제는 받았지만 좌석을 줄 수 없어요. 이때는 결제를 취소하거나 환불하는 보상 흐름으로 넘겨요. 시뮬레이터에서 늦게 결제한 사용자가 환불 칸에 찍히는 장면이 이 경우예요.

## FE 체크 포인트

- 409 는 실패가 아니라 "지금 상태가 바뀌었다"는 안내예요. 사용자에게 이유를 보여 주고, 좌석 목록을 다시 받아 오세요.
- 선점 응답에는 보류 토큰과 만료 시각을 함께 받으세요. 예시 응답은 이래요.

```http
HTTP/1.1 201 Created
Content-Type: application/json

{"holdToken": "h_01J9X", "seatId": 7, "expiresAt": "2026-11-23T20:35:00Z", "serverTime": "2026-11-23T20:30:00Z"}
```

- 카운트다운은 클라이언트 시계가 아니라 서버 시간을 기준으로 맞추세요. 응답의 serverTime 과 내 시계의 차이를 한 번 구해 두고, expiresAt 까지 남은 시간을 계산해요. 사용자 기기 시계가 틀려도 시한이 어긋나지 않아요.
- 409 를 받으면 해당 좌석의 상태를 서버에서 다시 받아 화면을 바꾸세요. 화면의 좌석 색을 옛 값으로 두면 다음 클릭도 같은 409 를 받아요.
- 결제 확정을 기다리기 전에 화면에서 SOLD 로 바꾸지 마세요. 낙관적으로 바꾸면 결제가 실패했을 때 되돌리기 어려워요.
- 같은 선점 요청을 네트워크 재시도로 다시 보낼 수 있어요. [트랜잭션 · 락 · 데드락](/m/transactions)의 멱등성 키 규칙을 그대로 써서, 같은 시도에는 같은 키를 보내세요. 재시도로 두 번째 보류를 만들면 안 돼요.
- 좌석 배치 갱신은 두 방식이 있어요. 주기적으로 조회하는 폴링은 구현이 단순하지만 지연이 생겨요. 변경을 밀어 주는 push 는 실시간에 가깝지만 연결 관리가 필요해요. 어느 쪽이든 최종 판단은 서버의 409 와 보류 토큰이에요.

## 정리 — 누가 가져가는지는 DB 가 정해요

같은 좌석을 두고 누가 가져가는지는 "확인과 쓰기를 한 덩어리로 묶었는가"에 달려 있어요. 읽고 나서 쓰면 이중 예약이 생기고, 조건부 UPDATE 나 UNIQUE 제약은 DB 가 한 명만 통과시켜요. 아무 자리나 배정할 때는 SKIP LOCKED 가 잠긴 행을 건너뛰어요. Redis 의 SET NX PX 는 빠르지만 원장이 아니라서 결제 확정은 DB 에서 다시 확인해야 해요.

기초 모듈로 돌아가 보면, 이 글의 조건부 UPDATE 와 행 잠금은 [트랜잭션 · 락 · 데드락](/m/transactions)에서 본 규칙 위에 서 있어요. 여러 좌석 목록을 나눠 받는 방식은 [페이지네이션](/m/pagination)과, 좌석마다 추가 조회가 붙는 실수는 [N+1 문제](/m/n-plus-one)와 이어져요.
