FE 를 하다 보면 목록 API 에 `page=3` 을 보내는 순간이 와요. 어떤 API 는 `cursor=...` 를 받아요. 둘 다 "다음 글 20개 주세요"라는 요청인데, 서버 안에서 하는 일은 많이 달라요.

이 글은 한 질문에서 출발해요. **목록 API 가 offset 이면 무엇을 조심해야 하나요?** 답을 찾으려면 DB 가 offset 을 어떻게 처리하는지, 목록이 바뀌는 동안 무슨 일이 생기는지, 그리고 대안인 keyset 이 무엇을 바꾸는지 차례로 봐야 해요.

예시로 쓰는 테이블은 이래요. 이 글의 숫자는 모두 설명을 위한 예시예요.

```sql
CREATE TABLE posts (
  id         BIGINT PRIMARY KEY,
  title      TEXT NOT NULL,
  created_at TIMESTAMP NOT NULL
);
```

## offset 과 limit — 서버가 건너뛰는 방식

최신순 목록의 11번째부터 5개를 받는 쿼리는 이렇게 쓰여요.

```sql
SELECT id, title, created_at
FROM posts
ORDER BY created_at DESC, id DESC
LIMIT 5 OFFSET 10;
```

여기서 `OFFSET 10` 은 "앞의 10개를 건너뛰어 주세요"라는 뜻이에요. 그런데 건너뛴 행을 DB 가 세지 않고 넘어가지는 않아요. PostgreSQL 공식 문서는 OFFSET 으로 건너뛴 행도 서버 안에서 계산해야 하므로 큰 OFFSET 은 비효율적일 수 있다고 설명해요. Use The Index, Luke 도 요청한 페이지에 닿을 때까지 처음부터 행을 세야 한다고 짚어요. 정렬 인덱스가 있어도 DB 는 앞쪽 항목을 하나씩 따라가며 버려요.

그래서 페이지가 뒤로 갈수록 버리는 행이 늘어나요. 페이지 크기가 5일 때 계산하면 이래요.

## keyset 페이지네이션 — 마지막 글 다음부터 이어 읽기

keyset 방식은 마지막으로 받은 글의 정렬 키를 WHERE 조건으로 넘겨요.

```sql
SELECT id, title, created_at
FROM posts
WHERE (created_at, id) < (:last_created_at, :last_id)
ORDER BY created_at DESC, id DESC
LIMIT 5;
```

`(created_at, id) < (c, i)` 는 행 값 비교예요. PostgreSQL 문서는 행 값 비교가 왼쪽 요소부터 차례로 비교하고, 처음 다른 쌍에서 결과가 정해진다고 설명해요. 그래서 `created_at` 이 같으면 `id` 로 순서가 정해져요. 정렬 방향인 `DESC` 와 비교 방향이 맞아야 "마지막 글 다음"이 정확히 같은 줄을 가리켜요.

이 방식에는 OFFSET 이 없어요. DB 는 조건에 맞는 시작점을 인덱스에서 바로 찾고, 거기서부터 5개를 읽어요. Use The Index, Luke 는 seek 방식에서 DB 가 조건을 인덱스 접근에 쓰면 이전 페이지의 행을 실제로 건너뛸 수 있다고 설명해요.

### 정렬 키 — 동률 처리와 복합 인덱스

정렬 키가 유일하지 않으면 keyset 도 깨져요. 같은 `created_at` 을 가진 글이 세 개 있다고 해 볼게요. 커서가 `created_at` 하나뿐이면 `created_at < 10` 은 같은 시각의 나머지 글을 전부 건너뛰어요. `id` 를 함께 비교하면 `(10, 4)` 다음에 `(10, 3)` 이 와서 빠지지 않아요.

그래서 정렬 키 끝에 유일한 값을 붙여요. 보통 기본 키를 써요. 인덱스도 같은 순서로 만들어야 해요.

```sql
CREATE INDEX posts_feed_idx ON posts (created_at DESC, id DESC);
```

Use The Index, Luke 는 정렬이 결정적이지 않으면 유일한 컬럼을 ORDER BY 와 인덱스 양쪽에 덧붙이라고 권해요. 인덱스 순서와 ORDER BY 가 어긋나면 DB 가 정렬을 따로 하거나 시작점을 찾지 못해서 keyset 의 장점이 사라져요.

## 커서 토큰 — 값을 해석하지 않고 되돌려 주기

실제 API 에서는 `created_at` 과 `id` 를 그대로 노출하지 않고 커서 토큰 하나로 감싸는 경우가 많아요. 예시 응답은 이래요.

```json
{
  "items": [{ "id": 1037, "title": "두 번째 글", "createdAt": "2026-11-20T09:00:00Z" }],
  "nextCursor": "MjAyNi0xMS0yMDowOTowMDoxMDM3",
  "hasMore": true
}
```

Slack 문서는 응답의 `next_cursor` 를 다음 호출의 `cursor` 에 그대로 넣으라고 안내해요. Stripe 는 `starting_after` 에 객체 ID 를 넣어서 목록에서 내 자리를 정한다고 설명해요. 두 문서 모두 클라이언트가 값을 만들거나 고치지 않고 받은 값을 되돌려 준다는 점이 같아요.

FE 가 커서 안을 뜯어서 날짜나 id 를 꺼내 쓰기 시작하면 BE 가 정렬 기준을 바꾸는 순간 깨져요. 그래서 커서는 불투명한 값으로 다루는 편이 안전해요. 이건 권장하는 설계 습관이에요. 어떤 값을 담을지는 BE 가 정해요.

## UI 별 선택 — 무한 스크롤과 번호 페이지

화면이 어떻게 움직이는지에 따라 맞는 방식이 달라요.

- 피드, 최신 글, 무한 스크롤은 keyset 이 잘 맞아요. 목록 앞쪽에 글이 계속 들어오는 화면이라서, 번호 기준이 쉽게 밀리기 때문이에요.
- 관리자 표, 검색 결과 번호 페이지는 offset 이 자연스러워요. 특정 페이지로 점프하는 기능이 필요하고, 데이터가 많이 바뀌지 않으면 중복과 누락도 드물어요.
- 데이터가 적고 거의 바뀌지 않는 목록이라면 offset 으로도 충분해요. 깊이가 얕으면 건너뛰기 비용도 작아요.

BE 에게는 이런 질문을 해 보세요.

1. 정렬 기준이 무엇이고, 같은 값일 때 무엇으로 순서를 나누나요?
2. 페이지를 받는 사이에 글이 들어오거나 지워지면 중복이나 누락을 허용하나요?
3. 특정 페이지로 점프하는 기능이 필요한가요, 아니면 다음 · 이전만 있으면 되나요?
4. 전체 개수가 꼭 필요한가요? 필요하다면 정확도 기준이 있나요?
5. 커서는 얼마 동안 유효한가요? 정렬이 바뀌거나 만료되면 어떤 응답을 주나요?

FE 쪽에서 임시로 할 수 있는 일도 있어요. 받은 글을 id 로 한 번 더 거르면 화면에 같은 글이 두 번 보이는 건 막을 수 있어요. 하지만 빠진 글은 화면에 없으니 걸러 낼 수 없어요. 누락은 BE 의 방식을 바꾸거나 다시 받아야 해요. 그래서 중복 제거는 증상을 가리는 조치이고, 근본은 방식 선택이라는 점을 기억해 주세요.
