검색창에 글자를 칠 때마다 요청을 보내면 가장 빨라 보여요. 그런데 "사과주스" 다섯 글자를 치면 요청이 다섯 번 나가요. 이 글은 세 가지를 나눠 봐요. 요청이 몇 번 나가는지, 늦게 온 응답이 최신 결과를 덮지 않게 하는 법, 그리고 검색 쿼리가 인덱스를 타는지예요. 마지막에 응답 캐시와 429 처리도 짧게 다뤄요.

아래 시뮬레이터에서 전송 시점과 낡은 응답 처리를 바꿔 보면, 같은 타이핑에서 요청 수와 화면에 남는 결과가 어떻게 달라지는지 직접 볼 수 있어요.

## 키 입력마다 요청 — 요청 수는 글자 수와 같아요

키마다 요청을 보내면 요청 수는 입력한 글자 수와 같아요. 이 자체가 나쁜 것은 아니에요. 문제는 서버에서 요청 하나가 DB 쿼리 하나를 뜻하는 경우가 많다는 점이에요. 예를 들어 손님 1,000명이 각자 6글자를 치면 키마다 보내는 방식은 6,000 건이에요. 이 숫자는 설명을 위한 예시 계산이에요. 실제 부하는 쿼리 비용과 캐시에 따라 달라요.

## 늦게 온 응답 — 경쟁 상태로 낡은 결과가 최신 결과를 덮어요

요청을 보낸 순서와 응답이 도착하는 순서는 같지 않을 수 있어요. 네트워크 경로와 서버 처리 시간이 요청마다 다르기 때문이에요. 예를 들어 "사과주" 요청이 먼저 도착하고, 그보다 먼저 보낸 "사과" 요청이 나중에 도착하면 화면에는 "사과" 결과가 남아요. 입력창은 "사과주" 인데 결과는 낡은 검색어의 것이에요.

이런 문제를 막는 방법은 두 가지예요.

- **순번 확인**: 요청마다 증가하는 번호를 붙이고, 도착한 응답의 번호가 화면에 그린 번호보다 오래됐으면 버려요. 이것은 FE 가 맡는 설계예요.
- **취소**: `AbortController` 로 이전 요청을 끊어요. MDN 은 `abort()` 가 fetch 요청과 응답 본문을 읽는 일 같은 비동기 작업을 중단한다고 설명해요.

취소는 클라이언트 쪽 중단이에요. 이미 서버가 받은 요청을 서버가 멈춘다는 뜻은 아니에요. 그래서 취소는 보낸 요청 수를 줄이지 않아요. 시뮬레이터에서 취소를 켜면 보낸 요청 수는 그대로이고, 취소된 요청만 늘어나는 것을 볼 수 있어요.

| 방법      | 막는 것               | 보낸 요청 수 | 서버에서 일어나는 일                             |
| --------- | --------------------- | ------------ | ------------------------------------------------ |
| 아무것도  | 없음                  | 그대로       | 모든 요청을 처리해요                             |
| 순번 확인 | 낡은 응답의 화면 반영 | 그대로       | 오래된 응답도 서버에서는 이미 처리됐을 수 있어요 |
| 취소      | 끊은 요청의 화면 반영 | 그대로       | 이미 받은 요청은 서버가 끝까지 처리할 수 있어요  |

## 전송 시점 — 디바운스와 스로틀은 요청 수를 줄여요

요청 수를 줄이는 것은 전송 시점을 바꾸는 일이에요. 아래 정의는 이 글의 설계 용어예요. 정해진 법칙이 아니에요.

- **디바운스**: 마지막 입력 뒤 정해진 시간 동안 입력이 없을 때 한 번 보내요.
- **스로틀**: 정해진 간격마다 최대 한 번 보내요.

| 방식     | 요청 수                  | 맞는 곳                 | 주의                                                       |
| -------- | ------------------------ | ----------------------- | ---------------------------------------------------------- |
| 키마다   | 입력 글자 수만큼         | 화면 안에서 끝나는 필터 | 서버 검색에는 부하가 커요                                  |
| 디바운스 | 입력이 멈출 때마다 한 번 | 검색창 자동완성         | 대기 시간만큼 결과가 늦게 나와요                           |
| 스로틀   | 간격마다 최대 한 번      | 스크롤, 실시간 집계     | 마지막 입력을 놓치지 않도록 간격 끝에 한 번 더 보내야 해요 |

디바운스의 대기 시간은 타이핑 속도와 서버 응답 시간을 함께 보고 정해요. 이 글과 시뮬레이터의 간격 값은 예시예요. 디바운스를 써도 낡은 응답은 남을 수 있으니, 전송 시점과 순번 확인은 따로 생각해요.

## LIKE '%어%' — 앞이 열린 패턴은 B-tree 인덱스를 타지 못해요

PostgreSQL 문서는 B-tree 인덱스를 LIKE 에 쓰려면 패턴이 상수이고 문자열 시작에 고정돼 있어야 한다고 설명해요. `col LIKE 'foo%'` 는 되고, `col LIKE '%bar'` 는 안 돼요. 데이터베이스가 C 로케일을 쓰지 않으면 `text_pattern_ops` 같은 연산자 클래스로 인덱스를 따로 만들어야 접두어 LIKE 를 쓸 수 있어요.

`%어%` 처럼 가운데를 찾는 검색은 다른 인덱스를 봐야 해요.

- **trigram 인덱스**: pg_trgm 문서는 GIN 또는 GiST trigram 인덱스가 LIKE 와 ILIKE 를 지원한다고 설명해요. trigram 은 세 글자 묶음이라, `%주스%` 처럼 패턴에서 세 글자 묶음을 하나도 뽑을 수 없으면 같은 문서 설명대로 인덱스 전체를 훑는 검색이 돼요. 자동완성에서 한두 글자 입력은 따로 다루는 편이 나아요.
- **전문 검색 인덱스**: 문서는 `tsvector` 열에 GIN 인덱스를 만들라고 안내해요. 단어 단위로 찾는 방식이라, 한국어에서 어떤 단위로 쪼갤지는 설정에 따라 달라요. 실제 데이터로 확인해야 해요.

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX products_name_trgm ON products USING GIN (name gin_trgm_ops);
```

| 검색 모양 | 예                 | 기본 B-tree                | 고를 인덱스               |
| --------- | ------------------ | -------------------------- | ------------------------- |
| 접두어    | `사과%`            | 쓸 수 있어요 (로케일 조건) | `text_pattern_ops` B-tree |
| 중간 일치 | `%오렌지%`         | 쓸 수 없어요               | pg_trgm GIN               |
| 단어 검색 | 단어 목록에서 찾기 | 맞지 않아요                | `tsvector` 열의 GIN       |

## 응답 캐시와 429 — 서버 부하를 응답 쪽에서 줄여요

자동완성 결과가 모든 손님에게 같다면 캐시에 둘 수 있어요. `Cache-Control` 의 `max-age` 는 응답을 신선하다고 볼 시간을 정해요. 예시로 `public, max-age=60` 을 붙이면 공유 캐시가 60초 동안 같은 응답을 재사용할 수 있어요. 값은 예시예요.

RFC 9111 은 공유 캐시를 여러 사용자가 쓰는 캐시로, 개인 캐시를 한 사용자 전용 캐시로 정의해요. 손님마다 추천이 달라지면 `private` 을 붙이거나 공유 캐시에 두지 않아요. 개인 정보가 섞인 자동완성을 공유 캐시에 두면 다른 손님이 그 결과를 받을 수 있어요.

요청이 너무 많으면 서버는 429 Too Many Requests 를 줄 수 있어요. RFC 6585 는 이 상태 코드를 짧은 시간에 너무 많이 보낸 경우로 정의하고, 응답에 `Retry-After` 를 붙일 수 있다고 해요. MDN 은 429 에서 `Retry-After` 가 다시 요청하기 전 기다릴 시간을 알려 준다고 설명해요. 값은 음이 아닌 정수 초(`delay-seconds`) 또는 날짜예요.

FE 는 429 를 받으면 같은 입력을 바로 다시 보내지 않아요. `Retry-After` 뒤에 가장 최신 검색어 하나만 보내는 편이 나아요. 이것은 설계 제안이에요.

## FE 가 할 일 — 요청 전에 정하고, 응답에서 확인해요

| 시점      | 할 일                                               | 확인 신호                                 |
| --------- | --------------------------------------------------- | ----------------------------------------- |
| 요청 전   | 디바운스나 스로틀로 전송 시점을 정해요              | 요청 수가 입력 글자 수보다 줄었는지       |
| 요청 중   | 순번을 붙이거나 이전 요청을 취소해요                | 취소된 요청이 화면에 반영되지 않았는지    |
| 응답 도착 | 응답의 검색어가 지금 입력창과 같은지 비교해요       | 응답에 검색어 필드를 넣으면 대조가 쉬워요 |
| 응답 헤더 | `Cache-Control` 과 `429` 의 `Retry-After` 를 읽어요 | 공유 캐시 가능 여부와 재시도 간격         |

## 시뮬레이터 — 전략과 보호 방식을 바꿔 확인해요

기본값은 키마다 보내고 아무 보호도 없는 상태예요. 이 상태에서 낡은 응답이 최신 검색어를 덮는 경우를 먼저 확인해요. 그다음 순번 확인이나 취소를 켜서 화면에 남는 결과가 어떻게 바뀌는지 보세요. 디바운스로 바꾸면 보낸 요청 수가 줄어요. 취소만 켜면 보낸 요청 수는 그대로예요. 두 가지가 서로 다른 문제를 막는다는 점을 기억해요.
