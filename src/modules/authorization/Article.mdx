관리자 메뉴를 화면에서 숨기는 것만으로는 주문을 지킬 수 없어요. 주소창의 주문 id를 바꾸면 요청은 그대로 서버에 도착해요. 서버가 주문마다 주인을 확인하지 않으면 남의 주문이 응답에 담겨요.

이 글은 권한 검사를 어디서, 어떤 단위로, 어떤 실패 응답으로 막을지 정리해요. 아래 시뮬레이터에서 요청자와 주문 주인을 바꿔 가며 검사 전략별 응답을 보면 차이가 잘 보여요.

## 증상 — 화면 숨김이 막은 범위

회원 화면에는 관리자 메뉴가 없어요. 그런데 `/orders/1042`를 직접 열면 주문 내용이 보여요. 화면은 버튼을 보여 줄지 정하고, 서버는 응답을 줄지 정해요. 두 판단은 서로 다른 곳에서 일어나요.

화면에서 숨긴 기능은 사용자 경험을 맞춘 것이에요. 공격자는 브라우저 밖에서 같은 요청을 보낼 수 있어요. 그래서 막아야 하는 판단은 서버에 있어야 해요.

## 인증과 인가 — 신원 확인과 권한 확인 구분

OWASP Authorization Cheat Sheet는 인가를 요청한 행위나 서비스가 특정 주체에게 승인되었는지 확인하는 과정이라고 설명해요. 인증은 주체의 신원을 확인하는 과정이라고 구분해요. 로그인한 사용자도 모든 자원과 동작에 접근할 수 있는 것은 아니라고 설명해요.

| 구분      | 인증                                               | 인가                                       |
| --------- | -------------------------------------------------- | ------------------------------------------ |
| 질문      | 이 요청을 보낸 사람은 누구인가요?                  | 이 사람이 이 대상에 이 동작을 해도 되나요? |
| 실패 응답 | 401                                                | 403 또는 404                               |
| 예시      | 액세스 토큰이 만료됐어요                           | 회원이 다른 조직의 주문을 조회했어요       |
| 더 읽기   | [로그인 유지 — 세션과 토큰](/m/auth-session-token) | 이 글의 객체 수준 인가와 역할 검사         |

401 갱신 흐름은 인증 글에서 다뤄요. 이 글은 인증이 끝난 뒤의 판단에 집중해요.

## 화면 숨김 — 보안이 아니라 표시 규칙

OWASP는 클라이언트 쪽 권한 검사가 사용자 경험을 높이는 데는 허용될 수 있다고 설명해요. 하지만 접근을 결정하는 요소로 쓰면 안 된다고 설명해요. 클라이언트 로직은 쉽게 우회되기 때문이에요. 권한 검사는 서버, 게이트웨이, 서버리스 함수에서 해야 한다고 설명해요.

그래서 FE는 두 가지를 나눠 생각해요. 버튼을 숨기는 것은 헷갈리지 않게 하는 일이에요. 주문을 지키는 것은 서버가 하는 일이에요. 서버 검사가 있으면 버튼을 숨기는 것은 선택 사항이 돼요. 서버 검사가 없으면 버튼을 숨겨도 주문은 나가요.

## 객체 수준 인가 — 주문 id마다 주인 확인

OWASP API1:2023은 BOLA(Broken Object Level Authorization, 객체 수준 인가 실패)를 설명해요. 요청에 담긴 객체 ID를 바꾸면 접근할 수 있는 상태예요.

OWASP는 이 문제가 API 기반 애플리케이션에서 매우 흔하다고 설명해요. ID는 순차 정수, UUID, 일반 문자열 어느 것이든 될 수 있어요. 또 경로나 쿼리 문자열에서 쉽게 찾아진다고 설명해요.

### 예시 — URL의 id만 바꾸는 요청

예를 들어 회원 A가 `GET /orders/1042`를 보내요. 1042는 같은 조직 동료의 주문이에요. 주문 번호와 관계는 설명을 위한 예시예요.

서버가 "회원인가?"만 확인하고 통과시키면 응답에 동료 주문이 담겨요. 이것이 BOLA예요.

OWASP는 엔드포인트가 객체 ID를 받아 그 객체에 동작하면 객체 수준 인가 검사가 있어야 한다고 설명해요. 검사는 로그인한 사용자가 그 요청된 객체에 요청한 동작을 할 권한이 있는지 확인해야 해요.

OWASP는 세션의 사용자 id와 요청의 id를 비교하는 것만으로는 BOLA를 충분히 풀지 못한다고 설명해요. 주인 확인 하나로 끝나지 않고, 대상마다 정책을 적용해야 한다는 뜻이에요. 같은 타입의 객체에 접근할 수 있다고 해서 모든 객체에 접근할 수 있는 것은 아니라고 Authorization Cheat Sheet는 설명해요.

ID를 예측하기 어렵게 만드는 것도 방법이에요. 다만 Authorization Cheat Sheet는 ID를 숨기거나 무작위로 만드는 것만으로는 충분하지 않다고 설명해요. 무작위 ID는 열거 공격을 어렵게 할 뿐이고, 검사를 대신하지 않아요.

## RBAC와 ABAC — 역할 검사와 속성 검사 비교

RBAC(Role-Based Access Control)는 권한을 역할에 붙이고, 사용자에게 역할을 주는 모델이에요. NIST RBAC 페이지는 RBAC가 1992년 David Ferraiolo와 Rick Kuhn이 정식화했고, NIST 모델이 미국 국가 표준 359-2004로 채택됐다고 설명해요.

ABAC(Attribute-Based Access Control)는 속성으로 판단하는 모델이에요. NIST ABAC 페이지는 ABAC를 규칙 기반 접근 제어라고 설명하고, 설정은 쉽지만 관리가 복잡할 수 있다고 설명해요. OWASP Authorization Cheat Sheet는 NIST SP 800-162를 인용해, 주체 요청을 주체 속성, 객체 속성, 환경 조건, 정책에 따라 허용하거나 거부하는 모델이라고 설명해요.

| 비교        | RBAC                                                    | ABAC                                                           |
| ----------- | ------------------------------------------------------- | -------------------------------------------------------------- |
| 판단 근거   | 역할이 있는지                                           | 주체, 객체, 환경의 속성과 정책                                 |
| 객체 주인   | 역할만으로는 대상마다 나누기 어려워요                   | 주인 속성을 정책에 넣어 표현할 수 있어요                       |
| 멀티 테넌트 | 조직마다 규칙 세트를 따로 두는 부담이 생긴다고 설명해요 | 속성을 일관되게 정의하면 같은 정책으로 다룰 수 있다고 설명해요 |
| 관리        | 처음에는 쉽지만 역할이 늘면 테스트와 감사가 어려워져요  | 표현은 풍부하지만 정책과 속성을 함께 관리해야 해요             |

OWASP는 응용 프로그램 개발에는 ABAC와 ReBAC(관계 기반 접근 제어)를 보통 RBAC보다 더 선호해야 한다고 설명해요. 역할 검사가 여러 개 이어지면 빠뜨리기 쉽다는 점도 함께 적어요. 예를 들어 `hasAnyRole("SUPERUSER", "ADMIN", "ACCT_MANAGER")` 같은 조건이 여러 곳에 흩어지면 어느 쪽이 빠졌는지 찾기 어려워요.

실무에서는 역할로 동작을 가리고, 주인이나 조직 같은 속성으로 대상을 가리는 조합으로 시작하는 편이 좋아요. 역할만 있으면 대상을 못 가리고, 속성만 있으면 정책이 복잡해지기 때문이에요. 이 조합은 설계 판단이에요.

## 함수 수준 인가 — 관리자 기능을 역할로 막기

BFLA(Broken Function Level Authorization, 함수 수준 인가 실패)는 일반 사용자가 관리자 기능에 접근하는 문제예요. OWASP API5:2023은 일반 사용자가 관리자 엔드포인트에 접근할 수 있는지 묻도록 권해요. 또 GET을 DELETE로 바꿔 민감한 동작을 시도할 수 있는지도 확인하라고 설명해요. 다른 그룹의 기능을 URL을 추측해 호출할 수 있는지도 확인하라고 설명해요.

OWASP는 URL 경로만 보고 일반 기능인지 관리자 기능인지 단정하지 말라고 설명해요. 관리자 메뉴가 없어도 `/admin/orders/export` 같은 경로는 호출될 수 있어요. 그래서 관리자 기능도 서버에서 역할을 확인해야 해요.

OWASP는 객체 ID를 통해 다른 사람의 객체에 접근하는 것을 BOLA로, 접근하면 안 되는 기능에 접근하는 것을 BFLA로 나눠요. 이 글의 내보내기 예시는 둘이 같이 걸린 경우예요. 관리자 역할은 기능을 가리고, 조직은 대상을 가려요.

## 401 · 403 · 404 — 존재 숨기기 선택

RFC 9110은 세 상태 코드를 다음처럼 정의해요.

| 상태             | RFC 9110의 정의                                                            | FE가 할 일                                                                  |
| ---------------- | -------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| 401 Unauthorized | 유효한 자격 증명이 없어요. 서버는 `WWW-Authenticate` 헤더를 보내야 해요.   | 로그인이나 토큰 갱신 흐름으로 보내요.                                       |
| 403 Forbidden    | 서버가 요청을 이해했지만 거부해요. 자격 증명이 있어도 부족하다는 뜻이에요. | 같은 자격 증명으로 자동 재시도하지 않는 것이 좋아요. 권한 안내를 보여 줘요. |
| 404 Not Found    | 현재 표현이 없거나, 있다는 사실을 밝히고 싶지 않을 때 써요.                | 없는 주문과 같은 화면을 보여 줘요.                                          |

RFC 9110은 403 설명에서 금지된 대상의 존재를 숨기고 싶은 서버는 404를 줄 수 있다고 설명해요. 단정이 아니라 선택지예요. 이 선택이 "404 숨기기" 옵션이에요.

403과 404 중 무엇을 고를지는 설계 판단이에요. 역할 실패는 403으로 답하는 편이 좋아요. 관리자 메뉴의 존재는 보통 공개돼도 되기 때문이에요. 객체 실패는 주문 번호의 존재 자체가 민감하면 404로 숨기는 편이 좋아요.

시뮬레이터에서 "404로 숨기기"를 켜도 역할 실패는 403으로 남아요.

## 목록 API — 테넌트 조건을 쿼리에 넣기

목록 API는 객체 하나를 보는 API보다 자주 놓쳐요. 목록에서 다른 조직의 주문을 빼는 것과, 상세 주소로 직접 들어가는 것을 막는 것은 다른 검사예요. 둘 다 서버에서 해야 해요.

OWASP Multi-Tenant Security Cheat Sheet는 테넌트가 정해진 리소스마다 인증된 주체가 그 테넌트에서 행동할 수 있는지 확인하라고 설명해요. 소유권이 테넌트에 묶여 있으면 조회 조건이나 권한 정책에 테넌트 범위를 넣으라고 설명해요. `tenant_id`와 `resource_id`를 묶은 복합 키는 한 가지 선택지이고, 모든 경우에 필요한 것은 아니라고 설명해요.

요청 헤더나 쿼리로 테넌트를 넘기는 설계에도 주의해야 해요. 같은 치트시트는 요청, 토큰, 헤더의 테넌트 식별자를 바꾸는 공격을 Tenant Context Injection으로 나열해요. 예를 들어 `GET /orders?orgId=B`처럼 FE가 조직 id를 보내면, 서버는 이 값을 믿지 않고 로그인한 사용자의 조직을 조건에 넣어야 해요. FE가 보낸 값은 참고만 해요.

목록 페이지를 나누는 방법은 [페이지네이션 — offset · cursor](/m/pagination)에서 다뤄요. 나누는 방식과 권한 조건은 같은 쿼리 안에서 함께 적용돼야 해요.

## 시뮬레이터 안내 — 검사 전략 비교

시뮬레이터는 요청자(로그인하지 않음, 회원, 조직 관리자), 소속 조직, 주문 주인(본인, 같은 조직 동료, 다른 조직 고객), 요청 동작(조회, 수정, 조직 주문 내보내기), 서버 검사 전략을 고르게 해요. 결과로 응답 코드와 주문 내용이 담기는지 보여 줘요.

세 전략을 같은 요청에 바꿔 보세요. "화면 숨김만"에서는 어떤 요청도 막히지 않아요. "역할 검사만"에서는 회원 역할로도 동료 주문이 나가요. "역할 + 소유자 검사"에서만 동료 주문이 403으로 막혀요.

시뮬레이터는 설명을 위한 순수 모델이에요. 인증은 이미 되어 있다고 가정해요. 실제 서비스의 정책이나 데이터 구조를 흉내 낸 것은 아니에요.

## FE 체크 포인트 — 서버 권한 정보 · 버튼 표시

서버가 응답에 권한 정보를 함께 내려주면 FE가 버튼을 그릴 수 있어요. 예시 응답은 이래요.

```json
{ "id": 1042, "status": "paid", "permissions": { "canEdit": false, "canExport": false } }
```

이 값은 화면 표시를 위한 힌트예요. 버튼을 누르면 서버가 다시 검사해요. 권한 정보가 낡았을 수 있으니, 403을 받으면 권한 정보를 다시 받는 편이 좋아요. 이 판단은 설계 판단이에요.

FE가 역할 표를 따로 들고 있으면 정책이 서버와 화면 두 곳에 생겨요. 그래서 권한 판단은 서버에서 내려주는 값을 쓰는 편이 좋아요. 권한이 바뀌었을 때 고칠 곳도 하나로 줄어요.

403 응답은 로그인 화면으로 보내지 말고 권한 안내를 보여 줘요. 응답 형식은 [에러 응답 설계 — 상태 코드와 문제 형식](/m/api-errors)에서 다뤄요.

404로 숨긴 경우에는 없는 주문과 같은 문구를 쓰는 편이 좋아요.

## 정리 — 검사 위치 · 객체 단위 · 실패 응답 기준

권한 검사는 서버에서 요청마다 해요. ID로 접근하는 대상마다 주인이나 테넌트를 확인해요. 역할은 동작을 가리고, 주인이나 조직 같은 속성은 대상을 가려요. 실패는 역할 실패라면 403으로 답하고, 객체 실패는 존재를 숨길지에 따라 403이나 404로 답해요.

인증 흐름은 [로그인 유지 — 세션과 토큰](/m/auth-session-token)을, 처리 위치의 판단 기준은 [서버 · 클라 처리 판단](/m/server-or-client)을 함께 읽어 보세요.
