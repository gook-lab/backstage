가입 완료 화면은 떴는데 인증 메일이 일부 사용자에게만 안 와요. 같은 시간에 보낸 다른 메일은 잘 가고, 스팸함에 들어간 메일도 있어요. 화면의 "다시 보내기" 버튼을 누르면 "메일을 보냈어요"라는 문구가 나오지만, 메일은 여전히 안 와요. 이 글은 이 메일이 서버에서 어떻게 나가고 어디서 사라지는지 따라가요. 그리고 FE가 무엇을 보여 주고 무엇을 말하지 않아야 하는지 정리해요.

아래 시뮬레이터에서 수신 상태와 발신 설정, 재시도 정책을 바꿔 보면 메일 한 통이 전달, 재시도 후 전달, 스팸함 가능성, 반송, 유실 중 어디로 가는지 볼 수 있어요.

## 요청 응답과 발송 분리 — 큐에 넣고 접수만 알리기

가입 API가 메일 서버의 응답을 기다리면, 메일 서버가 느린 순간 가입 요청도 같이 느려져요. 그래서 인증 메일은 요청 안에서 보내지 않고 큐에 넣어요. 요청은 계정과 토큰을 저장한 뒤 "발송을 예약했어요" 수준으로 응답하고, 실제 전송은 워커가 나눠서 해요.

이 구조에서 응답은 메일이 전달됐다는 뜻이 아니에요. 응답이 말하는 것은 "요청을 받아 저장했다"까지예요. 큐의 전달 보장과 재시도 간격은 [메시지 큐와 재처리](/m/message-queue)에서 자세히 다뤄요.

FE는 접수 응답을 받은 뒤 "메일을 보냈어요"라고 쓸 수 있어요. 다만 "도착했어요"라고 쓰면 안 돼요. 도착 여부는 이 응답으로 알 수 없어요.

## SMTP 응답 — 4yz 일시 실패와 5yz 영구 실패 나누기

메일을 보내는 쪽은 수신 서버의 응답 코드 첫 자리로 다음 행동을 정해요. [RFC 5321](https://www.rfc-editor.org/rfc/rfc5321.txt)은 4yz를 "같은 요청을 바꾸지 않고 반복하면 성공할 수 있는 일시 실패"로, 5yz를 "같은 요청을 반복하지 말아야 하는 영구 실패"로 설명해요.

| 응답 | 분류      | 대표 코드               | 보내는 쪽이 할 일             |
| ---- | --------- | ----------------------- | ----------------------------- |
| 4yz  | 일시 실패 | 421, 450, 451, 452      | 간격을 두고 다시 시도해요     |
| 5yz  | 영구 실패 | 550, 551, 552, 553, 554 | 재시도하지 않고 반송 처리해요 |

확장 상태 코드도 같은 기준이에요. [RFC 3463](https://www.rfc-editor.org/rfc/rfc3463.txt)은 `4.X.X`를 지속적 일시 실패, `5.X.X`를 영구 실패로 나눠요. `550 5.1.1`은 메일함 주소가 없다는 뜻이고, 이 코드는 영구 실패에만 쓰인다고 명시해요. 메일함이 가득 찬 `X.2.2`는 반대로 일시 실패(4.X.X)로 분류돼요. 사용자가 메일함을 비우면 다시 받을 수 있기 때문이에요.

4yz를 받았을 때 재시도 간격도 정해져 있어요. RFC 5321은 재시도 간격을 30분 이상으로 두는 것이 좋다고(SHOULD) 설명하고, 포기까지는 최소 4~5일이 필요하다고 설명해요. 시뮬레이터의 분 단위 값은 감을 잡기 위한 예시라서 이 권장보다 짧아요.

## 반송 처리 — 비동기 알림과 주소 상태 기록

영구 실패는 대개 반송 알림으로 돌아와요. RFC 5321은 반송 알림이 원래 메일의 발신 경로(MAIL FROM)로 가도록 설명하고, 알림 메일 자체는 빈 발신 경로(`MAIL FROM:<>`)로 보내도록 정해요([4.5.5](https://www.rfc-editor.org/rfc/rfc5321.txt)). 그래서 알림은 보통 앱 서버의 봉투 발신 주소로 돌아와요. 사용자 화면으로 바로 가지 않아요.

반송을 받으면 앱은 그 주소를 "반송됨"으로 기록해 다음 발송을 멈출지, 다른 주소를 요청할지 판단할 수 있어요. 이 기록은 설계 선택이에요. RFC가 정한 규칙은 아니에요.

반송 사실을 사용자에게 그대로 말하면 안 돼요. "이 주소로는 메일을 보낼 수 없어요"라는 문장은 계정이 있는지 없는지를 드러내요. 가입이나 재설정 요청에서 계정 존재 여부를 드러내지 말라는 것이 [OWASP 인증 치트시트](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)의 기본 원칙이에요.

## 발신 인증 — SPF · DKIM · DMARC가 각각 확인하는 것

메일이 스팸함에 가거나 거절되는 이유 가운데 발신 설정이 큰 몫을 해요. 세 기술은 서로 다른 것을 확인해요.

| 방식  | 확인하는 것                                                                                                 | 근거                                                            |
| ----- | ----------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| SPF   | 연결한 SMTP 클라이언트 IP가 봉투 발신자(MAIL FROM) 도메인이 허락한 발신 서버인지                            | [RFC 7208](https://www.rfc-editor.org/rfc/rfc7208.txt) 2.4      |
| DKIM  | 메일에 붙은 서명이 서명 도메인(`d=`)의 공개 키로 검증되는지. 서명은 본문 해시(`bh=`)와 지정한 헤더를 덮어요 | [RFC 6376](https://www.rfc-editor.org/rfc/rfc6376.txt) 2.5, 3.5 |
| DMARC | 사용자가 보는 From 도메인이 SPF 또는 DKIM이 통과한 도메인과 맞는지(정렬), 실패했을 때 수신 측이 어떻게 할지 | [RFC 7489](https://www.rfc-editor.org/rfc/rfc7489.txt) 3.1, 6.3 |

세 가지를 나눠 보면 헷갈리는 점이 정리돼요.

- SPF는 봉투 발신자 도메인을 봐요. 사용자가 보는 From과 다를 수 있어요. RFC 7489는 SPF가 MAIL FROM 도메인을 인증하지만, DMARC는 From 도메인과 맞아야 한다고 설명해요.
- DKIM은 전달 중에 내용이 바뀌면 서명이 깨질 수 있어요. RFC 6376은 전달 뒤 서명이 살아남는다는 보장이 없다고 설명해요.
- DMARC 정책은 세 가지예요. `none`은 조치를 요청하지 않고, `quarantine`은 실패한 메일을 의심스럽게 다루라는 요청이고, `reject`는 거부를 요청해요. RFC 7489는 quarantine을 스팸함 배치, 더 면밀한 검사, 의심 표시 중 수신 측 능력에 맞는 방식으로 처리한다고 설명해요.

스팸함에 들어갈지는 RFC가 정하지 않아요. 수신 메일 서비스가 판단하는 몫이에요. 그래서 발신 설정을 맞춰도 특정 수신자의 스팸함 배치는 보장되지 않아요. 발신 설정은 "인증이 실패했다"는 신호를 줄이는 것이에요.

SPF를 설계할 때는 조회 한도도 봐야 해요. [RFC 7208](https://www.rfc-editor.org/rfc/rfc7208.txt) 4.6.4는 `include`, `a`, `mx`, `ptr`, `exists`, `redirect`처럼 DNS 조회를 일으키는 항목이 전체 10개를 넘으면 안 된다고 설명해요. 한도를 넘기면 결과는 `permerror`가 돼요.

## 인증 링크 토큰 — 한 번만 쓰고 만료되게

인증 · 재설정 링크의 토큰은 [OWASP 비밀번호 찾기 치트시트](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)가 정리한 기준을 따라요.

- 암호학적으로 안전한 난수로 만들고, 무차별 대입을 막을 만큼 길게 만들어요.
- 토큰을 사용자와 연결해 저장하고, 쓴 뒤에는 무효화해요.
- 적절한 기간이 지나면 만료되게 해요. 치트시트는 한 번만 쓰이고 적절한 기간이 지나면 만료되어야 한다고 설명해요.
- 유효한 토큰이 제시되기 전에는 계정 상태를 바꾸지 않아요.

재설정 링크의 호스트는 요청의 Host 헤더로 만들지 않아요. 고정하거나 허용 목록으로 검증하라고 치트시트는 설명해요. 토큰이 URL에 들어가면서 생기는 노출 문제는 [민감 정보 누출](/m/sensitive-data)에서 다뤄요.

## 다시 보내기 — 쿨다운과 같은 응답 문구

다시 보내기 버튼은 두 가지를 같이 지켜야 해요. 메일 발송이 과하게 나가지 않아야 하고, 응답이 계정 존재 여부를 알려 주면 안 돼요.

쿨다운은 같은 주소에 대한 요청 사이의 최소 간격이에요. 치트시트는 요청 횟수 제한을 계정 단위로 두라고 설명해요. 그렇지 않으면 한 계정에 재설정 요청이 몰리고, 사용자의 받은편지함이 채워져요. 일반적인 요청 제한 알고리즘은 [레이트 리밋 알고리즘](/m/rate-limiting)에서 다뤄요.

응답 문구는 계정이 있든 없든 같아야 해요. OWASP는 재설정 응답의 올바른 예로, 해당 주소가 데이터베이스에 있다면 재설정 메일을 보내 드린다는 문장을 들어요. 영문 예시의 뜻을 옮긴 것이에요. 응답 시간도 두 경우에서 비슷해야 해요. 치트시트는 응답이 같은 시간에 돌아오도록 맞추라고 설명해요.

이 원칙을 지키려면 쿨다운도 계정 존재와 무관하게 주소 기준으로 기록해야 해요. 계정이 없는 주소의 요청을 기록하지 않으면, 대기 중인지 아닌지가 계정 존재 여부를 드러내요. 시뮬레이터의 "다시 보내기"는 계정이 있을 때와 없을 때 같은 대기 문구를 받아요.

## FE 체크 포인트 — 응답 문구와 버튼 상태

- 접수 응답과 전달 결과를 다른 문구로 나눠요. 접수는 "보냈어요"까지만 말해요.
- 다시 보내기 버튼 상태는 서버 응답을 따라요. 쿨다운 중이면 남은 시간을 보여 주고 버튼을 막아요.
- 반송, 유실, 스팸 판정은 사용자 화면에서 볼 수 없어요. 그래서 "스팸함도 확인해 주세요" 안내와 재발송 경로를 같이 둬요.
- 형식이 틀린 주소는 발송 전에 알려 줄 수 있어요. 형식 검사는 계정 존재 여부를 드러내지 않아요.
- 쿨다운 안내에는 대기 시간만 넣고, 계정이나 주소 상태에 대한 말은 넣지 않아요.

## 시뮬레이터 안내

시뮬레이터는 메일 한 통이 한 수신자에게 가는 경로를 순수 함수로 계산해요.

- **수신 상태**: 정상, 일시 거절(451), 없는 주소(550 5.1.1) 중 하나를 골라요.
- **일시 거절 시간**을 늘리면 고정 간격 재시도는 포기하고, 백오프는 뒤늦게 전달하는 경우가 생겨요.
- **DMARC 정책**을 스팸함(quarantine)으로 두고 From 정렬을 끄면 전달은 되지만 스팸함 가능성이 떠요.
- **다시 보내기**를 두 번 누르면 쿨다운이 걸려요. "1분 지나기"를 세 번 누르고 다시 보내면 접수돼요. 계정 없음을 고르면 접수 문구는 같고 실제 발송만 없어요.

결과 카드의 "유실"이 어떤 조건에서 생기는지, 재시도 정책을 바꿔 가며 확인해 보세요.

## 정리 — 발송 분리 · SMTP 4yz·5yz 분류 · 발신 인증 · 같은 응답 문구

- 인증 메일은 요청 응답과 떼어 큐에서 보내고, 접수와 전달을 다른 문구로 나눠요.
- SMTP 4yz는 재시도하고, 5yz는 반송으로 처리해요. 재시도를 포기하면 사용자에게 알리는 경로를 따로 둬요.
- SPF는 봉투 발신자, DKIM은 서명 도메인, DMARC는 From 정렬을 확인해요. 스팸함 배치는 수신 측 판단이에요.
- 인증 링크 토큰은 한 번만 쓰고 만료되게 해요.
- 다시 보내기는 쿨다운을 계정 존재와 무관하게 주소 기준으로 걸고, 응답 문구를 같게 유지해요.
