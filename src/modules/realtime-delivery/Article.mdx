채팅 메시지가 도착하면 상대 화면에 바로 떠야 해요. 알림 배지는 새 알림이 생기면 숫자가 바뀌어야 하고, 주문 상태는 "배송 시작"이 되는 순간 버튼 문구가 바뀌어야 해요. 세 장면 모두 **서버가 먼저 말하는** 순간이 필요해요.

이 글은 HTTP가 서버에서 먼저 말하기 어려운 이유에서 출발해요. 그다음 네 가지 방식(짧은 폴링, 롱 폴링, SSE, WebSocket)이 연결을 어떻게 쓰는지, 연결이 끊겼을 때 무엇을 놓치는지를 차례로 봐요.

글의 숫자는 모두 설명을 위한 예시예요. 아래 시뮬레이터의 기본값과 같아요. 시뮬레이터에서 10분 동안 클라이언트 10명에게 분당 60건의 이벤트가 도착하고, 가운데 90초 동안 연결이 끊겨요.

## 서버 푸시의 한계 — HTTP 요청-응답 구조

HTTP는 클라이언트가 요청하고 서버가 응답하는 구조예요. 서버가 할 말이 생겨도 보낼 통로가 없으면 전할 수 없어요. 그래서 실시간 기능은 "통로를 어떻게 계속 열어 둘지"의 문제로 바뀌어요.

통로를 여는 방법은 크게 두 갈래예요. 하나는 클라이언트가 자주 물어보는 방법이고, 다른 하나는 응답을 늦게 주거나 연결 자체를 열어 두는 방법이에요. 이 글의 네 방식이 그 두 갈래에 들어가요.

## 통신 방식 네 가지 — 폴링 · 롱 폴링 · SSE · WebSocket

| 방식      | 방향              | 연결                       | 지연               | 맞는 곳                         |
| --------- | ----------------- | -------------------------- | ------------------ | ------------------------------- |
| 짧은 폴링 | 클라이언트가 물음 | 요청마다 새로 열고 닫아요  | 간격 P의 절반 근처 | 몇 분에 한 번 바뀌는 값         |
| 롱 폴링   | 서버가 늦게 답함  | 응답이 올 때까지 열어 둬요 | 거의 없어요        | SSE를 쓸 수 없는 환경의 알림    |
| SSE       | 서버 → 클라이언트 | 하나를 계속 열어 둬요      | 거의 없어요        | 알림 배지, 주문 상태, 피드 갱신 |
| WebSocket | 양방향            | 하나를 계속 열어 둬요      | 거의 없어요        | 채팅, 협업 편집, 게임           |

### 짧은 폴링 — 고정 간격 질의

가장 단순한 방법이에요. 클라이언트가 2초, 10초처럼 정해진 간격으로 "새 이벤트 있어요?"라고 물어봐요. 서버는 그 순간 쌓인 것을 돌려주고, 없으면 빈 응답을 줘요.

질문 간격을 P 초로 두면, 이벤트는 다음 질문 시각까지 기다려요. 이벤트가 질문 사이에 고르게 도착한다면 평균 지연은 P/2에 가까워요. 간격을 10초로 잡으면 평균 5초쯤 늦게 보여요.

시뮬레이터에서 간격을 10초로 두고 이벤트를 분당 6건 정도로 줄여 보세요. 대부분의 응답이 빈 응답으로 돌아와요. 빈 응답도 HTTP 요청이라서 서버 입장에서는 같은 비용을 치러요.

### 롱 폴링 — 응답 지연 보류

롱 폴링은 짧은 폴링과 같은 HTTP 요청을 쓰지만, 서버가 새 이벤트가 생길 때까지 응답을 미뤄요. 이벤트가 오면 바로 응답하고, 이벤트 없이 제한 시간(예시로 30초)이 지나면 빈 응답을 줘요. 클라이언트는 응답을 받자마자 다음 요청을 보내요.

지연은 거의 없어요. 대신 서버는 기다리는 요청마다 연결 하나를 붙잡고 있어요. 이벤트가 적으면 빈 응답이 시간 제한마다 나와요.

### SSE — 서버 → 클라이언트 단방향 스트림

SSE(Server-Sent Events)는 `text/event-stream` 형식의 응답을 끊지 않고 흘려 보내는 방식이에요. 클라이언트는 `EventSource` 객체를 만들고, 서버는 `data:` 줄을 빈 줄로 구분해서 보내요. 메시지는 UTF-8 텍스트예요. [WHATWG HTML 명세](https://html.spec.whatwg.org/multipage/server-sent-events.html)는 이 형식과 `EventSource`의 동작을 정의해요.

SSE는 방향이 하나예요. 서버에서 클라이언트로만 흘러요. 클라이언트가 보낼 것이 있으면 따로 `POST` 요청을 보내요. 알림, 주문 상태, 피드 갱신처럼 서버가 주도하는 데이터에 맞아요.

`EventSource`는 연결이 끊기면 스스로 다시 연결해요. 명세는 연결을 다시 세우는 과정을 정의하고, 재연결 때 `Last-Event-ID` 요청 헤더에 마지막으로 받은 `id`를 실어 보내요. 서버는 이 값을 보고 그 뒤의 이벤트부터 보내면 돼요. [MDN의 EventSource 문서](https://developer.mozilla.org/en-US/docs/Web/API/EventSource)와 [Using server-sent events](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)도 같은 흐름을 설명해요.

서버가 `retry:` 필드를 보내면 재연결까지 기다릴 시간을 바꿀 수 있어요.

### WebSocket — 양방향 전이중 연결

WebSocket은 HTTP로 연결을 시작한 뒤 프로토콜을 바꿔 양쪽이 자유롭게 보내는 연결이에요. [RFC 6455](https://www.rfc-editor.org/rfc/rfc6455.html)에 따르면 클라이언트는 `Upgrade: websocket`과 `Sec-WebSocket-Key`를 담은 GET 요청을 보내요. 서버가 `101 Switching Protocols`로 답하면 그다음부터는 프레임을 주고받아요.

프레임에는 Ping과 Pong이 있어요. RFC는 Ping을 받은 쪽이 Pong을 반드시 돌려주도록 정해요. 이 두 프레임으로 연결이 살아 있는지 확인할 수 있어요.

채팅이 WebSocket에 맞는 이유는 양방향이기 때문이에요. 상대의 메시지를 받는 연결과 내가 보내는 연결을 나눌 필요가 없어요.

[MDN의 WebSocket API 문서](https://developer.mozilla.org/en-US/docs/Web/API/WebSocket)가 지적하듯 이 API에는 역압(backpressure)을 거는 방법이 없어요. 메시지가 처리보다 빨리 오면 앱이 메시지를 메모리에 쌓거나, 앱이 멈추거나, 연결이 끊길 수 있어요. 받는 쪽에서 처리 속도를 봐야 해요.

### 탭 종료 후 알림 — Web Push

SSE와 WebSocket은 페이지가 열려 있어야 해요. 탭을 닫으면 연결도 사라져요. [MDN의 Push API 문서](https://developer.mozilla.org/en-US/docs/Web/API/Push_API)는 Push API가 웹 앱이 전경에 있지 않거나 로드되어 있지 않아도 서버가 보낸 메시지를 받을 수 있게 한다고 설명해요. 실제 수신은 서비스 워커가 맡아요.

알림을 탭이 닫힌 뒤에도 보여 줘야 하면 Web Push가 필요해요. 대신 구독 절차, 사용자 동의, 서비스 워커 배포를 모두 맡아야 해요. 채팅 본문을 푸시로 보내는 것은 보안과 개인정보 측면에서 따로 판단할 일이에요.

### WebTransport — 신규 방식 · 지원 범위 확인

[MDN의 WebTransport API 문서](https://developer.mozilla.org/en-US/docs/Web/API/WebTransport_API)는 WebTransport가 HTTP/3과 QUIC 위에서 돌고, 스트림과 데이터그램을 함께 쓸 수 있다고 설명해요. 같은 문서가 2026년 3월부터 최신 기기와 브라우저에서 Baseline으로 쓸 수 있다고 설명해요.

다만 오래된 기기나 브라우저에서는 다를 수 있어요. 따라서 지금 서비스의 기본 선택으로 두기보다는, 지원 범위를 확인한 뒤 고려하는 편이 안전해요.

## 서버 비용 — 연결당 자원 점유

짧은 폴링은 요청이 끝나면 연결이 사라져요. 롱 폴링과 SSE, WebSocket은 연결이 살아 있는 동안 서버 자원을 써요. 클라이언트 한 명당 보통 다음 자원이 들어요.

- 연결을 나타내는 소켓(파일 디스크립터 하나)
- 연결마다 쌓는 버퍼와 상태
- 연결을 유지하기 위한 하트비트와 타이머

클라이언트가 10만 명이면 열린 연결도 10만 개예요. 클라이언트 한 명의 메모리가 작아도 곱하면 커져요. 그래서 "접속자 수 × 연결당 비용"을 먼저 계산하는 습관이 필요해요.

### 프록시와 유휴 시간 제한

서버 앞에는 보통 로드 밸런서나 리버스 프록시가 있어요. 프록시는 응답을 모아서 보내려고 버퍼링을 해요. SSE는 이벤트가 바로 나가야 하니까 버퍼링이 문제가 돼요.

nginx 문서에 따르면 `proxy_buffering` 기본값은 `on`이에요. 응답 헤더 `X-Accel-Buffering: no`로 끌 수 있다고도 적혀 있어요.

SSE를 프록시 뒤에서 돌린다면 이 경로의 버퍼링 설정을 확인해야 해요. 예를 들어 해당 location에 `proxy_buffering off;`를 두는 식이에요(설정 예시이며, 환경에 맞게 검토해야 해요).

같은 문서에 따르면 `proxy_read_timeout` 기본값은 60초예요. 이 시간은 업스트림에서 읽기 두 번 사이의 간격에 걸려요.

이벤트가 한동안 없으면 프록시가 연결을 끊을 수 있어요. 그래서 SSE나 WebSocket에는 주기적으로 빈 주석(SSE의 `:` 줄)이나 Ping을 보내 연결이 살아 있음을 알려야 해요.

### 여러 서버 — pub/sub 백플레인

서버가 한 대면 연결을 가진 서버가 이벤트를 만든 서버이기도 해요. 서버가 여러 대가 되면 주문을 처리한 서버와 클라이언트가 붙은 서버가 달라져요. 이때 이벤트를 연결 쪽 서버로 전달할 통로가 필요해요. 그 통로가 pub/sub 백플레인이에요.

[Redis Pub/Sub 문서](https://redis.io/docs/latest/develop/pubsub/)는 Redis Pub/Sub이 at-most-once 전달 의미를 가진다고 설명해요. 메시지를 한 번 보내면 다시 보내지 않아요. 구독자가 그 순간 끊겨 있다면 메시지를 받을 수 없어요.

즉 백플레인은 "지금 붙어 있는 연결에게 전하는" 통로이지, 놓친 이벤트를 저장하는 곳이 아니에요. 놓친 이벤트를 채우려면 이벤트를 따로 저장해야 해요.

### 스티키 세션 — 장단점

로드 밸런서가 같은 클라이언트를 같은 서버로 보내면(스티키 세션) 연결 관리가 쉬워져요. 대신 서버를 줄이거나 배포할 때 그 서버의 연결이 한꺼번에 끊기고, 부하가 고르게 나뉘지 않을 수 있어요.

이 글에서는 백플레인이 있으면 스티키 세션 없이도 전달할 수 있다는 점만 기억하면 돼요.

어느 쪽을 택할지는 배포 방식과 운영 여력을 보고 정하는 설계 판단이에요.

## 전달 보장 — 누락 · 중복 · 순서

이벤트는 세 가지 방식으로 틀어질 수 있어요.

- 연결이 끊긴 동안 도착한 이벤트를 놓쳐요.
- 재연결 과정에서 같은 이벤트를 두 번 받아요.
- 네트워크나 서버 경로에 따라 순서가 뒤바뀌어 보여요.

### 재연결 — 놓친 구간 채우기

끊긴 뒤 다시 붙을 때 놓친 구간을 채우는 방법은 두 가지예요.

1. **이어받기**: 마지막으로 받은 id나 커서를 보내고, 서버가 그 뒤의 이벤트를 다시 보내요. SSE는 `Last-Event-ID`가 이 역할을 해요. 서버는 이벤트를 일정 기간 저장해야 해요.
2. **상태 재조회**: 이벤트를 다시 받지 않고, 재연결 뒤 현재 상태를 API로 한 번 가져와요. 주문 상태처럼 "지금 값"이 중요한 데이터에 잘 맞아요.

시뮬레이터에서 "재연결 때 놓친 구간 이어받기"를 끄고 90초 끊김을 켜면, SSE와 WebSocket에서 끊긴 동안의 이벤트가 사라져요. 이어받기를 켜면 같은 흐름에서도 하나도 잃지 않아요.

짧은 폴링은 매번 "마지막 본 시점 이후"를 묻기 때문에 끊김 뒤에도 잃지 않아요. 대신 끊긴 동안은 지연이 쌓여요.

### 중복 제거 — id 기준 한 번만 반영

보장 수준은 보통 "최소 한 번(at-least-once)"으로 잡아요. 같은 이벤트가 재연결이나 재시도 때문에 두 번 올 수 있어요. 그러니 FE는 이벤트마다 고유한 id를 보고, 이미 반영한 id는 버려야 해요.

```ts
function applyEvent(seen: Set<string>, ev: { id: string; body: unknown }, apply: (body: unknown) => void) {
  if (seen.has(ev.id)) return;
  seen.add(ev.id);
  apply(ev.body);
}
```

`seen`을 무한정 키우면 메모리가 계속 늘어요. 최근 id 몇백 개만 남기거나, 대화방이나 주문 단위로 나눠 두는 방식이 필요해요. 이것도 설계 판단이에요.

### 순서 보장 — 대상 단위 시퀀스

모든 이벤트의 전역 순서를 지키려면 비용이 커요. 실제로는 대화방 하나, 주문 하나처럼 대상 단위 순서만 지키면 대부분 충분해요. 서버가 대상마다 번호(시퀀스)를 붙이고, FE는 번호가 건너뛰면 빈 구간을 채우는 방식으로 맞춰요.

## 브라우저 연결 수 — HTTP/1.1과 HTTP/2의 차이

[MDN의 Using server-sent events](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)는 HTTP/2를 쓰지 않을 때 SSE에 최대 연결 수 제한이 있다고 경고해요. 제한은 탭마다가 아니라 브라우저 전체에 걸리고, 탭을 여러 개 열면 특히 불편해요.

같은 문서는 이 수치를 흔히 도메인당 6개로 알려져 있다고 적고, 그 출처로 Stack Overflow를 인용해요.

예를 들어 탭 여섯 개가 각각 SSE를 하나씩 열면 6개를 모두 써요. 일곱 번째 탭부터는 새 연결이 대기하거나 실패할 수 있어요. 해결책은 두 가지예요.

- **HTTP/2를 쓰기**: MDN은 HTTP/2에서는 동시 스트림 수가 서버와 클라이언트 사이에서 협상되고 기본값은 100이라고 설명해요. 같은 연결 안에서 스트림을 여러 개 쓸 수 있어 제한이 훨씬 넉넉해요.
- **탭 사이에서 연결 하나를 공유하기**: `BroadcastChannel`이나 `SharedWorker`로 한 탭만 연결을 열고 나머지 탭에는 전달하는 방식이에요. 구현 범위가 넓어지니 필요한 만큼만 쓰세요.

WebSocket도 탭마다 따로 열면 연결과 메모리가 탭 수만큼 쌓여요. "컴포넌트마다 소켓 하나"는 피하고, 앱 전체에서 하나만 두고 구독을 나누는 방식이 좋아요.

## 방식 고르기 — 결정 표

| 상황                                     | 추천                         | 이유                                                              |
| ---------------------------------------- | ---------------------------- | ----------------------------------------------------------------- |
| 몇 분에 한 번 바뀌는 값                  | 짧은 폴링                    | 구현이 가장 단순하고 빈 응답 비용이 감당 가능해요                 |
| 주문 상태, 결제 결과 확인                | 짧은 폴링 (백오프) 또는 SSE  | 상태가 몇 번만 바뀌고, 놓치면 조회로 다시 맞출 수 있어요          |
| 알림 배지, 새 알림 개수                  | SSE                          | 서버 → 클라이언트 한 방향이고, 자동 재연결과 id 이어받기가 있어요 |
| 채팅, 입력 중 표시, 읽음 표시            | WebSocket                    | 양쪽이 자주 보내요                                                |
| 탭을 닫은 뒤에도 알림이 필요             | Web Push                     | 페이지가 로드되지 않아도 서비스 워커가 받을 수 있어요             |
| 프록시나 방화벽이 WebSocket을 막는 환경  | SSE 또는 롱 폴링             | HTTP로만 흘러서 통과하기 쉬워요                                   |
| 대규모 접속자, 브라우저 연결 수가 부족함 | HTTP/2 + SSE, 또는 짧은 폴링 | 연결 한도를 HTTP/2가 넓히고, 폴링은 연결을 오래 잡지 않아요       |

표의 추천은 설명을 위한 판단이에요. 실제 선택은 이벤트 빈도, 방향, 탭이 닫혔을 때의 필요, 인프라 제약을 함께 봐서 정하세요.

## FE 체크 포인트

- **재연결은 백오프와 jitter로.** 끊기면 즉시 다시 붙지 말고 지수 백오프에 jitter를 더해요. 같은 시각에 모든 탭이 붙으면 서버에 재연결 폭풍이 와요. 자세한 방법은 [가상 대기실 · 처리량 제한](/m/waiting-room)에서 이미 다뤘어요.
- **id로 이어받기.** SSE는 `Last-Event-ID`가 자동으로 붙어요. WebSocket은 마지막 id나 커서를 직접 보내야 해요.
- **화면 복귀 때 다시 맞추기.** 탭이 숨겨졌다가 보이면 [Page Visibility API](https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API)의 `visibilitychange`로 감지해요. 복귀할 때 상태를 한 번 재조회하면 숨긴 동안의 변화를 맞출 수 있어요.
- **숨긴 탭은 폴링을 줄여요.** 숨긴 동안 폴링 간격을 늘리거나 멈추면 배터리와 서버 부하를 줄일 수 있어요. 이 판단은 설계 권장이에요.
- **online 이벤트로 복구 시도.** 네트워크가 돌아왔을 때 연결을 다시 시도하면 기다림을 줄일 수 있어요.
- **id로 중복 제거.** 같은 id는 한 번만 반영해요. 메모리에 쌓이지 않게 상한을 두세요.
- **하트비트와 타임아웃 감지.** 일정 시간 데이터가 없으면 연결이 죽었다고 보고 다시 붙어요. 프록시의 유휴 시간 제한보다 짧은 간격으로 하트비트를 보내세요.
- **연결은 하나만.** 컴포넌트마다 소켓이나 `EventSource`를 만들면 브라우저 연결 한도를 금방 써요. 앱 전체에서 하나를 열고 구독자 목록으로 나눠 주세요.
- **언마운트 때 닫기.** 화면을 떠날 때 `EventSource.close()`나 `WebSocket.close()`를 호출해요. 닫지 않으면 연결과 콜백이 쌓여요.
- **받는 쪽 처리 속도 보기.** WebSocket은 역압이 없어서 메시지가 몰리면 메모리가 차요. 메시지를 모아 한 번에 그리거나, 우선순위가 낮은 이벤트는 버리는 판단이 필요해요.

## 정리 — 방향 · 비용 · 재연결 기준 선택

알림은 서버가 한 방향으로 보내면 되니 SSE가 잘 맞아요. 채팅처럼 양쪽이 자주 보내면 WebSocket을 고르세요.

이벤트가 드물거나 프록시 환경이 까다로우면 짧은 폴링이나 롱 폴링도 충분할 수 있어요. 어떤 방식이든 연결 하나가 서버 자원이라는 점을 잊지 마세요.

더 어려운 문제는 끊겼다가 다시 붙을 때 생겨요. 이벤트 id로 이어받거나, 재연결 뒤 상태를 다시 조회해서 맞춰야 해요. 그리고 같은 이벤트가 두 번 와도 한 번만 반영되도록 id로 걸러야 해요.

결제 뒤 주문 상태를 기다리는 흐름은 [결제 — 이중 결제 막기](/m/payment-idempotency)에서 다룬 UNKNOWN 상태와 맞닿아 있어요. 응답을 받지 못했을 때 상태를 조회하는 것처럼, 실시간 연결이 끊겼을 때도 상태를 다시 물어보는 길을 준비해 두세요.
