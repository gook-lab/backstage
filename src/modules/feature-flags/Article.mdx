새 결제 화면을 사용자 5%에게만 먼저 보여 주자는 요청에는 일이 두 가지 들어 있어요. 하나는 이번에 올린 코드를 사용자에게 여는 시점을 따로 정하는 일이고, 다른 하나는 서버와 화면이 같은 5%를 고르게 하는 일이에요.

답은 사용자 id를 같은 규칙에 넣는 데 있어요. 같은 id와 같은 규칙이면 서버도 화면도 같은 답을 내요.

이 글은 기능 플래그(feature flag, 기능 토글)로 이 두 가지를 푸는 방법을 정리해요. 아래 시뮬레이터에서 평가 위치와 캐시 지연을 바꿔 보면, 화면과 서버가 어긋나는 요청이 어떻게 생기는지 직접 볼 수 있어요.

## 배포와 출시 — 코드는 올리고 여는 시점은 따로 정하기

Fowler 글은 릴리스 토글이 "[기능] 출시와 [코드] 배포를 나누는" 지속적 배포 원칙을 구현하는 가장 흔한 방법이라고 설명해요. 미완성 코드를 메인 가지에 넣어 두고, 실제로 켜는 결정은 나중에 내리는 방식이에요.

배포는 서버와 화면 번들을 올리는 일이에요. 출시는 사용자 화면에 기능이 보이는 일이에요. 배포가 끝나도 플래그가 꺼져 있으면 사용자 화면은 그대로예요. 그래서 배포 날짜와 출시 날짜를 따로 정할 수 있어요.

## 플래그 종류 — 수명과 결정 방식으로 나누기

Fowler 글은 토글을 네 가지로 나눠요. 종류마다 얼마나 오래 두는지, 그리고 결과가 요청마다 달라지는지가 달라요.

| 종류                             | 쓰는 목적                           | 글이 설명하는 수명                                               | 결정 방식                        |
| -------------------------------- | ----------------------------------- | ---------------------------------------------------------------- | -------------------------------- |
| 릴리스 토글 (release toggle)     | 덜 끝난 코드를 숨긴 채 배포         | 1~2주를 넘기지 않는 편이에요. 제품 이유가 있으면 더 길 수 있어요 | 릴리스마다 거의 같아요           |
| 실험 토글 (experiment toggle)    | A/B 테스트                          | 통계적으로 결과가 나올 때까지, 몇 시간에서 몇 주                 | 사용자마다 한 경로에 고정        |
| 운영 토글 (ops toggle)           | 장애나 과부하 때 기능을 끄거나 낮춤 | 대부분 짧아요. 킬 스위치는 오래 둘 수 있어요                     | 설정을 바꾸면 실행 중에 바뀌어요 |
| 권한 토글 (permissioning toggle) | 사용자 등급별 기능                  | 여러 해 단위로 길 수 있어요                                      | 요청마다 사용자 기준으로 정해요  |

수명이 다르면 관리 방법도 달라요. 릴리스 토글은 정리 작업을 처음부터 잡아 두고, 권한 토글은 오래 간다는 전제로 설계해요.

## 비율 배포 — 사용자 id 버킷으로 고정하기

Fowler 글은 카나리 출시(canary release) 예시에서 사용자 1%를 무작위로 뽑아 코호트를 만들고, 그 사용자들이 계속 같은 쪽을 보게 해요. 글은 이 샘플링에 사용자 id의 모듈로(modulo)를 쓸 수도 있다고 설명해요.

버킷 방식은 이렇게 동작해요. 사용자 id를 0~99 숫자(버킷)로 바꾸고, 버킷이 출시 비율보다 작으면 새 결제를 보여 줘요. 출시 비율이 5%면 버킷 0~4가 대상이에요.

같은 id를 같은 규칙에 넣으면 같은 버킷이 나와요. 서버와 화면이 같은 규칙을 가지면 같은 사용자에게 같은 답을 줘요.

이 글에서는 같은 입력에 같은 출력이 나온다는 성질만 써요. 해시 함수의 품질이나 특정 함수를 고르는 기준은 이 글의 출처에서 확인하지 않았어요.

출시 비율을 5%에서 10%로 올리면 버킷 0~4는 그대로 대상이에요. 그래서 이미 새 결제를 본 사용자가 다시 옛 결제로 돌아가지 않아요. 사용자 수가 적으면 비율이 정확히 맞지 않을 수 있어요. 시뮬레이터에서 1,000명 중 몇 명이 뽑히는지 보면 돼요.

플래그마다 다른 접두어를 id 앞에 붙이는 편이 좋아요. 같은 규칙을 모든 플래그에 쓰면 A 기능에 뽑힌 사람이 B 기능에서도 항상 같은 쪽에 들어가요. 접두어를 나누면 기능마다 사용자 묶음이 달라져요.

## 평가 위치 — 서버 평가와 클라이언트 평가

| 기준             | 서버 평가                          | 클라이언트 평가                                                      |
| ---------------- | ---------------------------------- | -------------------------------------------------------------------- |
| 규칙 위치        | 규칙이 서버에만 있어요             | 브라우저가 규칙이나 판정 결과를 받아야 해요. 규칙이 노출될 수 있어요 |
| 첫 화면          | 응답을 받아야 값을 알아요          | 평가가 끝나기 전에는 기본값으로 그려요                               |
| 같은 사용자의 값 | 서버가 한 번 정해 응답에 실어 줘요 | 화면마다 따로 평가하면 서로 다를 수 있어요                           |
| 돈이 걸린 분기   | 서버가 최종 판단해요               | 서버가 화면 값을 그대로 믿으면 조작할 수 있어요                      |

비밀 규칙이 있으면 서버 평가가 맞아요. 규칙을 브라우저에 내려보내면 누구나 읽을 수 있기 때문이에요. 이 판단은 [서버 · 클라 처리 판단](/m/server-or-client) 글의 신뢰 기준과 같은 결이에요.

## 첫 렌더 — 기본값 깜빡임 막기

OpenFeature 제공자 명세는 제공자가 아직 준비되지 않았거나 복구할 수 없는 오류가 났을 때, 클라이언트가 기본값(default value)을 돌려준다고 정해요. 화면이 이 기본값으로 먼저 그려지면, 나중에 실제 값이 도착했을 때 화면이 바뀌어요. 이 변화가 깜빡임이에요.

막는 방법은 두 가지예요. 서버가 페이지를 만들 때 플래그 값을 함께 내려주면 첫 화면부터 실제 값을 쓸 수 있어요. 값이 올 때까지 해당 영역을 로딩 상태로 두면 화면이 바뀌는 순간을 줄일 수 있어요.

## 캐시와 전파 지연 — 바뀐 값이 닿는 시간

OpenFeature 제공자 명세는 평가 결과의 이유(reason)에 CACHED, STALE 같은 값을 쓸 수 있다고 정해요. 값이 캐시에서 왔거나 옛 값일 수 있다는 뜻이에요. 운영자가 출시 비율을 바꿔도, 모든 서버와 브라우저가 새 값을 받기까지 시차가 생겨요.

그래서 출시 비율을 올린 직후 노출 수가 바로 맞지 않는 것은 자연스러워요. 이 글에서는 캐시 만료 시간의 수치를 다루지 않아요. 시뮬레이터의 캐시 지연은 몇 번 방문 뒤에 반영되는지로만 보여 줘요.

## 서버와 화면이 다른 값 — 두 버전이 함께 도는 요청

화면은 새 결제 화면을 보여 주는데 서버는 아직 옛 결제 로직을 쓰는 순간이 생겨요. 요청 형식이 맞지 않아 실패하거나, 더 나쁘게는 옛 로직으로 잘못 처리될 수 있어요. 옛 버전과 새 버전이 함께 도는 기간은 [스키마 변경과 무중단 배포](/m/schema-migration) 글에서 다룬 문제와 같아요.

이 불일치를 줄이는 방법은 세 가지예요.

- 서버가 새 형식을 받을 수 있게 먼저 배포한 뒤에 화면 플래그를 켜요.
- 돈이 걸린 분기는 서버가 같은 규칙으로 다시 평가해요. 화면이 보낸 플래그 값은 어떤 화면을 봤는지 기록하는 데만 써요.
- 서버가 화면 값과 자기 값이 다르면 그 요청을 기록해요. 어긋난 요청 수가 관찰 지표가 돼요. 기록을 읽는 방법은 [로그 · 트레이스로 원인 찾기](/m/observability) 글에서 이어 봐요.

## 킬 스위치 — 배포 없이 운영 토글 끄기

Fowler 글은 소수의 장기 운영 토글을 킬 스위치(kill switch)라고 부르고, 과부하일 때 중요하지 않은 기능을 우아하게 낮추는 데 쓴다고 설명해요. 글은 새 릴리스를 내야 운영 토글을 뒤집을 수 있다면 운영자가 곤란하다고 짚어요.

그래서 킬 스위치는 배포 없이 설정 값만 바꿔 끌 수 있어야 해요. 추천 영역이나 부가 기능처럼 빠져도 주요 흐름이 끝까지 이어지는 기능을 대상으로 두는 편이 좋아요.

## 오래된 플래그 정리 — 기술 부채로 세기

Fowler 글은 팀이 플래그를 재고(inventory)로 보고, 보관 비용(carrying cost)을 줄이려 한다고 설명해요. 방법으로는 정리 작업을 백로그에 넣기, 만료일 두기, 만료되면 테스트를 실패시키는 시한폭탄 두기, 플래그 개수에 상한 두기를 소개해요.

FE에서는 플래그마다 정리 날짜를 남겨요. 날짜는 플래그 이름 옆 주석이나 플래그 목록에 적어요. 날짜가 지나면 플래그를 지우거나, 연장한 이유를 적어요.

## A/B 실험 — 노출 기록과 지표 맞추기

Fowler 글은 실험 토글에서 사용자를 코호트에 넣고, 각 사용자를 일관되게 한 경로로 보낸 뒤 코호트별 집계를 비교한다고 설명해요. 실험 중에 설정을 바꾸면 결과가 통계적으로 무효가 될 수 있다는 점도 짚어요.

집계가 맞으려면 사용자가 실제로 본 변형을 기록해야 해요. 이 글에서는 그 기록을 노출 기록이라고 부를게요. 노출 기록은 화면이 값을 정한 시점에 남겨야 해요. 서버 응답 기준으로만 남기면 화면과 서버가 어긋난 요청을 놓칠 수 있어요.

OpenFeature는 평가 전후에 동작을 끼워 넣는 훅(hook)을 로깅, 텔레메트리, 추적에 쓸 수 있다고 소개해요. 노출 기록을 훅에 두면 평가 호출마다 같은 방식으로 남길 수 있어요.

배정 방식도 집계에 영향을 줘요. 방문마다 무작위로 배정하면 같은 사용자가 방문마다 다른 쪽을 볼 수 있어서, 사용자를 한 경로에 고정한다는 실험 토글의 전제가 깨져요.

## OpenFeature — 평가 API와 평가 컨텍스트 표준

OpenFeature는 플래그 평가를 위한 공통 API를 정의해요. 앱 코드는 평가 API만 부르고, 제공자(provider)가 그 호출을 실제 플래그 서비스의 표현으로 옮겨요. 제공자를 바꿔도 앱의 평가 호출은 그대로 둘 수 있어요.

평가 컨텍스트(evaluation context)는 평가에 쓰는 주변 정보를 담는 그릇이에요. 사용자 정보는 여기에 실어요. 명세는 `targetingKey` 필드를 평가 대상을 식별하는 값으로 정의하고, 비율 배정이나 규칙에 쓰인다고 설명해요. 이 값이 없으면 제공자가 예측하기 어렵게 동작할 수 있어요.

컨텍스트는 전역, 트랜잭션, 클라이언트, 호출, 훅 순서로 합쳐지고, 뒤에 오는 값이 같은 이름의 앞 값을 덮어써요. 명세는 사용자 속성 같은 동적 값을 클라이언트나 호출 단계에 두는 것이 적합하다고 설명해요. 이 글에서는 로그인한 사용자 id를 `targetingKey`에 넣는 방식을 예로 들어요.

## FE 체크 포인트

**첫 렌더 전에 플래그 값을 받아요.** 서버가 페이지를 만들 때 값을 함께 내려주거나, 값이 올 때까지 해당 영역을 로딩으로 둬요.

**요청에 플래그 값을 실어 서버와 맞춰요.** 서버는 같은 규칙으로 다시 평가하고, 값이 다르면 그 요청을 기록해요. 돈이 걸린 분기는 서버 결과를 따라요.

**기본값을 안전한 쪽으로 정해요.** 값을 받지 못했을 때 옛 화면이 나오도록 기본값을 두면, 준비되지 않은 상태에서 새 기능이 잘못 열리지 않아요.

**플래그마다 정리 날짜를 적어요.** 날짜가 지나면 정리 작업을 먼저 잡아요.

## 시뮬레이터 안내

아래 시뮬레이터는 사용자 1,000명이 방문 4번 하는 상황을 만들어요. 사용자 id가 고정돼 있어서 같은 설정이면 항상 같은 결과가 나와요. 출시 비율, 평가 위치, 캐시 지연, 배정 방식을 바꿔 보세요.

- 캐시 지연이 없을 때 사용자 id 해시로 배정하면, 같은 사용자가 방문 4번 모두 같은 결과를 받아요.
- 매번 무작위로 배정하면 같은 비율에서도 결과가 바뀌는 사용자가 생겨요.
- 둘 다 각자 평가에서 서버에 캐시 지연을 주면, 화면은 새 결제를 보여 주고 서버는 옛 결제로 처리한 요청이 생겨요.
- 클라이언트 평가에서는 서버가 화면 값을 따라서 어긋난 요청이 0회예요. 대신 서버가 화면이 보낸 값을 그대로 믿는 구조라, 돈이 걸린 분기에는 쓰지 않아요.

## 정리 — 사용자 id 버킷 · 돈 분기 서버 기준 · 정리 날짜

비율 배포에서 사용자는 id 버킷으로 고정해요. 같은 id와 같은 규칙이면 서버와 화면이 같은 답을 내요. 돈이 걸린 분기는 서버가 최종 판단하고, 화면 값은 기록과 확인에만 써요. 플래그는 종류별 수명에 맞춰 정리 날짜를 정해요.

두 버전이 함께 도는 기간은 [스키마 변경과 무중단 배포](/m/schema-migration) 글에서 더 자세히 다뤄요. 돈과 재고를 서버가 정하는 기준은 [서버 · 클라 처리 판단](/m/server-or-client) 글에서 이어 봐요.
