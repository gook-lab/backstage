두 사람이 같은 글을 열어 두고 고치는 장면을 떠올려 보세요. A가 제목을 고쳐 저장해요. 몇 초 뒤 B는 A의 수정이 없는 화면에서 본문을 고쳐 저장해요. B의 저장이 옛 제목을 그대로 실어 보내면, A의 제목 수정은 조용히 사라져요. 이 현상을 덮어쓰기(lost update)라고 불러요.

FE에서는 "저장 성공이 떴는데 내 수정이 없어요"로 보여요. 서버는 저장 요청이 어떤 버전을 보고 만들어졌는지 알아야 이걸 막을 수 있어요. 이 글은 그 확인을 HTTP 조건부 요청과 DB 버전 칼럼으로 하는 방법을 다뤄요. 같은 행을 잠가서 기다리게 하는 방식은 [트랜잭션 · 락 · 데드락](/m/transactions) 글에서 다뤘어요.

아래 시뮬레이터에서 두 사람의 읽기와 저장 순서를 고르고, 저장 전략을 바꿔 보세요. 최종 본문과 각 요청이 받은 응답 코드가 바로 보여요.

## 덮어쓰기 — 읽기와 저장 사이의 틈

문제는 읽기와 저장 사이에 시간이 있을 때만 생겨요. 한 명씩 읽고 저장하면 두 번째 사람은 최신 값을 읽어요. 두 사람이 먼저 읽어 둔 뒤 저장하면 이야기가 달라져요.

| 순서 | A             | B                                 | 서버 상태         |
| ---- | ------------- | --------------------------------- | ----------------- |
| 1    | 읽기 (버전 1) | 읽기 (버전 1)                     | 버전 1            |
| 2    | 저장 → 200    |                                   | 버전 2 (A의 수정) |
| 3    |               | 저장 → 200 (버전 1을 기준으로 함) | 버전 3 (B의 수정) |

B는 버전 1을 기준으로 저장했어요. 그래서 A의 저장을 모른 채 값을 덮어요. 서버가 "이 요청이 어떤 버전을 보고 만들어졌는지"를 확인하지 않으면 두 저장 모두 통과해요. 이 확인을 서버가 하도록 만드는 것이 이 글의 중심이에요.

## 조건부 저장 — ETag와 If-Match

MDN은 ETag를 리소스의 특정 버전을 가리키는 식별자라고 설명해요. 서버가 GET 응답에 ETag를 붙이면, 클라이언트는 다음 저장 요청에 `If-Match`로 그 값을 돌려보내요. RFC 9110은 `If-Match`가 조건이 참일 때만 메서드를 적용하게 만든다고 정의해요. 조건이 거짓이면 서버는 412로 응답해요. RFC 9110은 `If-Match`를 비교할 때 서버가 강한 비교를 써야 한다고도 정해요.

```http
GET /articles/42

200 OK
ETag: "v1"

PUT /articles/42
If-Match: "v1"

{"body": "B의 수정"}
```

서버 상태가 이미 버전 2라면 위 PUT은 412로 거절돼요. MDN은 412가 GET이나 HEAD가 아닌 메서드에서 `If-Match` 조건이 맞지 않을 때 나온다고 설명해요. 그러면 요청은 적용되지 않아요. MDN은 ETag가 동시 수정이 서로를 덮어쓰는 일을 막는 데 쓰인다고도 설명해요.

ETag는 응답 캐시에도 쓰여요. 같은 값을 두 용도로 쓰면 구현이 단순해져요. 서버는 보통 `version` 칼럼 값을 ETag로 바꿔 내보내는 편이 좋아요.

## 428 — 조건 헤더 누락 거절

조건을 걸지 않은 저장은 조건이 없는 것과 같아요. RFC 6585는 428을 덮어쓰기 문제를 피하려고 요청을 조건부로 만들도록 요구하는 응답이라고 정해요. MDN은 428이 보통 `If-Match` 같은 조건 헤더가 빠졌을 때 나온다고 설명해요. 헤더가 있지만 서버 상태와 맞지 않으면 412가 나와요.

FE에서 헤더를 빠뜨리는 실수는 흔해요. 서버가 조건 없는 저장을 받아 주면 그 실수는 조용히 덮어쓰기가 돼요. 서버가 428로 거절하면 실수가 바로 드러나요. 시뮬레이터의 "B의 저장이 If-Match를 빠뜨림" 옵션과 "If-Match 없는 저장을 428로 거절" 옵션을 함께 켜 보세요.

| 상태 코드 | 뜻                              | FE가 할 일                                     |
| --------- | ------------------------------- | ---------------------------------------------- |
| 200       | 조건이 맞아 저장됐어요          | 응답의 새 ETag를 저장해 다음 요청에 쓰기       |
| 412       | `If-Match`와 서버 상태가 달라요 | 최신 값을 받아 충돌 처리로 넘기기              |
| 428       | 조건 헤더가 필요해요            | 헤더 누락 버그로 보고, 헤더를 붙여 다시 보내기 |
| 409       | 버전 칼럼 조건이 맞지 않아요    | 최신 값을 받아 충돌 처리로 넘기기              |

RFC 9110은 409를 현재 상태와 충돌해서 요청을 완료할 수 없고, 사용자가 충돌을 해결한 뒤 다시 보낼 수 있을 때 쓴다고 설명해요. 버전 칼럼 방식의 충돌을 409로 돌려줄지 412로 돌려줄지는 API 설계 판단이에요. 이 시뮬레이터는 409로 가정해요.

## 버전 칼럼 — DB 쓰기 한 문장에 조건 넣기

`If-Match`는 요청을 받는 시점에 비교해요. DB의 `WHERE`는 실제로 쓰는 시점에 비교해요. 두 요청이 거의 동시에 들어오면 둘 다 헤더 검사를 통과할 수 있어요. 그래서 헤더 검사만으로는 충분하지 않아요. 저장 쿼리에도 읽은 버전을 넣어 두는 편이 안전해요.

```sql
UPDATE articles
SET body = $1, version = version + 1
WHERE id = $2 AND version = $3;
```

영향받은 행이 0이면 충돌이에요. 확인과 갱신이 한 문장이라 두 요청 사이에 다른 쓰기가 끼지 않아요. PostgreSQL 문서는 기본 격리 수준(Read Committed)에서 같은 행을 먼저 바꾼 트랜잭션이 커밋하거나 롤백할 때까지 두 번째 UPDATE가 기다린다고 설명해요. 그다음 WHERE 조건을 바뀐 행에 다시 평가해요. 그래서 `version`이 이미 바뀌었다면 두 번째 UPDATE는 0행을 갱신해요.

`updated_at` 타임스탬프를 버전 대신 쓰는 것도 가능하지만, 시각 정밀도에 따라 같은 값이 나올 수 있어요. 정수 `version` 칼럼을 쓰는 편이 비교가 명확해요.

## 충돌 처리 — 다시 불러오기와 병합 기준

충돌이 나면 화면에서 할 수 있는 일은 몇 가지예요. MDN은 충돌을 받은 클라이언트가 사용자에게 처음부터 다시 시작하라고 알리거나, 두 버전의 차이를 보여 주고 어떤 변경을 남길지 고르게 하는 방식이 있다고 설명해요.

| 처리             | 맞는 경우                                         | 대가                                                 |
| ---------------- | ------------------------------------------------- | ---------------------------------------------------- |
| 다시 불러오기    | 내 수정이 작고, 다시 적용해도 되는 경우           | 작성 중이던 내용이 사라질 수 있어요. 임시본을 남겨요 |
| 병합 화면        | 두 수정이 같은 필드나 같은 문장을 건드린 경우     | 사용자가 판단해야 해서 화면과 작업이 늘어요          |
| 마지막 저장 우선 | 잃어도 되는 값이고, 조건 없이 덮는 것을 알린 경우 | 앞 수정이 조용히 사라져요. 알리지 않고 쓰면 안 돼요  |

고르는 기준은 두 가지예요. 두 수정이 같은 필드를 건드렸는지, 그리고 잃어도 되는 값인지예요. 같은 필드를 건드렸고 잃으면 안 되는 값이면 병합 화면이 맞아요. 서로 다른 필드를 고쳤다면 서버가 필드 단위로 합칠 수 있어요.

412나 409를 받으면 서버가 최신 본문과 ETag를 같이 주는 편이 좋아요. 그래야 병합 화면을 바로 만들 수 있어요. 최신 값이 없다면 GET을 다시 해야 해요.

## 낙관적 UI — 먼저 보여 주고 실패하면 되돌리기

낙관적 UI는 저장 응답을 기다리지 않고 화면에 새 값을 먼저 보여 주는 방식이에요. 실패하면 이전 값으로 되돌려요. 이때 값은 서버가 확정한 값이 아니에요. 서버 확정 전까지는 "저장 중" 표시를 붙여요. 이 구분은 [서버 · 클라 처리 판단](/m/server-or-client) 글의 즉시 반응과 서버 확정을 나누는 설계와 같아요.

흐름은 네 단계예요.

1. 저장을 보내기 전에 현재 화면 값과 읽은 ETag를 보관해요.
2. 화면에 새 값을 반영하고 저장 중 표시를 붙여요.
3. 200이면 응답의 새 ETag로 기준값을 갱신해요.
4. 412나 409면 화면을 서버 최신 값으로 맞추고, 사용자가 쓴 내용은 임시본으로 남겨요.

되돌리기에서 가장 흔한 실수는 사용자가 쓴 내용까지 지우는 것이에요. 임시본을 남기면 병합 화면에서 다시 쓸 수 있어요.

네트워크가 끊겨 응답을 못 받으면 저장이 됐는지 몰라요. 이때 같은 조건으로 다시 보내면 412를 받을 수 있어요. RFC 9110은 상태를 바꾸는 요청이 이미 적용된 것처럼 보일 때 서버가 412 대신 2xx를 줄 수도 있다고 설명해요. 재시도 기준은 [결제 멱등성](/m/payment-idempotency) 글에서 다룬 멱등성 키 설계와 함께 보세요.

## FE 체크 포인트

- GET 응답의 ETag를 저장해 두었다가, 수정 요청에 `If-Match`로 보내요.
- 저장 응답의 새 ETag로 기준값을 바꿔요. 이전 값을 계속 쓰면 자기 저장 때문에 412가 나요.
- 412와 409를 같은 충돌 처리 함수로 받아요.
- 428을 받으면 화면 문구보다 헤더 누락 버그로 보고 로그를 남겨요.
- 충돌 뒤에 조건 없이 다시 저장하지 않아요. 최신 값을 보고 다시 판단해요.
- 낙관적 값은 "저장 중"으로 표시하고, 실패하면 임시본을 남긴 채 되돌려요.

## 시뮬레이터 안내

시뮬레이터에는 A와 B가 같은 버전을 읽고 저장하는 상황이 있어요. 저장 전략을 세 가지 중 하나로 고르고, 두 사람의 읽기와 저장 순서를 고를 수 있어요. 옵션 두 개는 If-Match 전략에서만 바뀌어요.

- 조건 없음은 모든 저장이 200으로 통과해요. 나중 저장이 앞 수정을 덮어써요.
- If-Match는 읽은 버전이 서버와 같을 때만 저장해요. 늦은 저장은 412를 받아요.
- 버전 칼럼은 WHERE 조건으로 같은 검사를 해요. 늦은 저장은 409를 받아요.

수치와 순서는 설명을 위한 예시예요. 실제 서비스의 요청 수나 지연 시간이 아니에요.

- RFC 9110 (13.1.1 If-Match, 15.5.10 409, 15.5.13 412)
- RFC 6585 (428 Precondition Required)
- MDN — ETag, If-Match, 412, 428, Conditional requests

## 정리 — 조건 검사 위치와 충돌 처리 기준

- 여러 사람이 고치는 값은 ETag와 `If-Match`로 조건을 걸어요.
- 헤더 검사와 DB의 `WHERE version` 검사를 함께 둬요.
- 조건 헤더가 빠진 저장은 428로 거절해요.
- 충돌은 같은 필드 여부와 잃어도 되는 값인지로 병합 화면과 다시 불러오기를 나눠요.
- 낙관적 UI는 저장 중 표시를 붙이고, 실패하면 임시본을 남긴 채 되돌려요.
