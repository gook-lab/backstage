관리자 주문 목록에서 상태와 기간 필터를 걸고 금액순으로 바꾸면 응답이 몇 초씩 걸릴 수 있어요. 같은 화면인데 필터 조합마다 DB가 읽는 행 수가 달라서 생기는 일이에요.

이 글은 한 질문에서 출발해요. **서버는 필터 조합과 정렬을 어떻게 처리하나요?** 답을 찾으려면 복합 인덱스의 열 순서, 정렬을 인덱스가 대신하는 조건, 전체 개수를 세는 비용을 차례로 봐야 해요.

인덱스 기초와 `EXPLAIN` 읽기는 [N+1 글](/m/n-plus-one)에서 먼저 봐요. offset과 cursor의 차이는 [페이지네이션 글](/m/pagination)에서 다뤘어요. 이 글은 그 위에서 필터와 정렬이 겹칠 때 생기는 판단만 다뤄요.

예시로 쓰는 테이블은 주문 100만 건이에요. 이 글의 행 수는 모두 예시예요.

```sql
CREATE TABLE orders (
  id         BIGINT PRIMARY KEY,
  status     TEXT NOT NULL,   -- 'pending' · 'shipping' · 'done' 등
  amount     BIGINT NOT NULL,
  created_at TIMESTAMP NOT NULL
);
```

## 필터 조합 — 조합마다 달라지는 실행 계획

목록 API는 보통 이런 쿼리로 바뀌어요.

```sql
SELECT id, status, amount, created_at
FROM orders
WHERE status = 'pending'
  AND created_at >= now() - interval '7 days'
ORDER BY created_at DESC
LIMIT 20;
```

필터가 하나 늘거나 정렬 키가 바뀌면 DB는 다른 길을 고를 수 있어요. 실행 계획을 볼 때는 세 가지를 나눠 보면 좋아요. 인덱스를 쓰는지, 인덱스에서 몇 항목을 훑는지, 정렬 단계가 남는지예요. 이 세 가지를 보면 느린 이유를 좁힐 수 있어요.

## 복합 인덱스 열 순서 — 등호, 범위, 정렬 순서

PostgreSQL 문서는 다중 열 B-tree 인덱스에서 앞 열의 등호 조건과, 등호가 없는 첫 열의 부등호 조건이 스캔할 범위를 줄인다고 설명해요. 그 오른쪽 열의 조건은 인덱스 안에서 확인하지만, 스캔 범위를 줄인다고 보장하지는 않는다고 해요.

위 쿼리에 맞는 세 가지 인덱스를 나란히 보면 차이가 보여요.

| 인덱스                 | 상태 등호와 기간 범위                             | 최신순 정렬                     | 해석                                        |
| ---------------------- | ------------------------------------------------- | ------------------------------- | ------------------------------------------- |
| `(status, created_at)` | 상태가 앞 열이라 범위가 좁아져요                  | 상태가 고정돼서 정렬을 대신해요 | 이 쿼리에 가장 잘 맞아요                    |
| `(created_at)`         | 기간만 범위로 좁혀요. 상태는 테이블에서 확인해요  | 정렬을 대신해요                 | 상태가 드물면 훑는 항목이 많아져요          |
| `(created_at, status)` | 기간 범위만 좁혀요. 상태는 인덱스 안에서 확인해요 | 정렬을 대신해요                 | 테이블 방문은 줄지만 훑는 범위는 그대로예요 |

`(created_at, status)`가 마지막 행처럼 동작하는 이유는 문서의 규칙에 있어요. 오른쪽 열 조건은 인덱스 안에서 확인해 테이블 방문을 줄여요. 하지만 훑어야 하는 인덱스 범위를 줄이지는 않아요.

### 상태 조건이 없을 때 — 앞 열이 비면 범위가 안 줄어요

상태 필터를 `전체`로 두면 `(status, created_at)` 인덱스에서 앞 열에 걸리는 등호 조건이 없어요. 그러면 기간 범위를 여러 상태 묶음에 걸쳐 넓게 읽어야 해요. 인덱스 순서가 상태 다음에 `created_at`이라서, 상태가 섞인 결과는 최신순으로 나오지 않아요. 그래서 정렬 단계가 다시 필요해요.

이 차이 때문에 인덱스 열 순서는 "자주 거는 필터"를 기준으로 정하는 편이 좋아요. 자주 쓰는 필터가 앞 열이어야 같은 인덱스가 여러 화면을 함께 감당해요.

## 정렬을 인덱스가 대신하는 경우 — LIMIT과 역방향 스캔

PostgreSQL 문서는 플래너가 ORDER BY를 두 방법으로 처리한다고 설명해요. 맞는 인덱스를 훑거나, 테이블을 읽고 따로 정렬하거나예요. 특히 `ORDER BY`와 `LIMIT n`이 함께 있으면 맞는 인덱스가 있을 때 앞의 n건을 바로 가져올 수 있어요.

따로 정렬하면 앞 n건을 고르기 위해 데이터 전체를 처리해야 해요.

B-tree 인덱스는 뒤에서부터도 읽을 수 있어요. 그래서 `created_at`에 인덱스가 있으면 최신순 목록은 가장 최근 값부터 거꾸로 읽고, 20건이 차면 멈춰요. 정렬 단계가 없어요.

이 방식은 조건에 맞는 행이 많을 때 잘 맞아요. 결제 대기가 전체의 2%처럼 드물면 어떻게 되는지 예시로 보면 이해가 쉬워요. 최신순으로 20건을 채우려면 `(created_at)` 인덱스에서 약 1,000개 항목을 훑어야 해요.

상태 조건에 맞는 행이 드물수록 한 번에 버려지는 항목이 늘어요. `EXPLAIN`의 `Rows Removed by Filter`가 크면 이런 낭비를 의심해 볼 수 있어요.

## 따로 정렬하는 경우 — 금액순과 인덱스에 없는 키

금액순 목록은 `amount`에 인덱스가 있어야 정렬을 대신해요. 예시의 인덱스 정의에는 금액 인덱스가 없어요. 그러면 조건에 맞는 행을 모두 읽은 뒤 금액으로 정렬해요. `LIMIT 20`이 있어도 정렬 전에는 어떤 20건이 앞에 와야 하는지 알 수 없어요.

PostgreSQL 문서는 `LIMIT`이 있는 정렬에서 맞는 인덱스가 없으면 명시적 정렬이 데이터 전체를 처리해야 한다고 설명해요. 정렬 방향이 열마다 다르면 `(x ASC, y DESC)`처럼 열별 방향을 가진 인덱스가 필요하다는 점도 같은 문서에 있어요.

## 드문 값 필터 — 정렬 인덱스를 따라 읽을 때 많이 훑는 이유

PostgreSQL 플래너는 WHERE 조건이 행의 몇 퍼센트를 고르는지, 곧 선택도를 추정해서 계획을 짜요. 그 추정값은 `pg_statistic`의 통계에서 와요. 통계가 낡으면 추정이 어긋나고, 그러면 플래너가 계획을 잘못 고를 수 있어요.

조건에 맞는 행이 드문 필터, 곧 선택도 값이 작은 필터는 정렬용 인덱스를 따라 읽을 때 훑는 양이 커요. 선택도가 "높다·낮다"는 말은 사람마다 반대로 쓰기도 해서, 이 글은 "드문 값"이라고 부를게요.

앞 장의 예시처럼 2%짜리 상태 필터는 최신순 20건을 얻는 데 항목을 많이 훑게 만들어요. 이때는 인덱스를 더 넓히기보다 다음 절의 부분 인덱스를 검토하는 편이 좋아요.

## 부분 인덱스 — 드문 값만 따로 담기

부분 인덱스는 WHERE 조건을 만족하는 행만 담는 인덱스예요. PostgreSQL 문서는 흔한 값을 인덱스에서 빼려는 것이 주된 이유라고 설명해요. 흔한 값을 찾는 쿼리는 어차피 인덱스를 쓰지 않는다고 해요.

반대로 드문 값을 담으면 인덱스가 작아져요. 결제 대기만 담은 `(created_at) WHERE status = 'pending'` 인덱스가 그 예예요. 예시에서 이 인덱스는 전체 100만 항목 대신 2만 항목만 가져요.

부분 인덱스에는 조건이 있어요.

- 쿼리의 WHERE가 인덱스의 조건을 수학적으로 함의해야 쓸 수 있다고 문서는 설명해요. `status = 'pending'`을 같이 말한 쿼리만 이 인덱스를 써요.
- `status IN ('pending', 'shipping')`처럼 조건이 넓어지면 함의가 성립하지 않아 쓰이지 않아요.
- 조건값이 미리 정해져 있어야 해요. 값의 분포가 바뀌면 인덱스를 다시 만들어야 할 수 있어요.

## 정확한 COUNT 비용 — 조건에 맞는 행을 전부 세기

목록 상단의 "총 N건"은 보통 `COUNT(*)`로 만들어요. PostgreSQL 위키는 `count(*)`가 느릴 수 있다고 설명해요. MVCC 때문에 모든 행의 가시성을 확인해야 하기 때문이라고 해요.

필터 조건이 넓을수록 세는 행도 많아요. 예시에서 기간을 `전체`로 두고 상태도 `전체`로 두면 정확한 COUNT는 100만 행을 읽어요. 목록 쿼리는 빨라도 개수를 세는 쿼리가 느려지는 이유예요.

Stripe 검색 API도 같은 문제를 다르게 풀어요. 응답의 `total_count`는 기본으로 넣지 않고, 확장을 요청할 때만 포함해요. 그리고 10,000까지만 정확하다고 명시해요.

## COUNT 대안 — 추정치 · 상한 · 다음 페이지 여부

정확한 개수가 꼭 필요한지부터 물어보세요. 필요 없다면 아래 대안으로 바꿀 수 있어요. 시뮬레이터의 값과 같은 기준으로 정리했어요.

| 방식             | 읽는 행 (예시)      | 화면 예 (예시)   | 쓰기 좋은 곳                            |
| ---------------- | ------------------- | ---------------- | --------------------------------------- |
| 정확한 COUNT(\*) | 조건에 맞는 행 전부 | 1,280개          | 정산이나 감사처럼 숫자가 정확해야 할 때 |
| 상한 표시        | 최대 1,001행        | 1,000건 이상     | 목록 상단에서 규모만 알려 줄 때         |
| 다음 페이지 여부 | LIMIT + 1, 즉 21행  | 다음 페이지 있음 | 다음 버튼이나 무한 스크롤               |
| 통계 추정치      | 행을 세지 않음      | 약 1,300개       | 대략적인 표시를 하고, 통계가 최신일 때  |

통계 추정치는 PostgreSQL 위키의 방법이 참고가 돼요. 위키가 인용한 매뉴얼은 `pg_class.reltuples`를 플래너가 쓰는 행 수 추정치이고 VACUUM과 ANALYZE로 갱신된다고 설명해요.

특정 필터 조건의 개수를 얻으려면 `EXPLAIN`의 예상 행 수를 읽는 방법을 쓸 수 있어요. 위키는 정제되지 않은 쿼리 문자열을 넘기면 SQL 주입이 생긴다고 경고해요.

상한 표시는 1,001행까지만 세고 넘으면 "1,000건 이상"으로 보여 줘요. 실제 개수를 몰라도 규모는 전달돼요. 다음 페이지 여부는 한 페이지보다 한 건 더 가져와서 다음이 있는지만 확인해요.

## facet 개수 — 필터 값마다 세는 비용

상태 탭마다 개수를 붙이는 화면을 facet이라고 불러요. 값마다 COUNT를 따로 보내면 쿼리가 값 수만큼 늘어요. 예시에서 상태 값이 3개라면 쿼리도 3개예요.

예시 모델에서는 인덱스가 `(status, created_at)`처럼 상태를 앞 열에 두면 각 쿼리가 자기 값의 행만 읽어요. 그러면 읽는 양의 합이 기간 안 행 수와 같아져요. 상태가 앞 열이 아니면 값마다 기간 안의 행을 다시 훑어요.

`GROUP BY status` 한 번으로 세면 쿼리는 1개지만, 기간 안 행을 한 번 전부 읽어야 해요. 어느 쪽이 나은지는 쿼리 수와 읽는 양 중 무엇이 더 비싼지에 따라 달라요. 시뮬레이터는 두 방식의 읽는 양을 나란히 보여 줘요.

## 허용 목록 — 정렬과 필터 키 제한하기

인덱스는 정해진 열 조합에만 있어요. 사용자가 고를 수 있는 정렬 키와 필터 키가 많을수록 인덱스 없이 훑는 조합이 늘어나요. 그래서 서버가 받을 수 있는 키를 허용 목록으로 제한하는 편이 좋아요.

입력값을 그대로 `ORDER BY`에 넣는 방식은 피하세요. 서버가 허용 목록에서 키를 고르고, 그 결과로 쿼리를 만드는 편이 안전해요. 허용되지 않은 키는 400 같은 명확한 오류로 돌려주면, FE가 잘못된 조합을 보내는 시점을 바로 알 수 있어요.

## URL에 필터 상태 두기 — FE 쪽 설계

FE에서는 필터와 정렬 상태를 URL 쿼리에 두는 편이 좋아요. MDN은 `URLSearchParams`가 URL의 쿼리 문자열을 다루는 메서드를 제공한다고 설명해요. 예를 들어 `?status=pending&period=7d&sort=created`처럼 두면 새로고침, 뒤로 가기, 공유 링크가 같은 목록을 가져와요.

필터를 바꾸면 페이지 커서나 page 번호도 함께 초기화해야 해요. 앞 페이지의 커서는 이전 조건에서 나온 값이라 새 조건에서는 맞지 않아요. 정렬 옵션 계약과 커서 초기화는 [검색 순위 글](/m/search-ranking)에서 더 자세히 봐요.

## FE 체크 포인트 — 응답 모양과 BE에 물을 질문

- 이 화면의 전체 개수가 정확해야 하는지 먼저 물어보세요.
- 정렬 키 목록과 각 키에 인덱스가 있는지 물어보세요.
- 자주 쓰는 필터 조합 세 개를 정해서, 그 조합의 실행 계획을 같이 보자고 하세요.
- 잘못된 정렬 키나 필터 키를 보내면 400으로 응답하는지, 기본값으로 바뀌는지 확인하세요.
- 개수가 근사값이라면 응답에 그 사실을 알려 주는 필드가 있는지 확인하세요.

## 시뮬레이터 안내 — 조합과 인덱스 열 순서 바꿔 보기

아래 시뮬레이터에서 상태, 기간, 정렬을 바꾸고 인덱스 열 순서를 골라 보세요. 훑은 인덱스 항목과 테이블 행 방문이 어떻게 달라지는지, 정렬 단계가 언제 사라지는지 확인하세요. 개수 방식과 facet 비용도 같이 바꿔 보세요. 수치는 모두 예시예요.

## 정리 — 열 순서 · 정렬 위치 · 개수 방식 결정

- 자주 거는 등호 조건을 앞 열에, 정렬 열을 뒤에 두는 인덱스를 고르는 편이 좋아요.
- 드문 값을 고르는 필터는 부분 인덱스로 따로 담는 것을 검토하는 편이 좋아요.
- 금액순처럼 인덱스에 없는 정렬은 정렬 단계가 남는다는 전제로 페이지 크기와 조건 범위를 정하는 편이 좋아요.
- 전체 개수는 정확도 요구를 먼저 확인하고, 필요 없으면 상한 표시나 다음 페이지 여부로 바꾸는 편이 좋아요.
- 정렬 키와 필터 키는 허용 목록으로 제한하고, 필터 상태는 URL에 두는 편이 좋아요.
