티켓 오픈 시각에 화면에는 "대기 순번 3,201번"이 떠요. 버튼을 눌러도 예매 화면으로 바로 가지 못하고, 숫자만 조금씩 줄어들어요. 이 숫자는 누군가 일부러 만든 장치예요. 서버가 한꺼번에 받을 수 없는 사람을 입구에서 잠시 세워 두는 방법이에요.

이 글은 한 질문에서 출발해요. **티켓 오픈 때 "대기 순번 3,201번"은 어떻게 동작하나요?** 답을 찾으려면 왜 입구를 막아야 하는지, 대기실이 순번과 입장 토큰을 어떻게 나누는지, 그리고 그 앞뒤에서 요청 제한과 재시도가 어떤 역할을 하는지 차례로 봐야 해요.

글의 숫자는 모두 설명을 위한 예시예요. 아래 시뮬레이터의 기본값과 같아요. 시뮬레이터에서 1틱은 1초예요.

## 입구를 막는 이유 — 처리 능력은 정해져 있어요

예매 서버와 DB 가 한 번에 처리할 수 있는 요청 수는 정해져 있어요. 이 글에서는 그 값을 C 라고 부를게요. 예시로 C 가 초당 100건이라고 해요.

접속이 1,000명인데 전부 한꺼번에 들어오면 어떻게 될까요?

| 입장 방식             | 성공    | 포기  | 최고 부하  |
| --------------------- | ------- | ----- | ---------- |
| 보호 없음             | 300명   | 700명 | 1,000건/초 |
| 대기실 (R = 100명/초) | 1,000명 | 0명   | 100건/초   |

보호 없이 들어오면 첫 틱에 1,000건이 몰리고, 100건만 처리돼요. 나머지 900건은 실패해요. 실패한 사용자는 다음 틱에 다시 요청하고, 그 재시도가 다시 처리 능력을 넘어요. 세 번째 시도까지 실패하면 포기해요. 실패한 요청이 재시도로 다시 몰리는 이 현상을 흔히 **재시도 폭풍(retry storm)** 이라고 불러요.

AWS 아키텍처 블로그는 여러 클라이언트가 같은 시점에 재시도하면 서로 경쟁하는 호출이 덩어리로 생긴다고 설명해요. 그래서 재시도 간격에 무작위성을 넣으라고 권해요. 이 내용은 아래 "재시도는 흩어지게" 절에서 다뤄요.

## 가상 대기실 — 순번을 주고 일정한 속도로 들여보내요

Cloudflare 는 대기실을 "넘치는 사용자를 대기실로 보내 원본 서버가 요청에 압도되지 않게 보호하는 장치"로 설명해요. 원리는 단순해요. 처리 능력보다 많이 들어온 사람은 줄 세우고, 정해진 속도로만 안으로 들여보내요.

흐름은 네 단계예요.

1. 접속하면 대기실이 순번을 발급하고, 그 사실을 쿠키나 토큰으로 브라우저에 남겨요.
2. 서버는 초당 R 명만 입장시켜요. 입장 속도 R 은 백엔드 처리 능력 C 이하로 잡아야 해요.
3. 입장한 사용자에게는 짧은 시간만 쓰는 서명된 입장 토큰을 줘요.
4. 예매 API 는 요청마다 입장 토큰을 검증하고, 없거나 만료됐으면 대기실로 돌려보내요.

Cloudflare 의 설정 화면도 같은 구조예요. 입장 속도는 "New users per minute", 동시에 머무를 수 있는 사람 수는 "Total active users", 입장 뒤 세션이 유지되는 시간은 "Session duration"으로 나뉘어 있어요. 세 값이 각각 입구 속도, 안쪽 정원, 입장 유효 시간에 대응해요.

### 순번과 예상 대기 시간은 다른 값이에요

화면에 "3,201번"과 "약 32분"이 같이 뜨는 경우가 많아요. 두 값은 성격이 달라요.

| 값        | 무엇인가요                              | 신뢰도                  |
| --------- | --------------------------------------- | ----------------------- |
| 순번      | 서버가 발급하고 기록한 실제 위치예요    | 사실이에요              |
| 예상 대기 | 남은 순번을 입장 속도로 나눈 추정이에요 | 추정이라 틀릴 수 있어요 |

예상 대기는 입장 속도가 바뀌거나 이탈자가 생기면 달라져요. 그래서 순번은 확정된 값처럼 보여 주고, 예상 대기는 "약"이나 "대략"을 붙여 보여 주는 편이 정직해요. 이건 설계 판단이에요.

### 새로고침과 여러 탭

순번은 브라우저에 남긴 쿠키나 토큰으로 유지해요. Cloudflare 도 대기실 쿠키를 써요. 그래서 새로고침을 해도 순번은 그대로 남아요. 쿠키가 없어지면 서버는 이 사람을 새 사람으로 봐요. 이때 대기 줄 맨 뒤로 가는 것이 자연스러워요.

여러 탭을 열면 같은 쿠키를 공유하니 한 순번을 함께 써요. 다른 기기에서 접속하면 새 순번을 받아요. 한 사람이 기기를 바꿔 여러 순번을 얻는 것을 막으려면 로그인 계정이나 서버 쪽 세션 기준으로 묶는 방법이 필요해요. 이 부분은 설계 판단이에요.

### 봇은 순번을 여럿 만들 수 있어요

자동화 프로그램은 순번 발급 요청을 빠르게 많이 보낼 수 있어요. 순번만 있고 입장 토큰 검증이 없으면 대기실이 의미를 잃어요. 그래서 순번 발급 자체에도 속도 제한을 걸고, 입장 토큰은 짧게 유효하게 두고, 예매 API 가 토큰을 반드시 확인하게 해야 해요. 이것도 설계 판단이에요. 특정 방식이 항상 막는다고 말하지는 않아요.

## 요청 제한 알고리즘 — 다섯 가지 방법

대기실은 "들어오는 총량"을 줄여요. 요청 제한은 "한 사람이나 한 IP 가 시간당 얼마나 보내는지"를 막아요. 제한은 게이트웨이, 엣지, 앱 중 한 곳에서 돌아가요. 키는 사용자, IP, API 키 중 무엇으로 셀지 정해요.

시뮬레이터의 한도는 5건, 창은 1,000ms 로 맞췄어요. 같은 패턴에도 알고리즘마다 결과가 달라요.

| 알고리즘        | 동작                                                 | 장점                                          | 주의                                        |
| --------------- | ---------------------------------------------------- | --------------------------------------------- | ------------------------------------------- |
| 고정 창         | 정해진 창마다 카운트를 0 으로 되돌려요               | 구현이 가장 단순해요                          | 창 경계에서 한도의 두 배가 통과할 수 있어요 |
| 슬라이딩 로그   | 최근 창 안의 요청 시각을 모두 기록해요               | 어떤 창에서도 한도를 정확히 지켜요            | 기록이 많아지면 메모리를 써요               |
| 슬라이딩 카운터 | 이전 창과 현재 창의 개수를 비율로 섞어 추정해요      | 메모리가 적어요                               | 추정이라 경계에서 약간 어긋날 수 있어요     |
| 토큰 버킷       | 버킷에 토큰이 초당 일정량 차고, 요청마다 하나씩 써요 | 짧은 버스트를 허용하면서 평균 속도를 제한해요 | 버킷 용량만큼 한꺼번에 나갈 수 있어요       |
| 누수 버킷       | 요청을 큐에 쌓고 일정한 속도로만 흘려보내요          | 출력이 매우 고르게 나와요                     | 큐가 차면 밀린 요청을 버려야 해요           |

Amazon API Gateway 문서는 토큰 버킷을 이렇게 설명해요. 요청마다 토큰 하나가 필요하고, 버스트는 정해진 만큼 한도를 넘을 수 있어요. 이 문서는 한도가 보장된 최댓값이 아니라 목표라고도 밝혀요.

시뮬레이터에서 **고정 창 + 창 경계에 몰린 요청**을 골라 보세요. 1,000ms 창 끝에 5건, 다음 창 처음에 5건이 들어오면 100ms 안팎에 10건이 통과해요. 슬라이딩 로그로 바꾸면 5건만 통과하고 나머지는 429 가 돼요.

## HTTP 응답 — 429 와 Retry-After

요청을 막을 때 쓰는 상태 코드는 429 예요. RFC 6585 는 429 를 "정해진 시간 안에 너무 많은 요청을 보낸 사용자"에게 주는 응답이라고 정의해요. 응답에는 Retry-After 헤더를 함께 붙일 수 있어요.

RFC 9110 은 Retry-After 를 "사용자 에이전트가 다음 요청을 보내기 전까지 기다려야 할 시간"이라고 정의해요. 값은 초 단위 숫자나 HTTP 날짜 중 하나예요. 503 과 함께 쓰이면 서비스가 얼마 동안 사용할 수 없는지를 알려 줘요.

둘을 나누면 이래요.

| 상태 | 뜻                             | 클라이언트가 할 일                                       |
| ---- | ------------------------------ | -------------------------------------------------------- |
| 429  | 이 사용자가 너무 많이 보냈어요 | Retry-After 만큼 기다린 뒤 재시도해요                    |
| 503  | 서비스가 지금 받을 수 없어요   | Retry-After 가 있으면 따르고, 없으면 백오프로 재시도해요 |

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 30
Content-Type: application/json

{"error": "rate_limited", "message": "잠시 후 다시 시도해 주세요."}
```

요청 제한 정보를 응답 헤더로 알려 주는 방식도 있어요. IETF 의 RateLimit 헤더 초안은 `RateLimit-Policy`와 `RateLimit` 필드를 정의해요. 이 문서는 아직 RFC 가 아니라 인터넷 초안(Internet-Draft)이에요. 초안이라 헤더 이름과 형식이 바뀔 수 있어요.

## 재시도는 흩어지게 — 백오프와 jitter

재시도 간격을 1초, 2초, 4초처럼 늘리는 방법을 지수 백오프라고 해요. AWS 아키텍처 블로그는 백오프만으로는 충분하지 않다고 말해요. 클라이언트들이 같은 시점에 재시도하는 덩어리가 그대로 남기 때문이에요. 해결책은 백오프를 없애는 것이 아니라 jitter 를 더하는 것이에요.

블로그의 예시에서 클라이언트 100개가 경쟁할 때, jitter 를 넣은 방식은 지수 백오프만 쓴 방식보다 호출 수를 절반 넘게 줄였어요. 이 수치는 그 글의 시뮬레이션 예시이고, 여러분의 서비스에서 같은 값이 나온다는 뜻은 아니에요.

FE 에서 재시도를 짤 때 지킬 규칙을 정리해 볼게요.

- 서버가 Retry-After 를 주면 그 값을 최우선으로 따르세요.
- 주지 않았다면 지수 백오프에 jitter 를 더해 재시도 시각을 정하세요.
- 최대 횟수를 정하고, 넘으면 사용자에게 상태를 보여 주고 멈추세요.
- 자동 재시도 루프를 두 개 이상 겹쳐 두지 마세요. 한 요청을 여러 계층에서 다시 보내면 부하가 곱해져요.

## FE 체크 포인트

- 순번과 예상 대기는 서버 응답에서 받아 그대로 보여 주세요. 클라이언트에서 계산한 값을 순번처럼 보여 주지 마세요.
- 폴링 간격은 서버가 준 값을 따르세요. 응답에 간격이 없다면 몇 초 이상으로 넉넉히 잡으세요. 짧은 간격으로 돌리면 대기실 자체가 부하가 돼요.
- 429 와 503 을 받으면 Retry-After 를 읽어 다음 요청 시각을 정하세요. 버튼을 연타하거나 새로고침을 반복하게 두지 마세요.
- 재시도 간격에는 jitter 를 넣으세요. 같은 시각에 모인 탭들이 같은 시각에 다시 보내지 않게 해요.
- 입장 토큰은 쿠키나 메모리에 보관하고, 만료되기 전에 갱신 요청을 보내세요.
- 순번이 바뀔 때마다 스크린 리더가 읽도록 `aria-live="polite"` 영역에 넣으세요. 매초 바뀌면 읽기 과하니 몇 초 간격으로 묶어 알리는 편이 좋아요. 이것도 설계 판단이에요.

## 정리 — 입구에서 속도를 맞추고, 실패는 흩어요

대기실은 처리 능력을 넘지 않도록 입장 속도를 정해요. 순번은 서버의 사실이고, 예상 대기는 추정이에요. 요청 제한은 시간 창과 알고리즘 선택에 따라 경계에서 통과하는 수가 달라져요. 실패가 나면 429 와 Retry-After 를 따르고, 재시도에는 jitter 를 넣어 흩어요.

앞선 모듈에서 본 좌석 선점은 같은 좌석 한 칸에 요청이 몰리는 문제였어요. [콘서트 좌석 선점](/m/concert-seats)에서 이어지는 이 글은 그 앞의 입구를 다뤄요. 입구가 속도를 맞춰 주면 좌석 행에 닿는 요청도 줄어들어요. 요청을 한 번에 받지 않으면 [트랜잭션 · 락 · 데드락](/m/transactions)의 락 경쟁도 덜 커져요.
