상품 상세 화면 하나를 그리려면 API를 여러 번 불러야 하는 일이 흔해요. 상품, 판매자, 배송비, 리뷰, 추천을 각각 다른 곳에서 받아 오기 때문이에요. 이 글은 호출이 늘어날 때 생기는 지연과 받은 데이터의 낭비를 보고, 화면 단위로 응답을 묶는 BFF와 GraphQL을 비교해요. 글 아래 시뮬레이터에서 왕복 시간을 바꿔 보면 감이 빨리 와요.

## 화면 데이터 호출 — 요청 수와 워터폴

상품 상세 화면을 열면 네트워크 탭에 요청이 여러 줄 찍혀요. 화면 한 장을 채우는 데 데이터 출처가 여러 개이기 때문이에요. 요청이 늘면 그만큼 왕복 지연도 늘어요.

요청이 앞 요청의 응답을 기다려야 할 때 시간이 앞뒤로 쌓여요. 이 모양을 워터폴이라고 불러요. 판매자 정보는 상품 응답 안의 판매자 id가 있어야 보낼 수 있어요.

## 리소스 중심 REST — 오버페칭과 언더페칭

REST는 리소스 하나를 한 엔드포인트가 맡는 방식이에요. 예를 들어 `GET /products/123`은 상품 리소스 전체를 돌려줘요. 화면이 상품 이름과 가격만 쓰더라도 나머지 필드가 함께 내려와요. 이것이 오버페칭이에요.

반대로 화면에 필요한 값이 다른 리소스에 있으면 클라이언트가 한 번 더 요청해야 해요. 이것이 언더페칭이에요. GraphQL 명세는 이렇게 받으면 오버페칭과 언더페칭을 피한다고 설명해요.

## 호출 의존 관계 — 순차 지연과 병렬 묶기

의존이 없는 호출은 같이 보낼 수 있어요. 의존이 있는 호출은 부모가 끝난 뒤에만 보낼 수 있어요. 그래서 전체 시간은 모든 호출을 더한 값이 아니라, 의존 경로에서 가장 긴 경로에 가까워져요.

아래는 이 글의 시뮬레이터 기본값이에요. 왕복 120 ms, 서비스 기준 처리 20 ms로 가정한 예시예요.

| 호출 방식           | 요청 수 | 화면 완성 (예시) |
| ------------------- | ------- | ---------------- |
| REST 순서대로       | 5번     | 813 ms           |
| REST 가능한 것 병렬 | 5번     | 439 ms           |
| BFF 한 번           | 1번     | 202 ms           |

병렬로 보내도 배송비는 판매자 응답 뒤에 나가야 해요. 그래서 병렬 REST도 439 ms가 걸려요.

## N+1의 FE 쪽 모양 — 목록마다 호출하는 패턴

[N+1 사례](/m/n-plus-one)에서는 서버가 글마다 댓글을 따로 조회하는 모양을 봤어요. FE에서도 같은 모양이 나와요. 목록의 카드마다 판매자 정보 API를 따로 부르면 FE가 N+1 호출을 만드는 셈이에요.

이때는 쿼리 수 대신 요청 수를 세 보면 돼요. 카드 수에 비례해 요청이 늘면 목록 응답을 묶는 API나 BFF를 검토할 만해요.

## BFF 패턴 — 화면 단위 서버 한 층

Sam Newman은 범용 API 백엔드 하나 대신 사용자 경험마다 백엔드를 두는 방식을 설명해요. 이를 Phil Calçado가 Backend For Frontend(BFF)라고 불렀다고 해요. 이 층은 특정 UI에 강하게 묶이고, 보통 그 UI를 맡는 팀이 함께 관리한다고 설명해요.

Azure Architecture Center 문서는 BFF가 프런트엔드와 백엔드 서비스 사이에 놓인다고 설명해요. 인터페이스가 여러 개라면 BFF를 인터페이스마다 하나씩 만들라고 권해요. 같은 문서는 클라이언트마다 코드가 중복되는 비용과 맞춤 응답의 이점을 비교해 보라고 권해요.

| 장점                                   | 비용                                      |
| -------------------------------------- | ----------------------------------------- |
| 응답을 화면 모양에 맞출 수 있어요      | 화면마다 서버 코드가 생겨요               |
| FE와 서버 사이 왕복을 한 번으로 줄여요 | 서버 안에서는 여전히 여러 서비스를 불러요 |
| 팀이 릴리스 주기를 독립적으로 정해요   | 공통 로직이 BFF마다 중복될 수 있어요      |

BFF는 클라이언트 왕복을 줄여요. 서버 안에서 상품, 판매자, 리뷰를 부르는 호출 수는 그대로예요. 호출이 서버로 옮겨 갈 뿐이에요.

## GraphQL 질의 — 필요한 필드만 한 번에

GraphQL에서 클라이언트는 필요한 필드를 질의로 적어요. 서버는 그 모양대로만 응답해요. GraphQL 명세는 연산이 필요한 정보만 선택하고 그 정보만 받는다고 설명해요.

```graphql
# 예시: 상품 상세 화면이 쓰는 필드만 고른 질의
query ProductDetail($id: ID!) {
  product(id: $id) {
    name
    price
    seller {
      name
      shippingFee
    }
    reviews(first: 3) {
      rating
      body
    }
  }
}
```

GraphQL 서버는 보통 `/graphql` 같은 단일 URL 하나에서 동작한다고 공식 문서는 설명해요. 모든 요청을 그 엔드포인트로 보내요. Azure 문서는 GraphQL의 질의 방식이 별도 BFF 층이 필요 없어진다고 설명해요. 응답 모양을 누가 맡을지는 여전히 팀이 정해야 해요.

## HTTP 캐시 — POST 질의와 persisted query

GraphQL 서버는 query 연산을 POST로 처리해야 해요. GET으로도 query를 받을 수 있어요. GraphQL 공식 문서는 GET 요청이 보통 기본적으로 캐시 가능하다고 여겨져서, HTTP 캐시나 CDN과 맞출 여지가 있다고 설명해요.

RFC 9111은 오늘 많이 쓰이는 HTTP 캐시가 GET 응답만 캐시해서 URI를 캐시 키로 쓴다고 설명해요. POST 질의는 이런 캐시와 잘 맞지 않아요. 긴 질의는 브라우저와 CDN의 URL 크기 제한 때문에 GET에 싣기도 어려워요. 그래서 질의 본문 대신 해시를 보내는 persisted query가 쓰여요. GraphQL 공식 문서는 이 방식으로 서버가 저장된 문서를 찾아 실행한다고 설명해요.

## 서버 쪽 N+1 — resolver 배치와 DataLoader

GraphQL은 필드마다 resolver를 실행해요. 리뷰 목록에서 작성자를 resolver 마다 따로 조회하면, 서버 안에서 N+1이 생겨요. GraphQL 공식 문서는 이를 여러 요청을 모아 한 번에 보내는 배치로 풀고, 예로 DataLoader를 든다고 설명해요.

DataLoader README는 한 번의 실행 단계 안에서 들어온 load 호출을 묶는다고 설명해요. 같은 요청 안에서 일어난 load 결과는 메모이제이션 캐시에 남긴다고 설명해요. 인스턴스는 보통 요청마다 새로 만든다고 해요.

## 부분 실패 처리 — data와 errors 함께 읽기

GraphQL 응답은 data와 errors를 함께 담을 수 있어요. null을 받을 수 있는 필드에서 오류가 나면 그 필드는 null로 바뀌고, 나머지 필드는 그대로 남아요. 명세는 이 결과를 부분 응답이라고 불러요.

errors의 각 항목은 path로 실패한 응답 필드를 가리켜요. HTTP 상태 코드도 알아 둘 만해요. 공식 문서는 data가 null이 아니면 errors가 있어도 2xx를 보낸다고 설명해요. HTTP에 부분 성공을 뜻하는 상태 코드가 없기 때문이에요. 실행 자체를 막는 검증 오류는 보통 400이에요.

## 화면 전용 API 비용 — 응답 모양의 소유 팀

화면이 바뀌면 응답 모양도 바뀌어야 해요. 그 변경을 누가 맡는지가 정해져 있어야 해요. Azure 문서는 공유 백엔드를 여러 프런트엔드 팀이 쓰면, 한 팀이 요청한 변경을 다른 팀과 맞춰 봐야 해서 합의가 늦어진다고 설명해요. 같은 문서는 프런트엔드 팀이 각자 BFF를 관리하면 릴리스 주기와 기능 통합을 스스로 정할 수 있다고 설명해요.

Newman은 BFF를 UI와 같은 팀이 맡으면 API를 UI 요구에 맞춰 바꾸기 쉽고, 클라이언트와 서버의 릴리스를 맞추기도 쉽다고 설명해요. 반대로 화면마다 서버 코드가 생기는 만큼 운영할 대상도 늘어요. 이 비용을 감수할지는 화면이 얼마나 자주 바뀌는지로 정하는 편이 좋아요.

## FE 체크 포인트

### 호출 지도 — 데이터 출처 그리기

화면의 데이터 항목마다 어느 호출이 주는지 표로 적어요. 항목 사이의 의존 화살표도 그려요. 화살표가 긴 경로가 화면 완성 시간을 정해요.

### 병렬 묶기 — Promise.all과 부분 실패

의존이 없는 호출은 `Promise.all`로 같이 보내요. MDN 문서는 Promise.all()이 모든 입력이 이행되면 값 배열로 이행하고, 하나라도 거부되면 첫 거부 이유로 거부한다고 설명해요. 리뷰 하나가 실패해도 화면 전체를 막으면 안 될 때는 `Promise.allSettled`를 검토해요. MDN은 이 메서드가 한 입력이 거부되어도 모든 입력이 끝날 때까지 기다린다고 설명해요.

### 필드 목록 — 화면이 렌더하는 값만

화면이 실제로 그리는 필드 목록을 적어요. GraphQL을 쓰면 그 목록을 질의에 그대로 옮겨요. REST를 쓰면 응답에서 안 쓰는 필드를 어디서 줄일지 정해요.

### 캐시 키 — 화면 입력으로 정하기

화면 단위 응답을 캐시하면 키에 상품 id 같은 화면 입력을 넣어요. 캐시 만료 순간 같은 키 요청이 몰리는 문제는 [캐시와 캐시 스탬피드](/m/cache-stampede)에서 따로 다뤄요.

## 시뮬레이터 안내 — 호출 방식별 완성 시간

시뮬레이터는 상품 상세 화면의 의존 그래프를 고정해 두고, 호출 방식과 왕복 시간, 서비스 처리 기준을 바꿔 봐요. 완성 시간은 왕복, 처리, 전송 시간을 더한 단순화 모델이에요. 모든 숫자는 예시예요.

기본값에서 왕복을 1 ms 늘리면 순차 REST는 5 ms 늘고, BFF는 1 ms만 늘어요. 호출 수만큼 왕복이 쌓이기 때문이에요. BFF와 GraphQL은 이 모델에서 같은 숫자를 내요. 차이는 응답 모양을 누가 정하는지에 있어요.

## 정리 — 호출 수 · 응답 모양 · 서버 부담

- 호출이 늘면 왕복 지연이 쌓여요. 의존이 없는 호출은 병렬로 묶어요.
- BFF는 클라이언트 왕복을 줄이지만, 서버 안 호출과 팀 경계는 그대로 남아요.
- GraphQL은 필요한 필드만 받지만, 서버 쪽 N+1과 HTTP 캐시 문제를 가져와요.
- 부분 실패는 data와 errors를 함께 읽고, 실패한 필드만 화면에서 비워 둬요.

아래 시뮬레이터에서 왕복 시간과 서비스 처리 시간을 바꿔 보세요. 요청 수, 완성 시간, 안 쓰는 바이트가 호출 방식에 따라 어떻게 달라지는지 확인하세요.
