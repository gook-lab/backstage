"결제가 느려요"라는 제보가 오면 먼저 나눠 볼 것이 세 가지예요. 화면이 늦게 그렸는지, 서버가 늦게 답했는지, 서버 안 어느 단계가 오래 걸렸는지요. 이 글은 그 나눔에 쓰는 도구를 정리해요. 글 아래 시뮬레이터에서 원인을 하나씩 켜 보면 워터폴이 어떻게 바뀌는지 직접 볼 수 있어요.

## 로그 · 메트릭 · 트레이스 — 세 신호가 답하는 질문

OpenTelemetry는 관측 데이터를 세 신호로 나눠 설명해요. 셋은 같은 사건을 다른 모양으로 기록한 것이라서, 어느 하나만 보면 놓치는 것이 생겨요.

| 신호     | 담는 것                      | 답하는 질문                     | 예시                             |
| -------- | ---------------------------- | ------------------------------- | -------------------------------- |
| 로그     | 시각과 함께 남긴 개별 기록   | 이 요청에서 무슨 일이 있었나요? | 결제 거절 사유 코드              |
| 메트릭   | 시간에 따라 모은 측정값      | 지금 전체가 괜찮나요?           | 초당 요청 수, 지연 시간 분포     |
| 트레이스 | 요청 하나가 거친 span의 모음 | 이 요청은 어디서 시간을 썼나요? | 게이트웨이 → API → DB → 결제 API |

OpenTelemetry 문서는 메트릭을 "런타임에 잡은 측정값"으로 설명하고, 요청 지표가 가용성과 성능의 중요한 지표라고 말해요. 트레이스는 span 들이 중첩된 구조라서, 자식 span이 하위 작업을 나타낸다고 설명해요. 같은 문서는 트레이스를 "맥락, 연관성, 계층을 가진 구조화된 로그의 모음"으로 보는 방법도 있다고 해요.

## FE 요청과 BE 기록 연결 — traceparent 헤더

FE에서 보낸 요청과 BE 로그를 잇는 열쇠는 W3C Trace Context 권고안의 `traceparent` 헤더예요. 형식은 네 칸이에요.

```text
traceparent: 00-0af7651916cd43dd8448eb211c80319c-b7ad6b7169203331-01
             │   │                                │                 └ trace-flags
             │   └ trace-id (32자리 16진수)        └ parent-id (16자리 16진수)
             └ version (지금은 00)
```

권고안은 trace-id가 16바이트, parent-id가 8바이트이고 모두 0으로 채우면 안 된다고 정해요. trace-flags의 최하위 비트는 sampled 플래그예요. 이 플래그는 호출한 쪽이 추적 데이터를 기록했을 수 있다는 표시예요.

흐름은 이래요. FE가 요청마다 `traceparent`를 붙이면, BE는 받은 trace-id를 꺼내 자기 로그와 span에 실어요. 같은 trace-id로 검색하면 FE 요청과 BE 로그가 한 묶음으로 모여요. OpenTelemetry 문서도 이 헤더에서 원격 맥락을 꺼내 로컬 맥락에 넣으면, BE에서 두 요청을 한 트레이스의 span으로 볼 수 있다고 설명해요.

요청 ID와 trace-id는 같은 목적이에요. 팀은 trace-id를 요청 ID로 쓰거나, 별도 헤더를 정해서 쓸 수 있어요. W3C 권고안은 `traceparent`와 `tracestate`를 정하지만, 요청 ID 헤더 이름은 정하지 않아요.

## span 트리 — 워터폴에서 시간이 쓰인 곳 찾기

span은 작업 한 단위예요. 이름, 부모 span ID, 시작과 끝 시각을 가져요. 아래는 결제 요청 하나를 예시로 그린 트리예요. 모든 숫자는 예시 값이에요.

```text
요청 전체 171ms (예시)
├─ 게이트웨이 · 라우팅 4ms
├─ API 서버 · 결제 확정 164ms
│  ├─ DB · 세션 조회 9ms
│  ├─ DB · 장바구니 조회 9ms
│  ├─ DB · 상품 12개 IN 조회 14ms
│  ├─ 외부 결제 API 호출 120ms
│  └─ DB · 결제 기록 저장 12ms
└─ 응답 직렬화 · 전송 3ms
```

워터폴을 읽을 때는 이 순서로 봐요.

1. 가장 긴 막대를 찾아요. 이 예시에서는 외부 결제 API 호출이에요. 서버가 외부 서비스를 기다린 시간이라서, FE 화면 코드를 고쳐도 줄지 않아요.
2. 같은 이름의 DB span이 줄줄이 나오면 N+1 쿼리를 의심해요. 앞 글의 목록 조회 패턴과 같은 모양이에요.
3. 부모 span과 자식 span의 합이 맞는지 봐요. 자식 사이에 빈 시간이 있으면 그 시간은 부모가 직접 쓴 시간이거나, span을 남기지 않은 작업이 쓴 시간이에요.
4. 서버 span 합계와 브라우저가 잰 요청 시간의 차이는 네트워크 왕복과 대기 쪽에서 나와요. 이 차이는 span 으로는 안 보여요.

## 백분위 — 평균 대신 p95 · p99를 함께 보기

평균은 한 번에 보기 좋지만 느린 꼬리를 가려요. Google SRE 책은 평균 지연이 100ms 인 서비스가 초당 1,000요청을 받을 때, 요청의 1%가 5초쯤 걸릴 수 있다고 예를 들어요. 평균만 보면 이 문제가 안 보여요.

FE 에는 더 직접적인 문제가 있어요. 화면 하나가 BE 여러 개를 부를 때, 한 BE의 99백분위 값이 FE 응답의 중앙값이 될 수 있다고 같은 책이 설명해요. API를 여러 번 부르는 화면에서는 가끔 느린 호출이 거의 항상 보이는 지연이 돼요.

백분위는 정렬한 값에서 순위로 골라요. 요청 100개라면 p95는 95번째, p99는 99번째 값이에요. 이 글의 시뮬레이터는 이 순위 방식으로 계산해요. 예시로 기본 설정에서 평균은 212ms, p95는 649ms, p99는 742ms가 나와요. 평균만 보고 "괜찮다"고 하면 꼬리를 놓치는 숫자예요.

## Server-Timing — 서버 시간을 브라우저에서 보기

`Server-Timing` 응답 헤더는 서버가 처리 단계별 시간을 브라우저에 알려 줘요. MDN은 `Server-Timing: db;dur=53, app;dur=47.2` 같은 형식을 보여 줘요. `dur`는 밀리초예요.

```http
Server-Timing: db;dur=53;desc="DB 4회", payment;dur=120
```

몇 가지 조건이 있어요.

- 기본적으로 같은 출처에서만 읽을 수 있어요. 다른 출처에 보여 주려면 `Timing-Allow-Origin` 헤더로 출처를 적어야 해요. `*`를 쓰면 모든 출처가 볼 수 있어요.
- MDN은 이 헤더가 민감한 애플리케이션과 인프라 정보를 드러낼 수 있다고 경고해요. 어떤 지표를, 언제, 누구에게 보낼지 정하라고 권해요. 예를 들어 로그인한 사용자에게만 보내는 식이에요.
- 일부 브라우저에서는 이 인터페이스가 보안 컨텍스트(HTTPS)에서만 동작해요.

브라우저에서는 Performance API로 이 값을 읽어요. MDN은 `name`, `dur`, `desc`가 각각 PerformanceServerTiming의 name, duration, description에 대응한다고 설명해요.

## CORS 헤더 조건 — 보내는 헤더와 읽는 헤더

FE가 다른 출처의 API를 부르면 헤더마다 조건이 달라요. MDN은 직접 설정할 수 있는 요청 헤더가 CORS 안전 목록(Accept, Accept-Language, Content-Language, Content-Type 등)으로 한정된다고 설명해요. 그 밖의 헤더를 붙이면 브라우저는 먼저 preflight 요청을 보내요.

| 방향           | 헤더                          | 필요한 설정                                  | 근거                                                         |
| -------------- | ----------------------------- | -------------------------------------------- | ------------------------------------------------------------ |
| FE → BE 요청   | `traceparent`                 | 응답의 `Access-Control-Allow-Headers`에 포함 | 안전 목록 밖의 요청 헤더라 preflight가 나가요                |
| BE → FE 응답   | 요청 ID 같은 커스텀 응답 헤더 | `Access-Control-Expose-Headers`에 나열       | 기본으로 노출되지 않는 헤더는 서버가 나열해야 읽을 수 있어요 |
| BE → FE 타이밍 | `Server-Timing`               | `Timing-Allow-Origin`에 출처                 | 같은 출처 제한을 이 헤더로 풀어요                            |

## 로그 내용 — 구조화하고 민감한 값 빼기

OWASP 로깅 치트 시트는 기록하지 말아야 할 값을 나열해요. 직접 남기지 않고 제거, 마스킹, 정화, 해시, 암호화 중 하나를 하라고 해요.

- 액세스 토큰, 인증 비밀번호, 암호화 키와 기타 주요 비밀값
- 세션 식별 값 (추적에 필요하면 해시한 값을 쓰라고 해요)
- 민감한 개인정보와 PII (건강, 주민등록 같은 정부 식별자 포함)
- 데이터베이스 연결 문자열
- 카드 소유자 데이터

결제 요청 body를 통째로 로그에 남기면 이 목록을 한 번에 어기게 돼요. 로그에는 trace-id, 요청 ID, 결과 코드처럼 짧은 값만 남기는 편이 안전해요. 이 부분은 판단이에요.

OWASP는 로그 줄이 CR/LF 문자로 위조되는 것을 막으려면 비구조 텍스트 형식을 쓰지 말라고 권해요. 그래서 JSON 같은 구조화 로그로 남기고, 필드 이름을 고정해 두면 검색과 집계가 쉬워져요.

## 샘플링 — 전부 남기지 않을 때 고르는 위치

모든 요청을 트레이스로 남기면 비용이 커져요. OpenTelemetry는 샘플링 위치를 두 가지로 나눠요.

- 헤드 샘플링은 요청 시작 시점에 남길지 정해요. 트레이스 전체를 보지 않아요.
- 테일 샘플링은 트레이스의 span 대부분을 본 뒤 결정해요. 트레이스의 여러 부분에서 나온 기준으로 고를 수 있어요.

W3C 권고안은 sampled 플래그를 설명하면서, 요청 일부만 기록하면 트레이스가 끊길 수 있다고 설명해요. FE가 보낸 `traceparent`를 BE가 따라가려면 샘플링 결정이 호출 체인에서 맞아야 해요. 그래서 샘플링 설정은 게이트웨이와 서비스가 같이 맞춰요.

## FE 에러 리포트 — 요청 ID 붙이기

FE가 에러를 리포트할 때 요청 ID를 같이 보내면, BE 로그에서 그 요청을 바로 찾을 수 있어요. 실무에서는 다음처럼 해요.

1. 응답 헤더에서 요청 ID를 읽어요. 이 헤더는 `Access-Control-Expose-Headers`에 있어야 읽혀요.
2. 에러 화면에는 "문의 번호"처럼 짧은 ID만 보여 줘요.
3. 에러 리포트에는 ID와 에러 코드를 담고, 요청 body나 토큰은 넣지 않아요.
4. 운영자는 같은 ID로 BE 로그와 트레이스를 검색해요.

## FE 체크 포인트 — 화면에서 맞추는 것

- API 호출을 감싸는 함수 한 곳에서 `traceparent`를 붙여요. 호출마다 손으로 붙이면 빠지는 곳이 생겨요.
- 교차 출처 API 라면 서버가 `Access-Control-Allow-Headers`에 `traceparent`를 넣었는지 확인해요.
- 에러 리포트에 요청 ID 필드가 있는지 확인해요.
- 평균만 보고 성능 이야기를 끝내지 않아요. p95와 p99를 같이 봐요.
- 화면이 여러 API를 기다리는지 세어 봐요. 기다리는 API가 많을수록 꼬리의 영향이 커져요.

## 시뮬레이터 — 원인을 바꿔 워터폴과 분포 보기

아래 시뮬레이터에는 세 가지 원인이 있어요. N+1 쿼리, 외부 결제 API 지연, 큰 응답이에요. 켜면 요청 하나의 워터폴이 바뀌고, 가장 긴 span이 강조돼요. 아래쪽에서는 요청 100개를 만들어 평균과 p50 · p95 · p99를 기본 설정과 나란히 보여 줘요.

요청 100개는 고정된 시드로 만들어서, 설정이 같으면 숫자도 같아요. 일부러 4% 정도의 요청은 외부 호출이 5배 느리게 만들었어요. 이 값은 꼬리가 어떻게 생기는지 보여 주려는 예시 값이고, 실제 서비스의 비율이 아니에요.
