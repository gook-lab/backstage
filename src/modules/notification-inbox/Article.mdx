종 아이콘의 빨간 숫자가 실제 안 읽은 알림 수와 자꾸 달라지고, "모두 읽음"을 누르면 몇 초씩 걸리기도 해요. 알림 하나를 읽는 일이 왜 이렇게 번거로울까요? 이 글에서는 알림을 어떤 행으로 저장할지, 읽음을 행마다 기록할지 커서 하나로 나타낼지, 안 읽은 개수를 매번 셀지 칸에 저장할지를 나눠 봐요. 그리고 탭 사이 배지를 맞추는 법과 오래된 알림을 정리하는 법까지 정리해요.

아래 시뮬레이터에서 읽음 방식과 개수 방식을 바꾸고, 새 알림 도착 · 하나 읽기 · 모두 읽음 · 두 탭 동시 읽기를 직접 실행해 볼 수 있어요. 숫자는 이 시뮬레이터 안에서만 쓰는 예시예요.

## 저장 모델 — 사용자별 행과 공지 한 건 + 읽음 기록

알림을 저장하는 방식은 두 가지예요. 하나는 받는 사람마다 알림 행을 하나씩 만드는 방식이에요. 다른 하나는 여러 사람에게 같은 내용을 보내는 알림을 한 건만 저장하고, 누가 읽었는지는 읽음 기록으로 따로 남기는 방식이에요.

| 저장 모델              | 알림이 올 때 쓰기            | 목록을 읽을 때                 | 주의                                    |
| ---------------------- | ---------------------------- | ------------------------------ | --------------------------------------- |
| 사용자별 행            | 받는 사람 수만큼 INSERT 해요 | `user_id` 조건 하나로 읽어요   | 받는 사람이 많으면 쓰기가 그만큼 늘어요 |
| 공지 한 건 + 읽음 기록 | 공지 한 건만 INSERT 해요     | 공지와 읽음 기록을 붙여 읽어요 | 쓰기 비용이 읽을 때로 옮겨 가요         |

사용자별 행은 쓰기가 받는 사람 수에 비례해요. 이 구조는 feed-fanout 글의 밀어 넣기와 같은 쓰기 증폭을 가져요. 그 계산은 [피드 팬아웃](/m/feed-fanout) 글에서 이어 봐요.

이 시뮬레이터는 사용자별 행 하나를 기준으로 읽음을 다뤄요. 공지 한 건 모델에서도 읽음 표시와 개수를 맞추는 문제는 같이 남아요.

## 읽음 표시 — 행마다 read_at과 읽음 커서

행마다 `read_at`을 두는 방식은 알림 하나를 읽을 때 그 행만 갱신해요. 구현이 가장 단순해요.

```sql
UPDATE notification
SET read_at = now()
WHERE user_id = 42 AND id = 9001 AND read_at IS NULL;
```

PostgreSQL 문서는 UPDATE가 조건을 만족하는 모든 행의 값을 바꾼다고 설명해요. 갱신된 행 수도 돌려줘요. `read_at IS NULL` 조건을 넣으면 이미 읽은 알림에 같은 요청이 와도 0 행을 갱신해요. 두 탭이 같은 알림을 눌러도 1 행을 갱신한 쪽만 뒤의 카운터를 줄이면 돼요.

읽음 커서 방식은 사용자마다 "여기까지 읽었어요" 값을 하나 둬요. 이 값보다 오래된 알림은 모두 읽은 것으로 봐요. 시간 값(`last_read_at`)을 써도 되고, 이 시뮬레이터처럼 도착 순서 번호를 써도 돼요.

커서 방식의 약점은 가운데 알림 하나만 읽는 동작이에요. 커서를 그 알림까지 옮기면 그보다 오래된 안 읽은 알림이 조용히 읽음이 돼요. 그래서 커서 밖에서 읽은 알림은 예외 행으로 따로 기록해요. 커서 바로 다음 번호가 예외 행으로 이어지면 커서를 옮기고 예외 행을 지워요.

| 읽음 방식      | 알림 하나 읽기                 | 모두 읽음                      | 주의                                  |
| -------------- | ------------------------------ | ------------------------------ | ------------------------------------- |
| 행마다 read_at | 행 1개 UPDATE                  | 안 읽은 행 수만큼 UPDATE       | 모두 읽음이 알림 수에 비례해요        |
| 읽음 커서      | 커서 밖이면 예외 행 1개 INSERT | 커서 1행 UPDATE와 예외 행 삭제 | 가운데를 먼저 읽으면 예외 행이 쌓여요 |

## 안 읽은 개수 — COUNT 조회와 칸 저장 비교

COUNT 방식은 배지를 열 때마다 안 읽은 행을 세요. 원본을 세기 때문에 어긋날 일이 없어요. PostgreSQL 위키는 `SELECT count(*) FROM tbl`이 행의 가시성을 하나씩 확인해야 해서 보통 순차 스캔으로 모든 행을 읽는다고 설명해요. 알림이 많아지면 배지를 여는 비용도 같이 늘어요.

안 읽은 행만 담는 부분 인덱스를 두면 세는 범위가 줄어요. PostgreSQL 문서는 부분 인덱스가 술어를 만족하는 행의 항목만 담는다고 설명해요. 쿼리의 WHERE 조건은 술어를 논리적으로 함의해야 이 인덱스를 쓸 수 있어요. 그래서 조건을 같은 모양으로 써야 해요.

```sql
CREATE INDEX notification_unread
ON notification (user_id)
WHERE read_at IS NULL;

SELECT count(*) FROM notification
WHERE user_id = 42 AND read_at IS NULL;
```

인덱스만으로 답하는 인덱스 전용 스캔도 있어요. 다만 PostgreSQL 문서는 가시성 정보가 인덱스 항목에는 없고 힙 항목에만 있다고 설명해요. 그래서 인덱스만 읽어도 힙을 확인해야 하는 행이 남을 수 있어요.

카운터 방식은 안 읽은 수를 칸 하나에 저장해요. 알림이 오면 +1, 읽으면 -1을 해요. 배지는 칸 하나만 읽으니 빨라요. 대신 두 가지 문제가 생겨요.

- 칸 하나에 쓰기가 몰려요. 같은 행에 UPDATE가 줄을 서는 문제는 [좋아요와 조회수 카운터](/m/hot-counters) 글과 같아요.
- 차감 규칙이 실제 행 변화와 어긋나면 칸이 틀려요. 두 탭이 같은 알림을 읽을 때 두 요청이 모두 -1을 하면 칸이 실제보다 1 작아져요. 차감 전에 갱신된 행 수를 확인하면 이 어긋남을 막을 수 있어요.

칸이 어긋났을 때는 COUNT로 다시 세서 칸을 맞춰요. 재계산에도 COUNT 만큼의 읽기 비용이 들어서, 주기 작업이나 배지를 열 때 확인하는 식으로 어긋남이 오래 남지 않게 해요. 예시로 하루에 한 번만 재계산하면 그 사이 틀린 숫자가 하루 동안 보여요.

| 개수 방식  | 배지 한 번에 읽는 행             | 어긋남                    | 주의                                         |
| ---------- | -------------------------------- | ------------------------- | -------------------------------------------- |
| 매번 COUNT | 안 읽은 행 수 (부분 인덱스 기준) | 없어요 (원본을 세요)      | 알림이 많으면 배지를 열 때마다 비용이 들어요 |
| 카운터 칸  | 칸 1개                           | 차감 규칙이 틀리면 생겨요 | 칸 하나에 쓰기가 몰려요. 재계산이 필요해요   |

## 모두 읽음 — 행 UPDATE 대신 커서 이동

"모두 읽음"이 느린 이유는 행마다 `read_at`을 채우기 때문이에요. 안 읽은 알림이 300개면 UPDATE가 300개 행을 바꿔요. PostgreSQL 진공 문서는 대량 UPDATE가 죽은 행 버전을 많이 남기고, 일반 VACUUM이 그 공간을 다시 쓸 수 있게 표시한다고 설명해요. 읽음 표시가 자주 바뀌는 테이블일수록 이 정리 비용이 함께 늘어요.

커서 방식은 커서를 가장 최근 알림 번호로 옮기고 예외 행을 지워요. 예시로 안 읽은 알림이 300개일 때 행마다 방식은 300 행을 갱신하고, 커서 방식은 커서 1행과 예외 행 몇 개만 건드려요.

커서 값을 정하는 시점도 중요해요. "모두 읽음"을 처리하는 순간 이후에 도착한 알림까지 읽음으로 바꾸면 사용자가 보지 못한 알림이 사라져요. 그래서 커서는 요청을 받은 시점에 있던 가장 최근 번호로 정해요. 그 뒤에 온 알림은 커서 뒤에 남아서 안 읽은 상태로 보여요.

## 여러 탭과 기기 — 배지 동기화

같은 브라우저 안의 탭끼리는 BroadcastChannel로 바로 알릴 수 있어요. MDN은 BroadcastChannel이 같은 출처의 문서(창, 탭, 프레임) 사이에서 통신하게 하고, 보낸 객체를 뺀 나머지에게 message 이벤트를 보낸다고 설명해요. 한 탭에서 읽음을 처리하면 다른 탭에 "배지를 다시 받으라"는 신호를 보내 숫자를 맞출 수 있어요.

숨겨진 탭은 신호를 바로 처리하지 않아도 돼요. MDN은 Page Visibility API가 탭을 바꾸거나 창을 최소화할 때 visibilitychange 이벤트를 보내고, visibilityState로 현재 상태를 알려 준다고 설명해요. 숨은 탭은 배지 조회를 미뤘다가, 다시 보이는 순간 한 번 맞추는 편이 좋아요.

BroadcastChannel은 같은 출처 안에서만 동작해요. 다른 기기까지 배지를 맞추려면 서버가 신호를 밀어 줘야 해요. 그 실시간 전달은 [실시간 전달](/m/realtime-delivery) 글 범위예요. 이 글에서는 신호를 받은 뒤 숫자를 어떻게 맞추는지만 다뤄요.

## 목록 페이지네이션 — 알림 번호 이후를 이어 읽기

알림 목록은 최신순으로 쌓이고 사용자는 오래된 쪽으로 이어 읽어요. 페이지 번호를 쓰면 읽는 도중 새 알림이 위에 쌓일 때 같은 알림이 두 번 보이거나 빠질 수 있어요. 마지막으로 받은 번호보다 작은 알림을 달라고 요청하면 이 문제를 줄일 수 있어요. 자세한 방식은 [페이지네이션](/m/pagination) 글에서 이어 봐요.

## 묶기 — 같은 글 좋아요를 한 줄로 모으기

예시로 "A 님 외 29명이 회원님의 글에 좋아요를 눌렀어요"라는 알림은 30개를 따로 두지 않아요. 받는 사람, 종류, 대상 글을 묶음 키로 두고 한 줄에 행위자 수와 최근 몇 명을 담아요. 같은 묶음 키로 들어오는 알림은 그 줄을 갱신해요.

묶음에는 두 가지를 정해야 해요.

- 시간 창: 같은 날, 같은 한 시간처럼 어디까지 한 묶음으로 볼지 정해요.
- 읽음 상태: 묶음 안에 읽은 것과 안 읽은 것이 섞이면, 새 행위가 들어왔을 때 묶음을 다시 안 읽음으로 바꿀지 정해요.

배지 숫자는 줄 수 기준으로 셀지, 행위 수 기준으로 셀지도 정해야 해요. 줄 수로 세면 30명이 와도 배지는 1이에요. 이 선택은 사용자가 "몇 개가 새로 왔나"를 어떻게 이해하는지에 따라 달라요.

묶음 줄도 같은 행에 쓰기가 몰릴 수 있어요. 인기 글에 좋아요가 몰리면 묶음 줄 하나를 계속 갱신하게 되므로, 앞의 카운터 글과 같은 판단이 필요해요.

## 보관 기간과 정리 — 오래된 알림 지우기

알림함은 보통 보관 기간을 둬요. 예시로 90일이 지난 알림은 지우는 식이에요. 이때 `DELETE ... WHERE created_at < ...`처럼 대량으로 지우면 죽은 행 버전이 많이 남아요. 앞에서 본 진공 문서의 내용과 같은 이유예요.

PostgreSQL 파티셔닝 문서는 파티션을 DROP TABLE 하거나 ALTER TABLE ... DETACH PARTITION 하는 방식이 대량 작업(bulk operation)보다 훨씬 빠르다고 설명해요. 다만 이 방법은 파티션 설계가 사용 패턴을 반영할 때 쓸 수 있어요. 알림을 생성 월 단위 파티션으로 나누면 오래된 달 전체를 한 번에 떼어 낼 수 있어요.

정리에는 두 가지 함정이 있어요.

- 안 읽은 알림이 기간이 지나 지워지면 칸 값도 같이 줄어야 해요. 정리 작업이 카운터를 함께 맞추거나, 정리 뒤에 재계산해야 해요.
- 기간을 넘긴 알림을 읽음으로 칠지, 그냥 지울지 정책으로 정해야 해요. 정책이 없으면 목록과 배지가 서로 다른 기준을 쓰게 돼요.

## 알림 설정 — 채널과 종류별 끄기

알림 설정은 보내는 단계와 저장하는 단계에서 다르게 적용돼요. 푸시를 꺼도 알림함에는 남기는 방식이 흔해요. 설정을 저장 단계에서 확인하면 나중에 다시 켰을 때 과거 알림이 없어요. 전송 단계에서만 확인하면 알림함에는 그대로 남아요. 이 판단은 서비스 정책이에요. 푸시 채널 자체의 전송 방식은 [푸시 알림](/m/push-notifications) 글에서 이어 봐요.

## 시뮬레이터 안내

아래 시뮬레이터에서 다음 순서로 눌러 보세요.

1. 읽음 방식을 행마다 read_at으로 두고, 모두 읽음을 눌러요. 갱신 행 수가 안 읽은 수와 같아요.
2. 읽음 방식을 읽음 커서로 바꾸고, 맨 위 알림을 여러 번 읽은 뒤 모두 읽음을 눌러요. 예외 행이 쌓였다가 커서가 따라잡는 과정을 볼 수 있어요.
3. 개수 방식을 카운터 칸 하나로 바꾸고 차감 규칙을 무조건 -1로 둔 뒤, 두 탭 동시 읽기를 눌러요. 배지와 실제의 차이가 생겨요.
4. 카운터 다시 세기를 눌러 차이가 0이 되는 것을 확인해요.

## FE 체크 포인트

**배지는 서버가 준 숫자로 그려요.** 알림을 누르면 로컬에서 숫자를 먼저 줄여도 되지만, 응답이 오면 서버 숫자로 덮어써요. 응답 전에 받은 다른 변화가 있으면 로컬 계산은 틀려요.

**모두 읽음은 실패할 수 있다고 보고 되돌릴 수 있게 해요.** 목록과 배지를 먼저 바꾸고, 실패 응답이 오면 이전 상태로 되돌려요. 되돌릴 때는 한 줄로 알려 주세요.

**목록을 여는 것과 알림을 읽는 것을 구분해요.** 알림함을 여는 것만으로 모든 알림을 읽음으로 바꾸면 사용자가 보지 못한 알림이 사라져요. 읽음은 항목을 누르거나 "모두 읽음"을 눌렀을 때만 보내요.

**탭이 다시 보일 때 배지를 한 번 받아요.** 숨겨진 탭은 신호를 놓칠 수 있어요. 보이는 순간 조회 한 번으로 맞추면 충분해요.

**두 탭의 숫자가 잠깐 다른 것은 정상이에요.** 다른 기기와 탭의 배지는 다음 조회나 신호가 올 때 맞춰져요.

## 정리 — 읽음은 행마다 두거나 커서로 두고, 개수는 칸과 재계산으로 맞추기

읽음을 행마다 기록하면 구현이 단순하지만 모두 읽음이 행 수에 비례해요. 커서로 기록하면 모두 읽음이 빠르지만 가운데 알림을 읽는 예외 행을 관리해야 해요. 개수는 매번 세면 어긋나지 않지만 비용이 들고, 칸에 두면 빠르지만 차감 규칙과 재계산이 필요해요. 여기에 탭 사이 동기화와 보관 기간 정리를 더하면 배지 하나에도 여러 결정이 붙어요.
