글을 저장하고 목록으로 돌아왔어요. 그런데 방금 쓴 글이 없어요. 새로고침하면 보여요. 이 현상은 대부분 읽기 복제본이 주 DB를 아직 따라오지 못해서 생겨요. 이 글은 그 간격을 다뤄요. 아래 시뮬레이터에서 같은 상황을 직접 돌려 볼 수 있어요. 시뮬레이터의 수치는 예시예요.

## 주 DB와 읽기 복제본 — 쓰기는 한 곳, 읽기는 여러 곳

쓰기는 주 DB가 받아요. 읽기 요청이 많아지면 복제본을 늘려 나눠 읽게 해요. PostgreSQL 복제본은 읽기 전용 질의에 쓸 수 있어요. 이런 복제본을 hot standby라고 불러요.

복제본은 주 DB의 변경을 따라가며 적용해요. 그래서 주 DB에서 커밋된 글이 복제본에 보이는 데 시간이 걸려요.

| 시점 (예시) | 주 DB          | 복제본 A     | 목록 요청의 결과            |
| ----------- | -------------- | ------------ | --------------------------- |
| 0ms         | 글 커밋        | 아직 모름    | 요청 없음                   |
| 300ms       | 커밋 상태 유지 | 아직 모름    | 복제본 A에서 읽기 → 글 없음 |
| 900ms       | 커밋 상태 유지 | 글 적용 완료 | 복제본 A에서 읽기 → 글 있음 |

## 복제 지연 — 커밋과 복제본 반영 사이의 간격

PostgreSQL 문서는 비동기 복제를 이렇게 설명해요. 주 DB의 변경이 복제본에 아직 안 보이는 짧은 구간이 항상 있고, 앱이 주 DB에 쓴 뒤 바로 복제본에서 읽으면 불일치가 생길 수 있어요.

복제본이 커밋 기록을 재생하면 그 변경은 복제본의 새 스냅샷에 보여요. 그 전까지는 옛 값이 보여요.

지연을 확인하는 뷰도 있어요. `pg_stat_replication`의 `replay_lag`은 비동기 복제본에서 최근 트랜잭션이 쿼리에 보이기까지의 지연을 대략 보여 줘요.

복제 지연은 고정된 값이 아니에요. 복제본마다 속도가 다르고, 쓰기가 몰리면 늘어나요. 이 글의 시뮬레이터는 쓰기가 순서대로 적용된다고 가정해요. 앞 쓰기가 늦으면 뒤 쓰기도 그 뒤에서 기다려요.

## 동기 복제 — 커밋이 복제본을 기다리는 비용

지연을 없애는 가장 직접적인 방법은 커밋이 복제본을 기다리게 하는 거예요. PostgreSQL 에서는 `synchronous_commit`으로 정해요. 기본값은 `on`이에요. 값은 `remote_apply`, `on`, `remote_write`, `local`, `off`가 있어요.

`remote_apply`는 커밋이 현재 동기 복제본들의 응답을 기다리게 해요. 복제본이 커밋 기록을 받아 적용하고 쿼리에 보이게 된 것까지 확인해요. 문서는 이때 커밋 지연이 훨씬 커진다고 설명해요.

| 설정              | 커밋이 기다리는 것                        | 비용                                     |
| ----------------- | ----------------------------------------- | ---------------------------------------- |
| `on` (기본값)     | 동기 복제본을 지정했으면 그 응답          | 지정한 복제본이 느리면 커밋도 느려요     |
| `remote_apply`    | 동기 복제본이 적용해서 쿼리에 보일 때까지 | 가장 큰 커밋 지연이에요                  |
| `off`, `local` 등 | 복제본을 기다리지 않아요                  | 복제본 반영 전 읽기는 여전히 옛 값이에요 |

`synchronous_standby_names`가 비어 있으면 동기 복제본이 없으니 `on`도 복제본을 기다리지 않아요. `remote_apply`도 로컬 수준에서는 `on`과 같아요. 기본 설정만으로는 커밋이 복제본을 기다리지 않는다는 뜻이에요.

설정은 트랜잭션마다 커밋 시점의 값이 적용돼요. 그래서 중요한 쓰기만 동기로 바꿀 수 있어요.

동기 복제는 모든 쓰기에 대기를 더해요. 그래서 "쓰기 전부를 `remote_apply` 로" 대신 "자기 쓰기를 읽어야 하는 경로만 따로 보장" 하는 방법을 많이 써요. 아래 방식들이 그 방법이에요.

## 자기 쓰기 읽기 — 다섯 가지 방식 비교

read-your-writes는 사용자가 방금 쓴 값을 자기 요청에서 다시 읽을 수 있어야 한다는 요구예요. 방식마다 막는 것과 치르는 것이 달라요.

| 방식                 | 무엇을 하나                                                     | 잘 막는 것          | 치르는 것                                                  |
| -------------------- | --------------------------------------------------------------- | ------------------- | ---------------------------------------------------------- |
| 무작위 복제본        | 읽기마다 복제본을 골라요                                        | 주 DB 부하          | 첫 화면 미노출, 새로고침 때 뒤로 감                        |
| 세션마다 복제본 고정 | 한 사용자의 읽기는 같은 복제본으로 가요                         | 새로고침 때 뒤로 감 | 첫 화면 미노출은 그대로, 그 복제본이 늦으면 계속 안 보여요 |
| 쓴 뒤 N초 주 DB 읽기 | 쓴 직후 N초 동안은 주 DB에서 읽어요                             | 쓴 직후 미노출      | 주 DB 읽기 증가, N초보다 긴 지연은 못 막아요               |
| 쓴 위치(LSN) 확인    | 쓴 위치까지 따라온 복제본만 골라 읽어요                         | 미노출, 뒤로 감     | 위치 전달과 확인 비용, 아무도 못 따라오면 주 DB            |
| 응답 글 직접 넣기    | 쓰기 응답의 글을 목록에 넣고 서버 목록에 나타날 때까지 유지해요 | 첫 화면 미노출      | 새로고침하면 화면 상태가 사라져요                          |

## 쓴 위치 확인 — LSN으로 복제본 골라 읽기

PostgreSQL 문서는 자기 쓰기 읽기 방법을 직접 설명해요. 커밋이 끝나면 주 DB의 현재 위치를 받아요. 함수는 `pg_current_wal_insert_lsn()`이에요. 이 위치를 복제본에 전달하고, 복제본에서 그 위치까지 재생될 때까지 기다려요. 문서는 이 전달을 앱에서 하거나 커넥션 풀러에서 하도록 설명해요.

PostgreSQL 19 문서의 `WAIT FOR LSN` 명령은 기다리는 일을 서버에서 해요.

```sql
-- 주 DB: 커밋 직후 위치를 받아요
SELECT pg_current_wal_insert_lsn();   -- 예: 0/306EE20

-- 복제본: 그 위치까지 재생될 때까지 기다려요
WAIT FOR LSN '0/306EE20' WITH (TIMEOUT '0.5s', NO_THROW);
-- 결과가 success 면 그 위치까지의 변경이 적용됐어요. 이후 읽기는 그 글을 봐요.
```

`WAIT FOR`의 기본 모드는 `standby_replay`예요. 시간 안에 도달하지 못하면 오류가 나요. `NO_THROW`를 주면 `timeout` 같은 상태 문자열로 받아요. 문서는 복제본이 승격되면 대기 중인 명령이 오류가 될 수 있다고 설명해요. 그래서 실패 경로를 미리 정해야 해요.

복제본의 재생 위치는 `pg_last_wal_replay_lsn()` 으로도 읽을 수 있어요. 이 값이 쓴 위치보다 크거나 같으면 그 글은 복제본에 보여요. 복제본에서 복구가 진행 중이면 이 값은 단조 증가해요.

이 방식은 복제본을 항상 쓰면서 자기 쓰기는 보장해요. 대신 위치를 어디에 보관할지 정해야 해요. 응답 헤더, 쿠키, 세션 저장소 중 하나에 두고 다음 읽기 요청에 실어 보내요. 위치를 가진 요청만 확인하고, 확인되지 않으면 주 DB로 보내요.

## 단조 읽기 — 새로고침마다 값이 뒤로 가는 문제

새로고침할 때마다 다른 복제본에 가면 값이 앞뒤로 흔들려요. 어떤 때는 글이 보이고, 다음 새로고침에서는 없어요. 한 복제본에서 본 값을 다른 복제본에서 옛 값으로 되돌려 보는 문제예요.

한 복제본은 재생 위치가 뒤로 가지 않아요. 그래서 한 사용자를 같은 복제본에 고정하면 그 사용자가 보는 값은 뒤로 가지 않아요. 다만 그 복제본이 늦으면 첫 화면은 여전히 안 보여요. 복제본이 바뀌거나 장애가 나면 고정이 깨져요. 시뮬레이터의 "세션마다 복제본 고정"이 이 방식이에요.

## FE가 할 일 — 응답 반영 · 낙관적 갱신 · 목록 무효화 시점

FE에서 가장 흔한 실수는 쓰기가 끝난 직후 목록을 무효화하고 다시 받는 거예요. 재조회는 복제본으로 갈 수 있어요. 그러면 방금 쓴 글이 다시 빠져요. 무효화는 쓰기 응답을 목록에 반영한 뒤에 하고, 서버 목록에 그 글이 나타날 때까지 임시 항목을 남겨 두세요.

```ts
function mergeList(serverRows: Post[], pending: Post[]): Post[] {
  const seen = new Set(serverRows.map((row) => row.id));
  // 서버 목록에 아직 없는 방금 쓴 글만 앞에 남겨요.
  return [...pending.filter((post) => !seen.has(post.id)), ...serverRows];
}
```

- 쓰기 응답의 본문으로 화면 상태를 바꿔요. 새로 만든 리소스는 201 Created로 응답하고, 그 리소스를 Location 헤더로 가리킬 수 있어요 (RFC 9110).
- 낙관적 갱신은 응답을 기다리기 전에 임시 id로 목록 맨 앞에 넣어요. 실패하면 되돌려요. 성공하면 서버 id로 바꿔 끼워요.
- 목록을 무효화해도 결과가 복제본에서 오면 pending 항목이 유지돼요. 이 규칙이 없으면 목록이 한 번 깜빡이며 글이 사라져요.
- 새로고침은 메모리의 pending 항목을 버려요. 그래서 새로고침 뒤에도 보장하려면 서버 쪽 신호가 필요해요. 예를 들어 쓴 위치를 쿠키에 두고 목록 요청에 실어 보내는 방식이 있어요. 이건 설계 예시이고 표준 규칙은 아니에요.

## 캐시와 겹칠 때 — 복제본에서 읽은 값을 캐시에 넣는 문제

목록을 캐시하면 복제본에서 읽은 옛 값이 캐시에 들어갈 수 있어요. 쓰기 뒤 캐시를 지워도 옛 값이 다시 저장되는 경쟁은 [캐시와 캐시 스탬피드](/m/cache-stampede)에서 다뤘어요. 복제 지연이 더해지면 이 경쟁은 더 길어져요. 쓰기 직후 캐시를 채울 때는 주 DB에서 읽거나, 쓴 위치를 확인한 값만 넣는 편이 안전해요. 이건 이 글의 설계 판단이에요.

## 시뮬레이터 안내 — 방식별 미노출 · 뒤로 간 횟수 · 주 DB 부하

시뮬레이터는 쓰기 400건을 초당 몇 건씩 넣고, 세션마다 저장 뒤 목록으로 돌아와 새로고침을 여섯 번 해요. 복제본마다 속도가 다르고, 가끔 지연이 튀어요. 같은 시드면 같은 순서로 돌아요.

- **첫 목록에서 안 보임** — 저장 뒤 목록을 처음 열었을 때 방금 쓴 글이 없었던 세션의 비율이에요.
- **새로고침 때 뒤로 간 횟수** — 보였던 글이 다음 새로고침에서 사라진 횟수예요.
- **주 DB 읽기 비율** — 전체 읽기 중 주 DB로 간 몫이에요. 쓰기 대비 주 DB 읽기 (초당)와 함께 보세요.

이렇게 돌려 보세요.

1. 기본 설정에서 "무작위 복제본"은 첫 목록에서 글이 빠져요. "세션마다 복제본 고정"으로 바꾸면 뒤로 가는 횟수는 0이 되지만 첫 목록 미노출은 그대로예요.
2. 복제 평균 지연을 1500ms로 올리고 복제본을 5개로 두세요. "응답 글 직접 넣기"는 첫 목록을 지키지만 새로고침 횟수가 늘어요.
3. "쓴 뒤 N초 주 DB"는 주 DB 읽기 비율이 높아요. "쓴 위치 확인"은 따라온 복제본만 골라서 주 DB 읽기가 훨씬 적어요.

## 정리 — 최신 값을 아는 곳을 기억하기

복제 지연은 피할 수 없는 간격이에요. 그래서 질문은 "언제 최신 값을 읽어야 하나"가 돼요. 쓴 직후 읽기는 주 DB나 쓴 위치로 보장하고, 같은 사용자의 읽기는 한 복제본에 고정해 값이 뒤로 가지 않게 해요. FE는 쓰기 응답을 목록에 반영하고, 서버 목록에 글이 나타날 때까지 임시 항목을 유지해요.

재고와 결제처럼 맞아야 하는 값은 이 글의 방식보다 더 엄격한 경로를 써야 해요. 쓰기 충돌은 [트랜잭션 · 락 · 데드락](/m/transactions)에서, 어디에서 계산할지는 [서버 · 클라 처리 판단](/m/server-or-client)에서 이어서 볼 수 있어요.
