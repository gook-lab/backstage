웹 프론트엔드(FE)는 배포하면 보통 새로고침이나 다음 방문 때 새 코드를 받아요. 앱은 달라요. 설치된 앱은 사용자가 업데이트를 받아야 새 코드가 들어가요. 스토어 심사가 끝나도 업데이트를 미루는 기기가 남아요. 그래서 백엔드(BE)가 API를 바꿔도 옛 앱은 같은 서버에 한동안 계속 붙어요.

이 글은 옛 앱을 어떻게 살려 두고, 언제 끄고, 끄기 전에 무엇을 알릴지 따라가요. 호환 판단 표와 배포 순서는 [API 계약 사례](/m/api-contracts)와 [스키마 마이그레이션 사례](/m/schema-migration)에서 이미 다뤘어요. 여기서는 버전 표시, 폐기 일정, 강제 업데이트를 다뤄요.

## 증상 — 웹과 달리 앱에 남는 옛 버전

BE가 응답의 `name` 칸을 `displayName`으로 바꿨다고 해요 (예시). 웹은 새 코드를 받아서 금방 맞춰져요. 앱은 옛 코드를 그대로 돌려요. 옛 앱은 `name`을 찾다가 값이 없어서 화면에 빈 이름이 남아요.

BE 입장에서는 같은 URL에 새 앱, 옛 앱, 웹이 함께 붙어요. 한 응답 모양으로 세 클라이언트를 모두 맞추기 어려워요. 그래서 버전을 나누는 방법이 필요해요.

## 버전 표시 위치 — 경로 · 헤더 · 쿼리 · 미디어 타입 비교

버전은 요청의 네 군데에 실을 수 있어요. 어느 쪽이든 서버는 버전마다 응답을 다르게 만들어요. 차이는 버전이 눈에 보이는 곳과 캐시가 버전을 구분하는 방법이에요.

| 위치        | 예                     | 장점                                                                        | 주의                                                   |
| ----------- | ---------------------- | --------------------------------------------------------------------------- | ------------------------------------------------------ |
| URL 경로    | `/v1/orders`           | 주소창, 로그, 네트워크 탭에 버전이 보여요. 경로별로 요청 수를 셀 수 있어요. | 버전마다 라우트가 복제돼요.                            |
| 헤더        | `Stripe-Version`       | URL이 같아서 링크가 바뀌지 않아요.                                          | 응답이 헤더에 따라 달라서 캐시가 헤더를 구분해야 해요. |
| 쿼리        | `api-version` 파라미터 | 경로를 건드리지 않고 버전을 붙여요.                                         | 빠진 요청을 서버가 거절하도록 정해 둬야 해요.          |
| 미디어 타입 | `Accept` 헤더          | 응답 형식과 버전을 함께 골라요.                                             | 캐시가 `Accept`를 구분해야 해요.                       |

출처가 정한 내용은 이래요.

- Google AIP-185는 REST API의 major 버전 번호를 URI 경로 첫 부분에 두라고 정해요.
- Stripe 문서는 계정마다 기본 API 버전을 두고, 요청의 `Stripe-Version` 헤더로 그 기본값을 덮어쓴다고 설명해요.
- Microsoft Azure REST API 지침은 `api-version`이 빠진 요청에 `MissingApiVersionParameter` 오류와 400 응답을 돌려주라고 정해요.
- RFC 9110은 `Accept`를 응답 미디어 타입에 대한 선호를 나타내는 헤더로 정의해요. `Vary`는 응답을 고르는 데 영향을 준 요청 헤더를 나열한다고 정해요.

경로 버전은 측정하기 쉬워요. 경로마다 요청 수를 세면 옛 버전이 얼마나 남았는지 바로 보여요. 헤더 버전은 서버가 계정이나 클라이언트마다 기본값을 관리하는 운영에 맞아요. 앱처럼 옛 버전을 오래 유지하는 API에서는 경로 버전이 판단하기 쉬운 편이에요.

## 하위 호환 변경 — 버전을 올리지 않는 경우

버전을 한 벌 더 만들면 옛 버전 코드도 한 벌 더 관리해야 해요. 그래서 옛 클라이언트가 무시할 수 있는 변경은 같은 버전에서 처리하는 편이 좋아요. 응답 칸 추가와 새 엔드포인트가 여기에 들어가요.

깨지는 변경만 새 버전으로 보내요. 칸 이름 변경, 칸 삭제, 타입 변경이 여기에 들어가요. 칸 추가가 안전하다는 판단은 클라이언트가 모르는 칸을 무시한다는 가정이 있을 때만 맞아요. 이 가정과 변경별 표는 [API 계약 사례](/m/api-contracts)에서 다뤄요.

Google AIP-185는 major 버전을 URI 경로에 두고, 호환되지 않는 변경은 AIP-180과 AIP-181의 절차를 따르라고 안내해요.

## Deprecation · Sunset 헤더 — 알림과 차단을 나누기

헤더는 옛 버전을 알리는 신호예요. 차단 장치가 아니에요. 헤더 값의 형식은 [스키마 마이그레이션 사례](/m/schema-migration)에서 다뤘어요. 여기서는 두 헤더가 폐기 정책에서 맡는 역할만 봐요.

| 헤더                   | 알리는 내용                                         | 값                                                | 응답 동작     |
| ---------------------- | --------------------------------------------------- | ------------------------------------------------- | ------------- |
| Deprecation (RFC 9745) | 리소스가 폐기됐거나 폐기될 예정이에요               | 유닉스 시각 앞에 `@`를 붙여요 (예: `@1688169599`) | 바뀌지 않아요 |
| Sunset (RFC 8594)      | 이 URI가 특정 시각 뒤에 응답하지 않을 가능성이 커요 | HTTP-date                                         | 바뀌지 않아요 |

- RFC 9745는 폐기 표시가 리소스의 동작을 바꾸지 않는다고 정해요. 클라이언트는 이 값을 힌트로 받아야 해요.
- RFC 9745는 Sunset 시각이 Deprecation 시각보다 빠르면 안 된다고 정해요.
- Microsoft Azure REST API 지침은 승인된 호환 깨짐을 `azure-deprecating` 응답 헤더로 알리라고 정해요. 이 헤더는 사람이 읽는 정보라서, 클라이언트 코드가 파싱하지 않는다고 설명해요.

헤더만 붙이면 옛 앱은 그대로 살아요. 헤더는 알림이고, 차단은 사용량을 본 뒤 날짜로 정하는 결정이에요.

## 폐기 일정 — 공지 · 사용량 측정 · 차단 순서

폐기는 네 단계로 나눠요.

1. 공지: 옛 버전 응답에 Deprecation 헤더를 붙이고, 문서에 대체 버전과 날짜를 적어요.
2. 측정: 옛 버전 요청 수를 클라이언트 종류별로 세요. 앱 버전을 요청에 실어 보내야 셀 수 있어요. 헤더 이름은 팀이 정해요 (예: `X-App-Version`).
3. 날짜 확정: 옛 버전 비율이 충분히 줄었을 때 Sunset 날짜를 정해요. 날짜는 헤더로 미리 알려요.
4. 차단: 날짜가 지나면 옛 버전 요청에 410 Gone을 돌려줘요. RFC 9110은 410을 대상 리소스에 더는 접근할 수 없고, 그 상태가 영구적일 가능성이 크다는 뜻으로 정의해요.

측정 없이 날짜를 정하면 아직 옛 버전을 쓰는 사용자가 갑자기 차단돼요. 측정한 비율을 보고 날짜를 미루거나 당기는 편이 좋아요.

## 최소 지원 버전 — 강제 업데이트 응답 설계

옛 앱을 업데이트 화면으로 보내는 길은 두 가지예요.

- 시작 설정: 앱이 켜질 때 최소 지원 버전을 받아요. 현재 버전이 낮으면 업데이트 화면과 스토어 링크를 띄워요. 이 방식은 설계 예시예요.
- 차단 응답: 최소 버전보다 낮은 요청은 문제 형식(problem+json) 본문으로 거절해요. 본문 형식은 [API 에러 사례](/m/api-errors)를 따라요.

앱을 열지 않은 기기는 시작 설정을 받지 못해요. 그 기기는 요청을 보내는 순간에만 차단 응답을 받아요. 그래서 강제 업데이트만으로는 옛 기기를 다 막을 수 없어요. 차단 날짜는 여전히 필요해요.

RFC 9110은 426 Upgrade Required를 프로토콜을 바꿔야 한다는 뜻으로 정의해요. 서버는 필요한 프로토콜을 Upgrade 헤더로 알려야 해요. 앱 버전 차단에 426을 그대로 쓰면 의미가 어긋나요. 앱 버전 차단은 상태 코드보다 문제 형식의 `type`으로 구분하는 편이 좋아요. 화면은 `type`을 보고 업데이트 화면을 골라요.

## 배포 속도 차이 — 웹 FE와 모바일 앱

같은 BE 정책도 두 클라이언트에서 다르게 끝나요.

| 구분      | 새 코드가 닿는 방식              | 옛 버전이 남는 기간                      |
| --------- | -------------------------------- | ---------------------------------------- |
| 웹 FE     | 새로고침이나 다음 방문           | 짧아요. 열어 둔 탭만 옛 코드를 써요.     |
| 모바일 앱 | 스토어 심사 뒤 사용자가 업데이트 | 길어요. 업데이트를 미루는 기기가 남아요. |

웹 FE는 옛 응답 처리 코드를 빨리 지울 수 있어요. 앱은 폐기 날짜까지 옛 응답 처리 코드를 남겨 둬요. 같은 정책을 두 속도에 맞춰 설계해야 해요.

## FE 체크 포인트

- 요청에 앱 버전을 실어 보내요. 측정이 없으면 폐기 날짜를 정할 수 없어요.
- 최소 지원 버전은 앱 시작 때 받고, 업데이트 화면은 한 곳에서 띄워요.
- 차단 응답은 빈 화면이 아니라 업데이트 안내로 받아요. 오류 파서 한 곳을 거쳐요.
- Deprecation과 Sunset 헤더는 사용자 화면에 쓰지 않아요. 개발 점검과 모니터링 신호로 봐요.
- 모르는 응답 칸은 무시해요. 칸 추가가 안전하려면 이 규칙이 필요해요. [API 계약 사례](/m/api-contracts)의 경계 파싱을 따라요.

## 시뮬레이터 안내

아래 시뮬레이터는 폐기 정책 네 가지 중 하나를 고르고, 날짜를 움직여 봐요. 플랫폼 비율, 업데이트가 끝나는 날, 업데이트하지 않는 비율은 모두 예시예요. 같은 정책에서도 웹과 앱의 결과가 다르다는 점을 보세요. 강제 업데이트를 고른 뒤 차단 날짜까지 움직이면, 앱을 열지 않은 기기가 어떻게 남는지 보여요.

## 정리 — 버전 위치 · 호환 기준 · 폐기 일정 · 최소 버전

버전은 측정하기 쉬운 위치에 두고, 옛 클라이언트가 무시할 수 있는 변경은 버전을 올리지 않아요. Deprecation과 Sunset은 알림이고, 차단은 사용량을 본 뒤 날짜로 정해요. 강제 업데이트는 최소 지원 버전 응답으로 하고, 앱을 열지 않는 기기는 차단 날짜에 막혀요.
