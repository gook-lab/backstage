게시글 삭제 버튼을 누르면 화면에서 글이 사라지고, 응답은 204 No Content로 끝나요. 그런데 서버 안에서 그 행이 정말 지워졌는지는 삭제 방식에 따라 달라요. 이 글은 행을 지우는 방식과 남기는 방식을 비교하고, 소프트 삭제가 조회 전체에 남기는 부담, 같은 이메일 재가입, 외래 키 연쇄 삭제, 복구 기간 뒤 영구 삭제, 탈퇴 시 개인정보 처리를 차례로 봐요. 예시 데이터는 모두 가짜예요.

## 증상 — 화면에서 사라진 글이 DB에 남는 경로

FE가 보는 결과는 단순해요. 삭제 버튼을 누르면 목록에서 글이 빠지고, 응답은 204예요. 다시 목록을 열어도 글이 없어요. 그런데 복구 요청이 오거나 같은 이메일로 다시 가입하려고 하면 이 "없음"이 맞지 않아요. 지운 글을 되돌려 달라는 요청이 들어오고, 탈퇴한 이메일은 쓸 수 없다는 응답이 나와요.

원인은 "지웠다"는 말이 두 가지 뜻을 가진다는 점이에요. 행을 실제로 없애는 하드 삭제가 있고, 행에 삭제 시각만 남기는 소프트 삭제가 있어요. 화면은 둘 다 같은 204로 보여 줘요. 그래서 BE가 어느 방식을 골랐는지 모르면 복구와 재가입 요청에 답할 수 없어요.

## 하드 삭제와 소프트 삭제 — 행을 지우는 자리와 남기는 자리

| 항목      | 하드 삭제                                   | 소프트 삭제 (`deleted_at`)                       |
| --------- | ------------------------------------------- | ------------------------------------------------ |
| 행        | 지워요                                      | 남고, `deleted_at`에 삭제 시각이 들어가요        |
| 복구      | 행이 없어서 되돌릴 수 없어요                | `deleted_at`을 비우면 같은 행이 돌아와요         |
| 조회      | 행이 없으니 기본으로 빠져요                 | 모든 조회에 `deleted_at IS NULL` 조건이 필요해요 |
| 유일 제약 | 지운 행이 없어서 같은 값을 쓸 수 있어요     | 일반 UNIQUE는 지운 행도 세요                     |
| 개인정보  | 행과 함께 사라져요(백업 · 로그 사본은 따로) | 행이 남아서 따로 지워야 해요                     |

RFC 9110은 DELETE가 대상 리소스와 원서버의 연결을 지우는 요청이라고 설명해요. 저장 공간을 회수할지, 연결 설비를 비활성화하거나 보관할지는 구현에 달렸다고 해요. 그래서 행을 남기는 소프트 삭제도 DELETE를 구현하는 선택지 중 하나예요. 복구 요구가 있으면 소프트 삭제가 맞고, 복구 기간이 끝난 뒤에는 실제로 지우는 절차를 함께 둬야 해요. 이 두 가지가 이 글의 기본 판단이에요.

## 조회 조건 누락 — 모든 쿼리에 deleted_at 조건을 강요하는 문제

소프트 삭제 행은 테이블에 계속 남아 있어서, 목록, 상세, 검색, 집계, 관리자 화면이 모두 조건을 알고 있어야 해요. 한 쿼리라도 조건을 빠뜨리면 지운 글이 보여요. FE에서는 "지운 글이 또 나와요"로 보이지만 원인은 BE 쿼리 하나인 경우가 많아요.

### 뷰로 조건 모으기

PostgreSQL 문서는 뷰가 물리적으로 저장되지 않고, 뷰를 참조할 때마다 질의가 실행된다고 설명해요. 그래서 살아 있는 행만 보이는 뷰를 `WHERE deleted_at IS NULL`로 한 번 정의해 두면, 조회 코드는 뷰만 읽으면 돼요. 조건이 정의 한 곳에 있으니 빠뜨릴 자리가 줄어요.

뷰도 완전하지 않아요. 뷰를 거치지 않고 테이블을 직접 읽는 코드가 있으면 여전히 지운 행이 나와요. 테이블 직접 접근 권한을 어디까지 줄지는 설계 판단이에요.

### 부분 인덱스의 한계 — 조건 누락은 막지 못함

부분 인덱스는 술어를 만족하는 행만 담는 인덱스예요. PostgreSQL 문서는 쿼리가 부분 인덱스를 쓰려면 쿼리의 WHERE 조건이 인덱스의 술어를 논리적으로 함의해야 한다고 설명해요. 그래서 `WHERE deleted_at IS NULL` 인덱스는 살아 있는 행을 찾는 쿼리를 빠르게 해 줘요.

하지만 조건을 빠뜨린 쿼리는 막지 못해요. 조건이 없으면 DB는 이 인덱스를 쓸 수 없고, 결과에는 지운 행이 그대로 들어가요. 같은 문서는 수식 모양이 달라도 같은 뜻인지 알아내는 증명기가 없다고도 설명해요. 그래서 조건을 다른 식으로 쓰면 인덱스를 못 쓸 수 있어요. 부분 인덱스는 속도 장치이지, 조건을 강요하는 장치가 아니에요.

| 방법               | 막는 것               | 못 막는 것                     |
| ------------------ | --------------------- | ------------------------------ |
| 쿼리마다 조건 반복 | 조건을 쓴 쿼리의 누출 | 조건을 빠뜨린 쿼리의 누출      |
| 살아 있는 행 뷰    | 뷰를 거친 조회의 누출 | 뷰를 우회해 테이블을 읽는 코드 |
| 부분 인덱스        | 조건 쿼리의 느린 조회 | 조건 누락 자체                 |

## 부분 유일 인덱스 — 살아 있는 행끼리만 같은 값을 막기

탈퇴한 회원의 행이 남아 있으면 `UNIQUE(email)`은 같은 이메일을 계속 막아요. 삭제된 행도 유일성 검사에 들어가기 때문이에요. PostgreSQL 문서는 부분 유일 인덱스가 술어를 만족하는 행 사이에서만 유일성을 강제하고, 그 밖의 행은 제약하지 않는다고 설명해요. 예시 코드는 다음과 같아요.

```sql
-- 예시: 살아 있는 회원끼리만 이메일이 겹치지 않아요
CREATE UNIQUE INDEX members_email_alive
  ON members (email)
  WHERE deleted_at IS NULL;
```

이 인덱스를 만들면 탈퇴한 옛 행과 새 가입자가 같은 이메일을 가질 수 있어요. 재가입은 열리지만, 옛 행이 계속 남는다는 점은 그대로예요. 탈퇴 회원을 복구하는 기능을 같이 열면, 복구 시점에 같은 이메일이 살아 있는지 확인해야 해요. 이때는 복구를 거절하거나 이메일을 바꾸도록 안내하는 편이 좋아요. 이 선택은 설계 판단이에요.

주의할 점이 하나 있어요. PostgreSQL 문서는 외래 키가 참조하는 열이 기본 키이거나 유일 제약이거나, 부분이 아닌 유일 인덱스의 열이어야 한다고 설명해요. 부분 유일 인덱스는 외래 키의 참조 대상이 될 수 없어요. 그래서 댓글이 회원을 가리킬 때는 이메일이 아니라 기본 키 `id`를 참조하게 해요.

## 외래 키와 연쇄 삭제 — ON DELETE 동작 고르기

PostgreSQL 문서는 기본 동작이 NO ACTION이라고 설명해요. CASCADE는 참조되는 행이 지워질 때 참조하는 행도 자동으로 지운다고 해요. RESTRICT는 참조되는 행의 삭제를 막고, SET NULL은 참조 열을 NULL로 바꿔요.

고를 때 기준은 두 행이 독립적인지예요. 문서는 참조하는 행이 상위 행의 구성 요소여서 독립적으로 존재할 수 없다면 CASCADE가 맞을 수 있다고 설명해요. 독립된 객체라면 RESTRICT나 NO ACTION이 맞고, 두 행을 모두 지우려면 애플리케이션이 명시적으로 두 번 지우라고 해요. 문서의 예시도 주문 항목은 주문의 일부라서 CASCADE가 편하지만, 상품과 주문은 서로 다른 것이라 상품 삭제가 주문 항목을 지우면 곤란하다고 말해요.

소프트 삭제와 연결하면 중요한 점이 하나 있어요. ON DELETE 동작은 참조되는 행이 실제로 지워질 때 실행돼요. `deleted_at`을 채우는 것은 UPDATE이고, 참조되는 열이 바뀌지 않으니 댓글에 아무 일도 일어나지 않아요. 그래서 소프트 삭제 글의 댓글은 그대로 남아요. 댓글 목록은 부모 글의 `deleted_at`을 따로 확인해야 해요.

## 복구 기간과 영구 삭제 배치 — 기간이 지난 행 지우기

소프트 삭제만 하면 행은 영원히 쌓여요. 그래서 복구 기간을 정하고, 기간이 지난 행을 실제로 지우는 배치를 둬요. 시뮬레이터와 예시에서는 30일을 써요. 이 숫자는 예시이고, 실제 기간은 서비스 정책과 법에 따라 정해요.

배치의 순서는 설계 판단이에요. 댓글처럼 자식 행을 먼저 지우고 글을 나중에 지워야 RESTRICT 제약에 걸리지 않아요. 배치는 중간에 끊겨도 다시 돌렸을 때 같은 상태가 되도록 짜는 편이 좋아요. 배치 운영 방법은 [배치 작업 글](/m/batch-jobs)에서 이어 봐요.

```sql
-- 예시: 기간이 지난 글의 댓글을 먼저 지우고, 그다음 글을 지워요
BEGIN;
DELETE FROM comments
WHERE post_id IN (
  SELECT id FROM posts
  WHERE deleted_at < now() - interval '30 days'
);
DELETE FROM posts
WHERE deleted_at < now() - interval '30 days';
COMMIT;
```

두 문장을 한 트랜잭션에 넣으면 `now()`가 같은 값이라 두 문장이 같은 기준 시각으로 대상을 골라요. 따로 실행하면 그 사이에 기준을 넘은 글이 생겨, 댓글은 남았는데 글을 지우려다 제약에 걸릴 수 있어요.

복구 기간 안에 복구된 글은 `deleted_at`이 비워지므로 배치 대상에서 빠져요. 기간이 끝난 뒤의 복구 요청에는 404나 410으로 답하는 편이 맞아요. 영구 삭제가 끝났다는 것을 서버가 알고 있다면 RFC 9110은 404보다 410을 선호한다고 설명해요.

## 탈퇴 — 개인정보 파기 · 익명화와 남길 기록

탈퇴는 글 삭제보다 범위가 넓어요. 이메일, 이름, 전화번호 같은 개인 식별 값은 지우거나 바꿔야 해요. 글과 댓글은 남길지 지울지를 따로 정해야 하고, 거래나 감사 기록은 다른 기준으로 보관해요.

GDPR 제17조 1항은 개인정보가 더 이상 필요하지 않거나 동의가 철회되는 등 정해진 경우에 지체 없이 지울 의무를 정해요. 같은 조 3항은 처리가 EU나 회원국 법이 요구하는 법적 의무를 지키기 위해 필요하면 1항과 2항이 적용되지 않는다고 설명해요. 법이 요구하는 보관 기간은 나라와 기록 종류마다 달라서, 이 글은 구체 기간을 쓰지 않아요.

설계 판단으로 나누면 세 갈래예요. 첫째, 식별 값은 파기하거나 익명화해요. 둘째, 작성한 글과 댓글은 작성자를 "탈퇴한 회원"으로 표시하고 남길지, 함께 지울지 정해요. 셋째, 감사 이력은 행위자 id를 가명으로 바꾸는 식으로 따로 보관해요. 이력 쪽은 [감사 로그 글](/m/audit-history)에서, 값을 가리는 방법은 [민감 정보 글](/m/sensitive-data)에서 이어 봐요.

## 삭제 API 응답과 멱등성 — DELETE 반복 시 204와 404

RFC 9110은 같은 요청을 여러 번 보내도 서버에 생기는 효과가 한 번 보낸 것과 같은 메서드를 멱등 메서드라고 설명해요. DELETE가 여기에 들어가요. 같은 문서는 응답은 다를 수 있다고도 설명해요. 그래서 첫 요청은 204로 성공하고, 두 번째 요청은 이미 없는 글을 찾아 404를 줘도 상태는 같아요.

| 상황                     | 응답         | 근거                                                     |
| ------------------------ | ------------ | -------------------------------------------------------- |
| 삭제 성공                | 204          | RFC 9110은 내용 없이 요청이 처리됐다는 뜻이라고 설명해요 |
| 이미 없는 글에 다시 삭제 | 404          | 현재 표현이 없다는 뜻이에요                              |
| 영구 삭제가 끝난 글      | 404 또는 410 | 영구적임을 알면 410을 선호한다고 설명해요                |

404는 캐시될 수 있어요. RFC 9110은 404 응답이 기본으로 휴리스틱 캐시 대상이라고 설명해요. 삭제된 글의 조회 응답이 캐시에 남으면, 복구된 뒤에도 옛 404가 보일 수 있어요. 캐시 제어는 [HTTP 캐시 글](/m/http-caching)에서 이어 봐요.

## 검색 색인과 캐시 — 지운 뒤 남는 사본

행을 지워도 검색 색인, 캐시, 목록용 요약 테이블에는 사본이 남아 있을 수 있어요. 이 사본들은 DB 삭제와 다른 경로로 갱신돼요. 그래서 삭제 흐름은 DB 행만 바꾸고 끝나면 안 돼요. 소프트 삭제라면 색인에서도 빼고, 캐시 무효화 신호도 함께 보내야 해요. 설계 판단이에요.

색인을 어떻게 맞추는지는 [검색 색인 동기화 글](/m/search-index-sync)에서, 캐시를 어떻게 비우는지는 [HTTP 캐시 글](/m/http-caching)에서 다뤄요. 이 글에서는 삭제 흐름이 그 사본들까지 건드려야 한다는 것만 기억하면 돼요.

## FE 체크 포인트 — 화면에서 맞추는 것

**목록에 지운 글이 섞이면 BE 조회 조건부터 봐요.** 같은 화면에서 상세는 404인데 목록에는 보인다면, 목록 쿼리가 `deleted_at` 조건을 빠뜨렸을 가능성이 커요. 응답 필드에 삭제 표시가 있는지도 같이 확인해요.

**복구 버튼은 기간 안에서만 보여 줘요.** 응답에 복구 기한을 담아 주면 화면이 그 시각까지만 복구 버튼을 보여 줄 수 있어요. 기한이 지난 뒤에는 "복구 기간이 끝났어요"처럼 사실을 보여 주고, 다음 행동을 안내해요.

**DELETE가 404를 주면 실패로 보지 않아요.** 이미 지워진 상태라는 뜻이라서, 목록에서 빼고 이미 삭제된 글이라고 알려 주면 돼요. 재시도 버튼으로 같은 요청을 보내게 하지 않아요.

**재가입 실패는 원인을 구분해 보여 줘요.** 같은 이메일이 쓰이는 중이라는 사실과, 탈퇴 후 기간이 남은 상태인지 같이 안내할 수 있으면 좋아요. 다만 응답에 어떤 정보를 실을지는 BE와 맞춰요.

## 시뮬레이터 안내 — 방식과 사건 조합 비교

시뮬레이터에서는 삭제 방식을 네 가지 중에서 고르고, 사건을 여섯 가지 중에서 골라요. 방식은 하드 삭제, 소프트 삭제, 소프트 삭제와 부분 유일 인덱스, 소프트 삭제와 기간 뒤 영구 삭제예요. 사건은 복구 요청, 기간이 지난 뒤의 복구 요청, 같은 이메일 재가입, 조회 조건 누락, 댓글이 달린 글 삭제, 같은 DELETE 반복이에요.

조회 방식과 댓글 외래 키 옵션은 해당 사건에서만 결과를 바꿔요. 화면에서 흐리게 보이는 옵션은 그 사건에서 쓰이지 않는다는 뜻이에요.

먼저 소프트 삭제에 재가입을 골라 보세요. 409가 나와요. 그다음 부분 유일 인덱스로 바꾸면 201이 나오고, 옛 행이 남는다는 주의가 붙어요. 조회 조건 누락에서는 부분 인덱스만으로 지운 글이 보이고, 살아 있는 행 뷰로 바꾸면 사라져요. 기간이 지난 뒤의 복구 요청에서는 배치 없는 소프트 삭제가 지운 데이터를 계속 살려 두는 것을 볼 수 있어요.

## 이미 있는 글과 겹치는 부분 — 링크로 넘기기

- 소프트 삭제의 복구 기록과 이력 테이블은 [감사 로그 글](/m/audit-history)에서 자세히 다뤄요.
- 보관 기간과 개인정보를 가리는 방법은 [민감 정보 글](/m/sensitive-data)에서 다뤄요.
- 기간이 지난 행을 주기적으로 지우는 운영은 [배치 작업 글](/m/batch-jobs)에서 다뤄요.
- 검색 색인을 원본과 맞추는 방법은 [검색 색인 동기화 글](/m/search-index-sync)에서 다뤄요.
- 404와 캐시 제어는 [HTTP 캐시 글](/m/http-caching)에서 다뤄요.

## 정리 — 삭제 방식 · 조회 가드 · 부분 유일 · ON DELETE · 응답 코드

복구 요구가 있으면 `deleted_at`으로 소프트 삭제하고, 모든 조회는 살아 있는 행 뷰를 거치게 해요. 재가입은 `WHERE deleted_at IS NULL` 부분 유일 인덱스로 열고, 외래 키는 기본 키를 참조해요. 댓글 같은 자식 행의 ON DELETE는 관계의 성격으로 고르고, 소프트 삭제에서는 실행되지 않는다는 점을 기억해요. 복구 기간이 끝난 행은 자식부터 배치로 지우고, 탈퇴 시에는 식별 값을 파기하거나 익명화하면서 남길 기록을 따로 정해요. DELETE 응답은 첫 요청 204, 반복 요청 404로 두고, 색인과 캐시에서도 같이 지워요.
