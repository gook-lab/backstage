인기 글에 좋아요를 누르면 내 화면의 숫자는 바로 1 올라가는데, 다른 사람 화면에서는 몇 초 뒤에야 올라가요. 어떤 때는 새로고침할 때마다 숫자가 조금씩 달라지기도 해요. 좋아요 하나를 세는 일이 왜 이렇게 어려울까요? 이 글에서는 좋아요와 조회수를 나눠 보고, 인기 글 하나에 요청이 몰릴 때 카운터 행이 어떻게 막히는지, 그리고 그 문제를 푸는 선택지가 무엇을 바꾸는지 정리해요.

아래 시뮬레이터에서 인기 글 하나에 좋아요가 몰리는 상황을 직접 돌려 볼 수 있어요. 숫자는 이 시뮬레이터 안에서만 쓰는 예시예요.

## 좋아요 — (글, 사용자) 쌍으로 한 번만 세기

좋아요는 "이 사용자가 이 글을 좋아해요"라는 사실이에요. 그래서 숫자 하나를 올리기보다 (글, 사용자) 쌍의 고유 행으로 저장하고, 개수는 그 행을 세어서 얻는 편이 자연스러워요.

```sql
CREATE TABLE post_like (
  post_id bigint NOT NULL,
  user_id bigint NOT NULL,
  PRIMARY KEY (post_id, user_id)
);

INSERT INTO post_like (post_id, user_id) VALUES (1, 42)
ON CONFLICT DO NOTHING;
```

PostgreSQL 문서에 따르면 `ON CONFLICT DO NOTHING` 은 충돌하는 행을 넣지 않고 넘어가요. 같은 사용자가 두 번 눌러도 행은 하나뿐이에요. 이때 INSERT 가 실제로 행을 넣었는지 영향받은 행 수로 알 수 있어요. 이 값이 1 일 때만 글의 좋아요 수를 올리면, 중복 요청은 숫자를 건드리지 않아요.

반대로 `POST /posts/1/like` 를 받을 때마다 `like_count = like_count + 1` 을 실행하면 더블 탭과 재시도가 그대로 숫자가 돼요. 시뮬레이터에서 요청 방식을 POST 로 두고 더블 탭을 올려 보면 이 차이가 바로 보여요.

| 저장 방식               | 더블 탭 · 재시도                           | 숫자를 얻는 방법               | 주의                                               |
| ----------------------- | ------------------------------------------ | ------------------------------ | -------------------------------------------------- |
| 좋아요 행 + 고유 키     | 행이 하나라서 한 번만 세요                 | `count(*)` 또는 집계 행에 반영 | 인기 글은 `count(*)` 가 느려요. 집계 행이 필요해요 |
| 숫자 한 개를 POST 로 +1 | 요청마다 +1 이 되어 중복이 숫자에 남아요   | 저장된 숫자를 그대로 읽어요    | 숫자와 실제 좋아요가 어긋나요. 되돌리기도 어려워요 |
| 상태를 PUT 으로 설정    | 같은 상태를 여러 번 설정해도 결과가 같아요 | 행 수 또는 집계 행             | 아래 멱등 토글 절을 보세요                         |

고유 키로 중복을 막아도 집계 행을 따로 두면 그 행이 다시 병목이 돼요. 이 문제가 이 글의 중심이에요.

## 조회수 — 근사해도 되는 이벤트로 다루기

조회수는 좋아요보다 느슨하게 다뤄도 되는 경우가 많아요. 같은 사람이 새로고침을 열 번 해도 조회수를 열 번 올리면 안 돼요. 다만 정확한 값을 실시간으로 맞출 필요는 보통 없어요.

- 조회 이벤트는 쌓기만 하는 기록으로 남겨요. 같은 사용자의 중복 제거 기간(예: 30분)을 정해 두고, 그 안의 반복은 한 번으로 세요.
- 고유 방문자 수는 HyperLogLog 로 근사해요. Redis 의 PFADD 는 원소를 넣고, PFCOUNT 는 추정치를 돌려줘요. Redis 문서는 이 추정치의 표준 오차를 0.81% 로 설명해요. 정확한 집합을 전부 저장하지 않아도 되는 대신 값은 추정치예요.
- 조회 기록을 보내는 신호는 페이지를 떠나는 순간에도 끝까지 가야 해요. MDN 은 `navigator.sendBeacon()` 이 페이지를 떠나는 동안에도 비동기로 데이터를 보내고, 페이지 이동을 막지 않는다고 설명해요. 브라우저가 비동기 요청을 취소할 수 있는 상황을 줄이는 데 쓸 수 있어요.

조회수를 얼마나 정확하게 셀지는 서비스가 정할 일이에요. 광고 정산처럼 돈과 맞물리면 더 엄격하게 세고, 인기 순위처럼 대략의 크기만 필요하면 근사치가 충분해요.

## 핫 행 — 같은 카운터 행을 UPDATE 하면 줄이 생겨요

`UPDATE posts SET like_count = like_count + 1 WHERE id = 1` 은 글 한 줄을 갱신해요. PostgreSQL 은 UPDATE 를 하는 동안 해당 행에 행 수준 락을 잡아요(명시적 락 문서의 행 수준 락 절). 두 번째 요청은 첫 번째 트랜잭션이 끝날 때까지 기다려요. 인기 글에 요청이 초당 수백 건 몰리면, 처리량은 행 하나가 락을 주고받는 속도에 묶여요.

시뮬레이터의 기본 설정이 이 상황이에요. 한 행이 틱마다 처리할 수 있는 쓰기 수에는 상한이 있어요(이 시뮬레이터의 가정이에요). 좋아요 요청이 그 상한을 넘으면 대기 줄이 생기고, 줄이 길수록 화면의 숫자는 실제보다 늦어요.

이 문제를 줄이는 방법은 네 가지예요. 어느 것이 맞는지는 쓰기 속도, 허용하는 지연, 장애 때 잃어도 되는 값에 따라 달라요.

| 방식                               | 빨라지는 것                                | 대가                                                                    |
| ---------------------------------- | ------------------------------------------ | ----------------------------------------------------------------------- |
| 한 행에 바로 UPDATE                | 구현이 가장 단순해요                       | 인기 글일수록 행 락 대기가 길어져요                                     |
| 카운터를 N 개 조각으로 나누기      | 조각마다 줄이 N 분의 1 로 짧아져요         | 총합을 읽을 때 조각을 모두 더해야 해요. 조각 수만큼 읽기 비용이 늘어요  |
| Redis INCR 로 모아 주기적으로 반영 | 요청마다 DB 를 건드리지 않아요             | 반영 전에 장애가 나면 쌓인 증가분을 잃어요. 화면 숫자가 주기만큼 늦어요 |
| 이벤트 로그에 쌓고 주기적으로 집계 | 이벤트가 남아서 집계를 다시 만들 수 있어요 | 이벤트 저장 비용이 들고, 집계 주기만큼 숫자가 늦어요                    |

Google Cloud 의 Firestore 문서도 같은 문제를 다뤄요. 자주 바뀌는 카운터 하나를 문서 하나로 두면 쓰기가 몰려요. 그래서 카운터를 샤드 문서 여러 개로 나누고, 값은 샤드의 합으로 정하라고 안내해요. 같은 문서에 대한 쓰기 처리량을 샤드 수에 따라 늘릴 수 있다는 설명도 있어요. 이 원리는 PostgreSQL 행 하나에도 그대로 적용돼요.

샤딩은 쓰기를 빠르게 하지만, 숫자를 읽는 쪽이 조각을 모두 더해야 해요. 조각이 많으면 읽기가 무거워지고, 조각 하나의 값을 잘못 고치면 총합이 틀려요. 그래서 샤딩을 할 때는 조각별 증가만 허용하고, 총합은 주기적으로 맞추는 편이 안전해요.

버퍼링은 Redis INCR 로 증가분을 메모리에 쌓아요. INCR 은 키에 저장된 숫자를 1 올리는 명령이에요(Redis 문서). 주기마다 쌓인 합을 DB 에 한 번만 더해요. 이때 주기가 길수록 DB 의 쓰기는 줄지만, 반영 전 장애가 나면 쌓인 값은 사라져요. 시뮬레이터에서 장애 넣기를 켜고 반영 주기를 길게 해 보세요. 잃은 건수가 경고로 나와요.

이벤트 로그는 좋아요 하나마다 행을 추가해요. 추가만 하니 행 락 경합이 거의 없어요. 대신 집계 작업이 로그를 읽어 숫자를 만들고, 그 사이에는 화면과 실제가 어긋나요. 로그가 남아 있으니 장애가 나도 집계를 다시 만들 수 있어요.

## 일관성 — 내 좋아요는 바로, 총합은 나중에

좋아요 시스템은 대개 강한 일관성 대신 최종 일관성을 택해요. 다른 사람 화면의 총합이 잠깐 늦어도 서비스가 깨지지 않기 때문이에요. 다만 **내가 누른 결과는 바로 보여야** 해요. 방금 누른 좋아요가 사라지면 손님은 버그라고 느껴요.

그래서 두 값을 나눠 저장하고 보여 줘요.

- 내가 좋아요를 눌렀는지는 내 상태로 따로 두고, 누르자마자 반영해요.
- 총합은 서버가 준 값을 그대로 보여 줘요. 내 상태와 총합을 한 객체에 섞지 않아요.
- 총합을 화면에서 다시 계산하지 마세요. 오래된 목록을 들고 있다가 +1 하면 다른 사람의 변화가 사라져요.

숫자는 1.2만처럼 줄여 보여 줄 때가 많아요. 시뮬레이터의 `formatCount` 는 1만 이상을 만 단위로 줄이고 소수 한 자리만 보여 줘요. 이렇게 하면 숫자가 조금 늦게 바뀌어도 사용자는 차이를 잘 느끼지 못해요.

## 멱등 토글 — PUT 과 DELETE 로 상태 설정하기

좋아요 버튼은 "토글"처럼 보이지만, API 를 토글로 만들면 재시도에 약해요. `POST /posts/1/like` 를 두 번 받으면 서버는 두 번 바뀌어요. RFC 9110 은 멱등 메서드를 "같은 요청을 여러 번 보내도 서버에 의도한 효과가 한 번 보낸 것과 같은 메서드"라고 정의해요. PUT 과 DELETE 가 여기에 해당해요.

그래서 좋아요는 상태를 설정하는 방식으로 설계해요.

- `PUT /posts/1/like` 는 "이 사용자는 이 글을 좋아해요"라는 상태를 만들어요.
- `DELETE /posts/1/like` 는 "좋아요를 취소했어요"라는 상태를 만들어요.

화면이 "지금 좋아요 상태"를 기준으로 PUT 또는 DELETE 를 고르면, 더블 탭이나 네트워크 재시도가 있어도 결과는 같아요. 시뮬레이터에서 요청 방식을 PUT 으로 바꾸면 중복 요청이 있어도 숫자가 어긋나지 않아요.

## FE 체크 포인트

**누르는 즉시 바꾸고, 실패하면 되돌려요.** 버튼 상태와 숫자를 바로 바꾸고, 실패 응답이 오면 이전 상태로 되돌려요. 되돌릴 때는 조용히 바꾸지 말고 한 줄로 알려 주세요.

**빠른 연타는 마지막 상태 하나만 보내요.** 좋아요를 짧은 시간에 여러 번 누르면 디바운스로 마지막 상태만 보내요. 요청이 줄고, 응답이 뒤섞이는 일도 줄어요.

**내 상태와 총합을 따로 둬요.** `isLiked` 와 `likeCount` 는 서로 다른 출처에서 와요. 내 상태를 응답으로 맞추고, 총합은 서버가 준 값을 그대로 써요.

**기기마다 잠깐 다른 숫자를 허용해요.** 다른 기기의 총합은 다음 조회나 실시간 신호가 올 때 맞춰져요. 같은 순간에 두 기기의 숫자가 다른 것은 정상이에요.

**조회 기록은 페이지를 막지 않게 보내요.** 페이지를 떠날 때 `navigator.sendBeacon()` 으로 보내면 이동을 기다리게 하지 않아요. 응답을 기다릴 필요가 없는 신호에만 써요.

## 정리 — 좋아요는 세지 말고 상태로 저장해요

좋아요는 (글, 사용자) 쌍의 고유 행으로 저장하면 중복이 숫자에 남지 않아요. 인기 글의 숫자는 한 행에 몰리는 UPDATE 때문에 줄을 서요. 샤딩, 버퍼링, 이벤트 로그는 각각 줄을 나누거나 미루거나 기록으로 남기는 방식이에요. 어느 쪽이든 화면의 숫자는 잠깐 늦고, 버퍼는 장애 때 값을 잃을 수 있어요.

더 읽어 보려면 같은 행을 두고 경합하는 문제를 다룬 [트랜잭션 · 락 · 데드락](/m/transactions) 글과, 캐시가 몰리는 순간을 다룬 [캐시 스탬피드](/m/cache-stampede) 글을 이어서 보세요.
