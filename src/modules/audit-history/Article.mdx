관리자 화면에 상품 가격 변경 이력을 붙여 달라는 요청이 와요. 목록 API를 붙이고 나서 가격을 세 번 바꿔 보면, 이력에는 마지막 값 한 줄만 보일 때가 많아요. 서버가 이전 값을 어디에도 남기지 않았기 때문이에요.

이 글은 백엔드(BE)가 "누가 언제 무엇을 바꿨나"를 어떻게 남기는지, 그리고 지운 데이터를 어떻게 되돌리는지 정리해요. 이력은 로그와 목적이 달라요. 애플리케이션 로그는 장애를 찾으려고 남기고, 감사 기록은 데이터가 어떻게 바뀌었는지 되짚으려고 남겨요. OWASP 로깅 치트시트도 감사 · 거래 추적 기록은 보안 이벤트 로그와 목적이 달라서 따로 두는 편이 좋다고 설명해요. 로그 자체의 설계는 [로그 · 메트릭 · 트레이스 글](/m/observability)에서 이어 읽어요.

## 증상 — 덮어쓴 값이 이력에서 사라지는 경로

FE가 보는 증상은 보통 세 가지예요.

- 가격을 1,000원에서 1,200원, 900원으로 바꿨는데 이력이 한 줄뿐이에요.
- 이력에 누가 바꿨는지 이름이 없어요.
- 삭제한 상품을 복구했더니 삭제 직전 값과 다른 값이 나와요.

원인은 대개 한 가지예요. 현재 값 테이블 한 개에 UPDATE만 하고 있어서 이전 값이 덮여요. PostgreSQL 트리거 문서는 UPDATE와 DELETE에서 변경 전 행을 `OLD`로 준다고 설명해요. 이 순간에 기록하지 않으면, 옛 값은 DB 안에 남지 않아요.

## 현재 값과 이력 — 테이블을 둘로 나누기

현재 값은 목록과 결제가 읽는 원본 테이블에 두고, 이력은 옆 테이블에 쌓아요. 두 역할을 섞으면 이력 쓰기가 빠질 때 현재 값까지 틀려져요.

```sql
-- 예시: 현재 값. 목록과 결제가 읽어요.
CREATE TABLE products (
  id          bigint PRIMARY KEY,
  price       integer NOT NULL,
  deleted_at  timestamptz
);

-- 예시: 이력. 바뀐 사실을 쌓기만 하고, 이력 화면만 읽어요.
CREATE TABLE product_history (
  id          bigserial PRIMARY KEY,
  product_id  bigint NOT NULL,
  changed_at  timestamptz NOT NULL,
  actor_id    text NOT NULL,
  action      text NOT NULL,
  before_price integer,
  after_price  integer,
  request_id  text
);
```

OWASP는 감사 대상으로 데이터 추가, 수정, 삭제, 내보내기를 들어요. 이 글의 이력 테이블은 그중 수정과 삭제를 기록하는 자리예요.

## 기록 위치 — 앱 코드 · DB 트리거 · 변경 데이터 캡처 비교

이력을 쓰는 자리는 세 곳이 흔해요. 어디서 쓰느냐에 따라 놓치는 변경이 달라요.

| 방식                   | 어떻게 기록하나                                                   | 좋은 점                        | 놓치는 경우                                                |
| ---------------------- | ----------------------------------------------------------------- | ------------------------------ | ---------------------------------------------------------- |
| 앱 코드                | 서비스 함수가 현재 값을 바꾸면서 이력 행도 같은 트랜잭션에 넣어요 | 행위자와 요청 id를 쉽게 담아요 | DB를 직접 고치거나 다른 서비스가 같은 테이블을 쓰면 빠져요 |
| DB 트리거              | 테이블마다 트리거가 변경 전후 행을 이력 테이블에 넣어요           | 앱을 거치지 않은 쓰기도 잡아요 | 행위자는 DB 계정 기준이에요                                |
| 변경 데이터 캡처 (CDC) | DB의 변경 기록을 읽어 별도 저장소로 흘려보내요                    | 앱 코드를 고치지 않아요        | 별도 파이프라인을 운영하고 지연을 따로 봐야 해요           |

OWASP는 애플리케이션이 사용자 정보와 사건 맥락을 가장 많이 안다고 설명해요. 그래서 행위자와 요청 맥락은 앱 코드에서 담기 쉬워요. 반면 DB 트리거는 PostgreSQL 문서 예시처럼 `current_user`를 기록해요. 그 예시에는 앱 사용자 id를 넘기는 코드가 없어요. 앱 사용자 id를 남기려면 따로 넘겨야 해요.

행 단위 트리거(`FOR EACH ROW`)는 바뀐 행마다 한 번씩 실행돼요. PostgreSQL 문서는 한 번의 DELETE가 10행을 지우면 그 테이블의 ON DELETE 트리거가 10번 불린다고 설명해요. AFTER 트리거도 에러를 내면 원래 작업 전체를 중단할 수 있다고 설명해요. 그래서 이력 쓰기 실패가 현재 값 변경을 막을지 말지를 함께 정해야 해요.

작은 서비스라면 앱 코드가 쉬워요. 운영자가 DB를 직접 고치는 경로가 잦으면 트리거를 더하는 편이 좋아요. 두 곳에서 같이 쓰면 같은 변경이 두 줄 생기니, 한 곳을 기준으로 정해요. 트랜잭션으로 현재 값과 이력을 함께 묶는 방법은 [트랜잭션 · 락 · 데드락 글](/m/transactions)에서 이어 읽어요.

## 이벤트 필드 — 행위자 · 시각 · 대상 · 값 · 요청 id

"누가 언제 무엇을"에 답하려면 한 줄에 필요한 값이 다 있어야 해요. OWASP는 로그 항목이 "when, where, who and what"을 담아야 한다고 설명해요.

| 필드                           | 답하는 질문            | OWASP 항목                                           |
| ------------------------------ | ---------------------- | ---------------------------------------------------- |
| `actor_id`                     | 누가                   | Who: 사람 또는 기계 사용자                           |
| `changed_at` (UTC)             | 언제                   | When: 이벤트 날짜와 시각                             |
| `product_id`                   | 무엇을                 | What: 대상 객체 (Object)                             |
| `action`                       | 어떻게                 | 행위 (Action)                                        |
| `before_price` · `after_price` | 무엇이 어떻게 바뀌었나 | OWASP 목록 밖의 필드예요. 복원하려면 필요해서 넣어요 |
| `request_id`                   | 어떤 요청에서          | 상호작용 식별자 (Interaction identifier)             |
| 결과 · 사유                    | 성공했나, 왜 실패했나  | Result status · Reason                               |

`request_id`는 OWASP가 말하는 상호작용 식별자예요. 한 사용자 행동으로 생긴 이벤트들을 묶는 값이에요. 같은 요청이 상품 행과 쿠폰 행을 함께 바꿨다면, 두 이력이 같은 `request_id`로 이어져요.

예시 이벤트 한 줄은 이래요.

```json
{
  "at": "2026-11-22T06:00:00.000Z",
  "actor": "admin-17",
  "action": "edit",
  "object": "product:42",
  "before": { "price": 1000 },
  "after": { "price": 1200 },
  "requestId": "req-1"
}
```

행위자에는 이름 대신 내부 id만 남겨요. 이름과 이메일은 개인정보라서, 화면에 보일 때 조회해서 붙이는 편이 나아요. 이 기준은 아래 개인정보 항목에서 이어 봐요.

## 덧붙이기 전용과 변조 감지 — 수정 막기와 감지를 나누기

이력은 덧붙이기 전용(append-only)으로 두는 편이 좋아요. 이력을 고치는 경로를 아예 없애는 방식이에요. OWASP는 DB에 로그를 쓸 때 로그 쓰기만 하는 별도 계정을 쓰고, 테이블과 명령 권한을 아주 좁게 주라고 설명해요. 앱 계정에는 이력 테이블에 대해 INSERT와 SELECT 정도만 주는 식이에요.

다만 권한으로 막는 것과 변조를 알아내는 것은 달라요. 권한이 큰 계정은 이력 테이블도 바꿀 수 있어요. 그래서 OWASP는 기록이 수정이나 삭제됐는지 알 수 있도록 변조 감지를 만들라고 설명해요. 로그를 읽는 접근도 기록하고 감시하라고 해요.

| 장치                             | 무엇을 돕나                                   | 출처                                                |
| -------------------------------- | --------------------------------------------- | --------------------------------------------------- |
| 앱 계정 권한 좁히기              | 앱 경로로 이력을 고치거나 지우는 일을 막아요  | OWASP: 로그 쓰기 전용 계정과 좁은 권한              |
| 읽기 전용 매체와 다이제스트 보관 | 저장한 뒤 바뀌었는지 알 수 있는 근거를 남겨요 | NIST SP 800-92: 원본 다이제스트를 변경으로부터 보호 |
| 로그 읽기 접근 기록              | 누가 이력을 봤는지 남겨요                     | OWASP: 로그 접근은 기록하고 감시                    |

해시 체인처럼 행끼리 잇는 방식은 이 글에서 자세히 다루지 않아요. 위 표는 OWASP와 NIST가 말한 범위까지만 담았어요.

## 소프트 삭제와 복구 — 지운 값을 되돌리는 두 길

소프트 삭제는 행을 지우지 않고 `deleted_at`을 채우는 방식이에요. 복구는 `deleted_at`을 비우는 동작이에요. 이때 복구도 변경이라서 이력에 `restore`로 남겨요. 복구를 이력에 안 남기면, 삭제와 복구 사이의 가격 변화가 보이지 않아요.

소프트 삭제는 데이터를 지우지 않아요. 그래서 개인정보가 든 행을 소프트 삭제만 하면 보존 기간이 끝나도 남아요. 기간이 지난 행을 실제로 지우는 절차는 따로 둬야 해요. 개인정보를 가리는 방법은 [민감 데이터 글](/m/sensitive-data)에서 이어 봐요.

## 시각 — UTC로 저장하고 화면에서 바꾸기

시각은 UTC로 저장하고, 보여 줄 때만 바꿔요. PostgreSQL 문서는 `timestamptz` 값이 입력받은 시간대를 UTC로 바꿔 저장하고, 원래 시간대는 남기지 않는다고 설명해요. 그래서 "행위자가 보던 시간대"를 남기려면 따로 열이 필요해요.

쓰는 시각도 조심해요. PostgreSQL 문서는 `now()`와 `CURRENT_TIMESTAMP`가 현재 트랜잭션이 시작된 시각을 준다고 설명해요. 한 트랜잭션에서 이력을 여러 줄 쓰면 시각이 모두 같아져요. 실제 시각이 필요하면 `clock_timestamp()`를 써요. 이 함수는 SQL 문 안에서도 값이 바뀐다고 설명돼요. 같은 시각 이벤트가 생기면 순서를 정하는 보조 키가 있어야 해요.

화면에서는 JavaScript `Date`를 써요. MDN은 `Date` 값이 UTC 기준 시각을 담고, 로컬 메서드는 기기 시간대로 바꾸어 준다고 설명해요. `toISOString()`은 UTC 기준으로 끝에 `Z`가 붙은 문자열을 줘요. 표시 시간대를 정할 때는 `Intl.DateTimeFormat`의 `timeZone` 옵션을 써요. MDN은 옵션을 주지 않으면 실행 환경의 기본 시간대를 쓴다고 설명해요.

이력 화면에 "어제 오후 3시 값"을 보여 주려면, 관리자의 시간대를 기준으로 시각을 UTC로 바꿔서 질의해야 해요. 서버 시간대나 기기 시간대와 섞이면 같은 시각을 다르게 읽게 돼요. NIST SP 800-92는 로그 소스마다 타임스탬프가 일관되지 않은 것을 로그 관리의 어려움으로 꼽고, 각 호스트 시계를 공통 시간원에 맞추라고 설명해요.

## 이력 목록 — 최신순 페이지와 동률 정렬

이력은 최신순으로 나눠 읽어요. 같은 시각 줄이 많으면 정렬 키에 `id`를 붙여 순서를 고정해요. 페이지 사이에 새 이력이 끼는 문제는 [페이지네이션 글](/m/pagination)의 커서 설계로 이어서 봐요.

## 개인정보와 보존 기간 — 값을 가리고 지울 시점 정하기

이력에는 행위자 id와 바뀐 값이 남아요. OWASP는 로그가 개인정보와 민감 정보를 담을 수 있다고 설명해요. 이름, 전화번호, 이메일처럼 민감하지 않은 개인정보도 기록하기 전에 특별히 다뤄야 할 수 있다고 해요. 개인이 식별될 필요가 없으면 삭제, 흐리기, 가명 처리 같은 방법을 고려하라고도 해요.

보존 기간도 정해야 해요. OWASP는 로그를 필요한 보존 기간이 끝나기 전에는 지우지 말고, 기간을 넘겨서 두지도 말라고 설명해요. 법이나 계약 의무가 기간을 바꿀 수 있다고도 덧붙여요. NIST SP 800-92는 보존 기간이 며칠이나 몇 주처럼 짧으면 온라인에 두고 정기 백업에 담는 것으로 충분할 수 있다고 설명해요. 몇 달이나 몇 년처럼 길면 아카이브 형식을 골라 보관해야 한다고 해요.

이 글 예시에서는 행위자 id만 남기고, 기간이 지난 이력은 행위자 id를 가명으로 바꾸는 방식을 떠올리면 돼요. 이 결정은 서비스 정책과 법에 따라 달라요.

## 시점 복원 — 기록으로 "어제 오후 3시 값" 찾기

어느 시점 값은 그 시점 이전의 마지막 이력 줄로 찾아요. 이력이 빠짐없이 쌓였을 때만 맞아요. 앱 밖에서 바뀐 변경이 한 번이라도 기록되지 않았다면, 그 뒤 시점 값은 틀린 값이 돼요.

현재 값만 두면 시점 복원은 아예 불가능해요. 과거 값이 덮였기 때문이에요. 이력을 쌓는 비용은 쓰기가 한 번 더 일어나는 것과 저장 공간이에요. 대신 시점 복원과 감사 질문에 답할 수 있어요.

## FE 체크 포인트 — 화면에서 맞추는 것

**시각은 오프셋이 붙은 문자열로 받아요.** 응답의 `changedAt`이 `Z`나 오프셋을 담는지 확인해요. 표시 시간대는 관리자 설정이나 기기 기본값 중 하나로 정하고, 그 기준을 화면에 적어 줘요.

**목록은 커서로 더 불러와요.** 이력 목록을 페이지로 나눈다면 응답의 커서를 그대로 넘기고, 새 이력이 끼어도 중복 없이 이어지는지 BE에 확인해요.

**행위자 이름은 응답에 없을 수 있어요.** `actorId`만 오면 화면에서 이름을 조회해 붙여요. 조회가 실패했을 때 id를 보여 줄지 정해 둬요.

**복구 버튼은 서버 권한을 따라 보여요.** 화면 숨김은 보안이 아니에요. 권한 판단은 [인가 글](/m/authorization)에서 이어 봐요.

## 시뮬레이터 안내 — 기록 방식과 위치 비교

아래 시뮬레이터에서 편집, 삭제, 복구, DB 직접 수정 버튼을 눌러 동작 순서를 만들어요. 그다음 기록 방식과 기록 위치를 바꿔 보세요.

- "현재 값만"을 고르면 이력이 비고, 옛 시점 복원이 불가능해요.
- "앱 코드에서 기록"을 고르고 DB 직접 수정을 누르면, 현재 값은 바뀌었지만 이력에는 줄이 없어요.
- "DB 트리거에서 기록"으로 바꾸면 같은 직접 수정도 이력에 남아요.
- 시점 복원에서 동작을 고르면 그 시점 값을 기록으로 맞출 수 있는지 나와요.

수치는 감을 잡기 위한 예시예요.

## 정리 — 이력 분리 · 기록 위치 · 덧붙이기 · UTC 시각

현재 값과 이력은 테이블을 나눠요. 기록 위치는 앱 코드나 DB 트리거 중 하나를 골라요. 이벤트에는 행위자, UTC 시각, 대상, 이전 값과 새 값, 요청 id를 담아요. 이력은 덧붙이기 전용으로 두고, 변조 감지는 따로 설계해요. 소프트 삭제는 복구를 쉽게 하지만, 개인정보는 보존 기간이 지나면 지워요.

더 깊이 보려면 같은 값을 여러 서비스가 쓸 때의 색인 갱신은 [검색 색인 동기화 글](/m/search-index-sync)을, 시간대 저장과 표시는 [시간과 지역 설정 글](/m/time-and-locale)을 이어서 읽어 보세요.
