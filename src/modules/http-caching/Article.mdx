배포했는데 사용자 화면에 옛 데이터가 남아 있어요. 서버는 고쳤는데 어떤 사용자는 예전 목록을 보고, 다른 사용자는 새 목록을 봐요. 옛 값을 들고 있는 곳은 브라우저일 수도, CDN이나 프록시일 수도 있어요.

HTTP 캐시는 응답 헤더로 정해져요. 이 글은 API JSON 응답을 "누가 얼마나 오래 들고 있나"에 초점을 맞춰요.

이미지 파일의 캐시 키와 장기 캐시는 [이미지 CDN](/m/image-cdn) 글에서, 만료 순간 몰리는 요청은 [캐시 스탬피드](/m/cache-stampede) 글에서 다뤄요.

아래 시뮬레이터에서 헤더 조합과 경과 시간을 바꿔 보면, 개인 캐시와 공유 캐시가 각각 무엇을 하는지 볼 수 있어요.

## 저장 위치 — 개인 캐시와 공유 캐시

HTTP 캐시는 두 종류로 나뉘어요. MDN은 개인 캐시를 브라우저처럼 한 클라이언트에 묶인 캐시라고 설명해요. 공유 캐시는 클라이언트와 서버 사이에 있어 여러 사용자가 같은 응답을 나눠 쓸 수 있어요. CDN과 프록시가 여기에 속해요.

| 구분               | 개인 캐시        | 공유 캐시                                   |
| ------------------ | ---------------- | ------------------------------------------- |
| 위치               | 브라우저         | CDN · 프록시                                |
| 응답을 쓰는 사람   | 한 사용자        | 여러 사용자                                 |
| 개인화된 응답      | 저장할 수 있어요 | `private`면 저장하지 않아요                 |
| 기간을 정하는 헤더 | `max-age`        | `s-maxage`가 있으면 `max-age`보다 먼저 써요 |

같은 응답이 두 곳에 따로 남을 수 있어요. 그래서 배포 뒤 옛 값이 한 층에서는 사라지고 다른 층에는 남아요.

MDN은 개인화된 내용이 공유 캐시에 들어가면 다른 사용자에게 새어 나갈 수 있다고 설명해요.

## 신선도 — max-age와 s-maxage로 확인 없이 쓰는 기간

RFC 9111은 응답이 신선한지를 신선 기간이 나이보다 긴지로 계산한다고 정해요. 신선한 응답은 원 서버에 묻지 않고 쓸 수 있어요.

공유 캐시는 `s-maxage`, 그다음 `max-age` 순서로 신선 기간을 정해요. 개인 캐시는 `s-maxage`를 읽지 않아요. 이 글은 `Expires`는 다루지 않아요.

예시로 `Cache-Control: public, max-age=60` 응답은 60초 동안 원 서버에 묻지 않고 저장본을 쓸 수 있어요. 그 안에서 배포된 새 값은 이 응답을 받은 사용자에게 보이지 않아요.

### 휴리스틱 캐시 — Cache-Control이 없을 때 추정

신선 기간을 알려 주는 헤더가 없으면 캐시가 기간을 추정할 수 있어요. RFC 9111은 이를 캐시에 허용(MAY)하고, `Last-Modified`를 기준으로 삼는 방법을 권해요. 전형적인 값으로 마지막 수정 뒤 기간의 10%를 들어요.

추정은 명시된 기간이 없을 때만 써요. 알고리즘은 정해 두지 않아서 캐시마다 값이 달라요. MDN도 휴리스틱 캐시를 `Cache-Control`이 널리 쓰이기 전의 우회 방식이라고 설명하고, 대부분의 응답에 `Cache-Control`을 명시하라고 권해요.

API 응답에는 `Cache-Control`을 직접 붙이는 편이 좋아요. 추정에 기대면 배포 뒤 얼마나 옛 값이 나갈지 예측하기 어려워요.

## 저장 범위 — no-store · private · Authorization

저장 범위는 헤더 세 개로 좁혀요.

| 조건                 | 개인 캐시             | 공유 캐시                                                              |
| -------------------- | --------------------- | ---------------------------------------------------------------------- |
| `no-store`           | 저장하지 않아요       | 저장하지 않아요                                                        |
| `private`            | 저장할 수 있어요      | 저장하지 않아요                                                        |
| `Authorization` 요청 | 저장본을 쓸 수 있어요 | `public`, `must-revalidate`, `s-maxage` 중 하나가 있어야 저장본을 써요 |

RFC 9111은 `no-store`를 개인 캐시와 공유 캐시 모두에 적용해요. 캐시는 응답의 일부도 저장하지 않아야 해요. `private`는 공유 캐시가 저장하지 않게 하고, `Authorization` 요청에 대한 규칙은 RFC 9111 §3.5에 있어요.

헤더를 새로 붙여도 이미 저장된 응답이 사라지지는 않아요. MDN은 `no-store`를 붙여도 이전에 저장된 옛 응답의 재사용은 막지 않는다고 설명해요. 배포 계획에는 기존 `max-age` 기간을 함께 넣어 두세요.

쿠키가 있다고 응답이 자동으로 개인용이 되지는 않아요. MDN은 개인화된 응답에 `Cache-Control: private`을 붙이는 방식을 권해요. 쿠키 값을 `Vary`에 넣는 방식보다 낫다고 설명해요.

## 재검증 — ETag · Last-Modified와 304

저장본의 기간이 지나도 바로 버리지 않을 수 있어요. RFC 9111 §4.3은 캐시가 조건부 요청으로 저장본을 확인할 수 있다고 정해요.

캐시가 `If-None-Match`에 저장본의 ETag를 실어 보내면, 서버는 현재 ETag와 같을 때 본문 없이 304를 줄 수 있어요. 다르면 200으로 새 본문을 줘요(RFC 9110 §13.1.2).

304 응답에는 200이었다면 보냈을 `ETag`, `Vary`, `Date` 같은 헤더를 실어야 해요(§15.4.5). 캐시는 304를 받으면 저장본의 헤더를 새 정보로 고쳐요(RFC 9111 §4.3.4).

- 본문이 그대로면 304를 받고 저장본을 써요.
- 본문이 바뀌었으면 200으로 새 본문을 받고 저장본을 갈아요.
- 검증 값(`ETag`, `Last-Modified`)이 없으면 전체 응답을 받아요.

`no-cache`는 저장을 막지 않고, 저장본을 쓰기 전에 원 서버에 확인하게 해요. MDN은 `max-age=0, must-revalidate` 조합보다 `no-cache`를 쓰는 편이 낫다고 설명해요.

## 옛 값 먼저 — stale-while-revalidate 창

RFC 5861은 `stale-while-revalidate`를 정의해요. 예를 들어 `Cache-Control: max-age=600, stale-while-revalidate=30` 응답은 600초 동안 신선하고, 그 뒤 30초 동안은 옛 값을 줄 수 있어요.

캐시는 그 사이 옛 값을 주면서 뒤에서 재검증해요. 창이 지나면 다음 요청은 기다렸다가 정상 처리돼요.

이 확장은 응답이 오래되었을 때 지연을 숨기는 대신, 옛 값이 나갈 수 있는 시간을 늘려요. 창이 클수록 옛 값이 나갈 수 있는 기간이 길어져요.

이 시뮬레이터는 두 가지 경우에 옛 값을 주지 않아요. `must-revalidate`가 있을 때와, 공유 캐시에 `s-maxage`가 있을 때예요. 근거는 RFC 9111 §4.2.4와 §5.2.2.10이에요. 두 규칙이 겹치는 부분은 RFC 5861과 함께 보세요.

## Vary — 요청 헤더별 저장본 나누기

RFC 9110 §12.5.5에 따르면 `Vary`는 응답을 고르는 데 쓰인 요청 헤더 이름을 나열해요. RFC 9111 §4.1은 저장본을 쓰려면 `Vary`에 나열된 요청 헤더가 저장할 때와 같아야 하고, 같지 않으면 재검증 없이 쓸 수 없다고 정해요.

예를 들어 `Accept-Language: en`으로 받은 응답을 `ja` 요청에 그대로 주면 안 돼요. `Vary: Accept-Language`를 붙이면 언어별로 저장본이 나뉘어요.

이 시뮬레이터는 언어가 다르면 맞는 저장본이 없다고 보고 원 서버로 보내요. MDN은 `User-Agent`를 `Vary`에 넣으면 변형이 너무 많아져 재사용 기회가 크게 줄어든다고 설명해요. `Vary: Origin`은 [CORS](/m/cors) 글에서 이어 볼 수 있어요.

## FE 체크 포인트

**옛 값이 어느 층에서 왔는지 응답 헤더로 좁혀요.** `max-age`와 `s-maxage`가 있는지 먼저 보세요. MDN은 공유 캐시가 저장한 응답에 `Age`를 붙여 나이를 알려 준다고 설명해요. `Age`가 있으면 중간 캐시를 거쳤을 가능성이 있어요.

**개인화 API에는 `private`를 붙여요.** 사용자별 응답이 공유 캐시에 들어가면 다른 사용자에게 보일 수 있어요. 로그인 상태에 따라 내용이 바뀌는 응답에 `private`을 붙이는 편이 안전해요.

**결제나 주문 상세처럼 민감한 응답에는 `no-store`를 붙여요.** 저장 자체를 막아야 하는 값이라서 기간 설정으로 대신하기 어려워요.

**만료 뒤 재검증이 되도록 `ETag`를 붙여요.** 본문이 그대로면 304로 끝나서 네트워크 비용이 줄어요. 검증 값이 없으면 만료 뒤에는 매번 전체 응답을 받아요.

같은 ETag를 저장 요청의 `If-Match`에 써서 덮어쓰기를 막는 방법은 [동시 편집](/m/concurrent-edits) 글에서 다뤄요.

**`Vary`에는 값 종류가 적은 헤더만 넣어요.** `User-Agent`처럼 값이 많은 헤더는 저장본 재사용을 줄여요.

## 시뮬레이터 안내

예시 응답을 고르거나 헤더를 직접 바꿔 보세요. 개인 캐시 카드와 공유 캐시 카드가 각각 무엇을 하는지 보여 줘요. 가능한 결과는 다섯 가지예요.

- 신선 사용
- 옛 값 즉시 응답
- 304 재검증
- 200 재검증
- 원 서버 요청

이 모델은 RFC 규칙을 단순하게 옮긴 것이에요. 저장본은 한 개만 있다고 가정하고, `Expires`와 `Age` 계산은 넣지 않았어요. 실제 브라우저와 CDN은 세부 동작이 다를 수 있어요. 휴리스틱의 30일과 10% 값도 예시예요.

## 정리 — 신선 기간과 저장 범위 결정

옛 데이터는 신선 기간 안에서 나와요. 그래서 `max-age`와 `s-maxage`를 얼마로 둘지가 배포 뒤 옛 값의 길이를 정해요. 공유 캐시만 길게 두고 싶다면 `s-maxage`를, 개인화 응답이라면 `private`와 `Authorization` 규칙을 먼저 맞추세요.

`ETag`로 재검증이 되게 하면 기간이 지난 뒤에도 본문 전송을 줄일 수 있어요. 민감한 응답은 `no-store`로 저장 자체를 막는 편이 좋아요.

더 보고 싶다면 만료 순간 몰리는 요청은 [캐시 스탬피드](/m/cache-stampede) 글을, 이미지 파일의 캐시 키와 장기 캐시는 [이미지 CDN](/m/image-cdn) 글을 이어서 읽어 보세요.
