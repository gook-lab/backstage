팀 초대 링크를 단톡방에 올렸더니 모르는 사람이 들어왔어요. 취소한 초대 링크를 눌렀는데도 팀에 들어가졌어요. 이 글은 초대 링크 하나가 만들어지고, 수락되고, 무효가 되기까지 서버가 무엇을 확인하는지 따라가요. 그리고 FE가 수락 결과 문구를 어떻게 나눠야 하는지 정리해요.

글의 숫자는 예시예요. 아래 시뮬레이터의 기본값과 같은 조건을 가정해요.

## 초대 토큰 — 무작위 값 · 해시 저장 · 만료 · 1회 사용

초대 토큰은 링크에 들어가는 값이에요. 서버는 토큰으로 초대 기록을 찾아요. 토큰을 추측할 수 있으면 링크를 모르는 사람도 초대를 찾아 수락할 수 있어요.

OWASP Forgot Password 치트시트는 토큰과 코드를 암호학적으로 안전한 난수 생성기로 만들라고 설명해요. 추측 공격을 막을 만큼 길어야 하고, 사용한 뒤에는 무효화하고, 적절한 기간이 지나면 만료해야 한다고 설명해요. 이 문서는 토큰을 안전하게 저장하라고만 설명하고, 저장 방법은 비밀번호 저장 치트시트로 넘겨요. 이 글은 해시 저장을 설계 판단으로 골라요. DB가 잠깐 노출돼도 토큰 원문으로 바로 수락할 수 없게 하려는 거예요.

```ts
import { createHash, randomBytes } from 'node:crypto';

// 링크에는 token 을 넣고, DB에는 해시만 저장해요
const token = randomBytes(32).toString('base64url');
const tokenHash = createHash('sha256').update(token).digest('hex');
```

토큰 길이 32바이트는 예시예요. 치트시트는 길이의 숫자를 정하지 않고, 추측 공격을 막을 만큼 길어야 한다고만 설명해요. 토큰은 사람이 고르는 값이 아니라서 빠른 해시로도 충분하다는 것이 이 글의 판단이에요. 번호처럼 경우의 수가 적은 값과는 달라요. 6자리 번호의 해시 이야기는 [인증번호 (OTP)](/m/verification-codes)에서 다뤄요.

| 속성     | 서버가 하는 일                                  | 근거                                                                   |
| -------- | ----------------------------------------------- | ---------------------------------------------------------------------- |
| 추측     | 암호학 난수로 만들고 충분히 길게 둬요           | OWASP Forgot Password 치트시트                                         |
| 저장     | 해시만 저장하고 원문은 응답 한 번에만 보여 줘요 | 해시 저장은 설계 판단이에요                                            |
| 만료     | `expires_at`을 행에 저장하고 수락 때 확인해요   | 기간 숫자는 치트시트에 없어요. GitHub 문서는 7일로 만료한다고 설명해요 |
| 1회 사용 | 수락하면 상태를 `accepted`로 바꿔요             | 치트시트는 사용 뒤 무효화하라고 설명해요                               |

토큰 발급과 보관의 세부는 [API 키 발급과 관리](/m/api-keys)에서 더 자세히 다뤄요.

## 초대 방식 비교 — 이메일 지정과 공유 링크

이메일 지정 초대는 초대 행에 받을 사람의 이메일을 적어요. 공유 링크는 받을 사람을 적지 않아요. 이 차이가 수락 조건을 바꿔요.

| 항목      | 이메일 지정                        | 공유 링크                     |
| --------- | ---------------------------------- | ----------------------------- |
| 받을 사람 | 초대 행에 이메일이 있어요          | 기록이 없어요                 |
| 수락 조건 | 로그인 이메일이 대상과 맞아야 해요 | 링크를 가진 계정이면 돼요     |
| 유출 피해 | 다른 이메일 계정은 거절돼요        | 먼저 연 계정이 들어가요       |
| 쓰는 장면 | 특정 사람을 초대할 때              | 여러 사람에게 한 번에 알릴 때 |

GitHub 문서는 이메일로 초대하면 초대받은 사람이 그 이메일을 계정의 확인된 이메일로 가진 경우에만 수락할 수 있다고 설명해요. 이메일 지정 방식은 이 원리를 쓴 것이에요.

공유 링크는 이 확인 대상이 없어요. 링크를 가진 계정이 누구인지 서버가 판단할 근거가 없어서, 유출되면 누구나 수락할 수 있어요. 그래서 공유 링크는 기본값으로 두지 않는 편이 좋아요. 꼭 써야 하면 만료를 짧게 두고, 1회 사용으로 묶고, 부여할 권한은 멤버로 제한하는 편이 좋아요. 이 조합도 설계 판단이에요.

## 수락 계정 확인 — 로그인 이메일과 초대 대상 비교

이메일 지정 초대는 수락 요청의 로그인 계정 이메일과 초대 대상 이메일을 비교해요. 다르면 거절해요. 이때 비교 대상은 인증이 끝난 이메일이어야 해요. 인증 안 된 이메일을 대상과 같게 맞춰 두면 확인이 의미를 잃어요. GitHub 문서도 확인된 이메일만 맞는다고 설명해요.

이메일 소유를 어떻게 확인하는지는 [계정 핵심 정보 변경](/m/account-changes)에서 다뤄요.

다른 계정으로 로그인된 상태에서 링크를 누르면, 서버는 자동으로 계정을 바꾸지 않아요. 거절 문구와 함께 대상 이메일 계정으로 다시 로그인하라고 안내하는 편이 좋아요. 안내 문구에 대상 이메일을 그대로 적으면 안 돼요. 민감 정보가 화면이나 로그에 남는 문제는 [민감 정보 누출](/m/sensitive-data)과 같아요.

OWASP Forgot Password 치트시트는 URL 토큰이 쿼리 문자열로 전달된다고 설명해요. 그리고 재설정 페이지에는 `no-referrer` 값의 Referrer Policy를 넣어 Referrer 누출을 막으라고 설명해요. 초대 페이지에서 토큰을 쿼리에 담으면 같은 문제가 생기므로, 이 글은 같은 조치를 초대 페이지에 두는 편이 좋다고 판단해요. 치트시트가 직접 다루는 범위는 재설정 페이지까지예요.

## 수락 처리 — 조건부 상태 갱신과 멱등성

초대 상태는 `pending`에서 `accepted`, `revoked`, `expired` 중 하나로만 바뀌어요. 바꾸는 쿼리는 현재 상태를 조건에 넣어요.

```sql
UPDATE team_invites
SET status = 'accepted', accepted_by = $1, accepted_at = now()
WHERE id = $2
  AND status = 'pending'
  AND expires_at > now()
RETURNING team_id, role;
```

PostgreSQL 문서는 갱신된 행 수가 0이면 쿼리가 행을 바꾸지 않은 것이고, 이것이 오류는 아니라고 설명해요. 그래서 0행이면 서버는 실패 이유를 한 번 더 읽어서 응답을 나눠요. 이 쿼리가 없으면 확인과 갱신이 나뉘어요. 두 요청이 모두 `pending`을 읽고 둘 다 통과해서 같은 초대로 두 번 들어갈 수 있어요.

초대 상태는 조건부 UPDATE로만 바뀌어요. 만료 기간이 지난 요청이 오면 상태를 `expired`로 바꿔요. 수락 요청을 여러 번 보내도 결과가 같게 만드는 것이 멱등성이에요. 같은 계정의 재요청은 이미 수락된 상태를 알려 주고, 멤버 행은 하나로 유지해요. 응답 코드를 어떻게 줄지는 설계에 따라 골라요.

## 취소 처리 — 상태 변경으로 즉시 무효화

취소는 초대 행의 상태를 `revoked`로 바꾸는 일이에요. 링크 문자열을 지우는 것만으로는 충분하지 않아요. 토큰 행을 지우면 감사 기록도 같이 사라지므로, 상태를 바꾸는 편이 좋아요. 이것도 설계 판단이에요.

취소도 조건부로 해요. `WHERE status = 'pending'`을 걸면, 수락과 취소가 동시에 들어와도 한쪽만 행을 바꿔요. 이미 수락된 초대는 취소할 수 없어요. 이때는 멤버를 내보내는 흐름으로 따로 처리해요.

## 권한 기록과 재검증 — 초대 시점과 수락 시점

초대 행에는 부여할 권한을 기록해요. 하지만 수락할 때 그 권한을 그대로 믿으면 안 돼요. 초대한 뒤 초대한 사람의 권한이 줄었을 수 있어요.

OWASP Authorization 치트시트는 접근 제어 검사를 요청마다 대상과 기능에 맞춰 하라고 설명해요. 권한은 업무에 필요한 최소만 주라고도 설명해요. 이 원칙을 수락 시점에 적용하면 다음처럼 돼요.

| 확인 시점 | 확인 내용                                      | 결과                                          |
| --------- | ---------------------------------------------- | --------------------------------------------- |
| 초대 발송 | 초대한 사람이 부여할 권한을 가지고 있는지      | 권한이 없으면 발송을 막아요                   |
| 수락      | 초대한 사람의 현재 권한이 기록된 권한 이상인지 | 줄었으면 거절하거나 멤버로 낮춰 들어가게 해요 |

시뮬레이터의 "초대자 권한 박탈 뒤 수락"이 이 상황이에요. 재검증을 끄면 관리자 권한으로 들어가요. 초대한 사람은 이미 멤버인데도요. 이 차이가 권한 재검증이 필요한 이유예요. 권한 모델을 고르는 세부는 [인가 · 객체 수준 권한](/m/authorization)에서 다뤄요.

## 좌석 제한과 남발 방지 — 수락 안에서 좌석 세기와 발송 한도

유료 플랜에는 좌석 수가 있어요. 좌석을 세는 쿼리와 멤버를 추가하는 쿼리가 떨어져 있으면, 동시 수락 두 번이 둘 다 자리가 남았다고 보고 좌석을 넘길 수 있어요. 좌석을 세는 값과 멤버 추가를 조건부 갱신이나 잠금으로 묶는 편이 좋아요. 트랜잭션과 잠금의 세부는 [트랜잭션 · 락 · 데드락](/m/transactions)에서 다뤄요. 플랜 변경과 해지는 [구독 결제](/m/subscription-billing)에서 다뤄요.

초대 남발은 발송 한도로 막아요. GitHub 문서는 조직 초대를 24시간에 50건으로 제한하고, 조직이 한 달을 넘었거나 유료 플랜이면 500건으로 제한한다고 설명해요. 한도의 알고리즘은 [레이트 리밋 알고리즘](/m/rate-limiting)에서 다뤄요.

## 초대 메일 발송 — 초대 행 생성과 발송 분리

초대 행을 만드는 일과 메일을 보내는 일을 나눠요. 메일 서버가 느리거나 실패해도 초대 행은 남아야 해요. 발송이 실패하면 초대 행을 다시 발송할 수 있어야 해요. 발송 상태를 추적하는 방법은 [트랜잭션 메일](/m/transactional-email)에서 다뤄요.

메일에 들어간 링크가 로그나 Referer에 남지 않게 해야 해요. 토큰을 로그에 찍으면 DB에 해시만 둔 의미가 줄어요. [민감 정보 누출](/m/sensitive-data)에서 URL과 로그에 남는 값을 다뤄요.

## FE 체크 포인트 — 수락 결과 문구와 버튼

- 거절 이유를 나눠서 보여 주세요. 취소, 만료, 다른 계정, 이미 수락됨, 권한 변경을 구분하면 사용자가 다음 행동을 알 수 있어요.
- 문구마다 다음 행동을 한 문장으로 붙이세요. 예를 들어 "초대가 취소됐어요. 초대한 사람에게 다시 요청하세요."처럼 쓰세요.
- 다른 계정 문구에는 대상 이메일 전체를 적지 마세요. 일부만 가리는 편이 좋아요.
- 수락 버튼은 요청 중에 비활성화하세요. 서버가 멱등하게 처리해도, 연타는 불필요한 요청을 만들어요.
- 성공 응답을 받으면 팀 목록을 다시 불러오세요. 멤버 목록을 클라이언트에서 임의로 추가하지 마세요.

## 시뮬레이터 안내

시뮬레이터에서 초대 방식, 초대에 적을 권한, 사건, 방어 다섯 가지를 고르세요. 사건은 정상 수락, 다른 계정으로 수락, 링크 유출 뒤 제3자 수락, 취소 뒤 수락, 만료 뒤 수락, 동시 수락 두 번, 초대자 권한 박탈 뒤 수락 중 하나예요.

결과로 수락 요청마다 성공과 거절, 그리고 팀 멤버 목록 변화를 볼 수 있어요. 이 시뮬레이터는 순수 모델이에요. 동시 수락은 두 요청을 한 줄로 세워서 처리한다고 가정해요. 실제 DB의 잠금 시간은 다루지 않아요.

## 정리 — 토큰 · 방식 · 수락 검증 · 상태 갱신 · 권한 재검증

- 초대 토큰은 암호학 난수로 만들고, 만료와 1회 사용을 둬요. 저장은 해시로 해요.
- 이메일 지정 초대는 로그인 이메일과 대상이 맞을 때만 수락해요. 공유 링크는 유출되면 누구나 수락할 수 있어요.
- 수락과 취소는 `pending` 조건이 붙은 UPDATE로 처리해요. 0행이면 이유를 읽어 응답을 나눠요.
- 취소는 상태를 바꿔서 이미 보낸 링크도 즉시 무효로 만들어요.
- 수락할 때 초대한 사람의 현재 권한으로 기록된 권한을 다시 확인해요.

시뮬레이터에서 "재검증"과 "1회 사용"을 하나씩 끄고 사건을 바꿔 보세요. 어떤 방어가 빠졌을 때 누가 들어가는지 확인해 보세요.
