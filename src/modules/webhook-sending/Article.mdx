주문이 결제 완료되면 고객 서버에 "결제 완료" 이벤트를 웹훅으로 보내야 해요. 고객 서버는 500을 내기도 하고, 응답이 느리기도 하고, 잠깐 끊기기도 해요. 이때 우리 서버가 무엇을 하는지가 이 글의 주제예요. 받는 쪽의 서명 검증과 중복 처리는 [웹훅 수신](/m/webhook-receiving) 글에서 다뤘어요. 여기서는 보내는 쪽만 봐요.

아래 시뮬레이터에서 고객 A 서버의 상태와 발송 설정을 바꿔 보세요. 고객 B 서버는 늘 정상이에요. A의 실패가 B의 발송까지 밀어내는지 확인할 수 있어요.

## 발송 흐름 — 저장 뒤 비동기 발송

이벤트를 보내는 가장 흔한 방법은 이벤트를 먼저 DB에 저장하고, 발송은 뒤에서 하는 것이에요. [microservices.io](https://microservices.io/patterns/data/transactional-outbox.html)의 트랜잭셔널 아웃박스 (transactional outbox) 패턴은 비즈니스 데이터를 바꾸는 같은 트랜잭션 안에서 OUTBOX 테이블에 메시지를 먼저 쓰고, 그다음 메시지 브로커로 발행한다고 설명해요. 우리 쪽에서는 발송 워커가 이 테이블을 읽어 고객 서버로 보내는 구조로 볼 수 있어요.

그래서 큐 방식에서는 주문 요청이 고객 서버의 응답을 기다리지 않아요. 큐의 전달 특성과 재처리는 [메시지 큐와 재처리](/m/message-queue) 글에서 자세히 다뤘어요.

발송 방식은 세 가지로 나눠 볼 수 있어요.

| 방식                      | 요청과의 관계                                    | 실패할 때                | 고르는 기준                                   |
| ------------------------- | ------------------------------------------------ | ------------------------ | --------------------------------------------- |
| 동기 발송                 | 이벤트를 만든 요청이 전송이 끝날 때까지 기다려요 | 재시도하지 않아요        | 이벤트가 적고, 잃어도 다시 만들 수 있을 때    |
| 큐 + 백오프               | 요청은 저장만 하고 바로 끝나요                   | 백오프로 다시 보내요     | 대부분의 경우 기본으로 고르는 편이 좋아요     |
| 큐 + 백오프 + 고객별 격리 | 위와 같아요                                      | 고객마다 따로 재시도해요 | 고객 수가 많고, 고객 서버의 응답 편차가 클 때 |

동기 발송은 가장 단순해요. 하지만 고객 서버의 응답 시간이 주문 요청 시간에 그대로 더해지고, 실패하면 남는 기록이 없어요. 시뮬레이터에서 동기 발송과 500 반복을 고르면 고객 A의 이벤트 6건이 재시도 없이 실패로 남는 것을 볼 수 있어요.

## 서명 — 메시지 id와 타임스탬프를 HMAC으로 묶기

고객 서버는 요청이 우리 서버에서 왔다는 것을 확인해야 해요. [Standard Webhooks 명세](https://github.com/standard-webhooks/standard-webhooks/blob/main/spec/standard-webhooks.md)는 서명 대상을 `msg_id.timestamp.payload`로 정하고, 비밀 키로 HMAC-SHA256을 계산한 뒤 결과를 base64로 인코딩한다고 설명해요. 요청 헤더는 `webhook-id`, `webhook-timestamp`, `webhook-signature` 세 개예요.

메시지 id와 타임스탬프를 서명에 넣는 이유는 재전송 때문이에요. 명세는 재시도할 때마다 시도의 타임스탬프가 갱신되지만, `webhook-id`는 실패를 여러 번 재시도해도 그대로라고 설명해요. 그래서 고객 서버는 이 id로 같은 이벤트를 한 번만 처리할 수 있어요.

비밀 회전도 서명 설계에 들어가요. 명세는 `webhook-signature` 헤더를 공백으로 구분한 목록으로 보내고, 같은 메시지를 현재 키와 이전 키로 함께 서명한다고 설명해요. 고객 서버는 둘 중 맞는 서명 하나만 있으면 통과해요. 명세는 이를 무중단 비밀 회전을 위한 장치라고 설명해요.

- **고객마다 비밀을 따로 둬요.** 명세는 대칭 서명 키가 엔드포인트마다 고유해야 한다고 설명해요.
- **발송과 수신 양쪽의 보안을 우리가 통제하지 못하면 비대칭 서명을 검토해요.** 명세는 그런 경우 비대칭 서명을 권한다고 설명해요.
- **GitHub도 같은 방식을 써요.** [GitHub 문서](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries)는 각 전달에 `X-Hub-Signature-256` 헤더로 HMAC-SHA256 해시를 붙인다고 설명해요.

## 재시도 — 2xx만 성공과 백오프, 재시도 기간 상한

명세는 2xx 응답만 성공으로 보고, 404나 500, 시간 초과, 연결 끊김은 모두 실패로 본다고 설명해요. 3xx도 실패로 봐요. 리다이렉트를 따라가면 보내는 쪽과 받는 쪽 모두에 부하가 생기니, 리다이렉트 대신 URL을 고치라고 권해요.

재시도 간격은 지수 백오프로 늘려요. 명세는 여러 날에 걸친 재시도 일정과 지수 백오프를 권하고, 재시도가 몰리지 않도록 jitter도 섞으라고 해요. 명세의 예시 일정은 즉시 보낸 뒤 5초, 5분, 30분, 2시간, 5시간, 10시간, 14시간, 20시간, 24시간 간격으로 재시도해요. 열 번째 시도는 첫 시도로부터 75시간 35분 뒤예요.

Stripe 문서는 라이브 모드에서 최대 3일 동안 지수 백오프로 재시도한다고 설명해요. GitHub 문서는 서버가 10초 안에 2xx로 응답하지 않으면 실패로 기록하고, 실패한 전달을 자동으로 다시 보내지는 않는다고 설명해요. 우리 서비스가 어떤 기간을 고를지는 고객 서버의 복구 시간과 이벤트의 중요도로 정하는 설계 판단이에요.

재시도 횟수와 기간에는 상한을 둬요. 상한이 없으면 고객 서버가 오래 죽어 있을 때 재시도 작업이 계속 쌓여요. 시뮬레이터의 큐 모드는 최대 6번 시도하고, 대기는 2^시도 (상한 16틱) 범위 안에서 무작위로 골라요. 틱의 길이와 횟수는 설명을 위한 예시예요.

응답 코드에 따라 다르게 처리하는 것도 명세에 있어요. 410 Gone은 고객 서버가 더 이상 웹훅을 받지 않겠다는 뜻이라 엔드포인트를 비활성화하고 보내지 말라고 해요. 429, 502, 504는 과부하 신호라 발송 속도를 낮추라고 해요. `Retry-After` 헤더가 있으면 그 값을 다음 시도 시각에 반영해요.

## 타임아웃 — 워커를 붙잡는 시간 정하기

발송 타임아웃은 워커가 한 건에 붙잡혀 있는 시간이에요. 명세는 소비자가 처리하고 응답할 시간을 주기 위해 요청 타임아웃을 15~30초 사이로 권장해요. GitHub는 10초 안에 2xx를 기대해요.

타임아웃을 짧게 줄이면 워커가 빨리 풀리지만, 느린 고객 서버가 정상이어도 실패로 기록돼요. 그래서 타임아웃 값은 우리 쪽 편의가 아니라 고객 서버의 처리 시간에 맞춰 정하는 편이 좋아요. 시뮬레이터의 3틱은 느린 응답이 타임아웃을 넘는 장면을 보이려는 예시예요.

## 실패 누적 — 엔드포인트 비활성화와 알림

고객 서버가 오래 실패하면 재시도만으로는 해결되지 않아요. 명세는 장기간 실패가 이어지면 이메일 같은 다른 채널로 고객에게 알리고, 그 엔드포인트로의 발송을 멈추는 것을 권장해요. Stripe 문서도 대상이 비활성화되면 이후 재시도를 막는다고 설명해요.

우리 설계에서는 연속 실패가 정해진 횟수에 닿으면 엔드포인트를 멈추고, 보류한 이벤트를 발송 기록에 남기고, 고객에게 알려요. 시뮬레이터의 자동 비활성화는 연속 실패 3번을 기준으로 해요. 이 횟수는 설계 판단이에요. 중요한 고객이면 더 늦게 멈추고, 실패가 짧게 끝나는 서비스라면 더 빨리 멈춰요.

잠깐 다운된 서버와 500을 계속 내는 서버는 구분해서 보는 편이 좋아요. 시뮬레이터에서 잠깐 다운을 고르면 연결 실패가 12틱 동안 이어져서 자동 비활성화가 먼저 걸려요. 다운이 연속 실패 3번 안에 끝났다면 멈추지 않고, 복구 뒤에 다시 보내요.

## 순서와 중복 — 순서 미보장과 이벤트 id 제공

Stripe 문서는 이벤트를 생성된 순서대로 전달하지 않는다고 설명해요. 같은 이벤트를 두 번 이상 받을 수 있다고도 설명해요. 그래서 고객 서버에 "생성 시각"으로 순서를 판단하지 말라고 권해요.

우리도 순서를 보장하지 않는다고 명시하는 편이 좋아요. 대신 이벤트마다 고정된 id와 이벤트가 생긴 시각을 같이 보내요. 명세의 페이로드 타임스탬프는 이벤트가 일어난 시각이라 전달 시각과 다를 수 있어요. 고객이 순서가 중요하면 이벤트 안에 객체의 현재 상태나 버전을 담아 보내는 방법을 안내해요.

순서를 강하게 보장하려면 고객마다 워커 하나가 한 줄로 보내야 해요. 그러면 느린 고객 하나가 그 고객의 큐 전체를 막아요. 순서와 격리는 서로 부딪히는 선택이에요.

## 수동 재전송 — 발송 기록과 같은 이벤트 id 유지

명세는 고객이 실패한 메시지 목록과 실패 이유를 볼 수 있게 하고, 특정 웹훅이나 범위를 수동으로 재전송할 수 있게 하라고 권해요. 장애가 길었다면 이 재전송으로 메시지를 놓치지 않고 복구할 수 있어요.

GitHub 문서는 지난 3일 안의 전달을 수동으로 재전송할 수 있다고 설명해요. Stripe 문서는 수동 재전송을 해도 자동 재시도가 취소되지 않고, 2xx를 받아도 마찬가지라고 설명해요. 같은 이벤트가 자동 재시도와 수동 재전송으로 두 번 도착할 수 있다는 뜻이에요. 그래서 고객 서버는 이벤트 id로 중복을 걸러야 해요.

우리 설계에서 수동 재전송은 같은 이벤트 id로 새 시도 한 건을 만드는 것이에요. 시도 번호와 응답 코드, 걸린 시간, 실패 이유를 발송 기록에 남겨요.

## 등록 URL 검증 — https 요구와 내부 주소 차단

고객이 입력한 URL로 우리 서버가 요청을 보내므로, 입력값을 믿으면 안 돼요. 공격자가 내부 주소를 등록하면 우리 서버가 내부 네트워크에 요청을 보내게 돼요. 이를 서버 측 요청 위조 (SSRF)라고 해요.

[OWASP 치트시트](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)는 호출할 대상이 정해져 있으면 허용 목록 (allowlist) 방식을 쓸 수 있다고 설명해요. 웹훅처럼 고객마다 주소가 다르면 허용 목록만으로는 부족하고, 주소를 검사하는 규칙을 함께 써야 해요. 이때 도메인 이름만 검사하면 부족해요. 치트시트는 도메인 허용 목록만으로는 DNS 재바인딩을 막지 못한다고 설명해요. 그래서 DNS로 해석된 IP를 허용된 네트워크와 대조하고, 검사한 IP로만 연결하라고 권해요. 재시도와 대체 경로에도 같은 정책을 적용해야 해요.

명세는 내용에 따라 모든 웹훅 엔드포인트를 HTTPS로 받는 편이 좋다고 설명해요. 등록할 때 https가 아니면 막고, 내부 주소로 해석되는 URL도 막아요. DNS 결과는 바뀔 수 있으니 등록 때 한 번 검사하고 끝내지 않고, 발송할 때도 다시 검사하는 편이 안전해요.

## 고객 격리 — 엔드포인트별 큐와 동시성 한도

발송 워커를 고객 모두가 함께 쓰면 느린 고객 하나가 전체를 막아요. 시뮬레이터에서 큐 + 백오프를 고르고 고객 A를 느림으로 바꾸면 고객 B의 발송이 여러 틱 밀리는 것을 볼 수 있어요.

격리는 이 문제를 줄이는 설계예요. 고객마다 큐를 나누고, 고객 한 명당 동시에 보내는 시도를 1건으로 제한해요. 워커 풀 전체는 여전히 공유하지만, 느린 고객이 워커를 독점하지는 못해요. [장애 격리 — 서킷 브레이커와 부분 응답](/m/graceful-degradation) 글에서 다룬 벌크헤드 (bulkhead) 패턴과 같은 발상이에요. 이 값들은 설계 예시예요. 실제 한도는 워커 수와 고객 규모에 맞춰 정해요.

격리를 켜면 고객 B의 이벤트는 생성된 뒤 1틱 안에 나가요. 대신 고객 A의 실패 이벤트는 A 큐 안에서 천천히 처리돼요.

## FE 체크 포인트 — 등록 검증과 전송 기록 화면

- **등록할 때 검증 결과를 바로 보여 주세요.** https가 아니거나 내부 주소로 해석되면 저장을 막고, 이유를 한 줄로 알려 주세요.
- **전송 기록을 목록으로 보여 주세요.** 이벤트 id, 생성 시각, 시도 횟수, 마지막 응답 코드, 상태(대기 · 성공 · 포기 · 보류)를 나란히 두면 고객이 원인을 스스로 찾을 수 있어요.
- **다시 보내기 버튼은 연타를 막으세요.** 누르면 같은 이벤트 id로 새 시도가 생기니, 응답을 기다리는 동안 버튼을 잠가 두세요. 연타로 시도가 쌓이는 문제는 [장애 격리 — 서킷 브레이커와 부분 응답](/m/graceful-degradation) 글에서 다뤘어요.
- **멈춘 엔드포인트는 이유와 재활성화 경로를 보여 주세요.** 자동으로 멈춘 이유와 마지막 성공 시각, 그리고 고객이 확인한 뒤 다시 켤 수 있는 버튼이 있어야 해요.

## 시뮬레이터 — 엔드포인트 상태와 발송 설정 조합

시뮬레이터는 고객 A 서버의 상태(정상, 느림, 500 반복, 잠깐 다운)와 발송 설정(동기, 큐 + 백오프, 격리, 자동 비활성화)을 골라요. 틱 슬라이더를 움직이면 그 시점의 대기 · 전송 중 · 성공 · 포기 · 보류 수를 볼 수 있어요. 1틱은 1분이라고 가정했어요.

다음 네 조합을 비교해 보세요.

1. 동기 발송 + 500 반복: 재시도 없이 이벤트가 실패로 남아요.
2. 큐 + 백오프 + 느림: 고객 B의 발송이 밀려요.
3. 큐 + 백오프 + 격리 + 느림: 고객 B는 제때 나가고, A는 천천히 실패해요.
4. 자동 비활성화 + 500 반복: 시도 횟수가 줄고, 보류한 이벤트가 남아요.

## 정리 — 저장 후 발송, 서명, 백오프, 격리, 멈춤 결정

이벤트는 저장하고 비동기로 보내요. 서명에는 메시지 id와 타임스탬프를 넣고, 비밀은 고객마다 따로 둬요. 재시도는 2xx만 성공으로 보고, 지수 백오프와 기간 상한을 둬요. 순서는 보장하지 않고 이벤트 id를 줘요. 고객 워커는 나눠서 느린 고객이 다른 고객을 막지 않게 해요. 계속 실패하면 멈추고 알려요. 수동 재전송은 같은 이벤트 id로 기록을 남겨요.
