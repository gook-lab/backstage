관리자 화면에서 "정산 실행" 버튼을 눌렀는데 화면이 몇 분째 돌고 있어요. 응답은 오지 않고, 탭을 닫아도 될지 모르겠어요. 이런 작업은 요청 하나 안에서 끝나지 않아요.

이 글은 긴 작업을 서버에서 어떻게 돌리고, 중간에 실패해도 이어 하고, 두 번 돌지 않게 막는지 정리해요. 화면이 무엇을 보여 줘야 하는지도 함께 다뤄요.

아래 시뮬레이터에서 정산 건수, 청크 크기, 실패 지점, 재시작 방식을 바꿔 보면 중복 정산이 언제 생기는지 직접 볼 수 있어요. 숫자는 시드로 정한 예시이고, 실제 서비스의 수치가 아니에요.

## 긴 작업 — 요청 대신 작업 리소스로 응답하기

HTTP 요청 하나에 몇 분짜리 일을 넣으면 여러 곳에서 문제가 생겨요. 브라우저 탭을 닫으면 응답을 받을 곳이 없고, 중간에 있는 장비가 연결을 끊을 수도 있어요. 같은 요청을 다시 보내면 정산이 또 시작될지도 몰라요.

그래서 서버는 작업을 리소스로 만들고, 요청에는 "받았어요"만 돌려줘요. RFC 9110은 202 (Accepted)를 "요청이 처리를 위해 받아들여졌지만 처리는 끝나지 않았다"는 뜻으로 정의해요. 응답의 표현은 요청의 현재 상태를 설명하고, 상태를 볼 수 있는 모니터를 가리키면 좋다고 권해요.

202는 작업이 성공했다는 뜻이 아니라는 점이 중요해요.

예시 응답은 이래요. 이 필드 이름은 설계 예시이고, 표준이 정한 형식이 아니에요.

```json
{
  "id": "job_8f2",
  "status": "running",
  "progress": { "done": 420, "total": 1000 },
  "statusUrl": "/admin/jobs/job_8f2"
}
```

화면은 `statusUrl`을 주기적으로 조회해서 진행률을 갱신해요. 서버가 다시 시도 전 대기 시간을 알려 주고 싶으면 `Retry-After` 헤더를 쓸 수 있어요. RFC 9110은 이 헤더를 클라이언트가 다시 시도할 수 있는 시점을 알려 주는 용도로 정의해요.

메시지 큐 글은 작업을 큐에 넣고 여러 워커가 가져가는 전달 방식을 다뤄요. 이 글은 그 위에서 작업의 진행 상태를 어떻게 남기고, 실패했을 때 어디서 다시 시작하는지에 집중해요.

## 대량 처리 — 청크 커밋과 체크포인트

백만 건을 한 트랜잭션으로 고치면 세 가지 문제가 생겨요.

- 긴 트랜잭션이 많은 행을 오래 잡고 있어요.
- 중간에 실패하면 전부 되돌아가요.
- 지금 몇 건째인지 알 수 없어요.

대안은 청크예요. N 건마다 커밋하고, 커밋할 때 체크포인트를 같이 남겨요. 체크포인트는 "여기까지 확실히 끝났다"는 마지막 건 번호예요.

| 청크 크기 | 장점                                | 주의                                                      |
| --------- | ----------------------------------- | --------------------------------------------------------- |
| 작음      | 락이 짧고, 실패 때 잃는 양이 적어요 | 커밋 횟수가 많아서 전체 시간이 길어져요                   |
| 큼        | 커밋 비용이 적어요                  | 실패 때 다시 처리할 건이 많고, 락이 길어요                |
| 한 덩어리 | 코드가 가장 단순해요                | 중간 체크포인트가 없어서 실패하면 처음부터 다시 해야 해요 |

청크 크기는 정답이 없어요. 시뮬레이터에서 청크를 10 건으로 줄이면 총 처리 시간이 늘고, 500 건으로 키우면 실패 때 되돌릴 양이 늘어요. 어느 쪽을 택할지는 락이 얼마나 길어도 되는지, 실패를 얼마나 자주 겪는지에 따라 정해요.

## 재시작 지점 — 커밋 이후만 다시 처리하기

청크 중간에 워커가 죽으면 어떻게 될까요? 커밋하지 않은 부분은 DB에서 "안 한 일"이에요. 그런데 정산 송금이나 외부 API 호출은 이미 나갔을 수 있어요. DB는 되돌아가도 외부 세계는 되돌아가지 않아요.

재시작 방식은 두 가지예요.

| 방식           | 다시 처리하는 범위    | 결과                                               |
| -------------- | --------------------- | -------------------------------------------------- |
| 처음부터 다시  | 건 0부터 전부         | 시간이 가장 오래 걸리고, 멱등이 없으면 중복이 커요 |
| 체크포인트부터 | 마지막 커밋 뒤의 건만 | 중복은 커밋 전 부분으로 줄어요                     |

건 번호는 0부터 세요. 시뮬레이터의 기본 설정은 정산 대상 1,000 건, 청크 100 건, 55% 지점에서 워커가 죽는 상황이에요.

체크포인트 500은 건 0부터 499까지 커밋됐다는 뜻이에요. 멱등 처리를 끄고 체크포인트부터 이으면 건 500부터 549까지 50 건이 두 번 나가요.

같은 상황에서 처음부터 다시 돌리면 실패 전 550 건이 모두 두 번 나가요. 이 숫자는 이 시뮬레이터 설정에서 나온 결과일 뿐이에요.

## 재실행 — 멱등 처리로 건너뛰기

중복을 줄이는 근본 방법은 같은 건을 두 번 처리해도 효과가 한 번과 같게 만드는 거예요. RFC 9110은 여러 번 보내도 서버에 의도한 효과가 한 번 보낸 것과 같은 메서드를 멱등하다고 정의해요. 배치는 메서드가 아니라 건 단위로 같은 성질을 만들어야 해요.

건마다 정산 키를 정해요. 예를 들어 "정산 기간 + 판매자 + 주문 번호" 같은 조합이에요. 처리 전에 이 키가 이미 처리됐는지 확인하고, 처리한 기록을 같은 키로 남겨요.

여기서 cart-stock 글과 같은 함정이 있어요. "확인하고 나서 기록하기"를 두 단계로 나누면 두 실행이 둘 다 "아직 안 했다"고 볼 수 있어요.

키를 유일 제약(UNIQUE)으로 두고 한 번에 기록하면 두 번째 기록이 충돌로 막혀요. 결제 쪽의 멱등성 키 설계는 [결제 멱등성 사례](/m/payment-idempotency)에서 더 자세히 다뤄요.

외부 정산 API가 멱등 키를 받는다면, 같은 키로 다시 불러도 한 번만 적용되는지 문서에서 확인해야 해요. 키를 지원하지 않으면 배치 쪽에서 건너뛰기를 책임져야 해요.

시뮬레이터에서 멱등 처리를 켜면 같은 건이 두 번 나가지 않아요. 대신 이미 처리된 건을 다시 보는 횟수, 곧 "다시 본 건수"가 늘어요. 건너뛰기에도 비용이 있어요.

## 동시 실행 — advisory lock과 SKIP LOCKED 고르기

관리자가 버튼을 두 번 누르거나 워커가 두 대 뜨면, 두 실행이 같은 건을 집을 수 있어요. 멱등이 없으면 중복이 바로 생겨요. 멱등이 있어도 동시에 돌면 같은 자원을 두고 경쟁해서 불필요한 호출이 늘어요. 그래서 "같은 배치는 한 번에 하나만"을 서버가 보장해야 해요.

PostgreSQL은 애플리케이션이 뜻을 정하는 락인 advisory lock을 제공해요. 공식 문서에 따르면 세션 수준 락은 명시적으로 풀거나 세션이 끝날 때까지 유지돼요. 트랜잭션 수준 락은 트랜잭션이 끝나면 자동으로 풀려요.

그리고 `pg_try_advisory_lock`은 잠글 수 없으면 기다리지 않고 false를 돌려줘요. 두 번째 실행이 false를 받으면 바로 끝내면 돼요.

락은 세션 수준으로 잡으면 워커가 죽었을 때 세션이 끝나면서 풀려요. 그래서 재시작한 워커가 락을 얻을 수 있어요. 반대로 트랜잭션이 롤백돼도 세션 수준 락은 남는다는 점도 문서에 있어요. 락 획득과 해제를 짝으로 설계해야 하는 이유예요.

여러 워커가 작업을 나눠 가져가야 한다면 다른 도구가 맞아요. `FOR UPDATE SKIP LOCKED`는 이미 잠긴 행을 건너뛰어요. 문서는 이 방식이 불일치한 조회를 준다고 설명하고, 일반적인 작업보다 큐처럼 쓰는 테이블에서 락 경합을 피하는 용도에 맞다고 설명해요. 정산 한 건이 한 워커에만 가야 하는 구조라면 이 방식이 잘 맞아요.

| 방법                   | 적합한 경우                     | 주의                                                        |
| ---------------------- | ------------------------------- | ----------------------------------------------------------- |
| advisory lock (try)    | 같은 배치 종류를 하나만 돌릴 때 | 락 이름을 팀이 정해서 공유해야 해요                         |
| FOR UPDATE SKIP LOCKED | 여러 워커가 건을 나눠 가질 때   | 불일치 조회를 감안해야 해요. 건별 상태를 함께 갱신해야 해요 |

시뮬레이터에서 락을 끄고 두 번째 실행을 켜면 같은 건이 다시 나가요. 락을 켜면 두 번째 실행은 거절돼요.

## 스케줄 실행 — 기준 시각만 먼저 정하기

매일 밤 자동으로 도는 정산은 cron 같은 스케줄러가 시작해요. 이때 "자정"이 어느 시간대의 자정인지 먼저 정해야 해요. 서머타임을 쓰는 지역에서는 같은 시각이 두 번 오거나 아예 건너뛸 수 있어요.

시간대와 날짜 경계의 문제는 이 글에서 깊이 다루지 않아요. 정산 기간을 어떤 시각으로 자를지는 배치를 설계할 때 문서로 먼저 적어 두세요.

## 대량 UPDATE — 서비스 트래픽과 나눠 쓰기

정산 배치가 주문 테이블을 크게 고치면, 그 시간 동안 같은 행을 쓰는 주문 요청이 락을 기다려요. 배치는 조용히 도는데 사용자에게는 결제가 느려진 것처럼 보여요.

완화 방법은 대부분 청크와 같은 방향이에요. 청크를 작게 하고, 청크 사이에 짧게 쉬고, 부하를 보면서 속도를 조절해요. 트래픽이 적은 시간에 돌리는 것도 방법이에요.

스키마를 바꾸면서 기존 행을 채우는 백필도 같은 문제를 겪어요. [스키마 마이그레이션 사례](/m/schema-migration)의 백필 절을 함께 보면 좋아요. 여기서 말하는 숫자는 예시일 뿐이고, 테이블 크기와 부하에 맞춰 정해요.

## 금액 계산 — 정수 최소 단위로 더하기

정산은 금액을 더하고 나눠요. JavaScript의 Number는 64 비트 부동소수점이에요. MDN에 따르면 정수는 -(2^53 - 1)부터 2^53 - 1 까지만 정확하게 나타낼 수 있고, 그 이상의 산술은 반올림될 수 있어요.

원화는 최소 단위가 1 원이니 정수 원으로 계산하는 편이 안전해요. 수수료율 3.3%는 소수점 대신 정수로 바꿔요. 예를 들어 1/10000 단위인 330을 쓰면 이렇게 계산해요.

```ts
// 예시: 수수료율 3.3%를 1/10000 단위(330)로 바꿔 정수로 계산해요
const fee = Math.floor((amountWon * 330) / 10000);
```

버림, 반올림, 올림 중 무엇을 쓸지는 정책이에요. 코드에서 정해 두고 문서에 적어야 나중에 돈이 맞지 않을 때 원인을 찾을 수 있어요. FE도 금액을 정수 원으로 받고, 표시할 때만 천 단위 구분을 붙여요.

## FE 화면 — 진행률 · 취소 · 중복 실행 막기

정산 화면은 세 가지를 보여 줘야 해요.

첫째, 진행률이에요. 서버가 준 처리 건수와 전체 건수로 보여 줘요. 퍼센트만 보여 주면 정산이 멈췄는지 느리게 가는지 구분하기 어려워요. 진행률이 오래 멈춰 있으면 워커가 살아 있는지부터 확인해요.

둘째, 취소 버튼의 의미예요. 취소는 "지금부터 새 건을 가져가지 않겠다"는 요청이에요. 이미 나간 정산은 되돌리지 않아요. 그래서 상태는 바로 취소됨이 아니라 취소 중을 거쳐 취소됨으로 바뀌고, 화면에는 취소 전에 끝난 건수를 함께 보여 줘요.

셋째, 중복 실행을 막는 방법이에요. 버튼은 작업이 진행 중이면 비활성화하고, 서버도 락으로 두 번째 실행을 거절해야 해요.

이미 같은 작업이 돌고 있다는 응답은 RFC 9110의 409 (Conflict)로 보낼 수 있어요. RFC 9110은 409를 대상 자원의 현재 상태와 충돌해서 요청을 끝낼 수 없을 때 쓰고, 사용자가 충돌을 풀고 다시 보낼 수 있는 경우에 맞다고 설명해요.

화면을 닫아도 작업은 서버에서 계속 돌아요. 그래서 화면에는 "창을 닫아도 정산은 계속돼요. 진행 상황은 이 페이지에서 다시 볼 수 있어요" 같은 안내가 필요해요. 사용자가 작업이 사라졌다고 오해하고 다시 누르면 중복 실행으로 이어질 수 있어요.

응답에서 확인할 신호는 이래요.

- 202와 상태 주소를 받으면 폴링을 시작해요.
- 상태가 `failed`이면 마지막 체크포인트와 재시도 버튼을 보여 줘요.
- 409이면 "이미 진행 중이에요"를 보여 주고 기존 작업으로 이동하게 해요.

## 시뮬레이터 안내

시뮬레이터에서 다음 순서로 바꿔 보세요.

1. 기본 설정: 체크포인트부터 이어서, 멱등 켜짐, 락 켜짐. 중복 정산은 0 건이에요.
2. 멱등 처리를 끄면: 커밋 전 50 건이 두 번 나가요.
3. 2번 상태에서 재시작 방식을 처음부터로 바꾸면: 실패 전 550 건이 모두 두 번 나가요.
4. 멱등을 켠 채 락을 끄고 두 번째 실행을 켜면: 중복은 없고, 이미 처리된 건을 다시 본 횟수가 늘어요. 멱등을 끈 채 같은 조작을 하면 같은 건이 여러 번 나가요. 락을 켜면 두 번째 실행은 거절돼요.
5. 청크 크기를 10으로 줄이면: 총 처리 시간이 늘어나요.

멱등과 락은 서로 대신하지 못해요. 락은 동시에 도는 실행을 막고, 멱등은 재실행에서 같은 건을 다시 처리하지 않게 해요. 배치를 설계할 때는 둘 다 가져야 해요.
