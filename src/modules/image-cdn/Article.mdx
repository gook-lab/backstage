원본 이미지를 내려받아 CSS로 줄이면 화면에서는 작아 보여도 전송량은 원본 그대로예요.

이 글은 화면에 맞는 변형을 만들고 브라우저가 고르게 하는 방법, 캐시 키에 무엇을 넣을지, 해시 파일 이름과 immutable로 얼마나 길게 캐시할지, 무효화와 원본 요청이 만드는 비용을 다뤄요. 아래 시뮬레이터에서 기기와 변형을 바꾸면 받는 파일과 캐시 결과가 어떻게 달라지는지 바로 확인할 수 있어요.

## 증상 — CSS로 줄인 이미지도 원본 크기로 내려받기

가로 2400px 원본을 CSS로 375px에 맞춰 보여 주면, 화면에는 작게 보여도 네트워크로는 원본 전체를 받아요. 파일 크기를 정하는 것은 화면 표시 크기가 아니라 파일 자체예요.

MDN은 srcset이 브라우저가 고를 수 있는 이미지의 집합과 각 이미지의 크기를 정한다고 설명해요. 원본 한 장만 주면 브라우저가 고를 수 있는 파일이 하나뿐이에요.

## 크기별 변형 — 원본 대신 화면에 맞는 파일 미리 만들기

원본에서 너비별 변형을 미리 만들어 두면 작은 화면은 작은 파일을 받아요. 형식도 함께 바꿀 수 있어요. MDN은 WebP와 AVIF가 압축률이 더 좋지만 지원 범위가 더 좁다고 설명해요. AVIF를 쓸 때는 지원 범위가 넓은 형식으로 폴백을 두라고 권해요.

변형 너비는 기기 종류가 아니라 화면 너비 구간과 DPR로 정하는 경우가 많아요. 몇 개를 둘지는 설계 판단이에요. 너무 많으면 만들고 저장하는 비용이 늘고, 너무 적으면 가장 가까운 변형도 크게 받아요.

## srcset · sizes — 브라우저가 기기에 맞는 변형을 고르게 하기

sizes는 이미지가 화면에서 차지하는 너비를 알려 줘요. 브라우저는 슬롯 너비에 DPR을 곱해 이상적인 픽셀 너비를 정하고, 같은 크기가 없으면 그보다 큰 첫 이미지를 골라 줄여서 보여 줘요. MDN은 이 과정이 이미지를 내려받기 전에 일어난다고 설명해요.

다만 HTML 표준은 후보 중 무엇을 고를지 브라우저에 맡겨요. 아래 표는 이 규칙을 따랐을 때의 예시이고, 실제로 받은 파일은 Network 패널에서 확인해요.

| 기기                  | sizes 슬롯 | 이상적인 픽셀 너비 | 고르는 변형 (예시) |
| --------------------- | ---------- | ------------------ | ------------------ |
| 휴대폰 375px · DPR 3  | 100vw      | 1125px             | 1280w              |
| 태블릿 768px · DPR 2  | 50vw       | 768px              | 960w               |
| 노트북 1440px · DPR 1 | 고정 320px | 320px              | 320w               |

형식은 srcset에 넣지 않아요. 서버가 Accept 헤더로 응답을 고르는 방식을 MDN은 서버 주도 협상이라고 설명해요. 그래서 같은 URL이라도 기기마다 다른 형식이 나갈 수 있어요. 이 차이가 아래 캐시 문제를 만들어요.

형식을 HTML에서 고르게 하려면 `<picture>`의 source에 type을 두는 방법도 있어요. MDN은 브라우저가 type, srcset, media를 보고 고른다고 설명해요.

sizes를 실제 레이아웃과 다르게 적으면 브라우저는 틀린 슬롯으로 계산해요. 큰 파일을 받거나 흐린 파일을 받을 수 있어요. 레이아웃이 바뀌면 sizes도 같이 고쳐요.

## 캐시 키 — 크기와 형식을 키에 넣는 범위

RFC 9111은 저장된 응답을 재사용할 때 Vary에 적힌 요청 헤더 값을 비교한다고 정해요. 같은 URL이라도 Vary 값이 다르면 따로 저장돼요. Vary 값에 `*`가 있으면 어떤 요청과도 맞지 않아요.

반대로 키에 넣을 것을 빼면 캐시는 다른 크기나 형식을 같은 것으로 보고 돌려줘요. 시뮬레이터 기본값(요청 2,000건, 이미지 12장, 전체 슬롯, 변형 5개, AVIF · WebP · JPEG)에서 네 가지 키를 비교하면 이래요.

| 캐시 키                 | 적중률 | 원본 요청 | 잘못된 응답 |
| ----------------------- | ------ | --------- | ----------- |
| 경로만                  | 99%    | 12        | 1,321       |
| 크기만 (w)              | 98%    | 36        | 355         |
| 크기 + 형식 등급        | 98%    | 48        | 0           |
| 쿼리 전체 + Accept 원문 | 90%    | 192       | 0           |

경로만 쓰면 적중률이 가장 높아 보여요. 하지만 같은 이미지의 모든 크기가 한 키로 묶여서 처음 저장된 크기를 계속 돌려줘요. 적중률이 높아도 잘못된 응답이 많으면 쓸 수 없어요. 이 값은 시뮬레이션 결과이고, 실제 서비스의 수치가 아니에요.

크기만 쓰면 형식이 섞이는 기기에서 잘못된 응답이 나와요. AVIF를 읽는 기기와 JPEG만 읽는 기기가 같은 크기를 요청하면 같은 키로 묶이기 때문이에요. 형식을 협상하지 않는 설정이라면 크기만으로도 충분해요.

Accept 원문을 그대로 키에 넣으면 잘못된 응답은 없지만, 같은 형식을 받는 기기도 Accept 문자열이 달라서 키가 잘게 쪼개져요. 원본 요청이 네 배로 늘어요. 형식 등급으로 줄여 키에 넣는 편이 대부분의 경우 나아요. 이 부분은 설계 판단이에요. 쓰는 CDN이 Vary를 어떻게 다루는지는 그 CDN의 공식 문서로 확인해요.

## 장기 캐시 — 해시 파일 이름과 immutable

MDN은 cache-busting 패턴을 쓰는 리소스에 긴 max-age를 주면 immutable을 함께 써서 재검증을 피할 수 있다고 설명해요. immutable은 응답이 fresh 한 동안 바뀌지 않는다는 뜻이에요.

이 조건이 지켜질 때만 안전해요. 파일 이름에 내용 해시가 들어 있어서 내용이 바뀌면 URL도 바뀌어야 해요. 같은 URL에 새 내용을 덮어쓰면 immutable은 거짓말이 돼요. 그래서 해시 이름과 긴 캐시는 한 세트로 쓰고, 원본 파일 이름을 그대로 두는 경우에는 짧은 캐시와 재검증을 택하는 편이 안전해요. 이 역시 설계 판단이에요.

## 캐시 무효화 — URL 수만큼 드는 비용

해시 파일 이름을 쓰지 않으면 이미지를 바꿀 때 예전 URL을 모두 무효화해야 해요. 시뮬레이터 기본값에서 이미지 한 장에 필요한 URL은 변형 5개 × 형식 3개 + 원본 1개, 즉 16개예요. 12장이면 192개가 돼요.

해시 파일 이름을 쓰면 새 내용은 새 URL로 받아서 무효화 대상이 0개예요. 무효화 요청 수와 전파 시간은 쓰는 CDN마다 달라요. 무효화 API가 키 변형까지 지우는지도 CDN마다 달라서, 쓰는 서비스의 공식 문서에서 확인해요.

## 원본 요청 — 적중률과 origin 부하

캐시가 한 계층이라고 가정하면 원본 서버 요청 수는 캐시 미스 수와 같아요. 키가 더 잘게 나뉠수록 미스가 늘고, 원본 서버 요청도 늘어요. 키의 수는 처음 보는 조합의 수와 같아서, 요청이 적은 시간대에는 처음 미스가 대부분이 돼요.

이 시뮬레이터는 빈 캐시에서 시작해요. 그래서 요청 수가 적을수록 적중률이 낮게 나와요. 실제 부하는 트래픽과 캐시 수명, 콘텐츠가 바뀌는 빈도에 따라 달라요. 이 수치는 결정의 방향을 보여 주는 용도로만 봐요.

## 로딩 — lazy와 fetchpriority를 역할로 나누기

loading="lazy"는 이미지가 뷰포트 근처에 올 때까지 내려받기를 미뤄요. MDN은 이때 width와 height를 명시하라고 권해요. 그래야 이미지가 도착하기 전후로 레이아웃이 흔들리지 않아요.

fetchpriority는 이미지를 받을 때의 상대 우선순위를 알려 주는 힌트예요. web.dev는 LCP가 될 가능성이 높은 이미지에 fetchpriority="high"를 쓰라고 권해요. 같은 힌트를 두 장이 넘는 이미지에 쓰면 효과가 줄어요. 또 web.dev는 LCP 이미지를 lazy로 두지 말라고 경고해요.

그래서 첫 화면 히어로 이미지는 lazy를 빼고 fetchpriority="high"를 주고, 아래쪽 카드 이미지는 lazy를 주는 식으로 역할을 나눠요.

## FE 할 일 · 응답 신호

- 응답 헤더에서 Content-Type으로 실제 형식을 확인해요.
- Vary에 Accept가 들어 있는지 확인해요. 형식을 협상하는데 Vary가 없으면 캐시 문제를 의심해요.
- 긴 max-age와 immutable은 파일 이름에 해시가 있을 때만 붙여요.
- 개발자 도구 Network 패널에서 실제로 받은 이미지 크기와 너비를 확인해요. MDN은 Chrome과 Firefox의 네트워크 패널에서 어떤 이미지를 받았는지 볼 수 있다고 안내해요. 이때 캐시를 끄고 보는 것이 좋아요.
- 원본을 CSS로 줄이지 않고, 변형 목록과 sizes를 화면 레이아웃과 같이 관리해요.

## 시뮬레이터 안내

아래 시뮬레이터에서 기기, sizes 슬롯, 변형 너비, 형식, 캐시 키, 해시 파일 이름을 하나씩 바꿔 보세요. 받는 파일의 크기와 캐시 표가 함께 바뀌는 것을 볼 수 있어요. 요청 순서는 고정된 seed로 만들어서, 같은 설정이면 항상 같은 결과가 나와요. 파일 크기는 형식별 예시 계수로 계산한 값이에요. 실제 인코더 결과와는 다를 수 있어요.
