가입 화면에 인증번호 입력칸이 떴어요. 6자리 번호는 문자로 왔고, 화면에는 3분 타이머와 재전송 버튼이 있어요. 그런데 서버가 번호를 어떻게 저장하는지, 몇 번까지 틀려도 되는지는 화면에 보이지 않아요. 이 글은 번호가 만들어지고, 검증되고, 사라지기까지 서버가 하는 일을 따라가요. 그리고 FE가 타이머와 버튼, 오류 문구를 어떻게 맞춰야 하는지 정리해요.

글의 숫자는 예시예요. 공격자가 초당 20번 시도하고 10분 동안 공격한다고 가정해요. 기본값은 아래 시뮬레이터의 기본값과 같아요.

## 경우의 수 — 6자리 번호와 시도 한도

6자리 숫자는 000000부터 999999까지 100만 가지예요. 번호가 균등하게 뽑힌다면 추측 한 번에 맞힐 확률은 100만 분의 1이에요. 추측을 100번 하면 0.01%이고, 이 값은 경우의 수로 직접 계산한 결과예요.

OWASP MFA 치트시트는 OTP 구현에 엄격한 시도 한도를 두라고 설명해요. NIST SP 800-63B-4는 상한 100회를 정한 이유로, 6자리 십진수 OTP를 맞힐 가능성과 계정 복구의 필요를 함께 따졌다고 설명해요. 연속 실패는 한 인증기에서 최대 100회까지만 허용하고, 실패가 한도에 닿으면 그 인증기를 비활성화하라고 해요. 기관은 이보다 낮게 정할 수 있어요.

| 시도 한도         | 추측 가능 횟수          | 맞힐 확률 |
| ----------------- | ----------------------- | --------- |
| 5회               | 5번                     | 0.0005%   |
| 10회 (기본값)     | 10번                    | 0.001%    |
| 100회 (NIST 상한) | 100번                   | 0.01%     |
| 시도 한도 없음    | 3,600번 (3분 동안 전부) | 약 0.36%  |

한도가 없으면 3분 유효 시간 안에 초당 20번씩 3,600번을 추측할 수 있어요. 번호 길이보다 시도 한도가 먼저 정해져야 하는 이유예요.

NIST는 사용자가 값을 직접 입력하는 인증기에 최소 10번의 입력 기회를 주라고 설명해요. 그래서 기본값을 10회로 둬요. 5회는 이 권장보다 낮아요.

## 번호 저장 — 해시 · 만료 시각 · 시도 횟수

서버는 번호 자체보다 검증에 필요한 기록을 저장해요. 보통 사용자 식별자, 번호의 해시, 만료 시각, 실패 횟수, 사용 여부를 한 행에 둬요. 이 구성은 설계 판단이에요.

OWASP는 OTP를 장기 평문으로 저장하지 말고, 로그에 값을 남기지 말라고 설명해요.

해시를 쓰는 이유는 오프라인 공격을 막기 위해서가 아니에요. 6자리 번호는 경우의 수가 적어서, DB를 가진 공격자가 해시를 빠르게 맞힐 수 있어요. OWASP는 해시가 오프라인 공격에 강하지 않다고 설명해요. 해시의 역할은 로그나 DB가 잠깐 노출된 동안 피해를 줄이는 것이에요. 시도 한도와 짧은 만료가 여전히 주된 방어예요.

검증할 때는 실패 횟수를 올리고 한도를 넘었는지 한 번에 확인하는 편이 좋아요. 확인과 증가가 떨어져 있으면, 동시에 들어온 요청 여러 개가 같은 실패 횟수를 보고 모두 통과할 수 있어요. 동시 요청을 다루는 방법은 [트랜잭션 · 락 · 데드락](/m/transactions)에서 다뤄요.

## 만료와 재전송 — 이전 번호 무효화와 실패 횟수 유지

만료는 짧게 둬요. OWASP는 OTP에 짧은 유효 시간(TTL)을 두라고 설명해요. NIST는 아웃오브밴드 인증을 10분 안에 끝내지 않으면 무효로 보라고 설명해요. 3분은 이 범위 안에 있어요.

재전송은 새 번호를 만들고 이전 기록을 덮어쓰라고 OWASP는 설명해요. 이전 번호가 살아 있으면 공격자는 살아 있는 번호 수만큼 맞힐 기회가 늘어요.

실패 횟수도 중요해요. NIST는 인증 비밀을 새로 만든다고 실패 횟수를 초기화하면 안 된다고(SHALL NOT) 설명해요. 이 조항은 64비트보다 짧은 인증 비밀에 적용돼요. 6자리 번호는 약 20비트라서 여기에 해당해요.

| 재전송 정책                                                    | 추측 가능 횟수             | 맞힐 확률 |
| -------------------------------------------------------------- | -------------------------- | --------- |
| 실패 횟수 유지 · 이전 번호 무효화                              | 10번                       | 0.001%    |
| 실패 횟수 초기화 · 이전 번호 무효화                            | 100번 (발송 10건)          | 0.01%     |
| 실패 횟수 초기화 · 이전 번호 유지                              | 100번 (살아 있는 번호 6개) | 0.06%     |
| 실패 횟수 초기화 · 번호당 발송 한도 없음                       | 210번 (발송 21건)          | 0.021%    |
| 실패 횟수 초기화 · 간격 없음 · 발송 한도 없음 · 시도 한도 없음 | 12,020번 (발송 601건)      | 약 1.2%   |

표의 기본 조건은 시도 한도 10회, 재전송 간격 30초, 번호당 발송 10회예요. 재전송 때 실패 횟수가 초기화되면 번호를 새로 받을 때마다 추측 기회가 다시 생겨요. 그래서 실패 횟수 유지와 이전 번호 무효화가 같이 있어야 해요.

## 발송 남용 — 번호별과 IP별 한도

OWASP는 재설정 요청에 번호나 계정 단위 제한이 없으면, 공격자가 수신함(메일이나 SMS)을 쓸모없는 요청으로 채울 수 있다고 설명해요. 문자는 건마다 발송 비용이 들어요. 다만 비용 금액은 이 글에서 확인하지 않았으므로 건수로만 다뤄요.

한도는 두 축으로 나눠 거는 편이 좋아요. 설계 판단이에요.

- 번호별 한도와 재전송 간격: 한 사람에게 가는 발송을 묶어요.
- IP별 한도: 번호를 여러 개 바꿔 가며 보내는 공격을 묶어요.

| 번호별 한도 | IP별 한도    | 재전송 간격 | 발송 건수 (번호 10개) |
| ----------- | ------------ | ----------- | --------------------- |
| 10회 (기본) | 100회 (기본) | 30초        | 100건                 |
| 한도 없음   | 100회        | 30초        | 100건                 |
| 한도 없음   | 한도 없음    | 30초        | 210건                 |
| 한도 없음   | 한도 없음    | 없음        | 6,010건               |

NIST는 PSTN(문자와 음성)으로 보내는 아웃오브밴드 인증을 제한된(restricted) 인증기로 분류해요. 이 인증기를 쓰려면 조직이 위험을 평가하고 받아들여야 한다고 설명해요. 요청 제한 알고리즘과 429 응답은 [레이트 리밋 알고리즘](/m/rate-limiting)에서 다뤄요.

## 계정 존재를 드러내지 않는 응답 — 문구 · 코드 · 시간

발송과 재전송 요청의 응답은 계정이 있든 없든 같아야 해요. OWASP 인증 치트시트는 로그인, 비밀번호 재설정, 복구 모두에서 일반 오류 메시지를 쓰라고 설명해요. HTTP 응답 코드가 다르면 메시지가 같아도 계정 존재가 드러날 수 있다고도 설명해요.

응답 시간도 맞춰요. OWASP 비밀번호 찾기 치트시트는 응답 시간을 일정하게 하라고 설명해요. 비동기 호출을 쓰거나, 계정이 없을 때도 같은 처리 흐름을 따르라고 설명해요.

쿨다운 기록은 계정이 없는 주소에도 남겨요. 기록이 없으면 대기 여부가 계정 존재를 알려요. 이것도 설계 판단이에요. 메일 쪽 세부 문구는 [트랜잭션 메일](/m/transactional-email)에서 다뤄요.

## 검증 성공 뒤 — 번호 일회용과 짧은 토큰

NIST는 OTP를 유효한 동안 한 번만 받아들이라고 설명해요. 재사용을 막기 위해서예요. OWASP MFA 치트시트도 OTP를 단일 사용으로 만들고, 성공하면 무효화하라고 설명해요.

다음 단계, 예를 들어 비밀번호 설정 화면에서는 번호를 다시 쓰면 안 돼요. OWASP 비밀번호 찾기 치트시트는 번호 검증 뒤에 비밀번호 재설정만 허용하는 제한된 세션을 만들라고 설명해요. 이 세션이 다음 단계의 토큰 역할을 해요. 토큰의 수명과 저장 위치는 [로그인 유지 — 세션과 토큰](/m/auth-session-token)에서 다뤄요.

## 안전한 난수 — 서버에서 암호학적 난수로

번호는 서버에서 만들고, 암호학적으로 안전한 난수로 뽑아요. OWASP MFA 치트시트는 OTP를 암호학적으로 안전한 난수 생성기로 만들라고 권해요.

MDN은 Crypto.getRandomValues()가 암호학적으로 강한 난수를 채운다고 설명해요. Math.random은 암호용이 아닌 난수라고 설명해요.

```ts
// crypto.getRandomValues 를 제공하는 런타임에서 실행해요
const buf = new Uint32Array(1);
crypto.getRandomValues(buf);
const code = String(buf[0] % 1_000_000).padStart(6, '0');
```

2^32는 10^6으로 나누어떨어지지 않아서, 이 코드는 값이 아주 조금 치우쳐요. 치우침이 걱정되면 범위 밖 값을 버리고 다시 뽑는 방법을 써요. 이것도 설계 판단이에요.

## 이메일 링크 방식과 비교 — 입력 대 클릭

| 항목        | 번호 입력 (OTP)             | 링크 토큰                                                                     |
| ----------- | --------------------------- | ----------------------------------------------------------------------------- |
| 사용자 동작 | 화면에 번호 입력            | 메일 링크 클릭                                                                |
| 경우의 수   | 짧아서 시도 한도가 필수예요 | 충분히 길게 만들어 무차별 대입을 막아요                                       |
| 추가 방어   | 시도 한도와 짧은 만료       | 무차별 대입을 막는 요청 제한을 둬요 (OWASP)                                   |
| 노출 경로   | 화면 입력 중심              | 쿼리 문자열이 로그와 Referer에 남을 수 있어요                                 |
| 자세히      | 이 글                       | [트랜잭션 메일](/m/transactional-email) · [민감 정보 누출](/m/sensitive-data) |

OWASP 비밀번호 찾기 치트시트는 URL 토큰도 무차별 대입을 막는 요청 제한을 두라고 설명해요. 그래서 링크 방식이라고 시도 제한을 뺄 수는 없어요.

앱에서 보는 TOTP 코드는 서버가 번호를 보내지 않아서 발송 비용이 없어요. 대신 서버가 공유 비밀(시드)을 들고 있어야 해요. OWASP MFA 치트시트는 시드를 암호화해 보관하고, 검증할 때만 풀라고 설명해요. RFC 4226은 실패 횟수 한도를 매개변수 T로 두고, T번 실패한 뒤에는 서버가 그 사용자의 연결을 거부한다고 설명해요. RFC 6238은 네트워크 지연을 위해 시간 단계를 하나까지만 허용하라고 권해요.

## FE 체크 포인트 — 타이머와 버튼을 서버 값에 맞추기

- 타이머는 서버가 준 만료 시각으로 계산하세요. 화면에서 임의로 정한 3분을 기준으로 삼지 마세요.
- 재전송 버튼은 서버가 준 재전송 간격으로 막으세요. 화면에서 버튼을 풀어도 서버는 같은 간격을 요구해요.
- 남은 시도 횟수를 알려 주세요. NIST는 남은 시도 횟수와, 다음 시도까지 기다릴 시간을 알려 주라고 설명해요.
- 틀렸을 때 문구는 사실만 쓰세요. 예시 문구는 "번호가 맞지 않아요. 남은 시도는 3번이에요."예요. 계정이 있는지 없는지는 말하지 마세요.
- 검증이 성공하면 번호 입력칸을 비우고 다음 단계로 가세요. 번호를 저장하거나 로그에 남기지 마세요.
- 발송 요청이 진행 중일 때는 재전송 버튼을 막으세요. 연타하면 발송 한도를 빨리 써요.

## 시뮬레이터 안내

시뮬레이터는 공격 시나리오 하나와 서버 설정을 골라서, 추측 횟수와 발송 건수, 맞힐 확률을 계산해요.

- **무차별 대입**: 번호 하나에 계속 추측해요. 시도 한도와 만료 시간이 맞힐 확률을 정해요.
- **재전송 반복**: 재전송 때 실패 횟수를 초기화하는지, 이전 번호가 살아 있는지 바꿔 보세요.
- **문자 폭탄**: 번호별과 IP별 발송 한도를 바꿔 보세요. 추측은 하지 않아요.

계산은 단순화한 모델이에요. 번호는 균등하게 뽑히고 서로 독립이라고 가정해요. 수치는 감을 잡기 위한 예시예요.

## 정리 — 시도 한도 · 해시 저장 · 재전송 정책 · 발송 한도

- 6자리 번호는 100만 가지라서, 시도 한도가 첫 번째 방어예요. NIST는 상한을 100회로 두고, 입력 기회는 최소 10회를 권해요.
- 번호는 해시로 저장하지만, 해시는 오프라인 공격을 막지 못해요. 만료와 시도 한도가 주된 방어예요.
- 재전송할 때는 이전 번호를 무효화하고 실패 횟수는 유지해요.
- 발송은 번호별과 IP별 한도로 같이 묶어요.
- 응답은 계정 존재와 무관하게 문구, 코드, 시간을 맞춰요.
- 검증이 끝나면 번호를 일회용으로 만들고, 다음 단계는 짧은 토큰으로 넘겨요.

시뮬레이터에서 설정을 하나씩 바꿔 보세요. 어떤 값이 맞힐 확률을 가장 크게 바꾸는지 확인해 보세요.
