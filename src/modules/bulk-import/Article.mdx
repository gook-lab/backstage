엑셀로 만든 상품 1만 행 파일을 올리는 상황을 예로 들어요. 몇 행만 틀렸을 때 결과는 보통 두 가지 중 하나예요. 전부 실패해서 아무것도 안 들어가거나, 절반만 들어가고 어디가 틀렸는지 알 수 없어요.

이 글은 이 둘 사이에서 서버가 고를 수 있는 처리 방식과, 틀린 행을 사람이 고칠 수 있게 알려 주는 오류 형식을 정리해요.

아래 시뮬레이터에서 예시 CSV를 직접 고쳐 보면, 같은 파일을 세 방식으로 올렸을 때 저장되는 행과 거절되는 행이 어떻게 달라지는지 바로 확인할 수 있어요.

## 증상 — 한 행의 오류가 전체 결과를 바꾸는 경우

예시 상황이에요. 1만 행 중 세 행의 가격 칸이 비어 있어요. 서버가 첫 행부터 차례로 저장하다가 빈 칸에서 멈추면, 앞의 행은 들어갔고 뒤의 행은 안 들어간 상태가 돼요. 이 상태에서 화면이 "실패"라고만 보여 주면 사용자는 어디까지 들어갔는지 알 수 없어요.

처리 방식은 이 질문에 대한 답이에요. 오류가 났을 때 무엇을 저장하고, 무엇을 보고할지를 미리 정해야 해요.

## CSV 형식 — RFC 4180이 정한 칸과 줄 규칙

RFC 4180은 CSV 형식을 정리한 문서예요. 레코드를 줄바꿈(CRLF)으로 구분하고, 칸은 쉼표로 구분한다고 정리해요. 헤더 줄은 선택 사항이고, 있는지는 `header` 파라미터로 나타낸다고 설명해요.

함정은 세 가지예요.

- **따옴표와 쉼표.** 칸 안에 쉼표가 있으면 큰따옴표로 감싸야 해요. 칸 안의 따옴표는 따옴표 두 개로 써요. 예를 들어 `"잔 ""특별판"""`은 `잔 "특별판"`이에요.
- **칸 안의 줄바꿈.** 큰따옴표 안에서는 줄바꿈도 칸의 일부가 돼요. 줄 단위로 나누는 파서는 이 칸을 두 행으로 잘못 나눠요.
- **공백과 열 개수.** RFC 4180은 공백을 칸의 일부로 보고 무시하지 말라고 해요. 각 줄의 칸 수는 같아야 한다고도 해요(should).

RFC 4180은 Microsoft Excel처럼 큰따옴표를 아예 쓰지 않는 프로그램이 있다고도 적어요. 그래서 "엑셀이 저장한 파일"이 항상 같은 규칙을 따르지는 않아요.

빈 칸도 헷갈려요. PostgreSQL 문서는 CSV 형식에 NULL과 빈 문자열을 구분하는 표준 방법이 없다고 설명해요. 기본 설정에서 PostgreSQL은 NULL을 따옴표 없는 빈 칸으로, 빈 문자열을 `""`로 쓴다고 설명해요. 파일에서 빈 칸을 보면 "값이 없음"인지 "빈 문자열"인지 칸마다 확인해야 해요.

## 인코딩과 BOM — 바이트를 문자로 읽는 첫 단계

파일은 바이트 묶음이에요. 글자로 읽으려면 인코딩을 알아야 해요. MDN은 `Blob.text()`가 데이터를 UTF-8로 가정한다고 설명해요. UTF-8이 아닌 파일을 이 메서드로 읽으면 글자가 어긋날 수 있어요.

`TextDecoder`는 기본 인코딩이 utf-8이고, 인코딩 이름을 넘겨 다른 인코딩을 디코딩할 수 있어요. MDN은 UTF-8 · ISO-8859-2 · GBK 같은 인코딩을 예로 들어요.

디코더에는 두 속성이 있어요. `ignoreBOM`은 BOM을 무시하는지 나타내고, `fatal`은 오류 모드가 fatal인지 나타내요.

BOM은 파일 맨 앞의 보이지 않는 문자(U+FEFF)예요. BOM이 그대로 남으면 첫 열 이름이 `sku`가 아니라 BOM이 붙은 문자열로 읽혀서, 열 이름 검사가 실패할 수 있어요.

이 시뮬레이터의 파서는 BOM을 떼고 읽어요. 서버가 CSV를 직접 읽을 때도 인코딩을 명시하는 편이 좋아요. PostgreSQL `COPY`는 `ENCODING` 옵션으로 파일 인코딩을 지정할 수 있다고 설명해요.

## 처리 방식 — 전체 롤백 · 행별 부분 성공 · 검증 후 확정

세 방식의 차이는 저장되는 행과 보고되는 오류에 있어요.

| 방식           | 저장 결과                  | 보고되는 오류                          | 주의                                                             |
| -------------- | -------------------------- | -------------------------------------- | ---------------------------------------------------------------- |
| 전체 롤백      | 오류가 하나라도 있으면 0행 | 첫 오류 한 개. 뒤 행은 확인하지 않아요 | 고칠 때마다 다시 올려야 해요. 한 번에 여러 오류를 알 수 없어요   |
| 행별 부분 성공 | 맞는 행만 저장             | 틀린 행의 오류 전부                    | 파일이 반만 들어간 상태가 생겨요. 화면에 확정 여부를 알려야 해요 |
| 검증 후 확정   | 오류가 없을 때만 전부 저장 | 전체 오류(저장 전 검사)                | 검사 뒤 저장 전에 데이터가 바뀌면 검사 결과가 낡아요             |

전체 롤백은 한 트랜잭션으로 묶는 방식이에요. PostgreSQL 문서는 `BEGIN`과 `COMMIT`으로 묶은 안에서 `ROLLBACK`을 하면 그 안의 변경이 모두 취소된다고 설명해요.

트랜잭션 안에서 오류가 나면 트랜잭션은 중단 상태가 되고, `COMMIT`과 `ROLLBACK`을 뺀 명령은 거절된다고도 해요. 그래서 전체 롤백은 첫 오류에서 멈추고 전부 되돌리는 흐름으로 가요. 오류가 많으면 사용자가 한 번에 다 보기 어려워요.

행별 부분 성공은 행마다 따로 확정하는 방식이에요. 맞는 행은 들어가고, 틀린 행은 목록에 남아요. 맞는 행을 바로 쓸 수 있다는 장점이 있어요. 대신 반만 들어간 상태를 화면이 분명히 보여 줘야 해요.

검증 후 확정은 저장 전에 전체를 먼저 검사해요. 오류가 하나도 없을 때만 저장해요. 사용자는 오류 목록을 한 번에 보고 고칠 수 있어요.

검사와 저장이 떨어져 있으면 그 사이 데이터가 바뀔 수 있어요. 저장 단계에서 다시 확인하는 편이 좋아요. 이 판단은 [트랜잭션](/m/transactions) 글의 원자적 갱신 설명과 이어져요.

PostgreSQL 문서는 `COPY`가 기본적으로 오류를 만나면 명령이 실패한다고 설명해요. `ON_ERROR ignore`를 주면 오류 행을 버리고 계속하고, `stop`이 기본값이라고 해요. 다만 문서가 말하는 대상은 칸 값을 자료형으로 바꿀 때 생긴 오류예요. "오류 행 버리기"를 고르기 전에 어떤 오류가 걸러지는지 문서 범위를 먼저 맞춰 봐야 해요.

## 오류 보고 — 행 번호 · 열 이름 · 이유를 담은 형식

틀린 행을 고치려면 세 가지가 있어야 해요. 엑셀에서 찾을 수 있는 행 번호, 어느 칸인지 알려 주는 열 이름, 왜 틀렸는지 알려 주는 이유예요. 행 번호는 엑셀과 맞춰야 해요. 헤더가 1행이고 첫 데이터 행이 2행이에요.

예시 응답은 이래요. 형식의 바탕은 [API 오류 형식](/m/api-errors) 글과 [입력 검증](/m/input-validation) 글의 칸 위치 규칙이에요.

```json
{
  "committed": false,
  "rejected": [
    { "row": 3, "column": "price", "reason": "비어 있어요" },
    { "row": 6, "column": "sku", "reason": "2행과 같은 sku예요" }
  ]
}
```

이유 문구는 사람이 고칠 수 있게 쓰는 편이 좋아요. "잘못된 값"보다 "비어 있어요"나 "음수는 쓸 수 없어요"가 더 쓸모 있어요.

## 다시 올리기 — 업서트 키 기준의 고쳐 쓰기

사용자는 틀린 행을 고쳐서 같은 파일을 다시 올려요. 이때 행을 새로 넣기만 하면 맞는 행이 두 번 들어가요. 해결은 행을 식별하는 키를 정하고, 같은 키가 오면 기존 행을 고치는 것이에요.

PostgreSQL 문서의 `INSERT ... ON CONFLICT DO UPDATE`가 이 동작을 지정해요. 충돌을 볼 고유 인덱스를 `conflict_target`으로 고르고, 충돌하면 기존 행을 고쳐요.

문서는 오류가 없는 한 `ON CONFLICT DO UPDATE`가 INSERT 또는 UPDATE 중 하나의 결과를 원자적으로 보장한다고 설명해요. 이 키가 같은 파일 안에서 두 번 나오면 두 번째 행을 중복으로 거절하는 편이 좋아요. 시뮬레이터도 그렇게 해요.

업서트 키는 "같은 행을 가리키는 값"이어야 해요. 상품이면 sku가 맞고, 이름은 바뀔 수 있어서 키로 맞지 않아요.

같은 행을 두 번 넣지 않으려면 식별 키가 필요해요. 이 생각은 [결제 멱등성](/m/payment-idempotency) 글과 [트랜잭션](/m/transactions) 글의 멱등 재시도와 같아요.

## 큰 파일 — 청크 커밋과 진행률 (다른 글 링크)

1만 행을 한 트랜잭션으로 묶으면 락을 오래 잡아요. 큰 파일은 일정한 건수마다 커밋하고, 어디까지 끝났는지 체크포인트를 남기는 편이 좋아요. 이 판단과 재시작 지점은 [배치 작업](/m/batch-jobs) 글에서 자세히 다뤄요.

파일을 올리는 길 자체는 [파일 업로드](/m/file-transfer) 글에서 다뤄요. 처리가 길어지면 요청을 접수하고 상태 주소로 진행률을 보는 방식은 [백그라운드 작업](/m/background-jobs) 글의 202 응답과 상태 조회가 맞아요. 이 글에서는 행별 오류와 저장 방식만 다뤄요.

## 내보내기 — 수식 주입 방지 (CSV injection)

CSV 가져오기만 보면 안 돼요. 사용자 입력을 CSV로 내보내면 그 파일을 여는 스프레드시트가 수식을 실행할 수 있어요. OWASP는 셀이 `=`, `+`, `-`, `@`, 탭, CR, LF로 시작하면 수식으로 읽힐 수 있다고 설명해요. 전각 문자 `＝`, `＋`, `－`, `＠`도 일부 로케일에서 수식으로 읽힌다고 해요.

OWASP는 구분자와 따옴표도 함께 봐야 한다고 해요. 공격자가 쉼표로 새 칸을 만들고, 그 칸 맨 앞에 위험한 문자를 넣을 수 있기 때문이에요.

Excel에서 수식 실행을 안정적으로 막으려면 따옴표 안에서 탭 문자를 맨 앞에 붙이는 방식을 OWASP가 권해요. Excel에서 관찰된 방식이고 다른 스프레드시트에서는 다를 수 있다고 덧붙여요.

작은따옴표나 큰따옴표만 붙이는 완화책은 Excel에서 저장 뒤 다시 열면 믿기 어렵다고도 해요.

시뮬레이터의 `escapeCsvCell`이 이 방식을 따라요. 수식으로 읽힐 수 있는 첫 글자 앞에 탭을 넣고, 칸 전체를 큰따옴표로 감싸요.

## FE 체크 포인트

- 응답에서 `committed`를 먼저 확인해요. 확정 여부가 "저장됨"과 "저장 안 됨"을 가르는 첫 신호예요.
- 오류 목록은 행 번호를 누르면 그 행으로 이동하게 만들면 고치기 쉬워요.
- 롤백 응답에 "나머지 행은 확인하지 않았어요" 같은 안내가 있으면 그대로 보여 줘요. 사용자가 첫 오류만 고치면 끝났다고 여기지 않게 해요.
- 파일을 읽을 때 인코딩을 명시해요. 한글이 깨지면 `Blob.text()`가 UTF-8로 읽는다는 점부터 확인해요.
- 다시 올리기 버튼은 같은 파일을 여러 번 올려도 결과가 같게 만들어요. 업서트 키가 있는지 서버 응답의 `inserted`와 `updated`로 확인해요.

## 시뮬레이터 안내

예시 CSV에는 틀린 행이 네 개 있어요. 빈 가격, 음수 재고, 같은 sku 중복, 정수가 아닌 가격이에요. 처리 방식을 바꾸면 저장되는 행과 보고되는 오류가 어떻게 달라지는지 볼 수 있어요.

CSV 칸을 고쳐서 다시 올리면 업서트 키가 있을 때 행이 늘지 않는 것도 확인할 수 있어요.

숫자와 행은 감을 잡기 위한 예시예요. 실제 서비스의 파일 크기와 처리 시간은 다를 수 있어요.

## 정리 — 처리 단위 · 오류 형식 · 업서트 키 · 내보내기 이스케이프

- 대량 입력은 처리 단위를 먼저 정해요. 전체 롤백은 전부 아니면 전무이고, 행별 부분 성공은 맞는 행만 저장해요.
- 검증 후 확정은 오류가 없을 때만 저장해요.
- 어느 쪽이든 오류는 행 번호, 열 이름, 이유를 담아 보고해요.
- 다시 올리는 경우를 막으려면 업서트 키를 정해요.
- 내보내기에서는 수식으로 읽힐 수 있는 칸을 탭과 따옴표로 막아요.
