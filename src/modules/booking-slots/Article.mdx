회의실 예약 화면에서 예시로 14:00~15:00과 14:30~15:30이 둘 다 잡혔다고 해요. 두 요청 모두 "예약 완료"를 받았지만, 방은 한 칸이에요. 어느 예약을 살릴지는 서버가 정해야 해요.

이 글은 시간 구간이 겹치는지 판단하는 식, 겹침을 DB가 막게 하는 방법, 빈 시간을 계산하는 방법을 정리해요. 아래 시뮬레이터에서 같은 상황을 직접 돌려 볼 수 있어요. 글의 규칙과 시뮬레이터의 계산은 같아요.

## 증상 — 구간이 겹쳐도 둘 다 저장되는 경우

좌석 번호는 같은 값끼리만 비교하면 돼요. [좌석 선점 모듈](/m/concert-seats)에서 본 방식이에요. 회의실 예약은 값이 아니라 구간이 겹치는지를 봐야 해요. 14:00과 14:30은 다른 값이지만, 두 구간은 14:30~15:00에서 겹쳐요.

## 구간 겹침 — 두 조건을 같이 확인하기

두 구간 `a`와 `b`가 겹치려면 한쪽이 다른 쪽이 시작하기 전에 끝나지 않아야 해요. 조건은 두 개예요.

```text
겹침 = a.start < b.end  그리고  b.start < a.end
```

| 두 예약                   | a.start < b.end | b.start < a.end | 결과      |
| ------------------------- | --------------- | --------------- | --------- |
| 14:00~15:00과 14:30~15:30 | 참              | 참              | 겹쳐요    |
| 14:00~15:00과 15:00~16:00 | 참              | 거짓            | 안 겹쳐요 |
| 14:00~15:00과 13:00~14:00 | 거짓            | 참              | 안 겹쳐요 |

두 번째 행은 15:00에 끝나는 예약과 15:00에 시작하는 예약이에요. 두 번째 조건인 `15:00 < 15:00`이 거짓이라 겹치지 않아요.

## 반열린 구간 — 끝 시각을 빼는 [start, end) 표기

위 식에서 끝 시각은 `<`로 비교해요. 끝 시각 자신은 구간에 들어가지 않는다고 정하는 거예요. 이 표기를 반열린 구간 (half-open interval)이라고 불러요.

PostgreSQL 범위 타입 문서는 `[`를 포함하는 경계, `(`와 `)`를 포함하지 않는 경계로 설명해요. 범위를 만드는 생성 함수에서 세 번째 인자를 생략하면 `[)`가 쓰인다고도 설명해요.

이 표기를 쓰면 15:00에 끝난 예약과 15:00에 시작하는 예약이 같은 순간을 두 번 세지 않아요. 예약 길이도 `end - start` 한 식으로 나와요.

## PostgreSQL 범위 타입 — tstzrange와 && 연산자

예약 구간은 `tstzrange`에 담아요. 시각을 타임존 있는 값으로 저장하는 범위 타입이에요. 시각을 다루는 기준은 [시간대 모듈](/m/time-and-locale)에서 다뤘어요.

범위 타입 문서는 `&&`로 두 범위가 겹치는지 묻는 예를 보여 줘요. 예를 들어 `numrange(11.1, 22.2) && numrange(20.0, 30.0)`이 그런 질의예요. 아래는 같은 질의를 예약 구간에 적용한 예시예요.

```sql
SELECT tstzrange('2026-11-25 14:00+09', '2026-11-25 15:00+09')
    && tstzrange('2026-11-25 14:30+09', '2026-11-25 15:30+09') AS overlaps; -- true
```

## 확인 후 삽입 — 같은 순간 두 요청이 남기는 틈

가장 흔한 코드는 두 문장이에요. 먼저 겹치는 예약이 있는지 보고, 없으면 저장해요.

```sql
SELECT 1 FROM room_bookings WHERE room_id = $1 AND during && $2;  -- 결과가 없으면
INSERT INTO room_bookings (id, room_id, during, holder) VALUES ($4, $1, $2, $3);
```

이 패턴에는 [좌석 선점 모듈](/m/concert-seats)의 "읽고 나서 쓰기"와 같은 틈이 있어요. 두 요청이 같은 빈 상태를 읽고 둘 다 INSERT 할 수 있어요.

PostgreSQL 격리 수준 문서는 기본 수준인 Read Committed에서 팬텀 읽기가 일어날 수 있다고 설명해요. 같은 트랜잭션이 같은 조건으로 다시 읽었을 때 다른 트랜잭션이 커밋한 행이 보인다는 뜻이에요. 확인 쿼리가 본 빈 상태가 INSERT 시점에는 이미 바뀌어 있을 수 있어요.

Serializable로 올리면 PostgreSQL이 충돌을 직렬화 실패(40001)로 실패시킬 수 있어요. 이때 앱은 트랜잭션을 다시 시도해야 해요. 문서도 Repeatable Read와 Serializable에서 재시도를 준비하라고 설명해요.

## 배제 제약 — 방 id와 구간을 함께 막기

확인 코드를 앱에서 빼고, 규칙을 테이블에 두는 방법이에요. 예시 스키마는 이래요.

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE room_bookings (
  id      bigint PRIMARY KEY,
  room_id bigint NOT NULL,
  during  tstzrange NOT NULL,
  holder  bigint NOT NULL,
  EXCLUDE USING gist (room_id WITH =, during WITH &&)
);
```

PostgreSQL 배제 제약 문서는 두 행을 지정한 열과 연산자로 비교했을 때 적어도 하나의 비교가 거짓이나 null이 되도록 보장한다고 설명해요. 위 제약은 같은 방(`room_id =`)이고 구간이 겹치는(`during &&`) 두 행을 둘 다 허용하지 않아요.

문서는 범위 타입에 겹침 금지 제약을 거는 예로 `EXCLUDE USING GIST (during WITH &&)`를 들어요.

몇 가지 확인할 점이 있어요.

- `=`를 GiST 인덱스 안에서 쓰려면 btree_gist 모듈이 필요해요. 이 모듈은 int8과 timestamptz 같은 자료형에 B-tree와 같은 동작을 GiST에서 쓰게 해 줘요.
- 배제 제약을 추가하면 지정한 종류의 인덱스가 자동으로 만들어져요.
- `during`이 NULL이면 비교 결과가 null이 되어 충돌로 잡히지 않아요. 그래서 NOT NULL을 둬요.
- 위반은 SQLSTATE `23P01`(exclusion_violation)로 와요. 앱은 이 코드를 409로 바꿔요.

## 방법 비교 — 확인 없음 · 확인 후 삽입 · 배제 제약

같은 순간에 들어온 두 요청을 기준으로 세 방법을 비교해요. 시뮬레이터에서 같은 결과를 볼 수 있어요.

| 방법         | 같은 순간 두 요청의 결과                       | 장점                                      | 주의                                            |
| ------------ | ---------------------------------------------- | ----------------------------------------- | ----------------------------------------------- |
| 확인 없음    | 둘 다 201, 겹친 예약이 생겨요                  | 코드가 가장 짧아요                        | 앱이 이중 예약을 알아채지 못해요                |
| 확인 후 삽입 | 둘 다 확인을 통과해 겹친 예약이 생길 수 있어요 | 저장 전에 메시지를 미리 보여 줄 수 있어요 | 확인과 삽입 사이가 빈틈이에요                   |
| 배제 제약    | 하나는 201, 다른 하나는 23P01 → 409            | 모든 저장에서 DB가 겹침을 막아요          | 방 id와 구간 조건을 스키마에 맞춰 설계해야 해요 |

## 빈 시간 계산 — 영업시간에서 예약 구간 빼기

빈 시간은 영업시간 구간에서 예약 구간을 뺀 나머지예요. 계산은 세 단계예요.

1. 예약을 시작 시각 순으로 정렬해요.
2. 커서를 영업 시작에 두고, 다음 예약이 시작하기 전까지를 빈 시간으로 모아요.
3. 커서를 예약의 끝으로 옮겨요. 예약이 서로 겹치면 더 늦은 끝을 골라요.

```ts
function freeWindows(open: Interval, booked: Interval[]): Interval[] {
  const sorted = [...booked].sort((a, b) => a.start - b.start);
  const free: Interval[] = [];
  let cursor = open.start;
  for (const b of sorted) {
    if (b.start > cursor) free.push({ start: cursor, end: Math.min(b.start, open.end) });
    cursor = Math.max(cursor, b.end);
    if (cursor >= open.end) break;
  }
  if (cursor < open.end) free.push({ start: cursor, end: open.end });
  return free.filter((w) => w.end > w.start);
}
```

반열린 구간 덕분에 앞 예약의 끝과 다음 예약의 시작이 같으면 그 사이 빈 시간 길이가 0이 돼요. 그래서 길이 0인 빈 시간이 목록에 끼지 않아요.

`cursor = Math.max(...)`를 빼면 긴 예약 안에 들어 있던 짧은 예약 때문에 빈 시간이 잘못 나와요.

## 시간대와 서머타임 — UTC 저장과 지역 규칙 계산

영업시간 09:00~18:00은 회의실이 있는 지역의 벽시계 시간이에요. 서버는 이것을 UTC 구간으로 바꿔 저장해요. 바꿀 때는 IANA 시간대 이름(예: `Asia/Seoul`)을 기준으로 해요.

MDN Date 문서는 서머타임이 바뀌는 날의 규칙을 설명해요. 뉴욕에서 3월 10일 2:30 AM은 없는 시각이라 3:30으로 앞으로 밀린다고 해요. 11월 3일 1:30은 두 번 있는 시각이라 이른 쪽을 고른다고 해요.

그래서 서머타임 지역의 09:00이 날짜에 따라 UTC로 한 시간 달라질 수 있어요.

Intl.DateTimeFormat의 `timeZone` 옵션은 IANA 이름을 받는다고 MDN이 설명해요. 회의실마다 시간대 이름을 한 열에 두고, 영업시간을 그 지역 규칙으로 펼쳐 UTC 구간을 만드는 방식이 깔끔해요. 시각 표기 세부는 [시간대 모듈](/m/time-and-locale)을 보세요.

## 반복 예약 — 회차 펼쳐 저장과 규칙 저장 비교

"매주 월요일 10시" 같은 반복 예약은 두 방식으로 저장할 수 있어요.

| 방식                           | 장점                                      | 주의                                                        |
| ------------------------------ | ----------------------------------------- | ----------------------------------------------------------- |
| 회차마다 행을 펼쳐 저장        | 배제 제약이 회차마다 같은 규칙으로 막아요 | 행 수가 늘고, 규칙을 바꾸면 회차를 다시 써야 해요           |
| 규칙만 저장하고 조회할 때 펼침 | 행이 적고 규칙 변경이 쉬워요              | 겹침을 앱이 계산해야 해서 배제 제약이 같은 힘을 내지 못해요 |

반복 규칙은 RFC 5545의 RRULE로 정의돼요. 예를 들어 `RRULE:FREQ=WEEKLY;COUNT=10`은 열 번 반복하는 규칙이에요. RFC는 UNTIL이 그 날짜까지를 포함한다고 설명해요. UNTIL과 COUNT가 둘 다 없으면 규칙이 계속 반복한다고도 설명해요.

판단은 이래요. 보통은 회차를 펼쳐 저장하는 편이 좋아요. 배제 제약이 각 회차를 그대로 막기 때문이에요. 규칙만 저장하는 방식은 회차가 매우 많고 빈 시간 조회가 주된 일일 때 고려해요.

## 임시 홀드 — 만료 전에 정리하기

결제 전에 시간을 잠시 잡는 임시 홀드도 같은 테이블에 둘 수 있어요. 만료 규칙은 [좌석 선점 모듈](/m/concert-seats)과 같아요.

배제 제약은 테이블의 모든 행에 걸리기 때문에 만료된 홀드가 남아 있으면 새 예약을 막아요. 그래서 만료된 홀드를 지우는 정리가 필요해요.

정리 작업이 돌기 전까지 기다리지 않으려면, 예약을 넣는 트랜잭션 안에서 겹치는 만료 홀드를 먼저 지우고 INSERT 하는 방법이 있어요. 이건 설계 판단이에요. 확정 쓰기는 보류 시각을 다시 확인해요.

## FE 체크 포인트

- 409는 "방금 다른 사람이 이 시간을 잡았어요"라는 안내예요. 빈 시간 목록을 서버에서 다시 받아 와요.
- 화면에 있는 빈 시간을 클라이언트에서 계산해 두고 재사용하지 마세요. 영업시간과 시간대 규칙은 서버에 있어요.
- 시각은 오프셋 포함 형식으로 보내세요. 예시 요청은 이래요.

```http
POST /rooms/12/bookings
Content-Type: application/json

{"start": "2026-11-25T14:00:00+09:00", "end": "2026-11-25T15:00:00+09:00"}
```

- 네트워크 재시도로 같은 예약을 두 번 보낼 수 있어요. 첫 요청이 이미 저장됐다면 두 번째 요청은 자기 예약과 겹쳐 409를 받아요. 사용자는 실패로 보게 돼요.
- 같은 시도에는 같은 키를 보내세요. [트랜잭션 · 락 · 데드락 모듈](/m/transactions)의 멱등성 키 규칙을 그대로 써요.

## 시뮬레이터 안내

아래 시뮬레이터에서 세 가지를 확인해요.

1. 기본 값의 "확인 없음"을 보세요. 같은 시간에 예약이 두 개 저장돼요.
2. 같은 순간 두 요청으로 두고 "확인 후 삽입"과 "배제 제약"을 번갈아 보세요. 배제 제약에서는 두 번째 요청이 409가 돼요.
3. 두 요청을 15:00에 맞닿게 바꿔 보세요. 둘 다 201로 저장되고, 빈 시간 목록에 길이 0인 15:00 칸이 생기지 않아요.

시뮬레이터는 실제 PostgreSQL이 아니에요. 같은 규칙을 흉내 낸 모델이에요. 순서와 경계의 결과만 보여 줘요.

## 정리 — 겹침은 DB 제약, 빈 시간은 구간 차감

예약 구간은 반열린 `[start, end)`로 정해요. 겹침은 두 부등식으로 판단해요. 확인과 저장을 떼어 두면 같은 순간의 두 요청이 모두 통과할 수 있어서, 배제 제약으로 DB가 막게 해요. 빈 시간은 영업시간에서 예약을 빼서 서버가 계산하고, 시각은 UTC로 저장해요.

격리 수준 이야기는 [트랜잭션 · 락 · 데드락 모듈](/m/transactions)에서 이어져요. 재고를 한 문장으로 줄이는 방식은 [장바구니 재고 모듈](/m/cart-stock)에서 봤어요.
