폼에서 이미 검사하는데 서버가 같은 검사를 또 해야 하는지는 FE가 가장 자주 묻는 질문이에요. 답은 두 검사가 맡는 일이 다르다는 데 있어요. 화면 검사는 입력을 빨리 알려 주고, 서버 검사는 저장되는 값을 정해요. 이 글은 두 검사가 나눠 맡는 일, 길이를 세는 단위와 정규화를 합의하는 방법, 필드 오류 응답 형식을 다뤄요.

## 증상 — 같은 입력을 화면과 서버가 다르게 셀 때

닉네임 칸에 가족 이모지를 넣었어요. 최대 길이는 6이에요. 화면은 이 값이 6을 넘는다고 막는데, 서버는 같은 값을 받아 줘요. 사람 눈에는 글자 한 개인데, 화면과 서버가 길이를 다른 단위로 셌기 때문이에요.

MDN의 input 문서는 maxlength가 UTF-16 코드 유닛으로 센다고 설명해요. 같은 문서는 브라우저가 기본으로 그 이상 입력하지 못하게 막는다고 설명해요. 서버가 코드 포인트로 세면 같은 입력의 길이가 달라져요.

시뮬레이터 기본값이 이 상황이에요. 가족 이모지는 코드 포인트 5개이고, UTF-16 코드 유닛은 8개예요.

## 신뢰 경계 — 화면 검사는 힌트, 서버 검사는 판정

OWASP 입력 검증 치트 시트는 클라이언트만 하는 검사를 흔한 함정으로 꼽아요. 클라이언트 검사는 우회될 수 있으니 즉각 피드백용으로만 쓰고, 서버에서 같은 검사를 다시 하라고 설명해요. MDN 제약 검증 문서도 같은 말을 해요. 제약 검증이 있어도 서버 검증의 필요가 없어지지 않는다고 설명해요.

화면이 맡는 일은 틀린 이유를 입력하는 순간 알려 주는 데까지예요. 저장할지는 서버가 정해요. 누가 신뢰 기준을 쥐는지는 [서버 · 클라 처리 판단](/m/server-or-client) 글에서 자세히 다뤄요.

## 허용 목록 — 형식 · 범위 · 길이로 적은 규칙

OWASP는 입력을 받기 전에 무엇을 허용하는지 정하고, 그 밖의 값을 명확한 오류로 거절하라고 설명해요. 특수 문자를 막는 거부 목록은 정상 이름까지 막을 수 있고, DB 질의를 안전하게 만들어 주지도 않는다고 설명해요.

| 검사 | 묻는 것                 | 닉네임 예시              |
| ---- | ----------------------- | ------------------------ |
| 형식 | 정해진 모양인가요?      | 허용할 글자 종류         |
| 범위 | 허용 값 안인가요?       | 숫자라면 최소와 최대     |
| 길이 | 최대 · 최소 얼마인가요? | 최대 6, 단위를 같이 적음 |

OWASP는 자유 입력에서는 글자 종류를 좁히지 않고 길이만 제한하는 허용 목록도 가능하다고 설명해요. 그리고 패턴을 맞추기 전에 길이부터 제한하라고 설명해요. 그래서 길이 규칙은 형식 규칙보다 먼저 적어요.

## 길이 단위 — UTF-16 코드 유닛 · 코드 포인트 · UTF-8 바이트

길이를 세는 단위는 셋이에요. 단위를 정하지 않으면 같은 "6자"가 화면과 서버에서 달라져요.

| 단위             | 세는 것                      | 근거                                                               | 가족 이모지 |
| ---------------- | ---------------------------- | ------------------------------------------------------------------ | ----------- |
| UTF-16 코드 유닛 | JS `String.length`가 세는 값 | MDN은 문자 하나가 코드 유닛 1개 또는 2개로 인코딩된다고 설명해요   | 8           |
| 코드 포인트      | Unicode 문자 번호 하나       | MDN 용어집은 코드 포인트를 추상 문자 하나에 붙은 번호라고 설명해요 | 5           |
| UTF-8 바이트     | 인코딩한 뒤의 바이트 수      | RFC 3629는 UTF-8이 문자마다 1~4옥텟을 쓴다고 정해요                | 18          |

사람이 보는 글자 한 개는 셋 중 어느 값과도 같지 않을 수 있어요. MDN의 Intl.Segmenter는 그 글자 단위를 따로 나눠 준다고 설명해요. 이 글에서는 셋 중 하나를 골라 명세에 적는 것으로 다뤄요.

## 정규화 — NFC로 맞춘 뒤 세기

같은 "é"가 두 가지 방식으로 들어올 수 있어요. 하나는 글자 하나(U+00E9)이고, 다른 하나는 e와 결합 악센트(U+0301)예요. MDN의 예시는 두 방식으로 쓴 "Amélie"가 `===`로 다르고 길이도 다르다고 보여 줘요. 양쪽에 `normalize("NFC")`를 적용하면 둘 다 같아져요.

UAX #15는 정준 동치(canonical equivalence)를 정의하고, 한글 음절 "가"와 자모 "ᄀ+ᅡ"가 같은 예로 나온다고 설명해요. OWASP는 정규화 정책을 검사, 저장, 비교 전에 같은 방식으로 적용하라고 설명해요. 같은 문서는 정규화가 살균(sanitization)이 아니고 출력 인코딩을 대신하지도 않는다고 설명해요.

호환 정규화(NFKC)는 의미 차이를 지울 수 있다고 OWASP가 경고해요. 그래서 이 시뮬레이터는 NFC만 써요.

## 트림 — 앞뒤 공백을 떼는 위치

MDN의 trim()은 문자열 양쪽 끝의 공백을 떼고 새 문자열을 돌려준다고 설명해요. 공백에는 줄 바꿈 문자도 들어간다고 설명해요.

공백을 떼는 위치가 화면과 서버에서 다르면 저장되는 값도 달라요. 화면은 떼고 서버는 떼지 않으면 같은 입력이 다른 길이로 세어져요. 떼는 규칙은 서버 한 곳에서 정하고, 화면은 같은 규칙을 적용하거나 힌트만 줘요. 이 부분은 설계 판단이에요.

## 오류 응답 — 422와 409, 필드 경로

RFC 9110은 400을 구문이 잘못된 요청 같은 클라이언트 오류로 정의해요. 422는 요청 구문은 맞지만 안의 지시를 처리할 수 없을 때라고 정의해요. RFC의 예시는 XML이라서, JSON 필드 값이 규칙을 어기는 경우에 어느 쪽을 쓸지는 팀 규칙으로 정해요.

409는 대상 리소스의 현재 상태와 충돌해서 요청을 끝낼 수 없을 때라고 정의해요. 사용자가 충돌을 풀고 다시 보낼 수 있는 상황에서 쓴다고 설명해요. 중복 닉네임을 409로 줄지, 필드 오류로 줄지도 팀이 하나로 정해요.

오류 본문에 실패한 칸을 담는 형식은 [API 오류 형식](/m/api-errors) 글에서 다뤄요. 여기서는 검증 쪽에서 맞춰야 할 것만 정리해요.

- 검증이 끝나지 않은 데이터로 계속 처리하지 않아요. OWASP가 권하는 규칙이에요.
- 칸을 `/nickname` 같은 경로로 가리켜요.
- 메시지에 단위와 기준을 같이 넣어요.

예시 응답은 이래요.

```json
{
  "status": 422,
  "errors": [{ "pointer": "/nickname", "detail": "코드 포인트 기준 5로 세어져요. 최대 4 이하여야 해요." }]
}
```

## 서버만 아는 검증 — 중복 · 재고는 응답으로

중복 닉네임은 화면이 알 수 없어요. 미리 확인하는 요청을 따로 보내면 그 사이에 다른 사람이 같은 값을 먼저 가져갈 수 있어요. 그래서 최종 판단은 저장 요청의 응답으로 받는 편이 안전해요. 이 부분은 설계 판단이에요.

재고처럼 줄어드는 값은 [장바구니와 재고 — 담아 둔 상품이 품절되는 순간](/m/cart-stock) 글에서 더 자세히 다뤄요.

## 스키마 공유 — 화면과 서버가 한 정의를 쓸 때

화면과 서버가 같은 검증 스키마를 쓰면 규칙이 두 곳에 따로 적히지 않아요. 대신 공유할 때 따져야 할 것이 있어요.

| 장점                                    | 단점                                           |
| --------------------------------------- | ---------------------------------------------- |
| 길이 제한과 메시지가 한 번에 바뀌어요   | 서버에만 있어야 할 규칙이 화면 번들로 나가요   |
| 단위와 정규화 합의가 코드로 남아요      | 서버 언어와 화면 언어가 다르면 공유가 어려워요 |
| 화면과 서버 판정이 어긋날 여지가 줄어요 | 검증 코드가 화면 번들 크기를 늘려요            |

형식, 단위, 길이처럼 공개해도 되는 규칙은 공유하는 편이 이득이 커요. 할인 조건처럼 비밀 규칙은 공유하지 않아요. 중복이나 재고처럼 상태를 보는 검사는 공유해도 확정은 서버만 해요. 이 기준은 설계 판단이에요.

## FE 체크 포인트 — 규칙 한 벌과 응답 칸 위치

- 길이 단위와 정규화 여부를 API 명세에 적어요. 계약 쪽 기준은 [API 계약](/m/api-contracts) 글과 이어져요.
- 화면 제한은 힌트로 두고, 저장 실패는 응답의 경로가 가리키는 칸에 붙여요.
- 화면 판정을 서버와 맞추려면 같은 정규화와 트림을 입력 직후에 적용해요.
- 중복처럼 화면이 모르는 실패는 입력 전에 확정된 것처럼 보여 주지 않아요.

## 시뮬레이터 안내

예시를 고르거나 직접 입력해요. 최대 길이, 세는 단위, 정규화와 트림, 화면 구현을 바꾸면 화면 판정과 서버 판정이 어떻게 달라지는지 볼 수 있어요. 화면 구현을 "서버와 같은 규칙"으로 바꾸면 두 판정이 어긋나지 않아요. 중복 체크를 켜면 화면은 중복을 모르고, 서버만 409를 돌려줘요.

## 정리 — 신뢰 경계 · 길이 단위 · 정규화 · 오류 형식

- 저장 여부는 서버가 정하고, 화면은 같은 규칙으로 힌트만 줘요.
- 길이 단위는 하나를 골라 명세에 적어요.
- 정규화와 트림은 저장 전에 한 번 적용해요.
- 필드 오류는 경로와 함께 돌려주고, 중복과 재고는 서버 응답으로 받아요.
