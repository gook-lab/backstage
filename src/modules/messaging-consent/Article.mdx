설정 화면에서 "마케팅 메일 받기"를 껐는데 다음 날 쿠폰 메일이 왔다는 문의가 들어와요. 메일 아래 "수신 거부" 링크를 눌러도 바로 반영되지 않았다는 말도 같이 나와요. 이 글은 동의 상태가 어디에 저장되고, 예약된 메시지가 나가기 전에 무엇을 다시 확인해야 하는지 따라가요. 원클릭 수신 거부를 어떻게 받는지, 로그인 없이 받는 링크가 왜 위조되면 안 되는지도 정리해요.

아래 시뮬레이터에서 동의 확인 시점과 사건을 바꿔 보면, 같은 예약 메시지가 나가는지, 막히는지, 동의 위반으로 세지는지 볼 수 있어요.

## 증상 — 끈 뒤에 나간 예약 메일

메일은 요청이 들어온 시점에 만들어져 큐에 들어가고, 실제 발송은 나중에 일어나요. 큐 구조는 [트랜잭션 메일](/m/transactional-email)에서 다뤘어요. 요청을 만들 때 동의가 켜져 있었다면, 큐에 쌓인 메일은 그 뒤에 토글을 꺼도 그대로 나갈 수 있어요. 이 간격이 이 글이 다루는 핵심이에요.

## 거래 알림과 마케팅 메시지 — 발송 목적으로 나누기

주문 확인이나 보안 알림은 거래 알림이에요. 쿠폰이나 이벤트 안내는 마케팅 메시지예요. 두 종류는 동의 규칙이 달라요.

| 구분          | 예                                  | 동의 토글                                          | 근거                       |
| ------------- | ----------------------------------- | -------------------------------------------------- | -------------------------- |
| 거래 알림     | 주문 확인, 결제 완료, 비밀번호 변경 | 없어요. 계정 상태를 알리는 메시지라 끄지 않게 둬요 | 설계 판단                  |
| 마케팅 메시지 | 쿠폰, 이벤트, 할인 안내             | 있어요. 채널과 종류별로 따로 둬요                  | KISA 불법스팸대응센터 안내 |

KISA 불법스팸대응센터의 FAQ는 광고성 정보를 "전송자가 널리 경제적 이득을 취할 목적으로 전송하는" 정보로 설명해요. 그래서 메시지의 이름보다 목적으로 나눠요. 쿠폰이나 적립금 안내는 "안내"라는 이름이어도 마케팅 동의 대상으로 다루는 편이 좋아요.

## 동의 저장 — 채널과 종류별 현재 값

동의는 사용자와 채널, 종류의 조합마다 한 행으로 둬요. 채널마다 따로 끌 수 있어야 하기 때문이에요. 거래 알림은 행을 만들지 않아요.

예시 스키마는 이래요.

| 필드    | 예                 | 이유                               |
| ------- | ------------------ | ---------------------------------- |
| user_id | 사용자 식별자      | 계정 단위로 묶어요                 |
| channel | email · sms · push | 메일을 끄고 문자는 켜 둘 수 있어요 |
| kind    | marketing          | 거래 알림과 구분해요               |
| granted | true · false       | 지금 보내도 되는지에 대한 현재 값  |

현재 값 행은 덮어써도 돼요. 과거 값을 알아야 하는 질문은 행을 덮어쓰면 답할 수 없어서, 이력을 따로 남겨요. 다음 절에서 다뤄요.

## 동의 이력 — 현재 값 말고 언제 · 어디서 · 무슨 문구로

분쟁이 생기면 "언제 동의했는지, 어떤 문구를 보고 동의했는지"를 보여야 해요. 이 기록은 [변경 이력과 감사 로그](/m/audit-history)처럼 덧붙이기 전용으로 쌓아요. 한 번 쓴 기록을 고치지 않아요.

이벤트 한 건에 담을 것은 이래요. 예시예요.

- `granted_at`: 동의 또는 철회 시각 (UTC)
- `source`: 가입 폼, 설정 화면, 원클릭 수신 거부, 시스템 중지 중 하나
- `copy_version`: 동의 문구의 버전 id. 문구 원문을 행마다 복사하지 않아요
- 요청 id: 어떤 요청에서 나왔는지

IP 주소와 기기 정보는 민감한 값이라 보존 기간과 마스킹을 따로 정해요. 기준은 [민감 정보 누출](/m/sensitive-data)에서 다뤘어요.

KISA 안내는 광고성 정보 수신 동의 여부를 2년마다 확인하는 발송이 있다고 설명해요. 마지막 동의 시각과 출처가 남아 있어야 그 확인에 근거를 댈 수 있어요.

## 발송 직전 재확인 — 예약과 재시도 사이의 틈

요청을 만들 때만 확인하면, 예약 발송이 다음 날이어도 그 사이에 꺼진 동의를 무시해요. 재시도도 같아요. 일시 실패로 큐에 다시 들어간 메시지는 한참 뒤에 나갈 수 있어요.

| 확인 시점             | 장점                             | 빠지는 경우                                 |
| --------------------- | -------------------------------- | ------------------------------------------- |
| 요청 생성 시에만      | 큐에 넣는 비용이 적어요          | 예약 · 재시도 사이에 꺼진 동의를 놓쳐요     |
| 발송 직전에 다시      | 꺼진 동의로 나가는 것을 막아요   | 발송할 때마다 동의 저장소를 한 번 더 읽어요 |
| 발송 직전 + 이력 기록 | 막은 이유를 운영 기록으로 남겨요 | 쓰기가 늘어요                               |

발송 직전 확인을 기본으로 두는 편이 좋아요. 막은 메시지는 "동의 꺼짐"이라는 이유를 운영 기록에 남겨요. 다만 확인과 실제 전송 사이에 짧은 틈은 남아요. 발송 직전 확인은 꺼진 동의를 크게 줄일 뿐, 완벽한 보장은 아니에요.

## 원클릭 수신 거부 — RFC 8058 헤더 두 개와 POST

[RFC 2369](https://www.rfc-editor.org/rfc/rfc2369)는 메일 헤더 `List-Unsubscribe`에 수신 거부 명령을 담는 방법을 정의해요. 이 헤더는 mailto 주소나 웹 주소를 가리킬 수 있어요(3.2).

[RFC 8058](https://www.rfc-editor.org/rfc/rfc8058)은 HTTPS 주소 하나를 `List-Unsubscribe`에 두고, `List-Unsubscribe-Post` 헤더에 `List-Unsubscribe=One-Click` 한 쌍을 더하라고 정해요(3.1). 메일 클라이언트는 이 주소로 POST를 보낼 수 있어요. 본문에 링크만 두는 방식과 달라요.

| 방식                 | 헤더                                 | 수신자 쪽 동작                | 근거              |
| -------------------- | ------------------------------------ | ----------------------------- | ----------------- |
| 본문 링크            | 없음                                 | 링크를 눌러 페이지로 이동     | 일반 웹 링크      |
| 목록 명령 (RFC 2369) | mailto 또는 웹 주소                  | 클라이언트 버튼으로 명령 실행 | RFC 2369 3.2      |
| 원클릭 (RFC 8058)    | HTTPS 주소 + `List-Unsubscribe-Post` | 주소로 POST 한 번             | RFC 8058 3.1, 3.2 |

FE가 알아 둘 것은 이래요.

- 두 헤더는 DKIM 서명에 포함돼야 해요(3.1). 서명이 빠지면 수신 측은 이 신호를 믿을 근거가 없어요.
- POST에는 쿠키나 인증 정보를 실으면 안 돼요(3.1). 그래서 수신 거부는 로그인과 무관하게 주소 안의 값만으로 처리해요.
- POST 본문은 `List-Unsubscribe=One-Click`이에요(3.2).
- RFC 8058은 수신 측이 사용자 동의 없이 POST 하면 안 된다고 정하고, 동의를 어떻게 받는지는 이 규격의 범위 밖이라고 적어요(3.2).

발신 측 기준도 있어요. Gmail 발신자 가이드는 하루 5,000통을 넘게 Gmail 계정으로 보내는 발신자에게 마케팅 · 구독 메시지의 원클릭 수신 거부를 요구한다고 설명해요. 본문 링크를 함께 두라고도 하지만, 원클릭을 대신하지는 않는다고 설명해요. Yahoo 발신자 가이드는 마케팅 · 구독 메시지에 원클릭을 지원하는 list-unsubscribe 헤더를 구현하라고 권해요. 수신 거부는 2일 안에 반영하고, 로그인을 요구하지 않는 과정을 두라고 설명해요.

## 수신 거부 토큰 — 로그인 없이 위조를 막기

원클릭 요청에는 쿠키가 없어요. 서버가 알 수 있는 것은 URL 안의 값뿐이에요. RFC 8058 6은 보내는 쪽이 목록과 수신자를 식별하는 주소에 추측하기 어려운 식별자를 넣어야 한다고 권고(SHOULD)해요. 그래야 요청이 실제로 보낸 메일에서 나왔다고 믿을 수 있어요.

토큰을 설계할 때 보통 이렇게 가져가요. 예시 설계예요.

- 토큰에는 사용자, 채널, 종류를 담고 서버 비밀키로 서명하거나, 무작위 값을 저장소에 묶어요.
- 토큰은 수신 거부 범위만 허용해요. 같은 토큰으로 계정 설정이나 개인 정보를 읽지 못하게 해요.
- RFC 8058 3.2는 수동 수신 거부의 GET과 원클릭 POST가 같은 주소를 쓴다고 설명해요. 그래서 서버는 GET에는 확인 화면을, POST에는 처리 결과를 주는 편이 좋아요. 링크를 미리 열어 보는 것만으로 수신 거부가 되면 안 되기 때문이에요.
- 토큰이 틀리면 동의 상태를 바꾸지 않아요. 응답은 계정이 있는지 드러내지 않는 문구로 같게 줘요. 같은 원칙은 [트랜잭션 메일](/m/transactional-email)의 다시 보내기에서도 다뤘어요.

## 반송과 스팸 신고 — 마케팅 채널을 멈추는 조건

반송은 [트랜잭션 메일](/m/transactional-email)의 5yz 처리와 같은 경로로 들어와요. 여기서 멈추는 것은 해당 채널의 마케팅 발송뿐이에요. 거래 알림은 계속 보내요.

Gmail 발신자 가이드는 Postmaster Tools에서 보는 스팸 신고율을 0.10% 아래로 유지하고, 0.30% 이상에 이르지 않게 하라고 설명해요.

- 반송이나 스팸 신고가 들어온 주소는 그 채널의 마케팅 동의를 자동으로 내려요. 이력에는 `source`를 시스템 중지로 남겨요.
- 자동으로 내려간 동의는 사용자가 다시 동의해야 풀려요.
- 신고율 기준의 구체적인 숫자는 운영 정책이에요. 위 0.10% · 0.30%는 Gmail 가이드의 기준이에요.

## 법적 요건 — 국가마다 다르니 확인한 범위만

광고성 메시지 규정은 나라마다 달라요. 이 글은 한국의 공식 출처에서 확인한 범위만 짧게 정리해요.

- 국가법령정보센터에는 정보통신망 이용촉진 및 정보보호 등에 관한 법률의 현행 본문이 있어요. 2026년 11월에 확인했을 때 시행일은 2026년 10월 2일, 법률 제21988호(2026년 9월 29일 일부개정)로 표시돼 있었어요. 법은 계속 개정되니 읽을 때 현행 본문을 다시 확인해요.
- KISA 불법스팸대응센터는 광고성 정보를 영리 목적 전송으로 설명해요.
- KISA 안내서 제7차 개정본 요약은 세 가지를 짚어요. 수신 동의를 받을 때 "혜택 알림", "정보제공" 같은 모호한 표현을 쓰지 말 것, 앱 푸시 광고 수신 거부 때 로그인 등 복잡한 절차를 요구하지 말 것, 일방적으로 준 쿠폰 · 적립금의 발급 · 소멸 안내를 보낼 때는 명시적 사전 동의가 필요하다고 정리해요.

조문 단위의 세부 요건은 원문을 직접 읽고 확인하는 편이 안전해요.

## FE 체크 포인트 — 토글 문구와 수신 거부 화면

- 토글 문구는 채널과 종류를 밝혀요. 예를 들어 "마케팅 메일 받기(쿠폰 · 이벤트)"처럼 써요. "혜택 알림" 같은 모호한 말은 피해요.
- 토글을 끈 뒤 저장 응답과 발송 결과를 다른 문장으로 나눠요. "앞으로 보내지 않아요. 이미 예약된 메일도 발송 전에 다시 확인해요"처럼 말해요.
- 거래 알림 설정에는 토글을 두지 않아요. 대신 "주문 · 보안 알림은 계속 받아요"처럼 안내해요.
- 원클릭 수신 거부 뒤 화면은 로그인 없이 보여 줘요. 어떤 채널과 종류가 꺼졌는지 보여 줘요.
- 토큰이 틀렸을 때도 계정 상태를 드러내지 않는 문구를 써요. "링크가 만료됐어요. 설정에서 다시 확인해 주세요"처럼 말해요.

## 시뮬레이터 안내

시뮬레이터는 예약된 메시지 세 통을 두고, 한 사용자의 동의가 바뀌는 사건을 적용해요.

- **동의 확인 시점**을 "요청 생성 시에만"으로 두고 "설정에서 메일 마케팅 끄기"를 고르면, 예약된 쿠폰 메일이 나가고 동의 위반이 1건으로 세져요.
- 같은 사건에서 확인 시점을 "발송 직전에 다시 확인"으로 바꾸면 그 메일은 막혀요.
- 거래 알림은 어떤 사건에도 나가요. 문자 마케팅은 메일 동의를 끈 영향을 받지 않아요.
- "토큰이 틀린 위조 요청"은 동의 상태를 바꾸지 않아요. 토큰 서명 검증 자체를 계산하지는 않고, 위조 요청이 상태를 바꾸지 않는다는 결과만 보여 줘요.

## 정리 — 채널별 동의 · 이력 분리 · 발송 직전 확인 · 원클릭 수신 거부

- 거래 알림과 마케팅 메시지를 나누고, 거래 알림에는 마케팅 토글을 붙이지 않아요.
- 동의는 채널과 종류별 현재 값으로 저장하고, 이력은 덧붙이기 전용으로 따로 남겨요.
