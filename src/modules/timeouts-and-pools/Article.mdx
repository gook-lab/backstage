프론트엔드(FE)에서는 요청이 30초쯤 돌다가 `504 Gateway Timeout`이 떠요. 화면에는 "서버 응답이 없어요"만 보여요. 서버가 느린 것인지, DB 커넥션을 기다리며 줄을 서 있었는지는 이 응답만으로 구분하기 어려워요. 이 글은 요청이 지나는 계층마다 따로 걸린 시간 제한과 DB 커넥션 풀을 따라가요.

글의 숫자는 설명을 위한 예시예요. 아래 시뮬레이터의 기본값과 같아요.

## 요청 경로 — 계층마다 따로 걸린 시간 제한

요청 하나는 브라우저, 프록시, 앱 서버, DB를 차례로 지나요. 각 계층은 자기 시간 제한을 따로 가져요. 한 계층이 기다리기를 멈춰도 뒤쪽 계층은 그 사실을 바로 알지 못해서 계속 일할 수 있어요.

| 계층                  | 시간 제한                           | 알아 둘 점                                                               |
| --------------------- | ----------------------------------- | ------------------------------------------------------------------------ |
| 브라우저 (클라이언트) | `fetch`의 `signal`로 거는 시간 제한 | 시간으로 끊으려면 `signal`을 넘겨요                                      |
| 프록시 (nginx 등)     | `proxy_read_timeout`                | 응답 전체 시간이 아니라 두 번의 읽기 사이 간격이에요. 기본값은 `60s`예요 |
| 앱 서버               | 프레임워크와 HTTP 클라이언트 설정   | 서버마다 설정이 달라서 이 글에서는 다루지 않아요                         |
| DB                    | `statement_timeout`                 | 문장 하나의 실행 시간이 이 값을 넘으면 취소해요                          |

MDN 문서는 `AbortSignal.timeout()`이 지정한 시간이 지나면 자동으로 중단되는 AbortSignal을 돌려준다고 설명해요. 예제는 `fetch(url, { signal: AbortSignal.timeout(5000) })`처럼 써요.

nginx 문서는 `proxy_read_timeout`이 응답 전체가 아니라 두 번의 연속된 읽기 사이 간격에 걸린다고 설명해요. 이 글의 시뮬레이터는 이를 단순하게 응답을 기다리는 전체 시간으로 봐요.

PostgreSQL 문서는 `statement_timeout`이 문장 하나가 설정한 시간보다 오래 걸리면 중단하는 값이라고 설명해요. DB 입장에서 커넥션 풀에서 기다린 시간은 아직 문장을 받지 않은 시간이라, 이 값에는 들어가지 않아요.

## 계층 순서 — 바깥이 안쪽보다 짧을 때 생기는 일

바깥 계층이 안쪽보다 먼저 포기하면 안쪽은 그 사실을 모르고 끝까지 일해요. 이 글에서는 이런 요청을 "포기 뒤 실행"이라고 부를게요. 앞단은 응답을 받지 않았는데 서버는 쿼리를 실행하는 상태예요.

- 클라이언트가 3초, 프록시가 5초라면 클라이언트가 먼저 떠나요. 프록시가 내는 504는 아무도 받지 않아요.
- 프록시가 5초, DB가 10초라면 프록시가 504를 내도 DB는 `statement_timeout`까지 쿼리를 계속 실행해요.

안쪽 제한은 짧게, 바깥 제한은 길게 두는 편이 좋아요. DB 제한이 먼저 끊고 오류를 돌려주면, 그 응답이 프록시와 클라이언트까지 올라가요. 순서를 DB, 프록시, 클라이언트 순으로 길어지게 잡는 것은 설계 판단이에요.

## 502와 504 — 앞단이 받은 실패의 뜻

RFC 9110은 502를 게이트웨이나 프록시가 뒤쪽 서버에서 잘못된 응답을 받았을 때 쓴다고 정의해요. 504는 프록시가 응답을 완성하려고 필요한 뒤쪽 서버에서 제때 응답을 받지 못했을 때 쓴다고 정의해요.

그래서 504는 뒤쪽이 느렸다는 뜻이에요. 뒤쪽 작업이 실패했다는 뜻이 아니에요. 뒤쪽은 아직 쿼리를 실행하고 있을 수 있어요.

## 커넥션 풀 — 미리 열어 두고 빌려 쓰는 연결

PostgreSQL 문서는 클라이언트 프로세스 하나가 백엔드 프로세스 하나에 연결되는 "process per user" 모델이라고 설명해요. 연결마다 서버 쪽 프로세스가 하나씩 붙는 구조예요. 요청마다 연결을 새로 맺으면 그 작업을 요청마다 반복하게 돼요. 그래서 앱은 커넥션을 미리 열어 풀에 두고, 요청이 빌려 쓰고 돌려주는 방식을 써요. 설계 판단이에요.

PgBouncer 문서는 풀링 방식에 따라 커넥션을 돌려주는 시점이 달라진다고 설명해요. 세션 풀링은 클라이언트가 연결돼 있는 내내 서버 연결 하나를 붙잡고, 트랜잭션 풀링은 트랜잭션 동안만 붙잡아요.

풀이 다 차면 요청은 커넥션을 기다리며 줄을 서요. HikariCP 위키는 작은 풀을 두고 나머지 스레드가 풀에서 커넥션을 기다리게 하라고 권해요. 클라이언트 입장에서는 줄을 선 시간과 서버가 처리하는 시간이 구분되지 않아요. 둘 다 응답이 늦게 오는 것으로 보여요.

## 풀 크기 — 키울수록 빨라지지 않는 이유

HikariCP 위키는 출발점으로 `connections = ((core_count * 2) + effective_spindle_count)` 식을 소개해요. 위키는 이 식을 PostgreSQL 프로젝트가 출발점으로 제시한 것이라고 설명해요. 디스크 대기가 없다고 보면 코어 수를 넘는 연결은 문맥 전환 비용 때문에 느려져요.

같은 위키는 벤치마크에서 연결 수를 늘려도 처리량이 50개 근처에서 평평해졌다고 보여 줘요. 풀을 키우기 전에 앱에서 할 수 있는 일을 먼저 살펴보라고 권하기도 해요.

PostgreSQL 문서는 `max_connections`가 동시에 맺을 수 있는 연결 수의 상한이고, 기본값은 보통 100이라고 설명해요. 값을 올리면 공유 메모리 같은 자원 할당도 늘어나요. 앱 인스턴스마다 풀을 두면 DB가 받는 연결 수는 인스턴스 수와 풀 크기를 곱한 값이 돼요. 예를 들어 인스턴스가 10개이고 풀이 20개면 DB에는 연결이 200개까지 붙을 수 있어요. 예시예요.

## 느린 쿼리 연쇄 — 풀 칸을 잡고 놓지 않는 요청

예를 들어 풀 칸이 5개이고 보통 쿼리가 0.1초라고 해요. 느린 쿼리 하나가 3초 동안 칸을 잡으면, 그 칸으로 처리할 수 있던 빠른 쿼리 30개가 밀려요(예시). 빠른 쿼리 자체는 정상인데 전체가 느려 보여요.

`statement_timeout`은 칸을 빨리 돌려받게 해요. 값을 너무 짧게 잡으면 정상 쿼리까지 끊기니, 쿼리 시간 분포를 보고 정해요. 설계 판단이에요.

## 재시도 — 계층마다 곱해지는 부하

AWS Builders' Library는 다섯 단계로 호출이 이어지고 각 계층이 세 번씩 재시도하면, 마지막 DB 부하가 243배가 된다고 설명해요. 243은 3의 5제곱이에요. 같은 글은 실패 원인이 과부하일 때 부하를 키우는 재시도는 상황을 훨씬 나쁘게 만든다고 설명해요.

시뮬레이터에서 재시도를 3번으로 올리면 한 요청이 최대 4번 도착해요.

재시도 간격(백오프)과 대기 순서는 [가상 대기실 · 처리량 제한](/m/waiting-room)에서, 서버가 요청을 세는 방법은 [레이트 리밋 알고리즘](/m/rate-limiting)에서 다뤄요.

## 데드라인 전파 — 남은 시간을 아래로 넘기기

gRPC 문서는 데드라인을 걸지 않으면 클라이언트가 응답을 사실상 무한정 기다릴 수 있다고 설명해요. 그래서 현실적인 데드라인을 명시하라고 권해요.

같은 문서는 들어온 요청의 데드라인을 다른 서버 호출로 이어 받는 전파(deadline propagation)가 일부 구현에서 지원된다고 설명해요. 시각을 그대로 넘기면 두 서버의 시계가 맞지 않을 수 있어서, 이미 지난 시간을 뺀 타임아웃으로 바꿔 넘긴다고 설명해요.

HTTP에서 같은 일을 하려면 남은 시간을 요청에 실어 보내는 규칙을 팀이 정해야 해요. 이 글은 특정 헤더를 추천하지 않아요.

## FE 체크 포인트

- `fetch`에 `signal`을 넘겨 시간 제한을 거세요. MDN 예제처럼 `AbortSignal.timeout()`을 쓰면 돼요.
- 시간 초과는 `TimeoutError`로 구분하세요. MDN 문서는 시간이 다 되면 signal이 `TimeoutError` DOMException으로 중단된다고 설명해요. 화면에서는 "서버가 늦어요, 다시 해 볼까요?"와 "서버 오류예요"를 나눠 보여 주세요.
- 재시도는 멱등한 요청에만 하세요. RFC 9110은 PUT, DELETE와 안전한 메서드를 멱등하다고 정의해요. POST는 이 목록에 없어요. 결제처럼 POST로 돈이 움직이는 요청은 [결제 — 이중 결제 막기](/m/payment-idempotency)의 멱등성 키로 막으세요.
- 504를 받아도 뒤쪽 작업이 실패했다고 단정하지 마세요. 앞단이 기다리기를 멈춘 것일 수 있어요.
- 몇 분씩 걸리는 작업은 요청 안에서 기다리지 말고 [배치 작업 — 정산과 대량 처리](/m/batch-jobs)처럼 작업 리소스로 만드세요.

## 시뮬레이터 안내

아래 시뮬레이터에서 초당 요청 수, 풀 크기, 쿼리 시간, 느린 쿼리 비율, 세 계층의 시간 제한, 재시도 횟수를 바꿔 볼 수 있어요. 기본값은 프록시(5초)가 DB(10초)보다 짧아서 504가 먼저 나오고, 그 뒤에도 DB가 일하는 상태예요. DB 제한을 2초로 낮추면 경고가 사라지고, 쿼리 오류가 응답으로 돌아와요. 포기하면 취소하는 옵션을 켜면 포기 뒤 실행이 0개가 돼요.

## 정리 — 계층 순서 · 풀 크기 · 재시도 기준

시간 제한은 DB, 프록시, 클라이언트 순으로 길어지게 잡는 편이 좋아요. 풀은 작게 시작해서 부하 테스트로 늘리고, 느린 쿼리를 먼저 줄여요. 재시도는 멱등한 요청에만 하고, 한 계층에서만 해요. 504를 받으면 뒤쪽 작업이 아직 돌고 있을 수 있다고 생각해요.
