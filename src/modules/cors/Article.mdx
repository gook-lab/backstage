로컬에서는 잘 되던 API 호출이 배포 뒤에 "blocked by CORS policy" 오류로 막히는 일이 흔해요. 콘솔을 보면 서버 주소가 적혀 있는데, 정작 서버 로그에는 요청이 없는 것처럼 보이기도 해요.

이 글은 그 오류가 어디에서 생기는지, 서버에 요청이 도착했는지, 그리고 JS가 응답을 읽을 수 있는지를 차례로 나눠 봐요.

아래 시뮬레이터에서 요청 출처와 헤더, 서버 응답 설정을 바꿔 보면 브라우저의 판정이 단계별로 보여요. 글에서 말하는 규칙은 MDN CORS 가이드와 WHATWG Fetch 표준을 따라요.

## 출처 — 스킴 · 호스트 · 포트 비교 기준

출처(origin)는 스킴, 호스트, 포트를 묶은 값이에요. MDN은 두 URL의 프로토콜, 포트(지정된 경우), 호스트가 모두 같아야 같은 출처라고 설명해요. 페이지가 `https://shop.example`에서 열렸다면 아래 요청 가운데 하나라도 다르면 교차 출처 요청이 돼요.

| 요청 주소                            | 같은 출처 | 달라지는 부분 |
| ------------------------------------ | --------- | ------------- |
| `https://shop.example/api/cart`      | 같아요    | 없어요        |
| `https://api.shop.example/api/cart`  | 달라요    | 호스트        |
| `http://shop.example/api/cart`       | 달라요    | 스킴          |
| `https://shop.example:8443/api/cart` | 달라요    | 포트          |

MDN은 `fetch()`와 `XMLHttpRequest`가 동일 출처 정책을 따른다고 설명해요. 스크립트는 자기 출처에서 받은 자원을 읽을 수 있고, 다른 출처의 응답은 서버가 허락해야 읽을 수 있어요. 이 허락을 주는 장치가 CORS예요.

## CORS — 응답 읽기 허락 장치와 요청 도달

MDN은 CORS를 서버가 어떤 출처에 브라우저가 자원 로딩을 허용해야 하는지 HTTP 헤더로 알려 주는 방식이라고 설명해요. 중요한 점은 막히는 대상이 **요청이 아니라 응답 읽기**라는 거예요. 단순 요청은 브라우저가 서버에 그대로 보내고, 서버는 요청을 받아 처리해요. 응답을 스크립트에 넘기는 단계에서만 `Access-Control-Allow-Origin`이 없으면 브라우저가 막아요.

그래서 서버 로그에 요청이 남았는데도 JS에서는 실패로 보이는 일이 생겨요. MDN은 CORS 실패가 오류로 나타나지만, 보안상 JS에는 자세한 이유가 주어지지 않는다고 설명해요. 원인을 알려면 브라우저 콘솔을 봐야 해요.

## 단순 요청과 프리플라이트 — 안전 목록 밖 요청의 OPTIONS 선행

### 단순 요청 조건 — 메서드 · 헤더 · Content-Type 값

MDN은 프리플라이트 없이 나가는 단순 요청의 조건을 아래처럼 정리해요. 하나라도 벗어나면 브라우저는 실제 요청 전에 OPTIONS 요청을 먼저 보내요.

| 조건         | 단순 요청으로 보는 값                                                      | 벗어나는 예                                  |
| ------------ | -------------------------------------------------------------------------- | -------------------------------------------- |
| 메서드       | GET, HEAD, POST                                                            | DELETE, PUT                                  |
| 헤더         | Accept, Accept-Language, Content-Language, Content-Type (아래 값만)        | Authorization, 커스텀 헤더 (예: traceparent) |
| Content-Type | application/x-www-form-urlencoded, multipart/form-data, text/plain 중 하나 | application/json                             |

자격 증명은 이 조건에 들지 않아요. MDN은 단순 GET 요청에 `credentials: "include"`를 줘도 프리플라이트 없이 나간다고 설명해요. 그래서 쿠키를 붙이는 일만으로는 OPTIONS가 생기지 않아요.

### 프리플라이트 흐름 — OPTIONS 응답 뒤 실제 요청

프리플라이트는 실제 요청에 쓸 메서드와 헤더를 미리 묻는 요청이에요. 브라우저는 `OPTIONS` 메서드로 `Access-Control-Request-Method`와 `Access-Control-Request-Headers`를 보내고, 서버는 허락 헤더로 답해요.

1. 브라우저가 `OPTIONS`를 보내요. 이 요청에는 자격 증명을 싣지 않아요.
2. 서버가 `Access-Control-Allow-Origin`, `Allow-Methods`, `Allow-Headers`로 답해요.
3. 허락 조건을 통과하면 브라우저가 실제 요청을 보내요. 실패하면 실제 요청을 보내지 않아요.

Fetch 표준은 프리플라이트가 조건을 통과하지 못하면 실제 요청 대신 네트워크 오류를 돌려준다고 정해요. 그래서 서버 입장에서는 `OPTIONS`만 받고 끝나는 요청이 생겨요. 이 상황을 알아야 "서버에 요청이 안 왔다"는 판단이 맞는지 틀린지 구분할 수 있어요.

## 허락 헤더 — 다섯 헤더가 정하는 것

| 헤더                            | 정하는 것                                    | 주의                                                                                                                 |
| ------------------------------- | -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `Access-Control-Allow-Origin`   | 응답을 읽을 수 있는 출처. 단일 출처 또는 `*` | 자격 증명을 보내면 `*`를 쓸 수 없어요. 출처를 동적으로 고르면 `Vary: Origin`이 필요해요 (MDN)                        |
| `Access-Control-Allow-Methods`  | 프리플라이트에서 허락하는 메서드             | GET, HEAD, POST는 목록 없이도 돼요. `*`는 자격 증명이 없을 때만 DELETE 같은 메서드를 허락해요 (Fetch)                |
| `Access-Control-Allow-Headers`  | 프리플라이트에서 허락하는 요청 헤더          | `*`는 자격 증명이 없을 때만 커스텀 헤더를 허락해요. `Authorization`은 `*`로 허락되지 않고 이름을 적어야 해요 (Fetch) |
| `Access-Control-Max-Age`        | 프리플라이트 결과를 재사용할 초 단위 시간    | 없으면 기본값 5초예요. 브라우저마다 상한이 있어서 너무 큰 값은 그 상한으로 줄어들 수 있어요 (MDN, Fetch)             |
| `Access-Control-Expose-Headers` | JS에서 읽을 수 있는 응답 헤더 목록           | 기본으로 읽히는 헤더는 Content-Type 같은 안전 목록 헤더뿐이에요 (Fetch, MDN)                                         |

`Access-Control-Allow-Credentials: true`는 이 표에서 따로 봐요. 자격 증명을 보낼 때만 필요해요.

### 자격 증명 — 와일드카드 금지 규칙

쿠키나 HTTP 인증 정보를 교차 출처 요청에 실으려면 `fetch()`에 `credentials: "include"`를 줘요. 이때 서버는 응답에 `Access-Control-Allow-Credentials: true`를 돌려줘야 하고, `Access-Control-Allow-Origin`에 요청 출처를 정확히 적어야 해요. MDN은 `Access-Control-Allow-Origin`에 `*`가 있으면 브라우저가 응답을 막고 콘솔에 CORS 오류를 남긴다고 설명해요.

MDN은 `Allow-Origin`, `Allow-Headers`, `Allow-Methods`, `Expose-Headers` 네 헤더 모두 자격 증명 요청에서 `*`를 쓸 수 없다고 정리해요.

프리플라이트 자체는 자격 증명 없이 나가지만, 판정 기준은 실제 요청의 자격 증명 모드를 따라요. 프리플라이트가 있는 요청이라면 프리플라이트 응답의 검사도 실제 요청의 자격 증명 모드로 해요. 그래서 쿠키를 붙인 요청은 프리플라이트 응답에서도 `*`로 통과하지 못해요.

쿠키를 보낼지는 CORS와 별개의 쿠키 정책이 정해요. MDN은 서드파티 쿠키 정책이 서버의 CORS 설정과 무관하게 적용된다고 설명해요. SameSite 같은 속성의 동작은 [인증 세션 · 토큰 모듈](/m/auth-session-token)에서 다뤄요.

## 캐시와 Vary — 출처별 응답 분리

`Access-Control-Allow-Origin`에 요청 출처를 그대로 돌려주는 방식은 허락 대상이 여러 개일 때 흔해요. MDN은 이때 서버가 `Vary: Origin`을 함께 주어야 한다고 설명해요. `Vary`는 응답이 어떤 요청 헤더에 따라 달라졌는지 캐시에 알려 주고, 캐시는 그 헤더 값마다 응답을 따로 저장해요.

`Vary: Origin`이 빠지면 공유 캐시가 한 출처용 응답을 다른 출처의 요청에 다시 줄 수 있어요. 그러면 다른 출처의 브라우저는 엉뚱한 `Allow-Origin` 값을 받아 막혀요. 이 문제는 캐시 키를 어떻게 잡는지와 같은 원리예요. 캐시 키 설계는 [캐시 스탬피드 모듈](/m/cache-stampede)과 [이미지 CDN 모듈](/m/image-cdn)에서 자세히 다뤄요.

## 개발 프록시와 운영 설정 — 같은 출처 우회와 허락 헤더

개발 서버의 프록시는 브라우저가 보는 요청 주소를 페이지와 같은 출처로 바꿔요. 출처 비교 자체가 통과하니 CORS 검사도 일어나지 않아요. 그래서 로컬에서는 되고 배포에서만 막히는 일이 생겨요. 배포 환경에는 같은 프록시가 없을 수 있어요.

운영에서 같은 효과를 내는 방법은 두 가지예요.

- 페이지와 API를 같은 출처 아래에 두는 라우팅
- 서버가 허락 헤더를 정확히 주는 설정

어느 쪽을 고를지는 배포 구조와 팀의 운영 방식에 따른 설계 판단이에요. 두 방법은 서로 다른 것을 바꾸니, 로컬에서 되는 이유를 프록시에서 찾았다면 운영 설정을 따로 확인해야 해요.

## 서버 보호 범위 — CORS와 CSRF 구분

MDN은 단순 요청이 HTML 폼 제출과 비슷해서, 서버가 이미 CSRF를 막고 있어야 한다고 설명해요. CORS는 다른 출처의 스크립트가 응답을 읽는 것을 막을 뿐이에요. 요청을 처리하는 것을 막지는 않아요.

그래서 `Access-Control-Allow-Origin`을 정확히 맞췄다고 서버가 안전해지지는 않아요. 쿠키로 인증하는 API라면 CSRF 방어를 따로 설계해야 해요. 이 주제는 [인증 세션 · 토큰 모듈](/m/auth-session-token)의 CSRF 절에서 다뤄요.

## FE 체크 포인트

**오류 문구에서 헤더 이름을 먼저 읽어요.** JS에는 실패 이유가 오지 않으니 콘솔 문구가 단서예요. 문구에 `Access-Control-Allow-Origin`, `Allow-Methods`, `Allow-Headers`, `Allow-Credentials` 같은 헤더 이름이 나오면 서버 설정에서 그 헤더부터 확인해요.

**네트워크 탭에서 OPTIONS 행이 있는지 봐요.** 단순 요청이면 실제 요청 행만 있어요. 프리플라이트가 있으면 `OPTIONS` 행이 먼저 보이고, 그 응답이 실패하면 실제 요청 행이 없어요. "서버에 요청이 안 갔다"는 말이 나오면 이 행부터 확인해요.

**커스텀 헤더를 더하면 OPTIONS가 함께 늘어요.** 추적 헤더인 `traceparent`를 모든 요청에 붙이면 단순 요청이었던 호출도 프리플라이트를 부르게 돼요. 서버 허락 목록에 이름을 넣어야 하고, 이 헤더가 왜 필요한지는 [관측성 모듈](/m/observability)의 traceparent 절에서 확인할 수 있어요.

**응답 헤더를 JS에서 읽으려면 Expose-Headers를 써요.** 페이지 수나 남은 요청 수처럼 FE가 값을 읽어야 하는 헤더도 기본으로는 읽히지 않아요. 예를 들어 `Retry-After`는 429 응답에서 다시 시도할 시점을 알려 주는 헤더인데, 교차 출처에서 읽으려면 Expose-Headers에 적혀 있어야 해요. 429의 의미는 [요청 제한 모듈](/m/rate-limiting)에서 다뤄요.

**로컬과 배포의 출처를 같은 기준으로 비교해요.** 개발 프록시가 있으면 로컬은 같은 출처처럼 보여요. 배포 환경에서 요청 주소의 스킴, 호스트, 포트를 확인하고 그 출처를 서버 설정과 맞춰요.

## 시뮬레이터 안내 — 요청과 서버 응답 설정 비교

시뮬레이터는 요청 대상, 메서드, 헤더, 자격 증명을 고르고 서버가 주는 허락 헤더를 바꾸면서 판정을 따라가요. 기본값은 페이지 `https://shop.example`에서 `https://api.shop.example`으로 JSON POST를 보내는 상황이에요. 서버는 아무 허락 헤더도 주지 않아요.

이 설정에서는 OPTIONS만 서버에 도착하고 실제 요청은 나가지 않아요.

세 가지 설정을 순서대로 바꿔 보세요.

- `Allow-Origin *`과 `Allow-Headers` 목록을 주면 프리플라이트가 통과해요.
- 자격 증명을 켜고 `Allow-Origin *`을 고르면 프리플라이트부터 막히는 것을 볼 수 있어요.
- Expose-Headers에 `ETag`를 체크하면 JS가 읽는 헤더 목록이 늘어나요.

이 시뮬레이터는 MDN과 Fetch 표준의 판정 규칙을 옮긴 모델이에요. 실제 브라우저는 세부 구현이 다를 수 있어요.

MDN은 WebKit 계열 브라우저가 Accept, Accept-Language, Content-Language 헤더 값에 추가 제한을 둔다고 설명해요. 그 부분은 이 모델에 넣지 않았어요.

## 정리 — 실패 지점 나누기와 허락 헤더 설계

CORS 실패는 먼저 요청이 나갔는지, 프리플라이트가 막혔는지, 응답 읽기가 막혔는지를 나눠서 봐요. 서버 로그에 요청이 없으면 OPTIONS부터 확인하고, 있으면 응답 헤더를 확인해요.

허락 헤더는 필요한 만큼만 주는 편이 안전해요. 자격 증명을 쓸 때는 출처를 명시하고 `Allow-Credentials: true`를 함께 줘요. 출처를 동적으로 고르면 `Vary: Origin`을 빠뜨리지 않아요. 프리플라이트가 잦다면 커스텀 헤더를 줄이거나 Max-Age로 결과를 재사용하는 방법을 검토해요.
