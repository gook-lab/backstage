댓글 옆 신고 버튼은 간단해 보여도, 백엔드(BE)에서는 여러 일이 동시에 생겨요. 같은 사람이 버튼을 두 번 누르고, 응답을 놓친 클라이언트가 자동으로 다시 보내고, 여러 사람이 같은 댓글을 신고해요. 여러 계정을 모아 한 댓글을 몰아서 신고하는 경우도 있어요. 이 글에서는 신고를 어떻게 한 번만 세고, 자동 숨김을 언제 걸고, 검수 대기열을 두 검수자가 나눠 처리하게 하는지 정리해요.

아래 시뮬레이터에서 신고 수, 재시도, 유니크 제약, 임계값, 조직적 신고, 검수자 수, 대기열 방식을 바꿔 보면 숨김 시점과 두 번 처리되는 항목이 어떻게 달라지는지 볼 수 있어요. 글의 수치는 모두 예시예요.

## 증상 — 같은 댓글에 신고가 쌓이는 네 가지 경로

프론트엔드(FE)에는 "신고가 접수됐어요" 토스트 하나만 보이지만, 백엔드(BE)에는 같은 대상에 여러 행이 들어올 수 있어요.

| 경로             | 무슨 일이 생기나                                   | BE에서 볼 것                        |
| ---------------- | -------------------------------------------------- | ----------------------------------- |
| 버튼 중복 클릭   | 같은 사람이 같은 요청을 짧은 간격으로 두 번 보내요 | 신고자와 대상이 같은 행이 여러 개   |
| 네트워크 재시도  | 응답을 놓친 클라이언트가 같은 요청을 다시 보내요   | 요청 내용은 같고 응답만 빠진 경우   |
| 여러 사용자 신고 | 문제가 있다고 본 사람들이 각자 신고해요            | 서로 다른 신고자 수                 |
| 조직적 신고      | 여러 계정이 한 댓글을 짧은 시간에 몰아서 신고해요  | 서로 다른 계정이 한 시간대에 몰려요 |

앞의 두 경로는 같은 사람의 중복이에요. 뒤의 두 경로는 사람이 여럿이라서 같은 방법으로 막히지 않아요. 이 차이가 이 글의 중심이에요.

## 신고 중복 — (신고자, 대상) 유니크 제약으로 한 번만 세기

같은 사람의 중복 신고는 DB에서 막는 편이 안전해요. 앱에서 "이미 신고했는지 SELECT 하고, 없으면 INSERT"로 짜면 두 요청이 동시에 SELECT를 통과할 수 있어요. 둘 다 "아직 없음"을 보고 둘 다 INSERT 하면 같은 사람의 행이 두 개 생겨요.

PostgreSQL 문서는 유니크 제약이 지정한 열들의 값 조합을 테이블 전체에서 유일하게 만든다고 설명해요. 그래서 `(reporter_id, target_id)` 조합에 제약을 걸면 두 번째 INSERT는 충돌로 처리돼요.

```sql
CREATE TABLE content_reports (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  target_id   bigint NOT NULL,
  reporter_id bigint NOT NULL,
  reason      text NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now(),
  UNIQUE (reporter_id, target_id)
);

INSERT INTO content_reports (target_id, reporter_id, reason)
VALUES ($1, $2, $3)
ON CONFLICT (reporter_id, target_id) DO NOTHING;
```

PostgreSQL INSERT 문서는 ON CONFLICT DO NOTHING이 충돌한 행을 넣지 않고 넘어간다고 설명해요. 넘어간 경우에는 기존 신고 행을 다시 읽어서, 처음 신고할 때와 같은 응답을 만들어요. 같은 요청이 여러 번 와도 결과가 한 행으로 모인다는 점에서 [결제 멱등성](/m/payment-idempotency)과 같은 원리예요. 좋아요처럼 (사용자, 대상) 쌍을 한 행으로 두는 방식은 [핫 카운터](/m/hot-counters) 글에서 다뤘어요.

| 방식                                 | 두 요청이 동시에 오면                         | 주의                                  |
| ------------------------------------ | --------------------------------------------- | ------------------------------------- |
| 앱에서 SELECT 후 INSERT              | 둘 다 없다고 보고 행이 두 개 생길 수 있어요   | 검사와 저장이 떨어져 있어요           |
| 유니크 제약 + ON CONFLICT DO NOTHING | 행은 하나만 남고, 나머지는 같은 응답을 받아요 | 제약에 쓴 열 조합을 API 계약과 맞춰요 |

### 취소 후 재신고 — 일부 행에만 걸리는 유일성

신고를 취소한 뒤 다시 신고하게 하려면 제약을 전체 행에 걸 수 없어요. PostgreSQL 문서는 일부 행에만 적용되는 유일성은 유니크 제약으로 쓸 수 없고, 유니크 부분 인덱스로 강제할 수 있다고 설명해요. 취소되지 않은 신고끼리만 같은 조합을 막으려면 `WHERE withdrawn_at IS NULL` 조건의 부분 인덱스를 쓰는 편이 좋아요.

## 집계와 자동 숨김 — 임계값은 사람 수가 아니라 집계 수

자동 숨김은 "집계 수가 임계값에 닿으면 숨긴다"로 정의해요. 예시로 임계값을 5건으로 둘게요. 실제 서비스의 값이 아니라 계산을 따라가기 위한 숫자예요. 중요한 것은 무엇을 세느냐예요.

예를 들어 실제 신고자 3명이 한 댓글을 신고하고, 각자 재시도를 두 번씩 했다고 해 볼게요. 예시 결과는 다음과 같아요.

| 집계 기준           | 예시 집계        | 임계값 5건 기준      | 장단점                                                               |
| ------------------- | ---------------- | -------------------- | -------------------------------------------------------------------- |
| 요청 행 수          | 9건              | 숨김                 | 구현이 가장 단순해요. 같은 사람의 재시도가 그대로 부풀려요           |
| 중복 제외 신고자 수 | 3명              | 숨기지 않아요        | 같은 사람의 중복은 막아요. 여러 계정은 여전히 세요                   |
| 신고자 신뢰도 가중  | 0.3~1.0배 (예시) | 가중치에 따라 달라요 | 조직적 신고의 영향을 낮출 수 있어요. 가중치 기준을 설명하기 어려워요 |

임계값을 낮추면 빨리 숨기지만 오탐이 늘어요. 임계값을 높이면 오탐은 줄고, 정책 위반 글이 검수 전까지 더 오래 보여요. 이 균형은 서비스가 감수할 위험에 따라 정해요.

자동 숨김은 삭제가 아니라 검수 중인 임시 상태로 두는 편이 좋아요. 그래야 오탐이 나도 되돌릴 수 있어요. 상태 전이는 아래 상태 모델에서 다뤄요.

## 조직적 신고 — 서로 다른 계정이 한 글을 노리는 경우

유니크 제약은 같은 계정의 중복만 막아요. 계정이 다르면 제약에 걸리지 않아요. 그래서 조직적 신고는 집계 방식과 계정 쪽 신호로 따로 다뤄야 해요. 시뮬레이터에서 조직 신고 계정을 임계값 이상으로 두고 유니크 제약을 켜 보면, 정상 글이 자동으로 숨겨지는 것을 볼 수 있어요.

프론트엔드(FE)에서는 "정상 글이 갑자기 가려졌어요" 같은 문의로 드러나요. 백엔드(BE)에서는 짧은 시간에 한 대상으로 몰린 신고 행을 먼저 찾아야 해요.

대응은 여러 겹으로 쌓는 편이 좋아요.

- **신고 속도 제한**: 한 계정이 짧은 시간에 보낼 수 있는 신고 수를 제한해요. 제한 방식은 [요청 제한](/m/rate-limiting) 글에서 다뤘어요.
- **집중 신고 표시**: 짧은 시간에 몰린 신고를 표시하고, 자동 숨김 대신 검수 우선순위를 올려요.
- **계정 신뢰도**: 가입 기간이나 과거 신고 정확도를 가중치로 써요. 가중치 기준은 문서로 남겨요.
- **되돌리기 경로**: 오탐으로 숨긴 글은 복원으로 고쳐요. 복원 기록도 남겨요.

## 검수 대기열 — 우선순위, 담당자 배정, 잠금

숨겨진 글은 검수 대기열에 들어가요. 대기열에는 보통 세 가지가 필요해요. 우선순위(위험 유형과 신고 수), 담당자 배정(지금 누가 보고 있는지), 처리 상태(대기, 검수 중, 완료)예요.

우선순위는 정렬로 해결해요. 위험 유형이 높은 항목을 먼저 두고, 같은 등급이면 신고 수가 많은 항목을 먼저 두는 식이에요. 이 기준은 설계 판단이에요. 어려운 부분은 두 검수자가 같은 항목을 동시에 고르는 경우예요.

### 일반 SELECT — 같은 항목을 두 검수자가 고르는 경로

```sql
SELECT id
FROM moderation_queue
WHERE status = 'pending'
ORDER BY priority DESC, created_at
LIMIT 1;
```

두 검수자가 같은 순간에 이 쿼리를 실행하면, 둘 다 같은 `id`를 받아요. 둘 다 검수를 시작하고, 결정이 두 번 저장되고, 처리 기록도 두 번 남아요. 잠금이 없어서 생기는 일이에요.

### FOR UPDATE SKIP LOCKED — 잡힌 항목 건너뛰기

```sql
BEGIN;

SELECT id
FROM moderation_queue
WHERE status = 'pending'
ORDER BY priority DESC, created_at
LIMIT 1
FOR UPDATE SKIP LOCKED;

UPDATE moderation_queue
SET status = 'reviewing', assignee_id = $1
WHERE id = $2;

COMMIT;
```

PostgreSQL SELECT 문서는 FOR UPDATE가 선택한 행을 동시 수정에 대해 잠근다고 설명해요. 명시적 락 문서는 그 잠금이 현재 트랜잭션이 끝날 때까지 다른 트랜잭션의 수정, 삭제, 잠금을 막는다고 설명해요. SKIP LOCKED를 붙이면 바로 잠글 수 없는 행을 기다리지 않고 건너뛰어요. SELECT 문서는 잠긴 행을 건너뛰면 데이터가 일관되지 않게 보일 수 있어서 범용 작업에는 맞지 않고, 여러 소비자가 큐처럼 쓰는 테이블에서 잠금 경합을 피하는 데 쓸 수 있다고 설명해요. 검수 대기열이 바로 그 경우예요.

잠금은 트랜잭션이 끝날 때까지 유지돼요. 그래서 검수 한 건을 몇 분씩 붙잡는 긴 트랜잭션으로 만들면 안 돼요. 배정은 짧은 트랜잭션으로 끝내고, `reviewing` 상태와 배정 시각을 남기는 편이 좋아요. 일정 시간이 지나도 결정이 없으면 배정을 풀어 다른 검수자가 잡게 해요. 워커가 작업을 가져가는 구조는 [백그라운드 작업](/m/background-jobs) 글에서 상태 전이로 다뤘어요.

| 방식                                       | 같은 항목을 두 번 고르나               | 주의                                                  |
| ------------------------------------------ | -------------------------------------- | ----------------------------------------------------- |
| 일반 SELECT                                | 고를 수 있어요                         | 결정이 두 번 저장될 수 있어요                         |
| FOR UPDATE SKIP LOCKED                     | 잠긴 항목은 고르지 않아요              | 잠긴 행은 목록 조회에서 빠져 보여요. 큐 전용으로 써요 |
| 조건부 UPDATE (`WHERE status = 'pending'`) | 한 명만 성공하고 나머지는 0행을 받아요 | 실패한 검수자는 다음 항목을 다시 골라야 해요          |

조건부 UPDATE가 한 명만 성공하는 이유는 [장바구니와 재고](/m/cart-stock) 글에서 다룬 원자적 UPDATE와 같아요.

## 콘텐츠 상태 모델 — 게시, 숨김, 삭제, 복원

상태는 네 가지로 나눠요. 작성자와 다른 사용자에게 보이는 것이 다르다는 점이 핵심이에요.

| 상태             | 작성자에게            | 다른 사용자에게 | 들어오는 경로          |
| ---------------- | --------------------- | --------------- | ---------------------- |
| 게시             | 원문                  | 원문            | 작성 완료, 복원        |
| 숨김 (검수 중)   | 원문과 "검수 중" 표시 | 보이지 않아요   | 자동 임계값, 자동 필터 |
| 삭제 (정책 위반) | 삭제 사실과 안내      | 보이지 않아요   | 검수자가 확정          |
| 복원             | 원문                  | 원문            | 검수 기각, 이의 인정   |

작성자에게 원문을 보여 주는 쪽을 설계 판단으로 골라요. 작성자가 무엇이 숨겨졌는지 알아야 이의 제기를 할 수 있기 때문이에요.

전이는 네 방향이에요. 게시에서 숨김으로 가는 길은 자동 규칙이 열고, 숨김에서 게시로 돌아가는 길은 검수 기각이 열어요. 숨김에서 삭제로 가는 길은 검수자가 확정할 때만 열고, 삭제에서 복원으로 가는 길은 이의가 인정될 때만 열어요.

삭제를 행 자체의 제거로 처리하면 이의 제기의 근거가 사라져요. 지운 행을 남기고 상태만 바꾸는 방식은 [소프트 삭제](/m/soft-delete) 글에서 다뤘어요.

보는 사람에 따라 응답이 달라지면 캐시도 나눠야 해요. 작성자용 응답이 다른 사용자에게 캐시되면 숨긴 원문이 새어 나갈 수 있어요. 응답을 나누는 헤더는 [HTTP 캐시](/m/http-caching) 글의 Vary 설명을 참고해 보세요.

## 결정 기록과 이의 제기 — 누가 왜 바꿨는지 남기기

결정마다 행위자, 대상, 이전 상태, 새 상태, 이유 코드, 근거 신고 목록, 시각을 남겨요. 자동 규칙이 결정했다면 행위자 자리에 규칙 id를 넣어요. 기록은 고치지 않고 덧붙이기만 하는 테이블에 두는 편이 좋아요. 이 방식은 [감사 이력](/m/audit-history) 글에서 다뤘어요.

이의 제기는 같은 항목을 새 검수 건으로 다시 대기열에 넣는 방식으로 처리해요. 처음 결정한 검수자는 배정 대상에서 빼서, 같은 사람이 자기 결정을 다시 승인하지 않게 해요.

유럽연합(EU)의 디지털 서비스법(DSA)은 온라인 플랫폼에 비슷한 절차를 요구해요. 원문에서 확인한 내용은 이래요.

- 제16조는 누구나 불법 콘텐츠를 알릴 수 있는 통지 및 조치 절차를 두라고 정해요. 제16조 5항은 결정을 통지하고, 불복 방법에 대한 정보를 함께 주라고 정해요.
- 제17조는 콘텐츠 노출을 제한할 때 제한을 받는 이용자에게 결정 이유를 설명하라고 정해요. 설명에는 결정 내용과 기간, 결정 사실과 근거, 자동화 수단 사용 여부, 불복 방법이 들어가요.
- 제20조는 결정에 대해 최소 6개월 동안 무료이고 전자적으로 접수할 수 있는 내부 불복 절차를 요구해요.
- 제19조는 소규모 기업에는 이 절을 적용하지 않는다고 정해요. DSA는 EU 규정이라서, 여기서는 결정 이유와 불복 경로를 설계하는 참고 기준으로만 써요.

## 신고자 정보 — 작성자에게 신고자를 보여 주지 않는 방식

DSA 제17조 3항 (b)는 결정 이유에 신고가 있었는지 밝히되, 신고자의 신원은 "엄격히 필요한 경우"에만 밝히라고 정해요. 기본값은 가리는 쪽이에요. 신고 내용에 신고자의 이름과 이메일을 담도록 돕는 조항은 제16조 2항 (c)에 있어요. 이 정보는 사업자가 신고를 처리할 때 쓰는 값이고, 작성자 화면에 보여 줄 값은 아니에요. 어디까지 보여 줄지는 설계 선택이에요.

| 항목                 | 작성자 화면        | 검수자 화면               | 근거                                      |
| -------------------- | ------------------ | ------------------------- | ----------------------------------------- |
| 신고가 있었다는 사실 | 결정 이유에 넣어요 | 보여요                    | DSA 제17조 3항 (b)                        |
| 신고 건수            | 보여 주지 않아요   | 보여요                    | 설계 선택                                 |
| 신고자 id와 이메일   | 보여 주지 않아요   | 권한이 있는 검수자만 봐요 | DSA 제17조 3항 (b)의 "엄격히 필요한 경우" |

응답 DTO도 나눠요. 작성자용 응답에 `reporter_id` 같은 값이 섞이면 화면에서 숨겨도 네트워크에서 보여요. 어떤 필드를 누구에게 내보낼지는 [권한](/m/authorization) 글의 객체 수준 검사로 막아요.

## 자동 필터와 사람 검수 — 역할 나누기

금칙어 필터는 빠르고 값이 싸요. 대신 띄어쓰기나 비슷한 글자로 우회되고, 문맥을 몰라서 정상 글도 걸려요. 사람 검수는 문맥을 보지만 느리고 비싸요. 둘에게 같은 일을 맡기면 둘 다 나빠져요.

역할을 나누는 방법은 이래요.

- 필터는 숨김을 직접 확정하지 않고, 검수 대기열에 올리고 우선순위를 높이는 역할만 해요.
- 명백한 금칙어는 작성 시점에 거절하고, 거절 사유를 사용자에게 바로 알려요.
- 필터가 걸린 규칙 id를 결정 기록에 남겨서, 나중에 규칙을 고칠 때 근거로 써요.

필터가 숨긴 글은 사람이 확인할 때까지 임시 상태로 두는 편이 좋아요. 오탐이 나도 되돌릴 수 있어요.

## FE 체크 포인트 — 응답 상태를 화면에 맞추기

**신고 버튼은 서버 응답의 상태를 따라요.** 이미 신고한 경우를 응답으로 알려 주면, 버튼을 "신고함"으로 바꿀 수 있어요. 중복 클릭으로 두 번째 요청이 와도 같은 성공 응답이 돌아와요.

예시 응답은 이래요.

```json
{ "reportId": 1821, "status": "received", "alreadyReported": true }
```

**작성자 화면에는 검수 상태를 보여 줘요.** "검수 중이에요. 결과가 나오면 알림으로 알려 드릴게요." 같은 문구면 충분해요. 알림 설계는 [알림 받은 편지함](/m/notification-inbox) 글에서 다뤘어요.

**다른 사용자 화면에는 자리 표시만 보여요.** "이 댓글은 가려졌어요" 정도로 쓰고, 사유나 신고 수는 보여 주지 않아요.

**이의 제기 버튼은 기간 안에서만 열어요.** 기간이 지나면 버튼을 숨기고, 기간이 끝났다는 이유를 한 줄로 알려요. 기간은 서비스가 정해요. DSA 제20조는 EU 플랫폼에 최소 6개월을 요구하는 예시로만 참고해요.

## 시뮬레이터 안내 — 중복 제약, 임계값, 대기열 방식 조합

아래 시뮬레이터는 정책 위반 글 하나, 정상 글 하나, 그리고 대기열에 이미 있던 글들을 시간 단위(틱)로 돌려요. 조절할 수 있는 값은 이래요.

- **실제 신고자 수와 재시도 횟수**: 같은 사람의 중복과 실제 사람 수를 나눠 봐요.
- **유니크 제약**: 켜면 같은 사람의 재신고를 한 번만 세요. 다른 계정의 조직 신고는 그대로 세요.
- **자동 숨김 임계값과 조직적 신고 계정 수**: 정상 글이 숨겨지는 조건을 봐요.
- **검수자 수와 대기열 방식**: 일반 SELECT와 SKIP LOCKED의 차이를 봐요.

결과는 네 가지예요. 숨김 시점, 중복 처리 수(같은 사람의 중복 신고가 집계된 수), 오탐 숨김(정상 글이 숨겨진 수), 같은 항목을 두 번 처리한 수예요. 수치는 감을 잡기 위한 예시예요.

## 이미 있는 글과 겹치는 부분 — 링크로 넘기기

이 글은 신고와 검수에 필요한 판단만 다뤄요. 아래 주제는 각 글에서 자세히 봐요.

- 같은 신고를 여러 번 보내도 결과가 하나로 모이는 방식: [결제 멱등성](/m/payment-idempotency)
- 신고 수를 한 행의 카운터로 세면 생기는 핫스팟: [핫 카운터](/m/hot-counters)
- 검수 결정과 처리 기록을 남기는 방식: [감사 이력](/m/audit-history)
- 삭제 상태를 행으로 남기는 방식: [소프트 삭제](/m/soft-delete)
- 누가 신고 기록과 신고자 정보를 볼 수 있는지: [권한](/m/authorization)

## 정리 — 유니크 제약 · 집계 기준 · 잠금 방식 · 상태 모델 · 이의 경로

신고 중복은 (신고자, 대상) 유니크 제약과 ON CONFLICT DO NOTHING으로 한 번만 세요. 다시 신고한 사용자에게는 처음과 같은 응답을 주는 편이 좋아요.

자동 숨김은 삭제가 아니라 검수 중 상태로 두고, 임계값은 중복을 뺀 사람 수 기준으로 세는 편이 오탐을 줄여요. 조직적 신고는 유니크 제약이 막지 못하므로 속도 제한과 계정 신뢰도로 따로 다뤄요.

검수 대기열은 FOR UPDATE SKIP LOCKED로 잡아서 두 검수자가 같은 항목을 처리하지 않게 해요. 잠금은 트랜잭션이 끝날 때까지 유지되므로, 배정은 짧은 트랜잭션으로 끝내요.

상태는 게시, 숨김, 삭제, 복원으로 나누고, 작성자와 다른 사용자에게 보이는 것을 따로 정해요. 결정 이유와 이의 경로는 감사 이력으로 남겨요.
