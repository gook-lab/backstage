로그인 버튼을 누르면 공급자 화면으로 갔다가 우리 주소로 돌아와요. 돌아온 주소에는 `code`라는 값이 들어 있어요. 이 값을 프론트에서 바로 토큰으로 바꿔도 되는지, 그 전에 `state`와 PKCE가 무엇을 막는지가 이 글의 질문이에요.

이 글은 인가 코드 흐름과 PKCE를 중심으로 다뤄요. 공급자 설정 화면은 다루지 않고, 프로토콜이 정한 규칙만 봐요. 로그인 뒤 세션을 만드는 방법은 [로그인 유지 글](/m/auth-session-token)에서 이어서 봐요.

## 인가 코드 흐름 — 리다이렉트 · code · 토큰 교환 순서

RFC 6749는 인가 코드 흐름을 이렇게 설명해요. 앱이 공급자의 인가 주소로 보내고, 사용자가 로그인과 동의를 하고, 공급자가 `redirect_uri`로 `code`를 돌려주고, 앱이 `code`를 토큰으로 바꿔요.

| 단계      | 누가 누구에게         | 실리는 값                                              | 브라우저 주소창에 보이나요?            |
| --------- | --------------------- | ------------------------------------------------------ | -------------------------------------- |
| 인가 요청 | 앱 → 공급자 인가 주소 | `client_id`, `redirect_uri`, `state`, `code_challenge` | 예. 쿼리로 나가요.                     |
| 콜백      | 공급자 → 앱 주소      | `code`, `state`                                        | 예. 주소에 남아요.                     |
| 토큰 교환 | 앱 → 토큰 엔드포인트  | `code`, `redirect_uri`, `code_verifier`                | 아니요. 주소와 무관한 직접 요청이에요. |

`code`는 토큰이 아니에요. 토큰 엔드포인트에 한 번 교환해야 토큰을 받아요(RFC 6749 4.1). 토큰이 주소창에 나오지 않는다는 점이 이 흐름의 핵심이에요.

## implicit 흐름 — 토큰이 URL에 실리는 이유

implicit 흐름은 교환 단계가 없어요. RFC 6749는 implicit에서 액세스 토큰을 인가 응답의 fragment(`#` 뒤)로 돌려준다고 설명해요. 토큰이 주소에 그대로 남아요.

RFC 9700은 인가 응답에 액세스 토큰을 싣는 응답 타입을 쓰지 않도록(SHOULD NOT) 권해요. 토큰이 유출되거나 재사용될 수 있고, 인가 응답에서 발급된 토큰을 특정 클라이언트에 묶는 표준 방법이 없기 때문이에요. RFC 9700은 이 유출 경로를 여러 절에서 따로 다뤄요.

IETF 초안은 브라우저 클라이언트가 implicit을 쓰면 안 된다고(MUST NOT) 적어요. 이 초안은 아직 RFC가 아니에요.

| 흐름             | 토큰이 어디로 오나   | 교환 단계 | RFC 9700 권장                            |
| ---------------- | -------------------- | --------- | ---------------------------------------- |
| 인가 코드 + PKCE | 토큰 엔드포인트 응답 | 있음      | 공개 클라이언트는 PKCE를 써야 해요(MUST) |
| implicit         | 인가 응답의 fragment | 없음      | 쓰지 않는 편이 좋아요(SHOULD NOT)        |

## state — 콜백의 출처 확인

RFC 6749 10.12는 리다이렉트 주소에 대한 CSRF를 막으라고 해요. 클라이언트는 `state`를 인가 요청에 싣는 것이 좋고(SHOULD), 콜백에서 돌아온 값이 자기가 보낸 값과 같은지 확인해요. 값은 추측할 수 없어야 하고(MUST), 사용자 에이전트의 인증 상태와 묶여야 해요.

RFC 9700은 `state`에 앱의 상태(돌아갈 화면 등)를 담는다면, 그 내용이 바뀌지 않게 보호해야 한다고(MUST) 설명해요.

`state`는 콜백이 이 브라우저가 시작한 요청에 대한 응답인지만 확인해요. 가로챈 `code`를 토큰으로 바꾸는 공격은 `state`로 막지 않아요. 그 몫은 PKCE가 맡아요.

## PKCE — code_verifier와 S256 code_challenge

PKCE(RFC 7636)는 `code`를 낸 주인이 교환 요청을 한 주인과 같은지 증명하는 장치예요. 앱은 무작위 `code_verifier`를 만들고, 그 SHA-256 해시를 `code_challenge`로 인가 요청에 실어요. 토큰 교환 때는 원래 값인 `code_verifier`를 보내요. 서버는 해시가 맞는지 확인해요.

| 값               | 만드는 곳                      | 보내는 시점    | 공격자가 가로챈 code만 가졌을 때     |
| ---------------- | ------------------------------ | -------------- | ------------------------------------ |
| `code_verifier`  | 앱이 무작위로 만들어요         | 토큰 교환 요청 | 없으니 교환 요청을 증명할 수 없어요. |
| `code_challenge` | `code_verifier`의 SHA-256 해시 | 인가 요청      | 해시라서 교환 요청에 쓸 수 없어요.   |

RFC 7636은 `code_verifier`를 43~128자의 허용 문자로 만들도록 정해요. `code_challenge`는 `BASE64URL-ENCODE(SHA256(ASCII(code_verifier)))`로 계산해요. 방식은 `S256`이고, 쓸 수 있으면 `S256`을 써야 해요(MUST). `plain`은 `S256`을 쓸 수 없을 때만 써요.

`code_challenge_method`를 생략하면 `plain`이 기본값이에요(RFC 7636). 그래서 FE 코드에서는 `S256`을 명시하는 편이 좋아요.

RFC 9700은 공개 클라이언트가 PKCE를 써야 한다고(MUST) 하고, 비밀값을 가진 클라이언트도 PKCE를 권장한다고(RECOMMENDED) 해요. `code_challenge`는 거래마다 새로 만들어야 해요.

## redirect_uri — 등록 주소와 문자열 정확 일치

RFC 9700은 등록된 리다이렉트 주소와 요청의 주소를 정확한 문자열로 비교해야 한다고(MUST) 설명해요. 예외는 네이티브 앱 localhost의 포트 번호뿐이에요. 주소가 느슨하게 맞으면 공격자가 자기 주소로 `code`를 받을 수 있어요.

RFC 6749 10.6은 교환 요청의 `redirect_uri`가 인가 요청에서 쓴 것과 같아야 한다고 설명해요. 개발 주소와 배포 주소는 따로 등록해야 해요. 끝에 슬래시가 붙는지도 글자 단위로 같아야 해요.

## 클라이언트 비밀값 — 공개 클라이언트와 PKCE

RFC 6749는 클라이언트를 비밀을 지킬 수 있는 기밀 클라이언트와, 지킬 수 없는 공개 클라이언트로 나눠요(2.1). 브라우저에서 도는 JavaScript 번들에 넣은 값은 사용자가 읽을 수 있어요. 그래서 브라우저 앱은 공개 클라이언트로 봐야 해요.

공개 클라이언트는 `client_secret` 없이 `client_id`만 보내요(RFC 6749 4.1.3). 대신 PKCE로 교환 요청의 주인을 증명해요. RFC 9700은 공개 클라이언트에 PKCE를 요구해요.

## 브라우저 앱의 토큰 교환 — PKCE 직접 교환과 서버 중계

프론트에서 바로 교환해도 PKCE가 있으면 흐름이 막히지는 않아요. 다만 토큰이 JavaScript가 읽을 수 있는 곳에 남아요. IETF 초안은 세 가지 구조를 보안 순서대로 설명해요. 아래 표는 그 순서를 옮긴 것이에요.

| 구조                   | 토큰을 누가 들고 있나                  | 초안의 평가                                                         |
| ---------------------- | -------------------------------------- | ------------------------------------------------------------------- |
| BFF (6.1)              | 서버가 쿠키 세션에 보관해요            | 가장 안전한 패턴이라고 설명해요. 브라우저에는 토큰이 없어요.        |
| 토큰 중계 백엔드 (6.2) | 서버가 받고, 앱이 액세스 토큰을 받아요 | BFF보다 가볍지만 덜 안전하다고 설명해요.                            |
| 브라우저 단독 (6.3)    | 브라우저 JavaScript                    | 브라우저 안 악성 코드의 여러 시나리오에 그대로 노출된다고 설명해요. |

프론트에서 바로 교환하는 구조는 세 번째에 가까워요. 토큰을 JavaScript가 쥐고 있으면 XSS 한 번으로 빠질 수 있어요. XSS를 줄이는 방법은 [보안 헤더 글](/m/security-headers)과 이어서 봐요. 교차 출처 토큰 엔드포인트를 브라우저가 부르는 규칙은 [CORS 글](/m/cors)에서 다뤄요.

## ID 토큰 검증 — iss · aud · exp · nonce · 서명 항목

OpenID Connect Core 1.0의 3.1.3.7은 클라이언트가 ID 토큰을 받았을 때 확인할 항목을 정해요. 이 항목을 확인하지 않으면 다른 앱이나 다른 공급자가 발급한 토큰을 우리 로그인으로 받아들일 수 있어요.

| 항목    | 확인하는 것                                                                       | 빠지면 생기는 일                         |
| ------- | --------------------------------------------------------------------------------- | ---------------------------------------- |
| `iss`   | 발급자 식별자가 기대한 값과 정확히 같아요.                                        | 다른 공급자가 발급한 토큰을 받아요.      |
| `aud`   | `client_id`가 `aud`에 있어요. 신뢰하지 않는 `aud`가 더 있으면 거부해요.           | 다른 앱용 토큰을 우리 로그인으로 받아요. |
| `exp`   | 현재 시각이 `exp` 이전이에요.                                                     | 만료된 토큰을 받아요.                    |
| `nonce` | 인가 요청에 보낸 값과 같아요. 요청에 보냈다면 토큰에 `nonce`가 있어야 해요(MUST). | 재사용된 토큰을 받아요.                  |
| 서명    | 공급자 키로 JWS 서명을 검증해요. 검증 알고리즘은 헤더의 `alg` 값을 따라요.        | 위조된 토큰을 받아요.                    |

명세는 예외를 하나 둬요. 클라이언트가 토큰 엔드포인트에서 TLS로 직접 받은 ID 토큰이라면, 서명 검증 대신 TLS로 발급자를 확인해도 된다고(MAY) 적어요. 다른 경로로 받은 ID 토큰은 서명을 검증해야(MUST) 해요. 브라우저 앱이 교환 응답을 직접 받는 구조라면 이 예외가 적용될 수 있어요. 서명을 검증해 두면 이 예외에 기댈 필요가 없어요. 이 선택은 구현 판단이에요.

ID 토큰은 인증 결과를 담는 값이고, API 호출에 쓰는 액세스 토큰과는 용도가 달라요. 두 토큰을 섞어 쓰지 않는 편이 좋아요.

## 계정 연결 — 같은 이메일을 자동으로 묶는 위험

공급자가 주는 `sub`는 발급자 안에서 같은 사용자를 가리키는 값이에요. OpenID Connect Core 1.0은 `sub`가 발급자 안에서 유일하고 다시 할당되지 않는다고(never reassigned) 설명해요. 그래서 계정을 찾을 때는 이메일보다 `iss`와 `sub`의 조합을 키로 쓰는 편이 좋아요.

`email`은 키로 쓰기에 약해요. `email_verified`가 `true`여도 명세는 그 검증이 이뤄진 시점에 공급자가 이메일을 확인했다는 뜻이라고만 설명해요. 확인 방법은 상황마다 다르다고 해요. 우리 서비스가 그 이메일을 지금도 쓰고 있다는 보장은 아니에요.

| 연결 방식                               | 키            | 위험                                                                               |
| --------------------------------------- | ------------- | ---------------------------------------------------------------------------------- |
| 같은 이메일이면 자동으로 묶기           | `email`       | 확인되지 않았거나 나중에 다른 사람에게 넘어간 이메일로 남의 계정에 묶일 수 있어요. |
| `iss` + `sub`로 저장하고 새 계정 만들기 | `iss` + `sub` | 기존 계정과 이어 주지 않아서 중복 계정이 생길 수 있어요.                           |
| 기존 계정에 로그인한 뒤 연결하기        | 로그인한 계정 | 연결 화면과 확인 절차를 만들어야 해서 비용이 들어요.                               |

자동 연결은 편하지만, 이메일 확인이 빠지는 순간 계정이 넘어갈 수 있어요. 기존 계정에 로그인한 뒤 연결하는 방식이 더 안전해요. 이 판단은 설계 판단이고, 서비스가 감수할 위험 범위에 따라 달라질 수 있어요.

## 로그인 뒤 세션 — 토큰을 세션으로 바꾸는 지점

로그인이 끝나면 앱은 로그인 상태를 기억해야 해요. 쿠키 속성, 저장 위치, 토큰 갱신은 [로그인 유지 글](/m/auth-session-token)에서 다뤄요. 이 글은 그 앞 단계, 즉 공급자의 응답을 어디까지 믿을지만 봐요.

민감한 값이 로그에 남는 문제는 [민감 데이터 글](/m/sensitive-data)에서 이어서 봐요. `code`가 로그나 분석 도구로 새지 않게 마스킹하는 것도 같은 문제예요.

## FE 체크 포인트 — 콜백 화면에서 맞추는 것

**`state`와 `code_verifier`는 콜백 화면에서 다시 읽을 수 있어야 해요.** 교환에 쓴 뒤에는 지워요. 저장 위치는 설계 판단이에요.

**`code`는 한 번만 교환해요.** RFC 6749는 클라이언트가 같은 인가 코드를 두 번 쓰면 안 된다고(MUST NOT) 설명해요. React 개발 모드(StrictMode)처럼 콜백 효과가 두 번 실행되면 두 번째 교환이 실패해요. 교환 요청을 한 번만 보내도록 가드를 두세요.

**콜백 주소에서 `code`를 바로 지워요.** 주소창에 남은 값은 기록과 리퍼러로 새기 쉬워요. 교환을 마친 뒤 `history.replaceState`로 주소를 정리하는 방법은 설계 판단으로 고르세요.

**실패 응답을 화면에서 구분해요.** 공급자가 돌려준 오류, `state` 불일치, 교환 실패를 같은 문구로 뭉치면 원인을 찾기 어려워요. 로그인 버튼으로 다시 시작하는 길을 함께 보여 주세요.

## 시뮬레이터 안내 — 흐름과 공격 시나리오 비교

시뮬레이터는 흐름 네 가지와 공격 시나리오 네 가지를 골라 볼 수 있어요. 흐름은 인가 코드 + PKCE, PKCE 없음, state 없음, implicit이에요. 공격은 정상 로그인, 가로챈 code 또는 토큰 사용, 위조된 콜백, 토큰이 URL에 남음이에요.

- **인가 코드 + PKCE**: 가로챈 code는 토큰 교환에서 막혀요. 위조된 콜백은 state에서 막혀요.
- **PKCE 없음**: 가로챈 code가 그대로 토큰으로 바뀌어요.
- **state 없음**: 콜백 출처는 확인하지 않아요. 그래도 PKCE가 위조된 콜백을 교환 단계에서 막아요.
- **implicit**: 토큰이 URL에 있어서, 가로채거나 기록에서 꺼내면 바로 쓸 수 있어요.

시뮬레이터는 프로토콜을 줄여 그린 모델이에요. 실제 공급자가 보내는 응답의 순서와 항목은 다를 수 있어요.

## 정리 — 흐름 · 검사 · 계정 연결 결정

브라우저 앱은 인가 코드 흐름과 PKCE를 써요. implicit 흐름은 권장되지 않아요. `state`는 콜백의 출처를 확인하고, PKCE는 가로챈 `code`를 교환에서 막아요. 토큰을 프론트에서 받을지 서버가 중계할지는 토큰을 어디에 둘지에 따라 정해요.

ID 토큰은 `iss`, `aud`, `exp`, `nonce`, 서명을 확인한 뒤에만 로그인 판단에 써요. 계정은 이메일 하나로 자동 연결하지 않고, `iss`와 `sub`를 키로 저장하는 편이 좋아요.
