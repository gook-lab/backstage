비밀번호 재설정 링크에 토큰을 `?token=`으로 붙여 보내면, 그 값은 화면 코드 밖에서도 여러 곳에 남아요. 서버 접근 로그, 브라우저 기록, 에러 추적 도구, 분석 이벤트가 모두 요청 주소를 기록할 수 있어요. 이 글은 민감한 값이 새는 경로를 하나씩 따라가요. 예시 값은 모두 가짜예요.

## 증상 — 재설정 토큰이 로그와 분석 도구에 남은 경로

FE가 보기에는 링크 하나예요. `https://shop.example/reset?token=reset-EXAMPLE-token-0001`로 이동하고, 화면은 토큰을 읽어 비밀번호를 바꾸게 해요. 문제는 이 주소가 화면 밖으로 여러 번 나간다는 점이에요. 서버는 요청 줄을 기록하고, 브라우저는 주소를 저장하고, 페이지가 외부 스크립트를 불러오면 주소 일부가 Referer로 실려요.

원인은 값을 어디에 두었는지예요. 주소에 둔 값은 "기록되는 자리"에 있고, 본문이나 헤더에 둔 값은 기록되지 않는 설정이 많아요. 아래 시뮬레이터에서 같은 토큰을 세 자리에 두고 비교해 볼 수 있어요.

## URL은 공유되는 값 — 서버 로그와 프록시

RFC 9110은 URI가 보호되는 값이 아니라 공유되도록 만들어진 것이라고 설명해요. 많은 서버, 프록시, 사용자 에이전트가 대상 URI를 기록하거나 보여 주므로, 민감하거나 개인을 식별하거나 노출되면 위험한 정보를 URI에 넣지 않는 편이 좋다고 권해요.

서버 접근 로그는 요청 줄을 그대로 남겨요. 요청 줄에는 메서드와 경로와 쿼리가 함께 들어가요. 그래서 `?token=`에 든 값은 웹 서버 로그에 한 줄씩 남아요. RFC 9110은 프록시도 대상 URI를 기록할 수 있다고 설명해요. 로그를 받아 보는 장비와 사람이 많을수록 값이 퍼져요.

FE에서 할 수 있는 일은 많지 않아요. 서버 로그 설정은 BE가 바꿔요. 그래서 토큰을 주소에 넣지 않는 쪽이 가장 확실한 방법이에요.

## 브라우저 기록 — 주소 전체가 저장되는 자리

OWASP 세션 관리 치트 시트는 세션 식별 값을 URL로 주고받으면 웹 링크, 로그, 브라우저 기록과 북마크, Referer 헤더, 검색 엔진에 노출될 수 있다고 설명해요. 재설정 토큰도 같은 문제예요. 쿼리가 있는 주소로 이동하면 브라우저 기록에 주소 전체가 남아요.

시뮬레이터에서 토큰을 쿼리에 두면 브라우저 기록 줄에 나타나요. 본문이나 헤더에 두면 나타나지 않아요. 페이지 이동이 본문 없이 이루어지기 때문이에요.

## Referer — 외부 자원 요청에 실리는 쿼리

`Referer`는 요청이 어느 페이지에서 나왔는지 대상 서버에 알려 주는 헤더예요. MDN은 이 헤더에 출처, 경로, 쿼리 문자열이 들어갈 수 있다고 설명해요. 경로와 쿼리가 들어가면, 재설정 페이지가 외부 이미지나 분석 스크립트를 불러올 때 그 주소가 외부 서버로 가요.

MDN은 `Referrer-Policy` 기본값을 `strict-origin-when-cross-origin`으로 설명해요. 이 값이면 HTTPS에서 HTTPS로 가는 교차 출처 요청에는 출처만 가고 쿼리는 빠져요. `unsafe-url`로 바꾸면 모든 요청에 경로와 쿼리가 함께 가요. 헤더 값을 고르는 자세한 표는 [보안 헤더 글](/m/security-headers)에 있어요. 이 글에서는 쿼리 값이 Referer로 나가는지만 봐요.

## 로그 마스킹과 허용 목록 — 값을 가리는 방식과 고르는 방식

앱 로그를 남기는 방법은 크게 두 가지예요. 하나는 값을 가리는 마스킹이고, 다른 하나는 허용한 필드만 기록하는 허용 목록이에요.

OWASP 로깅 치트 시트는 세션 식별 값, 액세스 토큰, 인증 비밀번호, 카드 소유자 데이터처럼 기록하면 안 되는 값을 나열해요. 이런 값은 직접 기록하지 말고 제거, 마스킹, 정화, 해시, 암호화 중 하나로 처리하라고 권해요. 같은 치트 시트는 로그 줄 위조를 막으려면 비구조 텍스트 대신 JSON 같은 구조화된 형식을 쓰라고 설명해요.

| 방식      | 남는 것                  | 한계                                                                      |
| --------- | ------------------------ | ------------------------------------------------------------------------- |
| 원본 기록 | 요청 값 전부             | 목록에 있는 값이 전부 새요                                                |
| 마스킹    | 값 자리는 `***`로 남아요 | 키 이름으로 찾아 가려서, 목록에 없는 이름의 값은 가려지지 않아요          |
| 허용 목록 | 허용한 필드만 남아요     | 새 필드를 추가할 때 목록을 같이 봐야 해요. 빠진 필드는 디버깅에 안 보여요 |

마스킹은 값의 이름을 알아야 해요. `token` 이라는 키로 보낸 값은 가려지지만, `t`나 `q` 같은 이름으로 보낸 값은 가려지지 않아요. 그래서 FE가 쓰는 파라미터 이름을 로그 설정과 맞춰 두는 것이 중요해요. 로그 내용을 고르는 기준은 [관측성 글의 로그 내용 절](/m/observability)에서 더 자세히 봐요.

## 에러 추적 — 요청 본문과 헤더 정리

에러 추적 도구는 오류가 난 순간의 요청 정보를 함께 보내요. 주소, 본문, 헤더가 여기에 들어갈 수 있어요. 본문에는 이메일과 카드 번호가, 헤더에는 인증 값이 들어 있을 수 있어요.

설계 판단으로는 에러 추적으로 나가기 전에 본문과 헤더를 지우는 편이 좋아요. 이 설정은 에러 보고 쪽에서 한 번만 하면 모든 오류에 적용돼요. 다만 주소의 쿼리는 본문과 다른 자리라서 따로 지워야 해요. 본문과 헤더를 지워도 `?token=`은 주소에 남아 에러 추적 도구로 나가요.

## 분석 이벤트 — 페이지 주소와 속성 설계

분석 도구는 보통 페이지 주소와 사용자 행동 이벤트를 받아요. 주소 전체가 자동으로 담기는지, 폼 값을 속성으로 붙이는지는 설정과 코드에 따라 달라요. 이 부분은 출처가 정한 규칙이 아니라 설계 판단이에요.

분석 이벤트 속성을 설계할 때는 허용 목록을 쓰는 편이 좋아요. 예를 들어 `page_path`와 `button_id`처럼 이름이 정해진 속성만 보내고, 이메일이나 토큰은 속성으로 만들지 않아요. 주소도 쿼리를 떼고 경로만 보내면 토큰이 분석 도구에 남지 않아요.

## 과다 노출 — 응답 필드 최소화

이 글의 문제는 요청에서 값이 새는 것만이 아니에요. 응답에 필요 이상 필드를 내려도 민감한 값이 나가요. OWASP API Security Top 10 2023의 API3, Broken Object Property Level Authorization은 이 문제를 다뤄요. OWASP 페이지는 이 항목의 이전 이름이 Excessive Data Exposure 였다고 적어요. 페이지는 API가 민감한 객체 속성을 노출하면 취약하다고 설명해요.

OWASP는 `to_json()` 같은 범용 메서드 대신 필요한 속성만 골라 응답하라고 권해요. 반환하는 데이터 구조는 필요한 만큼만 두라고 설명해요. 예를 들어 사용자 객체를 통째로 내리면 `passwordHash` 같은 필드까지 브라우저에 도착해요. 응답 필드가 줄면 FE가 쓰지 않는 값을 들고 다니지 않게 돼요.

FE 입장에서는 응답을 보면서 쓰는 필드만 타입에 두는 습관이 도움이 돼요. 필요 없는 필드가 많으면 BE에 필드 목록을 물어보세요. 권한이 있는 값과 없는 값을 나누는 판단은 [인가 글](/m/authorization)에서 이어서 봐요.

## 보존 기간 — 필요한 기간과 노출 면적

로그와 분석 데이터는 오래 남을수록 노출 면적이 넓어져요. OWASP 로깅 치트 시트는 로그 데이터가 요구되는 보존 기간이 끝나기 전에 지워져서는 안 되고, 그 기간을 넘겨 보관해서도 안 된다고 설명해요. 기간은 법률이나 정책에 따라 정해야 하므로 이 글은 숫자를 드리지 않아요.

시뮬레이터의 보존 기간 숫자는 예시예요. 짧게 두면 노출 기간이 줄고, 길게 두면 같은 값이 오래 남아요. 기간을 정할 때는 장애 조사에 필요한 기간과 개인정보 보관 원칙을 같이 보세요.

## FE 체크 포인트 — 화면에서 맞추는 것

**토큰과 비밀값은 주소에 넣지 않는 쪽으로 요청을 설계해요.** 재설정 같은 흐름에서는 값을 본문으로 보내는 편이 좋아요. RFC 9110도 민감한 값을 GET 쿼리로 만들면 POST가 자주 선호된다고 설명해요. 다만 POST는 캐시가 되지 않고 안전하지 않은 메서드라는 점도 같이 봐야 해요.

**외부 스크립트를 부르는 페이지에서는 Referrer-Policy를 확인해요.** 값이 주소에 남은 페이지라면 외부 요청에 쿼리가 실리지 않도록 정책을 맞춰 달라고 요청해요.

**에러 보고 설정에서 본문과 헤더를 정리하는지 확인해요.** 정리 설정이 있는지, 주소 쿼리는 어떻게 다루는지 같이 확인해요.

**화면이 쓰지 않는 응답 필드를 타입에서 빼요.** 필드가 많으면 BE에 필요한 필드만 내려 달라고 요청하고, 로컬에서는 실제 응답을 한 번 열어 민감한 필드가 있는지 봐요.

## 시뮬레이터 안내 — 저장소별 남는 값 비교

시뮬레이터에서는 요청 하나와 설정을 고르면 여섯 저장소에 남는 값이 나와요. 요청은 토큰, 이메일, 카드 번호가 어느 자리에 있는지를 정해요. 설정은 앱 로그 방식, 에러 추적 정리, 분석 이벤트 방식, Referrer-Policy, 보존 기간, 응답 필드를 정해요.

예시 세 가지를 눌러 보세요. 기본 설정에서는 토큰이 다섯 곳에 남아요. 토큰만 본문으로 옮기면 기록되는 자리가 줄지만, 앱 로그와 에러 추적과 분석에는 여전히 남아요. 마스킹, 에러 정리, 분석 설계, Referrer-Policy까지 맞추면 남는 곳이 없어져요.

시뮬레이터는 실제 도구의 동작을 흉내 낸 순수 모델이에요. 실제 도구의 기본값은 설정마다 다르니, 이 결과를 그대로 옮기지 말고 사용하는 도구의 설정을 확인하세요.

## 정리 — 값 자리 옮기기 · 저장소별 정책 나누기

토큰은 주소 대신 본문으로 보내요. 앱 로그는 마스킹이나 허용 목록으로 기록하고, 에러 추적은 본문과 헤더를 지우고 주소 쿼리까지 봐요. 분석 이벤트는 허용한 속성만 보내고, Referrer-Policy는 쿼리가 빠지도록 맞춰요. 응답은 필요한 필드만 내리고, 로그와 분석 데이터는 필요한 기간만 보관해요.
