API 응답에서 `nickname`을 `displayName`으로 바꾸는 배포를 떠올려 봐요. 서버를 먼저 올리면 옛 앱이 `nickname`을 찾다가 빈 이름을 보여 줘요. 앱을 먼저 올리면 새 앱이 `displayName`을 찾는데 옛 서버가 `nickname`만 응답해요. 어느 쪽으로 가든, 두 버전이 같은 시간에 떠 있는 동안에는 한쪽이 깨질 수 있어요.

이 글은 그 "동시에 떠 있는 시간"을 어떻게 설계할지 정리해요. 아래 시뮬레이터에서 같은 이름 변경을 한 번에 바꾸는 방식과 단계별로 바꾸는 방식으로 나눠 돌려 볼 수 있어요. 시간축에서 어느 조합이 언제 깨지는지 확인해요.

## 롤링 배포 중 두 버전이 함께 도는 구간 — 복제본을 조금씩 바꾸는 방식

Kubernetes Deployment는 새 ReplicaSet을 만들고, 새 Pod를 늘리면서 옛 ReplicaSet의 Pod를 줄이는 방식으로 교체해요. 문서는 이 교체를 정해진 속도로 한다고 설명해요. 기본값은 maxSurge와 maxUnavailable이 각각 25%예요. 그래서 교체가 끝나기 전까지 옛 Pod와 새 Pod가 함께 떠 있어요.

FE도 같은 문제를 겪어요. 이미 열린 탭은 배포 전에 받은 번들로 계속 동작해요. 서버는 새 응답을 보내는데 탭은 옛 코드인 상황이 생겨요. 모바일 앱은 사용자가 업데이트하기 전까지 옛 버전이 남아요.

| 구간                  | 서버 응답                   | FE 번들                          | 생기는 일                                                |
| --------------------- | --------------------------- | -------------------------------- | -------------------------------------------------------- |
| 배포 전               | 옛 모양만                   | 옛 번들                          | 문제 없어요                                              |
| 롤링 중               | 옛 Pod와 새 Pod가 섞여 응답 | 새 번들을 받은 탭과 옛 탭이 섞임 | 같은 사용자도 요청마다 다른 모양의 응답을 받을 수 있어요 |
| 롤링 끝, 옛 탭이 남음 | 새 모양만                   | 옛 번들                          | 옛 번들이 옛 필드를 찾다가 깨져요                        |

이 표의 마지막 줄을 놓치기 쉬워요. 서버 배포가 끝났다고 옛 클라이언트가 없어지지는 않아요.

## 한 번에 바꾸기 — 옛 응답과 새 응답이 겹치는 자리

한 번에 바꾸면 서버는 `displayName`만 보내고, FE도 `displayName`만 읽는 번들로 같은 날 나가요. 이때 깨지는 조합은 두 가지예요.

- 옛 번들과 새 서버: 옛 번들은 `nickname`을 찾아요. 필드가 없으면 빈 이름이 보이거나 에러가 나요.
- 새 번들과 옛 서버: 롤링이 끝나기 전에는 새 번들이 옛 Pod의 응답을 받을 수 있어요. 그 응답에는 `displayName`이 없어요.

FE를 먼저 올리면 두 번째 조합이 생기고, 서버를 먼저 올리면 첫 번째 조합이 생겨요. 같은 날 같이 올려도 롤링이 끝날 때까지 두 조합이 함께 있어요. 그래서 "같이 배포했으니 괜찮다"는 가정은 맞지 않아요.

## 펼치고 옮기고 줄이기 — expand-and-contract 순서

Martin Fowler는 이 패턴을 Parallel Change라고 부르고, 세 단계로 나눠요. 인터페이스를 펼쳐서 옛 것과 새 것을 함께 지원하는 expand, 옛 것을 쓰는 쪽을 새 것으로 옮기는 migrate, 옛 것을 걷어내는 contract예요. 이 순서를 따르면 클라이언트가 깨지지 않게 하면서 새 버전을 조금씩 확인할 수 있어요.

API 이름 변경에 대입하면 이렇게 돼요.

| 단계      | 서버 응답                                | FE 번들                                          | 되돌릴 때 생기는 일                                                  |
| --------- | ---------------------------------------- | ------------------------------------------------ | -------------------------------------------------------------------- |
| 1. 펼치기 | `nickname`과 `displayName`을 함께 보내요 | 아직 `nickname`을 읽어요                         | 서버를 옛 코드로 되돌리면 `nickname`만 가요. 옛 번들과 맞아요        |
| 2. 옮기기 | 두 필드를 계속 보내요                    | `displayName`을 읽고, 없으면 `nickname`을 읽어요 | FE를 옛 코드로 되돌려도 서버가 두 필드를 주므로 맞아요               |
| 3. 줄이기 | `displayName`만 보내요                   | 옛 번들을 쥔 사용자이 없을 때 빼요               | 응답에 `nickname`을 다시 넣어야 해요. 원본 데이터가 남아 있어야 해요 |

중요한 점은 **3단계를 언제 하느냐**예요. 옛 번들을 쥔 사용자이 남아 있는 동안 줄이면 그 사용자의 요청이 깨져요. 시뮬레이터에서 "옛 필드를 빼는 시각"을 옛 번들 정리 기간보다 앞당기면 옛 번들 조합 칸에 깨진 요청이 생기는 걸 볼 수 있어요.

## DB 스키마 변경 — 락 수준과 백필을 나누는 기준

API와 같은 순서를 DB 칼럼에도 적용해요. 다만 DB에서는 **어떤 DDL이 테이블을 얼마나 오래 잠그는지**를 먼저 봐야 해요. PostgreSQL 문서에 따르면 ALTER TABLE은 명시가 없으면 ACCESS EXCLUSIVE 락을 잡아요. 이 락은 같은 테이블의 SELECT도 막아요. 일반 SELECT가 잡는 ACCESS SHARE 락이 ACCESS EXCLUSIVE와 충돌하기 때문이에요.

| 작업                                                    | 테이블 재작성                                    | 주의                                                                                       |
| ------------------------------------------------------- | ------------------------------------------------ | ------------------------------------------------------------------------------------------ |
| 기본값 없이 칼럼 추가                                   | 없어요. 새 칼럼 값은 NULL이에요                  | 락은 잡지만 재작성은 없어요                                                                |
| 상수 기본값으로 칼럼 추가                               | 없어요. 기본값은 메타데이터에 저장돼요           | 문서가 설명하는 동작이에요. 버전별 차이는 공식 문서를 확인해요                             |
| volatile 기본값으로 칼럼 추가 (예: `clock_timestamp()`) | 테이블과 인덱스 전체를 재작성해요                | 큰 테이블에서 오래 걸리고 디스크 공간이 최대 두 배까지 필요해요                            |
| NOT NULL 지정 (SET NOT NULL)                            | 재작성은 없지만 전체 스캔을 해요                 | 이미 검증된 CHECK 제약이 있으면 스캔을 건너뛸 수 있어요                                    |
| 칼럼 타입 변경                                          | 보통 재작성해요                                  | 예외가 있어요. 예외인지 문서로 확인해요                                                    |
| 칼럼 삭제 (DROP COLUMN)                                 | 물리적으로 바로 지우지 않고 보이지 않게 만들어요 | 공간을 실제로 돌려받으려면 재작성 명령이 따로 필요해요                                     |
| 인덱스 만들기 (CREATE INDEX)                            | 쓰기를 막아요. 읽기는 가능해요                   | CONCURRENTLY는 쓰기를 막지 않지만 테이블을 두 번 읽고, 트랜잭션 블록 안에서는 쓸 수 없어요 |

인덱스는 `CONCURRENTLY`를 쓰는 편이 안전해요. 다만 실패하면 `invalid` 인덱스가 남아요. 문서가 권하는 복구는 그 인덱스를 지우고 다시 만드는 거예요.

```sql
CREATE INDEX CONCURRENTLY idx_user_display_name ON user_profile (display_name);
-- 실패했다면 invalid 인덱스를 확인하고 지운 뒤 다시 만들어요
```

### 락 대기 — lock_timeout으로 상한 두기

락을 기다리는 시간이 길어지면 뒤에 쌓인 요청이 같이 멈춰요. `lock_timeout`은 락을 기다릴 때만 적용돼서, 긴 쿼리 자체를 끊지는 않아요. 문서는 전역 `postgresql.conf`에 두는 것을 권하지 않으니, 마이그레이션 세션에서만 짧게 걸어 두고 실패하면 다시 시도하는 편이 나아요.

### 백필 — 행 묶음을 나눠 커밋하기

새 칼럼에 옛 행의 값을 채우는 백필은 한 번의 UPDATE로 끝내지 않아요. 긴 트랜잭션 하나가 많은 행을 오래 잡으니까요. 예를 들어 천 건씩 끊어서 커밋하고, 사이에 짧게 쉬면서 진행률을 기록해요.

숫자는 테이블 크기와 부하에 맞춰 정해요. 이 숫자는 이 글에서 권장하는 값이 아니고, 예시일 뿐이에요.

DB 쪽 순서도 펼치고 옮기고 줄이는 방식이에요.

1. 새 칼럼을 추가해요. 기본값을 두지 않으면 재작성이 없어요.
2. 앱이 옛 칼럼과 새 칼럼에 함께 써요.
3. 백필로 옛 행을 새 칼럼으로 채워요.
4. 앱이 새 칼럼을 읽도록 바꿔요.
5. 옛 칼럼을 읽고 쓰는 코드가 없어지고 롤백 기간이 지난 뒤에 지워요.

각 단계 사이가 롤백 지점이에요. 5단계를 서두르면 되돌릴 데이터가 사라져요.

## API 하위 호환 — 추가는 안전, 이름 변경과 삭제는 위험

응답 변경을 옛 클라이언트 입장에서 나눠 보면 기준이 생겨요. 이 표의 "안전"은 옛 클라이언트가 모르는 필드를 무시한다는 가정이 있을 때의 판단이에요. 이 가정은 클라이언트 설계로 지켜야 해요.

| 변경                          | 옛 클라이언트 입장                              | 판단 |
| ----------------------------- | ----------------------------------------------- | ---- |
| 필드 추가                     | 모르는 필드는 무시해요                          | 안전 |
| 필드 이름 변경                | 옛 이름을 읽으면 값이 없어요                    | 위험 |
| 필드 삭제                     | 값을 읽는 곳에서 없는 값을 만나요               | 위험 |
| 타입 변경 (숫자에서 문자열로) | 파싱이나 비교가 조용히 틀어져요                 | 위험 |
| 새 열거형 값 추가             | 모르는 값을 받았을 때 처리 분기가 없으면 깨져요 | 주의 |

필드를 추가할 때도 "모르는 필드를 무시한다"는 규칙을 클라이언트가 지켜야 안전해요. 엄격하게 검증하는 클라이언트는 추가 필드에도 깨질 수 있어요.

## 버전 관리와 Deprecation · Sunset 헤더 — 신호와 차단을 나누기

헤더는 옛 버전을 알리는 신호예요. 차단 장치가 아니에요.

- **Deprecation** (RFC 9745): 리소스가 deprecated 됐다는 신호예요. RFC는 deprecation 표시 자체가 리소스의 동작을 바꾸지 않는다고 명시해요. 값은 `Deprecation: @1688169599`처럼 유닉스 시간 앞에 `@`를 붙인 형식이에요.
- **Sunset** (RFC 8594): URI가 특정 시각에 응답하지 않을 가능성이 크다고 알려요. 값은 HTTP-date예요. 이 헤더를 붙여도 응답이 멈추지는 않아요.

RFC는 두 헤더를 리소스(URI) 단위의 신호로 정의해요. 응답의 한 필드에 붙이는 것은 RFC가 정한 범위가 아니라 팀이 정한 규칙이에요.

따라서 헤더를 붙인 뒤에도 옛 사용자이 실제로 남아 있는지 측정해야 해요. 옛 필드를 읽는 요청 수, 옛 앱 버전의 비율을 보고 줄이는 시점을 정해요. 측정 방법은 팀마다 달라요. 시뮬레이터의 "오래 열린 탭"이 바로 측정하지 않으면 놓치는 사용자이에요.

## FE가 할 일 — 모르는 필드 무시와 기본값

FE가 맡을 일은 세 가지예요.

**1. 읽기 함수에서 두 필드를 함께 다뤄요.** 펼치기 단계에서는 어느 쪽이 올지 모르니까요.

```ts
type UserResponse = { nickname?: string; displayName?: string };

const nameOf = (u: UserResponse) => u.displayName ?? u.nickname ?? '이름 없음';
```

**2. 없는 필드의 기본값이 조용한 오류를 가리지 않게 해요.** 기본값을 두면 깨지는 대신 빈 이름이 보여요. 화면에는 정상처럼 보이니 알아채기 어려워요. 기본값을 쓸 때는 그 경우를 로그로 남겨요.

**3. 옛 필드 사용처를 목록으로 관리해요.** Deprecation이나 Sunset 헤더가 붙은 필드를 쓰는 화면을 찾아 두면, 3단계에서 무엇을 확인할지 분명해요.

오래 열린 탭은 FE가 직접 알려 줘야 해요. 빌드 버전이 바뀌었으면 새로고침을 안내하는 방식이 흔해요. 모바일 앱은 업데이트가 늦으니, 서버는 최소 지원 버전을 정하고 그 이전 버전의 Sunset 기간을 길게 잡아요.

## 시뮬레이터 — 배포 방식별 조작법

아래 시뮬레이터는 사용자 요청 한 건마다 서버 응답 모양과 FE 번들을 뽑고, 둘이 맞는지로 깨짐을 판정해요. 간단한 모델이라서 실제 서비스의 수치가 아니에요. 다음을 직접 바꿔 보세요.

1. 기본값인 "한 번에 바꾸기"에서 깨진 조합 칸을 확인해요.
2. "단계별로 바꾸기"로 바꾸고 오래 열린 탭을 0%로 두면 깨진 요청이 사라져요.
3. 오래 열린 탭을 5%로 되돌리고 옛 필드를 빼는 시각을 앞당겨 보세요. 충분히 기다려도 옛 탭이 남은 만큼 깨져요.
4. 시드를 바꾸면 같은 조건에서 사용자 흐름이 달라져요.

## 정리 — 두 버전이 함께 있는 시간을 설계하기

- 롤링 배포는 옛 서버와 새 서버를 같은 시간에 세워요. 열린 탭과 모바일 앱도 옛 번들을 계속 써요.
- 이름 변경은 펼치고, 옮기고, 줄이는 순서로 나눠요. 줄이는 시점은 옛 사용자이 남았는지 측정해서 정해요.
- DB 변경은 락 수준을 먼저 보고, 인덱스는 `CONCURRENTLY`로 만들고, 백필은 나눠서 해요.
- 응답 변경은 추가가 안전하고 이름 변경과 삭제가 위험해요. Deprecation과 Sunset은 신호일 뿐이에요.
- FE는 두 필드를 함께 읽고, 기본값이 오류를 숨기지 않게 하고, 오래 열린 탭을 다룰 방법을 가져요.
