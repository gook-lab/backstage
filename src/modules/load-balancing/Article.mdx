배포할 때마다 몇 초 동안 `502 Bad Gateway`가 떠요. 웹소켓 (WebSocket) 화면은 연결이 끊겼다가 다시 붙어요. 서버 코드를 바꾸지 않았는데도 요청은 서버를 바꾸는 동안 다른 곳으로 가요. 이 글은 로드밸런서가 요청을 어느 서버로 보내는지, 서버가 내려갈 때 무슨 일이 생기는지를 따라가요. 502, 503, 504가 각각 어느 단계에서 나는지도 나눠 봐요.

글의 시간과 횟수는 예시예요. 아래 시뮬레이터의 기본값과 같아요. 실제 값은 로드밸런서와 플랫폼 설정에 따라 달라요.

## 요청이 가는 곳 — 정상으로 판정된 등록 대상

AWS ALB 문서는 로드밸런서가 등록된 대상 가운데 정상인 대상으로 트래픽을 나눈다고 설명해요. 새로 등록된 대상도 첫 헬스 체크를 통과해야 요청을 받기 시작해요.

배포 도구가 서버를 대상 그룹에서 빼면 로드밸런서는 그 서버로 새 요청을 보내지 않아요. 문제는 목록에서 빠지는 시각과 프로세스가 내려가는 시각이 같지 않다는 점이에요. 그 사이에 들어온 요청은 갈 곳을 잃어요.

## 헬스 체크 — liveness와 readiness를 나누는 기준

Kubernetes 문서는 liveness probe가 컨테이너를 다시 시작할지 정하고, readiness probe는 컨테이너가 트래픽을 받을 준비가 됐는지 정한다고 설명해요. 두 신호는 실패했을 때 할 일이 달라요. liveness가 실패하면 재시작하고, readiness가 실패하면 트래픽에서만 빼요.

readiness가 실패하면 Kubernetes는 Pod의 IP를 Service에 붙은 EndpointSlice에서 지워요. 로드밸런서가 헬스 체크로 서버를 빼는 방식도 같은 생각이에요.

ALB 헬스 체크의 기본 간격은 인스턴스와 IP 대상 기준으로 30초이고, 비정상으로 판정하는 연속 실패 횟수의 기본값은 2회예요. 이 글은 서버가 실패를 시작한 뒤 목록에서 빠질 때까지 걸리는 시간을 감지 시간이라고 불러요. 간격에 연속 실패 횟수를 곱한 값으로 어림해요(이 글의 계산). 시뮬레이터도 같은 식을 써요.

## 종료 신호 — SIGTERM 뒤 서버가 하는 일

Kubernetes 문서는 Pod를 지울 때 kubelet이 컨테이너의 메인 프로세스에 SIGTERM을 보내고, 유예 시간이 지나면 KILL을 보낸다고 설명해요. 기본 유예 시간은 30초예요. 같은 때 컨트롤러는 종료 중인 Pod를 EndpointSlice에서 바로 지우지 않아요. 종료 중인 endpoint는 ready가 false로 표시되어 로드밸런서가 일반 트래픽에는 쓰지 않아요.

종료 신호와 목록 제거는 같은 때 시작하지만 끝나는 때가 달라요. 종료 신호를 받자마자 연결을 끊으면, 목록에 아직 남아 있는 동안 들어온 요청이 실패해요. 이 글은 이 틈을 배포 중 실패 구간이라고 불러요.

Kubernetes 문서는 천천히 내려가는 서버가 일반 트래픽을 더 받지 않고, 열린 연결을 마무리하며 종료를 시작해야 한다고 설명해요. 종료 순서가 중요하면 preStop 훅으로 맞추라고도 설명해요.

## 연결 드레이닝 — 목록에서 뺀 뒤 처리 중 요청 기다리기

AWS ALB 문서는 대상을 등록 해제하면 로드밸런서가 그 대상으로 요청을 보내지 않고, 대상은 진행 중 요청이 끝날 때까지 draining 상태가 된다고 설명해요. 등록 해제 지연 (deregistration delay) 값은 로드밸런서가 등록 해제된 대상을 기다려 주는 시간이고, 기본값은 300초, 범위는 0에서 3600초예요.

ALB 문제 해결 문서는 등록 해제된 대상이 처리하던 요청이 드레이닝 시간을 넘기면 502가 나올 수 있다고 적어요. 그래서 드레이닝 시간은 가장 긴 요청보다 길어야 해요. 긴 작업을 드레이닝 시간으로만 버티기보다 [백그라운드 작업](/m/background-jobs) 글처럼 나누는 편이 좋아요.

서버 프로세스가 내려가는 시각은 드레이닝과 따로 정해져요. 두 시각 가운데 빠른 쪽에서 처리 중 요청이 끊겨요. 시뮬레이터도 이 규칙을 그대로 써요.

## 502 · 503 · 504 — 실패가 나는 단계

| 코드                    | 실패가 나는 단계                                  | 흔한 원인                                                                                                                                                |
| ----------------------- | ------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 502 Bad Gateway         | 로드밸런서가 대상과 연결하거나 응답을 주고받는 중 | 대상이 TCP RST나 FIN으로 연결을 끊음. 대상의 keep-alive 시간이 로드밸런서의 idle timeout보다 짧음. 등록 해제 뒤 드레이닝 시간이 지나 처리 중 요청이 끊김 |
| 503 Service Unavailable | 받을 대상이 없거나 대상이 잠시 거절               | 등록된 대상이 없거나 모두 unused 상태. 종료 중인 서버가 새 요청을 거절                                                                                   |
| 504 Gateway Timeout     | 로드밸런서가 대상의 응답을 기다리다 포기          | 10초 안에 연결을 맺지 못함. 연결 뒤 idle timeout 동안 응답이 없음                                                                                        |

RFC 9110은 502를 게이트웨이나 프록시가 뒤쪽 서버에서 잘못된 응답을 받았을 때, 504를 뒤쪽 서버에서 제때 응답을 받지 못했을 때 쓴다고 정의해요. 503은 일시적인 과부하나 예정된 점검처럼 잠시 처리할 수 없을 때 쓰는 코드예요.

502가 항상 배포 때문은 아니에요. keep-alive 시간 불일치처럼 배포와 무관한 502도 있어요. 시간 제한이 계층마다 따로 걸리는 원리는 [시간 제한과 커넥션 풀](/m/timeouts-and-pools) 글에서 이어 봐요.

FE는 응답 코드만으로 원인을 단정하기 어려워요. 같은 503이라도 종료 중 거절인지 받을 대상이 없어서인지는 서버 쪽 로그와 함께 봐야 해요.

## 스티키 세션 — 같은 서버로 묶는 대가

ALB 문서는 스티키 세션이 로드밸런서가 만든 쿠키(lb_cookie)나 애플리케이션 쿠키로 같은 클라이언트를 같은 대상에 보내는 기능이라고 설명해요. 기본값은 꺼져 있어요.

묶는 방식의 대가는 이 글의 판단이에요. 한 서버에 묶인 클라이언트는 그 서버가 내려갈 때 한꺼번에 다른 서버로 옮겨 가요. 서버 메모리에만 있던 세션이나 임시 상태는 그때 사라질 수 있어요. 부하도 고르게 나뉘지 않아요. 긴 연결도 같은 서버에 묶여 있다가, 서버를 내리는 순간 재연결이 한꺼번에 몰려요.

스티키 없이 여러 서버에 이벤트를 전달하는 방법은 [실시간 전달](/m/realtime-delivery) 글의 백플레인 설명을 이어서 읽어 보세요.

## 롤링 배포 — 옛 버전과 새 버전이 섞이는 구간

Kubernetes Deployment의 롤링 업데이트는 maxSurge로 새 Pod를 옛 Pod 수보다 얼마나 더 띄울지 정해요. 기본값은 25%예요. 새 Pod가 준비되면 옛 Pod를 줄이는 식으로 바뀌어서, 교체가 끝나기 전까지 두 버전이 함께 응답해요.

로드밸런서는 버전을 구분하지 않아요. 요청마다 옛 서버나 새 서버로 갈 수 있어요. 같은 사용자의 연속된 요청도 다른 버전의 응답을 받을 수 있다는 뜻이에요. 응답 모양과 필드를 두 버전이 함께 맞추는 방법은 [스키마 마이그레이션](/m/schema-migration) 글에서 다뤄요. 두 버전이 같은 설정 값을 보게 하는 방법은 [기능 플래그](/m/feature-flags) 글에 있어요.

## 긴 연결 재연결 — SSE와 WebSocket이 끊기는 방식

서버 전송 이벤트 (SSE)는 연결이 끊기면 브라우저가 다시 연결해요. MDN은 서버가 보낸 retry 필드 값(밀리초)만큼 기다린 뒤 다시 연결한다고 설명해요. WHATWG 명세는 다시 연결할 때 마지막으로 받은 이벤트 id를 `Last-Event-ID` 헤더로 보낸다고 적어요. 서버가 이 헤더를 읽으면 놓친 이벤트부터 이어 보낼 수 있어요.

WebSocket은 연결이 닫히면 close 이벤트가 와요. MDN은 close 이벤트가 WebSocket 연결이 닫힐 때 발생한다고 설명해요. 다시 붙는 일은 이 이벤트를 받는 앱 코드가 맡아요.

서버가 내려갈 때는 WebSocket 연결을 닫는 코드 1001 (Going Away)로 끊을 수 있어요. RFC 6455는 1001을 서버가 내려가거나 브라우저가 페이지를 떠나는 상황의 코드로 정의해요. 재연결 간격은 점점 늘리는 편이 좋아요(이 글의 판단). 모든 클라이언트가 같은 순간에 다시 붙으면 새 서버도 부하를 받아요. 놓친 구간을 채우는 방법은 [실시간 전달](/m/realtime-delivery) 글에서 다뤄요.

## FE 체크 포인트 — 502 · 503 · 1001을 화면에서 다루기

**GET 요청은 502와 503에서 짧게 다시 시도해요.** RFC 9110은 멱등하지 않은 메서드를 의미를 확인할 수단 없이 자동으로 다시 보내면 안 된다고 설명해요. 결제나 주문처럼 두 번 실행되면 안 되는 POST는 [결제와 멱등성](/m/payment-idempotency) 글처럼 멱등성 키로 중복을 막은 뒤에 다시 보내요.

**503에 Retry-After가 있으면 그 시간을 기다려요.** RFC 9110은 Retry-After가 503과 함께 오면 서비스를 쓸 수 없을 것으로 예상되는 시간을 알려 준다고 설명해요.

**WebSocket 1001은 재연결 신호로 처리해요.** 화면에는 연결을 다시 맞추는 중이라고 보여 주고, 간격을 늘려 가며 다시 붙어요. 정상 종료를 뜻하는 1000과는 다르게 다뤄요.

**SSE는 마지막 이벤트 id를 기억해요.** 재연결 때 `Last-Event-ID`로 이어 받으려면 서버가 각 이벤트에 id를 붙이는지 확인해요.

## 시뮬레이터 안내

아래 시뮬레이터는 배포 한 번을 90초 시간 축에 그려요. 요청은 0.5초마다 들어오고, 서버 1이 교체 대상이에요. 점의 모양이 응답이에요. 진한 점은 502, 빈 점은 503이에요.

기본 설정은 종료 신호 전 대기가 0초예요. 종료 신호가 가는 10초부터 목록에서 빠지는 30초 전까지 종료 중인 서버가 503으로 거절해요. 종료 신호 전 대기를 감지 시간인 20초만큼 늘리면 실패가 사라져요. 바로 종료를 고르면 종료 뒤 들어온 요청과 처리 중 요청이 502로 끊겨요.

## 정리 — 감지 시간 · 드레이닝 · 종료 순서 기준

- 종료 신호는 로드밸런서가 서버를 목록에서 뺄 시간을 준 뒤에 보내요. 이 간격은 감지 시간(간격 × 연속 실패 횟수)보다 길게 둬요.
- 드레이닝 시간은 가장 긴 요청보다 길게 두고, 더 긴 작업은 백그라운드 작업으로 나눠요.
- 종료 신호를 받으면 새 요청은 거절하고, 진행 중 요청만 마무리해요.
- liveness로 재시작을 정하고, readiness로 트래픽에서 빼요.
- 긴 연결은 재연결 간격과 재연결 신호(1001, `Last-Event-ID`)를 함께 설계해요.
