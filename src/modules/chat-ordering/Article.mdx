채팅방에서 내가 보낸 메시지가 전송 직후에는 위쪽에 보였는데, 새로고침하면 아래로 내려가요. 상대 기기에서는 또 다른 순서로 보이고, 안 읽은 수도 기기마다 달라요. 화면만 보면 버그처럼 보이지만, 원인은 메시지 순서를 누가 정하는지에 있어요.

이 글은 순서를 기기 시계가 아니라 서버 순번으로 정하는 이유를 다뤄요. 보내는 순간 그린 임시 행을 서버 순번으로 옮기는 방법, 재전송이 중복 저장되지 않게 하는 id, 재연결 뒤 빈 구간을 채우는 방법, 읽음 위치로 안 읽은 수를 계산하는 방법, 과거 메시지를 커서로 불러오는 방법을 차례로 봐요. 연결 방식 자체(폴링 · SSE · WebSocket)와 재연결의 일반 규칙은 [실시간 알림](/m/realtime-delivery) 글에서 다뤘어요. id 생성 방식은 [분산 ID](/m/distributed-ids) 글과 이어져요.

아래 시뮬레이터에서 기기 시계 오차, 네트워크 지연, 노트북 연결 끊김, 재전송을 바꿔 보세요. 기기마다 보이는 순서와 안 읽은 수가 어떻게 달라지는지 바로 보여요. 수치는 모두 예시예요.

## 정렬 기준 — 기기 시계 대신 서버 순번

메시지 순서를 기기 시계로 정하면 두 가지 문제가 생겨요. 기기 시계는 서로 맞지 않을 수 있어요. 메시지가 기기를 떠나 서버에 도착하기까지 걸리는 시간도 메시지마다 달라요.

Lamport는 1978년 논문에서 한 사건이 다른 사건보다 먼저 일어났다는 관계(happened-before)를 정의해요. 이 관계는 모든 사건을 줄 세우지 못하는 부분 순서예요. 논문은 시계 조건(Clock Condition)을 세우고, 동률은 프로세스의 임의 순서로 깨면 전체 순서를 만들 수 있다고 설명해요. 논문은 물리 시계가 얼마나 어긋날 수 있는지도 상한으로 다뤄요.

Matrix 명세도 방의 이벤트마다 서버가 depth 값을 붙이고, 앞선 이벤트는 depth가 더 작아야 한다고 정해요. 순서를 클라이언트 시각에 맡기지 않는다는 점에서 같은 방향이에요.

채팅은 한 방의 메시지를 서버가 받아요. 그래서 서버가 도착한 순서대로 방 단위 번호(순번)를 붙이면 모든 기기가 같은 순서를 봐요. 이 순번은 보낸 순서가 아니라 서버에 도착한 순서예요. 순번만 보고는 누가 먼저 보냈는지 알 수 없어요. "내가 먼저 보냈는데 아래로 간다"는 현상도 보낸 시각이 아니라 도착이 늦었기 때문에 생겨요.

### 보낸 기기 시각 — 시계 오차 그대로 반영

보낸 기기의 시계로 찍은 시각은 그 기기의 오차를 그대로 가져요. 나 폰 시계가 30초 빠르면 내 메시지는 상대가 그 뒤에 보낸 메시지보다 뒤에 정렬돼요. 시뮬레이터에서 나 폰 시계 오차를 +30초로 두고 '보낸 기기 시각'을 고르면 이 현상을 볼 수 있어요.

### 서버 수신 시각 — 초 단위 기록의 동률

서버 수신 시각은 기기 시계에서 벗어나요. 대신 초 단위로 기록하면 같은 초에 도착한 메시지가 같은 값이 돼요. 이때 동률을 id 같은 임의 규칙으로 깨면 서버 도착 순서와 다른 순서가 나와요. 시뮬레이터에서 이 기준을 고르면 같은 초에 온 '내 1'과 '상대 1'의 순서가 뒤집혀요.

### 기기가 받은 순서 — 기기마다 달라지는 기준

각 기기가 메시지를 받은 순서대로 쌓으면 기기마다 순서가 달라져요. 재연결 때 채운 메시지는 나중에 받으니 뒤로 밀려요. 이 글에서는 피해야 할 기준으로 다뤄요.

### 서버 순번 — 방 단위 정수 발급

서버는 방마다 늘어나는 정수를 한 곳에서 발급해요. 기기 시계에 기대지 않으니 모든 기기가 같은 순서를 봐요. 순번을 발급하는 자리가 여럿이면 순번이 겹치지 않게 하는 장치가 따로 필요해요. 이것도 설계 판단이에요.

메시지 id는 방과 상관없이 전역으로 유일해야 해요. RFC 9562의 UUIDv7은 앞 48비트에 밀리초 시각을 담아 대략 시간 순으로 정렬돼요. 다만 그 시각은 생성한 쪽의 시계예요. 그래서 채팅 순서의 기준으로 쓰지 않아요.

## 정렬 기준 비교 — 시계 오차 · 동률 · 기기 간 일치

| 기준             | 기기 시계 오차  | 같은 값(동률)                      | 기기 사이 순서            | 쓰는 곳                        |
| ---------------- | --------------- | ---------------------------------- | ------------------------- | ------------------------------ |
| 보낸 기기 시각   | 그대로 반영해요 | 생겨요. 기기 id 등으로 깨야 해요   | 같아요 (값을 함께 보내면) | 사용자가 적은 시각을 보는 목록 |
| 서버 수신 시각   | 영향이 없어요   | 초 단위면 자주 생겨요              | 같아요 (규칙이 같으면)    | 로그와 감사 기록               |
| 기기가 받은 순서 | 해당하지 않아요 | 기기마다 달라요                    | 달라져요                  | 피해야 해요                    |
| 서버 순번        | 영향이 없어요   | 생기지 않아요 (방 안에서 유일해요) | 같아요                    | 채팅 순서                      |

## 임시 행 교체 — clientMsgId로 서버 순번 받기

보내기를 누르면 응답을 기다리지 않고 행을 먼저 그리는 방식을 낙관적 UI라고 불러요. 이 행에는 아직 서버 순번이 없어요. 그래서 목록 끝에 붙었다가, 응답을 받으면 서버 순번이 정한 자리로 옮겨 가요. 화면에서는 이 이동이 "내 메시지가 내려갔다"로 보여요.

임시 행은 클라이언트가 만든 `clientMsgId`로 식별해요. `crypto.randomUUID()`는 v4 UUID를 만들어요. MDN은 이 함수가 암호학적으로 안전한 난수를 쓰고 보안 컨텍스트에서만 쓸 수 있다고 설명해요. RFC 9562도 v4를 무작위 값으로 만드는 방식으로 정의해요.

```ts
type Row = { clientMsgId: string; seq: number | null; text: string };

function optimisticSend(list: Row[], text: string): Row[] {
  return [...list, { clientMsgId: crypto.randomUUID(), seq: null, text }];
}

// 응답의 clientMsgId 로 같은 행을 찾아 순번만 채워요. 위치가 아니라 id 로 찾아요.
function onAck(list: Row[], ack: { clientMsgId: string; seq: number }): Row[] {
  return list.map((r) => (r.clientMsgId === ack.clientMsgId ? { ...r, seq: ack.seq } : r));
}

// 화면 순서는 순번 기준이고, 아직 순번이 없는 행은 맨 뒤에 둬요.
function display(rows: Row[]): Row[] {
  const sent = rows.filter((r) => r.seq !== null).sort((a, b) => (a.seq ?? 0) - (b.seq ?? 0));
  return [...sent, ...rows.filter((r) => r.seq === null)];
}
```

서버는 응답에 같은 `clientMsgId`를 돌려줘야 해요. 같은 메시지가 실시간 채널로도 다시 오기 때문이에요. 기기는 이미 있는 `clientMsgId`면 행을 추가하지 않고 교체만 해요.

`clientMsgId`는 v4로 충분해요. v7을 쓰면 시간 순으로 정렬돼 디버깅에 편하지만, 그 시각은 기기 시계예요. 순서의 근거로 쓰지 않는다는 원칙은 같아요.

### 실패한 전송 — 같은 clientMsgId로 재시도

응답을 받지 못하면 같은 `clientMsgId`로 다시 보내요. Matrix 명세는 트랜잭션 ID를 HTTP 경로에 넣어, 서버가 새 요청과 재전송을 구분하게 한다고 설명해요. 같은 ID의 재전송이면 서버는 같은 응답을 돌려줘야 해요. 재시도 간격과 실패 판단의 일반 원칙은 [결제 — 이중 결제 막기](/m/payment-idempotency) 글과 같아요.

## 중복 전송 — 클라이언트 메시지 id로 한 번만 저장

서버는 메시지를 저장했지만 응답이 끊기는 경우가 있어요. 클라이언트는 응답이 없으니 다시 보내요. 서버가 이 재전송을 거르지 않으면 같은 메시지가 두 번 저장돼요. 시뮬레이터에서 재전송을 켜고 서버 거르기를 끄면 이 중복이 보여요. 예시 설정이에요.

### 서버 쪽 거르기 — 방 · 보낸 기기 · id 범위

서버는 방, 보낸 기기, 클라이언트 메시지 id가 같은 요청을 한 번만 저장해요. 재전송에는 처음 받은 순번을 돌려줘요. 시뮬레이터의 '내 2' 재전송이 이 경우예요.

Matrix 명세는 트랜잭션 ID의 범위를 한 기기와 한 엔드포인트로 정해요. 같은 ID를 다른 기기가 쓰면 서로 다른 요청으로 봐야 한다는 뜻이에요. 이 범위를 넘겨 id만으로 묶으면 다른 기기의 우연한 충돌이 중복 판단에 섞여요.

### 기기 쪽 거르기 — 실시간 에코 교체

내 메시지는 응답과 실시간 채널로 두 번 올 수 있어요. 기기는 `clientMsgId`가 이미 있는 행이면 교체만 해요. 이벤트 id로 한 번만 반영하는 일반 규칙은 [실시간 알림](/m/realtime-delivery) 글의 중복 제거 절에서 다뤘어요.

## 재연결 — 마지막 순번 이후 요청과 빈 순번 확인

연결이 끊긴 동안 도착한 메시지는 실시간 채널로 받을 수 없어요. MDN은 WebSocket 연결이 닫히면 `close` 이벤트가 발생하고, 데이터를 보내지 못하면 `error` 이벤트가 발생한다고 설명해요. 기기는 이 신호를 끊김의 시작으로 보고, 재연결한 뒤 자기가 가진 마지막 순번을 보내 그 뒤의 메시지를 요청해요.

XEP-0313 Message Archive Management는 아카이브를 시간순으로 조회하고, RSM의 `after`에 마지막 항목의 UID를 넣어 다음 묶음을 받는다고 설명해요. 마지막 순번 이후 요청과 같은 모양이에요. 이 명세는 같은 시각의 메시지가 여럿일 수 있어서 타임스탬프만으로 순서를 잡지 말라고도 적어요.

받은 순번이 3에서 5로 건너뛰면 4가 빠진 것으로 볼 수 있어요. 이 판단은 방마다 빈칸 없이 늘어나는 순번이 있어야 가능해요. 빈칸이 생길 수 있는지는 서버 구현에 따라 달라서 확인이 필요해요.

시뮬레이터에서 노트북 연결 끊김을 켜고 재연결 채우기를 끄면 '내 2'가 노트북 화면에서 빠져요. 채우기를 켜면 같은 순서가 돌아와요.

## 읽음 위치 — 마지막으로 읽은 순번과 안 읽은 수

읽음 위치는 "여기까지 읽었어요"라는 순번 하나예요. XEP-0333 Displayed Markers는 메시지마다 표시하지 않고, 그 지점까지의 모든 메시지를 뜻한다고 설명해요. 읽음 위치는 앞으로만 움직이고, 더 오래된 값은 무시해야 해요.

Matrix 명세는 `m.read`를 사용자가 특정 이벤트까지 읽었음을 알리는 영수증으로 정의해요. `m.read.private`은 다른 사용자에게 읽은 위치를 알리지 않고 알림을 지우는 데 쓴다고 설명해요.

### 안 읽은 수 계산 — 자기 메시지 제외와 순번 비교

안 읽은 수는 읽음 순번보다 큰 상대 메시지의 개수예요. 자기 메시지는 셈에서 빼요.

```ts
function unreadCount(messages: { seq: number; from: string }[], me: string, lastReadSeq: number): number {
  return messages.filter((m) => m.from !== me && m.seq > lastReadSeq).length;
}
```

기기가 받지 못한 메시지는 셀 수 없어요. 그래서 빠진 구간을 채운 뒤에 안 읽은 수가 맞아져요. 이 한계는 서버가 계산하는 값과 기기가 계산하는 값의 차이로 드러나요.

### 여러 기기 동기화 — 서버에 읽음 위치 저장

읽음 위치를 기기 안에만 두면 폰은 노트북에서 읽은 것을 몰라요. 시뮬레이터에서 '기기 안에만 저장'을 고르면 나 폰의 안 읽은 수가 노트북보다 커져요.

서버에 두면 기기마다 같은 읽음 위치를 봐요. Matrix 명세는 이벤트마다 영수증을 보내면 전송량이 많아질 수 있다고 적어요. 그래서 "여기까지"라는 값 하나만 올리는 편이 좋아요. 뒤로 가는 값은 무시하는 규칙을 같이 둬요.

앱 아이콘에 찍히는 전체 안 읽은 수는 여러 방의 합이에요. 내 상태는 즉시 반영하고 총합은 지연을 허용하는 방식은 [좋아요 · 조회수 카운터](/m/hot-counters) 글과 같은 판단이에요. 알림 배지는 [웹 푸시](/m/push-notifications) 글처럼 신호일 뿐이고, 원본은 서버의 읽지 않은 목록이에요.

## 과거 메시지 — 맨 위 순번을 커서로 불러오기

위로 스크롤하면 화면에 있는 가장 오래된 순번을 커서로 보내고, 그 이전 묶음을 받아요. 서버는 순번 내림차순으로 주고, 화면에는 오름차순으로 붙이는 방식이 자연스러워요. 이것도 설계 판단이에요.

XEP-0313은 `before`와 `after`로 UID 기준 다음 묶음을 받는다고 설명해요. 시간 범위로만 자르면 같은 시각의 메시지가 경계에서 나뉠 수 있어요. 목록 커서의 일반 원리는 [페이지네이션](/m/pagination) 글에서 다뤘어요.

## FE 체크 포인트

- 목록은 서버 순번으로 정렬하고, 기기 시계나 받은 시각으로 정렬하지 않아요.
- 임시 행은 `clientMsgId`로 식별해요. 응답을 받으면 같은 행의 순번만 채워요.
- 재시도는 같은 `clientMsgId`로 보내요. 응답이 여러 번 와도 순번이 바뀌지 않으면 정상이에요.
- 화면에서 순번이 건너뛰면 마지막 순번 이후를 요청해요.
- 안 읽은 수는 자기 메시지를 빼고, 읽음 순번보다 큰 상대 메시지만 세요.
- 임시 행이 자리를 옮기는 것은 피할 수 없어요. 대신 전송 중 표시를 붙여, 자리가 바뀌는 이유가 보이게 해요.

## 시뮬레이터 안내

- 정렬 기준은 보낸 기기 시각, 서버 수신 시각, 기기가 받은 순서, 서버 순번 네 가지예요.
- 나 폰과 상대 폰의 시계 오차(±60초)와 서버까지 지연(0~3초)을 바꿀 수 있어요.
- 노트북 연결 끊김, 재연결 채우기, 재전송, 서버 거르기, 읽음 위치 저장 위치를 켜고 끌 수 있어요.

## 정리 — 서버 순번 · 임시 행 교체 · 중복 거르기 · 읽음 위치 저장

- 메시지 순서는 서버가 방마다 붙인 순번으로 정하고, 기기 시계는 표시용 값으로만 써요.
- 임시 행은 `clientMsgId`로 찾아 서버 순번을 받은 뒤 자리를 옮겨요.
- 재전송은 같은 `clientMsgId`를 쓰고, 서버는 방과 보낸 기기와 id 기준으로 한 번만 저장해요.
- 재연결은 마지막으로 받은 순번 이후를 요청해서 빈 구간을 채워요.
- 안 읽은 수는 읽음 순번 뒤의 상대 메시지 수로 계산하고, 읽음 위치는 서버에 두는 편이 여러 기기에서 일관돼요.
