로그인 화면에서 비밀번호를 몇 번 틀리면 캡차가 뜨는 경우가 있어요. 그런데 공격은 IP를 계속 바꿔 가며 들어온다고 해요.

이 글은 로그인 공격의 두 모양을 나누고, 계정 · IP · 전체 실패율 신호를 함께 보는 이유를 정리해요. 계정 잠금의 부작용과 지연 → 캡차 → 추가 인증 순서의 대응도 다뤄요. 마지막으로 FE가 캡차와 잠금 상태를 다루는 방법을 짚어요.

글의 숫자는 예시예요. 아래 시뮬레이터의 기본 조건과 같아요.

## 공격 두 종류 — 무차별 대입과 크리덴셜 스터핑

OWASP 치트시트는 무차별 대입 (brute force)을 한 계정에 여러 비밀번호를 넣는 공격이라고 설명해요. 크리덴셜 스터핑 (credential stuffing)은 다른 사이트의 유출에서 얻은 아이디와 비밀번호 쌍을 여러 계정에 넣는 공격이에요. 같은 치트시트는 한 비밀번호를 많은 계정에 넣는 비밀번호 뿌리기 (password spraying)도 따로 나눠요.

OWASP 자동 위협 목록도 둘을 나눠요. OAT-007 Credential Cracking은 추측과 대입으로 값을 찾는 공격이에요. OAT-008 Credential Stuffing은 훔친 쌍을 시험하는 공격이라서 대입이나 추측을 하지 않는다고 설명해요.

| 구분                  | 무차별 대입      | 크리덴셜 스터핑            |
| --------------------- | ---------------- | -------------------------- |
| 시도 대상             | 한 계정          | 여러 계정 (쌍마다 한두 번) |
| 값의 출처             | 사전과 추측      | 다른 곳에서 유출된 쌍      |
| 계정 하나에 가는 시도 | 많아요           | 적어요                     |
| 잘 잡히는 신호        | 계정별 실패 횟수 | IP별 요청 수와 전체 실패율 |

마지막 행은 설계 판단이에요. 같은 계정에 시도가 몰리면 계정 기준 신호로, 많은 계정에 흩어지면 IP나 전체 기준 신호로 보는 편이 좋아요.

## IP 기준 제한 — 분산 공격에 약한 이유

IP 하나당 요청 수를 세면 한 IP에서 오는 대량 요청은 잡아요. 하지만 OWASP 치트시트는 공격 도구가 프록시 네트워크로 요청을 많은 IP에 나눠 보낼 수 있다고 설명해요. 그러면 IP 차단 목록도, IP별 요청 제한도 모두 무력해질 수 있어요. IP 하나에서 오는 요청 수가 낮게 유지되기 때문이에요.

그래서 치트시트는 IP 차단을 유일하거나 주된 방어로 쓰지 말고, 여러 대응을 겹쳐 쓰라고 권해요. IP마다 요청은 적지만 많은 IP에서 꾸준히 들어오는 패턴도 함께 보라고 설명해요.

시뮬레이터에서 스터핑을 IP 1개로 보내면 IP 제한이 공격을 늦추기는 해요. 그래도 250쌍은 모두 처리돼요. IP 1000개로 나눠 보내면 IP 하나당 요청이 한두 건뿐이라 IP 제한이 한 번도 걸리지 않아요. 이것은 예시 결과예요.

## 신호 조합 — 계정 · IP · 전체 실패율

OWASP 인증 치트시트는 로그인 실패 카운터를 IP가 아니라 계정에 붙이라고 설명해요. 여러 IP에서 시도해도 계정 하나에 쌓이는 실패를 세기 위해서예요. IP는 공격자가 쉽게 바꿀 수 있어서, 계정 기준 신호가 필요해요.

전체 실패율은 이 글의 설계 판단이에요. 최근 실패 비율이 높으면 공격이 진행 중일 가능성이 커요. 그래서 개별 계정이나 IP가 한도 아래에 있어도 전체 흐름을 따로 봐요.

| 신호           | 잘 잡는 공격               | 놓치는 공격                      | 정상 사용자 비용                     |
| -------------- | -------------------------- | -------------------------------- | ------------------------------------ |
| 계정별 실패 수 | 한 계정 무차별 대입        | 계정마다 한두 번 시도하는 스터핑 | 계정 주인이 같이 막혀요              |
| IP별 요청 수   | IP 하나에서 오는 대량 요청 | IP 1000개로 나눈 공격            | 같은 공유 IP의 사용자가 같이 막혀요  |
| 전체 실패율    | 실패가 몰리는 스터핑       | 실패율을 낮게 맞춘 느린 공격     | 캡차가 켜지면 모두 한 번 더 확인해요 |

시뮬레이터에서 IP 1000개 분산 공격에 IP 제한만 켜 보세요. 공격 성공 계정 수는 그대로이고, 정상 로그인에도 거의 영향이 없어요. 공유 IP 한계는 [레이트 리밋 알고리즘](/m/rate-limiting)에서 다뤘어요.

## 계정 잠금 — 공격을 끊지만 주인도 막는 부작용

계정 잠금은 일정 횟수 실패가 쌓이면 그 계정으로 더는 로그인을 받지 않는 방식이에요. OWASP 치트시트는 가장 흔한 보호라고 설명해요. 잠금 시간을 실패마다 두 배로 늘리는 지수 잠금도 있다고 설명해요.

문제는 공격자가 남의 계정을 일부러 틀릴 수 있다는 점이에요. OWASP 인증 치트시트는 잠금이 다른 사용자의 계정을 잠가 서비스 거부 (denial of service)로 쓰일 수 있다고 설명해요. 완화책으로, 잠긴 계정도 비밀번호 찾기 흐름으로는 들어갈 수 있게 하는 방법을 들어요.

시뮬레이터에서 한 계정 무차별 대입에 계정 잠금을 켜 보세요. 공격은 계정에 들어가지 못하지만, 피해자의 정상 로그인이 잠긴 동안 여러 번 막혀요. 스터핑에서는 계정마다 시도가 한두 번뿐이라 잠금 임계값에 닿지 않아서 결과가 거의 바뀌지 않아요. 이것도 예시 결과예요.

## 단계별 대응 — 지연 → 캡차 → 추가 인증

NIST SP 800-63B-4는 연속 실패를 한 인증기당 100회 이하로 제한하라고 설명해요. 100회는 상한이고, 기관은 더 낮게 정할 수 있다고 설명해요. 한도에 가까워질수록 기다리는 시간을 늘리는 방법, 봇 탐지 도전을 먼저 두는 방법, 위험 기반 적응형 인증을 쓰는 방법도 같은 절에서 함께 설명해요.

OWASP 치트시트는 위험 신호가 있는 로그인에만 추가 인증을 요구하는 방식을 설명해요. 새 기기나 새 IP, 여러 계정을 시도한 IP, 스크립트처럼 보이는 로그인이 예시예요. 그래서 대응을 아래처럼 나눠요. 순서는 설계 판단이에요.

| 단계            | 켜는 신호                             | 정상 사용자 비용         | 공격자 비용                  |
| --------------- | ------------------------------------- | ------------------------ | ---------------------------- |
| 지연            | 실패가 한도에 가까워질 때             | 잠깐 기다려요            | 시도 간격이 늘어요           |
| 캡차            | 최근 실패율이 높을 때                 | 문제를 풀어야 해요       | 자동 풀이 비용이 들어요      |
| 추가 인증 (MFA) | 비밀번호가 맞아도 위험 신호가 있을 때 | 인증 한 번이 더 필요해요 | 두 번째 요소가 없으면 막혀요 |
| 계정 잠금       | 한 계정의 실패가 임계값을 넘을 때     | 주인도 막혀요            | 그 계정을 멈춰요             |

계정 잠금은 주인까지 막으므로 마지막 단계에 두는 편이 좋아요. 설계 판단이에요.

## 캡차 — 막는 힘과 접근성 한계

OWASP 인증 치트시트는 캡차를 예방 수단이 아니라 방어를 한 겹 더하는 수단으로 보라고 설명해요. 무차별 대입을 더 느리고 비싸게 만든다는 뜻이에요.

많은 캡차 구현에는 자동으로 풀리는 약점이 있고, 풀이를 외부 서비스에 맡길 수도 있다고 설명해요. 그래서 처음부터 모든 로그인에 걸기보다 실패가 몇 번 쌓인 뒤에만 거는 편이 사용자에게 덜 불편하다고 설명해요.

OWASP 치트시트는 캡차 풀이율을 지켜보라고도 설명해요. 풀이율로 정상 사용자가 받는 영향을 알 수 있고, 비정상적으로 높은 풀이율은 자동 풀이가 쓰이는 신호일 수 있다고 설명해요.

W3C 문서는 이미지 글자를 읽게 하는 전통 캡차가 스크린리더를 쓰는 시각 장애인에게 풀기 어렵다고 설명해요. 캡차를 보안 수단으로 쓰는 것도 점점 효과가 줄고 있다고 설명해요.

시뮬레이터에서 실패가 몰리는 스터핑에 캡차만 켜면 공격 성공 수가 조금 줄어요. 봇이 캡차를 90% 통과한다고 가정한 결과예요. 캡차는 단독 방어보다 다른 신호와 함께 쓰는 편이 맞아요.

## 유출 비밀번호 확인 — 범위 조회와 k-익명성

NIST SP 800-63B-4는 비밀번호를 정하거나 바꿀 때 유출된 비밀번호 목록과 대조하라고 설명해요. 로그인 때마다 하라는 내용은 이 절에 없어요. 목록에는 이전 유출 데이터에서 나온 비밀번호가 들어가요.

Have I Been Pwned의 Pwned Passwords API는 k-익명성 방식으로 조회해요. 비밀번호의 SHA-1 해시에서 앞 5자리만 `range/{앞 5자리}`로 보내요. 응답은 같은 앞 5자리를 가진 해시들의 나머지 부분 목록이에요.

클라이언트는 그 목록에서 내 해시가 있는지 직접 찾아요. 없으면 그 비밀번호는 데이터셋에 없다고 설명해요. 원래 비밀번호와 해시 전체는 API로 나가지 않아요.

응답 크기로 어떤 접두어를 찾았는지 추측할 수 있다는 점은 패딩 헤더 (Add-Padding)로 줄일 수 있다고 설명해요.

## MFA — 가장 강한 대응이라는 근거 범위

OWASP 치트시트는 MFA가 대부분의 비밀번호 공격에 가장 효과적인 방어라고 설명해요. 그 근거로 Microsoft의 분석을 인용해요. 분석이 계정 침해의 99.9%를 막을 수 있었을 것이라는 내용이에요.

치트시트는 MFA가 모든 공격을 막는다고 쓰지 않아요. 가능한 곳에서는 MFA를 쓰라고 권하면서, 위험 신호가 있을 때만 두 번째 요소를 요구하는 방식도 함께 설명해요.

시뮬레이터에서 MFA를 켜면 공격 성공 계정 수가 0이 돼요. 공격자가 두 번째 요소를 갖지 않는다고 가정한 결과예요. 정상 사용자는 일부가 MFA에서 이탈해 막히는 것도 함께 보여요.

## 실패 응답 문구 — 계정 존재를 드러내지 않기

OWASP 인증 치트시트는 로그인, 비밀번호 찾기, 복구 모두에서 실패 문구를 같게 하라고 설명해요. 아이디나 비밀번호가 틀린 경우, 계정이 없는 경우, 계정이 잠기거나 비활성화된 경우에 같은 일반 문구를 보여야 해요. 그렇지 않으면 계정이 있다는 사실이 드러나요.

HTTP 응답 코드도 같아야 해요. 치트시트는 성공에 200, 실패에 403을 주는 식으로 나뉘면 화면 문구가 같아도 계정 존재가 드러난다고 설명해요. 응답 시간도 맞춰야 해요. 계정이 있을 때만 비밀번호 검사를 돌리면 시간 차이로 계정이 드러나요.

치트시트는 여러 단계로 나뉜 로그인이 계정 열거를 돕지 않도록 주의하라고 설명해요. 발송 요청의 응답을 맞추는 자세한 방법은 [인증번호 (OTP)](/m/verification-codes)에서 다뤘어요.

## FE 체크 포인트 — 캡차와 잠금 문구를 서버 값에 맞추기

- 캡차는 서버가 요구할 때만 띄워요. 클라이언트에서 캡차 조건을 따로 계산하지 않는 편이 좋아요. 설계 판단이에요.
- 기기 지문은 클라이언트가 보낸 값이라 바뀔 수 있다고 OWASP는 설명해요. 화면에서 이 값을 신뢰하는 판단을 하지 마세요.
- 잠긴 계정에도 실패 문구와 같은 일반 문구를 보여 주세요. 잠김을 따로 알리면 계정 존재가 드러나요. 대신 비밀번호 찾기 링크를 같이 보여 주세요.
- 로그인 요청을 자동으로 다시 보내지 않는 편이 좋아요. 재시도마다 실패 횟수가 하나씩 올라가서 잠금을 앞당기기 때문이에요. 설계 판단이에요.
- 429 응답과 `Retry-After`를 다루는 방법은 [레이트 리밋 알고리즘](/m/rate-limiting)에서 이어서 봐요.

## 시뮬레이터 안내

시뮬레이터에서 공격 방식을 고르고, 방어를 조합해 결과를 봐요. 공격 성공 계정 수, 막힌 정상 로그인 수, 잠긴 계정 수를 보여 줘요. 표에서는 방어 단계별로 막힌 공격 요청과 정상 요청을 나눠 봐요.

- 유출 쌍 스터핑을 IP 1000개로 나누고 IP 제한만 켜 보세요. 공격 결과가 그대로인지 봐요.
- 한 계정 무차별 대입에 계정 잠금을 켜 보세요. 공격 결과와 막힌 정상 로그인 수를 같이 봐요.
- MFA를 켜 보세요. 공격 성공 계정 수가 0이 되는지 봐요.

수치는 감을 잡기 위한 예시예요.
