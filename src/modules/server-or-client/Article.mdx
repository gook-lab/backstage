목록을 정렬하거나, 필터를 걸거나, 합계를 구하다 보면 같은 질문이 계속 나와요. 이 계산을 서버에서 해야 할까요, 화면에서 해도 될까요?

정답은 기능마다 달라요. 같은 "정렬"도 현재 화면에 받은 50건을 바꾸는 일이라면 화면에서 바로 하는 게 자연스럽고, 50만 건 전체를 바꾸는 일이라면 서버가 해야 해요. 이 글에서는 아홉 가지 기준으로 나눠 보고, 아래 시뮬레이터에서 직접 답해 보면서 추천이 어떻게 나오는지 확인해요.

## 판단 기준 — 아홉 가지 질문과 이유

아래 기준은 설계 판단이에요. 정해진 법칙이 아니라 "이걸 먼저 물어보자"는 목록으로 봐 주세요. 건수 기준처럼 숫자가 나오는 곳은 모두 예시예요.

| 기준                   | 확인할 질문                                             | 이유                                                                                                                                      | 이어 읽을 글                           |
| ---------------------- | ------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------- |
| 1. 신뢰                | 돈, 권한, 재고, 한도를 정하는 값인가요?                 | 클라이언트가 보낸 값은 누구나 바꿀 수 있어요. 금액과 권한은 서버가 다시 판단해야 해요.                                                    | 장바구니와 재고, 결제 — 이중 결제 막기 |
| 2. 데이터 크기         | 전체 데이터가 기기에 들어가고, 이미 받아 둔 상태인가요? | 50건 안팎은 기기에서 정렬 · 필터해도 부담이 작아요. 큰 데이터는 받을 수도 없고, 받아도 기기가 느려져요. 서버가 필요한 만큼만 골라야 해요. | 페이지네이션, N+1 쿼리와 인덱스        |
| 3. 일관성 · 공유 상태  | 다른 사람이 동시에 바꾸는 값인가요?                     | 좌석, 재고, 카운터는 화면에 보이는 값이 이미 낡았을 수 있어요. 최종 값은 서버가 쥐어야 해요.                                              | 콘서트 좌석 선점, 좋아요와 조회수      |
| 4. 지연 · 상호작용     | 입력하거나 누를 때 바로 보여야 하나요?                  | 응답을 기다리면 사용자가 다시 누르거나 떠나요. 즉시 반응은 클라이언트가 보여 주고, 확정은 서버가 해요.                                    | 장바구니와 재고                        |
| 5. 계산 비용           | 계산이 무겁고, 저사양 기기에서도 버텨야 하나요?         | 무거운 계산이 화면 스크립트와 같은 흐름에서 돌면 입력이 멈춰요. 데이터가 적으면 Web Worker로, 많으면 서버에서 해요.                       | N+1 쿼리와 인덱스                      |
| 6. 보안 · 비밀         | 사용자에게 보이면 안 되는 규칙이나 키가 있나요?         | 규칙이 클라이언트 코드에 있으면 누구나 읽을 수 있어요. 비밀 규칙과 키는 서버에 둬요.                                                      | 결제 — 이중 결제 막기                  |
| 7. 캐시 가능성         | 여러 사람이 같은 응답을 받고, 조금 낡아도 괜찮나요?     | 공유 캐시나 CDN에 둘 수 있으면 서버 부하가 줄어요. 개인 데이터는 공유 캐시에 두면 안 돼요.                                                | 캐시 스탬피드                          |
| 8. 오프라인 · 네트워크 | 연결이 끊겨도 기능이 돼야 하나요?                       | 오프라인에서는 서버 확정이 불가능해요. 기기에 임시로 적어 두고, 연결이 돌아오면 서버에 확정하는 흐름이 필요해요.                          | 결제 — 이중 결제 막기                  |
| 9. 응답 크기 · 직렬화  | 필요한 필드만, 나눠서 보내고 있나요?                    | 쓰지 않는 필드는 전송 시간과 기기 메모리를 써요. 응답은 Content-Encoding으로 압축해서 줄일 수 있어요.                                     | 페이지네이션                           |

## 이중 검증 — 클라이언트는 UX, 서버는 최종 판단

입력 검증은 화면과 서버에서 두 번 해요. 역할이 달라요.

OWASP 입력 검증 치트시트는 클라이언트 검증이 우회될 수 있으니 즉각 피드백용으로 쓰라고 안내해요. 같은 문서는 입력을 구문(형식)과 의미(업무적으로 말이 되는지) 양쪽에서 검증하라고 설명해요.

그래서 화면은 사용자가 바로 고칠 수 있게 힌트를 주고, 서버는 틀린 값이 저장되지 않도록 같은 규칙을 다시 확인해요.

| 검증 항목        | 클라이언트 (UX)                  | 서버 (진실)                                  |
| ---------------- | -------------------------------- | -------------------------------------------- |
| 형식             | 수량 입력란에 숫자가 아니면 힌트 | 숫자인지, 허용 범위인지 다시 확인            |
| 재고 · 한도      | "재고가 2개예요" 같은 안내       | 실제 재고를 조건부 차감하고 0 행이면 거절    |
| 가격 · 합계      | 줄 금액과 합계 미리보기          | 현재 가격으로 다시 계산한 값을 기준으로 확정 |
| 실패했을 때 행동 | 해당 줄 옆에 안내를 붙여요       | 상태 코드와 줄 단위 오류로 응답해요          |

## 응답 신호 — 서버 처리를 알려 주는 값

응답을 보면 BE가 어디서 처리하도록 설계했는지 짐작할 수 있어요. 한 가지 신호만으로 단정하지 말고 여러 신호를 같이 봐요.

| 응답에서 보이는 것                        | 뜻                                                                                       | 이어 읽을 글                                  |
| ----------------------------------------- | ---------------------------------------------------------------------------------------- | --------------------------------------------- |
| `page`, `cursor`, `nextCursor`, `hasMore` | 서버가 목록을 나눠 줘요. 화면이 전체를 가지고 있지 않다는 뜻이에요.                      | 페이지네이션                                  |
| `?sort=`, `?filter=` 같은 쿼리 파라미터   | 정렬과 필터를 서버가 해요. 정렬 키에 인덱스가 있어야 빨라요.                             | N+1 쿼리와 인덱스                             |
| `total` 같은 전체 개수                    | 서버가 전체 개수를 셌어요. 개수 계산은 비싸서 꼭 필요할 때만 줘요.                       | 페이지네이션                                  |
| `ETag`, `Cache-Control` 헤더              | 응답을 캐시해도 되는지 알려 줘요. 바뀌지 않았으면 `304 Not Modified`로 본문을 생략해요.  | 캐시 스탬피드                                 |
| `409 Conflict`                            | 요청이 현재 상태와 충돌했어요. RFC 9110은 대상 리소스의 현재 상태와 충돌했다고 정의해요. | 콘서트 좌석 선점, 장바구니와 재고             |
| `422 Unprocessable Content`               | 형식은 맞지만 의미상 처리할 수 없어요. RFC 9110이 정의한 상태 코드예요.                  | 결제 — 이중 결제 막기                         |
| `429 Too Many Requests`                   | 짧은 시간에 너무 많이 보냈어요. RFC 6585가 정의해요.                                     | 가상 대기실 · 처리량 제한                     |
| `Idempotency-Key` 요구                    | 같은 요청을 다시 보내도 한 번만 처리하라는 뜻이에요.                                     | 결제 — 이중 결제 막기, 트랜잭션 · 락 · 데드락 |
| `Server-Timing` 헤더                      | 서버가 DB나 CPU 같은 단계별 시간을 알려 줘요. 느린 구간을 찾을 때 단서가 돼요.           | N+1 쿼리와 인덱스                             |

RFC 9110은 여러 번 보내도 한 번 보낸 것과 같은 효과를 내는 메서드를 멱등 메서드라고 정의해요. 그래서 재시도가 생기는 요청은 멱등하게 설계해야 해요.

## 상황별 예시 — 어디서 무엇을 할지

같은 기능도 데이터 규모와 조건에 따라 답이 달라져요. 아래 표는 흔한 예시의 답이에요.

| 상황           | 어디서                                             | 이유                                                                                                          | 관련 모듈                              |
| -------------- | -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- | -------------------------------------- |
| 상품 목록 정렬 | 받아 둔 50건은 클라이언트, 전체 카탈로그는 서버    | 받아 둔 목록은 즉시 정렬해도 충분해요. 전체 상품은 기기에 다 받을 수 없으니 서버가 정렬해서 한 페이지씩 줘요. | 페이지네이션, N+1 쿼리와 인덱스        |
| 장바구니 합계  | 미리보기는 클라이언트, 확정은 서버                 | 수량과 단가로 합계를 바로 보여 주면 빨라요. 결제 전에는 서버가 현재 가격으로 다시 계산해요.                   | 장바구니와 재고                        |
| 쿠폰 할인 적용 | 서버                                               | 할인 금액은 돈과 연결되고, 할인 조건은 비밀 규칙일 수 있어요. 클라이언트 계산은 규칙을 드러내요.              | 결제 — 이중 결제 막기, 장바구니와 재고 |
| 검색 자동완성  | 서버, 입력은 디바운스                              | 상품 전체를 기기에 받을 수 없어요. 키를 누를 때마다 요청하지 않도록 입력을 묶어서 보내요.                     | N+1 쿼리와 인덱스                      |
| 좋아요 수 표시 | 클라이언트가 먼저 +1을 보여 주고, 서버 값으로 맞춤 | 다른 사람이 동시에 바꾸는 값이라 최종 값은 서버가 정해요. 반응은 바로 보여 줘요.                              | 좋아요와 조회수                        |
| 좌석 남은 수   | 서버                                               | 좌석은 재고와 같아요. 화면 숫자는 낡을 수 있으니, 예매할 때 서버가 조건부로 확정해요.                         | 콘서트 좌석 선점                       |
| 엑셀 다운로드  | 서버                                               | 데이터가 크고 파일을 만드는 계산이 무거워요. 서버가 만들고 결과 파일을 내려줘요.                              | N+1 쿼리와 인덱스                      |
| 차트 집계      | 서버, 집계된 결과만 받기                           | 원본 행을 기기로 받아 합치면 느리고 무거워요. 서버가 그룹별로 합쳐서 요약만 보내요.                           | N+1 쿼리와 인덱스                      |

## 시뮬레이터 — 질문 답변에 따른 추천

아래 시뮬레이터는 판단 기준을 규칙 표로 옮겨 둔 도구예요. 위 아홉 가지 기준 중 일곱 가지를 질문으로 물어요. 질문에 답하거나 예시를 고르면, 추천과 걸린 이유, 이어 읽을 글이 나와요.

돈이나 재고가 걸리면 추천은 서버 확정을 포함해요. 비밀 규칙이 있으면 미리보기도 서버가 해요. 미리보기를 클라이언트에서 만들면 규칙이 드러나기 때문이에요. 이 규칙도 설계 판단이라서, 서비스가 다르면 다르게 정할 수 있어요.

## FE 체크 포인트 — 화면에서 맞추는 것

**정렬과 필터는 받은 데이터 규모부터 확인해요.** 이미 받은 목록이 작으면 기기에서 처리하고, 그렇지 않으면 쿼리 파라미터로 서버에 넘겨요. 그때 응답의 `page`나 `cursor`를 보고 다음 페이지를 어떻게 요청할지 정해요.

**금액과 재고는 서버 응답을 기준으로 맞춰요.** 낙관적으로 먼저 보여 줬다면, 실패하거나 다른 값이 오면 이전 값으로 되돌리고 이유를 한 줄로 알려 줘요.

**입력 중 요청은 디바운스해요.** 자동완성처럼 키를 누를 때마다 바뀌는 검색은 입력이 잠깐 멈춘 뒤에만 요청해요.

**무거운 계산은 Web Worker로 옮길지 검토해요.** MDN은 Web Worker가 백그라운드 스레드에서 스크립트를 실행한다고 설명해요. 화면 반응을 덜 막을 수 있다는 점은 이 설명에서 이어지는 판단이에요. 데이터가 크면 Web Worker보다 서버 계산이 맞아요.

**응답의 크기와 압축을 확인해요.** 쓰지 않는 필드가 섞여 있지 않은지 보고, Content-Encoding 헤더로 gzip, br, zstd 같은 압축이 적용됐는지 확인해요.

## 정리 — 신뢰 · 규모 · 지연 순으로 나누기

돈, 권한, 재고가 걸리면 서버가 확정해요. 데이터가 작고 즉시 반응이 필요하면 클라이언트가 먼저 보여 줘요. 데이터가 크거나 비밀 규칙이 있으면 서버가 계산해요.

클라이언트 검증은 사용자를 돕고, 서버 검증은 데이터를 지켜요. 둘 다 있어야 해요.
