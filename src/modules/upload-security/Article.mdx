프로필 사진 업로드 화면에 `accept="image/*"`를 걸면 파일 선택 창에 이미지만 보여요. 그래서 확장자와 Content-Type까지 보면 충분하다고 느끼기 쉬워요. 보안팀이 서버에서도 막으라고 하는 이유는 이 세 값을 모두 파일을 보내는 쪽이 정하기 때문이에요. 이 글에서는 서버가 업로드 파일을 어떤 순서로 확인하는지, 각 검사가 무엇을 막고 무엇을 못 막는지 정리해요.

아래 시뮬레이터에서 업로드 파일 예시를 고르고 검사 단계를 하나씩 켜 보세요. 어느 단계에서 거절되는지, 통과하면 어떤 위험이 남는지 바로 보여요.

## 증상 — 화면에서 고른 파일이 서버를 그대로 통과하는 경우

MDN은 `accept` 속성이 선택된 파일의 형식을 검증하지 않고, 브라우저가 맞는 파일을 고르도록 돕는 힌트라고 설명해요. 그래서 `accept`는 서버 검증으로 뒷받침해야 한다고 권해요.

업로드 요청은 사용자의 브라우저에서 만들어져요. 서버는 요청 안의 파일 이름과 헤더를 받을 뿐이고, 그 요청이 화면을 거쳤는지 알 방법이 없어요. 그래서 화면에서 막은 조건은 서버가 다시 확인해야 해요.

## 클라이언트 값 — accept · 확장자 · Content-Type을 믿지 않는 이유

| 값                 | 누가 정하나        | 판정 근거로 쓸 수 있나                         |
| ------------------ | ------------------ | ---------------------------------------------- |
| `accept`           | 화면 코드          | 아니요. 선택 창의 힌트예요                     |
| 파일 이름의 확장자 | 사용자가 붙인 이름 | 아니요. 허용 목록으로 거르는 1차 단계로만 써요 |
| `Content-Type`     | 요청을 보내는 쪽   | 아니요. 위조하기 쉬워요                        |

OWASP는 Content-Type 헤더가 사용자가 보내는 값이라 믿을 수 없고, 위조가 쉽다고 설명해요. 확장자도 이름만 바꾸면 달라지니 같은 취급을 해요. OWASP는 특정 확장자만 막는 방식은 그 자체로 약한 보호라고도 설명해요.

## 매직 넘버 — 첫 바이트로 형식을 가리는 방식과 한계

OWASP는 Content-Type 검사와 함께 파일 시그니처를 확인하면 기대한 파일이 맞는지 검증할 수 있다고 설명해요. WHATWG MIME Sniffing 표준은 PNG를 `89 50 4E 47 0D 0A 1A 0A`로 시작하는 파일로, JPEG를 `FF D8 FF`로 시작하는 파일로 판정해요.

이 검사에는 분명한 한계가 있어요.

- 첫 바이트만 봐요. PNG 시그니처로 시작하는 파일 뒤에 HTML을 붙이면 이 검사는 통과해요. 시뮬레이터의 "PNG 머리에 HTML을 붙인 파일" 예시가 그 경우예요.
- HTML과 SVG는 텍스트라서 고정된 머리 바이트가 없어요. 그래서 이 검사는 두 형식을 이미지가 아니라고 거절하는 데 쓰여요.
- 형식이 맞다는 뜻이지, 안전하다는 뜻이 아니에요. 안전은 재인코딩과 서빙 방식이 맡아요.

## 허용 목록 — 받을 형식을 적고 나머지는 거절하기

OWASP는 허용 목록 방식을 우선하고, 차단 목록은 그다음 방법이라고 설명해요.

| 방식      | 예                            | 목록에 없는 새 형식이 들어오면 |
| --------- | ----------------------------- | ------------------------------ |
| 허용 목록 | `png`, `jpg`, `jpeg`만 받아요 | 거절돼요                       |
| 차단 목록 | `exe`, `html`을 막아요        | 통과해요                       |

이미지 업로드라면 허용 목록을 기본으로 고르는 편이 좋아요. 받을 형식이 적고 목록 밖은 모두 거절하는 쪽이 빠진 항목으로 생기는 실수를 줄여요.

## 크기와 해상도 — 작은 파일이 디코딩하면 커지는 문제

파일 크기 한도는 저장 공간을 지켜요. OWASP는 업로드 서비스에 크기 한도를 두라고 설명하고, 압축 파일을 풀어 처리하면 풀린 뒤의 크기로 한도를 봐야 한다고 설명해요.

이미지는 더 조심해야 해요. 파일이 작아도 가로와 세로 값이 크면 디코더가 펼친 픽셀을 메모리에 올려야 해요. 예를 들어 50000 × 50000 픽셀을 픽셀당 4바이트(RGBA)로 펼치면 10,000,000,000바이트, 약 10GB예요. 이 숫자는 계산 예시이고, 실제 메모리 사용량은 디코더 구현에 따라 달라요. OWASP는 이미지 라이브러리에 제한된 형식과 자원 한도를 두라고 권해요.

크기와 해상도는 디코딩 전에 확인하는 편이 좋아요. 재인코딩은 이미지를 펼친 뒤에 하는 일이라서, 한도를 넘는 파일은 펼치기 전에 걸러야 해요.

## 저장 이름 — 서버가 새 이름을 정하기

사용자가 붙인 이름을 그대로 저장하면 같은 이름의 파일이 덮어써질 수 있어요. 이름에 경로 조각이 섞여 들어오기도 해요. OWASP는 파일 이름을 애플리케이션이 생성한 값으로 바꾸라고 설명하고, UUID 같은 임의 문자열이 필수라고 설명해요. 공개 주소는 `someid -> file.ext`처럼 내부 식별자로 연결하라고 권해요.

RFC 6266은 filename 파라미터의 폴더 정보를 믿지 않는 방법으로, `\`와 `/`로 나눈 마지막 조각만 쓰는 방법을 든다고 설명해요.

## 서빙 — 다른 도메인에서 내려주고 헤더 붙이기

OWASP는 파일을 다른 호스트에 두는 방법을 가장 먼저 권해요. 파일을 받는 호스트와 앱 서버를 나누면 책임이 나뉘고, 공개 파일은 앱 도메인과 출처가 달라져요. 다른 호스트에 둘 수 없다면 웹 루트 밖에 두라고 해요.

응답 헤더도 함께 붙여요.

- `X-Content-Type-Options: nosniff`: MDN은 이 헤더가 있으면 브라우저가 보낸 Content-Type을 그대로 쓰고 내용으로 추측하지 않는다고 설명해요. 예를 들어 `text/plain`에 nosniff를 붙이면 HTML 마크업이 들어 있어도 HTML로 해석하지 않아요.
- `Content-Disposition: attachment`: MDN은 attachment를 파일을 바로 열지 않고 내려받게 하는 값으로 설명해요.

헤더 전체 목록과 스크립트 정책은 [보안 헤더](/m/security-headers) 글로 넘겨요. presigned URL로 저장소에 직접 올리는 흐름은 [파일 전송](/m/file-transfer) 글에서 다뤄요.

## SVG · HTML — 텍스트라서 스크립트를 담을 수 있는 형식

SVG는 이미지처럼 보이지만 텍스트 기반이에요. MDN은 SVG의 `<script>` 요소가 SVG 문서에 스크립트를 넣게 해 준다고 설명해요. WHATWG MIME Sniffing 표준은 `+xml`로 끝나는 MIME 타입을 XML MIME 타입으로 정하고, XML · HTML · PDF를 스크립트 가능한 MIME 타입으로 분류해요.

OWASP는 공개로 내려받을 수 있는 파일 안의 클라이언트 쪽 활성 콘텐츠가 XSS 같은 공격으로 다른 사용자를 해칠 수 있다고 설명해요. 그래서 사진 업로드에서 SVG와 HTML은 허용 목록에 넣지 않는 편이 좋아요. 로고처럼 SVG가 꼭 필요하다면 서버에서 래스터 이미지로 바꾸는 편이 우선이에요. 별도 도메인에서 내려줘도 스크립트 실행 위험은 남아요.

## 재인코딩 — 디코드 후 새 파일로 저장해 메타데이터 줄이기

OWASP는 이미지를 허용된 형식으로 디코드하고 다시 인코드하면서, 필요 없는 메타데이터를 명시적으로 지우라고 설명해요. 재인코딩한 파일에는 원본 바이트가 그대로 남지 않아요.

EXIF 메타데이터에는 위치 정보가 들어갈 수 있어요. Library of Congress는 Exif가 촬영 기기의 기술 정보를 기록하기 위한 형식이고, JPEG에서는 APP1과 APP2 세그먼트에 메타데이터를 넣는다고 설명해요. ExifTool 문서는 GPS 태그에 `GPSLatitude`와 `GPSLongitude` 같은 위치 값이 있다고 정리해요. 그래서 휴대폰으로 찍은 사진에는 촬영 위치가 남을 수 있어요.

재인코딩은 크기 검사 다음 단계예요. 디코딩은 이미 메모리를 쓰는 작업이라 한도를 먼저 확인해야 해요.

## 악성코드 검사와 격리 후 공개 — 공개 주소를 나중에 만들기

OWASP는 업로드 파일을 바이러스 백신이나 샌드박스에 통과시켜 악성 데이터가 없는지 확인하라고 설명해요. 공개하기 전에 샌드박스에서 사람이 검토하라고도 해요. 알려진 악성 파일의 해시와 대조하는 방법도 있지만, 이 방법은 이미 알려진 파일만 잡아요.

흐름은 이렇게 잡는 편이 좋아요. 아래는 예시 흐름이에요.

1. 업로드를 공개 주소가 없는 격리 위치에 받아요.
2. 형식과 크기를 확인하고 재인코딩해요.
3. 악성코드 검사를 통과하면 공개 저장소로 옮기고, 내부 식별자로 공개 주소를 만들어요.
4. 공개 주소를 응답에 담아요.

프론트엔드(FE)는 3번이 끝나기 전까지 "검사 중이에요" 상태를 보여 줘요. 공개 주소를 받은 뒤에만 공유 버튼을 켜요.

## FE 체크 포인트

- `accept`와 미리 보기는 사용자를 돕는 기능이에요. 판정은 서버 응답으로 받아요.
- 서버가 거절하면 이유를 받아 파일 옆에 보여 줘요. 필드 단위 오류를 나누는 방법은 [입력 검증](/m/input-validation) 글에서 이어 봐요.
- 공개 주소로 연결하기 전에 검사 상태를 확인해요. 검사 전 주소를 공유 버튼에 넣지 않아요.

## 시뮬레이터 안내

아래 시뮬레이터에서 업로드 파일 예시를 고르고 검사 단계를 켜거나 꺼 보세요. 어느 단계에서 거절되는지, 통과하면 어떤 위험이 남는지 함께 보여 줘요. "확장자 · Content-Type만", "형식 · 크기까지", "권장 조합" 예시를 누르면 검사 묶음이 한 번에 바뀌어요.

## 정리 — 믿지 않는 값 · 형식 판정 · 서빙 분리 · 이름 재발급

서버는 `accept`, 확장자, Content-Type을 힌트로만 봐요. 형식은 허용 목록과 첫 바이트로 가리고, 크기와 해상도는 디코딩 전에 막아요. 재인코딩으로 위치 정보와 덧붙은 내용을 줄이고, 저장 이름은 서버가 새로 정해요. 파일은 다른 도메인에서 내려주고 nosniff를 붙여요.

이 방법으로도 알려지지 않은 악성 내용은 걸러지지 않아요. 검사와 격리 단계를 따로 두는 이유예요.
