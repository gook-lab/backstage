인기 상품 상세 페이지를 생각해 볼게요. 가격은 49,000원, 재고는 12개예요. 이 상품 페이지가 초당 100번씩 조회되는데, 매번 DB를 치면 DB가 버티기 어려워요. 그래서 상품 정보를 캐시에 10초 동안 담아 두고, 그동안은 DB를 거치지 않게 해요.

문제는 10초가 끝나는 순간이에요. 캐시에 값이 없어지면 그 순간 들어온 요청이 전부 DB로 가요. 이 글은 그 순간을 다뤄요. 아래 시뮬레이터에서 같은 상황을 직접 돌려 볼 수 있어요. 시뮬레이터의 수치는 예시예요.

## 캐시 계층 — 요청이 지나가는 다섯 단계 비교

요청은 DB에 닿기 전에 여러 캐시를 지날 수 있어요. 자리마다 잘하는 일과 어려운 일이 달라요.

| 계층                         | 어디에 있나               | 잘하는 일                           | 어려운 일                                              |
| ---------------------------- | ------------------------- | ----------------------------------- | ------------------------------------------------------ |
| 브라우저 HTTP 캐시           | 사용자 기기               | 재방문 때 요청 자체를 없애요        | 서버가 지울 수 없어요. 허락한 시간 동안 그대로 써요    |
| CDN                          | 사용자와 가까운 엣지 서버 | 여러 사용자가 같은 응답을 나눠 써요 | 개인 데이터는 나눌 수 없어요                           |
| 앱 메모리 캐시               | 서버 프로세스 안          | 네트워크 없이 가장 빨라요           | 서버마다 값이 달라요. 지우려면 서버 모두에 알려야 해요 |
| 공유 캐시 (Redis, Memcached) | 별도 서버                 | 모든 서버가 같은 값을 봐요          | 네트워크 왕복이 들고, 장애가 나면 전부 미스가 돼요     |
| DB                           | 원장                      | 항상 정확한 값을 줘요               | 가장 느리고 비싸요. 캐시가 막아 주려는 대상이에요      |

이 글에서 말하는 스탬피드는 가장 아래 칸, DB로 몰리는 미스의 문제예요.

## Cache-Control — 캐시별 허용 범위

서버는 응답 헤더로 캐시에게 허락을 줘요. 같은 응답이라도 브라우저, CDN, 앱 캐시가 다르게 읽을 수 있어요.

| 지시어                   | 누구에게        | 뜻                                                                    |
| ------------------------ | --------------- | --------------------------------------------------------------------- |
| max-age=N                | 모든 캐시       | N초 동안은 확인 없이 써도 돼요                                        |
| s-maxage=N               | 공유 캐시 (CDN) | 공유 캐시에서만 max-age 대신 N초를 써요                               |
| no-cache                 | 모든 캐시       | 저장은 하되, 쓰기 전에 원 서버에 확인해요                             |
| no-store                 | 모든 캐시       | 아무 곳에도 저장하지 않아요                                           |
| private                  | 공유 캐시       | 한 사용자만 쓰는 캐시에만 저장할 수 있어요                            |
| stale-while-revalidate=N | 모든 캐시       | 만료된 뒤 N초 동안은 옛 값을 바로 주고, 뒤에서 다시 받아요 (RFC 5861) |
| stale-if-error=N         | 모든 캐시       | 원 서버가 오류일 때 만료된 뒤 N초 동안 옛 값을 줘도 돼요 (RFC 5861)   |
| immutable                | 브라우저        | 내용이 바뀌지 않으니 새로고침에도 확인하지 않아요                     |

상품 페이지 HTML 에는 이런 헤더를 줄 수 있어요.

```http
Cache-Control: public, max-age=0, s-maxage=60, stale-while-revalidate=30
```

브라우저는 매번 확인하고, CDN은 60초 동안 같은 응답을 나눠 줘요. 만료 뒤 30초 동안은 옛 값을 주면서 뒤에서 새 값을 받아요. 결제 API는 다른 규칙을 써요.

```http
Cache-Control: no-store
```

## 쓰기와 무효화 — 지운 뒤에 옛 값이 돌아오는 경쟁

캐시를 읽는 기본 패턴은 cache-aside예요. 앱이 먼저 캐시를 보고, 없으면 DB에서 읽은 뒤 캐시에 넣어요.

```ts
async function getProduct(id: string) {
  const cached = await redis.get(productKey(id));
  if (cached) return JSON.parse(cached);

  const product = await db.product.findUnique({ where: { id } });
  await redis.set(productKey(id), JSON.stringify(product), 'EX', 60);
  return product;
}

async function updatePrice(id: string, price: number) {
  await db.product.update({ where: { id }, data: { price } });
  await redis.del(productKey(id));
}
```

쓰기에서는 캐시를 지울지(delete-on-write), 새 값으로 바꿀지(update-on-write) 골라야 해요. 지우는 쪽이 대부분 더 안전해요. 다음 읽기가 최신 DB 값으로 다시 채우기 때문이에요. 바꾸는 쪽은 두 쓰기가 엇갈리면 나중에 캐시에 들어간 값이 DB와 달라질 수 있어요.

지우기만으로는 막히지 않는 경우도 있어요. 읽는 요청이 DB에서 옛 값을 읽은 뒤, 쓰는 요청이 DB를 바꾸고 캐시를 지워요. 그다음 읽는 요청이 옛 값을 캐시에 다시 넣으면 옛 값이 살아나요.

| 순서 | 요청 A (읽기)                       | 요청 B (가격 변경)       |
| ---- | ----------------------------------- | ------------------------ |
| 1    | 캐시 미스, DB에서 49,000원을 읽어요 |                          |
| 2    |                                     | DB를 39,000원으로 바꿔요 |
| 3    |                                     | 캐시를 지워요            |
| 4    | 읽어 둔 49,000원을 캐시에 써요      |                          |

이때 캐시에는 49,000원이 남아요. TTL이 그 안전망이에요. 틀린 값도 TTL이 지나면 사라져요. 그래서 TTL은 "최대로 틀릴 수 있는 시간"이라고 생각하면 편해요. 중요한 상품이라면 TTL을 짧게 잡고, 쓰기 뒤 짧은 지연을 두고 한 번 더 지우는 방법을 같이 써요.

### 캐시 수명을 짧게 둘 값 — 가격과 재고

가격과 재고는 목록과 상세 화면에서는 잠깐 옛 값이어도 괜찮아요. 하지만 결제 직전에는 옛 값이면 안 돼요. 장바구니에 담을 때 가격을 저장해 두더라도, 결제 시점에 서버가 다시 계산해야 해요. 재고도 마찬가지예요. 자세한 흐름은 [장바구니와 재고](/m/cart-stock)에서 이어서 볼 수 있어요.

## 스탬피드 — 만료 순간 미스가 몰리는 문제

시뮬레이터 기본값으로 계산해 볼게요. 초당 요청이 100건, TTL이 10초, DB 응답이 0.5초라고 해요. 캐시가 만료되면 DB 응답이 돌아오기 전까지 0.5초 동안 들어온 요청 50건이 모두 미스가 돼요. 캐시에는 아직 값이 없으니 50건이 같은 쿼리를 DB에 동시에 던져요.

이 현상을 스탬피드(thundering herd), dog-piling이라고 불러요. XFetch 논문은 인기 있는 캐시 항목이 만료되면 여러 요청이 미스를 보고 같은 항목을 같은 순간에 다시 만든다고 설명해요. 논문 초록은 이 현상이 데이터베이스와 웹 서버의 성능을 심하게 제한한다고 말해요.

핵심은 미스가 많다는 것보다, 같은 일을 여러 번 한다는 점이에요. 값은 하나면 충분한데 DB는 50번 계산해요.

### 요청 병합 (single-flight) — 같은 키 호출을 하나로 묶기

같은 키를 채우는 호출이 진행 중이면 새 호출은 그 결과를 기다려요. Go의 확장 패키지 golang.org/x/sync/singleflight도 같은 방식을 써요. 같은 키의 실행은 한 번에 하나만 진행되고, 중복 호출은 기다렸다가 같은 결과를 받아요.

```ts
const inflight = new Map<string, Promise<Product>>();

function loadOnce(id: string) {
  const running = inflight.get(id);
  if (running) return running;

  const promise = loadFromDb(id).finally(() => inflight.delete(id));
  inflight.set(id, promise);
  return promise;
}
```

이 코드는 한 프로세스 안에서만 병합해요. 서버가 여러 대면 서버마다 DB 조회가 하나씩 나가요. 기다리는 시간이 늘고, 로딩이 실패하면 기다린 요청 모두 같은 오류를 받아요.

### 키 락과 리스 — 여러 서버에서 하나만 채우기

여러 서버에 걸쳐 하나만 채우고 싶다면 공유 캐시에 락을 둬요. Redis SET은 NX와 PX 옵션을 함께 주면 키가 없을 때만, 밀리초 단위 만료와 함께 쓸 수 있어요.

```text
SET product:7:lock <token> NX PX 3000
```

락을 잡은 서버만 DB를 읽고, 나머지는 기다리거나 옛 값을 받아요. 락에도 만료가 있어야 해요. 락을 잡은 서버가 죽어도 락이 풀리도록 해요. 다만 락 만료가 DB 응답보다 짧으면 두 서버가 동시에 채우게 돼요. 락 시간은 DB 응답 시간보다 넉넉하게 잡아요.

### TTL 지터 — 만료 시각 분산

여러 키가 같은 순간에 채워졌다면 같은 순간에 만료돼요. 만료 시간에 무작위 흔들림을 주면 만료가 흩어져요. 시뮬레이터에서는 TTL의 30% 안에서 흔들어요.

지터는 키가 많을 때 효과가 커요. 상품 하나가 한꺼번에 몰리는 상황에서는 효과가 거의 없어요. 시뮬레이터에서 키 20개를 두고 일반 캐시와 TTL 지터를 비교해 보세요. 같은 요청 수에서 만료 순간 동시 조회 수가 크게 줄어요.

### 확률적 조기 갱신 (XFetch) — 만료 전 한 요청이 갱신

XFetch는 만료 전에 요청 한 개가 확률적으로 갱신을 맡아요. 논문의 공식은 이래요.

```text
현재 시각 − δ × β × ln(rand()) ≥ 만료 시각  →  이 요청이 갱신을 시작해요
```

δ 는 값을 다시 만드는 데 걸리는 시간이고, rand()는 0보다 크고 1 이하인 난수예요. ln(rand())은 음수라서, 만료에 가까워질수록 갱신이 시작될 확률이 올라가요. 논문은 β 를 1로 둔 가장 간단한 형태가 별도 튜닝 없이도 잘 동작한다고 말해요.

조기 갱신에도 빈틈이 있어요. 갱신을 맡은 요청이 DB를 기다리는 동안 다른 요청도 같은 조건에 걸릴 수 있어요. 시뮬레이터에서는 키마다 진행 중 표시를 하나 둬서, 갱신이 이미 돌고 있으면 다른 요청이 또 시작하지 않게 했어요.

### 옛 값 먼저 주기 (stale-while-revalidate) — 읽는 쪽 대기 없애기

만료된 값을 바로 주고, 뒤에서 한 번만 갱신하는 방법이에요. RFC 5861은 이 확장이 캐시가 옛 응답을 바로 돌려주면서 백그라운드에서 다시 검증하게 해서, 네트워크와 서버의 지연을 클라이언트에게서 감춘다고 설명해요. 캐시가 HTTP 응답이든, 앱 메모리든 같은 생각을 쓸 수 있어요.

대가는 옛 값이 보이는 시간이에요. 상품 설명이나 이미지 목록에는 잘 맞아요. 가격과 재고에는 옛 값이 보이면 안 되니 쓰지 않아요.

### 네거티브 캐싱과 워밍

없는 상품 조회 결과도 짧게 저장하면, 없는 ID를 반복해서 조회해도 DB를 치지 않아요. 대신 새로 생긴 상품이 짧은 시간 동안 안 보일 수 있어요.

런칭 직전에는 인기 키를 미리 채워 두는 워밍을 해요. 다만 채우는 작업도 DB 부하라서, 시간을 나눠서 채워요.

| 방법             | 무엇을 줄이나                   | 치르는 것                                    |
| ---------------- | ------------------------------- | -------------------------------------------- |
| 요청 병합        | 같은 키의 중복 DB 조회          | 기다리는 시간, 한 프로세스 안에서만 병합해요 |
| 키 락과 리스     | 여러 서버에 걸친 중복 조회      | 락 시간 튜닝, 락 소유자가 죽었을 때 처리     |
| TTL 지터         | 많은 키가 같은 순간 만료되는 것 | 한 키에는 효과가 없어요                      |
| 확률적 조기 갱신 | 만료 순간의 미스                | 갱신 중복 가능, 재계산 시간 추정이 필요해요  |
| 옛 값 먼저 주기  | 읽는 쪽의 대기                  | 옛 값이 보이는 시간                          |
| 네거티브 캐싱    | 없는 키를 반복 조회하는 것      | 새로 생긴 항목이 늦게 보여요                 |
| 워밍             | 런칭 직후 미스 폭주             | 채우는 작업 자체가 부하예요                  |

## 시뮬레이터 — 같은 트래픽, 다른 방법

시뮬레이터는 핫 키 하나에 초당 요청 수, 키 개수, TTL, DB 응답 시간을 넣고 다섯 방법을 비교해요. 같은 시드에서는 도착 순서가 같아서, 방법만 바꿔도 공정하게 비교할 수 있어요.

1. 기본값인 일반 캐시에서 만료 순간 동시 DB 조회 경고를 확인해요.
2. 요청 병합으로 바꾸면 키 하나당 조회가 하나로 줄어요. 대신 기다린 요청 수가 늘어요.
3. 옛 값 먼저 주기로 바꾸면 기다린 요청이 0이 돼요. 옛 값 응답이 그만큼 늘어요.
4. 키 개수를 20으로 올리고 TTL 지터를 고르면 만료가 흩어져요.

## FE 체크 포인트

### FE 캐시 두 층 — 쿼리 캐시와 HTTP 캐시

FE 에도 캐시가 두 층 있어요. 하나는 TanStack Query 같은 쿼리 캐시이고, 다른 하나는 브라우저의 HTTP 캐시예요.

TanStack Query의 staleTime은 데이터를 신선하다고 볼 시간이에요. 기본값은 0 이라서, 데이터를 가져오면 바로 옛 값으로 보고 필요할 때 다시 받아요. gcTime은 아무도 쓰지 않는 쿼리를 메모리에 남겨 두는 시간이에요. 기본값은 5분이에요. 둘은 다른 것을 조절해요. staleTime은 다시 받는 시점을, gcTime은 메모리에서 치우는 시점을 정해요.

```ts
useQuery({
  queryKey: ['product', id],
  queryFn: () => fetchProduct(id),
  staleTime: 30_000,
});
```

화면 여러 곳에서 같은 queryKey를 쓰면 같은 캐시 항목을 함께 써요. 한 곳에서 다시 받으면 다른 곳도 같이 바뀌어요.

### Cache-Control 헤더 — 파일과 API 응답 분리

빌드가 만든 파일은 이름에 해시가 붙어요. 내용이 바뀌면 이름도 바뀌니, 오래 캐시해도 안전해요.

```http
Cache-Control: public, max-age=31536000, immutable
```

상품 정보 API는 사용자나 시점에 따라 달라질 수 있어요. 그래서 ETag를 붙이고 매번 재검증하게 해요.

```http
GET /api/products/7 HTTP/1.1
If-None-Match: "33a64df5"

HTTP/1.1 304 Not Modified
```

If-None-Match 에는 저장해 둔 ETag를 보내요. 서버가 같은 버전이라고 판단하면 본문 없이 304를 주고, 브라우저는 저장해 둔 본문을 써요. MDN은 서버가 클라이언트의 ETag와 현재 값을 비교한다고 설명해요. 결제 API 에는 no-store를 붙여요.

### 가격 불일치 — 화면 가격과 결제 가격

목록은 TTL 안의 옛 가격을, 상세는 최신 가격을 보여 줄 수 있어요. 그래서 사용자는 "화면에서 본 가격과 다르다"고 느껴요. 원인은 대부분 캐시 계층이 다르기 때문이에요.

결제 직전에는 서버가 다시 계산한 가격을 받아서 비교하세요. 다르면 조용히 바꾸지 말고, 바뀐 가격을 보여 주고 사용자가 다시 확인하게 해요.

```ts
const latest = await fetchCheckout(productId);
if (latest.price !== shownPrice) {
  setNotice({ shown: shownPrice, latest: latest.price });
  return;
}
```

"가격이 49,000원에서 39,000원으로 바뀌었어요. 확인하고 다시 결제해 주세요." 같은 안내가 사용자에게 가장 덜 놀라워요.

## 정리 — 만료 순간 중복 조회 줄이기

캐시는 DB 앞에서 같은 조회를 줄여요. 그런데 만료 순간에는 같은 조회가 한꺼번에 몰려서, 캐시가 오히려 DB에 부하를 한꺼번에 줄 수 있어요. 요청 병합은 한 키의 중복을 없애고, TTL 지터는 많은 키의 만료를 흩어요. 조기 갱신과 옛 값 먼저 주기는 만료 순간의 대기를 없애요.

캐시는 입구에서 조회를 줄이고, 대기열은 입구에서 들어오는 속도를 조절해요. 대기열이 어떻게 이어지는지는 [대기열](/m/waiting-room)에서 볼 수 있어요. 같은 자리의 행이 몰리는 문제는 [콘서트 좌석 선점](/m/concert-seats)에서, 여러 문장을 묶어 읽고 쓰는 문제는 [트랜잭션 · 락 · 데드락](/m/transactions)에서 이어서 볼 수 있어요.
