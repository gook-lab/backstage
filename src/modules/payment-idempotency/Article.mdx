결제 버튼을 두 번 누르면 두 번 결제될까요? 대부분은 아니에요. 다만 그 답은 서버가 "같은 결제 시도"를 알아볼 수 있을 때만 맞아요. 이 글에서는 왜 결제가 DB 저장보다 까다로운지, 응답을 잃어버렸을 때 무슨 일이 생기는지, 그리고 멱등성 키와 웹훅 중복 제거로 어떻게 막는지 정리해요.

아래 시뮬레이터에서 같은 상황을 직접 돌려 볼 수 있어요. 더블 클릭, 응답 유실, 재전송, 웹훅 중복을 켜고 끄면서 카드사 승인이 몇 번 나는지 확인해 보세요.

## 결제 — 외부 시스템이라 DB 롤백이 닿지 않는 범위

주문 저장은 우리 DB 안에서 끝나요. 트랜잭션이 실패하면 `ROLLBACK`으로 전부 되돌릴 수 있어요. 결제는 달라요. 카드사 승인은 PG(결제 대행사)와 카드사가 하는 일이라서, 우리 트랜잭션이 롤백돼도 승인은 이미 난 뒤일 수 있어요.

흐름을 한 줄씩 보면 이래요.

| 순서 | 누가        | 무슨 일이 일어나요                             |
| ---- | ----------- | ---------------------------------------------- |
| 1    | 클라이언트  | 결제 요청을 보내요                             |
| 2    | 서버        | 주문을 결제 대기로 바꾸고 PG에 승인을 요청해요 |
| 3    | PG · 카드사 | 승인을 끝내요. 이 순간 돈이 빠져나가요         |
| 4    | 네트워크    | 서버가 클라이언트에 보낸 응답이 끊어져요       |
| 5    | 클라이언트  | 응답이 없어요. 성공인지 실패인지 몰라요        |

3단계까지 일어났고 4단계에서 응답이 사라졌어요. 서버 DB 에는 "결제 완료"가 남아 있지만, 클라이언트는 아무것도 받지 못했어요. 이 "모르는 상태"가 결제 설계의 핵심 문제예요.

## 결제 상태 — 다섯 상태와 UNKNOWN 해소

주문의 결제 상태는 보통 이렇게 흘러가요.

```text
CREATED ──▶ PAYMENT_PENDING ──▶ PAID
                    │
                    ├──▶ FAILED
                    └──▶ CANCELED (승인 뒤 취소)
```

| 상태              | 뜻                                                    |
| ----------------- | ----------------------------------------------------- |
| `CREATED`         | 주문만 만들어졌어요. 아직 승인을 요청하지 않았어요    |
| `PAYMENT_PENDING` | 승인을 요청했고 결과를 기다려요                       |
| `PAID`            | 승인이 확인됐어요. 이 상태만 "결제 완료"로 보여 줘요  |
| `FAILED`          | 승인이 거절됐어요. 다시 결제할지는 새 시도로 처리해요 |
| `CANCELED`        | 승인 뒤 취소됐어요. 환불 흐름이 따로 있어요           |

여기에 `UNKNOWN`이 끼어들어요. 서버가 PG에 요청을 보냈는데 응답이 시간 안에 오지 않으면, 서버도 승인 여부를 몰라요. 이때 주문을 `FAILED`로 바꾸면 돈이 빠져나간 주문이 실패로 남아요. 반대로 `PAID`로 바꾸면 승인이 안 난 주문을 완료로 보여 줄 수 있어요. 그래서 `UNKNOWN`은 "모르겠다"를 그대로 남기는 상태예요.

`UNKNOWN`은 두 방법으로 풀어요.

- **결제 조회.** PG에 "이 주문 승인됐나요?"라고 물어요. 토스페이먼츠는 주문 번호로 결제를 조회하는 `GET /v1/payments/orders/{orderId}`를 제공해요. 조회 결과가 `DONE`이면 `PAID`로, 승인 기록이 없으면 재시도 가능한 실패로 옮겨요.
- **정산 대조 배치.** 하루 한 번 우리 주문 목록과 PG의 승인 목록을 맞춰 봐요. 승인은 있는데 주문이 `PAID`가 아닌 건, 주문은 있는데 승인이 없는 건을 찾아 처리해요.

화면에서는 이 상태를 "결제 확인 중이에요"로 보여 줘요. 실패라고 말하지 않고, 완료라고 추측하지도 않아요.

## 멱등성 키 — 시도마다 키 하나와 서버 판단

멱등성은 같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같게 만드는 성질이에요. 결제에서는 "같은 결제 시도"를 식별하는 키를 요청에 붙여서 얻어요.

IETF의 Idempotency-Key 초안(draft-ietf-httpapi-idempotency-key-header-09, 아직 RFC가 아니에요)은 이 헤더를 이렇게 써요.

```http
POST /payments HTTP/1.1
Idempotency-Key: "8e03978e-40d5-43e8-bc93-6894a57f9324"
Content-Type: application/json

{"orderId": "ORD-1001", "amount": 10000}
```

서버는 키마다 세 가지를 저장해요. 요청의 지문(본문 해시), 처리 상태, 그리고 돌려준 응답이에요. 들어온 요청을 저장된 기록과 맞춰 보면 결과가 네 가지로 나뉘어요.

| 상황                           | 서버가 하는 일                                  | 응답                      |
| ------------------------------ | ----------------------------------------------- | ------------------------- |
| 처음 보는 키                   | 처리 중으로 기록하고 PG에 승인을 요청해요       | 처리 결과                 |
| 같은 키 + 같은 본문, 처리 끝남 | PG를 다시 부르지 않고 저장해 둔 응답을 돌려줘요 | 저장된 응답               |
| 같은 키 + 같은 본문, 처리 중   | 기다리게 해요. 새로 승인하지 않아요             | 409 Conflict              |
| 같은 키 + 다른 본문            | 승인하지 않고 거절해요                          | 422 Unprocessable Content |

초안은 다른 본문에 422, 처리 중 재시도에 409를 권장해요(SHOULD). 두 상태 코드는 RFC 9110에 정의돼 있어요. 422는 RFC 9110 15.5.21 절이에요.

서버 판단을 코드로 줄이면 이렇게 돼요.

```ts
function handlePayment(key: string, body: PaymentBody) {
  const record = store.get(key);
  const hash = fingerprint(body);

  if (!record) return startAndCharge(key, hash, body);
  if (record.hash !== hash) return reject(422);
  if (record.state === 'in-progress') return reject(409);
  return record.response;
}
```

이 판단은 DB 트랜잭션 안에서 키 행에 락을 먼저 걸거나 유니크 제약을 두어 한 요청만 키를 기록하게 해야 해요. 그래야 더블 클릭 두 요청이 동시에 "처음 보는 키"로 읽히지 않아요.

키를 다룰 때 지켜야 할 것도 있어요.

- **키의 수명.** Stripe는 API v1에서 키를 만든 뒤 최소 24시간이 지나면 지울 수 있다고 설명해요. 키가 지워진 뒤 같은 키를 다시 쓰면 새 요청으로 처리돼요. 그래서 클라이언트의 재시도 기간보다 키 보관 기간이 길어야 해요.
- **키의 길이와 내용.** Stripe는 키를 최대 255자로 제한하고, 이메일이나 개인 식별 정보를 키로 쓰지 말라고 권해요. UUID 같은 무작위 값을 쓰세요.
- **실패한 요청.** Stripe는 검증 실패나 동시에 실행 중인 요청과 충돌하면 결과를 저장하지 않는다고 설명해요. 그래서 그런 요청은 다시 보내도 괜찮아요.
- **저장된 500.** Stripe v1은 처리가 시작된 뒤의 첫 응답 상태 코드와 본문을 저장하고, 500 오류도 그대로 돌려준다고 설명해요. 서버 오류라도 같은 키로 재시도하면 같은 오류가 돌아와요. 그래서 키를 새로 만들지 말고 상태를 조회하는 쪽으로 가요.

토스페이먼츠도 취소 API에 멱등성 키를 헤더로 붙이면 중복 취소 없이 안전하게 처리된다고 안내해요. 결제 승인과 취소 모두 같은 원칙이에요.

## 웹훅 — 지연 · 중복 · 순서 뒤섞임

결제가 끝나면 PG가 우리 서버 주소로 웹훅을 보내 줘요. 이 웹훅은 결제 결과를 알려 주는 두 번째 경로예요. 문제는 웹훅이 믿을 수 없게 도착한다는 점이에요.

Stripe의 웹훅 모범 사례는 세 가지를 분명히 해요.

- **중복.** 같은 이벤트가 두 번 올 수 있어요. 처리한 이벤트 id를 기록해 두고, 이미 처리한 id는 건너뛰어요.
- **순서.** 이벤트는 만들어진 순서대로 온다고 보장하지 않아요. 이벤트의 `created` 시각으로 순서를 판단하지 않아야 해요. 이미 처리했는지도 이벤트 id로 판단하세요.
- **서명과 응답.** Stripe가 보낸 요청인지 서명 헤더로 검증해요. 검증에는 원본 본문(raw body)이 필요해서, 프레임워크가 본문을 바꾸면 검증이 실패해요. 처리 로직이 무거우면 먼저 2xx를 돌려주고 뒤에서 처리하세요.

그래서 웹훅 핸들러는 두 가지를 같이 만족해야 해요. 중복이 와도 결과가 같아야 하고, 순서가 뒤섞여도 상태가 뒤로 가지 않아야 해요. 예를 들어 실패 알림이 늦게 와도 이미 `PAID` 인 주문을 `FAILED`로 되돌리면 안 돼요.

프론트엔드가 특히 기억할 점은 결제 완료 페이지예요. 토스페이먼츠 결제위젯은 승인 뒤 `successUrl`로 돌아오면서 `paymentKey`, `orderId`, `amount` 등을 쿼리 문자열로 넘겨요. 이 값만 보고 "결제 완료"라고 표시하면 안 돼요. 서버가 결제 요청 전에 저장해 둔 `orderId`와 `amount`를 대조하고, 금액이 같을 때만 승인 API를 호출해야 해요. 결제 요청이 완료된 뒤 10분 안에 승인하지 않으면 결제 데이터가 유실돼 승인이 불가해요.

## 이중 쓰기 — DB 저장과 이벤트 발행을 같이 묶기

주문을 `PAID`로 저장하고 "결제 완료" 이벤트를 메시지 큐에 보내야 할 때가 있어요. 순서를 어떻게 잡아도 한쪽이 사라질 수 있어요.

- **DB 먼저, 발행 나중.** 저장 뒤 서버가 죽으면 이벤트는 영영 나가지 않아요. 재고 차감이나 알림이 누락돼요.
- **발행 먼저, DB 나중.** 이벤트는 나갔는데 DB가 롤백되면 존재하지 않는 결제를 알리게 돼요.

microservices.io의 트랜잭셔널 아웃박스 패턴은 이 문제를 이렇게 풀어요. 이벤트를 메시지 브로커에 직접 보내지 않고, 주문을 바꾸는 같은 트랜잭션 안에서 아웃박스 테이블에 이벤트 행을 함께 써요. 그러면 주문이 커밋될 때만 이벤트 행이 생기고, 롤백되면 둘 다 사라져요. 별도의 릴레이 프로세스가 아웃박스 행을 읽어 브로커로 보내요. 릴레이는 아웃박스를 폴링하거나 트랜잭션 로그를 따라가는 방식으로 구현할 수 있어요.

이 패턴은 at-least-once 전달을 전제해요. 릴레이는 보낸 뒤 행을 지우기 전에 죽을 수 있어서, 같은 이벤트가 다시 나갈 수 있어요. 그래서 소비자는 메시지 id를 기록해 중복을 걸러내야 해요. microservices.io도 메시지 소비자는 멱등해야 한다고 설명해요. 웹훅 중복 제거와 같은 원리예요.

재고 차감이 실패하면 어떻게 할까요? 결제가 이미 승인됐다면 결제를 되돌려야 해요. 같은 트랜잭션으로 묶을 수 없으니, 실패를 알리고 보상 동작(결제 취소)을 따로 실행하는 식으로 풀어요. 재고 쪽 동시성은 [재고 차감 사례](/m/cart-stock)에서 더 자세히 다뤄요.

## FE 체크 포인트

- **시도당 키 하나.** 결제 버튼을 누를 때마다 키를 하나 만들고, 재시도와 재렌더링에서도 그 키를 유지하세요. 세션 저장소(sessionStorage)에 주문 번호와 함께 두면 새로고침 뒤에도 같은 주문이면 같은 키를 쓸 수 있어요. 재시도 때마다 새 키를 만들면 멱등성이 없어져요.
- **버튼 비활성화는 UX 일 뿐 보장이 아니에요.** 버튼을 끄고 스피너를 보여 주면 대부분의 더블 클릭은 막혀요. 하지만 네트워크 재시도나 탭 두 개에서의 제출은 막지 못해요. 보장은 서버 키가 해요.
- **타임아웃이면 재전송 대신 조회하세요.** 응답이 없을 때 결제를 다시 보내지 마세요. 주문 상태를 조회하세요. 시뮬레이터의 "상태 조회" 시나리오가 이 차이를 보여 줘요.
- **리다이렉트 값만으로 완료 처리하지 마세요.** 쿼리 문자열의 성공 값은 결제의 증거가 아니에요. 완료 화면은 서버가 승인을 확인한 뒤에 보여 주세요.
- **모르는 상태를 그대로 보여 주세요.** 응답이 없으면 "결제 확인 중이에요"라고 보여 주세요. 409를 받으면 "이미 처리 중이에요"라고 안내하고, 422를 받으면 금액이 바뀌었다는 뜻이니 화면 금액을 다시 확인하게 하세요.
- **토스 에러 코드를 구분하세요.** `ALREADY_PROCESSING_REQUEST`는 같은 요청이 처리 중이라는 뜻이고, `DUPLICATED_ORDER_ID`는 이미 승인이나 취소가 진행된 주문 번호라는 뜻이에요. 둘을 같은 실패로 보여 주면 안 돼요.

## 정리 — 키로 시도를 묶고, 조회로 확인하고, 중복을 걸러요

결제는 DB 밖에서 일어나고, 응답은 언제든 사라질 수 있어요. 그래서 이중 결제를 막는 일은 화면 버튼이 아니라 서버가 맡아야 해요. 결제 시도마다 멱등성 키를 붙이고, 서버는 키의 기록으로 승인을 한 번만 해요. 응답을 잃은 결제는 UNKNOWN으로 두고 조회로 확인해요. 웹훅은 이벤트 id로 걸러내고, DB와 이벤트는 아웃박스로 같은 트랜잭션에 묶어요. 트랜잭션 격리와 동시 쓰기는 [트랜잭션 · 락 · 데드락](/m/transactions)에서 먼저 익히면 이 글이 더 쉽게 읽혀요.
