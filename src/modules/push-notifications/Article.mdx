알림 권한을 허용했는데 어떤 사용자만 알림을 못 받는다는 제보가 와요. 프론트엔드(FE)에서는 구독이 됐는지만 보이고, 실제 발송은 앱 서버, 푸시 서비스, 브라우저를 차례로 거쳐요. 이 글에서는 서버가 구독을 어떻게 저장하고, 어떤 헤더로 보내고, 만료된 구독을 어떻게 지우는지 정리해요.

아래 시뮬레이터에서 발송 시각과 TTL을 바꾸면 구독마다 전달, 대기 후 전달, 버림, 삭제 중 무엇이 되는지 직접 볼 수 있어요. 수치는 예시예요.

## 권한 요청 시점 — 사용자 동작 뒤에 묻기

알림 권한 창은 사용자가 누른 버튼 같은 동작 안에서 띄우는 편이 좋아요. MDN은 `Notification.requestPermission()`을 사용자 제스처(예: 클릭)를 처리할 때만 불러야 한다고 설명해요. MDN은 `PushManager.subscribe()`도 사용자 제스처에 맞춰 부르라고 설명해요.

그래서 페이지를 열자마자 권한을 묻기보다 "알림 받기" 버튼을 누른 뒤에 권한 요청과 구독 생성을 이어서 해요.

## 구독 정보 — endpoint와 키를 서버에 저장하기

구독 객체에는 endpoint와 암호화 키가 들어 있어요. MDN은 PushSubscription이 구독의 URL endpoint와 메시지 암호화에 쓸 공개키 및 비밀 값을 제공한다고 설명해요. 서버에 보낼 때는 `getKey()`로 두 키를 꺼내요.

| 값       | 무엇인가                     | 서버에서 쓰는 곳            |
| -------- | ---------------------------- | --------------------------- |
| endpoint | 푸시 서비스가 정한 구독 주소 | 발송 요청을 보내는 대상 URL |
| p256dh   | 브라우저의 P-256 ECDH 공개키 | 메시지 암호화               |
| auth     | 구독마다 만든 인증 비밀      | 암호화 키를 만들 때 섞는 값 |

RFC 8291은 사용자 에이전트가 구독마다 ECDH 키쌍과 인증 비밀을 만들어 앱 서버에 넘긴다고 설명해요. 앱 서버는 이 값으로 메시지를 암호화해서 보내요.

endpoint는 비밀로 다뤄야 해요. MDN은 endpoint를 알고 있으면 그 구독으로 메시지를 보낼 수 있다고 설명해요. 그래서 구독 목록 API 응답에 다른 사용자의 endpoint를 싣지 않는 편이 좋아요.

서버 테이블은 구독 한 기기를 한 행으로 두면 편해요. 예시 스키마는 이래요.

```sql
CREATE TABLE push_subscription (
  id          BIGSERIAL PRIMARY KEY,
  user_id     BIGINT NOT NULL,
  endpoint    TEXT   NOT NULL UNIQUE,
  p256dh      TEXT   NOT NULL,
  auth        TEXT   NOT NULL,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
  last_ok_at  TIMESTAMPTZ
);
```

같은 endpoint가 다시 등록되면 새 행을 만들지 않고 키와 소유자를 갱신하는 편이 좋아요. 이 판단은 설계 선택이에요.

## 전달 경로 — 앱 서버, 푸시 서비스, 브라우저

발송은 앱 서버가 구독의 endpoint로 HTTP POST를 보내는 일이에요. 푸시 서비스가 요청을 받아 브라우저에 전달하고, 브라우저는 Service Worker의 push 이벤트로 받아요. Push API는 웹 앱이 전면에 없거나 아예 로드되어 있지 않아도 서버가 보낸 메시지를 받을 수 있게 한다고 MDN이 설명해요.

RFC 8030은 푸시 서비스가 메시지를 TTL 동안 저장해 두면 사용자 에이전트가 가끔만 연결되어도 전달 신뢰도가 높아진다고 설명해요. 저장은 푸시 서비스의 몫이고, 앱 서버는 그 저장 기간을 TTL로 알려 줘요.

## 서버 식별 — VAPID 키와 JWT

발송 요청에는 누가 보냈는지 알려 주는 서명이 붙어요. RFC 8292는 앱 서버가 서명 키로 JWT를 만들고 Authorization 헤더에 `vapid` 스킴으로 실어 보낸다고 설명해요.

JWT의 claim은 세 가지가 중요해요.

| claim | 뜻                                   | 규칙                                      |
| ----- | ------------------------------------ | ----------------------------------------- |
| aud   | 푸시 서비스의 origin                 | 발송할 endpoint의 origin과 맞아야 해요    |
| exp   | 토큰이 만료되는 시각                 | 요청 시각으로부터 24시간을 넘으면 안 돼요 |
| sub   | 연락처 URI (`mailto:` 또는 `https:`) | 연락처를 담는 것이 권장돼요               |

구독을 만들 때 넘기는 `applicationServerKey`는 MDN에 따르면 푸시 서버가 앱 서버를 인증할 때 쓰는 P-256 공개키예요. 이 키를 넣으면 앱 서버의 메시지는 VAPID 방식을 써야 하고, 대응하는 개인키로 서명한 JWT를 실어야 해요. 그러니 구독 때 넣은 공개키와 서버가 서명하는 개인키는 한 쌍이어야 해요.

## 발송 헤더 — TTL · Urgency · Topic

발송 요청에 붙이는 헤더는 세 가지예요.

| 헤더    | 필수 여부 | 뜻                                      | 확인한 규칙                                                                                                                |
| ------- | --------- | --------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| TTL     | 필수      | 메시지를 저장할 최대 시간(초)           | TTL이 지나면 전달을 시도하지 않아요. TTL을 빼면 푸시 서비스가 400을 반환해요                                               |
| Urgency | 선택      | very-low, low, normal, high 중 하나     | 기기의 전원과 네트워크 상태에 맞춰 전달 시점을 고르는 기준이에요. 채팅은 normal, 긴급 알림은 high 예시가 RFC 8030에 있어요 |
| Topic   | 선택      | 같은 주제의 미전달 메시지를 대체하는 키 | 최대 32자, URL과 파일 이름에 안전한 base64 알파벳만 써요                                                                   |

TTL의 0은 특별해요. RFC 8030은 TTL 0 메시지가 사용자 에이전트가 연결되어 있으면 즉시 전달되고, 연결되어 있지 않으면 만료되어 전달되지 않는다고 설명해요. 그래서 TTL 0은 "지금 켜진 기기에만"이라는 뜻이에요.

Topic은 같은 주제의 메시지가 쌓여 있을 때 최신 상태만 남기는 데 써요. 예를 들어 "주문 상태 변경"처럼 최신 값만 의미가 있는 알림에 맞아요. 메시지가 바뀔 때마다 새 알림을 쌓지 않아도 돼요.

## 구독 만료와 응답 처리 — 404를 받으면 구독 삭제

푸시 서비스는 구독을 언제든 만료시킬 수 있어요. RFC 8030은 만료된 구독에 메시지를 보내면 푸시 서비스가 404를 반환해야 한다고 설명해요. 앱 서버는 이 응답을 받으면 그 구독을 더 보내지 않고 삭제하는 편이 맞아요.

404가 아닌 실패는 구독이 사라졌다는 근거가 아니에요. RFC 8030은 429를 푸시 서비스가 요청을 거절할 때 쓸 수 있는 응답으로 설명해요. 그래서 429나 서버 오류를 받은 구독은 지우지 않고, 재시도는 [메시지 큐](/m/message-queue) 글의 백오프 규칙으로 다뤄요.

RFC 8030에서 410(Gone)은 구독 만료 응답이 아니라 수신 확인(receipt) 실패 응답으로 나와요. 수신 확인은 앱 서버가 요청했을 때만 돌아와요. 이 글은 구독 만료 신호를 404로 설명해요.

클라이언트 쪽에도 만료 신호가 있어요. W3C Push API 명세는 구독을 더 쓸 수 없을 때, 예를 들어 만료되었을 때 브라우저가 `pushsubscriptionchange` 이벤트를 발생시키고, 새 구독이 없으면 newSubscription을 null로 준다고 설명해요. 권한이 취소될 때도 브라우저가 이 이벤트를 발생시킬 수 있어요(MAY). MDN도 이 이벤트를 구독이 무효화되거나 무효화되려 할 때 발생한다고 설명해요.

## 전달 보장 범위 — 푸시는 신호, 알림함이 원본

RFC 8030 발송 응답에서 201 Created는 메시지가 받아들여졌다는 뜻이에요. RFC 8030은 이 응답이 사용자 에이전트에게 전달되었다는 뜻이 아니라고 명시해요. 발송 성공을 기기 도착으로 기록하면 안 되는 이유예요.

수신 확인도 기본값이 아니에요. 앱 서버가 `Prefer: respond-async`로 요청할 때만 푸시 서비스가 확인 경로를 열어 줘요. RFC 8030은 수신이 확인되면 재전송, 폴링, 상태 재동기화를 피할 수 있다고 설명해요.

그래서 알림 내용은 앱 서버의 알림함 테이블에 먼저 저장하고, 푸시는 "확인하러 오세요" 신호로만 보내는 편이 안전해요. 이 부분은 설계 판단이에요. 본문을 푸시에 싣지 않으면 발송이 버려져도 알림 내용은 알림함에 남아요. 사용자는 알림함에서 놓친 알림을 다시 볼 수 있어요.

## 관련 모듈 — 실시간 전달 · 재시도 · 대량 발송 · 웹훅

이 글은 웹 푸시의 구독과 발송 헤더만 다뤄요. 다음 내용은 해당 글에서 이어 봐요.

- SSE와 WebSocket처럼 페이지가 열려 있을 때의 실시간 전달은 [실시간 전달](/m/realtime-delivery) 글에서 다뤄요. 탭을 닫은 뒤의 알림이 Web Push의 영역이에요.
- 발송 실패 재시도, DLQ, 중복 처리는 [메시지 큐](/m/message-queue) 글에서 다뤄요.
- 대량 발송을 작업 단위로 나누고 상태를 조회하는 방식은 [백그라운드 작업](/m/background-jobs) 글에서 다뤄요.
- 외부 이벤트가 발송을 트리거하고 같은 이벤트가 두 번 들어오는 경우는 [웹훅 수신](/m/webhook-receiving) 글에서 다뤄요.

## FE 체크 포인트

- 권한 요청과 구독 생성은 "알림 받기" 버튼 뒤에 한 번만 해요.
- 구독을 만든 직후 endpoint와 키를 서버에 보내요. 서버 저장이 끝난 뒤에만 "알림 받기가 설정됐어요"라고 보여 줘요.
- Service Worker에서 `pushsubscriptionchange`를 받으면 새 구독을 서버에 다시 보내요.
- 알림 목록은 서버 API에서 가져와요. 푸시는 목록을 다시 가져올 신호로만 써요.
- 설정 화면에서 알림을 끄면 브라우저 구독을 해제하고, 서버의 구독 행도 지워요.

## 시뮬레이터 안내

아래 시뮬레이터에서 다음 순서로 바꿔 보세요.

1. 기본값(발송 10, TTL 5)에서 노트북은 바로 전달돼요. 휴대폰은 2틱 뒤에 켜져서 대기 후 전달돼요. 태블릿은 TTL 안에 켜지지 않아 틱 15에 버려져요. 옛 구독은 404로 삭제돼요.
2. TTL을 0으로 내리면 꺼진 기기는 모두 그 자리에서 버려져요.
3. 발송 시각을 25로 옮기고 TTL을 20으로 올리면 태블릿은 틱 40에 대기 후 전달돼요. 휴대폰은 이미 켜져 있어서 바로 전달돼요.
4. 발송 시각을 15로 옮기면 휴대폰은 틱 12부터 켜져 있어서 TTL과 관계없이 바로 전달돼요.

## 정리 — 구독 저장 · VAPID 식별 · TTL · 404 삭제 · 알림함 원본

구독은 endpoint와 키로 서버에 저장하고, 발송은 VAPID로 서버를 밝힌 HTTP 요청으로 해요. TTL과 Topic으로 전달 시점과 대체를 정하고, 404를 받은 구독은 지워요. 발송 성공은 기기 도착이 아니므로 알림의 원본은 앱 서버의 알림함에 둬요.
