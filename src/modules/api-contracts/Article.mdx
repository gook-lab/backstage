프론트엔드(FE)에서 사용자 정보를 받아 화면에 그리는 코드가 있어요. 응답 타입은 개발자가 손으로 적어 두었고, 컴파일은 늘 통과해요. 그런데 백엔드(BE)가 `name`을 `fullName`으로 바꾸면 화면은 경고 없이 실행 중에 깨져요.

이 글은 이 어긋남을 줄이는 방법을 다뤄요. 계약(contract)을 명세 문서로 적고, 타입은 명세에서 만들고, 응답은 받은 자리에서 검사해요. 명세가 바뀔 때는 CI에서 깨짐을 먼저 찾는 흐름까지 이어 봐요.

글의 응답 예시와 필드 이름은 설명을 위한 예시예요. 아래 시뮬레이터의 값과 같아요.

## 증상 — 손으로 적은 타입과 서버 응답의 어긋남

```ts
interface User {
  name: string;
  nickname: string | null;
}

const user = (await res.json()) as User;
user.name.trim(); // 서버가 fullName 만 보내면 여기서 터져요
```

컴파일러는 서버가 실제로 보낸 값을 볼 수 없어요. `as User`는 "이 값은 User 모양이다"라고 적을 뿐이라 응답이 달라도 이 줄을 막지 않아요. 어긋남은 실행해야 드러나고, 드러나는 곳도 `trim`을 부르는 화면 깊은 곳이에요. 원인은 응답의 칸 이름인데 증상은 전혀 다른 자리에 나타나요.

## API 계약 — 경로 · 모양 · 허용 값을 적은 약속

계약은 소비자(FE)와 제공자(BE)가 주고받는 요청과 응답의 약속이에요. 경로와 메서드, 요청 칸, 응답 칸, 각 칸의 타입, 필수 여부, 허용 값을 담아요. 약속이 코드 안에만 있으면 한쪽이 바꿔도 다른 쪽은 알 수 없어요. 그래서 사람과 도구가 함께 읽는 명세 문서에 적어 둬요.

## OpenAPI 명세 — paths와 components/schemas

OpenAPI Specification 3.1.1은 HTTP API를 기계가 읽을 수 있는 문서로 적는 형식이에요. 최상위에는 경로별 동작을 적는 Paths Object가 있고, 여러 곳에서 쓰는 모델은 Components Object 아래 `schemas`에 둬요. 모델의 칸 규칙은 Schema Object로 적어요.

예시 명세는 이래요.

```yaml
paths:
  /users/{id}:
    get:
      responses:
        '200':
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/User'
components:
  schemas:
    User:
      type: object
      required: [id, name, email, nickname, role, createdAt]
      properties:
        id: { type: integer }
        name: { type: string }
        email: { type: string }
        nickname: { type: [string, 'null'] }
        role: { enum: [admin, member] }
        createdAt: { type: string, description: RFC 3339 날짜 시간 문자열 }
```

3.1.1 명세는 데이터 타입 목록에 `null`을 포함해요. 그래서 값이 null일 수 있는 칸은 타입 목록에 `null`을 넣어 표현해요. `nickname`이 문자열이거나 null이라는 뜻이에요.

## JSON Schema — 명세 칸 규칙의 바탕

OpenAPI 3.1의 Schema Object는 JSON Schema 2020-12의 어휘와 타입을 기반으로 해요. JSON Schema에서 `required`는 필수 칸 이름의 배열이에요. 이 목록에 없는 칸은 기본으로 필수가 아니에요.

`additionalProperties`를 적지 않으면 목록에 없는 추가 칸도 기본으로 허용돼요. 그래서 응답에 칸이 늘어나도 명세 검사는 통과해요. 칸 추가가 옛 소비자를 깨는지는 소비자가 추가 칸을 무시하는지에 달려 있어요. `enum`은 허용 값을 목록으로 제한하고, 목록에 없는 값은 명세 위반이에요.

## TypeScript 타입 — 컴파일 시점에만 있는 설계도

TypeScript 핸드북은 타입 단언(Type Assertions)이 컴파일러에 의해 지워지며 런타임 동작을 바꾸지 않는다고 설명해요. 같은 페이지는 단언이 컴파일 시점에 지워지므로 런타임 검사도 없다고 적어요. 타입 어노테이션과 마찬가지예요.

그래서 `as User`는 응답이 User 모양인지 확인하지 않아요. 타입은 개발할 때 쓰는 설계도이고, 실행 중에 도착하는 JSON은 그 설계도로 검사되지 않아요. 검사가 필요하면 실행 코드를 따로 두어야 해요.

## 경계 파싱 — unknown 수신과 칸별 검사

응답을 받는 자리에서 타입을 `unknown`으로 두고, 칸을 하나씩 확인한 뒤에야 `User`로 좁히는 방식을 경계 파싱이라고 불러요. 경계에서 멈추면 원인이 응답을 받은 곳에 드러나요. 화면 깊은 곳에서 엉뚱한 예외를 보는 일이 줄어요.

```ts
const body: unknown = await res.json();
const user = parseUser(body); // 어긋나면 여기서 멈추고, 화면은 그리지 않아요
```

| 방식                       | 어디서 드러나나                     | 화면 결과                             |
| -------------------------- | ----------------------------------- | ------------------------------------- |
| 타입 단언만 (`as`)         | 화면 깊은 곳, 또는 드러나지 않음    | 틀린 값이 에러 없이 보이기도 해요     |
| 경계 파싱                  | 응답을 받은 자리                    | 오류 화면과 위반 칸 목록              |
| 경계 파싱 + 모르는 값 대체 | 응답을 받은 자리 (대체 내역은 기록) | 모르는 값만 기본값으로 바꿔 보여 줘요 |

경계 파싱은 응답마다 검사 코드를 늘려요. 설계 판단이에요. 그래도 실패를 일찍 드러내는 편이 낫다고 보는 이유는, 틀린 값이 조용히 화면에 남는 실패는 찾기 어렵기 때문이에요.

## 명세 원본 — 명세 우선과 코드 우선

명세를 먼저 쓰는 방식(spec-first)과 서버 코드에서 명세를 만드는 방식(code-first)은 원본이 달라요.

| 방식                   | 원본      | 장점                                                                    | 주의                                              |
| ---------------------- | --------- | ----------------------------------------------------------------------- | ------------------------------------------------- |
| 명세 우선 (spec-first) | 명세 파일 | FE와 BE가 같은 문서를 먼저 리뷰해요. 목 서버와 타입을 명세에서 만들어요 | 구현과 명세가 어긋나지 않게 검사를 붙여야 해요    |
| 코드 우선 (code-first) | 서버 코드 | 구현을 바꾸면 명세가 따라가요                                           | 명세가 바뀌는 순간이 리뷰 대상에 잘 오르지 않아요 |

FE와 BE가 다른 사람이 맡는 팀이라면 명세 우선이 맞는 편이에요. 이 부분도 설계 판단이에요. 명세가 원본이면 명세 변경이 PR로 보이고, 그 변경을 양쪽이 함께 승인하게 돼요.

## 타입 생성 — 명세 기반 생성과 생성 파일 보호

openapi-typescript는 README에서 OpenAPI 3 명세로부터 TypeScript 타입을 생성하는 도구로 소개해요. 명세가 바뀌면 타입을 다시 만들어요. 생성된 타입도 TypeScript 타입이라 실행 중 검사를 만들지 않아요. 앞 절의 한계가 그대로 남아요.

생성 파일을 손으로 고치면 다시 만들 때 덮어써질 수 있어요. 명세와 코드가 어긋난 채 남기도 해요. 그래서 고칠 곳은 명세나 명세를 쓰는 코드예요. 생성 파일은 읽기만 해요.

## 하위 호환 판단 — 추가 · 이름 변경 · enum 값

아래 표는 기본 판단이에요. 실제 영향은 소비자가 그 값을 무엇에 쓰는지에 따라 달라요.

| 변경                      | 옛 소비자 영향 | 이유                                                                        |
| ------------------------- | -------------- | --------------------------------------------------------------------------- |
| 응답 칸 추가              | 대개 안전      | 소비자가 모르는 칸을 무시하면 돼요. JSON Schema 기본값도 추가 칸을 허용해요 |
| 응답 칸 제거 · 이름 변경  | 깨짐           | 옛 이름을 읽던 코드가 undefined를 받아요                                    |
| 타입 변경 (숫자 → 문자열) | 깨짐           | 칸 이름이 같아서 컴파일은 통과하고 실행 중에 어긋나요                       |
| enum 값 추가              | 깨질 수 있어요 | 목록을 닫힌 집합으로 보면 새 값에서 분기가 빠져요                           |
| 선택 칸을 필수로 바꿈     | 깨질 수 있어요 | 옛 응답에 그 칸이 없으면 검사에서 멈춰요                                    |

배포 순서와 옛 앱이 동시에 도는 구간은 [스키마 마이그레이션 사례](/m/schema-migration)에서 다뤄요. 이 글은 변경이 호환 규칙을 어기는지 자동으로 찾는 데 집중해요.

## 계약 테스트 — 소비자 주도 기대 검증

명세는 모양을 적지만, 소비자가 실제로 쓰는 칸은 따로 알려 주지 않아요. 소비자 주도 계약 테스트는 소비자가 요청과 기대하는 응답을 계약으로 적고, 제공자가 그 계약을 검증하는 방식이에요. Pact 문서는 Pact를 코드 우선 소비자 주도 계약 테스트 도구로 소개해요.

Pact 문서는 계약 테스트가 서비스 사이의 HTTP와 메시지 연동이 공유한 계약에 맞는지 검사한다고 설명해요. FE가 쓰는 칸을 계약으로 적어 두면, BE가 그 칸을 지우려 할 때 BE 쪽 검증이 먼저 실패해요. 명세만으로는 보이지 않던 "누가 무엇을 쓰는가"가 드러나는 지점이에요.

## CI 검사 — 명세 비교와 PR의 깨짐 목록

명세 파일을 PR마다 기준 브랜치의 명세와 비교하면, 깨지는 변경을 머지 전에 찾을 수 있어요. oasdiff는 README에서 OpenAPI 명세를 비교해 변경을 찾고 깨지는 변경(breaking changes)을 구분하는 도구로 소개해요. 직접 짠 스크립트로 같은 일을 해도 괜찮아요.

중요한 것은 깨짐 목록이 PR에서 보이게 하는 거예요. 명세 비교만으로는 소비자가 실제로 무엇을 쓰는지 알 수 없어요. 그래서 계약 테스트와 함께 써요.

## null과 칸 없음 — JSON 값 종류의 구분

RFC 8259는 JSON 값이 false, null, true, object, array, number, string 중 하나라고 정의해요. undefined는 이 목록에 없어요. JSON Schema 문서도 null은 칸이 없는 것과 같지 않다고 설명해요.

그래서 `{ "nickname": null }`과 `{}`는 서로 다른 응답이에요. 전자는 서버가 "값이 없다"고 말한 것이고, 후자는 서버가 칸을 말하지 않은 것이에요. 검사는 `'nickname' in body`로 칸의 존재를 먼저 보고, 그다음 값이 `string | null`인지 확인해요. 화면에서도 두 경우를 같은 문구로 덮지 않아요.

## 날짜 · 큰 정수 — 문자열과 정수 범위

RFC 3339는 날짜와 시간을 `2026-11-24T09:00:00Z`처럼 날짜, `T`, 시간, UTC 표시 또는 오프셋을 갖춘 문자열로 정의해요. 명세에는 이 형식을 description에 적고, 경계에서 형식을 검사해요. 시간대 표시는 [날짜 · 시간대 · 다국어](/m/time-and-locale)에서 다뤄요.

RFC 7493은 정수의 절댓값이 9007199254740991(2^53 − 1)을 넘으면 수신 쪽이 정확한 값으로 다룬다고 기대할 수 없다고 설명해요. 정확히 주고받아야 하는 큰 수는 JSON 문자열로 담는 방법을 권해요. 큰 ID를 JSON 숫자로 보내면 자바스크립트에서 값이 바뀔 수 있어요. ID를 어떻게 발급하는지는 [ID 설계 — 자동 증가와 UUID](/m/distributed-ids)에서 다뤄요.

시뮬레이터의 큰 번호 예시가 이 경우예요. `9007199254740993`이 JSON.parse를 지나면 `9007199254740992`가 돼요.

## FE 체크 포인트

- 응답은 받은 자리에서 `unknown`으로 받고, 파서 함수 하나를 거쳐 `User`로 좁혀요. 컴포넌트에서 `as`로 바로 쓰지 않아요.
- 모르는 enum 값은 화면을 멈출지, 기본값으로 보여 줄지 미리 정해요. 어느 쪽이든 조용히 바꾸지 않아요. 바꾼 내역은 로그에 남겨요.
- 생성된 타입 파일은 직접 고치지 않아요. 고칠 곳은 명세예요.
- 명세로 목(mock) 서버를 만들면 BE 구현을 기다리지 않고 같은 모양의 응답으로 화면을 만들 수 있어요. 목 서버 응답도 같은 경계 파서를 통과시켜서 명세와 어긋나지 않게 해요.
- 응답 본문의 큰 정수 ID가 문자열로 오는지 명세에서 먼저 확인해요.

## 시뮬레이터 안내

아래 시뮬레이터는 사용자 응답 명세 하나를 두고, 서버 응답 여덟 가지와 FE 처리 방식 세 가지를 골라 봐요. 기본값은 타입 단언만 쓰고 이름이 바뀐 응답이에요. 화면 깊은 곳에서 예외가 나는 것을 볼 수 있어요.

경계 파싱으로 바꾸면 같은 응답이 수신 자리에서 멈추고, 위반 칸 목록이 나와요. 타입 단언만 쓰고 번호가 문자열로 오면 에러 없이 다음 번호가 틀린 값으로 보여요. 컴파일 단계에서는 어떤 조합도 드러나지 않는다는 점도 화면 아래에 적어 뒀어요.

## 정리 — 명세 원본 · 경계 파싱 · 호환 규칙 · 계약 검사

계약의 원본은 명세 문서로 두고, TypeScript 타입은 명세에서 만들어요. 타입은 실행 중에 사라지므로 응답은 경계에서 `unknown`으로 받아 칸마다 검사해요. 칸 추가는 대개 안전하고, 이름 변경과 타입 변경, enum 값 추가는 옛 소비자를 깨질 수 있어요.

명세의 두 버전은 CI에서 비교해 깨지는 변경을 PR에서 먼저 보여 줘요. 소비자가 실제로 쓰는 칸은 계약 테스트로 확인해요.
