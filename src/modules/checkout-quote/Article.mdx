장바구니에서는 24,000원이던 주문이 결제 화면에서 26,000원이 된 적이 있을 거예요. 예시로 가격이 올랐거나, 쿠폰 기간이 지났거나, 배송비 기준이 바뀌었을 수 있어요. 프론트엔드에서는 "방금 본 금액인데 왜 다르죠?"라는 질문으로 시작하는 문제예요.

이 글은 결제 직전에 금액을 확정하는 흐름을 다뤄요. 서버가 어떤 금액을 믿는지, 그 금액을 견적으로 어떻게 기록하는지, 바뀐 항목을 사용자에게 어떻게 알리는지 정리해요. 아래 시뮬레이터에서 사건과 처리 방식을 고르면 청구 금액과 거절 여부가 어떻게 달라지는지 볼 수 있어요.

## 금액의 출처 — 클라이언트 금액은 참고값으로 두기

결제 요청에 담긴 금액은 브라우저가 보낸 값이에요. 브라우저에서 어떤 값으로든 바꿔 보낼 수 있어요. OWASP 치트시트는 가격, 소계, 세금, 합계를 클라이언트에게서 받지 말라고 권해요. 상품 식별자와 수량만 받고, 나머지는 서버가 자기 DB에서 계산하라는 뜻이에요.

할인과 배송비도 같은 원칙이에요. 같은 치트시트는 쿠폰 코드를 받아 서버가 검증하고 할인을 직접 적용하라고 권해요. 할인 금액 필드를 요청에서 받지 말라고도 해요.

| 클라이언트가 보내는 것 | 서버가 하는 일                           | 클라이언트 값을 쓰는 곳            |
| ---------------------- | ---------------------------------------- | ---------------------------------- |
| 상품 id · 수량         | 현재 단가로 줄 금액을 계산해요           | 없음                               |
| 쿠폰 코드              | 쿠폰 규칙을 확인하고 할인액을 계산해요   | 없음. 할인 금액 필드는 받지 않아요 |
| 배송지 · 배송 방식     | 서버의 배송비 기준표로 배송비를 계산해요 | 없음                               |
| 견적 id                | 저장된 견적을 찾아 재계산 값과 비교해요  | 비교 기준을 찾는 키                |

쿠폰 할인 계산은 [쿠폰 적용](/m/coupon-redemption)의 할인 금액 절에서 더 자세히 다뤄요. 금액 단위와 반올림은 [금액 계산](/m/money-amounts)을 따라요.

## 견적 스냅샷 — 결제 화면 진입 때 금액 내역 저장하기

결제 화면에 들어갈 때 서버가 금액 내역을 계산해 저장해요. 이 저장된 묶음을 견적이라고 불러요. 견적에는 견적 id, 줄별 금액, 할인, 배송비, 합계, 만료 시각이 들어가요.

예시 응답은 이래요.

```json
{
  "quoteId": "q_7f3a",
  "lines": [{ "productId": 101, "unitPrice": 12000, "quantity": 2, "lineAmount": 24000 }],
  "discount": 3000,
  "shippingFee": 3000,
  "total": 24000,
  "expiresAt": "2026-11-24T10:10:00+09:00"
}
```

견적 id는 결제 요청이 어떤 금액을 가리키는지 알려 줘요. 프론트엔드는 합계를 다시 계산해 보내지 않고, 견적 id와 화면에 보여 준 `total`을 함께 들고 가요. 화면에 보이는 합계도 응답의 `total`을 그대로 써요.

## 견적 만료 — 기한이 지난 견적을 거절하기

OWASP 치트시트는 사용자 입력을 기다리는 흐름에는 기한을 두라고 권해요. 견적도 결제 전까지 기다리는 상태이므로 같은 원칙을 따라요. 만료 시각을 두고, 기한이 지나면 재계산 전에 거절해요.

토스페이먼츠 API 레퍼런스는 결제 인증이 유효한 10분 안에 승인 API를 호출하지 않으면 결제가 만료된다고 설명해요. 견적 유효 시간을 10분으로 두는 것은 이 값을 참고한 예시예요. 실제 시간은 서비스 정책으로 정해요.

## 결제 요청 — 견적 id로 비교하고 거절하기

결제 요청을 받으면 서버는 아래 순서로 처리해요.

1. 견적 id로 저장된 견적을 찾아요. 없거나 다른 사용자의 견적이면 거절해요.
2. 만료 시각을 확인해요. 지났으면 거절해요.
3. 같은 상품, 수량, 쿠폰, 배송지로 금액을 지금 다시 계산해요.
4. 재계산 합계와 견적 합계를 비교해요. 같으면 주문을 만들어요. 다르면 바뀐 항목 목록을 담아 거절해요.

비교와 주문 생성 사이에도 가격이 바뀔 수 있어요. 그래서 견적 상태를 조건부 UPDATE로 `OPEN`에서 `USED`로 바꾸고, 영향받은 행 수가 1일 때만 주문을 만드는 편이 좋아요.

같은 견적으로 결제 요청이 두 번 들어와도 한 번만 통과해요. 네트워크 재시도를 안전하게 만드는 방법은 [결제 멱등성](/m/payment-idempotency)에서 따로 다뤄요.

거절 응답은 이런 모양이에요. 예시 응답이에요.

```http
HTTP/1.1 409 Conflict
Content-Type: application/json

{
  "code": "QUOTE_CHANGED",
  "quoteId": "q_7f3a",
  "changes": [{ "kind": "price", "before": 12000, "after": 13000 }],
  "total": 26000
}
```

## 상태 코드 — 409와 422 나누기

RFC 9110은 409 Conflict를 요청이 대상 리소스의 현재 상태와 충돌해 끝낼 수 없을 때 쓴다고 설명해요. 사용자가 충돌을 해결하고 다시 보낼 수 있을 때 쓰인다고도 해요. 가격과 만료는 현재 상태와 맞지 않는 요청이라 409로 보는 편이 자연스러워요.

RFC 9110은 422 Unprocessable Content를 요청 문법은 맞지만 담긴 지시를 처리할 수 없을 때 쓴다고 설명해요. 예를 들어 수량이 0 이하처럼 값의 의미가 틀린 요청이 여기에 들어가요.

| 상황                           | 상태 코드 | 이유                                            |
| ------------------------------ | --------- | ----------------------------------------------- |
| 재계산 금액이 견적과 다름      | 409       | 현재 가격 상태와 충돌해요. 새 견적으로 해결돼요 |
| 견적 유효 시간이 지남          | 409       | 현재 상태와 충돌해요. 새 견적을 받으면 해결돼요 |
| 요청은 맞지만 값이 의미상 틀림 | 422       | 문법은 맞지만 처리할 수 없는 요청이에요         |

RFC 9110은 409 응답에 충돌 원인을 사용자가 알아볼 수 있는 내용을 담으라고 권해요. 그래서 위 예시처럼 `changes` 목록을 함께 보내요. 상태 코드 전체 규칙과 오류 본문 형식은 [API 오류 응답](/m/api-errors)에서 다뤄요.

## 가격과 재고 — 견적 기록 항목과 결제 시점 확인 항목

기준은 하나예요. 사용자가 본 값은 견적에 기록하고, 결제 때 다시 계산한 값과 비교해요. 다르면 사용자에게 다시 동의를 받아요. 여러 사용자가 나눠 쓰는 자원은 견적에 잡아 두지 않고 결제 시점에 확인해요.

| 항목        | 다루는 방식                                  | 이유                                                                                           |
| ----------- | -------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| 상품 단가   | 견적에 기록하고 결제 때 재계산 값과 비교해요 | 사용자가 본 금액이에요. 바뀌면 다시 동의를 받아야 해요                                         |
| 쿠폰 할인액 | 견적에 기록하고 결제 때 재계산 값과 비교해요 | 화면의 금액 내역과 청구 금액이 같은 값을 써야 맞아요                                           |
| 배송비      | 견적에 기록하고 결제 때 재계산 값과 비교해요 | 배송지가 같으면 같은 값을 보여 줘야 해요                                                       |
| 재고        | 결제 시점에만 확인해요                       | 견적에서 잡아 두면 결제하지 않은 사용자가 재고를 묶어요. [장바구니와 재고](/m/cart-stock) 참고 |

견적이 유효한 동안은 값이 바뀌어도 견적 금액으로 받아 주는 정책도 있어요. 이 글은 바뀌면 다시 동의를 받는 쪽을 골랐어요.

쿠폰 수량 한도처럼 여러 사용자가 나눠 쓰는 값도 결제 시점에 확인해요. 이 값은 [쿠폰 적용](/m/coupon-redemption)에서 다뤄요. 어느 값을 견적에 기록하고 어느 값을 결제 때 확인할지는 설계 판단이에요. 위 표는 이 글의 기준이에요.

## 결제사 금액 검증 — 승인 전에 저장값과 맞추기 (토스페이먼츠)

토스페이먼츠 결제위젯 연동 가이드는 결제를 요청하기 전에 orderId와 amount를 서버에 임시로 저장하라고 안내해요. 결제 요청과 승인 사이에 데이터 무결성을 확인할 때 필요하다고 설명해요.

같은 가이드는 successUrl로 돌아온 쿼리의 amount와 `setAmount()`에 넣은 amount가 같은지 확인하라고 안내해요. 값이 다르면 결제를 취소하고 사용자에게 알리라고 설명해요.

결제 승인 API(`POST /v1/payments/confirm`)는 paymentKey에 해당하는 결제를 검증하고 승인해요. amount는 필수 요청 필드예요.

가이드가 비교하는 값은 `setAmount()`에 넣은 금액이에요. 여기에 견적 합계를 넣으면 같은 원리를 따를 수 있어요. 아래 흐름은 이 설계 판단이에요.

1. 결제 화면에서 견적을 받고, 견적 합계를 서버에 저장해요. 같은 값을 `setAmount()`에 넣어요.
2. successUrl로 돌아온 amount는 브라우저를 거친 값이라 참고용으로만 봐요. 서버 저장값과 비교만 해요.
3. 두 값이 같으면 승인 API를 호출해요. 승인 요청의 amount도 서버 저장값을 써요.
4. 다르면 승인하지 않고 결제를 취소한 뒤 사용자에게 알려요.

견적 만료 시각은 결제 인증 만료 시각보다 앞에 두는 편이 좋아요. 견적이 먼저 끊기면 사용자는 새 견적을 받으면 되고, 승인 직전에 금액이 바뀌는 틈을 줄일 수 있어요.

## FE 체크 포인트

**결제 화면에 들어갈 때 견적을 받아요.** 장바구니에서 계산해 둔 숫자를 결제 금액으로 그대로 쓰지 마세요. 응답의 `total`을 보여 주세요.

**바뀐 항목은 구체적으로 적어요.** "상품 가격 12,000원 → 13,000원"처럼 적으면 사용자가 무엇에 다시 동의하는지 알 수 있어요. "오류가 났어요"라는 토스트 하나로는 부족해요.

**재견적은 사용자가 누르게 해요.** 409를 받았을 때 바로 새 견적을 받아 결제를 이어 가면, 사용자가 본 적 없는 금액으로 결제될 수 있어요. "바뀐 금액으로 다시 견적 받기" 버튼을 두세요.

**만료 응답도 같은 흐름으로 처리해요.** "견적 시간이 지났어요. 다시 받으면 최신 금액을 볼 수 있어요"처럼 원인과 다음 행동을 한 문장씩 보여 주세요.

**재시도는 같은 견적 id와 같은 멱등성 키로 보내요.** 키 규칙은 [결제 멱등성](/m/payment-idempotency)을 따라요.

**로딩 문구는 짧게 써요.** "금액을 확인하는 중이에요"처럼 무엇을 기다리는지만 알려 주세요.

## 시뮬레이터 안내

시뮬레이터에서 결제 직전 사건과 처리 방식을 고를 수 있어요. 사건은 가격 인상, 쿠폰 만료, 배송비 기준 변경, 아무 일 없음이에요. 처리 방식은 클라이언트 금액 신뢰, 서버 재계산만, 견적 id + 재계산이에요. 견적을 받고 흐른 시간을 조절하면 만료 거절도 볼 수 있어요.

결과 영역에서 사용자가 본 금액, 서버 계산 금액, 청구 금액, 거절 여부를 확인해요. 사용자에게 보여 준 변경 항목도 함께 나와요. 같은 사건이라도 처리 방식에 따라 청구 금액과 안내 문구가 달라져요. 수치는 감을 잡기 위한 예시예요.

## 정리 — 서버 재계산 · 견적 스냅샷 · 줄 단위 변경 응답

서버는 클라이언트 금액을 참고값으로만 받아요. 견적 스냅샷과 재계산 값을 비교하고, 다르면 바뀐 항목을 담아 409로 거절해요. 가격은 견적에 기록해 결제 때 비교하고, 재고와 쿠폰 수량은 결제 시점에 확인해요. 결제사 승인 전에는 서버에 저장한 금액과 승인 요청의 금액을 맞춰요.

할인 계산의 세부 규칙은 [쿠폰 적용](/m/coupon-redemption), 재고 차감 시점은 [장바구니와 재고](/m/cart-stock)에서 이어서 읽어 보세요.
