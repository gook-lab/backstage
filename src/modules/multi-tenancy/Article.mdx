B2B SaaS는 한 서비스를 여러 회사가 함께 써요. 회사 하나를 테넌트(tenant)라고 불러요. 한 테넌트의 데이터가 다른 테넌트에 보이지 않게 하는 성질을 격리(isolation)라고 해요.

이 글은 격리를 어떤 모델로 나눌지, 테넌트를 요청의 어느 값으로 정할지, 빠진 조건을 어떻게 막을지 정리해요. 아래 시뮬레이터에서 사고 시나리오를 고르면 다른 회사 데이터가 보이는지와 영향 범위가 바로 달라져요.

## 증상 — 주소창의 회사 id만 바꾼 요청

회원 A는 회사 A의 화면을 열었어요. 주소창의 회사 id를 B로 바꾸자 회사 B의 주문 목록이 나와요. 예시 상황이에요. 로그인은 맞았고, 회원 역할 검사도 통과했어요.

AWS SaaS 아키텍처 문서는 테넌트 격리를 인증과 인가와 따로 다뤄요. 인증되고 권한도 받은 사용자가 다른 테넌트의 자원에 닿을 수 있다고 설명해요. 그래서 "로그인했으니 괜찮다"는 판단으로는 충분하지 않아요.

한 주문이 누구 것인지 확인하는 검사는 [인가 · 객체 수준 권한](/m/authorization) 글에서 다뤘어요. 이 글은 한 단계 위에서, 회사 전체가 서로 섞이지 않게 하는 문제를 다뤄요.

## 격리 모델 — 테이블 공유 · 스키마 · DB 비교

| 모델                         | 구조                                                    | 격리 강도               | 비용과 운영                                               |
| ---------------------------- | ------------------------------------------------------- | ----------------------- | --------------------------------------------------------- |
| 테이블 공유 · `tenant_id` 열 | 한 테이블에 모든 회사 행을 두고 `tenant_id` 열로 나눠요 | 쿼리 조건 하나에 기대요 | 마이그레이션이 한 번이에요. 회사가 늘어도 DB는 그대로예요 |
| 회사별 스키마                | DB 하나에 회사마다 스키마를 만들어요                    | 스키마 권한에 기대요    | 스키마 수만큼 마이그레이션을 돌려야 해요                  |
| 회사별 DB                    | 회사마다 DB를 따로 둬요                                 | 연결과 권한이 나뉘어요  | 연결과 운영 비용이 가장 많이 늘어요                       |

Azure 테넌시 모델 문서는 격리를 켜고 끄는 값이 아니라 공유와 격리 사이의 스펙트럼으로 봐요. 공유 인프라는 비용이 낮아요. 대신 한 구성 요소의 문제가 모든 테넌트의 장애로 번질 수 있다고 설명해요.

계층마다 격리 수준을 다르게 둘 수도 있어요. 같은 문서는 화면 계층은 공유하고, 데이터 계층만 DB나 테이블로 나누는 구성을 예로 들어요.

스키마를 나눴다고 격리가 자동으로 되지는 않아요. AWS 데이터 분할 문서는 데이터를 나누는 일과 격리하는 일이 같지 않다고 설명해요. 격리는 따로 적용해야 한다고 해요. PostgreSQL 문서도 스키마가 엄격히 나뉘지 않는다고 설명해요. 권한이 있으면 같은 DB 안의 다른 스키마 객체에도 접근할 수 있어요.

테이블 공유 모델은 `tenant_id` 열 하나가 경계의 전부예요. 그래서 쿼리 한 곳에서 조건이 빠지면 바로 섞여요.

회사 수가 많으면 테이블 공유로 시작하고, 방어 장치를 두껍게 두는 편이 좋아요. 규제 요구가 강한 회사가 있으면 그 회사만 DB를 따로 두는 편이 좋아요. 이 판단은 설계 판단이에요.

## 테넌트 식별 — 서브도메인 · 경로 · 토큰 클레임

회사를 정하는 값은 크게 세 곳에 있어요.

| 방식        | 예시                      | 서버가 확인할 것                                 |
| ----------- | ------------------------- | ------------------------------------------------ |
| 서브도메인  | `acme.example.com`        | 호스트가 등록된 테넌트와 맞는지                  |
| 경로        | `/companies/acme/orders`  | 경로의 회사가 로그인한 사용자의 소속인지         |
| 토큰 클레임 | 서명된 토큰의 `tenant` 값 | 서명이 맞고, 만료되지 않았고, 값이 허용 형식인지 |

어느 방식을 골라도 OWASP는 같은 원칙을 말해요. 보호된 테넌트 자원을 요청할 때마다 인증된 주체가 선택된 테넌트에서 행동할 권한이 있는지 확인해요. 테넌트 식별자는 허용 목록에 있는 정규 형식으로 검사해요.

## 클라이언트가 보낸 tenant id — 그대로 믿지 않는 이유

OWASP는 요청, 토큰, 헤더에 든 테넌트 식별자를 바꾸는 공격을 Tenant Context Injection이라고 설명해요. 주소창의 회사 id를 바꾸는 증상이 바로 이 공격이에요.

FE가 보내는 회사 id는 화면이 어느 회사를 보고 있는지 알려 주는 힌트로만 써요. 서버는 이 값을 조건에 그대로 넣지 않아요.

서버는 로그인 토큰에서 검증된 테넌트를 꺼내고, 요청 값과 맞는지 비교하거나 요청 값을 무시해요. 두 방법 중 무엇을 쓸지는 설계 판단이에요.

## 조건 누락 막기 — 조회 계층 강제와 RLS

모든 쿼리에 `tenant_id` 조건을 손으로 넣으면 한 곳에서 빠져요. 그래서 두 층으로 막아요. 하나는 조회 계층이 조건을 강제하는 방법이고, 다른 하나는 DB가 행을 직접 거르는 RLS예요.

### 조회 계층 강제 — 데이터 접근 함수가 조건을 붙이기

조회 계층은 쿼리를 만드는 함수가 검증된 테넌트 조건을 모든 쿼리에 붙이는 방식이에요. 호출하는 쪽은 조건을 생각하지 않아요.

OWASP는 ORM 수준 필터를 심층 방어로 보고, 완전한 격리 경계로 보지 않아요. ORM 필터가 원시 SQL이나 Core 문장에는 걸리지 않는다고 예를 들어요. 그래서 원시 SQL과 대량 작업에는 테넌트 조건을 명시적으로 넣으라고 설명해요. 가능하면 마지막 경계는 DB 정책과 제한된 역할에 두라고 해요.

### RLS — DB가 행을 거르는 정책

PostgreSQL 문서는 행 보안 정책으로 사용자별로 어떤 행을 조회하고 수정할지 제한할 수 있다고 설명해요. 테이블에 RLS를 켜고 정책이 없으면 기본 거부예요. 어떤 행도 보이지 않는다고 설명해요.

`USING` 식은 기존 행을 볼 수 있는지 확인해요. `WITH CHECK` 식은 새로 넣거나 고친 행을 허용하는지 확인해요. 정책은 아래처럼 쓸 수 있어요. 예시 정책이에요.

```sql
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON orders
  USING (tenant_id = current_setting('app.current_tenant')::uuid)
  WITH CHECK (tenant_id = current_setting('app.current_tenant')::uuid);
```

이 방식에는 함정이 두 가지 있어요.

- 정책이 읽는 세션 값은 연결 풀이 연결을 재사용할 때 다음 요청에 남을 수 있어요. OWASP는 일반 `SET`은 트랜잭션이 끝나도 세션이 끝날 때까지 남고, `SET LOCAL`은 현재 트랜잭션에만 남는다고 설명해요. 그래서 `SET LOCAL`로 같은 트랜잭션 안에서만 값을 두라고 해요.
- 테이블 소유자와 슈퍼유저, `BYPASSRLS` 속성의 역할은 정책을 건너뛰어요. PostgreSQL 문서는 슈퍼유저와 `BYPASSRLS` 역할이 항상 우회한다고 설명해요. 테이블 소유자도 기본으로 우회하는데, `FORCE ROW LEVEL SECURITY`를 쓰면 소유자도 정책을 따르게 할 수 있어요. OWASP는 요청 경로를 슈퍼유저도 `BYPASSRLS`도 아닌 최소 권한 역할로 연결하라고 설명해요.

조회 계층과 RLS는 함께 쓸 수 있어요. 조회 계층은 코드 안에서 조건을 강제하고, RLS는 빠진 조건이 있어도 DB가 막아요.

## 유일 제약 · 인덱스 — tenant_id를 포함하는 기준

PostgreSQL 문서는 유일 제약을 여러 열에 걸면 그 열들의 값 조합이 전체 행에서 겹칠 수 없다고 설명해요. 유일 제약을 걸면 그 열 묶음에 유일 B-tree 인덱스도 자동으로 만들어져요.

회사마다 주문 번호를 1번부터 매긴다고 해 봐요. 예시예요. 이때 `order_no` 하나에만 유일 제약을 걸면 회사 B의 1번 주문이 회사 A의 1번 주문과 부딪혀요. 그래서 테넌트 열을 같이 묶어요.

```sql
-- 예시: 회사마다 주문 번호가 1번부터 시작해요
ALTER TABLE orders ADD CONSTRAINT orders_tenant_order_no_key UNIQUE (tenant_id, order_no);
```

PostgreSQL 문서는 유일 제약에 `NULL`이 들어간 열이 있으면 중복 행을 저장할 수 있다고 설명해요. 그래서 `tenant_id`는 `NOT NULL`로 두는 편이 좋아요.

목록 조회는 보통 `tenant_id`로 먼저 좁혀요. PostgreSQL 문서는 복합 인덱스에서 앞쪽 열의 등호 조건이 스캔 범위를 제한한다고 설명해요. 그래서 `tenant_id`를 복합 인덱스의 맨 앞에 두는 편이 좋아요.

정렬이나 범위 조건이 같이 붙으면 쿼리 패턴을 보고 열 순서를 정해요. 이 판단은 설계 판단이에요. 목록 조건의 비용은 [목록 필터와 정렬 — 조합마다 달라지는 조회 비용](/m/list-filtering) 글에서 다뤄요.

## 시끄러운 이웃 — 테넌트별 한도

Azure 안티패턴 문서는 시끄러운 이웃 문제를 한 테넌트의 활동 때문에 다른 테넌트의 성능이 떨어지는 현상으로 설명해요. 각 테넌트가 전체 용량의 작은 부분만 써도 생길 수 있어요.

이 문서는 이를 자원 거버넌스 문제로 보라고 설명해요. 사용량 할당량과 스로틀링을 적용하라고 해요. 예를 들어 무거운 DB 쿼리를 막기 위해 한 번에 돌려줄 최대 행 수나 쿼리 시간 제한을 둘 수 있다고 설명해요.

OWASP는 공유 자원에 할당량이 있으면 테넌트 식별자를 요청 제한의 한 차원으로 넣으라고 설명해요. HTTP 경계의 요청 제한만으로는 모든 공유 자원을 제한하지 못한다고 설명해요.

한도 값은 용량, 악용 위험, 계약 조건, 요금제를 보고 정하라고 해요. 모든 회사에 같은 숫자 하나를 박아 두지 않는 편이 좋아요.

한도의 알고리즘은 [레이트 리밋 알고리즘 — 고정 창 · 슬라이딩 · 토큰 버킷 · 누수 버킷](/m/rate-limiting) 글에서 다뤄요.

## 캐시 키 — 테넌트 식별자를 넣는 기준

OWASP는 값이나 권한이 테넌트마다 다른 캐시 항목에는 캐시 키에 테넌트 식별자를 넣으라고 설명해요. 캐시 항목을 전역, 테넌트별, 사용자별로 나눠 분류하라고 해요.

MDN은 `Vary` 헤더로 지정한 요청 헤더 값마다 응답을 따로 캐시한다고 설명해요. 테넌트마다 응답이 달라진다면 그 구분이 캐시 키에 들어가야 해요.

캐시 키를 나누는 것은 권한 검사를 대신하지 않아요. OWASP는 보호된 캐시 값을 읽기 전에 요청을 먼저 인가해야 한다고 설명해요. 저장 범위는 [API 응답 HTTP 캐시 — 개인 캐시와 공유 캐시의 저장 범위](/m/http-caching) 글에서 다뤄요.

## 시뮬레이터 안내 — 모델 · 방어 · 사고 조합

시뮬레이터는 격리 모델, 쿼리에 회사 조건을 넣는 방법, 사고 시나리오를 고르게 해요. 테넌트별 한도와 캐시 키 설정도 바꿀 수 있어요. 결과는 다른 회사 데이터가 보이는지와 영향 범위(모든 회사, 한 회사, 영향 없음)로 보여 줘요.

이렇게 바꿔 보세요.

- 테이블 공유, 조건을 직접 쓰기로 두고 "조건 빠진 쿼리"를 고르세요. 같은 사고를 "조회 계층이 강제"나 "DB 행 보안"으로 바꾸면 막혀요.
- "위조된 tenant id"는 조건을 직접 쓸 때만 새요. 검증된 값에서 테넌트를 가져오면 모델과 상관없이 막혀요.
- "캐시 응답 재사용"에서 캐시 키 체크박스를 끄세요. 격리 모델을 바꿔도 다른 회사 응답이 나와요.
- "큰 회사에 요청 몰림"을 고르세요. 테이블 공유와 스키마는 모든 회사가 느려지고, 회사별 DB는 그 회사 하나에 머물러요. 테넌트별 한도를 켜면 영향이 제한에 걸린 회사 하나로 줄어요.

시뮬레이터는 판단 규칙을 보여 주는 순수 모델이에요. 실제 DB 동작을 흉내 낸 것은 아니에요.

## FE 체크 포인트 — 회사 전환 · 응답 · 캐시 키

회사를 바꾸는 화면에서는 이전 회사의 데이터가 잠깐이라도 보이지 않게 해요. 클라이언트 캐시의 키에 회사 id를 넣거나, 전환할 때 캐시를 비우는 방법을 써요. 이 선택은 설계 판단이에요.

URL의 회사 id와 응답에 담긴 회사가 다르면 데이터를 그리지 않고 오류 화면을 보여 줘요. 다른 회사의 객체를 요청하면 서버가 403이나 404로 답할 수 있어요. 존재를 숨길지는 서버가 정해요. 응답 코드 기준은 [인가 · 객체 수준 권한](/m/authorization) 글에서 다뤘어요.

로그인 토큰이 바뀌면 이전 토큰으로 받은 캐시를 버리는 편이 좋아요. 토큰의 회사와 화면의 회사가 어긋나는 순간이 가장 위험해요.

## 정리 — 격리 모델 · 식별 위치 · 강제 계층 · 한도와 캐시 기준

회사는 검증된 값에서 정해요. 격리 모델은 회사 수와 규제 요구로 고르고, 빠진 조건은 조회 계층과 RLS로 막아요.

유일 제약과 인덱스에는 `tenant_id`를 넣고, 큰 회사는 테넌트별 한도로 나눠요. 캐시 키에는 테넌트 식별자를 넣어요.

권한 검사는 [인가 · 객체 수준 권한](/m/authorization)에서, 한도의 알고리즘은 [레이트 리밋](/m/rate-limiting)에서, 캐시 저장 범위는 [HTTP 캐시](/m/http-caching)에서, 목록 조건의 비용은 [목록 필터와 정렬](/m/list-filtering)에서 이어서 읽어 보세요.
