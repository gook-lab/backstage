카드 결제가 실패했는데 사용자가 프리미엄 기능을 계속 써요. 플랜을 중간에 올렸더니 청구 금액이 차액과 다르게 나와요. 두 현상은 같은 곳에서 나와요. 구독을 "결제 한 번"으로 보고, 기간이 이어지는 "상태"로 보지 않아서예요.

이 글은 구독을 상태 머신으로 보고, 갱신 실패 뒤의 재시도와 유예, 중간 플랜 변경의 일할 계산, 해지 방식, 권한을 서버가 판단하는 방법을 다뤄요. 웹훅 순서와 기간 경계 시각도 함께 봐요. 아래 시뮬레이터에서 플랜 변경 금액과 결제 실패 뒤의 접근 기간을 직접 바꿔 볼 수 있어요.

결제 한 번의 멱등성, 웹훅 서명 검증, 금액을 정수로 다루는 법은 각각 [결제 — 이중 결제 막기](/m/payment-idempotency), [웹훅 수신 — 결제 완료는 누가 알려 주나요](/m/webhook-receiving), [금액 계산과 표현 — 소수점 · 반올림 · 통화 단위](/m/money-amounts) 글에서 다뤄요. 이 글은 그 위에 얹히는 구독 기간과 상태만 다뤄요.

## 구독 상태 — 여덟 가지 상태와 권한 기준

FE가 보는 상태 값은 Stripe 구독 객체의 `status`예요. Stripe 문서는 일부 상태에서 권한을 어떻게 다룰지도 함께 설명해요.

| 상태                 | Stripe 문서의 뜻                                                                                | FE가 보는 것              |
| -------------------- | ----------------------------------------------------------------------------------------------- | ------------------------- |
| `incomplete`         | 최초 결제를 23시간 안에 끝내야 활성화돼요                                                       | 결제 완료 전 대기 화면    |
| `incomplete_expired` | 23시간 안에 결제하지 않아 만료됐어요. 과금하지 않아요                                           | 새 구독을 만들도록 안내   |
| `trialing`           | 체험 기간이에요. 첫 결제가 성공하면 `active`로 바뀌어요                                         | 체험 남은 기간 표시       |
| `active`             | 정상 상태예요. 어떤 인보이스가 정산돼야 하는지는 구독 설정이 정해요                             | 기능 열림                 |
| `past_due`           | 최신 확정 인보이스의 결제가 실패했거나 아직 시도하지 않았어요. 재시도 중에도 이 상태가 유지돼요 | 결제 수단 변경 안내       |
| `unpaid`             | 대시보드 설정이 그렇게 정했을 때만 바뀌어요. 재시도를 멈추고 청구서만 계속 만들어요             | 기능 차단                 |
| `canceled`           | 해지된 상태예요. 이 상태는 다시 바꿀 수 없어요                                                  | 기능 차단, 새 구독 만들기 |
| `paused`             | 체험이 끝났는데 결제 수단이 없고, 설정이 `pause` 일 때 생겨요. 청구서를 만들지 않아요           | 결제 수단을 붙이면 재개   |

Stripe 문서는 `unpaid`로 바뀐 구독의 권한을 회수하라고 설명해요. 재시도는 `past_due` 동안 이미 했기 때문이에요. 이 판단을 FE 화면 조건문으로 흩으면 안 돼요. 상태 값을 서버가 권한 값으로 바꿔 내려 주는 편이 나아요.

## 갱신 실패 뒤의 흐름 — 재시도 간격과 기능 차단 시점

FE가 보는 증상은 "카드가 실패했는데 프리미엄이 그대로 열려 있어요"예요. 결제 실패 자체는 서버에서 바로 기능을 끊는다는 뜻이 아니에요. 어떤 시점에 끊을지는 서비스 정책이에요.

갱신 결제가 실패하면 Stripe는 구독을 `past_due`로 바꾸고 재시도를 이어가요. Smart Retries는 AI로 재시도 시점을 고르고, 신규 계정은 기본으로 2주 안에 최대 8회 재시도하도록 설정돼 있다고 설명해요. 직접 정하는 커스텀 규칙은 최대 3회이고, 이전 시도로부터 며칠 뒤에 다시 시도할지를 적어요. 마지막 재시도가 끝나면 설정에 따라 `canceled`, `unpaid`, `past_due` 중 하나로 가요.

FE가 확인할 신호는 `invoice.payment_failed` 웹훅의 `attempt_count`와 인보이스의 `next_payment_attempt`예요. 다음 시도 날짜를 보여 주면 사용자가 카드를 바꿀 시간을 알 수 있어요.

### 기능 차단 시점 — 실패 즉시, 유예 뒤, 최종 결과 뒤

| 차단 시점          | 장점                                    | 주의                                           |
| ------------------ | --------------------------------------- | ---------------------------------------------- |
| 실패 즉시 차단     | 미납 기간에 기능을 열지 않아요          | 일시적인 카드 한도 초과에도 바로 이탈이 생겨요 |
| 유예 기간 뒤 차단  | 사용자가 결제 수단을 바꿀 시간이 있어요 | 유예 동안은 대가 없이 기능을 쓰게 돼요         |
| 최종 결과까지 유지 | 재시도가 모두 끝날 때까지 기다려요      | 재시도 기간이 길면 미납 상태가 오래 이어져요   |

예를 들어 유예를 3일, 7일, 14일처럼 두고 실패 뒤 며칠째부터 막을지 고를 수 있어요. 이 숫자는 예시예요. 값은 손실 허용액과 이탈 비용을 같이 보고 정해요.

Stripe의 `past_due`는 "재시도 중"이라는 뜻이지 "권한이 있다"는 뜻이 아니에요. 그래서 유예가 끝난 `past_due` 구독은 우리 서버가 기능을 막아요. 이 정책은 서버 한 곳에 두고, 화면은 그 결과만 받아요.

## 플랜 중간 변경 — 일할 계산과 청구 시점

FE가 보는 증상은 "올렸더니 차액이 아니라 다른 금액이 나와요"예요. 일할 계산(proration)은 이번 주기의 미사용분을 크레딧으로 빼고, 새 플랜의 남은 기간을 차감으로 더해요. Stripe 문서의 예는 월 10 USD 플랜을 주기 중간에 20 USD 플랜으로 올리면, 미사용분 -5 USD와 남은 기간 +10 USD가 더해져 +5 USD를 청구한다고 설명해요.

청구 시점은 세 가지 방식으로 나뉘어요.

| 방식 (`proration_behavior`) | 변경 순간 청구                          | 다음 청구서                        | 주의                                                                 |
| --------------------------- | --------------------------------------- | ---------------------------------- | -------------------------------------------------------------------- |
| `create_prorations` (기본)  | 문서상 즉시 청구되는 조건이 따로 있어요 | 일할 항목이 다음 청구서에 들어가요 | 음수 차액은 자동으로 환불되지 않아요                                 |
| `always_invoice`            | 차액을 바로 청구해요                    | 새 플랜 정가                       | 변경 직후 결제가 실패하는 경우를 처리해야 해요                       |
| `none`                      | 청구하지 않아요                         | 새 플랜 정가                       | 주기 중 올린 차액을 받지 않아요. 그래서 금액 정책을 따로 정해야 해요 |

Stripe 문서는 미결제 인보이스가 있는 구독을 바꾸면 아직 내지 않은 기간까지 크레딧으로 계산될 수 있다고 설명해요. 그럴 때는 `proration_behavior`를 `none`으로 두거나, 변경 시점에 `billing_cycle_anchor`를 `now`로 설정해 새 주기를 여는 방법을 안내해요.

변경 금액은 누르기 전에 보여 주는 편이 좋아요. Stripe 문서에는 변경을 적용하지 않고 인보이스 미리보기를 받는 방법이 있어요. 화면 계산식을 따로 만들면 서버 금액과 어긋날 수 있어요.

### 금액 계산 기준 — 일 단위와 반올림

이 글의 모델은 30일 주기를 하루 단위로 계산하고, 원 단위로 반올림해요. 이 모델 기준이에요. Stripe는 기본적으로 초 단위로 일할 계산해요. 금액 계산은 서버가 한 곳에서 맡고, 반올림 규칙도 서버 규칙에 맞춰요.

## 해지 — 즉시 해지와 기간 끝 해지

FE가 보는 질문은 "해지를 누르면 언제부터 기능이 막히나요?"예요.

| 방식                                  | 끝나는 시점                    | 되돌리기                                        | 주의                                                                   |
| ------------------------------------- | ------------------------------ | ----------------------------------------------- | ---------------------------------------------------------------------- |
| 즉시 해지                             | 요청한 순간                    | 해지된 구독은 다시 시작할 수 없어요             | 새 구독을 만들어야 해요. 일할 환불은 요청 옵션으로 따로 정해요         |
| 기간 끝 해지 (`cancel_at_period_end`) | 이미 결제한 기간이 끝나는 시점 | 기간이 끝나기 전까지 `false`로 되돌릴 수 있어요 | 이미 낸 기간의 권한은 유지돼요. 해지 예약 상태를 화면에 보여 줘야 해요 |

Stripe 문서는 기간 끝 해지가 이미 결제한 기간을 끝까지 쓰게 한다고 설명해요. 해지 요청 때 `customer.subscription.updated`가 오고, 실제로 끝나면 `customer.subscription.deleted`가 와요. 즉시 해지하면 열린 인보이스의 자동 청구도 멈춰요.

### 해지 예약 표시 — 상태와 기간 끝 시각의 조합

기간 끝 해지 중에도 구독 상태는 아직 `active` 일 수 있어요. 화면은 상태만 보면 "해지 예약"을 놓쳐요. 그래서 `cancel_at_period_end`와 현재 기간 끝 시각을 함께 보여 주는 편이 좋아요.

## 권한 판단 — 웹훅 상태를 서버 DB에 저장한 값

결제 성공 화면은 권한의 근거가 아니에요. 결제 창에서 돌아온 클라이언트는 결제가 끝났다고 말할 뿐이고, 그 말을 서버가 확인하지 않아요. 웹훅이 늦거나 빠지면 화면과 실제 결제가 어긋나요.

Stripe 문서는 `invoice.paid`를 받은 뒤 구독을 다시 조회해 `status`가 `active` 인지 확인하고, 그다음에 접근 기간을 늘리라고 설명해요. 상태 판단 기준에 따라서는 인보이스 결제가 곧 `active`를 뜻하지 않아요.

| 권한 판단 근거              | 문제                                               | 판단                             |
| --------------------------- | -------------------------------------------------- | -------------------------------- |
| 클라이언트의 결제 성공 화면 | 웹훅이 빠져도 화면이 바뀌고, 위조할 수 있어요      | 권한 근거로 쓰지 않아요          |
| 매 요청마다 Stripe API 조회 | 요청마다 외부 호출이 생기고 지연과 한도가 따라와요 | 자주 쓰는 경로에는 맞지 않아요   |
| 웹훅 상태를 서버 DB에 저장  | 웹훅이 늦으면 잠시 옛 값이 남아요                  | 권한의 원천으로 두는 편이 좋아요 |

서버 DB에 저장하면 기능 요청마다 DB의 상태와 기간 끝 시각만 봐요. 웹훅은 서명을 검증한 뒤에만 처리해요. Stripe 문서는 웹훅 서명을 확인하지 않으면 위조 이벤트로 계정 접근을 열 수 있다고 설명해요.

## 웹훅 순서와 중복 — 이벤트 ID 기록과 최신 상태 조회

FE 관점의 증상은 "결제는 됐는데 화면이 한 번 구독 전으로 돌아갔다가 돌아와요"예요. 서버에서는 `invoice.paid`가 `customer.subscription.updated`보다 먼저 오거나, 같은 이벤트가 두 번 올 수 있어요.

Stripe 문서는 이벤트 전달 순서를 보장하지 않는다고 설명해요. `created`는 초 단위라서 같은 값이 여러 번 나올 수 있어요. 그래서 `created`로 순서를 판단하지 말고, 이벤트 ID를 기록해 중복을 걸러내라고 권해요. 빠진 객체는 API로 다시 조회하면 돼요.

| 방식                                      | 결과                                               | 주의                                                                                                                          |
| ----------------------------------------- | -------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| 이벤트 값을 그대로 DB에 덮어쓰기          | 늦게 온 옛 이벤트가 최신 상태를 덮어써요           | 순서가 바뀌면 옛 값이 남아요                                                                                                  |
| 이벤트 ID 기록 후 구독을 다시 조회해 저장 | 중복은 한 번만 처리하고, 저장값은 최신 상태가 돼요 | API 호출이 한 번 늘어요                                                                                                       |
| 상태 전이 규칙으로 거르기                 | 허용되지 않은 전이는 버리고 2xx로 응답해요         | 규칙을 유지해야 해요. 자세한 방식은 [주문 상태 전이 — 취소와 출고가 겹칠 때 서버가 정하는 순서](/m/order-state) 글에서 다뤄요 |

권한 판단에서는 두 번째 방식을 기본으로 두는 편이 안전해요. 이벤트 ID 기록은 중복을 막고, 구독 조회는 순서가 바뀌어도 최신 상태를 주기 때문이에요.

## 기간 경계 시각 — UTC 저장과 화면 변환 분리

"이번 달 말까지"나 "다음 결제일"은 시간대에 따라 하루가 달라 보여요. 결제일이 31일인 구독은 30일까지만 있는 달에 어떻게 할지 정해야 해요. 이 모델은 주기를 30일로 단순화해 이 문제를 피했어요.

이 글의 기준은 하나예요. 기간 시작과 끝은 UTC 시각으로 저장하고 비교해요. 화면에서만 사용자 시간대로 바꿔 보여 줘요. 사용량을 어느 달에 넣을지는 [사용량 과금 — 집계 지연과 한도 판단](/m/usage-metering) 글에서, 시간대 표시는 [날짜 · 시간대 · 다국어](/m/time-and-locale) 글에서 다뤄요.

## FE 체크 포인트

- `past_due` 면 기능을 바로 막지 말고, 결제 수단을 바꾸도록 배너를 보여 줘요. 막는 시점은 서버 응답을 따라요.
- 권한은 서버가 내려 준 값으로만 열어요. 결제 성공 화면을 보고 클라이언트 상태를 바꾸지 않아요.
- 플랜 변경 버튼을 누르기 전에 금액 미리보기를 받아요. 화면에서 차액을 직접 계산하지 않아요.
- 기간 끝 해지 중이면 "다음 갱신 때 해지돼요"와 해지 날짜를 같이 보여 줘요.
- 금액은 정수 원으로 받아 표시만 해요. 소수점 계산을 화면에서 하지 않아요.

## 시뮬레이터 안내

시뮬레이터는 두 부분이에요. 첫째는 플랜 변경이에요. 현재 플랜과 바꿀 플랜, 변경일(1~30일), 일할 계산 방식을 고르면 이번 청구, 남은 크레딧, 다음 청구서를 보여 줘요. 둘째는 결제 실패예요. 재시도 일정, 재시도 결과, 최종 결과, 유예 기간을 고르면 청구 시도 날짜와 기능이 막히는 날을 보여 줘요. 아래 띠에서 날짜별 상태를 한눈에 볼 수 있어요.

모델은 30일 주기와 하루 단위예요. 수치는 예시예요. 실제 Stripe 계산은 초 단위라서 금액이 조금 다를 수 있어요.

## 정리 — 상태 머신 · 유예 정책 · 일할 방식 · 해지 방식 · 서버 권한

- 구독 상태는 권한을 나누는 기준으로 보고, 화면 조건문에 흩지 않아요.
- 결제 실패의 기능 차단 시점은 재시도 결과와 별개로 정책으로 정해요.
- 플랜 변경은 일할 계산 방식을 정하고, 금액 미리보기를 서버에서 받아요.
- 해지는 즉시와 기간 끝 중 하나를 고르고, 해지 예약 상태를 화면에 드러내요.
- 권한은 웹훅으로 받은 최신 상태를 서버 DB에 저장해 판단하고, 클라이언트 성공 화면은 근거로 쓰지 않아요.
