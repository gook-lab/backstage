취소 버튼을 "배송 준비 중"까지만 보여 주라는 요구를 받으면, 화면에서 버튼을 숨기면 끝났다고 생각하기 쉬워요. 그런데 손님이 이미 열어 둔 화면에서 버튼을 누르거나, 같은 순간에 창고가 출고 버튼을 누르면 어떻게 될까요. 이 글은 주문 상태가 정해진 순서로만 바뀌도록 서버가 판정하는 방법을 정리해요. 취소와 출고가 겹칠 때 누가 이기는지, 늦게 온 결제 통지가 상태를 되돌리지 않게 하는 방법까지 다뤄요.

아래 시뮬레이터에서 같은 요청을 세 가지 판정 방식으로 돌려 볼 수 있어요. 글의 예시는 모두 이 시뮬레이터의 상태표를 따라요.

## 상태와 허용 전이 — 여덟 상태와 여섯 동작

주문은 아래 표에 있는 조합으로만 바뀌어요. 표에 없는 조합은 서버가 거부해야 해요.

| 현재 상태 | 동작           | 다음 상태 | 누가 요청하나 |
| --------- | -------------- | --------- | ------------- |
| 결제 대기 | 결제 완료 통지 | 결제 완료 | 결제사 웹훅   |
| 결제 대기 | 취소 요청      | 취소      | 손님          |
| 결제 완료 | 출고 준비      | 배송 준비 | 창고          |
| 결제 완료 | 취소 요청      | 환불 대기 | 손님          |
| 배송 준비 | 출고 처리      | 배송 중   | 창고          |
| 배송 준비 | 취소 요청      | 환불 대기 | 손님          |
| 배송 중   | 배송 완료 통지 | 배송 완료 | 택배사 웹훅   |
| 환불 대기 | 환불 완료 통지 | 환불 완료 | 결제사 웹훅   |

"배송 준비까지만 취소할 수 있다"는 규칙은 기술 규칙이 아니라 사업 정책이에요. 어디까지 취소를 허용할지는 서비스가 정하고, 서버는 그 표를 그대로 지켜요. Stripe 문서도 PaymentIntent를 processing이나 succeeded 상태에 이르기 전에만 취소할 수 있다고 설명해요. 취소가 가능한 마지막 지점을 상태표에 적어 두는 방식이 같아요.

## 상태 값 제한 — enum과 CHECK 제약

상태 값은 DB에서도 제한해요. PostgreSQL 문서는 열거형 (enum) 타입을 정해진 순서가 있는 값의 집합이라고 설명해요. 오타가 난 상태 값이 테이블에 들어가지 않게 막아요.

```sql
CREATE TYPE order_status AS ENUM (
  'pending_payment', 'paid', 'preparing', 'shipping',
  'delivered', 'canceled', 'refund_pending', 'refunded'
);
```

enum 대신 문자열 열에 CHECK 제약을 둘 수도 있어요. PostgreSQL 문서는 CHECK 뒤 괄호 안의 식이 제약이 된다고 설명해요. 다만 제약은 "이 값이 목록에 있는가"만 막아요. "배송 중에서 취소로 가는가"는 DB 제약으로 표현하기 어려워요. 그 판정은 서버 코드와 조건부 UPDATE가 맡아요.

## 버튼 노출 — 서버가 내려 주는 가능한 동작

FE가 주문 상태 문자열을 보고 버튼을 결정하면, 규칙이 두 군데에 생겨요. 서버 표가 바뀌면 화면 규칙을 같이 고쳐야 해요. 서버가 "지금 가능한 동작" 목록을 함께 내려 주면 FE는 그 목록에 있는 버튼만 그리면 돼요.

예시 응답은 이래요.

```json
{
  "id": "ord_1042",
  "status": "preparing",
  "allowed_actions": ["cancel"]
}
```

예시에서 같은 주문이 배송 중이 되면 `allowed_actions`는 빈 목록이 돼요. 화면에 취소 버튼이 사라지는 이유가 서버 응답에 있어요.

## 판정 위치 — 화면 숨김과 서버 확인을 나누기

버튼을 숨기는 것은 UX예요. 규칙을 막는 것은 서버 판정이에요. 세 가지 방식을 비교하면 차이가 보여요.

| 방식              | 손님이 겪는 것     | 뚫리는 곳                                    |
| ----------------- | ------------------ | -------------------------------------------- |
| 화면에서만 막기   | 버튼이 안 보여요   | API를 직접 호출하면 통과해요                 |
| 서버 확인 후 쓰기 | 거부 응답을 받아요 | 확인과 쓰기 사이에 끼어든 요청을 보지 못해요 |
| 조건부 UPDATE     | 거부 응답을 받아요 | 조건 검사와 쓰기가 한 문장이라 틈이 없어요   |

화면에서만 막은 서버는 요청이 오면 상태 규칙을 보지 않고 값을 써요. 배송 중인 주문이라도 취소 요청이 오면 `canceled`로 바꿔 버려요. 그래서 판정은 서버에서 해요. 화면 숨김은 그 위에 얹는 편의예요.

## 동시 전이 경쟁 — 조건부 UPDATE로 한쪽만 통과시키기

배송 준비 주문에 창고의 출고 처리와 손님의 취소가 같은 순간에 도착했다고 해요. 서버 확인 후 쓰기 방식에서는 두 요청이 모두 "배송 준비"를 읽고 통과해요. 출고가 먼저 쓰고 취소가 나중에 쓰면, 배송 중인 주문이 환불 대기로 기록돼요. 표에 없는 `배송 중 → 환불 대기` 전이가 생겨요.

조건을 쓰기 문장에 넣으면 이 틈이 사라져요.

```sql
UPDATE orders
SET status = 'shipping'
WHERE id = $1 AND status = 'preparing'
RETURNING id, status;
```

PostgreSQL 문서는 UPDATE가 실제로 갱신한 행 수를 돌려준다고 설명해요. RETURNING은 실제로 갱신된 행을 기준으로 값을 돌려준다고 해요. 이 쿼리의 갱신 행 수가 0이면 조건에 맞는 행이 없었다는 뜻이에요. 출고가 먼저 커밋되면 취소 쪽의 `WHERE status = 'preparing'`은 0 행이 돼요.

PostgreSQL 기본 격리 수준인 READ COMMITTED에서는, 먼저 쓴 트랜잭션이 끝날 때까지 기다린 뒤 WHERE 조건을 갱신된 행에 다시 맞춰 봐요. 두 번째 요청이 옛 상태를 근거로 통과하는 일이 없어요.

취소 쪽도 같은 방식으로 써요.

```sql
UPDATE orders
SET status = 'refund_pending'
WHERE id = $1 AND status IN ('paid', 'preparing')
RETURNING id, status;
```

0 행이 돌아오면 서버는 같은 주문을 다시 읽어 현재 상태를 응답 본문에 담아요. 응답을 만들 때 상태를 다시 읽는 과정은 이 글의 설계 판단이에요. 조건부 UPDATE 자체는 0 행이라는 사실만 알려 줘요.

### 대안 — 행 잠금과 버전 열

확인과 쓰기를 한 트랜잭션에서 여러 문장으로 나눠야 한다면 `SELECT ... FOR UPDATE`를 쓸 수 있어요. PostgreSQL 문서는 이 행을 UPDATE 하려는 다른 트랜잭션이 현재 트랜잭션이 끝날 때까지 막힌다고 설명해요. 자세한 락 동작은 [트랜잭션 · 락 · 데드락](/m/transactions) 글에서 다뤄요.

버전 열을 두는 방법도 있어요. `WHERE id = $1 AND version = $2`로 손님이 본 버전을 함께 보내면 같은 효과를 내요. 조건부 요청 헤더(`If-Match`)와 맞물리는 방식은 [동시 편집 · 낙관적 동시성 제어](/m/concurrent-edits) 글에서 다뤄요. RFC 9110은 `If-Match` 조건이 거짓이면 412 (Precondition Failed)를 줄 수 있다고 설명해요.

## 거부 응답 — 409와 현재 상태를 담은 문제 본문

RFC 9110은 409 (Conflict)를 대상 리소스의 현재 상태와 요청이 충돌할 때 쓴다고 설명해요. 사용자가 상황을 알고 다시 보낼 수 있을 때 쓰라고 해요. 충돌의 출처를 알아볼 정보를 응답에 담으라고 권하는 조항도 있어요.

응답 본문은 RFC 9457 (Problem Details) 형식을 쓰면 편해요. 이 문서는 `application/problem+json` 미디어 타입과, 명세에 없는 필드를 확장 멤버로 더할 수 있다는 점을 설명해요.

예시 응답은 이래요.

```json
{
  "type": "https://api.example.com/problems/invalid-transition",
  "title": "현재 상태에서는 취소할 수 없어요",
  "status": 409,
  "detail": "배송 중인 주문은 취소 요청을 받을 수 없어요.",
  "current_status": "shipping",
  "requested_action": "cancel"
}
```

`current_status`가 있어야 화면이 "이미 출고됐어요"라고 바꿔 보여 줄 수 있어요. 409 숫자만 받으면 이유를 짐작해야 해요.

## 전이 이력 — 상태 변경과 같은 트랜잭션에 기록하기

상태가 어떻게 바뀌었는지도 남겨야 나중에 "왜 취소가 환불로 갔는지"를 설명할 수 있어요. 예시 이력 테이블은 이래요.

| 열                          | 뜻                            |
| --------------------------- | ----------------------------- |
| `order_id`                  | 주문 번호                     |
| `from_status` · `to_status` | 바뀌기 전 상태와 바뀐 뒤 상태 |
| `actor` · `request_id`      | 누가 어떤 요청으로 바꿨는지   |
| `created_at`                | 바뀐 시각                     |

이력 한 줄은 상태를 바꾼 UPDATE와 같은 트랜잭션에서 쓰는 편이 좋아요. 둘 중 하나만 남으면 이력과 현재 상태가 어긋나요. 조건부 UPDATE가 0 행이면 이력도 쓰지 않아요. 이력 설계 자체는 [변경 이력과 감사 로그](/m/audit-history) 글에서 다뤄요.

## 늦은 외부 이벤트 — 순서 대신 전이 규칙으로 거르기

결제 완료 통지와 택배 상태는 서버가 직접 만든 요청이 아니에요. 결제사와 택배사가 보내는 웹훅이에요. 그래서 우리가 보낸 순서대로 오지 않을 수 있어요.

Stripe 문서는 이벤트 전달 순서를 보장하지 않는다고 설명해요. created 값으로 이벤트 순서나 처리 여부를 판단하지 말라고 권해요. 중복 수신에 대비해서는 처리한 이벤트 ID를 기록하라고 설명해요.

그래서 웹훅 처리는 "지금 상태에서 이 전이가 허용되는가"를 먼저 물어요. 예를 들어 배송 준비 주문에 늦은 결제 완료 통지가 도착했다고 해요.

| 방식                 | 결과                                  | 상태                                        |
| -------------------- | ------------------------------------- | ------------------------------------------- |
| 화면에서만 막기      | 결제 완료로 값을 덮어써요             | 배송 준비에서 결제 완료로 되돌아가요        |
| 전이 규칙으로 거르기 | 배송 준비에는 결제 완료 전이가 없어요 | 상태가 그대로이고, 웹훅은 2xx로 받아 버려요 |

웹훅 응답은 처리 결과와 상관없이 빨리 2xx로 돌려주는 편이 좋아요. Stripe 문서는 복잡한 처리 전에 2xx 응답을 먼저 돌려주라고 권해요. 규칙에 어긋난 통지는 버리고 기록만 남기면 돼요. 수신 쪽 설계 전반은 [웹훅 수신 — 결제 완료는 누가 알려 주나요](/m/webhook-receiving) 글에서, 결제 상태 조회와 멱등성은 [결제 — 이중 결제 막기](/m/payment-idempotency) 글에서 다뤄요.

## FE 체크 포인트

- 버튼은 `allowed_actions` 목록으로만 그려요. FE가 상태 문자열로 규칙을 다시 판정하지 않아요.
- 409를 받으면 `current_status`로 화면 상태를 바꾸고, 이유를 한 문장으로 보여 줘요. 예: "이미 출고돼서 취소할 수 없어요."
- 취소 버튼을 누르면 요청이 끝날 때까지 잠가 더블 클릭을 줄여요. 서버도 같은 요청을 두 번 받으면 두 번째를 409로 거부해요.
- 취소 상태를 먼저 보여 주는 낙관적 UI 라면, 409를 받을 때 이전 상태로 되돌려요. 재시도 규칙은 [트랜잭션 · 락 · 데드락](/m/transactions) 글의 멱등성 절을 참고해요.
- API 오류 본문을 한 곳에서 파싱하면 409와 다른 오류를 같은 방식으로 다룰 수 있어요. 오류 형식은 [에러 응답 설계 — 상태 코드와 문제 형식](/m/api-errors) 글에서 다뤄요.

## 시뮬레이터 안내

시뮬레이터에서 들어온 요청 네 가지를 고르고, 판정 방식 세 가지를 바꿔 볼 수 있어요.

- 결과 칸에서 최종 상태와 잘못된 전이 수를 봐요.
- 요청별 응답 표에서 200, 200 (무시), 409 중 무엇을 받았는지 봐요.
- 기록된 전이 목록에서 허용되지 않은 전이에 표시가 붙는지 봐요.

시뮬레이터는 순수 모델이에요. 실제 DB나 네트워크 지연은 없어요. 같은 묶음의 요청은 같은 옛 상태를 읽도록 묶어서 동시성을 흉내 내요. 실제 경쟁 타이밍은 DB와 격리 수준에 따라 달라져요.

## 정리 — 서버 판정 · 조건부 쓰기 · 409 본문 · 이력 · 규칙으로 거르기

- 전이 판정은 서버가 해요. 화면 버튼은 서버가 내려 준 가능한 동작으로 그려요.
- 동시 요청은 `WHERE status = ...` 조건부 UPDATE로 한쪽만 통과시켜요.
- 거부는 409와 현재 상태를 담은 문제 본문으로 응답해요.
- 상태 변경과 이력 기록은 같은 트랜잭션에 묶어요.
- 늦게 온 외부 이벤트는 순서 대신 허용 전이 표로 걸러서 상태가 되돌아가지 않게 해요.
