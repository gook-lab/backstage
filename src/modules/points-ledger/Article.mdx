마이페이지 포인트 잔액이 내역 합계와 맞지 않으면 FE 개발자는 BE에 무엇을 물어야 할지 막막해요. 잔액은 숫자 한 칸이라서 왜 줄었는지 남아 있지 않아요. 이 글에서는 잔액을 숫자 한 칸이 아니라 거래 기록의 합계로 바꾸는 방법을 다뤄요.

아래 시뮬레이터에서 적립 묶음 세 개, 사용, 취소, 만료 정책을 직접 바꿔 볼 수 있어요. 글에서 말하는 배분 규칙과 같은 계산을 따라요.

## 잔액 열 갱신 — 내역과 잔액이 어긋나는 경로

적립과 사용을 잔액 열 하나에 반영하면 쓰기는 `balance = balance - 사용액` 같은 한 줄이 돼요. 이 한 줄 뒤에는 어느 적립에서 얼마가 빠졌는지 남지 않아요. 잔액만 보면 현재 값만 알 수 있어요.

내역 테이블을 따로 두면 어긋남이 더 쉽게 생겨요. 잔액 갱신과 내역 행 추가 사이에 실패가 나면 잔액만 바뀌거나 내역만 남아요. 같은 묶음을 두 요청이 동시에 읽고 각자 빼면 실제로 나간 합계가 잔액을 넘기도 해요.

변경 이력을 어떻게 쌓을지는 [감사 이력](/m/audit-history) 글에서 따로 다뤄요. 이 글에서는 포인트 자체의 기록을 원장으로 두는 방법에 집중해요.

## 원장 — 거래 행을 쌓고 잔액은 합계로 구하기

원장은 거래를 한 행씩 덧붙이는 기록이에요. 행을 고치거나 지우지 않아요. 잔액은 행 금액을 모두 더한 값이에요.

Martin Fowler의 Event Sourcing 글은 애플리케이션 상태의 모든 변경을 이벤트 객체로 남기고, 그 객체를 적용된 순서대로 저장한다고 설명해요. 포인트 원장은 같은 발상을 잔액에 적용한 것으로 볼 수 있어요.

| 행 항목   | 예                             | 이유                                                        |
| --------- | ------------------------------ | ----------------------------------------------------------- |
| 종류      | 적립 · 사용 · 복원 · 소멸      | 잔액이 왜 바뀌었는지 종류로 나눠 설명해요                   |
| 묶음      | 묶음 A · 묶음 B                | 어느 적립에서 빠졌는지 추적해요                             |
| 금액      | +5,000 · -6,000                | 부호로 증감을 나타내고 합계에 그대로 더해요                 |
| 발생 시각 | UTC로 저장하고 화면에서 바꿔요 | 시각 표기는 [시각과 시간대](/m/time-and-locale) 글을 따라요 |
| 참조      | 주문 번호 · 취소 번호          | 어떤 거래에서 생긴 행인지 연결해요                          |

잘못 기록한 행은 반대 거래로 정정해요. 사용 6,000P를 잘못 기록했다면 +6,000P 행을 더해요. 원래 행은 그대로 둬요. 기록을 지우면 그 시점의 잔액을 다시 설명할 수 없어요.

## 적립 묶음 — 묶음별 만료일과 만료 임박 순 사용

적립은 묶음(lot) 단위로 들어와요. 묶음마다 금액과 만료일이 있어요. 사용자가 포인트를 쓰면 어느 묶음에서 얼마를 쓸지 정해야 해요.

| 배분 방식    | 설명                          | 주의                                           |
| ------------ | ----------------------------- | ---------------------------------------------- |
| 만료 임박 순 | 만료일이 가까운 묶음부터 써요 | 배분 계산이 필요해요. 만료 전에 쓰게 해요      |
| 적립 순      | 오래된 묶음부터 써요          | 계산은 단순하지만 만료 임박 묶음이 남기 쉬워요 |
| 비율 배분    | 묶음 금액 비율로 나눠 써요    | 한 번 사용이 여러 묶음 행으로 쪼개져요         |

이 글에서는 만료 임박 순(FIFO)으로 골라요. 같은 만료일이면 적립 순서를 따라요. 이 순서는 예시 정책이에요. 회사 정책이 다르면 그 정책을 따라요.

만료일 당일까지 쓸 수 있고, 다음 날부터 묶음의 남은 금액이 소멸 행으로 기록돼요. 이 경계도 예시 정책이에요.

사용 행에는 묶음별 배분을 남겨요. 한 번의 사용이 묶음 두 개에 걸치면 행도 두 개로 나눠요. 취소할 때 어느 묶음으로 돌려줄지 이 기록으로 정해요.

## 사용 취소 — 만료된 묶음 몫 처리 세 가지 (예시 정책)

취소는 사용 행의 배분을 거꾸로 따라가요. 묶음이 아직 살아 있으면 같은 묶음으로 복원해요. 취소 날짜에 묶음이 이미 만료됐다면 정책이 필요해요.

| 정책              | 원장에 남는 행                          | 잔액               | 사용자가 보는 결과           |
| ----------------- | --------------------------------------- | ------------------ | ---------------------------- |
| 복원 안 함        | 복원 행 없음. 복원하지 않은 금액만 기록 | 만료 몫만큼 적어요 | 만료 몫은 돌아오지 않아요    |
| 복원 후 즉시 소멸 | 복원 행과 소멸 행이 함께 남아요         | 변동이 없어요      | 돌아왔다가 바로 사라져요     |
| 유효기간 연장     | 복원 행과 묶음 만료일 변경 행이 남아요  | 만료 몫만큼 늘어요 | 취소한 날부터 기간을 더 써요 |

세 정책 중 무엇을 고를지는 회사 정책이에요. 이 글에서는 예시 정책으로만 보여 줘요. 연장 기간 30일도 예시 값이에요.

복원하지 않는 정책을 쓰더라도 복원하지 않은 금액은 기록으로 남기는 편이 좋아요. 원장 행이 없으면 잔액이 왜 그만큼 적은지 나중에 설명할 수 없어요.

## 동시 사용 — 음수 잔액 막는 조건부 UPDATE와 락

두 요청이 같은 묶음 잔액 4,000P를 읽고 각자 3,000P를 쓸 수 있다고 판단하면, 실제로는 6,000P가 나가요. 잔액 열은 읽은 값으로 쓰여서 1,000P로 남고, 원장과 어긋나요. 읽고 나서 쓰는 방식은 이 틈을 막지 못해요.

조건을 쓰기 문장에 넣으면 확인과 차감이 한 문장이 돼요. 아래 SQL은 예시 스키마예요.

```sql
UPDATE point_lot
SET remaining = remaining - $1
WHERE id = $2
  AND remaining >= $1;
```

PostgreSQL 문서는 UPDATE가 갱신한 행 수를 돌려준다고 설명해요. 조건에 맞는 행이 없으면 갱신 행 수는 0이고, 문서는 이것을 오류로 보지 않는다고 설명해요. 앱은 0이면 이 묶음을 건너뛰거나 사용을 거절해요.

CHECK 제약도 같은 행을 막는 데 쓸 수 있어요. `CHECK (remaining >= 0)`을 묶음 행에 두면 한 묶음이 음수가 되는 것은 막혀요. 다만 PostgreSQL 문서는 CHECK 제약이 같은 행의 새 값만 볼 수 있고 다른 행의 데이터를 참조할 수 없다고 설명해요. 그래서 여러 묶음의 합계가 0 이상이라는 조건은 CHECK로 걸 수 없어요.

한 번의 사용이 묶음 여러 개를 건드리면 행 잠금이 필요해요. PostgreSQL 문서는 FOR UPDATE로 가져온 행을 현재 트랜잭션이 끝날 때까지 다른 트랜잭션이 바꾸거나 잠그지 못하게 한다고 설명해요. 잠금은 트랜잭션이 끝날 때까지 행을 붙잡아요. 외부 호출을 그 안에 넣으면 잠금 시간이 길어져요. 자세한 내용은 [트랜잭션 · 락 · 데드락](/m/transactions) 글과 [환불과 부분 취소](/m/refunds) 글에서 다뤄요.

## 잔액 스냅샷 — 원장 합계와 대조 배치

매번 전체 원장을 더하면 느려져서 잔액 스냅샷 행을 따로 둬요. 스냅샷은 빠른 조회용이에요. 기준은 언제나 원장이에요.

스냅샷 갱신은 원장 행 추가와 같은 트랜잭션에서 해요. 두 쓰기가 한 트랜잭션에 묶여 있으면 한쪽만 남는 일을 줄일 수 있어요.

대조 배치는 사용자별로 원장 합계와 스냅샷을 비교해요. 차이가 나면 원장 기준으로 스냅샷을 고치고 기록을 남겨요. 배치를 어떻게 나누고 재시작할지는 [배치 작업](/m/batch-jobs) 글을 따라요.

대조는 실시간이 아니에요. 불일치가 발견되기 전에 화면에 옛 값이 먼저 보였을 수 있어요.

## 만료 예정 알림 — 대상 조회와 중복 발송 막기

만료 예고는 원장 전체가 아니라 만료 예정 묶음 조회 결과로 대상을 골라요. 예를 들어 3일 안에 만료되는 묶음이 남은 사용자를 찾아요.

같은 묶음에 같은 예고를 두 번 보내지 않으려면 예고 발송 기록을 남겨요. 배치가 재시도돼도 이 기록으로 중복을 걸러요.

발송 자체는 [트랜잭션 메일](/m/transactional-email) 글의 방식을 따라요.

## FE 체크 포인트 — 잔액과 내역을 같은 응답에서 받기

**잔액과 내역을 같은 응답에서 받아요.** 두 값을 다른 요청으로 받으면 그 사이에 원장이 바뀌어 어긋나 보일 수 있어요.

**곧 만료되는 포인트를 묶음 단위로 보여 줘요.** 만료일은 응답의 날짜 값을 그대로 쓰고, 화면에서 남은 일수만 계산해요.

**취소 정책 문구를 서버 응답에서 받아요.** 정책을 화면에 하드코딩하면 회사 정책이 바뀔 때 문구가 틀려요.

**사용 실패는 부족한 금액과 함께 받아요.** 부족 금액을 응답에 실으면 안내 문구를 정확하게 맞출 수 있어요.

## 시뮬레이터 안내

시뮬레이터에서 적립 묶음 A, B, C의 금액과 만료일을 정해요. 사용 금액과 날짜, 취소 여부와 취소 날짜, 만료된 묶음 처리 정책을 골라요.

결과에서는 묶음별 사용 배분, 확인 날짜 기준 남은 잔액, 소멸액, 복원하지 않은 금액을 볼 수 있어요. 아래 원장 행 목록에서 행마다 잔액이 어떻게 이어지는지도 확인해요.

## 정리 — 원장 행 · 묶음 배분 · 취소 정책 · 조건부 UPDATE · 대조 배치

잔액은 원장 행의 합계로 구해요. 행은 지우지 않고 반대 행으로 정정해요. 사용은 만료 임박 순으로 묶음에 배분해서 행으로 남겨요. 취소할 때 만료된 묶음 몫은 정책에 따라 원장에 기록해요. 음수 잔액은 조건부 UPDATE와 행 잠금으로 막아요. 스냅샷은 원장과 대조해요.
