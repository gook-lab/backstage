결제는 승인됐는데 재고 서비스가 실패해서, 주문이 '처리 중'에 멈춰 있다고 해 봐요. 주문, 결제, 재고는 서로 다른 서비스가 각자의 DB를 가져요. 처음 떠오르는 답은 세 DB를 트랜잭션 하나로 묶고, 실패하면 같이 롤백하는 거예요.

이 글은 그 답이 왜 바로 되지 않는지에서 시작해요. 그다음 사가(saga)가 보상 작업으로 앞 단계를 어떻게 되돌리는지, 보상이 다시 실패하면 무엇이 남는지를 차례로 봐요.

아래 시뮬레이터에서 실패 지점과 처리 방식을 바꾸면 서비스마다 최종 상태가 어떻게 달라지는지 직접 확인할 수 있어요.

## 서비스마다 DB가 다를 때 — 트랜잭션이 묶이지 않는 이유

Azure 아키텍처 센터는 ACID 보장이 독립적으로 관리되는 여러 데이터 저장소에는 직접 적용되지 않는다고 설명해요. microservices.io도 같은 예시를 들어요. 주문과 고객이 서로 다른 서비스가 소유한 DB에 있으면, 애플리케이션은 로컬 ACID 트랜잭션을 그냥 쓸 수 없어요.

이때 FE는 중간 상태를 봐요. 결제는 끝났고, 재고와 주문은 아직이에요. '처리 중'이라는 문구는 이 틈을 손님에게 알려 주는 표시예요. 틈을 없애려면 여러 DB를 한 덩어리로 맞추는 방법이 필요해요.

## 2단계 커밋 — 여러 DB를 한 덩어리로 맞추는 방법의 한계

2단계 커밋(2PC)은 외부 트랜잭션 관리자가 여러 자원을 두 단계로 묶는 방식이에요. PostgreSQL 문서는 `PREPARE TRANSACTION`이 트랜잭션을 2단계 커밋용으로 준비한다고 설명해요. 준비된 트랜잭션의 상태는 디스크에 저장되고, 나중에 `COMMIT PREPARED`나 `ROLLBACK PREPARED`로 끝내요. 관리자는 다른 DB도 커밋할 준비가 됐는지 확인한 뒤에 끝내는 흐름이에요.

문제는 준비 상태가 오래 남을 때예요. 같은 문서는 준비된 트랜잭션이 가진 락을 계속 들고 있어서, 오래 두면 VACUUM이 저장 공간을 회수하지 못한다고 경고해요. 외부 트랜잭션 관리자가 준비된 트랜잭션을 빨리 닫아 주지 않는다면 `max_prepared_transactions`를 0으로 두는 편이 낫다고 권해요.

microservices.io의 사가 문서는 서비스마다 DB가 다른 주문 처리에서 2PC를 선택지로 두지 않아요. 같은 사이트의 아웃박스 문서는 DB 저장과 메시지 발행을 2PC로 묶기 어려운 이유도 정리해요. 데이터베이스나 메시지 브로커가 2PC를 지원하지 않을 수 있고, 서비스를 DB와 브로커 둘 다에 묶는 것은 바람직하지 않아요.

| 구분      | 2단계 커밋 (2PC)             | 사가 (saga)                               |
| --------- | ---------------------------- | ----------------------------------------- |
| 묶는 방식 | 준비 후 함께 커밋하거나 롤백 | 로컬 트랜잭션을 순서대로 실행             |
| 참여 조건 | 자원이 2PC를 지원해야 해요   | 각 서비스가 자기 보상 작업을 가져야 해요  |
| 잠금      | 준비 상태 동안 락을 유지해요 | 각 로컬 트랜잭션은 자기 단계에서 커밋해요 |
| 실패 처리 | 외부 관리자가 커밋 또는 롤백 | 앞서 끝난 단계를 보상 작업으로 되돌려요   |

이 글은 2PC 대신 사가를 다뤄요. 사가는 원자성을 주지 않는 대신, 각 단계가 독립적으로 커밋되는 것을 받아들이고 되돌리는 길을 설계하는 방식이에요.

## 사가 — 로컬 트랜잭션의 순서와 보상 작업

microservices.io는 사가를 로컬 트랜잭션들을 신뢰성 있게 조정한 순서로 설명해요. 모든 단계가 성공하거나, 비즈니스 규칙을 어긴 로컬 트랜잭션이 생기면 앞서 끝난 단계의 변경을 보상 트랜잭션으로 되돌려요.

주문 예시는 네 단계예요.

| 단계      | 하는 일                 | 뒤에서 실패하면 되돌리는 방법    |
| --------- | ----------------------- | -------------------------------- |
| 주문 생성 | 주문을 처리 중으로 저장 | 주문 취소                        |
| 결제 승인 | 카드 승인               | 결제 취소 (환불)                 |
| 재고 차감 | 재고를 줄여요           | 재고 복구                        |
| 배송 요청 | 배송 업체에 요청해요    | 마지막 단계라 되돌릴 일이 없어요 |

Azure 패턴 문서는 보상 트랜잭션이 반대 효과를 내는 다른 트랜잭션으로 앞선 변경을 되돌린다고 설명해요.

## 보상 작업 — 되돌리기가 아니라 반대 효과의 새 작업

보상은 DB 롤백과 달라요. 롤백은 아직 커밋되지 않은 변경을 없애지만, 보상은 이미 커밋된 변경 위에 새 작업을 얹어요. 이 글의 모델도 환불을 승인과 따로 세어요. 승인 기록을 지우지 않고, 환불이 한 번 더 나갔는지를 따로 확인해요.

이 차이 때문에 되돌릴 수 없는 단계가 생겨요. Azure 보상 트랜잭션 문서는 외부 부작용이나 법적 효력이 있는 행동처럼 되돌릴 수 없는 단계가 있다고 설명해요. 그런 단계는 모든 검증이 끝난 뒤에 실행되도록 설계하라고 권해요.

이미 보낸 메일은 보상으로 회수할 수 없어요. 대신 "정정 메일을 보낸다" 같은 새 작업을 설계해야 해요.

보상 순서도 원래 순서의 정확한 역순이 아닐 수 있어요. 같은 문서는 한쪽 저장소가 불일치에 더 민감하면 그쪽을 먼저 되돌린다고 설명해요. 시뮬레이터는 단순하게 역순으로 되돌려요.

Azure 사가 문서는 되돌릴 수 있는 단계와 확정된 단계의 경계를 피벗 트랜잭션이라고 불러요. 피벗 이후의 단계는 되돌리지 않고 재시도로 끝내요. 이 경계가 되돌리기 가능 지점과 "앞으로 가야만 하는 지점"을 나눠요.

## 실패 처리 — 재시도로 먼저 풀고, 포기하면 보상하기

모든 실패를 보상으로 처리하지 않아요. Azure 보상 트랜잭션 문서는 일시 오류로 볼 수 있는 실패는 재시도로 먼저 처리하고, 반복해서 실패하거나 복구할 수 없을 때만 보상을 시작하라고 설명해요.

- 네트워크 시간 초과처럼 잠깐 실패하는 단계는 [메시지 큐와 재처리](/m/message-queue)에서 본 재시도 간격으로 다시 시도해요.
- 재고 부족처럼 다시 해도 같은 결과가 나오는 실패는 바로 보상으로 넘어가요. 재시도는 재고를 늘리지 않아요.

시뮬레이터의 '보상 + 재시도'는 보상 작업을 최대 3번까지 시도해요. 순방향 단계의 실패는 비즈니스 실패로 두었어요.

## 보상 작업의 재시도 — 멱등한 보상과 실패 지점부터 재개

보상도 실패할 수 있어요. Azure 문서는 보상 트랜잭션이 최종적으로 일관된 상태를 만드는 작업이라서 실패할 수 있다고 설명해요. 그래서 시스템은 진행 상태를 기록해서 실패한 지점부터 다시 시작할 수 있어야 해요. 같은 문서는 단계가 여러 번 실행될 수 있으니 각 단계를 멱등한 명령으로 설계하라고 권해요.

응답 유실이 특히 위험해요. 환불 요청은 서버에서 처리됐지만 응답이 네트워크에서 사라지면, 호출자는 실패로 보고 다시 보내요. 멱등하지 않은 보상이면 환불이 두 번 나가요. 멱등하면 두 번째 요청을 같은 작업으로 알아보고 건너뛰어요. 요청을 같은 작업으로 묶는 방법은 [결제 멱등성](/m/payment-idempotency)에서 본 멱등성 키와 같은 발상이에요.

진행 상태는 오케스트레이터가 저장해요. Azure 사가 문서는 오케스트레이터가 각 작업의 상태를 저장하고 해석하며, 보상으로 실패를 복구한다고 설명해요. 시뮬레이터는 이 저장 과정과 재시작은 흉내 내지 않아요. 보상이 포기된 지점을 보여 줄 뿐이에요.

## 오케스트레이션과 코레오그래피 — 중앙 조정자와 이벤트 연쇄 비교

사가를 조정하는 방식은 두 가지예요. Azure 사가 문서와 microservices.io가 같은 구분을 써요.

| 구분      | 오케스트레이션 (orchestration)                          | 코레오그래피 (choreography)                                            |
| --------- | ------------------------------------------------------- | ---------------------------------------------------------------------- |
| 흐름 제어 | 중앙 오케스트레이터가 참여자에게 실행할 작업을 지시해요 | 각 로컬 트랜잭션이 도메인 이벤트를 발행해 다음 단계를 촉발해요         |
| 장점      | 복잡한 흐름과 서비스 추가에 맞아요. 순환 의존을 피해요  | 중앙 조정자가 없어서 단일 장애점이 생기지 않아요                       |
| 단점      | 오케스트레이터가 장애점이 돼요                          | 흐름이 흩어져서 추적과 통합 테스트가 어려워요. 순환 의존 위험이 있어요 |

Azure 문서는 오케스트레이션이 복잡한 흐름이나 서비스를 추가할 때 맞다고 설명해요. 오케스트레이터가 상태를 저장하고 실패 복구를 맡기 때문이에요.

단계와 서비스가 적은 단순한 흐름이면 코레오그래피도 충분하다고 같은 문서가 설명해요. FE 입장에서는 어느 방식이든 주문 상태 하나로 보여요. 차이는 서버 안에서 실패를 추적하는 방식에 있어요.

## 격리 부족 — 처리 중인 주문을 다른 요청이 읽는 문제

microservices.io는 사가에 격리가 없다고 설명해요. ACID의 I가 없어서, 동시에 돌아가는 사가와 트랜잭션이 데이터 이상을 만들 수 있어요. Azure 문서는 대표적인 이상으로 세 가지를 들어요.

- 갱신 손실: 한 사가가 다른 사가의 변경을 모르고 쓰면서 앞의 변경이 덮여요.
- 더티 리드: 다른 사가가 아직 끝나지 않은 변경을 읽어요.
- 반복 불가능 읽기: 같은 사가의 두 단계가 사이에 일어난 갱신 때문에 다른 값을 읽어요.

예시로, 재고 복구 전에 다른 주문이 줄어든 재고를 보고 품절이라고 판단하면 더티 리드예요. 이 문제를 줄이는 방법은 Azure 문서에 다섯 가지가 있어요. 의미 잠금, 순서와 무관한 갱신, 비관적 뷰, 갱신 전 다시 읽기, 버전 파일이에요.

이 글에서 '처리 중' 상태는 의미 잠금과 비슷한 역할을 해요. Azure 문서는 의미 잠금을 보상 가능한 트랜잭션이 갱신 중임을 알리는 애플리케이션 수준의 표시로 설명해요. 손님에게 '처리 중'을 보여 주면, 그 주문을 완료된 것으로 취급하지 않도록 막아요.

다만 서버가 그 표시를 실제로 확인해야 해요. 화면만 막으면 같은 주문을 다른 기기에서 취소하는 요청은 막지 못해요. 그 판정은 [주문 상태 전이](/m/order-state)에서 다룬 조건부 쓰기로 해요.

## 메시지 발행 — 아웃박스로 DB 저장과 발행 묶기

사가의 각 단계는 다음 단계를 깨우는 메시지를 보내요. microservices.io는 서비스가 신뢰성 있으려면 DB 갱신과 메시지 발행을 원자적으로 해야 한다고 설명해요. 그런데 DB와 브로커를 2PC로 묶을 수 없으니, 같은 트랜잭션에 아웃박스 테이블을 쓰고 별도 프로세스가 발행하는 방식을 써요. 자세한 구조는 [메시지 큐와 재처리](/m/message-queue)의 아웃박스 절에서 다뤄요.

보상 명령도 같은 방식으로 발행해요. 환불 명령이 DB 저장과 따로 나가면, 주문은 취소됐는데 환불 명령은 유실되는 상태가 생겨요.

## FE 체크 포인트 — 처리 중 화면과 확인 필요 상태

- '처리 중'을 '완료'로 바꾸지 않아요. 최종 상태는 조회 API나 완료 통지로 확인해요. 통지는 [웹훅 수신](/m/webhook-receiving)이나 [백그라운드 작업](/m/background-jobs)의 상태 조회에서 다룬 방식으로 받아요.
- 완료 시각을 약속하지 않아요. 보상은 여러 단계와 재시도를 거쳐서 시간이 정해져 있지 않아요.
- 보상이 포기된 주문은 '확인 필요'로 따로 보여 줘요. 손님이 할 수 있는 일을 함께 보여 줘요. 고객센터 문의 경로가 그 예예요.
- 취소 버튼은 서버가 허용하는 동작 목록으로만 그려요. 취소와 출고가 겹치는 경우는 [주문 상태 전이](/m/order-state) 글을 참고해요.

## 시뮬레이터 안내

시뮬레이터는 주문 한 건을 네 단계로 돌려요. 한 줄의 시도가 한 틱이에요.

- **실패가 나는 단계**를 고르면 그 단계에서 순방향 실행이 멈춰요.
- **처리 방식**을 고르면 보상이 없는지, 있는지, 재시도까지 하는지가 정해져요.
- **보상 작업에서 일어나는 일**은 보상 단계마다 첫 시도에 적용돼요. '처리됐지만 응답 유실'은 효과는 났는데 실패로 보이는 경우예요.
- **멱등하게 만들어요**를 끄면 응답이 유실된 보상을 재시도할 때 효과가 한 번 더 나가요.

다음 세 가지 조합을 먼저 확인해 보세요.

1. 실패 지점을 '재고 부족'으로 두고 처리 방식을 '보상 없음'으로 두면, 결제는 남고 주문은 처리 중에 멈춰요.
2. 처리 방식을 '보상 + 재시도'로 두고 보상 상태를 '계속 실패'로 바꾸면, 재시도 3번 뒤 보상이 포기되고 멈춰요.
3. 보상 상태를 '처리됐지만 응답 유실'로 두고 멱등 체크를 끄면, 환불이 두 번 나가요.

시뮬레이터는 순수 모델이에요. 네트워크 지연과 타임아웃, 오케스트레이터가 중간에 죽는 상황은 없어요.

## 정리 — 2PC 대신 사가 · 보상 설계 · 멱등 재개

- 서비스마다 DB가 다르면 ACID 트랜잭션 하나로 묶을 수 없어요. 2PC도 준비 상태의 락과 지원 조건 때문에 서비스 사이의 주문에는 잘 맞지 않아요.
- 사가는 로컬 트랜잭션의 순서이고, 실패하면 앞 단계를 보상 작업으로 되돌려요.
- 보상은 롤백이 아니라 반대 효과를 내는 새 작업이에요. 되돌릴 수 없는 단계는 검증 뒤에 실행해요.
- 실패는 재시도로 먼저 풀고, 포기할 때만 보상을 시작해요.
- 보상은 멱등하게 설계하고 진행 상태를 저장해서 실패 지점부터 재개해요.
- 처리 중 상태는 손님에게 알리고, 서버가 판정할 때도 같은 상태를 확인해요.
