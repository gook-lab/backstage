지하철에서 메모를 고쳤어요. 연결이 없어서 저장 요청은 기기 안에 머물러요. 집에 와서 노트북으로 같은 메모의 본문을 고쳐 저장하면, 폰에 쌓여 있던 수정이 뒤늦게 올라와 노트북의 수정과 섞여요.

프론트엔드 (FE) 화면에서는 "내가 고친 내용이 사라졌어요"나 "다른 기기에서 고친 내용이 되돌아왔어요"로 보여요. 이 글은 세 가지를 나눠 다뤄요. 기기 안에 편집을 쌓아 두는 대기열, 서버가 바뀐 것만 알려 주는 변경 피드, 같은 항목을 두 기기가 고쳤을 때의 충돌 처리예요.

같은 행을 조건부 저장으로 막는 방식은 [동시 편집 · 낙관적 동시성 제어](/m/concurrent-edits) 글에서 다뤘어요. 재시도할 때 결제가 두 번 나가지 않게 하는 방법은 [결제 — 이중 결제 막기](/m/payment-idempotency) 글에서 다뤘어요. 목록을 나눠 읽는 커서는 [페이지네이션 — offset · cursor](/m/pagination) 글과 이어져요.

아래 시뮬레이터에서 두 기기의 도착 순서, 전송 범위, 충돌 전략을 바꿔 보세요. 서버 최종 상태, 기기별 화면, 잃은 변경이 바로 보여요.

## 오프라인 편집 — 기기 안 대기열과 재전송

오프라인에서는 저장 요청에 대한 응답을 받을 수 없어요. 그래서 편집을 바로 보내지 않고 기기 안 대기열 (outbox)에 먼저 적어 둬요. 웹에서는 보통 IndexedDB에 둬요. MDN은 IndexedDB를 키로 색인한 객체를 저장하고 가져오는 트랜잭션형 DB라고 설명해요. 작업은 비동기로 돌아서 화면을 막지 않아요.

대기열 항목에는 세 가지를 같이 적어요.

| 기록      | 담는 내용                | 빠지면 생기는 일                      |
| --------- | ------------------------ | ------------------------------------- |
| 바뀐 필드 | 필드 이름과 새 값        | 어떤 값을 보낼지 알 수 없어요         |
| 기준 버전 | 편집을 시작할 때 본 버전 | 서버가 충돌을 판단할 근거가 없어요    |
| 기기 순번 | 기기 안에서 편집한 순서  | 같은 필드의 두 편집이 뒤집혀 보내져요 |

이 글의 모델은 대기열을 순서대로 모두 보낸다고 가정해요.

### 재전송 시점 — 온라인 신호와 Background Sync

언제 보낼지가 첫 판단이에요. `navigator.onLine`은 가장 쉬운 신호지만, MDN은 이 값이 본질적으로 믿기 어렵다고 설명해요. LAN에만 붙어 있어도 온라인으로 나올 수 있어요. 그래서 MDN은 이 값으로 기능을 끄지 말고 힌트로만 쓰라고 권해요.

online · offline 이벤트로 상태가 바뀌었다는 것은 알 수 있어요. 이 이벤트도 힌트이므로, 대기열은 신호를 받은 뒤 항목을 하나 보내고 응답을 받은 항목만 지워요.

Background Sync API는 화면이 닫힌 뒤에도 일을 맡기는 길이에요. MDN은 서비스 워커가 네트워크 요청 사이에 서는 프록시 서버처럼 동작하며, 백그라운드 동기화 API에도 접근하게 한다고 설명해요. 등록한 동기화 작업은 네트워크가 다시 생기면 `sync` 이벤트로 처리돼요. 다만 MDN은 이 기능이 Baseline이 아니어서 일부 주요 브라우저에서는 동작하지 않는다고 표시해요. 그래서 Background Sync는 쓸 수 있을 때 붙이는 보강으로 보고, 화면이 열려 있을 때의 재시도 경로는 따로 두는 편이 좋아요.

| 신호                               | 쓰는 자리                               | 한계                                                 |
| ---------------------------------- | --------------------------------------- | ---------------------------------------------------- |
| `navigator.onLine`과 online 이벤트 | 화면이 열려 있을 때 재시도 시점 고르기  | 네트워크 연결만 보고 인터넷 도달은 보장하지 않아요   |
| Background Sync (`sync` 이벤트)    | 화면이 닫힌 뒤에도 서비스 워커가 보내기 | 일부 브라우저에서 동작하지 않아요                    |
| 실패 항목 재시도                   | 요청이 실패한 항목을 다시 보내기        | 실패가 이어지면 대기 시간을 늘리는 백오프가 필요해요 |

### 재전송 안전성 — 멱등한 메서드로 보내기

재전송에서 조심할 상황은 서버가 처리를 끝냈지만 응답이 기기에 닿지 않은 경우예요. 기기는 실패로 알고 같은 요청을 다시 보내요. RFC 9110은 PUT과 DELETE, 그리고 안전한 메서드를 멱등하다고 정의해요. 같은 요청을 여러 번 보내도 서버에 의도한 효과는 한 번 보낸 것과 같다는 뜻이에요.

RFC 9110은 PUT 요청을 보냈는데 응답을 받기 전에 연결이 끊기면, 클라이언트가 새 연결로 같은 요청을 다시 보낼 수 있다고 설명해요. 반대로 멱등하지 않은 요청은 클라이언트가 자동으로 다시 보내지 않도록 권해요.

그러면 대기열 항목을 POST로 "새 메모 만들기"로 보내는 설계는 재전송에 약해요. 응답이 유실되면 기기는 메모가 만들어졌는지 알 수 없고, 자동 재시도를 피하면 항목이 빠진 채로 남아요. 대기열 항목을 클라이언트가 고른 id를 가진 PUT으로 보내면 같은 자리에 같은 내용이 남아서 재전송이 안전해요. PUT으로 표현하기 어려운 요청은 [결제 — 이중 결제 막기](/m/payment-idempotency) 글처럼 멱등성 키로 시도를 묶어요.

## 서버 변경 피드 — 시작 토큰과 증분 커서

전체 목록을 매번 받으면 메모가 늘수록 낭비예요. 서버가 "이 지점 이후에 바뀐 것"을 알려 주는 구조가 필요해요. 이 지점을 가리키는 값을 동기화 토큰 (sync token)이라고 불러요. 서비스마다 이름은 다르지만, 기기가 마지막으로 본 지점을 기억해 두고 다음 요청에 되돌려 준다는 점은 같아요.

### 세 API의 토큰 흐름 — 처음 받기와 다음 요청

Google Calendar는 처음 전체 목록을 받을 때 응답의 `nextSyncToken`을 저장하라고 설명해요. 다음 증분 요청은 그 값을 `syncToken`으로 보내요. 결과가 여러 페이지면 새 토큰은 마지막 페이지에만 있어요.

Google Drive는 `changes.getStartPageToken`으로 시작 토큰을 받아요. `changes.list`로 변경을 읽고, 마지막에 응답의 `newStartPageToken`을 저장해요. Drive 문서는 변경 목록을 오래된 것부터 준다고 설명해요.

Microsoft Graph delta query는 응답에 `@odata.nextLink` 또는 `@odata.deltaLink`를 줘요. nextLink가 있으면 페이지가 더 남은 것이므로 계속 따라가요. deltaLink가 나오면 그 URL을 다음 동기화에 써요. 한 페이지에 둘이 같이 오지는 않아요.

| 항목      | Google Calendar             | Google Drive                      | Microsoft Graph               |
| --------- | --------------------------- | --------------------------------- | ----------------------------- |
| 처음 받기 | 전체 목록과 `nextSyncToken` | `getStartPageToken`으로 시작 토큰 | delta 요청 뒤 `nextLink` 반복 |
| 저장할 값 | `nextSyncToken`             | `newStartPageToken`               | `deltaLink`                   |
| 다음 요청 | `syncToken` 파라미터        | 저장한 토큰으로 `changes.list`    | `deltaLink` URL 그대로 호출   |
| 삭제 알림 | 증분 결과에 삭제 항목 포함  | `includeRemoved`로 포함 여부 결정 | `@removed` 객체               |

Microsoft Graph는 토큰 안의 내용을 클라이언트가 해석하지 않아도 된다고 설명해요. 받은 URL을 그대로 다음 요청에 쓰면 돼요. 같은 문서는 처음 요청에 넣은 `$select` 같은 파라미터가 토큰에 이미 담긴다고 설명해요. 그래서 다음 요청에 같은 파라미터를 다시 붙이지 말라고 권해요.

### 응답 순서 — 같은 항목이 여러 번 나올 수 있어요

Microsoft Graph는 delta 응답의 순서를 가정하지 말라고 설명해요. 같은 항목이 nextLink 흐름의 어느 자리에든 나올 수 있으니 병합 로직에서 처리하라고 권해요. 그래서 목록을 받은 순서대로 덮어쓰기보다, 항목 id별로 어떤 상태가 최신인지 골라서 적용하는 편이 안전해요.

## 전체 다시 받기와 증분 받기 — 비용과 복구 기준

| 방식           | 보내고 받는 양               | 기기가 맡는 일                       | 실패했을 때                             |
| -------------- | ---------------------------- | ------------------------------------ | --------------------------------------- |
| 전체 다시 받기 | 전체 항목 수에 비례해요      | 받은 목록으로 저장소를 통째로 맞춰요 | 다시 받으면 돼요                        |
| 증분 받기      | 바뀐 항목과 삭제 표시만 와요 | 토큰을 저장하고 항목별로 적용해요    | 토큰이 무효면 전체 다시 받기로 돌아가요 |

증분 받기가 항상 낫지는 않아요. 처음 로그인하거나 토큰을 잃은 경우처럼 기준점이 없으면 전체 다시 받기가 맞아요.

토큰이 무효가 되면 서버는 410 Gone으로 응답할 수 있어요. RFC 9110은 410을 대상 리소스를 원서버에서 더 이상 쓸 수 없고, 그 상태가 영구적일 가능성이 높다는 뜻으로 정의해요. Google Calendar는 토큰이 만료되거나 관련 ACL이 바뀌면 서버가 410을 준다고 설명해요. 이때는 저장소를 전부 비우고 전체 동기화를 다시 하라고 권해요. Microsoft Graph도 410 Gone이 오면 전체 동기화로 다시 시작해야 한다고 설명해요. 토큰은 일정 기간만 유효하고, 만료된 토큰에는 `syncStateNotFound` 같은 40X 계열 오류가 올 수 있다고 설명해요.

FE가 이 복구 경로를 짤 때 비우는 범위가 중요해요. 서버 데이터의 캐시는 비워도 되지만 대기열은 비우면 안 돼요. 아직 서버에 가지 못한 편집이 같이 사라지기 때문이에요.

## 삭제 표시 — 묘비로 알리는 삭제

목록에서 항목이 사라지면 기기는 두 경우를 구분할 수 없어요. 서버에서 삭제된 것인지, 이 기기가 처음부터 본 적이 없는 것인지요. 증분 받기는 목록이 아니라 변경 기록을 주므로 삭제도 기록으로 보내야 해요. 이 삭제 표시를 묘비 (tombstone)라고 불러요.

Google Calendar는 증분 결과에 삭제된 항목이 항상 포함된다고 설명해요. 기기가 저장소에서 그 항목을 지울 기회를 얻기 위해서예요. Drive는 `includeRemoved` 파라미터로 삭제 항목을 포함할지 정해요. Microsoft Graph는 삭제 항목을 id와 `@removed` 객체로 보내요.

`@removed`의 reason은 `changed`와 `deleted`예요. MS 문서는 `changed`를 deletedItems에서 복구할 수 있는 삭제로, `deleted`를 복구할 수 없는 삭제로 설명해요. 기기는 두 경우 모두 목록에서 빼되, 복구 가능성을 화면 문구에 반영하는 편이 좋아요. 묘비를 얼마나 오래 보관할지는 서비스 정책이에요. 이 글의 시뮬레이터는 보관 기간을 다루지 않아요.

편집 중인 항목이 서버에서 삭제되는 경우도 생겨요. 대기열에 본문 편집이 남아 있는데 묘비가 먼저 도착하면, 조용히 되살리거나 조용히 버리면 편집이 사라져요. 이때는 "삭제된 메모를 고치려 해요"처럼 사용자에게 보여 주는 편이 좋아요.

## 클라이언트 생성 id — 오프라인에서 만든 항목 식별

오프라인에서 새 메모를 만들면 서버 id가 아직 없어요. 기기가 id를 먼저 만들어야 대기열 항목과 화면의 항목을 이을 수 있어요. 여러 기기가 각자 만든 id가 겹치지 않도록 UUID를 쓰는 방식이 흔해요. id 방식의 차이는 [ID 설계 — 자동 증가와 UUID](/m/distributed-ids) 글에서 다뤘어요.

RFC 9110은 PUT이 대상 리소스를 새로 만들었으면 서버가 201 Created로 알려야 한다고 정해요. 그래서 클라이언트가 고른 id를 URL에 담아 PUT하면 새 항목 만들기와 재전송을 같은 요청으로 표현할 수 있어요. 같은 id로 두 번 보내도 항목은 하나만 남아요. 이 판단은 PUT이 멱등하다는 정의에 기대요.

## 충돌 처리 — 마지막 쓰기 우선 · 필드 병합 · 사용자 선택

충돌 전략은 잃을 수 있는 변경의 크기로 고르는 편이 좋아요.

| 전략             | 동작                                    | 잃을 수 있는 변경                            | 맞는 자리                   |
| ---------------- | --------------------------------------- | -------------------------------------------- | --------------------------- |
| 마지막 쓰기 우선 | 나중에 도착한 쓰기가 항목 전체를 덮어요 | 손대지 않은 필드도 옛 값으로 돌아가요        | 필드가 하나뿐인 작은 설정   |
| 필드 단위 병합   | 바뀐 필드만 비교해 나머지를 살려요      | 같은 필드를 두 기기가 고치면 한쪽이 사라져요 | 제목과 본문처럼 독립된 필드 |
| 사용자 선택      | 같은 필드 충돌을 저장하지 않고 보류해요 | 잃는 값은 없지만 보류 상태가 남아요          | 되돌리기 어려운 본문        |

마지막 쓰기 우선은 구현이 가장 단순해요. 대신 문서 전체를 보내면 기기가 고치지 않은 필드도 덮어써요. 시뮬레이터에서 "문서 전체 보내기"를 고르면, 폰이 고친 제목이 노트북이 들고 있던 옛 제목으로 돌아가는 것을 볼 수 있어요.

### 기준 버전과 실제 변경 — 손대지 않은 값 구분

필드 병합에는 두 정보가 필요해요. 편집을 시작할 때 본 버전과, 그 필드를 기기가 실제로 바꿨는지예요. 기준 버전만 보면 바꾸지 않은 필드도 충돌로 보여서 사용자를 귀찮게 해요. 실제 변경까지 보면 서버가 "손대지 않은 값을 유지"할 수 있어요.

같은 필드를 두 기기가 고쳤다면 병합으로는 해결되지 않아요. 이때는 사용자 선택으로 넘기는 편이 좋아요.

### CRDT — 이름과 쓰임만

같은 편집을 여러 기기에서 합쳐도 결과가 같아지도록 설계한 자료형을 CRDT (Conflict-free replicated data type)라고 불러요. 위키백과는 병합 함수가 교환 가능 (commutative), 결합 가능 (associative), 멱등 (idempotent) 이어야 한다고 설명해요. 상태 기반과 연산 기반 방식 모두 강한 최종 일관성 (strong eventual consistency)을 줄 수 있다고 적어요. 여러 기기 사이 오프라인 편집을 맞추는 예로 Apple Notes를 들어요. 이 글의 모델은 CRDT를 구현하지 않아요.

## FE 체크 포인트

- 편집하면 바로 "저장 대기"를 보여 줘요. 대기열 개수를 화면에 두면 오프라인 편집이 쌓였는지 알 수 있어요.
- 응답 코드를 나눠 처리해요. 200이면 응답에 담긴 새 토큰과 값을 저장해요. 410이나 40X 오류면 전체 다시 받기로 가요. 409면 충돌 화면으로 보내요.
- 마지막 쓰기 우선에서는 모든 응답이 200이어도 잃은 변경이 있을 수 있어요. 시뮬레이터에서 보듯 상태 코드만으로는 잃은 값을 알 수 없어요.
- 낙관적 UI는 대기열에 넣자마자 화면에 반영해요. 실패나 충돌이 오면 되돌리는 흐름이 필요해요. 되돌리기 규칙은 [동시 편집 · 낙관적 동시성 제어](/m/concurrent-edits) 글의 낙관적 UI 절과 같아요.
- 온라인 표시는 힌트로만 써요. `navigator.onLine`으로 저장 버튼을 막지 않아요.
- 토큰과 대기열은 IndexedDB에 둬요. 복구 코드에서 대기열을 지우지 않는 규칙을 한 곳에 모아 둬요.

## 시뮬레이터 안내

아래 시뮬레이터는 폰과 노트북이 같은 메모를 고치는 장면을 단순한 모델로 옮긴 것이에요.

- 도착 순서: 노트북 편집이 폰 대기열보다 먼저 닿는지, 나중에 닿는지예요.
- 전송 범위: 바뀐 필드만 보내는지, 문서 전체를 보내는지예요.
- 충돌 전략: 마지막 쓰기 우선, 필드 단위 병합, 사용자 선택이에요.

응답 표는 서버가 각 요청에 준 응답과 처리 결과를 보여 줘요. 화면 표는 서버와 두 기기에 남은 최종 값을 보여 줘요. 응답 코드가 모두 200인데 잃은 변경이 있는 조합을 찾아보세요.

## 정리 — 대기열 · 증분 토큰 · 묘비 · 충돌 전략 선택

- 대기열 항목에는 바뀐 필드, 편집 시점의 기준 버전, 기기 순번을 같이 적어요.
- 재전송 시점은 `navigator.onLine`을 힌트로만 쓰고, 응답을 받은 항목만 지워요.
- 재전송은 멱등한 PUT과 클라이언트 생성 id로 설계하는 편이 안전해요.
- 증분 받기는 토큰을 저장해요. 410이나 40X 오류면 전체 다시 받기로 돌아가되 대기열은 남겨요.
- 삭제는 묘비로 받아 기기가 옛 항목을 지울 수 있게 해요.
- 충돌은 기준 버전과 실제 변경을 함께 보고, 같은 필드 충돌은 사용자 선택으로 넘기는 편이 좋아요.
