해외 사용자만 첫 화면이 느린 것은 서버가 느려서가 아닐 수 있어요. 요청이 네트워크를 오가는 시간, 즉 왕복 시간(RTT)은 서버 코드를 고쳐도 줄지 않아요. 이 글은 첫 화면 데이터가 도착하기까지 몇 번 왕복하는지 세는 방법을 다뤄요. 연결을 새로 맺는 비용, 요청을 직렬로 보내는 구조, CDN 엣지와 리전 배치, FE가 쓸 수 있는 연결 힌트 순서로 봐요. 글의 숫자는 설명을 위한 예시예요.

## 증상 — 국내는 빠른데 해외에서만 3초 넘게 걸리는 첫 화면

서버가 재는 처리 시간은 요청이 서버에 도착한 뒤부터예요. 요청이 사용자에서 서버까지 오가는 시간은 그 바깥에 있어요. 그래서 서버 처리를 10ms 줄여도 해외 사용자의 첫 화면은 거의 그대로예요.

첫 화면이 여러 요청을 기다린다면 문제는 더 커져요. 요청마다 왕복 시간이 한 번씩 더해지기 때문이에요. 아래 시뮬레이터에서 같은 서버를 여러 거리에서 보면 이 차이가 어떻게 쌓이는지 확인할 수 있어요.

## 왕복 시간 — 빛의 속도가 정한 하한

HPBN은 광섬유에서 빛의 속도를 약 2억 m/s로 잡고, 굴절률을 약 1.5로 계산해요. 같은 책은 뉴욕과 시드니 사이 RTT가 기존 망에서 200~300ms 범위라고 적어요. 이 값은 거리와 망 구조에서 나오고, 서버 성능으로는 바꿀 수 없어요.

이 글은 사용자와 오리진 사이 RTT를 250ms로 두고 계산해요. 위 범위에 맞춘 예시 값이에요. 실제 사용자의 RTT는 측정해야 알 수 있어요.

## 연결 설정 비용 — TCP · TLS · QUIC 핸드셰이크 왕복

web.dev는 브라우저가 서버에 리소스를 요청하기 전에 먼저 연결을 맺어야 한다고 설명해요. HTTP/1.1과 HTTP/2는 TCP 위에서 돌고, TCP 3-way 핸드셰이크에만 왕복 1번이 들어요. HPBN은 한쪽 방향 전파가 28ms인 서버라면 이 핸드셰이크만 최소 56ms 걸린다고 계산해요.

TLS는 그 위에 한 번 더 얹혀요. HPBN은 새 TLS 연결의 전체 핸드셰이크에 왕복 2번이 든다고 설명해요. 같은 세션을 재개하는 축약 핸드셰이크는 왕복 1번이에요. RFC 8446은 전체 핸드셰이크에서 클라이언트가 한 번 보내고 서버가 응답하는 흐름을 그림 1로 보여 줘요(2절). 재개 시 0-RTT는 PSK로 첫 메시지에 데이터를 더해 보내는 방식이에요(2.3절).

QUIC은 전송 연결과 TLS 핸드셰이크를 한 번에 맞춰서 연결 설정 지연을 줄여요. RFC 9000은 이 결합 핸드셰이크를 설명하고, QUIC 패킷을 UDP 데이터그램에 실어 보낸다고 적어요. HTTP/3은 QUIC 버전 1 위에서 돌고, TLS 1.3 이상을 핸드셰이크로 써요(RFC 9114 3.2절).

## 프로토콜 비교 — 새 연결의 설정 왕복 수

아래 표는 첫 요청을 보내기 전까지 필요한 설정 왕복이에요. 요청 자체의 왕복은 따로 더해요.

| 프로토콜               | 새 연결           | 세션 재개         | 근거                      |
| ---------------------- | ----------------- | ----------------- | ------------------------- |
| HTTP/1.1 + TLS 1.2     | TCP 1 + TLS 2 = 3 | TCP 1 + TLS 1 = 2 | HPBN (TCP · TLS)          |
| HTTP/2 + TLS 1.3       | TCP 1 + TLS 1 = 2 | TCP 1 + 0-RTT = 1 | RFC 8446 2절 · 2.3절      |
| HTTP/3 (QUIC, TLS 1.3) | 전송과 TLS 합쳐 1 | 0-RTT = 0         | RFC 9000 · RFC 9114 3.2절 |

HTTP/2는 한 연결에서 요청마다 스트림을 따로 두고 여러 요청을 섞어 보내요. RFC 9113은 이를 다중화(multiplexing)라고 부르고, 한 스트림이 멈춰도 다른 스트림이 막히지 않는다고 설명해요. 다만 RFC 9113은 TCP 수준의 head-of-line 블로킹은 이 프로토콜이 해결하지 않는다고 적어요. HTTP/3은 QUIC 위에서 돌아요. RFC 9000은 스트림 간 head-of-line 블로킹을 피하는 것을 QUIC의 장점으로 꼽고, 패킷 손실이 생기면 그 패킷에 데이터가 있던 스트림만 재전송을 기다린다고 설명해요.

0-RTT 재개에는 주의가 필요해요. RFC 8446은 0-RTT 데이터가 연결 사이의 재전송(replay)을 막는다고 보장하지 않는다고 명시해요. 그래서 결제나 주문처럼 상태를 바꾸는 요청은 0-RTT로 보내지 않는 편이 좋아요.

## 연결 재사용 — 새 연결을 피하는 조건

이미 열린 연결을 쓰면 설정 왕복은 0이에요. RFC 9113은 HTTP/2 연결을 같은 오리진 권한 안의 여러 요청에 재사용할 수 있다고 정해요. https에서는 인증서가 요청하는 호스트에 유효해야 재사용 조건을 만족해요. RFC 9114는 HTTP/3 연결이 여러 요청에 걸쳐 유지되고, 필요가 없어질 때까지 닫지 않는 것이 성능에 좋다고 설명해요.

도메인을 여러 개로 나누면 재사용 조건을 도메인마다 따로 맞춰야 해요. RFC 9113 기준으로는 한 연결의 인증서가 다른 도메인에도 유효해야 그 연결을 같이 쓸 수 있어요. 그래서 API 도메인을 나눌 때는 연결 비용을 함께 따져 보는 편이 좋아요.

## 요청 직렬화 — 워터폴에 RTT가 곱해지는 구조

앞 응답을 받아야 다음 요청의 주소나 인자를 알 수 있으면 두 요청은 직렬이에요. 예를 들어 목록 API가 상품 ID를 준 뒤에야 상세 API를 호출할 수 있으면 왕복 두 번이 이어져요. 요청 N건이 직렬이면 RTT가 N번 곱해져요.

예를 들어 RTT 250ms에서 HTTP/2 + TLS 1.3 새 연결로 요청 3건을 직렬로 보내면 설정 2왕복과 요청 3왕복을 더해 5왕복이 돼요. 서버 처리를 0ms라고 가정해도 1,250ms가 걸려요.

같은 단계의 요청을 함께 보내면 한 왕복에 묶여요. 두 단계로 나눌 수 있으면 설정 2왕복과 단계 2왕복으로 4왕복, 1,000ms예요. HTTP/1.1로 병렬 요청을 보내려면 연결을 여러 개 열어야 해요. RFC 9113 소개 부분은 HTTP/1.0이 한 연결에서 요청 하나만 처리했고, HTTP/1.1의 파이프라이닝이 동시성 문제를 부분만 해결했다고 설명해요. 그래서 HTTP/1.x 클라이언트는 여러 연결을 쓴다고 해요.

## CDN 엣지 — 적중과 미스의 왕복 비용

AWS 문서는 CloudFront가 요청을 지연 시간이 가장 낮은 엣지 위치로 보낸다고 설명해요. 그 위치에 응답이 있으면 바로 돌려주고, 없으면 오리진에서 가져온다고 적어요. 그래서 적중이면 사용자와 엣지 사이 왕복만 남고, 미스면 엣지와 오리진 사이 왕복이 더해져요.

예를 들어 엣지 RTT를 20ms로 가정하면, 적중한 요청 한 번은 약 20ms, 미스한 요청 한 번은 엣지와 오리진 사이 250ms가 더해져 약 270ms예요. 적중률이 낮은 API는 엣지를 써도 오리진 거리가 그대로 드러나요. 캐시 규칙을 맞추는 방법은 [HTTP 캐시](/m/http-caching) 글에서 다뤄요.

## 리전 배치 — 데이터가 있는 곳과 사용자 사이 거리

엣지는 캐시할 수 있는 응답을 가까이 두지만, 쓰기와 개인 데이터는 주 DB가 있는 곳까지 왕복해야 해요. AWS 문서는 리전이 서로 격리되어 있고, 리소스를 리전 사이에 자동으로 복제하지 않는다고 설명해요. 해외 리전을 추가하면 어느 데이터를 어디에 둘지 따로 정해야 하는 이유예요.

읽기가 많은 데이터는 가까운 곳에 복제본을 두는 편이 좋아요. 쓰기가 많은 데이터는 주 리전 한 곳에 두고, 가까운 복제본은 읽기 전용으로 쓰는 편이 좋아요. 복제본에서 읽을 때 생기는 문제는 [복제 지연](/m/replication-lag) 글에서 다뤄요.

## FE 체크 포인트 — 연결 힌트와 요청 순서

### preconnect — 필요한 출처만 미리 연결

MDN은 preconnect가 DNS와 TCP, HTTPS라면 TLS까지 미리 수행해서 이후 요청을 빠르게 한다고 설명해요. web.dev는 중요한 제3자 출처에 일찍 연결하면 100~500ms를 줄일 수 있다고 적어요.

web.dev는 브라우저가 10초 안에 쓰이지 않는 연결을 닫는다고 설명해요. 그래서 곧 쓸 출처에만 preconnect를 두고, 개수를 제한하는 편이 좋아요. 필요 이상으로 많이 열면 다른 중요한 리소스가 늦어질 수 있어요.

폰트처럼 CORS 모드로 받는 리소스는 crossorigin 속성을 같이 써야 해요. web.dev는 이 속성을 빼면 브라우저가 DNS 조회만 한다고 설명해요.

### dns-prefetch — DNS 조회만 미리

MDN은 dns-prefetch가 DNS 해석만 미리 수행한다고 설명해요. 연결 설정까지 미리 하지 않아서, TLS 비용이 부담되는 출처에는 가벼운 선택이에요.

### 요청 순서 — 앞 응답 없이 보낼 수 있는 요청 먼저

화면에 필요한 요청 중 URL과 인자를 이미 아는 것은 함께 보내요. 한 요청의 응답을 받은 뒤에만 다른 요청을 시작하는 코드는 단계 수만큼 왕복을 더해요. 여러 호출을 한 번에 받는 방법은 [API 조립](/m/api-composition) 글에서 다뤄요.

### 연결 시간 확인 — 개발자 도구 타임라인

개발자 도구의 요청 타임라인에서 연결 설정 구간과 서버 응답 대기 구간을 나눠 보세요. 연결 구간이 길면 연결 힌트나 재사용을, 대기 구간이 길면 서버 처리나 엣지 적중을 먼저 봐요.

## 시뮬레이터 안내

아래 시뮬레이터에서 RTT, 프로토콜, 연결 상태, 엣지 적중, 요청 수, 단계 수, 병렬 여부를 바꿔 보세요. 기본값(RTT 250ms, HTTP/2 + TLS 1.3, 새 연결, 요청 3건, 단계 2, 병렬)은 1,060ms예요. 요청마다 서버 처리는 30ms로 고정했고, 엣지 RTT는 20ms로 가정했어요. 수치는 감을 잡기 위한 예시예요. 실측 RTT가 아니에요.

아래 표는 같은 요청 설정에서 프로토콜과 연결 상태만 바꾼 결과예요. 프로토콜 차이가 설정 왕복에서 나는지, 요청 수에서 나는지 비교해 보세요. HTTP/1.1의 병렬 요청은 연결을 여러 개 여는 방식을 단순하게 흉내 낸 것이고, 연결 수 상한은 모델에 넣지 않았어요.

## 정리 — 거리 · 연결 · 요청 순서별 줄이기

- 거리는 엣지 적중과 리전 배치로 줄여요. 서버 코드로는 줄지 않아요.
- 연결 설정은 연결 재사용과 세션 재개, 그리고 HTTP/3 같은 프로토콜 선택으로 줄여요.
- 직렬 요청은 같은 단계끼리 묶고, 필요하면 BFF로 한 번에 받아요.
- 연결 힌트는 곧 쓸 출처에만 preconnect를 두고, 나머지는 dns-prefetch로 가볍게 해요.
