주문 목록 URL이 `/orders/1042`처럼 번호로 끝나면, 다음 주문이 `1043` 이라는 걸 누구나 짐작할 수 있어요. 번호를 바꿔 넣어 다른 사람의 주문이 열리는지 확인해 보고 싶어지는 자리이기도 해요. 화면에서는 방금 만든 주문에 임시 ID를 붙여 보여 주고 싶은데, 서버 번호가 올 때까지 기다려도 될지 애매하기도 하죠.

이 글에서는 ID를 어떤 방식으로 만들지 정하는 기준을 정리해요. 자동 증가 번호, UUID v4와 v7, 64비트 정수를 나란히 놓고, 각각이 추측, 정렬, 인덱스 삽입, JS 정밀도에서 어떻게 다른지 봐요. 아래 시뮬레이터에서 같은 조건의 ID 목록을 방식별로 만들어 볼 수 있어요.

## 자동 증가 번호 — 빈 번호와 추측 가능성

PostgreSQL의 시퀀스는 `nextval`로 번호를 하나씩 받아요. 이 번호는 트랜잭션이 중단돼도 되돌아가지 않아요. 다른 트랜잭션이 기다리지 않도록 한 설계 때문이에요. 그래서 롤백된 주문이 있으면 번호에 구멍이 남아요. PostgreSQL 문서도 시퀀스 객체로는 빈 번호 없는 할당을 만들 수 없다고 설명해요.

```sql
CREATE TABLE orders (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY
  -- 이하 생략
);
```

자동 증가 번호는 이어지기 때문에 추측도 쉬워요. 번호 하나를 알면 앞뒤 번호를 바로 시도할 수 있어요. 번호를 숨기는 것만으로는 충분하지 않아요. 번호가 무작위여도 서버가 "이 요청자가 이 주문의 주인인가"를 확인하지 않으면 같은 문제가 생겨요.

## 노출 위험 — 예측 가능한 ID와 권한 검사

OWASP는 객체 ID를 바꿔 다른 사람의 자원에 접근하는 취약점을 IDOR(Insecure Direct Object Reference)이라고 불러요. 원인은 객체 단위 권한 검사가 빠진 것이에요. OWASP 치트 시트는 ID가 예측 가능하든 추측 불가능하든 권한 없는 접근을 막으라고 말해요.

그래서 ID 방식과 권한 검사는 따로 생각해야 해요.

| 질문                                | ID 방식으로 해결되나요?                            | 권한 검사가 필요하나요? |
| ----------------------------------- | -------------------------------------------------- | ----------------------- |
| 다음 번호를 맞힐 수 있나요?         | 무작위 ID 면 어려워져요                            | 네, 항상 필요해요       |
| 남의 주문 URL을 알 수 있나요?       | 무작위 ID 면 발견이 어려워져요. 링크 유출은 남아요 | 네, 항상 필요해요       |
| 권한 없는 요청을 서버가 거절하나요? | 아니요. 이건 서버 코드의 책임이에요                | 네                      |

FE가 권한을 맞춰 줄 수는 없어요. 화면에서 숨긴 버튼은 주소창으로 들어오는 요청을 막지 못해요.

## UUID 버전 — v4 무작위와 v7 시간 순

RFC 9562는 UUID의 여러 버전을 정의해요. 자주 쓰는 두 가지는 이래요.

- **UUID v4** 는 무작위 또는 의사 무작위 숫자로 만들어요. RFC 9562는 CSPRNG를 쓰면 예측하기 어렵고 충돌 가능성도 낮다고 설명해요.
- **UUID v7** 은 앞 48비트에 Unix 에포크 기준 밀리초 시각을 넣어요. 그 뒤는 무작위 또는 카운터 값이에요. 시간이 앞에 있어서 생성 순서와 거의 같은 순서로 정렬돼요.

최신 PostgreSQL 문서도 UUID 생성 함수로 v4와 v7을 함께 제공해요. 쓰는 버전에 `uuidv7()`이 있는지는 확인해요. v7은 시간 순 UUID라고 설명해요.

| 방식                    | 값 예시 (형태)             | 어디서 만드나요 | 추측                                    | 정렬                               | 인덱스 삽입                  |
| ----------------------- | -------------------------- | --------------- | --------------------------------------- | ---------------------------------- | ---------------------------- |
| 자동 증가 bigint        | `1042`                     | DB 한 곳        | 쉬워요 (앞뒤 번호)                      | 생성 순서                          | 끝에 붙어요                  |
| UUID v4                 | `3f2b…-4…-…` 무작위        | 어디서나        | 어려워요                                | 생성 순서와 무관해요               | 임의 위치에 들어가요         |
| UUID v7                 | `0195…-7…-…` 시각 + 무작위 | 어디서나        | 시각 부분은 짐작돼요. 나머지는 어려워요 | 밀리초가 다르면 생성 순서와 같아요 | 끝 근처에 모여요             |
| 64비트 정수 (구조 예시) | 시각 + 서버 + 순번 정수    | 서버마다        | 같은 순간 안에서는 쉬워요               | 생성 순서와 같아요                 | 끝에 붙어요 (단일 서버 기준) |

v7은 같은 밀리초 안에서 순서가 보장되지 않아요. 무작위 부분이 순서를 정하기 때문이에요. RFC 9562 §6.2는 rand_a 자리를 같은 밀리초 안의 카운터로 쓰는 방법을 설명해요. 시뮬레이터에서 "같은 밀리초 안에서 카운터 쓰기"를 켜면 이 차이가 사라져요.

## 무작위 키와 B-tree — 삽입 위치가 흩어지는 문제

RFC 9562는 시간 순이 아닌 UUID, 예를 들어 v4는 데이터베이스 인덱스 지역성이 나쁘다고 설명해요. 새로 만든 값들이 인덱스에서 서로 가까이 있지 않아서, 삽입이 매번 임의의 위치로 가야 한다는 뜻이에요. RFC는 이 영향이 B-tree 계열 구조에서 클 수 있다고 말해요. 다만 얼마나 느려지는지 수치는 말하지 않아요. 실제 영향은 테이블 크기와 캐시 상태에 따라 달라서 직접 재 봐야 해요.

시뮬레이터의 "새 값이 들어간 자리" 막대에서 확인해 보세요. 자동 증가와 v7은 뒤쪽에 몰리고, v4는 네 구간에 고르게 흩어져요.

## 여러 서버에서 충돌 없이 만들기 — 조정 없는 생성

자동 증가는 한 DB가 번호를 맡을 때 가장 간단해요. 서버가 여럿이면 이야기가 달라져요. RFC 9562도 자동 증가 방식이 네트워크 너머로 순번을 맞추느라 부담이 된다고 설명해요. UUID는 서로 조정하지 않고도 분산 시스템에서 값을 만들 수 있어요.

그래도 "충돌이 없다"를 보장으로 읽으면 안 돼요. RFC는 충돌 가능성이 낮다고 말할 뿐이에요. v7의 같은 밀리초 안 순서처럼, 생성 방식의 조건을 함께 확인해야 해요.

## 64비트 정수 — JSON 숫자 정밀도와 문자열 계약

PostgreSQL의 `bigint`는 -9223372036854775808부터 9223372036854775807까지 저장해요. 시각과 서버 번호를 합친 64비트 정수 ID는 이 범위 안에 들어가도록 설계해요. 문제는 DB가 아니라 FE 쪽이에요. 앞자리에 시각이 들어가면 값이 금방 아주 커져요.

JavaScript의 `Number`는 IEEE 754 배정밀도 실수예요. MDN은 `Number.MAX_SAFE_INTEGER`가 2의 53제곱에서 1을 뺀 9007199254740991이라고 설명해요. 이 값을 넘는 정수는 정확히 표현되지 않아요. 예를 들어 `9007199254740993`을 `Number`로 읽으면 `9007199254740992`가 돼요.

RFC 8259는 JSON 정수가 `[-(2^53)+1, (2^53)-1]` 범위일 때만 구현끼리 값이 같다고 보장해요. 이 범위 밖의 정수는 상호 운용을 보장하지 않아요. 그래서 큰 정수 ID는 응답에서 문자열로 주는 계약을 세우는 편이 안전해요.

```json
{ "id": "118274339635212288", "status": "paid" }
```

화면은 이 문자열을 그대로 보관하고 그대로 다시 보내요. 숫자 연산을 하거나 `Number()`로 바꾸면 안 돼요. 자동 증가 번호는 대부분 2의 53제곱보다 작아서 괜찮지만, 값이 커지는 순간 같은 문제가 생겨요.

## 클라이언트 UUID — 임시 ID와 멱등성 키

화면에서 주문을 누르자마자 목록에 행을 보여 주고 싶다면, 두 가지 흐름이 있어요.

1. **서버 ID를 기다려요.** 클라이언트는 임시 키로 행을 그리고, 응답의 서버 ID로 바꿔요. 응답이 늦거나 실패하면 임시 행을 어떻게 할지 정해야 해요.
2. **클라이언트가 UUID를 만들어 보내요.** `crypto.randomUUID()`는 v4 UUID를 만들어요. MDN은 이 함수가 암호학적으로 안전한 난수를 쓰고, 보안 컨텍스트(HTTPS 등)에서만 쓸 수 있다고 설명해요.

```js
const orderId = crypto.randomUUID();
await fetch('/orders', {
  method: 'POST',
  headers: { 'Idempotency-Key': orderId, 'Content-Type': 'application/json' },
  body: JSON.stringify({ orderId, items }),
});
```

두 번째 방식에서는 같은 UUID가 재시도 때도 같은 값으로 가요. 서버가 이 값을 기본 키나 멱등성 키로 쓰면 같은 주문이 두 번 생기는 것을 막을 수 있어요. Stripe 문서도 멱등성 키를 직접 만들되 V4 UUID 또는 충분한 무작위성을 가진 문자열을 쓰라고 권해요. 멱등성의 나머지 설계는 [결제 — 이중 결제 막기](/m/payment-idempotency) 글에서 다뤘어요.

임시 ID는 화면 안에서만 쓰세요. 임시 ID로 URL을 만들어 공유하면 서버 ID가 바뀐 뒤 링크가 깨져요.

## 시간 순 ID — 커서 페이지네이션의 정렬 키

목록을 커서로 넘길 때는 정렬 기준이 필요해요. 생성 시각 칼럼만 쓰면 같은 시각의 행이 여러 개일 때 순서가 흔들려요. 그래서 보통 `(created_at, id)`처럼 유일한 값을 덧붙여요. 시간 순 ID를 쓰면 ID 하나로 이 역할을 할 수 있어요.

```sql
SELECT id, total
FROM orders
WHERE id < :last_id
ORDER BY id DESC
LIMIT 20;
```

이 방식은 v7처럼 앞부분이 시각 순인 ID 에서만 자연스러워요. v4로 정렬하면 순서가 생성 순서와 무관해서 최신순 목록이 되지 않아요. 새로 생긴 행이 이미 지나간 구간에 끼어들면 그 행은 목록을 넘기는 동안 보이지 않아요. 같은 밀리초 안의 순서 문제는 여기서도 그대로 남아요. 카운터를 쓰거나, 정렬을 `(시각, id)`로 두는 편이 안전해요. 커서 설계는 [페이지네이션](/m/pagination) 글을 함께 보세요.

## FE 체크 포인트

**ID는 문자열로 받고 문자열로 보내요.** 큰 정수 ID를 `Number`로 바꾸는 코드가 한 줄이라도 있으면 값이 조용히 바뀔 수 있어요. 타입을 `string`으로 정하고, 숫자 비교가 필요하면 서버 정렬에 맡겨요.

**URL의 ID는 권한 검사를 전제로 해요.** 무작위 ID를 써도 서버가 404나 403으로 응답하는지 확인해요. 화면에서 숨긴 것을 보안으로 여기지 않아요.

**임시 ID는 화면 상태에만 두어요.** 서버 응답을 받으면 임시 ID를 서버 ID로 바꾸고, 같은 행을 다시 그리지 않도록 키를 맞춰요.

**재시도할 요청에는 UUID 멱등성 키를 붙여요.** 같은 요청을 다시 보낼 때 같은 키를 쓰세요. 새 키를 만들면 중복 생성을 막을 수 없어요.

**정렬이 필요한 목록은 정렬 키를 확인해요.** 커서가 시간 순 ID에 기대는지, 아니면 `(시각, id)` 조합을 쓰는지 API 문서에 적어 두세요.

## 정리 — ID 방식별 추측 · 정렬 · 삽입 비용

자동 증가는 단순하고 정렬이 깔끔하지만, 빈 번호가 생기고 추측이 쉬워요. UUID v4는 무작위라 분산 생성에 좋지만 인덱스 삽입이 흩어져요. UUID v7은 시간 순이라 인덱스와 커서에 잘 맞아요. 64비트 정수는 JS에서 정밀도가 깨지니 문자열 계약이 필요해요.

어떤 방식을 쓰든 권한 검사는 따로 있어야 해요. 화면에서 임시 ID를 만들 때는 클라이언트 UUID를 멱등성 키로 같이 보내면 재시도에도 안전해요.
