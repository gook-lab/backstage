관리자 화면에서 "정산 실행" 버튼을 두 사람이 거의 동시에 눌렀어요. 정산은 두 번 돌았고, 서버가 두 대라서 그렇다고 해요. 한 번만 돌게 하려면 어떻게 해야 할까요?

이 글은 서버 여러 대가 같은 작업을 겹쳐 실행하지 않게 막는 방법을 정리해요. 분산 락(distributed lock), 리스(lease), 펜싱 토큰(fencing token)이 핵심 단어예요. 먼저 짚을 점은, 락은 작업이 겹치는 시간을 줄일 뿐이라는 거예요. 결과가 한 번만 남으려면 저장소가 중복을 거절하도록 짜야 해요.

시뮬레이터에서 서버 두 대의 실행을 틱 단위로 돌려 볼 수 있어요. 틱은 시간의 한 칸이고, 실제 밀리초와는 관계가 없어요.

## 프로세스 뮤텍스 — 서버 한 대 안에서만 막히는 이유

서버 한 대에서는 메모리에 "지금 실행 중" 플래그를 두고 막을 수 있어요. 뮤텍스나 세마포어가 그런 도구예요. 문제는 이 플래그가 프로세스 안에만 있다는 점이에요.

서버 A와 서버 B는 서로의 메모리를 보지 못해요. 그래서 두 서버 모두 "나만 실행 중"이라고 판단하고 본문을 돌려요. 시뮬레이터의 "프로세스 뮤텍스" 방식은 같은 서버 안에서만 막히고, 다른 서버의 실행은 그대로 통과해요.

## 유일 제약 — 실행 키 한 줄만 저장하기

정산마다 실행 키를 정해요. 예를 들어 `settlement:2026-11-23`처럼 기준 날짜로 만들어요. 이 키에 유일 제약을 걸면 첫 INSERT만 성공하고 두 번째 INSERT는 실패해요.

PostgreSQL 문서는 유일 제약이 열 하나 또는 열 묶음의 값이 테이블의 모든 행에서 유일하도록 보장한다고 설명해요. 서버가 몇 대든 같은 DB의 같은 제약을 보기 때문에, 서버 수와는 상관없이 한 행만 남아요.

이 방식의 대가는 두 번째 실행이 본문을 이미 돌렸을 수 있다는 점이에요. 유일 제약은 저장만 막아요. 본문이 외부 정산 API를 호출했다면 그 호출은 막지 못해요. 이 차이는 아래 "멱등 작업" 절에서 다뤄요.

## 행 잠금 — 같은 행을 기다리게 하기

정산 대상 행을 `SELECT ... FOR UPDATE`로 가져오면, 같은 행을 바꾸려는 다른 트랜잭션은 기다려요. PostgreSQL 문서는 FOR UPDATE가 가져온 행을 갱신할 것처럼 잠그고, 현재 트랜잭션이 끝날 때까지 다른 트랜잭션을 막는다고 설명해요.

PostgreSQL 문서도 긴 트랜잭션을 열어 두는 것은 좋지 않다고 설명해요. 트랜잭션을 여는 규칙은 [트랜잭션 · 락 · 데드락](/m/transactions)에서 본 것과 같아요.

## advisory lock — 이름 있는 락을 DB에 두기

PostgreSQL의 advisory lock은 테이블이 아니라 애플리케이션이 정한 이름에 거는 락이에요. 서버 여러 대가 같은 DB에 붙어 있으면 같은 이름을 공유할 수 있어요. 같은 배치를 한 번에 하나만 돌리는 선택은 [배치 작업](/m/batch-jobs)의 동시 실행 절에서 다뤄요. 여기서는 고르는 기준만 짚어요.

- `pg_try_advisory_lock`은 잠글 수 없으면 기다리지 않고 false를 돌려준다고 문서에 나와요.
- 세션 수준 락은 명시적으로 풀거나 세션이 끝날 때까지 유지된다고 설명해요.
- 세션 수준 락은 그 트랜잭션이 롤백돼도 남아요. 그래서 획득과 해제를 짝으로 설계해야 해요.

## Redis 락 — SET NX PX로 잡고 만료에 맡기기

Redis 공식 분산 락 페이지는 가장 단순한 방법을 이렇게 설명해요. 키를 만들고, 만료 시간을 줘서 결국 풀리게 하고, 끝나면 키를 지워요. 단일 인스턴스에서는 `SET resource_name my_random_value NX PX 30000`처럼 써요.

- SET 명령 페이지는 NX가 키가 없을 때만 값을 쓴다고 설명해요.
- PX는 만료 시간을 밀리초 단위로 준다고 설명해요.
- 키가 이미 있으면 NX 설정은 실행되지 않아요. 시뮬레이터의 B1이 건너뛰는 이유예요.

Redis 키의 기본은 [콘서트 좌석 선점](/m/concert-seats)에서 이미 다뤘어요. 여기서는 락으로 쓸 때의 한계를 봐요. 분산 락 페이지는 Redis 복제가 비동기라서, 마스터가 쓰기를 복제본에 보내기 전에 죽으면 두 클라이언트가 같은 락을 잡을 수 있다고 설명해요.

### Redlock — 여러 Redis 노드와 그 논쟁

분산 락 페이지는 Redlock이 여러 독립 Redis 인스턴스에 같은 방식으로 잡아 과반을 얻는 알고리즘이라고 설명해요. 같은 페이지는 이 알고리즘이 프로세스들의 로컬 시계가 비슷한 속도로 흐른다는 가정에 기댄다고 밝혀요.

Kleppmann은 Redlock을 분석한 글에서 프로세스가 멈추는 경우 알고리즘이 실패할 수 있다고 지적해요. 분산 락 페이지도 이 분석 글과 반론을 함께 링크해요. 두 자료의 범위만 보면, Redlock의 안전성은 가정과 조건에 따라 달라져요. 이 글은 Redlock을 전제로 설계하지 않아요. 정산처럼 한 번만 반영돼야 하는 작업이라면, 저장소가 판단하게 하는 편이 좋아요. 이유는 아래 펜싱 토큰 절에서 설명해요.

## 락 해제 — 내 값일 때만 지우기

분산 락 페이지는 DEL만 쓰면 클라이언트가 다른 클라이언트의 락을 지울 수 있다고 설명해요. 예를 들면 이래요. 작업이 락 유효 시간보다 오래 걸리면 락은 이미 만료돼요. 그사이 다른 클라이언트가 락을 잡았는데, 처음 클라이언트가 끝나면서 DEL을 보내면 새 락이 지워져요.

그래서 잡을 때 무작위 값을 함께 저장하고, 해제할 때 값이 같을 때만 지워요. 확인과 삭제는 한 명령으로 묶여야 해요. 페이지는 Redis 8.4에 도입된 DELEX 명령을 쓰거나, 이전 버전에서는 같은 동작을 하는 Lua 스크립트를 쓴다고 설명해요.

시뮬레이터의 "Redis 락 · 해제를 DEL로"와 "Redis 락 · 값 비교 해제"를 같은 사건에서 비교해 보세요.

## 펜싱 토큰 — 만료 뒤 늦은 쓰기를 저장소가 거절하기

Kleppmann의 예시는 이래요. 락 보유자가 가비지 컬렉션 같은 이유로 멈추는 동안 리스가 만료돼요. 다른 클라이언트가 락을 잡고 쓰기를 끝내요. 그다음 멈췄던 보유자가 깨어나서 옛 데이터로 쓰면, 저장소에 틀린 값이 남아요.

해결은 증가하는 번호를 붙이는 거예요. 락 서비스가 락을 줄 때마다 더 큰 번호(펜싱 토큰)를 발급하고, 클라이언트는 쓰기 요청에 그 번호를 함께 보내요. 저장소는 이미 본 번호보다 작은 쓰기를 거절해요. Kleppmann은 이 방식이 저장소가 토큰을 능동적으로 확인하고, 토큰이 뒤로 가는 쓰기를 거절해야 한다고 설명해요.

Redis 분산 락 페이지도 펜싱 토큰을 구현하라고 권해요. 같은 페이지는 락의 수명을 늘리는 방법도 있지만, 락을 잡은 프로세스가 살아 있는 동안 락이 유지된다고 가정하지 말라고 덧붙여요.

세 방식을 비교하면 이래요.

| 방식                | 만료 뒤 늦은 쓰기              | 저장소가 확인해야 하나요    | 시뮬레이터 사건                  |
| ------------------- | ------------------------------ | --------------------------- | -------------------------------- |
| 락만 (값 비교 해제) | 그대로 반영될 수 있어요        | 아니요                      | 일시 정지 후 만료 · 남의 락 삭제 |
| 펜싱 토큰           | 옛 토큰이면 거절돼요           | 예. 가장 큰 토큰을 기록해요 | 일시 정지 후 만료                |
| DB 유일 제약        | 같은 실행 키가 있으면 거절돼요 | 예. 유일 제약이 막아요      | 모든 사건                        |

펜싱 토큰을 DB에서 쓰는 모양은 이런 식이에요. 예시 SQL이고, 컬럼 이름은 설계에 따라 달라요.

```sql
-- 예시: 저장된 토큰보다 큰 쓰기만 통과해요
UPDATE settlement SET amount = $1, last_token = $2
WHERE run_key = $3 AND last_token < $2;
```

영향받은 행 수가 0이면 쓰기가 거절된 거예요. 이 판단은 [트랜잭션 · 락 · 데드락](/m/transactions)의 조건부 UPDATE와 같은 규칙이에요.

## 멱등 작업 — 락보다 먼저 볼 실행 키

락은 실행이 겹치는 시간을 줄일 뿐이에요. 락이 풀린 틈에 작업이 다시 돌아도 결과가 같도록 짜면, 두 번 돌아도 한 번만 남아요. 작업 입력에 실행 키를 두고, 저장할 때 유일 제약으로 막는 방식이 여기에 해당해요.

정산 결과가 DB에만 쓰인다면, 락을 먼저 고르기보다 유일 제약을 먼저 두는 편이 좋아요. 락은 틈을 완전히 없애지 못하지만, 유일 제약은 저장 시점에 한 행만 통과시켜요.

본문이 외부 API를 부른다면 이야기가 달라져요. 저장소의 유일 제약은 외부 호출을 막지 못해요. 그 호출에는 상대 API의 멱등성 키가 필요해요. 이 규칙은 [결제 멱등 처리](/m/payment-idempotency)에서 다뤄요.

## 예약 작업 — 서버마다 같은 cron이 도는 문제

서버마다 같은 스케줄러를 띄우면 같은 시각에 모든 서버가 작업을 시작해요. 락이 없으면 작업이 여러 번 돌아요. 이것이 예약 작업이 서버 수만큼 도는 원인이에요.

해결은 두 가지예요. 스케줄러를 한 곳에서만 띄우거나, 발화 자체를 작업 한 건으로 만들어 실행 키를 붙여요. 실행 키는 "언제의 정산인지"를 나타내는 기준 시각으로 정해요. 기준 시각은 모든 서버에서 같으므로, 같은 키가 두 번 저장되지 않아요. 이 기준은 [배치 작업](/m/batch-jobs)의 스케줄 실행 절에서 다뤄요.

## FE 체크 포인트

- 버튼을 한 번만 눌리게 비활성화해도, 다른 사람이나 다른 탭의 요청은 막지 못해요. 중복 방지는 서버가 해요.
- 실행 요청에 같은 실행 키가 이미 있으면, 서버는 새 작업을 만드는 대신 기존 작업을 돌려주는 편이 좋아요. 예시 응답은 이래요.

```json
{ "runKey": "settlement:2026-11-23", "jobId": "job_8f2", "status": "running", "created": false }
```

- `created`가 false이면 "이미 실행 중인 정산이 있어요"라고 보여 주고, 같은 작업의 진행률을 조회하세요. 작업 상태 조회는 [배치 작업](/m/batch-jobs)의 202 흐름과 같아요.
- 상태가 `running`이면 버튼을 다시 누르게 하지 마세요. 새 요청은 같은 작업을 돌려받아요.
- 화면에는 누가 시작했는지, 언제 시작했는지를 함께 보여 주세요. 다른 사람이 실행한 작업이라는 점이 드러나야 해요.

## 시뮬레이터 안내

시뮬레이터에서 방식과 사건을 바꿔 가며 다음 순서로 보세요.

1. "락 없음"과 "두 서버 동시 실행"을 고르세요. 실행 횟수가 2이고, 반영된 쓰기도 2인 것을 보세요.
2. "프로세스 뮤텍스"로 바꾸세요. 서버가 다르면 여전히 2인 것을 보세요.
3. "Redis 락 · 값 비교 해제"와 "락 보유자 일시 정지 후 만료"를 고르세요. A1의 쓰기가 뒤늦게 반영되는 칸을 찾으세요.
4. "Redis 락 + 펜싱 토큰"으로 바꾸세요. A1의 쓰기가 거절되는 칸을 확인하세요.
5. "락 해제 시 남의 락 삭제"에서 "DEL" 방식과 "값 비교" 방식의 기록을 비교하세요.

타임라인의 "반영"은 저장소에 실제로 쓴 것이고, "거절"은 저장소가 막은 것이에요. 맨 아래 "락 보유자" 줄은 그 틱에 유효한 락 보유자를 보여 줘요. 수치는 모델 안의 예시예요.

## 정리 — 락 · 펜싱 토큰 · 유일 제약 역할 분담

서버 여러 대에서 한 번만 실행하려면 세 가지를 나눠 생각하면 돼요. 같은 작업이 겹쳐 도는 것을 줄이는 락, 늦게 온 쓰기를 거절하는 펜싱 토큰, 그리고 저장할 때 한 건만 남기는 유일 제약이에요. 셋 중 최종 판단은 저장소가 해야 해요.

백그라운드로 옮겨 실행하는 방법은 [백그라운드 작업](/m/background-jobs)에서 이어서 볼 수 있어요.
