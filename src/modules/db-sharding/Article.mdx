주문 DB를 회원 기준으로 여러 대에 나누면 회원 한 명의 주문 조회는 빨라져요. 그런데 관리자 화면의 "전체 주문 최신순" 목록은 느려지고, 페이지 이동도 이상해질 수 있어요. 이 글은 DB를 여러 서버로 나눌 때 샤드 키를 어떻게 고르는지, 샤드 키가 없는 조회가 왜 어려운지 정리해요.

아래 시뮬레이터에서 분할 방식과 조회 종류를 바꿔 가며 조회한 샤드 수와 합칠 행 수를 직접 볼 수 있어요. 시뮬레이터의 수치는 예시예요.

## 복제와 분할 — 같은 데이터를 여러 벌 두기와 나눠 두기

복제는 같은 데이터를 여러 서버에 두는 거예요. 읽기 요청을 여러 곳에 나눌 수 있지만, 저장되는 데이터의 양은 그대로예요. 복제본이 주 DB를 따라오는 간격은 [복제 지연](/m/replication-lag)에서 다뤘어요.

분할은 데이터를 조각으로 나눠 서로 다른 곳에 두는 거예요. 각 조각은 전체의 일부만 가져요. 그래서 저장량과 쓰기를 여러 서버로 넓힐 수 있어요.

| 구분        | 복제                | 분할                            |
| ----------- | ------------------- | ------------------------------- |
| 데이터      | 전체를 여러 벌 둬요 | 조각마다 일부만 둬요            |
| 늘어나는 것 | 읽기 처리량         | 저장량과 쓰기 처리량            |
| 대표 문제   | 복제 지연           | 샤드 키 선택과 샤드를 넘는 조회 |

MongoDB 문서는 샤딩에서 각 샤드를 복제 세트(replica set)로 배포해야 한다고 설명해요. 그래서 실제 운영에서는 둘을 함께 써요.

## 파티셔닝과 샤딩 — 한 DB 안의 나눔과 서버 여럿에 나누기

PostgreSQL 선언적 파티셔닝은 테이블을 RANGE, LIST, HASH 방식의 파티션으로 나눠요. 파티션은 일반 테이블이고, 질의 조건에 맞지 않는 파티션은 플래너가 실행 계획에서 빼요. 문서는 이를 파티션 프루닝이라고 설명해요.

파티션을 외부 테이블로 두면 다른 서버에 둘 수도 있어요. 문서는 이때 외부 테이블의 내용이 파티션 규칙을 지키는 책임이 사용자에게 있다고 설명해요. 이 지점부터는 파티셔닝이 샤딩에 가까워져요.

| 구분      | 파티셔닝 (PostgreSQL)              | 샤딩 (MongoDB · Citus 등)                           |
| --------- | ---------------------------------- | --------------------------------------------------- |
| 조각 위치 | 같은 테이블 아래 파티션 테이블     | 샤드마다 다른 서버                                  |
| 라우팅    | DB 플래너가 파티션 프루닝으로 고름 | mongos · Citus 코디네이터 같은 라우터가 샤드를 고름 |
| 유일 제약 | 파티션 키 열을 모두 포함해야 해요  | 샤드 안에서만 확인돼요 (설계 판단)                  |

파티션 키를 포함하지 않으면 유일 제약을 만들 수 없어요. 문서는 각 파티션의 인덱스가 자기 파티션 안에서만 유일성을 강제할 수 있기 때문이라고 설명해요. 같은 이유로 샤드 사이의 유일성도 따로 설계해야 해요. 이건 설계 판단이에요.

## 샤드 키 고르기 — 함께 읽는 데이터를 같은 샤드에

샤드 키는 행이 어느 샤드에 갈지 정하는 열이에요. MongoDB 문서는 샤드 키 값으로 문서를 나누고, 샤드 키 조건이 있는 조회를 해당 샤드로 보낸다고 설명해요.

Citus 문서는 분배 열(distribution column)을 고르는 일이 가장 중요한 모델링 결정 가운데 하나라고 설명해요. 같은 분배 열 값을 가진 행은 테이블이 달라도 같은 노드에 모여요. 그래서 그 값 안에서 하는 조인과 질의를 한 노드에서 끝낼 수 있어요. 멀티테넌트 서비스에서 테넌트 id를 쓰는 이유도 같아요. 격리 기준은 [멀티테넌시](/m/multi-tenancy)에서 다뤘어요.

| 후보 샤드 키 | 잘 되는 조회                    | 어려운 조회                            |
| ------------ | ------------------------------- | -------------------------------------- |
| 회원 id      | 회원 한 명의 주문 (샤드 한 곳)  | 날짜 범위, 전체 최신순                 |
| 주문 id      | 주문 한 건                      | 회원 한 명의 주문 목록 (여러 샤드)     |
| 주문 시각    | 최근 기간 범위 (범위 분할일 때) | 회원 조회, 최신 쓰기가 한 샤드에 몰림  |
| 주문 상태    | 없음                            | 값 종류가 적어 샤드를 많이 쓰지 못해요 |

Citus 문서는 상태처럼 값 종류가 적은 열은 분배 열로 좋지 않다고 설명해요. 값 종류가 적으면 샤드를 나눌 수 있는 수도 제한돼요. 시각도 그대로 분배 열로 쓰지 말라고 권해요. 해시로 나누면 시간이 샤드에 흩어져서, 기간 조회가 여러 샤드를 물어야 해요.

샤드 키는 나중에 바꿀 수도 있어요. MongoDB 5.0부터 샤드 키를 바꾸는 재샤딩이 가능하다고 설명해요. 다만 문서는 샤드 키 선택이 확장성과 성능 문제를 피하는 데 중요하다고 권해요.

## 범위 · 해시 · 디렉터리 분할 — 가까운 값을 묶을지, 고르게 흩을지

범위 분할은 샤드 키 값이 가까운 문서를 같은 청크나 샤드에 모아요. MongoDB 문서는 범위 샤딩이 가까운 값을 찾는 조회에 효율적이라고 설명해요. 다만 값이 계속 커지는 키는 가장 큰 청크에 삽입이 몰린다고 설명해요.

해시 분할은 키의 해시 값으로 나눠 고르게 흩어요. MongoDB 문서는 해시 샤딩이 데이터를 더 고르게 나누는 대신, 범위 조회가 여러 샤드로 퍼진다고 설명해요. 같은 키 값은 같은 해시 값이 되므로 같은 샤드로 가요. 그래서 한 회원의 주문도 한 샤드에 모여요.

디렉터리 분할은 키 값과 샤드를 짝지은 표를 따로 둬요. Vitess 문서는 이 표를 룩업 테이블로 두는 룩업 vindex를 설명해요. 표만 바꾸면 키를 다른 샤드로 옮길 수 있어요. 대신 문서는 룩업 테이블 때문에 삽입과 삭제마다 쓰기가 한 번 더 생기고, 읽기도 한 번 더 찾는다고 설명해요.

| 방식     | 같은 값을 모으는 힘 | 쏠림                      | 샤드 수를 바꿀 때                  | 조회 비용                      |
| -------- | ------------------- | ------------------------- | ---------------------------------- | ------------------------------ |
| 범위     | 좋아요              | 값이 커지는 키에서 쏠려요 | balancer가 청크를 옮겨요           | 범위가 샤드 한두 곳에 걸려요   |
| 해시     | 약해요              | 고르게 흩어져요           | 대부분 키가 옮겨가요 (아래 재샤딩) | 범위 조회가 여러 샤드로 퍼져요 |
| 디렉터리 | 표 설계에 따라요    | 표 설계에 따라요          | 표를 바꿔 옮겨요                   | 룩업 한 번이 더 필요해요       |

PostgreSQL의 LIST 파티션은 값 목록으로 나누는 같은 발상이에요. 이 글에서는 한 DB 안의 파티션 이야기라서, 샤드 수를 바꾸는 문제와는 따로 봐요.

## 샤드 키가 없는 조회 — 모든 샤드에 묻고 합치기

샤드 키 조건이 없는 질의는 모든 샤드로 나가요. MongoDB 문서는 이를 브로드캐스트 연산이라고 부르고, scatter/gather 질의는 오래 걸릴 수 있다고 설명해요. Vitess 문서도 보조 인덱스가 없으면 모든 샤드에 질의를 흩뿌려야 한다고 설명해요.

### 정렬과 페이지 — 샤드마다 상위 행을 받아 합치기

MongoDB 문서는 정렬을 각 샤드에서 먼저 수행하고, mongos가 그 결과를 받아 합친다고 설명해요. limit은 샤드로 넘긴 뒤 다시 적용해요. 반면 skip은 샤드로 넘기지 못해서 mongos가 결과를 받은 뒤 건너뛰어요. limit과 skip을 함께 쓰면 샤드에는 둘의 합을 넘긴다고 설명해요.

그래서 전체 최신순 목록의 페이지 번호가 커지면, 샤드마다 받아야 하는 행도 같이 커져요. 1페이지는 샤드마다 20건, 5페이지는 샤드마다 100건을 올려야 해요.

| 조회 (샤드 4개, 예시)       | 조회한 샤드 | 합칠 행 | 화면에 보여 주는 행 |
| --------------------------- | ----------- | ------- | ------------------- |
| 회원 한 명의 최신 주문 20건 | 1개         | 20건    | 20건                |
| 전체 최신순 1페이지         | 4개         | 80건    | 20건                |
| 전체 최신순 5페이지         | 4개         | 400건   | 20건                |
| 최근 2% 날짜 범위           | 4개         | 400건   | 20건                |

설계 판단으로는, 관리자 목록을 깊은 페이지 번호로 열어 두지 않는 편이 좋아요. 샤드 수가 늘수록 합쳐야 할 행도 함께 늘어요. 커서로 다음 페이지를 이어 가는 방식은 [페이지네이션](/m/pagination)에서 다뤘어요. 다만 샤드마다 마지막 위치가 달라서, 커서도 샤드별 위치를 담아야 해요. 이건 설계 판단이에요.

## 샤드를 넘는 쓰기와 ID — 트랜잭션과 번호표를 샤드마다 따로 두지 않기

주문과 재고가 서로 다른 샤드에 있으면 한 DB 트랜잭션으로 묶을 수 없어요. Vitess 문서는 룩업 테이블 갱신을 2PC 없이 일관되게 맞추려고 잠금과 세션 순서를 쓴다고 설명해요. 2PC 없이 맞추는 방법은 [사가와 보상 작업](/m/saga-compensation)에서 이어서 볼 수 있어요.

샤드마다 자동 증가 번호를 따로 쓰면 서로 다른 샤드에서 같은 번호가 나올 수 있어요. 여러 서버에서 충돌 없이 ID를 만드는 방법은 [분산 ID](/m/distributed-ids)에서 다뤘어요.

## 쏠리는 샤드 — 키 하나에 쓰기가 몰릴 때

MongoDB 문서는 값이 계속 커지는 키를 범위 샤딩하면 가장 큰 청크가 대부분의 삽입을 받는다고 설명해요. 이 경우 해시 샤딩으로 바꾸면 삽입이 여러 샤드에 고르게 퍼져요.

해시로 나눠도 한 회원의 주문이 아주 많으면 그 회원의 샤드는 계속 바빠요. 같은 키는 같은 샤드로 가기 때문이에요. 이 쏠림은 샤드 키를 바꿔도 풀리지 않을 수 있어요. 한 행의 카운터에 쓰기가 몰리는 문제는 [핫 카운터](/m/hot-counters)에서 이어서 볼 수 있어요. 이건 설계 판단이에요.

## 재샤딩과 일관 해싱 — 샤드 수를 바꿀 때 옮기는 키

해시 값을 샤드 수로 나누면(키 % N), N이 바뀔 때 대부분의 키가 다른 샤드로 가요. 정수 키 한 주기를 세어 보면 N에서 N+1로 늘릴 때 옮기는 비율은 정확히 N/(N+1)이에요. 4개에서 5개로 늘리면 80%, 8개에서 9개로 늘리면 약 89%예요.

일관 해싱은 샤드를 해시 링 위에 올리고, 키를 시계 방향으로 가장 가까운 샤드에 둬요. Karger 외 저자의 논문 Consistent Hashing and Random Trees는 기계가 추가되거나 제거될 때 옮겨야 하는 객체의 기대 비율이 균형을 유지하는 데 필요한 최소라고 정의해요. 또 새 버킷이 생길 때 객체가 옛 버킷끼리 옮겨 가지 않는다는 단조성(monotonicity)도 정의해요.

| 방식            | 4 → 5 샤드 | 8 → 9 샤드 |
| --------------- | ---------- | ---------- |
| 나머지 (키 % N) | 80%        | 89%        |
| 일관 해싱       | 20%        | 12%        |

이 표는 키 2만 개를 세어 계산한 예시예요. 샤드당 가상 노드를 400개 두면 1개에서 11개 샤드까지 이론값과의 차이가 1.5%p 안쪽이었어요. 가상 노드가 적으면 같은 계산이 몇 %p씩 흔들려요.

논문은 캐시 서버 집합을 다뤄요. DB를 재샤딩할 때 데이터를 복사하고 전환하는 절차는 다루지 않아요. 이 표는 옮겨지는 키의 비율만 보여 줘요. MongoDB는 balancer가 백그라운드에서 청크를 샤드 사이로 옮겨 분배를 맞춘다고 설명해요.

## 시뮬레이터 안내 — 조회와 분할 조합별 샤드 · 행 · 쏠림

시뮬레이터는 회원 2,000명과 주문 20,000건을 예시로 만들어요. 같은 시드면 같은 결과가 나와요. 이렇게 돌려 보세요.

1. 기본값은 범위 분할, 전체 최신순, 샤드 4개예요. 조회한 샤드 4개와 합칠 행 80건을 확인하세요.
2. "회원 한 명의 최신 주문 20건"으로 바꾸면 샤드 1개에서 끝나고, 합칠 행은 20건이에요.
3. 최근 가입 회원 주문 비율을 90%로 올리세요. 범위 분할은 마지막 샤드에 쏠려서 쏠림이 3.7배가 돼요. 해시 분할로 바꾸면 1.3배 근처로 내려가요.
4. 최신순 페이지를 5로 올리면 샤드마다 100건씩 올라와서 합칠 행이 400건이 돼요.
5. 재샤딩 줄에서 나머지 방식과 일관 해싱이 샤드 하나를 늘릴 때 옮기는 키 비율을 비교하세요.

## FE 체크 포인트 — 목록 응답과 샤드 한계

- 관리자 목록 API가 샤드 키 조건을 받는지 BE에 확인하세요. 받지 않는다면 어떤 색인이나 읽기 모델로 응답하는지 물어보세요.
- 목록이 샤드 수와 페이지 번호에 따라 느려지면 샤드를 넘는 조회를 의심하세요. 응답 시간을 페이지별로 같이 기록하면 원인을 좁히기 쉬워요.
- MongoDB 문서는 샤드 일부가 완전히 내려가도 나머지 샤드의 읽기와 쓰기는 계속될 수 있다고 설명해요. 그래서 일부 샤드 응답이 없을 때 목록이 일부만 보일 수 있어요. 응답에 누락 여부를 알리는 필드가 있는지 확인하는 편이 좋아요. 이건 설계 판단이에요.
- 관리자 검색이나 집계는 샤드 원본을 직접 치지 않는 읽기 모델로 옮기는 편이 좋아요. 옮기는 방법은 [검색 색인 동기화](/m/search-index-sync)에서 다뤘어요.

## 정리 — 샤드 키로 조회를 한 샤드에 두기

샤드 키는 자주 함께 읽는 데이터가 같은 샤드에 모이도록 고르는 게 핵심이에요. 범위는 가까운 값을 묶고, 해시는 고르게 흩고, 디렉터리는 표로 옮겨요. 샤드 키가 없는 목록은 모든 샤드에 묻고 상위 행을 합쳐야 해요. 그래서 관리자 목록은 샤드 원본이 아니라 별도 읽기 모델에서 받는 편이 좋아요.
