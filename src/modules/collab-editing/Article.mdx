같은 문서를 여러 명이 열어 두고 고치면 "저장이 됐는데 내 글이 없어요"라는 일이 생겨요. 같은 줄을 두 사람이 고치면 한 사람 글이 사라져요. 둘 다 남기려면 서버가 단순한 저장 이상의 일을 해야 해요. 이 글에서는 문서 전체를 덮어쓰는 방식이 왜 한계가 있는지, 편집을 연산으로 보내면 무엇이 달라지는지, 그리고 OT와 CRDT가 같은 문제를 어떻게 푸는지 정리해요.

아래 시뮬레이터에서 기준 문서 "회의록"에 두 사용자의 연산을 보내 볼 수 있어요. 방식을 고르면 서버와 두 화면의 최종 문자열이 같은지, 누구 글이 남았는지 바로 보여요. 시뮬레이터는 단순화한 모델이라 실제 제품의 구현과 같지 않아요.

## 전체 덮어쓰기 — 마지막 저장만 남는 이유

문서 전체를 저장 요청으로 보내는 방식은 구현이 가장 단순해요. 두 사람이 같은 기준 문서를 읽고 각자 고친 전체 문서를 보내면, 나중에 도착한 저장이 앞 저장을 통째로 덮어써요. 시뮬레이터에서 "A가 먼저 도착"을 고르고 전체 덮어쓰기를 보면 A의 글이 사라져요.

이 방식은 글이 짧고 한 명만 고치는 문서에는 충분할 수 있어요. 여러 명이 같은 문서를 고치는 순간 나중 저장이 앞 저장을 지워요.

## 버전 거절 — 다른 줄을 고쳐도 충돌로 보는 한계

덮어쓰기를 막는 버전 검사는 [동시 편집 · 낙관적 동시성 제어](/m/concurrent-edits) 글에서 다뤘어요. 문서에 버전 하나만 두면 서버는 "기준 버전이 바뀌었는지"만 봐요. 한 사람이 다른 줄을 고쳤더라도 다른 사람이 먼저 저장했다면 거절당해요.

거절된 쪽은 문서를 다시 받아 고쳐야 해요. 충돌은 막지만 편집이 자주 멈춰요. 줄이나 문단마다 버전을 나누면 거절은 줄어요. 하지만 같은 줄을 고치는 경우는 여전히 거절돼요. 둘 다 남기려면 저장 단위를 문서나 줄보다 작은 변경 하나로 낮춰야 해요.

## 연산으로 보내기 — 삽입 · 삭제 위치를 요청에 담기

편집을 문서 전체가 아니라 연산으로 보내면 서버는 무엇이 바뀌었는지 알아요. 연산은 삽입이나 삭제 하나와 그 위치로 표현해요. 예시 요청은 이래요.

```json
{ "type": "insert", "at": 0, "text": "정리: " }
{ "type": "delete", "at": 1 }
```

`at`은 보낸 사람이 본 기준 문서의 위치예요. 다른 사람의 연산이 먼저 적용되면 같은 `at`이 다른 글자를 가리켜요. 이 어긋남이 이 글의 핵심 문제예요.

## 위치가 어긋나는 문제 — 같은 자리 삽입과 같은 글자 삭제

시뮬레이터의 "위치 그대로 적용" 방식은 `at`을 그대로 써요. 두 사용자가 같은 자리 0에 글을 넣으면, 먼저 들어온 글이 자리를 밀어서 두 번째 글이 엉뚱한 쪽에 들어가요. 같은 글자 "의"를 두 명이 지우면 두 번째 삭제가 밀린 자리의 옆 글자 "록"을 지워요.

| 장면           | 위치 그대로 적용의 결과 (예시 모델)                              |
| -------------- | ---------------------------------------------------------------- |
| 같은 자리 삽입 | 두 화면이 "정리: 오늘 회의록"과 "오늘 정리: 회의록"으로 갈라져요 |
| 같은 글자 삭제 | 두 번째 삭제가 "록"을 지워서 최종 문자열이 "회"만 남아요         |

FE에서는 "내 화면과 다른 사람 화면이 달라요"라는 증상으로 보여요. 응답 코드는 모두 성공이어도 화면이 갈라질 수 있어요.

## 위치 변환 (OT) — 서버가 순서를 정하고 위치를 고쳐요

OT (operational transformation)는 1989년 Ellis와 Gibbs가 GROVE 시스템에서 처음 선보였다고 위키백과는 설명해요. 기본 생각은 편집 연산의 매개변수, 곧 위치를 다른 연산에 맞춰 고치는 것이에요. 위키백과는 이 고치는 함수를 변환 함수라고 불러요.

위키백과의 비교 표는 Jupiter 방식을 "인과 순서 + 중앙 변환 서버"로 적어요. 서버가 연산이 도착한 순서를 정하고, 나중 연산을 먼저 온 연산 기준으로 고쳐 적용하는 구조예요. 시뮬레이터의 위치 변환도 같은 순서를 따라요. 서버는 먼저 온 연산을 그대로 적용하고, 나중 연산의 위치를 고쳐요.

같은 자리 삽입처럼 위치가 같으면 어느 글이 앞에 올지 정하는 규칙이 있어야 해요. 이 모델은 먼저 도착한 쪽을 앞에 둬요. 두 화면이 이 규칙을 같이 써야 같은 문자열로 모여요.

FE가 할 일은 서버가 고쳐 보낸 연산을 받아 화면에 적용하는 것이에요. 내가 보낸 연산을 서버가 어떻게 고쳤는지 응답이나 이벤트로 알 수 있어야 해요.

## 글자 id (CRDT) — 위치 대신 id 사이에 넣기

CRDT (conflict-free replicated data type)는 여러 복사본을 따로 고쳐도 나중에 합치면 같은 값이 되도록 설계한 자료형이에요. 위키백과는 병합 함수가 교환 가능 (commutative), 결합 가능 (associative), 멱등 (idempotent)이어야 한다고 설명해요. 편집기를 만드는 글자 목록 CRDT는 OT의 대안으로 소개돼요.

이 글의 모델은 글자마다 고유 id를 붙여요. 새 글자는 "어느 글자 뒤에 넣을지"를 가리키는 id와 자기 id를 같이 가져요. 같은 자리에 둘이 들어오면 id 순서로 앞뒤를 정해요. 그래서 도착 순서가 바뀌어도 결과가 같아요. 시뮬레이터에서 도착 순서를 바꿔 보면 확인할 수 있어요.

Yjs 공식 문서는 자기 문서를 CRDT라고 소개하고, 모든 변경이 결국 도착하면 문서가 맞춰지며 적용 순서는 상관없다고 설명해요. 이 글의 모델은 Yjs 구현을 옮긴 것이 아니에요. 순서 규칙을 줄인 모델이고, 지운 글자는 실제로 없애지 않고 표시만 해요.

## OT와 CRDT 비교 — 중앙 서버 · 메타데이터 · 오프라인

| 기준          | 위치 변환 (OT)                                         | 글자 id (CRDT)                                                                  |
| ------------- | ------------------------------------------------------ | ------------------------------------------------------------------------------- |
| 중앙 서버     | 중앙 변환 서버가 순서를 정하는 방식이 있어요 (Jupiter) | Automerge는 중앙 서버 없이 다른 기기의 동시 변경을 자동으로 병합한다고 설명해요 |
| 보내는 양     | 연산과 위치만 보내요 (이 모델 기준)                    | 글자마다 id가 붙어 메타데이터가 커질 수 있어요 (이 모델 기준)                   |
| 오프라인 편집 | 되돌아온 연산을 서버 순서에 맞춰 고쳐야 해요           | 상대 변경을 나중에 합쳐도 같은 결과가 나와요                                    |

어느 쪽이 낫다고 고르기보다 기준을 고르는 편이 좋아요. 서버가 순서를 맡을 수 있고 메타데이터를 줄이고 싶으면 OT를 봐요. 서버 없이 합치거나 오프라인 편집을 오래 지원해야 하면 CRDT를 봐요.

## 커서 · 선택 영역 — presence 채널로 분리

커서와 선택 영역은 문서 내용이 아니라 상태예요. Yjs 공식 문서는 awareness로 커서 위치 같은 presence 정보를 보낸다고 설명해요. 이 정보는 문서에 저장하지 않고, 세션 사이에 보관할 필요도 없다고 적어요.

그래서 커서는 편집 연산과 다른 채널로 보내는 편이 좋아요. 연산 기록에 섞으면 커서 움직임마다 기록이 쌓여요. 접속 표시의 하트비트와 만료 기준은 [접속 중 표시 — 하트비트 · TTL · 마지막 접속](/m/presence) 글에서 다뤘어요.

## 기록과 스냅샷 — 재접속 때 따라잡기

편집이 계속 쌓이면 문서 스냅샷과 연산 기록을 같이 둬요. 다시 붙은 클라이언트는 자기가 가진 상태를 서버에 알리고, 서버는 빠진 변경만 골라 보내요. Yjs 공식 문서는 상태 벡터로 상대에게 없는 차이만 주고받아 대역폭을 줄인다고 설명해요.

Automerge 공식 문서는 변경 기록을 남겨서 이전 버전을 보거나 비교할 수 있다고 적어요. 스냅샷만 있으면 "어디까지 반영했는지"를 알기 어려워요. 스냅샷에 마지막 연산 번호를 함께 저장하는 편이 좋아요. 목록을 증분으로 받는 방식은 [오프라인 동기화 — 대기열 재전송과 변경 피드](/m/offline-sync) 글과 같은 원리예요.

## 되돌리기와 권한 — 내 연산에 출처 붙이기

되돌리기 (undo)는 내가 한 연산만 취소해야 해요. 다른 사람의 글까지 되돌리면 협업이 깨져요. Yjs 공식 문서의 UndoManager는 기본으로 출처 (transaction origin)가 없는 변경을 추적하고, `trackedOrigins`로 추적할 변경을 고른다고 설명해요. 연산마다 내 출처를 붙여야 내 변경만 되돌릴 수 있어요.

되돌릴 때도 위치 문제가 남아요. 내가 넣은 글자를 지우는 연산은 그 뒤에 들어온 다른 사람의 연산을 반영한 위치로 보내야 해요. 권한도 같은 자리에서 확인해요. 읽기만 가능한 사용자의 연산은 서버가 거절해야 해요. 권한 기준은 [인가 · 객체 수준 권한](/m/authorization) 글에서 다뤘어요.

## FE 체크 포인트

- 편집하면 연산을 만들어 먼저 화면에 보여 줘요. 실패나 거절이 오면 되돌리는 흐름이 필요해요. 되돌리기 규칙은 [동시 편집 · 낙관적 동시성 제어](/m/concurrent-edits) 글의 낙관적 UI 절과 같아요.
- 서버가 고쳐 보낸 연산을 받아 적용해요. 연산 번호를 받아 두면 화면과 서버가 어디까지 맞았는지 알 수 있어요.
- 커서는 편집 연산과 섞지 않고 presence 채널로 보내요.
- 되돌리기 대상은 내 출처로 추적해요. 다른 사람의 변경을 되돌리는 버튼은 만들지 않는 편이 좋아요.
- 화면이 서버와 다르다는 신호가 오면 문서를 처음부터 다시 받는 경로를 둬요.

## 시뮬레이터 안내

아래 시뮬레이터는 기준 문서 "회의록"에서 두 사용자가 연산을 하나씩 보내는 장면이에요.

- 방식: 전체 덮어쓰기, 위치 그대로 적용, 위치 변환 (OT), 글자 id (CRDT)
- 연산 조합: 같은 자리 삽입, 한쪽 삭제 · 다른 쪽 삽입, 같은 글자 동시 삭제
- 도착 순서: A가 먼저 도착, B가 먼저 도착

결과 표는 서버와 두 화면의 최종 문자열, 그리고 A와 B의 변경이 남았는지 보여 줘요. 두 화면이 같은 문자열인지도 함께 확인해요. 네트워크 지연, 재전송, 여러 연산 묶음은 다루지 않아요.

## 정리 — 저장 단위 · 위치 변환 · 글자 id · 기록 기준

- 저장 단위는 문서 전체보다 연산으로 잡는 편이 좋아요.
- 위치가 어긋나면 서버가 위치를 고치는 위치 변환 (OT)을 봐요. 서버가 순서를 맡을 수 있을 때 맞아요.
- 서버 없이 합치거나 오프라인 편집을 오래 지원해야 하면 글자 id (CRDT)를 봐요.
- 커서는 presence 채널로, 되돌리기는 내 출처로 분리해요.
- 재접속은 스냅샷과 연산 번호로 따라잡아요.
