결제창에서 돌아왔는데 주문 상태가 아직 "결제 대기"예요. 서버는 결제 완료를 언제 알게 될까요?

답은 "사용자 브라우저가 돌아왔을 때"가 아니라 "결제 서버가 우리 서버에 알려 줬을 때"예요. 이 글은 그 통지인 웹훅을 받는 쪽에서 무엇을 조심해야 하는지 정리해요. 아래 시뮬레이터에서 결제 100건을 돌리면서 복귀 유실, 웹훅 유실, 중복, 순서 뒤바뀜을 켜고 끄고, 처리 방식별로 최종 주문 상태가 몇 건 틀리는지 확인해 보세요.

## 브라우저 복귀 — 창을 닫으면 돌아오지 않아요

결제창에서 승인이 끝나면 사용자의 브라우저는 우리 사이트로 돌아와요. 이 복귀 요청은 사용자의 브라우저가 가져오는 것이라서, 사용자가 창을 닫거나 네트워크가 끊기면 우리 서버에 도착하지 않아요. 복귀 화면을 보고 "결제 완료"로 바꾸면, 그 화면을 보지 못한 사용자의 주문은 계속 결제 대기에 남아요.

그래서 복귀는 "지금 결제 결과를 확인하러 가 보세요"라는 신호로만 써요. 완료 여부는 서버가 결제 서버에서 확인한 값으로 정해요. 복귀 값을 어떻게 검증하는지는 [결제 — 이중 결제 막기](/m/payment-idempotency)에서 이어 다뤄요.

## 웹훅 — 서버가 서버에게 보내는 통지

웹훅은 결제 서버가 우리 서버의 정해진 주소로 HTTP 요청을 보내는 방식이에요. 사용자 브라우저를 거치지 않아서, 사용자가 창을 닫아도 와요. 대신 도착 시각과 순서, 횟수가 보장되지 않아요.

| 항목             | 브라우저 복귀                           | 웹훅                                                   |
| ---------------- | --------------------------------------- | ------------------------------------------------------ |
| 누가 보내나      | 사용자의 브라우저                       | 결제 서버                                              |
| 창을 닫으면      | 오지 않아요                             | 와요                                                   |
| 도착 순서 · 횟수 | 한 번이고, 순서가 문제 되지 않아요      | 보장되지 않아요. 중복으로 올 수 있어요                 |
| 진위 확인        | 없어요. 쿼리 값은 누구나 바꿀 수 있어요 | 서명으로 확인해요                                      |
| 완료 판단        | 근거가 될 수 없어요                     | 근거가 될 수 있어요. 필요하면 조회 API로 다시 확인해요 |

Stripe는 웹훅 엔드포인트가 같은 이벤트를 두 번 이상 받을 수 있다고 문서에서 설명해요. 이벤트 순서도 보장하지 않는다고 해요.

## 서명 검증 — 원문과 타임스탬프를 HMAC으로 확인

웹훅 주소는 인터넷에 열려 있어서, 누구나 가짜 "결제 완료" 요청을 보낼 수 있어요. 그래서 요청마다 서명을 붙이고, 서버는 같은 비밀 키로 서명을 다시 계산해서 맞춰 봐요.

- **원문으로 검증해요.** Stripe는 서명 검증에 요청 본문의 원문(raw body)이 필요하다고 문서에서 설명해요. JSON을 파싱했다가 다시 직렬화하면 공백이나 키 순서가 바뀌어서 서명이 맞지 않아요.
- **타임스탬프로 오래된 요청을 막아요.** Stripe는 `Stripe-Signature` 헤더에 타임스탬프를 넣고, 그 타임스탬프가 서명 대상에 포함된다고 해요. 공식 라이브러리의 기본 허용 차이는 5분이에요. 허용 차이를 0으로 두면 최근성 검사가 꺼진다고 문서에 경고해요.
- **토스페이먼츠는 전송 시각을 서명에 넣어요.** 토스 문서에 따르면 `{본문}:{전송 시각}`을 비밀 키로 HMAC-SHA256 해시하고, `tosspayments-webhook-signature` 헤더의 `v1:` 뒤 값을 base64로 디코딩해서 비교해요. 서명은 여러 개가 올 수 있어서 그중 하나라도 맞으면 된다고 해요.

서명이 맞지 않으면 처리하지 말고 4xx로 거절하세요. 서명 검증이 끝나야 요청 내용을 믿을 수 있어요.

## 중복과 순서 — 이벤트 ID로 걸러내고 상태 전이로 막기

같은 이벤트가 두 번 와도 주문은 한 번만 완료돼야 해요. 도착 순서가 바뀌어도 상태가 뒤로 가면 안 돼요.

- **이벤트 ID로 중복을 걸러요.** Stripe는 처리한 이벤트 ID를 기록해 두고, 이미 기록된 이벤트는 처리하지 말라고 권해요. 이벤트 생성 시각(`created`)으로 도착 순서를 판단하지 말라고도 해요. 순서가 중요하면 이벤트 안의 객체 상태나 조회 API로 지금 상태를 확인해요.
- **토스의 전송 ID는 중복 키가 아니에요.** 토스 문서는 `tosspayments-webhook-transmission-id`가 웹훅을 보낼 때마다 새로 발급된다고 설명해요. 중복 처리는 본문의 `eventId`로 하라고 해요.
- **허용된 상태 전이만 적용해요.** 예를 들어 `PENDING → PAID → CANCELED`만 허용하면, 환불 이벤트가 먼저 와도 결제 완료 전에는 취소로 바꾸지 않아요.

여기서 한계가 하나 생겨요. 환불이 먼저 와서 거절했다면, 그 이벤트는 다시 오지 않을 수 있어요. 전이 검사만으로는 주문이 "결제 완료"로 남아 틀려요. 이 문제는 아래 대사로 맞춰요.

## 재시도 — 빠른 2xx 응답과 큐 처리

웹훅을 받지 못하면 결제 서버는 재전송해요. 재전송 기간과 간격은 서비스마다 달라요.

- **Stripe**는 라이브 모드에서 최대 3일 동안 지수 백오프로 다시 보낸다고 문서에서 설명해요.
- **토스페이먼츠**는 웹훅을 10초 이내에 200으로 응답하라고 해요. 실패하면 최대 7회 재전송하고, 최초 전송으로부터 3일 19시간 뒤까지 간다고 해요. 재전송 간격은 1, 4, 16, 64, 256, 1024, 4096분이에요.

이 기간이 우리가 중복 기록을 보관해야 하는 기간이에요. 3일 뒤에 같은 이벤트가 올 수 있으니, 처리한 이벤트 ID를 최소 3일 이상은 지우면 안 돼요.

응답은 빨리 보내야 해요. Stripe 문서도 무거운 로직 전에 2xx를 먼저 돌려주라고 해요.

결제 서버 쪽 타임아웃이 짧으면, 우리가 DB 작업을 다 끝낼 때까지 기다린 응답은 실패로 처리돼서 재전송을 불러요.

그래서 구조는 이렇게 잡아요. 서명을 검증하고, 이벤트를 큐에 넣고, 200을 돌려줘요. 큐 워커가 중복 제거와 상태 전이를 처리해요. 큐의 재시도와 멱등 처리는 [메시지 큐와 재처리](/m/message-queue) 글에서 자세히 다뤄요.

## 놓친 웹훅 — 조회 API로 맞추는 대사

웹훅이 끝내 도착하지 않을 수 있어요. 우리 서버 장애로 기간 안에 처리하지 못했거나, 재시도가 끝났거나, 엔드포인트 설정이 잘못됐을 때요. 이때 주문은 결제 대기에 계속 머물러요.

Stripe는 빠진 객체를 API로 다시 가져올 수 있다고 문서에서 설명해요. 대사(reconciliation)는 이 원리를 주기적으로 돌리는 것이에요.

결제 대기인 주문을 골라 PG의 결제 조회 API로 실제 상태를 확인하고, 다르면 맞춰요. 시뮬레이터의 "주기적 대사" 옵션이 이 동작이에요.

대사가 있으면 웹훅이 전부 유실돼도 최종 상태가 맞아요. 대신 확정까지 걸리는 시간은 대사 주기만큼 늘어나요. 그래서 실시간 반영은 웹훅이 맡고, 대사는 빠진 것을 메우는 안전망으로 쓰는 것이 일반적이에요.

## FE 체크 포인트 — 확인 중 상태와 갱신 경로

- **복귀 직후는 "확인 중"이에요.** 복귀 화면에서 주문 상태가 결제 대기면 "결제 결과를 확인하고 있어요"라고 보여 주세요. 실패라고 말하지도, 완료라고 추측하지도 마세요.
- **상태를 조회만 하세요.** 확인 중 화면에서 결제 요청을 다시 보내면 안 돼요. 주문 상태 조회만 반복해야 해요. 이 차이는 [결제 — 이중 결제 막기](/m/payment-idempotency)에서 다뤘어요.
- **갱신 방식을 고르세요.** 일정 간격으로 조회하는 폴링은 구현이 간단하지만 지연과 요청 수가 늘어나요. 서버가 상태 변경을 밀어 주는 방식은 [실시간 알림](/m/realtime-delivery) 글에서 비교해요.
- **최대 대기 시간을 정하세요.** 일정 시간이 지나도 확정이 안 되면 "결제 내역에서 확인해 주세요"처럼 다음 행동을 안내해요. 무한 로딩으로 두지 마세요.
- **새로고침해도 같은 상태를 보여 주세요.** 확정 여부는 서버가 기억하니, 화면은 주문 상태를 다시 받아 그리면 돼요.

## 정리 — 복귀는 힌트, 웹훅은 알림, 대사는 최종 확인

복귀 화면은 사용자가 창을 닫으면 사라져요. 웹훅은 서명을 검증하고, 이벤트 ID로 중복을 걸러내고, 허용된 상태 전이만 적용해야 해요. 그래도 놓친 웹훅은 주기적인 대사로 PG에 직접 물어서 맞춰야 해요. 이 세 층을 합치면 주문 상태는 결국 결제 서버의 기록과 같아져요.
