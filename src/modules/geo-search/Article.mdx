지도를 드래그할 때마다 주변 가게를 다시 불러오는 화면이 있어요. 줌을 줄이면 가게가 수천 개 걸리고, 응답이 느려지고, 마커가 많아서 화면이 멈춰요. 이 글은 서버가 "근처"를 어떻게 찾는지, 줌에 따라 무엇을 덜 보내는지, 지도가 움직일 때 요청을 어떻게 줄이는지 정리해요.

아래 시뮬레이터에서 질의 방식과 줌을 바꿔 보면, 같은 지도 화면에서 검사하는 점 수와 응답 크기가 어떻게 달라지는지 볼 수 있어요. 점은 모두 가짜 좌표예요.

## 위도 · 경도와 거리 — 평면 근사와 구면 거리

좌표는 경도와 위도 두 수예요. GeoJSON 명세(RFC 7946)는 위치 배열의 첫 두 원소를 경도, 위도 순서로 정하고, 좌표계는 WGS 84의 십진 도 단위라고 설명해요. 순서를 바꿔 보내면 엉뚱한 곳에 점이 찍히니 API 계약에 순서를 먼저 적어 두세요.

거리를 재는 방법은 크게 세 가지예요.

| 방법        | 가정                                                                        | 쓰는 곳                        | 주의                                        |
| ----------- | --------------------------------------------------------------------------- | ------------------------------ | ------------------------------------------- |
| 평면 근사   | 짧은 구간을 평평한 격자로 보고, 경도 차에 위도 평균의 cos를 곱해요          | 가까운 점끼리 빠르게 비교할 때 | 거리가 길어지면 오차가 커져요               |
| 구면 거리   | 지구를 구로 보고 구 위의 거리를 구해요. 이 글의 모델은 하버사인 공식을 써요 | 구 모형으로 거리를 셀 때       | 반지름을 얼마로 잡느냐에 따라 값이 달라져요 |
| 타원체 거리 | 지구를 타원체로 보고 최단 측지선 거리를 구해요                              | PostGIS geography의 기본 계산  | 계산 비용이 더 들어요                       |

이 글의 모델에서 약 1.4km 떨어진 두 점을 재면 평면 근사와 구면 거리의 차이가 0.1% 아래였어요. 대륙 규모로 멀리 떨어진 두 점에서는 차이가 훨씬 커졌어요. 그래서 가까운 후보 비교에는 평면 근사를 쓰고, 결과를 보여 주는 거리 계산에는 구면이나 타원체 거리를 쓰는 식으로 나눌 수 있어요.

PostGIS 문서는 geography 타입이 경도와 위도 좌표를 그대로 저장하고, 함수는 geometry보다 적지만 CPU를 더 쓴다고 설명해요. ST_Distance는 geography의 기본 값을 타원체 위 최단 거리(미터)로 계산하고, use_spheroid를 false로 두면 더 빠른 구면 계산을 쓴다고 해요.

## 질의 모양 — 지도 화면은 상자, 내 주변은 원

지도 화면에 보이는 영역은 사각형이에요. 남쪽과 북쪽 위도, 서쪽과 동쪽 경도로 된 경계 상자(bounding box)로 질의하는 편이 자연스러워요. "내 위치에서 1km 안"은 기준점과 반경으로 된 원 질의예요.

원 질의도 보통 경계 상자로 먼저 걸러요. PostGIS 문서는 ST_DWithin이 경계 상자 비교를 포함해서 인덱스를 쓸 수 있다고 설명해요. 예시에서도 ST_DWithin으로 후보를 줄인 다음, 인덱스를 쓸 수 없는 ST_Distance로 남은 후보만 계산해요.

경계 상자는 원보다 넓어요. 상자 안에는 원 밖의 점도 들어와요. 이 차이가 검사한 점과 실제로 쓰는 점의 차이가 돼요. 상자가 날짜변경선(경도 180도)을 가로지르면 두 상자로 나눠 질의해야 해요. 이 글의 모델은 그 경우를 다루지 않아요.

## 공간 인덱스 — 1차원 B-tree와 다차원 인덱스

B-tree는 값을 한 줄로 정렬해서 찾아요. PostGIS 문서는 B-tree가 한 차원의 데이터만 저장하고 조회하므로, 두 차원 이상인 지오메트리에는 맞지 않는다고 설명해요. 위도 열에만 B-tree를 달면, 경도 조건은 찾아낸 후보를 하나씩 걸러내는 일이 많아요. 이런 경우 후보가 띠처럼 많이 남아요. 이는 구조를 따져 보면 그렇게 보인다는 추정이에요.

PostgreSQL 문서는 GiST가 트리를 "한쪽에 있는 것", "겹치는 것", "안에 있는 것"으로 나누는 범용 틀이라고 설명해요. PostGIS는 이 위에 R-tree를 구현해서, 지오메트리의 경계 상자를 기준으로 공간 데이터를 인덱싱해요.

격자 셀 방식은 지구 전체를 격자로 나누고, 점마다 셀 번호를 키로 써요. Redis는 GEO 값을 정렬 집합(sorted set)에 넣고, 점수로 지오해시 인코딩 값을 써요. GEOSEARCH의 WITHHASH 옵션이 이 점수를 돌려준다고 설명해요. 셀 방식은 상자와 겹치는 셀 전체를 가져오므로, 가장자리 셀의 바깥 점도 후보에 들어와요. 그래서 검사한 점 수는 화면 안 점 수보다 적을 수 없어요.

| 방식             | 후보를 찾는 법                                  | 검사하는 양                   | 장단                                             |
| ---------------- | ----------------------------------------------- | ----------------------------- | ------------------------------------------------ |
| 전체 스캔        | 모든 점을 확인해요                              | 전체 점 수                    | 구현이 단순하지만 점이 늘면 바로 느려요          |
| 경계 상자 인덱스 | R-tree 같은 공간 인덱스로 상자 안 후보만 찾아요 | 상자 안 점 수 (이상적인 가정) | 지도 질의에 맞아요. 인덱스 유지 비용이 있어요    |
| 격자 셀 인덱스   | 상자와 겹치는 셀의 점을 가져와요                | 겹치는 셀 안 점 수            | 키로 찾기 쉬워요. 셀이 크면 가장자리 낭비가 커요 |

Redis 문서는 GEOSEARCH의 COUNT에 ANY를 붙이면 찾는 대로 돌려주므로 빠르지만 결과가 정렬되지 않는다고 설명해요. 정렬하지 않으면 기준점에서 가장 가까운 점이 아닐 수 있어요. 빠른 응답과 정확한 순서 중 무엇을 고를지는 화면이 정하는 판단이에요.

## 줌 수준과 응답 크기 — 개수 제한과 서버 클러스터링

줌을 낮추면 같은 방식의 질의가 훨씬 많은 점을 돌려줘야 해요. 점이 수천 개면 응답이 커지고, 지도에 마커를 수천 개 그리는 것도 부담이에요. 두 가지로 줄일 수 있어요.

- **개수 제한(LIMIT)**: 응답에 담을 최대 개수를 정해요. 다만 정렬 기준 없이 앞에서부터 자르면, 요청마다 화면에 보이는 점이 달라질 수 있어요. 정렬과 다음 페이지 설계는 [페이지네이션](/m/pagination) 글에서 다뤄요.
- **서버 클러스터링**: 줌이 낮을 때 서버가 화면을 칸으로 나누고, 칸마다 개수와 평균 좌표만 돌려줘요. 응답 행 수는 칸 수로 정해져요. 이 글의 모델은 화면을 8 × 8 칸으로 나눠요.

클러스터는 점을 버리지 않고 합쳐요. 묶음 개수의 합은 화면 안 점 수와 같아야 해요. 시뮬레이터에서 묶기를 켜면 "잘림" 알림이 사라지는 것을 볼 수 있어요. 이것은 점을 빼는 대신 묶어서 보낸 결과예요.

줌 13 미만에서만 묶는 기준은 이 글의 설계 판단이에요. 실제 서비스에서는 화면 크기와 데이터 밀도에 맞춰 기준을 정해요.

## 지도 이동 요청 — 멈춘 뒤 한 번, 이전 요청 취소

지도를 드래그하면 이동 이벤트가 연달아 나와요. 이벤트마다 요청을 보내면 검색창의 타이핑과 같은 문제가 생겨요. [검색 자동완성](/m/search-autocomplete) 글의 디바운스와 취소가 그대로 쓰여요. 여기서는 지도에서 달라지는 부분만 짚어요.

- **멈춘 뒤 한 번**: 이동이 잠깐 멈췄을 때만 요청해요. 드래그 중에는 기존 결과를 그대로 두고, 멈춘 뒤 새 영역을 불러와요.
- **이전 요청 취소**: AbortController로 이전 요청을 끊어요. MDN은 abort()가 fetch 요청과 응답 본문 읽기 같은 비동기 작업을 중단할 수 있다고 설명해요. 취소는 클라이언트 쪽 중단이라서, 서버가 이미 한 계산을 되돌리지는 않아요.
- **영역 단위 재사용**: 이미 받은 영역을 다시 보면 응답을 재사용하는 편이 좋아요. 저장 기간과 재검증은 [HTTP 캐시](/m/http-caching) 글을 봐요. 영역을 타일 단위로 나눠 키로 쓰면, 조금 움직인 지도도 이미 받은 타일을 재사용할 수 있어요. 타일 경계에 걸친 점을 어떻게 다룰지는 설계 판단이에요.
- **요청 폭주 방지**: 429를 받으면 응답이 알려 준 시간만큼 기다려요. 서버 쪽 한도는 [요청 제한](/m/rate-limiting) 글에서 다뤄요.

## 좌표 정밀도와 개인정보 — 소수 자리와 권한

Geolocation API는 보안 컨텍스트(HTTPS)에서만 쓸 수 있어요. MDN은 개인정보 때문에 사용자에게 위치 정보 제공 권한을 묻는다고 설명해요. 권한을 거부하면 위치 없이 쓰는 화면, 예를 들어 지역을 직접 고르는 화면이 있어야 해요.

좌표의 소수 자리를 줄이면 위치가 흐려져요. 구 반지름을 6,371km로 가정한 예시 계산으로는 소수 다섯째 자리가 약 1.1m, 셋째 자리가 약 111m예요. 주변 검색에 필요한 정밀도를 먼저 정하고, 그 자리 수까지만 보내는 편이 좋아요.

좌표는 개인을 가리키는 정보예요. 요청 로그나 에러 추적에 전체 좌표를 남기지 않는 편이 좋아요. 민감 정보를 다루는 방법은 [민감 정보 보호](/m/sensitive-data) 글을 봐요.

## FE 체크 포인트

**좌표 순서를 계약에 적어요.** GeoJSON은 [경도, 위도] 순서예요. 지도 라이브러리마다 순서 관례가 달라서, 섞이기 쉬워요. 요청과 응답 모두 한 가지 순서로 맞춰 주세요.

**응답의 잘림과 묶음을 구분해요.** 응답에 잘렸는지, 묶였는지를 알려 주는 표시가 있으면 화면 문구를 나눌 수 있어요. "일부만 보여요"와 "묶어서 보여요"는 사용자가 할 일이 달라요.

**멈춘 뒤 한 번만 요청해요.** 드래그 중에는 요청하지 않고, 멈춘 뒤 새 영역을 불러와요. 이전 요청은 AbortController로 취소해서 늦게 온 응답이 최신 결과를 덮지 않게 해요.

**권한 거부 화면을 따로 그려요.** 위치를 거부해도 앱을 쓸 수 있게 지역 선택 같은 대체 입력을 두세요. 권한 요청 시점은 사용자가 주변 기능을 누르는 순간이 좋아요.

**좌표는 필요한 자리 수만 보내요.** 화면 축척에 맞는 소수 자리로 반올림해서 보내세요. 전체 정밀도 좌표를 로그에 남기지 마세요.

## 시뮬레이터 안내

화면의 가짜 점은 작은 영역에 깔려 있어요. 사각형은 지도 화면이에요.

- 질의 방식을 골라 검사한 점 수가 어떻게 달라지는지 보세요.
- 줌을 낮춰 보세요. 응답 상한을 넘으면 잘림 알림이 떠요.
- 묶어서 보내기를 켜 보세요. 잘림이 사라지고, 응답 단위가 묶음으로 바뀌어요.
- 점 수를 늘려서 전체 스캔과 인덱스 방식의 차이가 커지는지 보세요.

수치는 감을 잡기 위한 예시예요.

## 정리 — 질의 모양 · 인덱스 · 줌별 응답

지도 질의는 경계 상자로 하고, 공간 인덱스나 격자 셀로 검사할 점을 줄여요. 셀 방식은 가장자리 후보가 늘어난다는 점을 알고 쓰세요. 줌이 낮으면 개수를 제한하고, 서버에서 묶어서 보내는 편이 좋아요. 지도 이동 요청은 멈춘 뒤 한 번만 보내고, 이전 요청은 취소해요. 좌표는 필요한 자리 수만 보내요.

쿼리를 여러 번 나눠 점마다 상세 정보를 읽으면 목록 조회와 같은 N+1 문제가 생겨요. 그 문제와 인덱스 열 순서는 [N+1 쿼리](/m/n-plus-one) 글에서 자세히 다뤄요.
