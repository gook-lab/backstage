쿠폰 한 장은 "한 사람이 한 번, 전체에서 정해진 장수까지"라는 약속이에요. 같은 쿠폰을 두 탭에서 동시에 누르면 할인이 두 번 들어갈 수 있어요. 결제가 실패하면 쿠폰은 돌아와야 해요. 서버는 이 세 가지를 어떻게 기록할까요?

이 글은 쿠폰을 규칙과 사용 기록으로 나누고, 각 약속을 DB가 어떻게 지키는지 정리해요. 아래 시뮬레이터에서 같은 사건을 직접 돌려 볼 수 있어요. 글의 규칙과 시뮬레이터의 동작은 같아요.

시뮬레이터에서 시간의 단위인 "틱"은 DB 요청 한 번을 뜻해요.

## 쿠폰 모델 — 규칙과 사용 기록 나누기

쿠폰은 세 가지 대상으로 나눠 보면 쉬워요.

| 대상                 | 뜻                                            | 예시                                   |
| -------------------- | --------------------------------------------- | -------------------------------------- |
| 쿠폰 규칙            | 할인 방식, 금액, 유효 기간, 남은 수량         | 정률 10%, 남은 수량 100장, 12월 말까지 |
| 사용 기록            | 누가 어떤 주문에 썼는지, 지금 상태가 무엇인지 | 사용자 7, 주문 91, RESERVED            |
| 손님에게 보이는 코드 | 손님이 입력하거나 누르는 값                   | `WELCOME10`                            |

Stripe도 같은 나눔을 써요. 프로모션 코드 문서는 프로모션 코드가 기반 프로모션을 가리키고, 고객 · 사용 횟수 한도 · 만료일을 덧붙일 수 있다고 설명해요. 쿠폰 문서의 max_redemptions는 모든 고객에 걸친 총 사용 횟수 한도이고, 프로모션 코드의 max_redemptions는 그 코드의 사용 횟수 한도예요.

규칙 행과 사용 기록 행을 나누면 경쟁이 몰리는 곳이 분명해져요. 사용 기록은 요청마다 바뀌고, 남은 수량도 요청마다 바뀌어요. 그래서 경쟁은 이 두 곳에서만 막으면 돼요. 규칙 자체는 그대로 두어요.

## 1인 1회 — 유일 제약으로 두 번째 사용 막기

"이미 썼는지 확인하고 나서 기록하기"는 두 탭이 같은 옛 값을 보는 패턴이에요. 두 요청이 모두 "안 썼어요"를 받고, 둘 다 기록해요. 이 빈틈은 [콘서트 좌석 선점](/m/concert-seats)의 읽고 나서 쓰기와 같아요.

PostgreSQL 문서는 UNIQUE 제약이 열 묶음의 값 조합을 테이블 전체에서 유일하게 만든다고 설명해요. 그래서 (쿠폰, 사용자) 쌍에 UNIQUE를 걸어요.

```sql
CREATE TABLE coupon_redemptions (
  coupon_id      bigint      NOT NULL REFERENCES coupons (id),
  user_id        bigint      NOT NULL,
  order_id       bigint      NOT NULL,
  status         text        NOT NULL,   -- RESERVED · CONFIRMED · RELEASED
  reserved_until timestamptz,
  UNIQUE (coupon_id, user_id)
);
```

`user_id`에 NOT NULL을 붙이는 이유가 있어요. PostgreSQL 문서는 기본적으로 NULL 두 값을 같다고 보지 않아서, 유일 제약이 있어도 NULL이 들어간 중복 행이 생길 수 있다고 설명해요.

두 탭이 동시에 INSERT하면 어떻게 될까요? PostgreSQL 문서는 unique 인덱스가 있는 테이블에서 동시 세션이 같은 값을 다루면 INSERT가 막힐 수 있다고 설명해요. 두 번째 INSERT는 같은 값을 허용하지 않는 제약에 걸려요. 앱은 이 오류를 409로 바꿔요.

단, 해제된 쿠폰을 같은 사용자가 다시 쓸 수 있어야 해요. 그래서 다음 절의 예약 쿼리는 INSERT에 `ON CONFLICT`를 붙이고, 해제된 행만 다시 쓰게 해요.

## 총 수량 한도 — 조건부 UPDATE로 차감하기

남은 수량은 규칙 행의 숫자 하나예요. 차감은 확인과 변경을 한 문장에 넣어요.

```sql
UPDATE coupons
SET remaining = remaining - 1
WHERE id = $coupon_id
  AND remaining > 0
  AND valid_until > now()
RETURNING remaining;
```

PostgreSQL 문서는 UPDATE의 갱신 행 수가 0이어도 오류가 아니라고 설명해요. 그래서 앱은 행 수를 확인해야 해요. 0이면 수량 소진으로 보고 트랜잭션을 롤백해요. 행 수를 확인하지 않으면 실패가 조용히 지나가요.

`CHECK (remaining >= 0)` 제약도 함께 두는 편이 좋아요. PostgreSQL 문서는 CHECK 제약이 조건을 만족하지 않는 값을 막는다고 설명해요. 다만 CHECK만 두면 차감이 오류로 끝나서, 조건부 UPDATE가 주는 "0 행" 신호를 쓸 수 없어요. 둘을 같이 두면 DB가 음수를 막고, 앱은 0 행으로 소진을 알아요.

## 사용 흐름 — 예약 · 확정 · 해제 나누기

쿠폰 상태는 세 가지예요.

| 상태      | 바뀌는 때                      | 수량       |
| --------- | ------------------------------ | ---------- |
| RESERVED  | 주문을 만들고 결제를 시작할 때 | 한 장 차감 |
| CONFIRMED | 결제 성공을 확인할 때          | 차감 유지  |
| RELEASED  | 결제 실패 또는 예약 만료       | 한 장 복구 |

예약은 한 트랜잭션에서 두 문장을 실행해요. 첫 문장이 사용 기록을 잡고, 둘째 문장이 수량을 줄여요.

```sql
BEGIN;

-- 1. 사용자의 행을 잡아요. 이미 RESERVED 나 CONFIRMED 면 행이 돌아오지 않아요.
INSERT INTO coupon_redemptions (coupon_id, user_id, order_id, status, reserved_until)
VALUES ($coupon_id, $user_id, $order_id, 'RESERVED', now() + interval '15 minutes')
ON CONFLICT (coupon_id, user_id) DO UPDATE
  SET order_id = EXCLUDED.order_id,
      status = 'RESERVED',
      reserved_until = EXCLUDED.reserved_until
  WHERE coupon_redemptions.status = 'RELEASED'
RETURNING user_id;

-- 2. 1번이 행을 돌려준 경우에만 수량을 줄여요.
UPDATE coupons
SET remaining = remaining - 1
WHERE id = $coupon_id AND remaining > 0 AND valid_until > now()
RETURNING remaining;

COMMIT;  -- 어느 쪽이든 0 행이면 ROLLBACK 해요
```

PostgreSQL 문서는 ON CONFLICT ... WHERE 조건을 만족하지 않은 행은 RETURNING으로 돌아오지 않는다고 설명해요. 그래서 이미 쓴 사용자는 첫 문장에서 빈 결과를 받아요. 둘째 문장이 0 행이면 첫 문장의 변경도 롤백돼요.

확정은 예약이 살아 있을 때만 바꿔요.

```sql
UPDATE coupon_redemptions
SET status = 'CONFIRMED', reserved_until = NULL
WHERE order_id = $order_id
  AND status = 'RESERVED'
  AND reserved_until > now();
```

0 행이면 예약이 이미 풀렸다는 뜻이에요. 결제는 성공했지만 쿠폰을 줄 수 없으니, 환불 흐름으로 넘겨요.

해제는 결제 실패나 만료에서 호출해요. 같은 해제가 두 번 불려도 수량은 한 번만 돌아와야 해요.

```sql
BEGIN;
UPDATE coupon_redemptions
SET status = 'RELEASED'
WHERE order_id = $order_id AND status = 'RESERVED'
RETURNING coupon_id;   -- 0 행이면 아래 문장을 실행하지 않아요
UPDATE coupons SET remaining = remaining + 1 WHERE id = $coupon_id;
COMMIT;
```

두 번째 호출은 첫 문장이 0 행을 돌려줘서 수량을 다시 올리지 않아요. 앱이 행 수로 분기하는 것이 핵심이에요.

확정과 만료가 동시에 일어나면 누가 이길까요? PostgreSQL 격리 수준 문서는 기본 격리인 Read Committed에서, 먼저 바뀐 행을 기다렸다가 갱신된 행에 WHERE 조건을 다시 검사한다고 설명해요. 확정 쿼리의 `reserved_until > now()`가 이 재검사에서 판단을 맡아요. 잠금의 세부는 [트랜잭션 · 락 · 데드락](/m/transactions)에서 다뤄요.

## 할인 금액 — 서버가 다시 계산하기

클라이언트가 보낸 "할인 1,000원"은 참고값으로만 받아요. 서버는 쿠폰 규칙, 주문 줄의 DB 가격, 유효 기간으로 할인액을 다시 계산해요.

Stripe 쿠폰 문서는 정액 쿠폰의 `amount_off`가 인보이스의 소계에서 빠진다고 설명해요. 그래서 할인을 계산하는 기준 금액도 서버가 가진 값이어야 해요.

한 주문 안에서 계산 순서도 정해야 해요. 예시로 소계 10,000원에 정률 10%와 정액 1,000원을 같이 쓴다고 해 볼게요.

| 순서        | 계산                                      | 결제 금액 (예시) |
| ----------- | ----------------------------------------- | ---------------- |
| 정률 → 정액 | 10,000 − 1,000 − 1,000                    | 8,000원          |
| 정액 → 정률 | 10,000 − 1,000 = 9,000, 9,000 × 10% = 900 | 8,100원          |

같은 두 쿠폰인데 순서에 따라 100원이 달라요. 규칙은 하나로 정하고, 클라이언트와 서버가 같은 순서로 계산하게 해요.

## 중복 적용 — 여러 장과 적용 순서, 반올림

중복 적용 정책은 두 가지 중 하나로 정해요.

- 한 주문에 한 장만 허용해요. 가장 단순하고 계산 순서 문제가 없어요.
- 여러 장을 허용해요. 이때는 적용 순서와 반올림 규칙을 명시해야 해요.

반올림도 같이 정해요. 예시로 소계 10,005원에 10%를 적용하면 1,000.5원이에요. 버림이면 1,000원, 반올림이면 1,001원이에요. 한 번 정한 방식을 줄마다, 합계마다 똑같이 써야 1원 차이가 생기지 않아요. 자세한 내용은 [금액 계산 · 최소 단위](/m/money-amounts)에서 다뤄요.

이 절의 규칙은 서비스 정책이에요. 공식 문서가 정하는 규칙이 아니에요.

## 환불 — 쿠폰을 되돌릴지 정하기

환불 때 쿠폰을 어떻게 할지도 정책이에요. 세 가지 중에서 골라요.

| 방식                 | 쿠폰 처리                          | 주의                                           |
| -------------------- | ---------------------------------- | ---------------------------------------------- |
| 전액 환불, 쿠폰 복구 | 해제와 같은 방식으로 수량을 올려요 | 쿠폰 유효 기간이 지났으면 복구하지 않아야 해요 |
| 전액 환불, 사용 유지 | 변화가 없어요                      | 손님에게 이유를 보여 줘야 해요                 |
| 부분 환불            | 할인액을 줄별로 나눠 계산해요      | 1원 차이를 어느 줄에 둘지 정해야 해요          |

복구는 행을 RELEASED로 바꾸고 수량을 올리는 것과 같은 트랜잭션에서 해요. 따로 두 번 쓰면 중간에 실패했을 때 수량과 상태가 어긋나요.

## 시뮬레이터 안내

시뮬레이터에서 기록 방식과 사건을 고를 수 있어요.

- 기록 방식은 확인 후 쓰기와 유일 제약 + 조건부 차감 두 가지예요.
- 사건은 두 탭 동시 사용, 결제 실패로 해제, 예약 만료 뒤 늦은 결제, 쿠폰 1장에 10명 요청 네 가지예요.
- 쿠폰 수량과 보류 시간 TTL을 조절할 수 있어요.

결과 표에서 요청마다 확정, 거절, 해제, 확정 실패가 어떻게 나뉘는지 볼 수 있어요. 수치는 감을 잡기 위한 예시예요.

## FE 체크 포인트

- 쿠폰 적용 응답에는 할인 금액과 결제 금액을 서버 계산값으로 받으세요. 화면에서 계산한 값은 보여 주기용으로만 쓰세요.
- 거절 응답은 409로 받으세요. RFC 9110은 409가 대상의 현재 상태와 충돌해서 요청을 끝낼 수 없다는 뜻이라고 설명해요. 이미 사용과 수량 소진은 오류 코드로 구분하세요. 예시 응답은 이래요.

```http
HTTP/1.1 409 Conflict
Content-Type: application/json

{"code": "COUPON_ALREADY_USED", "couponId": 12}
```

- 결제 실패 뒤 쿠폰이 돌아왔다는 표시는 서버가 해제를 마친 뒤에 보여 주세요. 해제 전에 미리 바꾸면 다음 손님이 받지 못한 쿠폰을 보게 돼요.
- 결제 요청을 네트워크 재시도로 다시 보낼 수 있어요. 같은 시도에는 같은 멱등성 키를 보내세요. 키 규칙은 [결제 멱등성](/m/payment-idempotency)에서 다뤄요.
- 두 탭의 적용 결과는 서버 응답을 기준으로 맞추세요. 브라우저 저장소에 "사용 완료"를 적어 두면 다른 기기나 탭과 어긋나요.

## 정리 — 유일 제약 · 조건부 차감 · 예약 흐름 · 서버 재계산

1인 1회는 (쿠폰, 사용자) 유일 제약이 막아요. 총 수량은 `remaining > 0` 조건부 UPDATE가 막고, 0 행을 소진 신호로 써요. 예약은 확정과 해제로 나뉘고, 해제는 행 수로 한 번만 수량을 돌려요. 할인 금액은 서버가 규칙과 DB 가격으로 다시 계산해요. 환불 때 쿠폰을 어떻게 할지는 정책으로 정해요.

이 글의 조건부 UPDATE와 격리 수준은 [트랜잭션 · 락 · 데드락](/m/transactions)의 규칙 위에 서 있어요. 같은 좌석 한 칸을 두고 경쟁하는 구조는 [콘서트 좌석 선점](/m/concert-seats)과 같아요. 장바구니에 담긴 상품의 재고 차감 시점은 [장바구니와 재고](/m/cart-stock)에서 따로 다뤄요.
