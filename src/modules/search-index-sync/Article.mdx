상품 이름을 고치고 저장하면 상세 페이지에는 바로 새 이름이 보이는데, 검색 결과에는 잠깐 옛 이름이 남을 수 있어요. 버그처럼 보이지만, 검색이 읽는 저장소가 DB와 따로 있어서 생기는 일이에요. 이 글은 한 질문에서 출발해요. **DB와 검색 색인은 어떻게 같은 값을 유지할까요?** 갱신 방식 세 가지를 비교하고, refresh 간격과 실패가 시간을 어떻게 늘리는지, 옛 값이 끝까지 남는 경우가 언제인지 차례로 봐요.

아래 시뮬레이터에서 갱신 방식, 발행 지연, refresh 간격, 색인 쓰기 실패, 재시도, 재색인을 바꾸며 검색 결과가 DB와 언제 같아지는지, 영영 어긋나는지 직접 확인해 보세요. 수치는 모두 예시예요.

## 원본과 색인 — 검색이 DB를 직접 읽지 않는 구조

상세 페이지는 보통 DB에서 값을 읽어요. 검색은 검색 엔진이 미리 만들어 둔 색인에서 찾아요. [Elasticsearch 문서](https://www.elastic.co/guide/en/elasticsearch/reference/current/near-real-time.html)는 Lucene의 세그먼트가 역색인(inverted index)과 비슷하다고 설명해요. 검색에 맞게 다시 만든 사본이라는 뜻이에요.

그래서 같은 상품 이름이 두 곳에 있어요. 하나는 DB 원본이고, 다른 하나는 색인이에요. 둘을 맞추는 일은 자동으로 되지 않고, 앱이나 인프라가 따로 해야 해요.

## 갱신 방식 — 이중 쓰기 · 아웃박스 · CDC 비교

| 방식      | 색인에 쓰는 주체                                  | 특징                                | 주의                                    |
| --------- | ------------------------------------------------- | ----------------------------------- | --------------------------------------- |
| 이중 쓰기 | 앱이 DB 저장 뒤 색인 API를 직접 호출              | 구현이 가장 짧아요                  | 두 번째 쓰기가 실패하면 불일치가 남아요 |
| 아웃박스  | 같은 트랜잭션에 남긴 행을 별도 발행기가 읽어 전달 | 실패한 발행을 다시 시도할 수 있어요 | 발행기와 소비자가 중복을 처리해야 해요  |
| CDC       | DB 변경 로그를 커넥터가 읽어 전달                 | 앱 코드가 색인을 몰라도 돼요        | 로그 설정과 운영 부담이 커요            |

세 방식 모두 "DB가 바뀌었다"는 사실을 "색인도 바뀌어야 한다"로 옮기는 방법이에요. 차이는 그 사실을 누가, 어떤 기록을 근거로 옮기느냐에 있어요.

## 이중 쓰기의 불일치 — DB 저장 뒤 색인 쓰기가 실패하는 자리

이중 쓰기는 앱이 DB 저장과 색인 쓰기를 차례로 호출해요. 두 시스템을 하나의 트랜잭션으로 묶을 수 없어서 문제가 생겨요. [microservices.io의 Transactional outbox 패턴](https://microservices.io/patterns/data/transactional-outbox.html)은 DB와 브로커를 2PC(분산 트랜잭션)로 묶는 것이 많은 경우 선택지가 아니라고 설명해요. 같은 글은 트랜잭션을 커밋한 뒤에 메시지를 보내면, 보내기 전에 죽을 수 있어서 보장이 없다고 설명해요.

예를 들어 DB 저장은 성공했는데 색인 쓰기가 실패하면, DB에는 새 이름이 있고 검색에는 옛 이름이 남아요. 재시도가 없으면 이 상태는 다음 쓰기나 전체 재색인이 일어나기 전까지 그대로예요. 시뮬레이터의 "이중 쓰기 · 재시도 없음" 시나리오가 이 경우예요.

## 아웃박스와 CDC — DB 변경을 따로 흘려 보내기

아웃박스는 상품 이름 변경과 같은 트랜잭션에 발행할 행을 남겨요. 그 행이 DB에 저장되면 변경이 확정된 것이고, 별도 발행기가 나중에 그 행을 읽어 색인 쓰기를 맡아요. [microservices.io](https://microservices.io/patterns/data/transactional-outbox.html)는 발행기가 트랜잭션 로그를 따라가거나(transaction log tailing), 아웃박스를 주기적으로 조회하는 방식(polling publisher)으로 일할 수 있다고 소개해요.

[Debezium의 Outbox Event Router 문서](https://debezium.io/documentation/reference/stable/transformations/outbox-event-router.html)는 아웃박스 테이블에 INSERT만 허용하고, 행의 이벤트 ID를 중복 제거에 쓸 수 있다고 설명해요. 아웃박스 패턴에서 메시지 브로커는 같은 메시지를 두 번 이상 보낼 수 있어서, 소비자는 멱등하게 처리해야 해요. 자세한 내용은 [메시지 큐와 재처리](/m/message-queue) 글의 아웃박스 절에서 다뤄요.

CDC는 DB의 변경 로그를 읽는 방식이에요. [Debezium 아키텍처 문서](https://debezium.io/documentation/reference/stable/architecture.html)는 커넥터가 DB에 연결해 변경을 캡처하고, Kafka Connect를 거쳐 Elasticsearch 같은 곳으로 흘려 보낼 수 있다고 설명해요. [PostgreSQL 논리 디코딩 문서](https://www.postgresql.org/docs/current/logicaldecoding-explanation.html)는 복제 슬롯이 변경을 원본 서버에서 만들어진 순서대로 재생할 수 있는 흐름으로 제공하고, 한 시점에 한 수신자만 그 흐름을 읽는다고 설명해요.

## 검색 refresh — 쓴 값이 검색에 보이는 시각

색인에 쓴 문서가 바로 검색에 보이지는 않아요. [Elasticsearch 문서](https://www.elastic.co/guide/en/elasticsearch/reference/current/near-real-time.html)는 쓰기가 메모리 버퍼에서 세그먼트로 바뀌고, 그 뒤 refresh가 일어나야 검색에 보인다고 설명해요. 기본 주기는 1초예요. 다만 최근 30초 안에 검색 요청을 받은 인덱스에만 주기 refresh가 돈다고 설명해요.

[OpenSearch 문서](https://docs.opensearch.org/latest/api-reference/index-apis/refresh/)도 같은 구조예요. 문서는 먼저 translog와 메모리 버퍼에 쓰이고, refresh로 검색 가능한 세그먼트가 되기 전까지 검색에 보이지 않아요.

refresh 간격은 반영 시간을 직접 정해요. [Elasticsearch의 index.refresh_interval 설정](https://www.elastic.co/guide/en/elasticsearch/reference/current/index-modules.html)은 기본값이 1초이고, -1로 주기 refresh를 끌 수 있다고 설명해요. 같은 문서는 -1이어도 다른 메커니즘으로 refresh가 일어날 수 있어서 쓴 값이 검색에 보이지 않는 상태가 완전히 보장되지는 않는다고 설명해요.

명시적인 refresh를 자주 호출하는 방식은 권장되지 않아요. [Refresh API 문서](https://www.elastic.co/guide/en/elasticsearch/reference/current/indices-refresh.html)는 클러스터 성능을 위해 주기 refresh를 기다리는 편이 좋다고 설명해요. 색인한 뒤 바로 그 문서를 검색해야 하는 흐름이라면 `refresh=wait_for`를 쓰는 것이 권장된다고 설명해요.

## 전체 재색인과 별칭 전환 — 옛 값을 한 번에 정리하기

불일치가 쌓였거나 색인 설정을 바꿔야 하면 전체 재색인을 해요. 순서는 새 인덱스를 먼저 채우고, 다 채운 뒤에 별칭이 새 인덱스를 가리키게 바꾸는 것이에요. [Aliases API 문서](https://www.elastic.co/guide/en/elasticsearch/reference/current/aliases.html)는 여러 별칭 동작을 한 번의 원자적 작업으로 실행할 수 있다고 설명해요. 검색 코드는 별칭 이름으로만 요청하면 돼요.

[Reindex API 문서](https://www.elastic.co/guide/en/elasticsearch/reference/current/docs-reindex.html)는 원본 인덱스나 별칭, 데이터 스트림에서 문서를 옮기고, 원본의 설정은 복사하지 않는다고 설명해요. DB에서 다시 채우는 재색인은 이 API 밖의 일이라서, 앱이 배치 작업으로 만들어야 해요. 큰 작업을 나눠 처리하는 방법은 [배치 작업](/m/batch-jobs) 글에서 다뤄요.

재색인 중에 들어온 변경은 쉽게 빠져요. 새 인덱스를 채우는 동안의 변경을 아웃박스나 CDC로 같이 흘려야 해요. 이 부분은 설계상의 판단이고, 시뮬레이터는 이 과정을 단순화해서 재색인 시각의 값만 옮겨요.

## 삭제 반영 — 상품을 검색에서 지우는 경로

삭제도 색인 작업이에요. DB에서만 지우고 색인 삭제가 빠지면, 상세 페이지에는 없는데 검색 결과에는 남아요. [Elasticsearch 문서](https://www.elastic.co/guide/en/elasticsearch/reference/current/near-real-time.html)는 refresh가 마지막 refresh 뒤에 인덱스에 수행된 작업을 검색에 보이게 한다고 설명해요. 이 글의 시뮬레이터는 삭제도 같은 경로와 같은 refresh 규칙으로 반영된다고 가정해요.

## 재시도와 버전 — 같은 색인 쓰기를 여러 번 보내도 되는 조건

색인 쓰기가 실패하면 다시 보내야 해요. 이때 옛 버전이 새 버전을 덮어쓰면 안 돼요. [Elasticsearch 색인 API 문서](https://www.elastic.co/guide/en/elasticsearch/reference/current/docs-index_.html)는 순번(sequence number)을 써서 옛 버전이 새 버전을 덮어쓰지 않도록 막는다고 설명해요. 아웃박스나 CDC에서 같은 변경이 두 번 와도 문서 ID와 버전을 함께 쓰면 결과가 한 번 쓴 것과 같아지도록 설계할 수 있어요.

## FE 할 일 — 저장 응답 값 보여 주기와 반영 안내

FE 입장에서 할 일은 세 가지예요.

1. **저장 직후에는 저장 응답의 값을 보여 줘요.** 방금 저장한 상품의 상세와 목록은 응답에 담긴 이름으로 바꿔요. 검색을 다시 불러오면 색인이 아직 옛 값일 수 있어요.
2. **검색 결과에는 반영 시간을 알려요.** "반영까지 시간이 걸려요"처럼 기한을 약속하지 않는 문구가 안전해요. 지연은 refresh 간격과 발행 지연에 따라 달라지기 때문이에요.
3. **검색 응답을 캐시하고 있으면 만료 시각도 같이 봐요.** 캐시된 옛 응답은 색인이 맞아진 뒤에도 남을 수 있어요. API 응답을 누가 얼마나 들고 있는지는 [HTTP 캐시](/m/http-caching) 글에서, 검색어별 응답 캐시는 [검색 자동완성](/m/search-autocomplete) 글에서 다뤄요.

방금 쓴 항목이 검색에 보여야 하는 기능이라면, BE에 색인 반영을 기다리는 방식이 있는지 물어보는 것이 좋아요. 읽기 복제본의 지연을 다루는 방식은 [복제 지연](/m/replication-lag) 글과 비슷하지만, 지연이 생기는 곳이 달라요.

## 시뮬레이터 안내 — 방식과 시각을 바꿔 보기

- 갱신 방식을 이중 쓰기로 두고 색인 쓰기 실패를 1번 주면, 재시도를 끈 상태에서 옛 값이 끝까지 남아요.
- 재시도를 켜면 실패 뒤 5초 만에 색인이 맞아요.
- refresh 간격을 30초로 올리면 CDC 지연과 합쳐져서 같아지는 시각이 늦어져요.
- 전체 재색인을 켜면 실패로 남은 옛 값이 재색인 뒤에 정리돼요.
- 삭제 시나리오에서는 검색 결과의 항목이 refresh 뒤에 사라져요.

수치는 감을 잡기 위한 예시예요.

## 정리 — 값의 출처를 나누고 반영 시간을 안내하기

- 검색 결과와 상세 페이지는 서로 다른 저장소에서 와요. 잠깐 값이 다를 수 있어요.
- 이중 쓰기는 실패 경로를 따로 설계하지 않으면 옛 값이 영구히 남을 수 있어요.
- 아웃박스와 CDC는 DB 변경을 색인 쪽으로 흘려 보내요. 소비자는 같은 변경이 두 번 와도 결과가 같도록 처리해요.
- 색인 refresh 간격이 쓴 값의 검색 반영 시각을 정해요.
- 재색인은 옛 값을 정리하는 방법이고, 별칭 전환으로 검색 중단 없이 바꿔요.
- FE는 저장 응답의 값을 먼저 보여 주고, 검색 결과에는 반영 시간을 알려요.
