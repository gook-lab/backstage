요금제 화면의 이번 달 API 호출 수는 실제보다 늦게 올라가요. 한도를 넘었는데도 몇 분 동안 호출이 더 통과하기도 해요. 두 현상은 같은 원인에서 나와요. 사용량을 요청이 들어온 순간에 세지 않고, 이벤트로 쌓아 두었다가 나중에 집계하기 때문이에요.

이 글은 사용량을 세는 세 가지 방식을 비교해요. 이어서 다음 세 가지를 다뤄요.

- 재전송된 이벤트를 한 번만 세는 멱등성 키
- 월말 경계에 걸린 이벤트가 어느 달에 들어가는지
- 확정된 청구서를 고치는 방법

아래 시뮬레이터에서 같은 사건을 방식만 바꿔 가며 돌려 볼 수 있어요. 수치는 시뮬레이터 안의 예시예요.

## 증상 — 화면 지연과 한도 초과 허용

FE가 보는 증상은 두 가지예요. 첫째, 화면의 호출 수가 실제 호출보다 적어요. 둘째, 한도가 100인데 호출은 130까지 성공해요.

두 증상은 같은 저장 구조에서 나와요. 서버가 사용량을 이벤트로 쌓고 주기적으로 합계를 내면, 화면과 한도 판단이 모두 마지막 합계를 보게 돼요. 합계에 없는 호출은 화면에도 없고 한도 계산에도 빠져요.

Stripe는 사용 이벤트를 비동기로 처리하므로, 집계된 사용량이 방금 받은 이벤트를 바로 반영하지 않을 수 있다고 설명해요 ([Record usage for billing](https://docs.stripe.com/billing/subscriptions/usage-based/recording-usage)). 아래의 방식 비교는 이 사실 위에서 우리가 고르는 설계예요.

## 요청마다 DB 카운터 — 즉시 반영과 핫 행 쓰기 경합

가장 단순한 방식은 요청이 들어올 때 사용량 행을 바로 올리는 거예요. 한도 확인과 증가를 한 문장으로 쓰면 그 사이에 다른 요청이 끼지 않아요. 예를 들어 다음처럼 쓸 수 있어요(예시 쿼리예요).

```sql
UPDATE usage_counter
SET calls = calls + 1
WHERE account_id = $1 AND period = $2 AND calls < $3;
```

영향을 받은 행이 0이면 한도에 닿은 거라 호출을 막아요. 화면은 같은 행을 읽으므로 늦지 않아요.

대신 사용량이 많은 계정 하나의 요청이 모두 같은 행을 갱신해요. 행 하나의 쓰기 속도가 그 계정의 호출 속도를 정하게 돼요. 이 병목은 [좋아요와 조회수](/m/hot-counters)에서 다뤄요.

## 이벤트 + 1분 집계 — 기록 부하와 집계 지연

요청 처리 중에는 이벤트 한 줄만 추가해요. 쓰기가 같은 행이 아니라 이벤트 테이블에 쌓여서 한 행에 몰리지 않아요.

합계는 1분마다 따로 계산해요. 1분은 이 글의 예시 간격이에요.

이벤트를 나르는 경로는 [메시지 큐](/m/message-queue), 주기 집계 작업은 [배치 작업](/m/batch-jobs)에서 다뤄요.

문제는 한도 판단도 같은 합계를 본다는 점이에요. 집계 사이에 들어온 호출은 합계에 없으니, 막는 쪽은 한도에 닿았다는 걸 알 수 없어요.

시뮬레이터의 호출 몰림 사건에서는 1분 안에 90건이 들어와요. 집계는 그 전의 40건만 보고 있어서 90건이 모두 통과하고, 한도 100건을 30건 넘겨요.

Stripe의 미터도 청구 기간 동안 이벤트를 어떻게 합칠지 설정으로 정해요. 합계는 Sum, Count, Last 중 하나로 만들어요.

사전 집계 방식은 같은 시간 구간에서 가장 나중에 받은 이벤트만 써요. 값을 더하지 않고 덮어쓴다는 뜻이에요 ([Create and configure a meter](https://docs.stripe.com/billing/subscriptions/usage-based/meters/configure)). 집계 방식을 고르기 전에 이 차이를 알아야 해요.

## 멱등성 키 — 재전송 이벤트의 중복 제거

이벤트는 네트워크 오류나 워커 재시도 때문에 두 번 보내질 수 있어요. 같은 호출이 두 번 세어지면 화면도 청구도 부풀어요. 그래서 각 이벤트에 호출 식별자를 붙이고, 같은 식별자는 한 번만 세요.

Stripe의 Meter Event는 `identifier`를 받아요. 식별자의 고유성은 최소 24시간의 굴러가는 기간 안에서 강제된다고 설명해요.

같은 문서는 이 장치가 주로 아주 짧은 간격의 우발적 재시도를 막기 위한 것이라고 설명해요 ([Create a billing meter event](https://docs.stripe.com/api/billing/meter-event/create)). 그보다 긴 간격의 재전송까지 막는다고는 말하지 않아요.

그래서 저장소 쪽에서도 호출 식별자에 유일 제약을 두는 편이 좋아요.

PostgreSQL에서는 유일 인덱스를 중재자로 두고, 중복 삽입을 `ON CONFLICT DO NOTHING`으로 흘려보낼 수 있어요. 문서는 ON CONFLICT의 중재자로 NOT DEFERRABLE 제약과 유일 인덱스만 쓸 수 있다고 설명해요 ([PostgreSQL INSERT](https://www.postgresql.org/docs/current/sql-insert.html)).

시뮬레이터의 재전송 사건은 호출 70건에 이벤트가 140건 생기는 상황이에요(예시).

| 설정         | 허용 호출 | 잘못 막은 호출 | 청구 건수 |
| ------------ | --------- | -------------- | --------- |
| 멱등성 키 끔 | 54        | 16             | 108       |
| 멱등성 키 켬 | 70        | 0              | 70        |

## 화면 숫자 지연 — 집계 기준 시각 함께 싣기

화면 숫자가 늦는 것은 집계 구조의 결과라서 없애기 어려워요. 대신 숫자가 언제까지 반영됐는지 같이 보여 주는 편이 좋아요.

응답에 집계 기준 시각을 함께 실으면 FE는 "23:55 기준"처럼 표시할 수 있어요. 값과 기준 시각을 같이 싣는 응답 형식은 [대시보드 집계](/m/dashboard-aggregation)에서 다뤄요.

시뮬레이터에서 화면을 보는 시각을 옮기면 기준 시각이 1분 단위로 바뀌는 것을 볼 수 있어요.

## 청구 기간 경계 — 발생 시각 기준과 도착 시각 기준

월말 23시 59분에 보낸 호출이 0시 1분에 도착하면, 이 호출은 이번 달일까요 다음 달일까요? 정답은 정책이에요. 기준을 바꾸면 청구 결과가 달라져요.

| 기준      | 호출이 들어가는 달 | 장점                             | 주의                                   |
| --------- | ------------------ | -------------------------------- | -------------------------------------- |
| 발생 시각 | 호출이 일어난 달   | 사용자가 한 일과 청구가 맞아요   | 마감 뒤 도착한 건을 따로 처리해야 해요 |
| 도착 시각 | 이벤트가 도착한 달 | 마감 전까지 받은 값으로 확정해요 | 발생한 달과 청구 달이 어긋나요         |

시뮬레이터 예시에서 발생 시각 기준이면 23:59 호출은 이번 달에 들어가요. 도착 시각 기준이면 다음 달에 들어가요. 도착 시각 기준에서는 경계 근처의 호출 여섯 건이 발생한 달과 다른 달에 들어가요.

Stripe의 Meter Event는 이벤트 `timestamp`를 받고, 과거 35일 이내이거나 5분 이내의 미래여야 한다고 설명해요 ([Create a billing meter event](https://docs.stripe.com/api/billing/meter-event/create)). 그래서 발생 시각을 이벤트에 실어 보내는 편이 좋아요. 도착 시각만 있으면 발생 시각 기준 청구를 다시 만들 수 없어요.

## 마감과 정정 항목 — 확정 뒤 수정은 정정 항목

청구서가 확정된 뒤에 늦은 이벤트가 도착하면, 확정된 청구서를 다시 여는 대신 정정 항목으로 다음 기간에 넣는 편이 좋아요. 시뮬레이터에서는 발생 시각 기준일 때 00시 3분 마감 뒤에 도착한 23시 59분 50초 호출 한 건이 정정 항목으로 다음 달에 들어가요.

Stripe는 잘못 기록된 이벤트를 Meter Event Adjustment로 취소할 수 있다고 설명해요. 다만 24시간 안에 보낸 이벤트만 취소할 수 있어요.

확정된 청구서에 든 사용량을 취소해도 청구서는 고쳐지지 않고 정정 청구서도 만들어지지 않는다고 설명해요. 음수 수량을 기록해서 고치는 방법도 있다고 설명해요 ([Create and configure a meter](https://docs.stripe.com/billing/subscriptions/usage-based/meters/configure)).

취소 기간이 짧고 확정 뒤에는 취소가 청구서에 반영되지 않으니, 정정은 기존 이벤트를 지우기보다 새 항목을 더하는 쪽이 안전해요.

## 한도 차단과 알림 — 하드 리밋과 소프트 리밋

한도에는 두 종류가 있어요. 하드 리밋은 넘으면 호출을 막아요. 소프트 리밋은 정해 둔 비율(예: 80%)을 넘으면 알림만 보내고 호출은 통과시켜요. 두 이름은 이 글의 설계 용어이고, 출처가 정한 이름은 아니에요.

AWS는 API Gateway의 요청 제한을 토큰 버킷 알고리즘으로 처리한다고 설명해요. 제한과 할당량은 보장된 상한이 아니라 최선 노력의 목표라고도 설명해요.

제한을 넘으면 429 Too Many Requests 응답이 올 수 있고, 클라이언트는 속도를 줄여서 다시 보낼 수 있다고 설명해요 ([API Gateway 요청 제한](https://docs.aws.amazon.com/apigateway/latest/developerguide/api-gateway-request-throttling.html)).

그래서 게이트웨이 제한만으로는 과금 한도를 정확히 맞추기 어려워요. 과금 한도는 현재 숫자를 알아야 판단할 수 있으니, 요청 경로에서 판단하는 편이 좋아요.

Google Cloud는 속도 할당량이 기간이 바뀌면 자동으로 다시 채워지고, 일 단위 할당량은 태평양 시간 자정에 초기화된다고 설명해요 ([Quotas overview](https://cloud.google.com/docs/quotas/overview)). 한도 기간의 시작을 어느 시간대로 둘지도 정책이에요. 청구 기간과 한도 기간의 시간대가 다르면 화면 숫자가 다르게 보일 수 있어요.

## 빠른 카운터와 나중 정산 — 요청 경로 차단과 이벤트 청구

정확한 차단이 필요하면 요청 경로에 빠른 카운터를 두고, 청구는 이벤트로 나중에 맞춰요. 빠른 카운터는 요청마다 바로 올라가서 한도에서 멈춰요.

이벤트는 청구의 원장이 돼요. 두 숫자는 정산 때 비교하고, 차이가 나면 정정 항목으로 맞춰요.

시뮬레이터에서 '이벤트 + 빠른 카운터 차단'을 고르면 한도 초과 허용은 0건이 돼요. 화면 숫자는 여전히 집계 시점까지만 보여요.

빠른 카운터 저장소가 느리거나 죽었을 때 통과시킬지 막을지는 서비스가 정할 일이에요. 그 판단은 [요청 제한 (레이트 리밋)](/m/rate-limiting)에서 다뤄요.

## FE 체크 포인트

**숫자 옆에 기준 시각을 보여 줘요.** 집계 값은 늦을 수 있어요. 기준 시각이 있으면 숫자가 늦은 이유를 사용자에게 설명할 수 있어요.

**한도 판단을 화면 숫자로 하지 않아요.** 화면은 설명만 해요. 막는 쪽은 서버이고, 호출이 막히면 응답의 429 같은 상태 코드를 보고 안내를 바꿔요.

**호출 버튼을 누르자마자 숫자를 올리지 않아요.** 서버 숫자와 어긋난 채로 남아요. 다음 조회 응답의 값을 기다려요.

**재시도할 때 같은 식별자를 보내요.** 네트워크 오류 뒤에 새 식별자를 만들면 같은 호출이 두 번 세어질 수 있어요.

**월말 근처의 숫자 차이를 버그로 단정하지 않아요.** 기준 달과 기준 시각을 함께 보여 줘요.

## 시뮬레이터 안내

시뮬레이터는 기록 방식, 사건, 한도, 멱등성 키, 청구 기준, 화면을 보는 시각을 받아요. 결과로는 다음 다섯 가지를 보여 줘요.

- 화면 숫자
- 실제 호출
- 한도 초과 허용 호출
- 잘못 막은 호출
- 청구 결과

같은 사건에서 기록 방식만 바꿔 보세요. 한도 초과 허용 호출이 어떻게 달라지는지 볼 수 있어요. 모든 수치는 예시이고, 시간 단위는 10초예요.

## 정리 — 기록 방식 · 멱등성 키 · 청구 기준 · 정정 정책 결정

요청마다 카운터는 화면과 한도가 같은 숫자를 봐서 정확하지만, 한 행에 쓰기가 몰려요. 이벤트 집계는 기록이 가볍지만, 화면과 한도 판단이 집계만큼 늦어요. 멱등성 키로 재전송을 한 번만 세고, 청구 기준은 발생 시각과 도착 시각 중 정책으로 고르고, 마감 뒤 수정은 정정 항목으로 넘겨요.

Stripe는 신규 연동에 Metronome을 권장한다고 설명해요. 이 글의 모델은 Meters의 흐름을 예로 들었어요 ([Basic usage-based billing](https://docs.stripe.com/billing/subscriptions/usage-based)). 사용량에 단가를 곱한 금액의 반올림과 최소 단위는 [금액 계산](/m/money-amounts)에서 따로 다뤄요.
