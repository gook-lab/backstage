상품 공유 버튼에 짧은 링크를 붙였어요. 얼마 뒤 상품 페이지 주소를 바꿨는데, 예전 짧은 링크로 들어오는 사람은 여전히 옛 주소로 가요. 어떤 사람은 새 주소로 가고, 어떤 사람은 옛 주소로 가요. 프론트엔드(FE) 입장에서는 같은 링크인데 왜 결과가 다른지 알기 어려워요.

짧은 링크의 뼈대는 짧은 코드와 대상 URL을 짝지은 표예요. 사용자가 코드로 들어오면 백엔드(BE) 서버는 대상 주소를 알려 주는 리다이렉트 응답을 보내요. 이 글은 코드를 만드는 방식, 리다이렉트 상태 코드, 그 응답이 브라우저와 공유 캐시에 남기는 흔적, 클릭 집계를 차례로 봐요.

아래 시뮬레이터에서 방식과 상태 코드를 바꿔 보면 충돌 확률과 옛 주소 여부를 직접 볼 수 있어요.

## 저장 구조 — 코드와 대상 URL을 짝짓는 표

짧은 링크의 핵심은 표 한 줄이에요. 코드, 대상 URL, 만료 시각을 담아요. 코드 열에 기본 키나 `UNIQUE` 제약을 걸면 같은 코드가 두 번 저장되지 않아요.

```sql
CREATE TABLE short_link (
  code       varchar(8) PRIMARY KEY,
  target_url text NOT NULL,
  expires_at timestamptz
);
```

`/s/aB3xK9` 같은 요청이 들어오면 서버는 `code`로 행을 찾고, `target_url`을 `Location` 헤더에 실어 보내요. 여기까지는 누가 만들어도 같아요. 차이는 코드를 어떻게 만드느냐와 리다이렉트 응답을 어떻게 꾸미느냐에서 생겨요.

## 짧은 코드 만들기 — 순번 base62와 무작위 코드

두 방식이 가장 많이 쓰여요. 순번 방식은 행 번호를 62진수 문자열로 바꿔요. 무작위 방식은 코드를 무작위로 뽑고, 저장할 때 중복이면 다시 뽑아요.

### 순번 base62 — 충돌 없는 번호 변환

base62는 숫자 10개, 대문자 26개, 소문자 26개로 62글자를 써요. 번호 `0`은 `0`, `61`은 `z`, `62`는 `10`이 돼요. 번호가 겹치지 않으니 충돌이 없어요.

대신 번호가 이어져 있어요. 코드 하나를 알면 옆 코드를 바로 시도할 수 있어요. 공개 상품 링크라면 나열이 큰 문제가 아닐 수 있어요. 하지만 개인 문서나 주문 링크라면 나열 가능한 코드가 그대로 노출 경로가 돼요.

시뮬레이터에서 순번 방식을 고르고 추측 횟수를 늘려 보면, 0부터 차례로 맞힌 링크 수가 추측 횟수와 같아지는 것을 볼 수 있어요. 숫자 예측 문제는 [분산 ID](/m/distributed-ids) 글의 노출 위험 절과 같은 결이에요.

### 무작위 코드 — 저장 시점 충돌 확인과 재시도

무작위 코드는 나열이 어려워요. 대신 같은 코드가 이미 있는지 저장할 때 확인해야 해요. `SELECT`로 먼저 확인하고 넣으면 확인과 저장 사이에 다른 요청이 끼어들 수 있어요. 그래서 `UNIQUE` 제약에 맡기고, 충돌 오류를 받으면 다른 코드를 뽑아 다시 넣는 편이 좋아요.

| 방식        | 코드 길이              | 중복 처리         | 나열 위험                       | 주의                            |
| ----------- | ---------------------- | ----------------- | ------------------------------- | ------------------------------- |
| 순번 base62 | 번호가 커질수록 길어짐 | 필요 없음         | 높음. 앞에서부터 찾을 수 있어요 | 번호 하나로 옆 링크가 드러나요  |
| 무작위 6자  | 6자 고정               | `UNIQUE` + 재시도 | 낮음. 살아 있는 코드가 흩어져요 | 링크가 많아지면 재시도가 잦아요 |
| 무작위 8자  | 8자 고정               | `UNIQUE` + 재시도 | 더 낮음                         | 메신저에 붙이기에는 조금 길어요 |

## 코드 길이 — 경우의 수와 생일 문제 근사

6자 base62 코드는 62의 6제곱, 약 568억 개의 경우가 있어요. 8자는 약 218조 개예요. 자리가 늘수록 경우의 수가 빠르게 커져요.

충돌 확률은 생일 문제로 어림해요. 무작위 코드 n개 중 같은 코드가 한 쌍이라도 있을 확률은 1 - exp(-n(n-1) / 2N)에 가까워요. N은 경우의 수예요. 365일 달력에서 23명이면 생일이 겹칠 확률이 절반 가까이 되는 계산과 같은 원리예요. 이 식은 근사라서, 정확값과 비교해 오차가 작은지 확인해 두었어요.

예를 들어 링크 100만 개를 6자 무작위로 만들면 충돌이 한 번 이상 날 확률은 99.98%쯤이에요. 예상 충돌은 약 9쌍이에요(예시 계산). 저장 시점의 `UNIQUE`가 데이터를 지켜 주지만, 재시도가 자주 일어나요.

같은 100만 개를 8자로 만들면 충돌 확률은 약 0.23%예요(예시 계산). 같은 링크 수라도 자릿수 하나 차이로 재시도 횟수가 크게 달라져요.

## 리다이렉트 상태 코드 — 영구 · 임시와 메서드 유지

리다이렉트는 3xx 상태 코드와 `Location` 헤더로 이뤄져요. 브라우저는 `Location`의 주소로 다시 요청해요. RFC 9110은 301, 302, 307, 308을 리다이렉트로 정의하고, 307과 308이 메서드를 바꾸지 않는 리다이렉트라고 설명해요.

| 상태 코드 | 영구 여부 | POST 요청 처리          | 헤더 없을 때 캐시 | 대상을 나중에 바꾸면           |
| --------- | --------- | ----------------------- | ----------------- | ------------------------------ |
| 301       | 영구      | GET으로 바뀔 수 있어요  | 가능 (휴리스틱)   | 옛 주소가 남을 수 있어요       |
| 302       | 임시      | GET으로 바뀔 수 있어요  | 기본 아님         | 헤더가 없으면 새 주소를 받아요 |
| 307       | 임시      | 메서드를 바꿀 수 없어요 | 기본 아님         | 헤더가 없으면 새 주소를 받아요 |
| 308       | 영구      | 메서드를 바꿀 수 없어요 | 가능 (휴리스틱)   | 옛 주소가 남을 수 있어요       |

RFC 9110은 301과 302에서 사용자 에이전트가 POST를 GET으로 바꿔도 된다고 설명하고, 307에서는 메서드를 바꾸면 안 된다고(MUST NOT) 정해요. MDN은 308에서 메서드와 본문이 바뀌지 않는다고 설명해요.

짧은 링크는 보통 주소창이나 링크 클릭, 곧 GET으로 열려서 이 차이가 드물게 보여요. 폼이 짧은 링크 주소로 POST를 보내는 경우에만 차이가 나요. 짧은 링크를 만드는 API가 POST인지와는 관계가 없어요.

대상을 바꿀 여지가 있는 링크라면 302나 307을 고르는 편이 좋아요. 영구 상태 코드는 브라우저가 저장해 두고, 나중에 대상을 고쳐도 옛 주소로 갈 수 있어요. 대상이 바뀌지 않는다고 확신할 수 있을 때만 301이나 308을 쓰는 편이 안전해요.

## 리다이렉트 캐시 — 휴리스틱 기본값과 Cache-Control

RFC 9111은 응답을 저장하려면 `max-age` 같은 명시적 기간이 있거나, 상태 코드가 휴리스틱 캐시 가능으로 분류돼야 한다고 설명해요. RFC 9110은 301과 308을 휴리스틱 캐시 가능으로 분류하고, 302와 307은 그 목록에 넣지 않아요.

휴리스틱은 만료 정보가 없을 때 캐시가 기간을 추정하는 방식이에요. RFC 9111은 알고리즘을 정해 두지 않아요. `Last-Modified`가 있으면 그 뒤 기간의 일정 비율을 넘지 않게 잡기를 권하고, 전형적인 값으로 10%를 들어요. 그래서 캐시마다 저장 기간이 달라요.

명시된 `Cache-Control: max-age` 값이 있으면 캐시는 휴리스틱을 쓰지 않아요. 그래서 대상을 바꿀 수 있는 링크에는 기간을 직접 적는 편이 예측하기 쉬워요.

`no-store`는 응답의 어떤 부분도 저장하지 않게 해요(RFC 9111 §5.2.2.5). 시뮬레이터에서 '헤더 없음', 'max-age', 'no-store'를 바꾸면 같은 301이라도 옛 주소 여부가 달라지는 것을 볼 수 있어요. 헤더를 바꾸기 전에 나간 응답은 이미 저장되어 있을 수 있어요.

## 클릭 집계 — 응답 뒤 비동기 기록

클릭 수를 세려면 리다이렉트 요청마다 DB에 써야 해요. 그 쓰기를 응답 전에 기다리면 리다이렉트가 그만큼 느려지고, 쓰기가 실패하면 리다이렉트까지 실패해요. 그래서 리다이렉트 응답을 먼저 보내고, 집계는 메시지 큐나 버퍼에 넘겨 비동기로 처리하는 편이 좋아요.

인기 링크 하나에 클릭이 몰리면 같은 집계 행에 쓰기가 몰리는 문제가 생겨요. 이 병목과 해결 방법은 [핫 카운터](/m/hot-counters) 글에서 자세히 다뤄요. 정확한 숫자보다 추세가 중요하다면 샘플링이나 근사 집계도 골라 볼 수 있어요.

## 열린 리다이렉트 — 대상 URL 검사

짧은 링크 서비스는 사용자가 넣은 URL로 보내 줘요. 검사가 없으면 악성 사이트 주소도 믿을 만한 도메인의 짧은 링크로 바뀌어요. OWASP는 신뢰할 수 없는 입력에 든 URL로 리다이렉트하면 Unvalidated Redirects and Forwards 취약점이 된다고 설명해요. 대상 검사는 [입력 검증](/m/input-validation) 글의 원칙을 그대로 따라요.

OWASP는 외부 목적지를 허용해야 한다면 허용 목록을 파싱한 URL 구성 요소(스킴, 정규화된 호스트, 포트)로 비교하라고 권해요. 공개 단축기는 목적지를 미리 정할 수 없어서 허용 목록만으로는 부족한 경우가 많아요. 그래서 스킴을 `http`와 `https`로만 제한하고, 사용자 정보가 들어간 주소와 내부 주소를 거르는 검사를 함께 두는 편이 좋아요(판단).

## 만료와 삭제 — 404와 410 응답

만료되었거나 삭제된 링크에는 어떤 상태 코드를 줄지 정해야 해요. RFC 9110은 404가 일시적인지 영구적인지 알려 주지 않는다고 설명해요. 서버가 영구적이라고 알고 있다면 404보다 410을 선호한다고 설명해요. 410은 웹 정리를 돕기 위한 응답이고, 기간 한정 프로모션처럼 서비스가 의도적으로 끝난 경우에 흔하다고 설명해요.

404와 410은 둘 다 휴리스틱 캐시 가능이에요(RFC 9110 §15.5.5, §15.5.11). 그래서 한 번 받은 404나 410은 브라우저에 남을 수 있어요. 나중에 같은 코드를 새 링크에 다시 쓰면 옛 404가 보일 수 있어요.

짧은 링크 코드는 재사용하지 않는 편이 좋아요. 순번 방식이라면 지운 번호를 다시 쓰지 않아요.

## 미리보기 봇 — 클릭 부풀림

짧은 링크를 메신저에 붙이면 메신저 서버가 링크를 가져와 미리보기를 만들기도 해요. Slack 문서는 링크가 메시지에 나타나면 Slack이 링크를 크롤링해 미리보기를 제공한다고 설명해요. 이 요청도 리다이렉트를 따라가면 서버에는 클릭처럼 기록돼요. 실제 사람이 누른 수보다 많이 잡힐 수 있어요.

User-Agent로 봇을 거르는 방법은 완전하지 않아요. 흉내 낸 요청을 구별하기 어렵기 때문이에요. 그래서 숫자 이름을 바꾸는 편이 정직해요. '방문'이 아니라 '리다이렉트 요청 수'로 기록하고, 같은 사용자의 반복 요청은 한 번만 세는 식으로 기준을 적어 두세요.

## FE 체크 포인트

- 링크 관리 화면이나 미리보기에서 410은 "더는 쓸 수 없는 링크예요"로, 404는 "찾을 수 없는 링크예요"로 나눠 보여 줘요. 만료와 삭제는 서버가 영구로 알고 있으니 410으로 받는 편이 맞아요.
- 공유 버튼은 짧은 링크 주소 전체를 복사해요. 코드만 받아 화면에서 조립하면 주소 형식이 바뀔 때 복사 결과가 틀어져요.
- 대상 URL 검사에 실패하면 어떤 규칙에 걸렸는지 응답에 담아 화면에 보여 줘요.
- 클릭 수가 공유 직후 바로 늘지 않으면 집계가 비동기라서 그럴 수 있어요. "잠시 뒤 반영돼요"를 붙여요.

## 시뮬레이터 안내

아래 시뮬레이터에서 두 묶음을 나눠 봐요.

- 위쪽은 코드 방식과 링크 수, 추측 횟수를 바꿔 코드 길이, 충돌 확률, 추측 결과를 보는 칸이에요.
- 아래쪽은 상태 코드, 캐시 헤더, 대상 변경 여부를 바꿔 재방문자가 옛 주소로 가는지 보는 칸이에요.

수치는 감을 잡기 위한 예시예요.

## 정리 — 코드 방식 · 상태 코드 · 집계 방식 결정

- 코드는 무작위 코드에 `UNIQUE`와 재시도를 붙이는 방식을 기본으로 골라요. 순번은 나열해도 괜찮은 링크에만 써요.
- 상태 코드는 대상을 바꿀 수 있으면 302나 307로 골라요. 301과 308은 대상이 확정일 때만 써요.
- 캐시는 `Cache-Control`로 기간을 직접 적어요. 휴리스틱에 기대지 않아요.
- 클릭은 리다이렉트 뒤에 비동기로 기록하고, 봇 요청을 구분하는 기준을 적어 둬요.
- 대상 URL은 스킴과 호스트를 검사해 열린 리다이렉트를 막아요.
