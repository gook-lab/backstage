프론트엔드(FE)에서 회원 가입 버튼을 눌렀더니 서버가 `400 Bad Request` 한 줄만 돌려줘요. 화면에는 "입력을 확인해 주세요"만 보이고, 이메일이 틀렸는지 비밀번호가 짧은지는 알 수 없어요. 이 글은 같은 실패를 서버가 어떤 모양으로 보내는지에 따라 FE 화면이 어떻게 달라지는지 따라가요.

글의 응답 예시와 숫자는 설명을 위한 예시예요. 아래 시뮬레이터의 입력값과 같아요.

## 증상 — 한 줄짜리 400이 화면에 남기는 것

`400`은 요청 쪽에 문제가 있다는 사실만 알려 줘요. 어느 칸이 틀렸는지, 사람이 읽을 문장이 무엇인지, 같은 요청을 다시 보내도 되는지는 이 응답에 없어요. 그래서 FE는 실패를 추측해서 문구를 고르거나, 모든 실패를 같은 문구로 덮어요.

## 상태 코드 — 4xx는 요청 쪽, 5xx는 서버 쪽 책임

RFC 9110은 상태 코드가 요청의 결과와 응답의 의미를 나타낸다고 정의해요. 이 글에서 다루는 코드는 아래와 같아요.

| 코드                             | RFC 정의 요지                                                                       | 책임 쪽               |
| -------------------------------- | ----------------------------------------------------------------------------------- | --------------------- |
| 400 Bad Request                  | 문법이나 형식 때문에 처리할 수 없다고 판단한 클라이언트 오류                        | 요청 쪽               |
| 401 Unauthorized                 | 유효한 인증 정보가 없어 요청을 적용하지 않음. `WWW-Authenticate`를 함께 보내야 해요 | 요청 쪽               |
| 403 Forbidden                    | 요청은 이해했지만 응하지 않음. 자격과 무관한 이유일 수도 있어요                     | 요청 쪽               |
| 404 Not Found                    | 현재 표현을 찾지 못함. 있다는 사실을 숨기려고 쓰기도 해요                           | 요청 쪽               |
| 409 Conflict                     | 대상의 현재 상태와 충돌함. 사용자가 해결하고 다시 보낼 수 있어요                    | 요청 쪽 (상태와 충돌) |
| 422 Unprocessable Content        | 형식은 맞지만 내용을 처리할 수 없음                                                 | 요청 쪽               |
| 429 Too Many Requests (RFC 6585) | 짧은 시간에 요청이 너무 많음                                                        | 요청 쪽 (빈도)        |
| 500 Internal Server Error        | 서버가 예기치 않은 상황을 만남                                                      | 서버 쪽               |
| 503 Service Unavailable          | 일시적 과부하나 점검. `Retry-After`로 기다릴 시간을 알릴 수 있어요                  | 서버 쪽               |

OWASP 에러 처리 치트 시트도 같은 구분을 써요. 클라이언트 쪽 오류에는 4xx를, 서버에서 생긴 예기치 않은 버그에는 5xx를 쓰라고 설명해요.

## 200 응답 — 본문에 에러를 담을 때 생기는 일

`200 OK` 본문에 `{ "error": "이미 가입된 이메일이에요" }`를 담는 응답이 자주 보여요. RFC 9110에서 200은 요청이 성공했다는 상태 코드예요. MDN은 `Response.ok`가 상태 코드가 200~299 범위인지 여부라고 설명해요. 그래서 `response.ok`만 보는 FE 코드는 이 실패를 성공으로 지나가요.

재시도 신호도 사라져요. RFC 9110은 `Retry-After`를 503이나 3xx 응답에서 기다릴 시간을 알리는 데 쓴다고 설명해요. 200에는 "잠시 후 다시 시도" 버튼을 뒷받침할 상태 코드가 없어요.

## Problem Details — 다섯 멤버로 실패를 같은 모양에

RFC 9457은 HTTP API의 오류를 담는 문제 상세(problem detail) 객체를 정의해요. RFC 7807을 대체한 문서예요. 본문은 `application/problem+json` 미디어 타입으로 보내요. 기본 멤버는 아래 다섯 개예요.

| 멤버       | RFC 9457 정의 요지                                                          | 쓰는 방식                                                  |
| ---------- | --------------------------------------------------------------------------- | ---------------------------------------------------------- |
| `type`     | 문제 종류를 가리키는 URI 참조. 소비자가 식별하는 기본 키예요                | FE 분기 기준. 주소를 자동으로 열어 보지 않아요             |
| `title`    | 종류의 짧은 요약. 종류가 같으면 바뀌지 않아야 하고, 번역만 예외예요         | 사람이 읽는 참고용                                         |
| `status`   | HTTP 상태 코드의 복사본. 실제 응답 상태와 같아야 해요                       | 중간 장비가 상태를 바꿨을 때 원래 상태를 확인하는 용도예요 |
| `detail`   | 이번 발생에 대해 사람이 읽는 설명. 고치는 데 도움이 되는 내용이어야 해요    | 화면 문장으로만 써요. 파싱하지 않아요                      |
| `instance` | 이번 발생을 가리키는 URI 참조. 주소로 열 수 없으면 불투명한 고유 식별자예요 | 문의용 요청 번호로 써요                                    |

예시 본문은 이래요. `type` 주소는 설명을 위한 예시 주소예요.

```json
{
  "type": "https://example.com/problems/invalid-input",
  "title": "입력값을 확인해 주세요",
  "status": 422,
  "errors": [{ "detail": "올바른 이메일 형식이 아니에요", "pointer": "#/email" }]
}
```

## 필드 오류 — errors 확장과 pointer

RFC 9457은 문제 종류마다 확장 멤버를 더할 수 있다고 정해요. 소비자는 알아볼 수 없는 확장을 무시해야 해요.

RFC의 검증 오류 예시는 `errors` 배열에 칸별 `detail`과 JSON Pointer 형식의 `pointer`를 담아요. 이 예시는 가상의 문제 종류(fictional problem type)를 쓰므로, `errors`라는 이름이 표준으로 정해진 것은 아니에요. 이 글은 RFC 예시가 보여 주는 모양을 빌려 쓰는 방법을 다뤄요.

RFC는 서로 다른 종류의 문제가 여러 개면 가장 중요한 문제 하나를 보내는 편을 권해요. 그래서 칸 오류 묶음은 같은 종류 안에서 쓰는 편이 자연스러워요. 이 부분은 설계 판단이에요.

## 코드와 문장 — type은 기계가, detail은 사람이

FE가 분기할 기준은 `type`과 상태 코드예요. `detail`은 사람이 읽는 문장이라 문구가 바뀔 수 있어서, 분기에 쓰면 안 돼요. 다국어 문장을 서버에서 만들지 화면에서 만들지는 설계 판단이에요. 언어 협상과 번역 위치는 [날짜 · 시간대 · 다국어](/m/time-and-locale)에서 다뤄요.

## 내부 정보 — 스택과 SQL은 로그에만

RFC 9457의 보안 고려사항은 오류 세부 정보로 시스템이나 사용자 정보가 새어 나갈 수 있다고 경고해요. 스택 덤프 같은 구현 세부를 HTTP 인터페이스로 보여 주지 말라고 권해요.

OWASP 에러 처리 치트 시트도 예외 메시지가 그대로 나오면 프레임워크 버전 같은 기술 스택이 드러나는 예를 들어요. 같은 문서는 사용자에게는 일반 응답을 주고, 자세한 내용은 서버 로그에 남기라고 설명해요.

그래서 응답에는 요청 번호(`instance`)만 두고, 원인은 로그에서 그 번호로 찾아요. 로그와 추적 방법은 [로그 · 트레이스로 원인 찾기](/m/observability)에서 다뤄요.

## 재시도 신호 — 503 · 429와 Retry-After

RFC 9110은 503 응답에 `Retry-After` 헤더를 보내 기다릴 시간을 알릴 수 있다고 정의해요. 값은 날짜 또는 초 단위 숫자예요. RFC 6585는 429가 과도한 요청을 뜻하고, 응답에 `Retry-After`를 함께 보낼 수 있다고 정의해요.

그래서 FE는 재시도 버튼을 본문 문장으로 추측하지 않고, 상태 코드와 헤더로 정해요. 이 글의 기준은 503 또는 429이면서 `Retry-After`가 있을 때만 버튼을 보여 주는 거예요. 이 기준은 설계 판단이에요.

자동 재시도는 따로 봐야 해요. RFC 9110은 PUT, DELETE, 안전한 메서드만 멱등하다고 정의해요. POST는 이 목록에 없어서, 가입이나 결제 요청을 같은 방식으로 다시 보내면 중복이 생길 수 있어요. 재시도 기준은 [타임아웃과 커넥션 풀](/m/timeouts-and-pools)과 [레이트 리밋 알고리즘](/m/rate-limiting)에서 더 자세히 다뤄요.

## 형식 통일 — 모든 API에 같은 에러 모양

엔드포인트마다 에러 모양이 다르면 FE 파서도 엔드포인트마다 달라져요. 그래서 한 형식으로 맞추고, 종류 목록(`type`)을 문서로 함께 관리하는 편이 좋아요. 이 부분도 설계 판단이에요.

## FE 체크 포인트 — 파서 한 곳과 화면 위치

- 응답 파서는 한 곳에 둬요. `application/problem+json`이면 `errors`를 칸별 오류로 나누고, 아니면 상태 코드 기준 일반 메시지로 바꿔요.
- 칸 오류는 입력칸 옆에 둬요. `pointer`로 칸을 찾고, 칸을 찾지 못한 오류는 상단 메시지로 올려요.
- 전역 오류는 배너나 토스트로 보여 줘요. 503이나 500처럼 입력칸과 무관한 실패가 여기에 들어가요.
- 알 수 없는 `type`은 일반 메시지로 물러나요. RFC 9457은 소비자가 모르는 확장을 무시하라고 정해요. 모르는 `type`을 같은 방식으로 받는 것은 FE 설계 판단이에요.
- 요청 번호(`instance`)를 문의용으로 보여 주고 복사할 수 있게 해요. 추적 연결은 로그 글과 같은 흐름이에요.
- 화면 검증은 즉각 피드백용으로만 써요. OWASP 입력 검증 치트 시트는 클라이언트 검증이 우회될 수 있으니, 서버에서 같은 규칙을 다시 확인해야 한다고 설명해요.

## 시뮬레이터 안내

아래 시뮬레이터는 같은 입력(이메일 `kim@`, 비밀번호 `123`, 닉네임 비움)에 대해 서버 응답 방식 세 가지와 실패 네 가지를 골라 볼 수 있어요. 기본값은 problem+json 입력 오류예요.

방식을 텍스트 한 줄로 바꾸면 칸 옆 오류가 사라지고 일반 메시지만 남아요. 200 에러 문자열로 서버 과부하를 고르면 재시도 버튼이 사라져요.

## 정리 — 상태 코드 책임 · 문제 형식 · 재시도 신호 기준

실패의 책임은 상태 코드로 나누고, 실패 본문은 problem+json으로 통일해요. 칸 오류는 `errors`와 `pointer`로 보내요. FE 분기는 `type`과 상태 코드로 하고, `detail`은 화면 문장으로만 써요.

재시도 버튼은 503 또는 429와 `Retry-After`가 함께 있을 때만 보여요. 스택과 SQL은 응답에 넣지 않고, 요청 번호로 로그를 찾아요.
