외부 API 키를 `.env` 파일에 넣고 `import.meta.env`로 읽었다고 해 볼게요. 그런데 배포한 뒤 브라우저 개발자 도구에서 빌드된 JS 파일을 열어 보면 키 문자열이 그대로 보여요. 이 글은 왜 그런지, 어떤 값을 브라우저에 보내도 되는지, 비밀 값은 어디에 둬야 하는지, 키가 샜을 때 무엇부터 해야 하는지 정리해요.

아래 시뮬레이터에서 빌드 도구와 각 값의 자리, 접두를 바꿔 보면 배포 번들에 들어가는 값과 판정이 바로 바뀌어요. 글과 시뮬레이터의 값 이름은 모두 가짜 예시예요.

## 번들 노출 — 빌드할 때 문자열로 박히는 값

Vite 문서는 `import.meta.env`로 노출되는 상수가 빌드할 때 정적으로 치환된다고 설명해요. `VITE_` 접두가 붙은 변수는 클라이언트 소스 코드에 노출돼요. 그래서 `VITE_SOME_KEY=123`은 브라우저에서 `"123"`으로 읽히고, 접두가 없는 `DB_PASSWORD`는 `undefined`가 돼요.

Next.js 문서도 같은 구조예요. `NEXT_PUBLIC_` 접두가 붙은 변수는 `next build` 때 `process.env.NEXT_PUBLIC_…` 참조가 값으로 바뀌어 JS 번들에 들어가요. 접두가 없는 변수는 Node.js 환경에서만 읽을 수 있어요.

이름을 변수에 담아 `process.env[varName]`으로 찾으면 치환되지 않는다고도 설명해요.

| 구분                 | Vite                                 | Next.js                                             |
| -------------------- | ------------------------------------ | --------------------------------------------------- |
| 번들에 들어가는 조건 | `VITE_` 접두 + 빌드 환경에 값이 있음 | `NEXT_PUBLIC_` 접두 + `next build` 환경에 값이 있음 |
| 접두가 없는 값       | 브라우저 코드에서 `undefined`        | 서버(Node.js)에서만 읽음                            |
| 값을 바꾸려면        | 재빌드                               | 재빌드 (빌드 뒤 `NEXT_PUBLIC_` 값은 바뀌지 않아요)  |

핵심은 접두가 노출 여부를 정하는 스위치라는 점이에요. 접두를 붙인 값은 빌드 환경에 있는 순간 공개 값이 돼요. 그래서 접두를 붙이기 전에 그 값을 브라우저에 보내도 되는지부터 물어보는 편이 좋아요.

## 공개 값과 비밀 값 — 브라우저에 보내도 되는 기준

The Twelve-Factor App은 자격 증명을 포함해 배포마다 달라지는 설정을 환경 변수에 두라고 설명해요. 같은 문서는 코드를 지금 공개해도 자격 증명이 새지 않는지를, 설정이 코드 밖에 있는지 보는 시험으로 설명해요. Vite 문서도 `VITE_*` 변수에 API 키 같은 민감 정보를 담지 말라고 설명해요.

| 값                                    | 브라우저에 보내도 되나요 | 이유                                                                                      |
| ------------------------------------- | ------------------------ | ----------------------------------------------------------------------------------------- |
| API 주소 (`https://api.example.test`) | 돼요                     | 접근을 막는 값이 아니라 호출할 주소예요.                                                  |
| 브라우저용으로 발급된 공개 키         | 돼요, 제한을 함께 걸어요 | 서비스가 브라우저에서 쓰도록 낸 키예요. 어떤 키가 여기에 드는지는 서비스 문서로 확인해요. |
| 결제 서버 비밀 키                     | 안 돼요                  | 키를 가진 쪽이 서비스의 권한을 써요.                                                      |
| DB 비밀번호                           | 안 돼요                  | DB에 직접 접속하는 자격 증명이에요.                                                       |
| 토큰 서명 키                          | 안 돼요                  | 이 키로 토큰을 만들 수 있어요.                                                            |

판단이 애매하면 값이 노출됐을 때 피해를 떠올려 보세요. 노출돼도 괜찮은 값이면 공개 값이고, 아니면 비밀 값이에요.

## 공개 키 — 사용처와 사용량 제한 걸기

Google Cloud 문서는 제한이 없는 API 키는 안전하지 않다고 설명해요. 제한은 두 가지예요.

- **API 제한**: 키로 부를 수 있는 API를 정해요.
- **애플리케이션 제한**: 키를 쓸 수 있는 웹사이트 · IP · 앱을 정해요.

같은 문서는 두 제한을 같이 걸라고 권해요.

같은 문서에 따르면 `https://example.com`을 웹사이트 제한에 넣으면 그 주소에서 온 호출만 키를 쓸 수 있어요. 제한은 키가 노출됐을 때 영향 범위를 줄여요.

키를 주기적으로 교체하면 손상된 키의 영향을 제한할 수 있다고도 설명해요. 사용량 모니터링은 권한 없는 사용을 알리는 데 도움이 된다고 설명해요.

주의할 점은 제한이 키 문자열을 가리지 않는다는 거예요. 번들에 있는 키는 누구나 읽을 수 있고, 제한은 그 키로 할 수 있는 일의 범위를 좁힐 뿐이에요.

## 서버 프록시 — 자격 증명을 서버에서 붙이는 구조

Google 문서는 API 키를 클라이언트 코드에 넣거나 저장소에 커밋하면 가로채기나 도난에 열려 있다고 설명해요. 그래서 클라이언트는 요청을 서버에 보내고, 서버가 자격 증명을 붙여 요청하라고 권해요.

화면 단위 서버 한 층 구조인 BFF(Backend For Frontend)는 [화면 단위 API 글](/m/api-composition)에서 다뤄요.

| 항목           | 브라우저가 직접 호출              | 서버(BFF)가 대신 호출                     |
| -------------- | --------------------------------- | ----------------------------------------- |
| 자격 증명 위치 | 번들 안                           | 서버 실행 환경이나 비밀 관리 서비스       |
| 키 교체        | 번들을 다시 빌드해야 할 수 있어요 | 서버 설정만 바꿔요                        |
| 호출 조건      | 브라우저 코드를 믿어야 해요       | 서버에서 사용자 권한과 요청 수를 확인해요 |
| 화면이 받는 것 | 외부 API 응답을 그대로 받아요     | 서버가 정한 응답 모양을 받아요            |

프록시를 거치면 외부 API의 오류 응답을 그대로 넘길지 다른 코드로 바꿀지는 서버가 정해요. 화면은 프록시가 준 코드와 본문을 기준으로 처리해요. 요청 수 제한은 [레이트 리밋 글](/m/rate-limiting)에서 이어 봐요.

## 비밀 관리 서비스 — 값을 두는 자리와 교체 주기

OWASP 치트 시트는 비밀이 소스 코드와 설정 파일에 평문으로 흩어진다고 설명해요. 그래서 비밀의 저장, 발급, 감사, 교체를 한 곳에서 관리할 필요가 커지고 있다고 설명해요.

최소 권한 원칙을 적용해서 엔지니어가 모든 비밀에 접근하지 못하게 하라고 권해요.

OWASP는 비밀을 정기적으로 교체해서 훔친 자격 증명이 짧은 시간만 쓰이게 하라고 설명해요. 교체는 보통 새 값 만들기, 새 값 설정, 새 값 시험, 교체 마무리 순서로 나뉘어요. 클라우드 비밀 관리 서비스는 예약된 자동 교체를 지원하는 경우가 많다고 설명해요.

| 자리                        | 누가 읽나                                   | 값을 바꾸는 방법                                                 |
| --------------------------- | ------------------------------------------- | ---------------------------------------------------------------- |
| 빌드 환경 (`.env`, CI 변수) | 빌드 과정. 접두가 붙은 값은 번들에 들어가요 | 값을 바꾸고 재빌드해요                                           |
| 서버 실행 환경              | 서버 프로세스                               | 새 값을 넣고 프로세스를 다시 시작해요                            |
| 비밀 관리 서비스            | 서버가 실행 중에 가져가요                   | 새 버전을 만들고, 서버가 새 버전을 읽게 한 뒤 옛 버전을 폐기해요 |

앱을 다시 시작해도 훔친 자격 증명은 무효가 되지 않아요. OWASP는 자격 증명이 뒤의 서비스에서 만료되거나 폐기되기 전까지는 계속 쓸 수 있다고 설명해요.

## 노출 대응 — 폐기 · 교체 · 사용 기록 확인

GitHub는 비밀 스캐닝 알림을 받으면 영향을 받은 자격 증명을 즉시 교체하라고 설명해요. 교체나 폐기가 끝나면 그 값으로는 더 접근할 수 없어서, 이 단계만으로 문제가 풀릴 수 있다고 GitHub 문서는 설명해요.

1. 노출된 값을 먼저 폐기하거나 교체해요.
2. 값이 들어간 빌드를 버리고 새 빌드를 배포해요. 이전 번들은 이전 값을 담고 있어요.
3. 빌드 환경(`.env`, CI 변수)에서 비밀 값을 지워요.
4. 사용 기록을 확인해요. Google 문서는 API 사용량을 모니터링하면 권한 없는 사용을 알리는 데 도움이 된다고 설명해요.
5. 커밋 이력 정리는 마지막에 검토해요.

## 커밋 이력 — 교체 뒤에 정리하는 순서

비밀을 커밋했다가 다음 커밋에서 지워도, 이전 커밋에는 값이 그대로 남아요. OWASP는 노출 기록을 커밋 이력에서 지우려면 이력을 다시 써야 하고, 그러면 다른 커밋 링크가 깨질 수 있다고 설명해요.

GitHub 문서는 이력에서 민감 정보를 지우기 전에 먼저 자격 증명을 폐기하거나 교체하라고 설명해요. 폐기가 끝나면 이력 정리가 꼭 필요하지 않을 수 있다고도 설명해요. 이력을 다시 쓰면 커밋 해시가 바뀌고, 이전 클론을 가진 개발자가 `git pull` 뒤 `git push` 하면 민감 정보가 다시 돌아올 수 있다고 설명해요.

로컬 설정 파일은 Git에서 빼 두세요. Vite 문서는 `*.local` 파일을 `.gitignore`에 넣으라고 설명해요. Next.js 기본 템플릿도 `.env` 파일을 `.gitignore`에 넣어 둬요.

## FE 체크 포인트

- `import.meta.env`나 `process.env`로 읽는 이름에 접두가 맞는지 봐요. 접두가 없으면 브라우저 코드에서 `undefined`가 되는지 확인해요.
- 배포된 결과물에서 키 문자열을 검색해 봐요. 검색되면 그 값은 번들에 들어간 거예요.
- 브라우저 코드가 외부 API를 직접 부르는지 봐요. 직접 부른다면 그 호출에 자격 증명이 실리는지 확인해요.
- 프록시가 외부 오류를 어떻게 바꾸는지 응답 코드로 확인해요. 요청 제한 응답은 [레이트 리밋 글](/m/rate-limiting)에서 봐요.
- 값을 코드 밖에서 바꾸는 방식은 [기능 플래그 글](/m/feature-flags)에서 이어 봐요.

## 시뮬레이터 안내

아래 시뮬레이터에서 빌드 도구를 고르고, 값마다 자리와 접두를 바꿔 보세요. 판정 표에 각 값이 번들에 들어가는지와 판정이 나와요. 노출 판정이 있으면 노출됐을 때 할 일도 함께 나와요.

먼저 `잘못 만든 예`를 보고, `권장`과 비교해 보세요. 모든 값은 가짜 예시예요.

## 정리 — 접두 규칙 · 값 자리 · 노출 대응 순서

- 접두가 붙은 값만 번들에 들어가요. 접두는 노출 여부를 정하는 스위치로 다뤄요.
- 비밀 값은 서버나 BFF 뒤에 두고, 브라우저에는 공개 값만 보내요.
- 공개 키에도 사용처 제한과 사용량 감시를 같이 걸어요.
- 비밀은 비밀 관리 서비스에 두고 정기적으로 교체해요.
- 노출되면 폐기와 교체, 재빌드, 사용 기록 확인 순서로 대응해요. 커밋 이력 정리는 마지막에 검토해요.
