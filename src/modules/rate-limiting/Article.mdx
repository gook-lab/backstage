API를 호출했더니 `429 Too Many Requests`가 왔어요. 화면에는 "잠시 후 다시 시도해 주세요"만 떠 있어요. 서버는 무엇을 세고 있었고, 언제 다시 보내야 할까요?

답은 두 부분이에요. 서버가 어떤 규칙으로 요청을 세는지, 그리고 그 규칙이 응답 헤더와 클라이언트 재시도에 어떻게 전해지는지예요. 글의 숫자는 설명을 위한 예시예요. 아래 시뮬레이터의 기본값과 같고, 시뮬레이터에서 시간은 3초이고 한도는 1초에 5건이에요.

## 키 선택 — IP · 사용자 · API 키 중 무엇으로 셀지

서버는 "누구의 요청을 세는지"를 먼저 정해요. 이 값을 키라고 해요. Redis 문서는 레이트 리밋 카운터를 사용자, IP, API 키, 테넌트, 모델처럼 제한하려는 차원마다 따로 둔다고 설명해요. 키를 고르는 기준은 세 가지예요.

| 키     | 잘 맞는 경우                        | 주의                                                    |
| ------ | ----------------------------------- | ------------------------------------------------------- |
| IP     | 로그인 전 요청까지 막아야 할 때     | 같은 공유기나 회사 망 뒤의 사용자가 한 IP를 나눠 써요   |
| 사용자 | 로그인한 한 사람씩 공평하게 막을 때 | 로그인 전에는 쓸 수 없어요                              |
| API 키 | 외부 개발자에게 할당량을 줄 때      | 키 하나를 여럿이 나눠 쓰면 한 사람이 다른 사람을 막아요 |

AWS API Gateway는 계정 단위와 리전 단위 한도도 따로 둬요. 키는 하나만 고르는 것이 아니라, 여러 한도를 겹쳐 거는 경우가 많아요. 이 부분은 설계 판단이에요.

## 다섯 알고리즘 — 같은 한도도 허용 방식이 달라요

한도는 "1초에 5건"으로 같아요. 그런데 요청이 1초 경계 앞 100ms에 5건, 뒤 100ms에 5건 몰리면 결과가 달라요.

고정 창에서는 앞뒤 요청이 서로 다른 창에 들어가요. 각 창의 카운터는 5건까지만 세니까 10건이 모두 통과해요. 1초 안에 처리되는 양이 한도의 두 배가 되는 셈이에요. 이 결과는 고정 창의 정의에서 나오는 계산이에요. 출처 문장을 옮긴 것이 아니에요.

| 알고리즘        | 저장하는 상태              | 경계 문제                                             | 버스트 허용                         | 근거                                       |
| --------------- | -------------------------- | ----------------------------------------------------- | ----------------------------------- | ------------------------------------------ |
| 고정 창         | 창마다 카운터 하나         | 경계 양쪽에서 각각 한도까지 통과해요                  | 창 안에서는 한도까지 한꺼번에       | Redis는 INCR와 EXPIRE로 구현해요           |
| 슬라이딩 로그   | 허용된 요청 시각 전부      | 최근 1초 기준으로 정확히 세요                         | 한도 안에서만                       | 요청 수에 비례해 메모리를 써요 (설계 판단) |
| 슬라이딩 카운터 | 창마다 카운터 두 개        | 비율로 섞어 추정해서 조금 넘을 수 있어요              | 한도 안에서만                       | Cloudflare 블로그                          |
| 토큰 버킷       | 토큰 수와 마지막 갱신 시각 | 고정 창의 경계 문제는 없고, 버킷에 모인 만큼만 나가요 | 버킷 용량만큼 한꺼번에              | AWS API Gateway · Stripe 블로그            |
| 누수 버킷       | 대기열                     | 처리 간격이 일정해요                                  | 대기 칸만큼 쌓이고, 처리는 일정해요 | nginx limit_req                            |

시뮬레이터에서 **창 경계에 몰림**을 골라 보세요. 고정 창은 10건을 모두 처리해요. 슬라이딩 로그는 5건만 처리하고 나머지는 429가 돼요. 토큰 버킷도 5건만 처리해요.

## 슬라이딩 카운터 — 이전 창을 비율로 섞은 추정

슬라이딩 로그는 정확하지만 요청마다 시각을 저장해야 해요. 슬라이딩 카운터는 창마다 개수 두 개만 들고, 이전 창의 개수에 겹치는 비율을 곱해 더해요. Cloudflare 블로그의 예시를 그대로 옮기면 이래요. 한도가 1분에 50건이고, 현재 1분은 15초 지났고, 현재 창에 18건, 이전 1분에 42건이 있었다고 해요.

> 42 × ((60 − 15) / 60) + 18 = 42 × 0.75 + 18 = 49.5

추정값이 49.5라서 한 건만 더 오면 한도를 넘어요. 이 블로그는 4억 건 요청(27만 개 출처)을 분석해서 0.003%의 요청만 잘못 허용하거나 막았다고 보고해요. 실제 비율과 추정 비율의 평균 차이는 6%였다고 해요. 이 수치는 그 블로그의 측정이에요. 여러분의 서비스에서도 같다는 뜻은 아니에요.

시뮬레이터에서 슬라이딩 카운터를 고르면 같은 패턴에서 한도보다 1건 많은 6건이 1초 안에 처리돼요. 추정이라 생기는 차이예요.

## 토큰 버킷과 누수 버킷 — 평균은 같고 모양이 다름

토큰 버킷은 요청마다 토큰 하나를 쓰고, 토큰은 일정한 속도로 채워져요. AWS API Gateway 문서는 이 방식을 그대로 설명해요. 버스트는 정해진 만큼 한도를 넘을 수 있어요. 그리고 문서는 이 값들을 보장된 최댓값이 아니라 목표로 보라고 말해요.

Stripe는 중앙 버킷에서 요청마다 토큰을 가져가고, 천천히 토큰을 채우고, 버킷이 비면 요청을 거절한다고 설명해요.

누수 버킷은 요청을 대기열에 쌓고 일정한 간격으로 흘려보내요. nginx의 `limit_req`는 이 방식이에요. 예를 들어 `rate=1r/s burst=5`는 평균 초당 1건을 허용하고, 5건까지는 지연해서 처리해요. 지연을 원하지 않으면 `nodelay`를 붙여요. 지연된 요청이 버스트 크기를 넘으면 에러로 끝나요.

누수 버킷에서는 "통과"와 "처리 시각"이 달라요. 시뮬레이터의 처리 줄을 보면 통과한 요청이 일정한 간격으로 밀려서 처리되는 것을 볼 수 있어요.

## 서버가 여럿일 때 — 카운터 위치

서버 두 대가 각자 카운터를 가지면, 로드 밸런서가 요청을 나눠 줄 때 한도가 서버 수만큼 불어나요. 이 결과는 구조에서 나오는 계산이에요. 각 서버는 자기 카운터만 보고 한도 안이라고 판단하니까요. 시뮬레이터에서 **고른 흐름 (약속의 1.5배)**을 골라 보세요. 서버 한 대에서는 1초에 5건만 처리돼요. 서버 두 대가 카운터를 각자 가지면 1초에 8건이 처리돼요.

공유 카운터는 이 문제를 줄여요. Redis 문서는 INCR와 EXPIRE로 원자적인 고정 창 카운터를 만들 수 있고, 모든 인스턴스에서 같은 한도를 걸 수 있다고 설명해요.

INCR는 키가 없으면 0으로 만든 뒤 1을 더해요. 읽고, 판단하고, 갱신하는 과정을 Lua 스크립트(EVAL)로 묶으면 원자적으로 실행된다고 설명해요. 그래야 동시에 들어온 요청이 토큰을 두 번 쓰거나 카운터 갱신을 잃지 않아요.

다만 요청 경로에 Redis 호출을 넣으면 Redis가 느리거나 죽었을 때 어떻게 할지 정해야 해요. 통과시킬지 막을지는 서비스가 정할 설계 판단이에요.

## 429와 Retry-After — 다음 시각 알림

RFC 6585는 429를 "정해진 시간 안에 사용자가 너무 많은 요청을 보냈다"는 뜻으로 정의해요. 응답에는 `Retry-After` 헤더를 붙일 수 있어요. RFC 9110은 이 헤더 값을 HTTP 날짜나 초 단위 숫자 중 하나로 정의해요. MDN도 같은 두 형식을 설명해요.

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 30
```

IETF의 RateLimit 헤더 초안은 서버가 정책과 남은 한도를 헤더로 알려 주는 방법을 정의해요. 필드 이름은 `RateLimit-Policy`와 `RateLimit`이에요. 이 문서는 아직 RFC가 아니라 인터넷 초안이에요. 2026년 11월 20일에 갱신된 12번째 개정본을 기준으로 봤어요. 이름과 형식은 바뀔 수 있어요.

백오프와 jitter로 재시도 간격을 정하는 방법은 [가상 대기실 · 처리량 제한](/m/waiting-room)에서 자세히 다뤄요. 여기서는 429가 어떤 신호인지만 봐요.

## FE 체크 포인트

- 429를 받으면 `Retry-After`를 읽고, 그 시각 전에는 같은 요청을 보내지 마세요. 헤더가 없으면 백오프 규칙을 따르세요.
- 버튼은 요청이 끝날 때까지 비활성화하세요. 연타로 같은 요청이 여럿 나가면 서버 한도를 대신 쓰는 셈이에요.
- 자동 재시도 라이브러리와 버튼 연타가 겹치면 요청이 곱해져요. 재시도는 한 곳에서만 하세요.
- 중복 요청이 위험한 작업(결제 같은 것)은 재시도 전에 서버의 멱등성 키를 먼저 확인하세요. [결제 — 이중 결제 막기](/m/payment-idempotency)를 참고하세요.
- 화면에는 "잠시 후 다시"보다 몇 초 뒤 가능한지를 보여 주세요. `Retry-After`가 있으면 그 값을 쓰세요.
- 클라이언트에서 초당 호출 횟수를 줄이는 것은 좋지만, 서버 한도를 대신하지 못해요. 서버는 여전히 막아야 해요.

## 정리 — 키 · 알고리즘 · 공유 카운터 선택

서버는 키별로 요청을 세고, 알고리즘에 따라 경계에서 통과하는 양이 달라요. 고정 창은 경계에서 두 배까지 통과할 수 있고, 슬라이딩 카운터는 추정이라 조금 넘을 수 있어요. 토큰 버킷은 버스트를 허용하고, 누수 버킷은 처리를 일정하게 만들어요.

서버가 여럿이면 카운터를 공유해야 한도가 지켜져요. 429를 받으면 `Retry-After`를 따르고, 재시도와 연타를 한 곳에서만 막으세요.

시뮬레이터에서 패턴과 알고리즘, 서버 구성을 바꿔 가며 1초 최대 처리량이 어떻게 달라지는지 확인해 보세요.
