두 사람이 같은 상품을 거의 동시에 저장하는 상황을 떠올려 볼게요. 화면에는 둘 다 "저장됐어요"가 떴는데, DB 를 보면 한 사람의 변경이 사라져 있어요. 왜 이런 일이 생기고, 프론트엔드가 무엇을 알아야 하는지 이 글에서 정리해요.

아래 시뮬레이터에서 같은 상황을 한 단계씩 직접 돌려 볼 수 있어요. 글의 SQL 과 시뮬레이터의 동작은 같은 규칙을 따라요.

## 트랜잭션 — 여러 문장을 한 덩어리로 묶기

트랜잭션은 여러 문장을 "전부 아니면 전혀 아님"으로 묶는 단위예요. PostgreSQL 문서도 트랜잭션을 all-or-nothing 연산이라고 설명해요. 그 중간 상태는 동시에 실행 중인 다른 트랜잭션에게 보이지 않아야 해요.

ACID 를 한 줄씩 보면 이래요.

| 속성                 | 뜻                                                | 이 글에서 다루는 정도        |
| -------------------- | ------------------------------------------------- | ---------------------------- |
| 원자성 (Atomicity)   | 전부 반영되거나 전혀 반영되지 않아요              | 롤백이 무엇을 되돌리는지     |
| 일관성 (Consistency) | 제약 조건을 지키는 상태로만 끝나요                | 재고가 음수가 되지 않는 조건 |
| 격리성 (Isolation)   | 동시 실행이 서로의 중간 상태를 엿보지 못하게 해요 | 이 글의 중심이에요           |
| 지속성 (Durability)  | 커밋된 결과는 장애 뒤에도 남아요                  | 여기서는 깊이 다루지 않아요  |

동시 저장 문제는 대부분 격리성에서 나와요.

## 갱신 손실 — 읽고 계산해서 쓰는 패턴

가장 흔한 실수는 "읽고, 앱에서 계산하고, 다시 쓰는" 패턴이에요. 재고가 2 인 상품을 두 사람이 한 개씩 사는 상황으로 볼게요.

| 순서 | 트랜잭션 A                                  | 트랜잭션 B                                                               |
| ---- | ------------------------------------------- | ------------------------------------------------------------------------ |
| 1    | `SELECT stock FROM items WHERE id = 1;` → 2 |                                                                          |
| 2    |                                             | `SELECT stock FROM items WHERE id = 1;` → 2                              |
| 3    | `UPDATE items SET stock = 1 WHERE id = 1;`  |                                                                          |
| 4    |                                             | `UPDATE items SET stock = 1 WHERE id = 1;` (A 가 커밋할 때까지 기다려요) |
| 5    | `COMMIT;`                                   | 기다림이 풀려 실행돼요                                                   |

두 구매가 모두 성공했는데 재고는 1 이에요. 한 번의 구매가 사라졌어요. 이것을 갱신 손실(lost update)이라고 불러요.

B 의 UPDATE 가 기다렸다는 점이 중요해요. 쓰기 락은 충돌을 막아 주지만, 값을 앱이 옛날 값으로 계산해 넣으면 그 계산은 그대로 덮어써요. 락만으로는 부족하다는 뜻이에요.

## 원자적 UPDATE — 읽기와 쓰기를 한 문장에

가장 짧은 해결책은 계산을 DB 에 맡기는 거예요.

```sql
UPDATE items
SET stock = stock - 1
WHERE id = 1 AND stock > 0;
```

PostgreSQL 은 대기하던 UPDATE 가 앞선 변경의 커밋을 기다린 뒤, 갱신된 행에 WHERE 조건을 다시 적용해요. 재고가 1 이었다면 B 의 조건 `stock > 0` 은 더 이상 맞지 않아서 0 행이 갱신돼요. 앱은 영향받은 행 수가 0 이면 "재고가 없어요"로 응답하면 돼요.

> 앱이 영향받은 행 수를 확인해야 이 방식이 완성돼요. 행 수를 무시하면 실패가 조용히 지나가요.

## 비관적 락 — SELECT ... FOR UPDATE 로 먼저 잠그기

계산 로직이 복잡해서 SQL 한 문장으로 못 쓸 때는 읽는 순간 락을 잡아요.

```sql
BEGIN;
SELECT stock FROM items WHERE id = 1 FOR UPDATE;
-- 앱에서 재고와 정책을 확인해요
UPDATE items SET stock = stock - 1 WHERE id = 1;
COMMIT;
```

PostgreSQL 문서는 FOR UPDATE 로 가져온 행이 현재 트랜잭션이 끝날 때까지 다른 트랜잭션에게 잠긴다고 설명해요. 다른 트랜잭션의 UPDATE, DELETE, SELECT ... FOR UPDATE 는 기다려요.

핵심은 락을 읽기 전에 잡는 순서예요. 락 없이 읽고 나중에 잠그면 그 사이에 값이 바뀌어요.

락을 쥔 채 외부 API 호출이나 긴 계산을 하면 뒤에 오는 요청이 모두 줄을 서요. 트랜잭션은 짧게 유지하세요.

## 낙관적 락 — version 컬럼과 409, 412

락을 오래 잡지 않고 "쓸 때 내가 읽은 버전이 그대로인지" 확인하는 방식이에요.

```sql
UPDATE items
SET title = $1, version = version + 1
WHERE id = 1 AND version = 3;
-- 영향받은 행 수가 0 이면 누군가 먼저 고쳤어요
```

HTTP 에서는 두 가지 응답으로 나타나요. 둘 다 RFC 9110 에 정의돼 있어요.

서버가 조회 응답에 ETag 를 붙이고, 수정 요청에서 If-Match 로 그 값을 돌려받는 방식이에요.

```http
GET /items/1 HTTP/1.1
```

```http
HTTP/1.1 200 OK
ETag: "3"
```

```http
PUT /items/1 HTTP/1.1
If-Match: "3"
Content-Type: application/json

{"title": "새 제목"}
```

현재 ETag 가 "3" 이 아니면 서버는 `412 Precondition Failed` 를 돌려줘요. RFC 9110 은 412 를 요청의 조건 헤더가 현재 상태에서 거짓으로 평가됐다는 뜻으로 정의해요.

본문의 version 을 비교하는 구현이라면 `409 Conflict` 가 자연스러워요. RFC 9110 은 409 를 요청을 대상 리소스의 현재 상태와 맞출 수 없다는 뜻으로 설명해요.

예시 응답은 이래요.

```http
HTTP/1.1 409 Conflict
Content-Type: application/json

{"title": "다른 사람이 먼저 수정했어요", "current_version": 4}
```

## 격리 수준 — 기본값부터 확인하기

격리 수준은 "동시에 도는 트랜잭션이 서로를 얼마나 볼 수 있는가"를 정해요. 기본값은 DBMS 마다 달라요.

| 시스템       | 기본 격리 수준  | 알아 둘 점                                                       |
| ------------ | --------------- | ---------------------------------------------------------------- |
| PostgreSQL   | READ COMMITTED  | FOR UPDATE 가 없는 SELECT 는 문장 시작 전에 커밋된 데이터만 봐요 |
| MySQL InnoDB | REPEATABLE READ | 기본 격리 수준이 PostgreSQL 과 달라요                            |

격리 수준을 올린다고 read-modify-write 문제가 자동으로 해결되지는 않아요. PostgreSQL 의 REPEATABLE READ 에서는 같은 행을 먼저 바꾼 트랜잭션이 커밋되면, 나중 트랜잭션이 `could not serialize access due to concurrent update` 오류로 실패해요. 그래서 격리 수준을 올리면 재시도 경로도 같이 준비해야 해요.

## 데드락 — 서로 반대 순서로 잠글 때

두 트랜잭션이 같은 두 행을 반대 순서로 잠그면 서로가 쥔 락을 기다리게 돼요.

| 순서 | 트랜잭션 A                               | 트랜잭션 B                                      |
| ---- | ---------------------------------------- | ----------------------------------------------- |
| 1    | `order` 행 락                            |                                                 |
| 2    |                                          | `stock` 행 락                                   |
| 3    | `stock` 행 락 요청 (B 가 쥐고 있어 대기) |                                                 |
| 4    |                                          | `order` 행 락 요청 (A 가 쥐고 있어 대기) → 순환 |

이때 DB 는 대기 관계가 순환하는 것을 찾아내고, 둘 중 하나를 중단시켜요. PostgreSQL 문서는 어느 트랜잭션이 중단될지는 예측하기 어렵고 의존하면 안 된다고 설명해요. 중단된 쪽은 오류 코드 `40P01` (`deadlock_detected`) 을 받아요.

PostgreSQL 은 `deadlock_timeout` 동안 락을 기다린 뒤에야 데드락 검사를 해요. 기본값은 1초예요. MySQL InnoDB 는 데드락 감지가 기본으로 켜져 있고, 한 트랜잭션을 희생자로 롤백해요.

예방은 두 가지예요.

1. 모든 코드가 여러 객체를 같은 순서로 잠그게 해요. PostgreSQL 문서도 이것을 가장 좋은 방어라고 설명해요.
2. 트랜잭션을 짧게 유지해서 락을 쥐는 시간을 줄여요.

시뮬레이터는 설명을 단순하게 하려고 "나중에 시작한 쪽"을 희생자로 골라요. 실제 DB 의 선택 기준은 이와 다를 수 있어요.

데드락은 앱이 막을 수 없을 때도 생겨요. 그래서 중단된 트랜잭션은 재시도해야 해요.

## 멱등성 — 재시도와 더블 클릭을 견디기

저장 요청의 응답이 늦거나 끊기면 앱의 재시도 로직이나 사용자가 같은 요청을 다시 보내요. 첫 요청이 서버에서는 이미 처리됐을 수도 있어서, 서버는 두 번째 요청을 새 저장으로 볼 수 있어요. 그래서 POST 저장 요청에는 멱등성 키를 붙여요.

IETF 의 Idempotency-Key 초안(draft-ietf-httpapi-idempotency-key-header, 아직 RFC 는 아니에요)은 이런 헤더를 제안해요.

```http
POST /orders HTTP/1.1
Idempotency-Key: "8e03978e-40d5-43e8-bc93-6894a57f9324"
Content-Type: application/json

{"item_id": 1, "quantity": 1}
```

초안은 UUID 같은 무작위 값을 권장해요. 같은 키에 다른 본문이 오면 422, 원래 요청이 아직 처리 중인데 재시도하면 409, 키가 없으면 400 을 돌려주라고 권장해요(SHOULD).

프론트엔드 규칙은 간단해요.

- 사용자의 제출 행위 하나에 키 하나를 만들어요.
- 네트워크 재시도에는 같은 키를 그대로 써요.
- 새 행위를 하면 새 키를 만들어요.

## FE 체크 포인트

- 버튼을 비활성화하는 것만으로는 부족해요. 응답이 늦어 앱이 재시도하거나, 탭을 두 개 열어 저장하면 서버는 두 요청을 받아요.
- 409 를 받으면 최신 데이터를 다시 받아 보여 주고, 사용자 변경과 비교할 기회를 주세요. "다른 사람이 먼저 고쳤어요" 같은 안내가 필요해요.
- 412 를 받으면 최신 ETag 를 받아 다시 시도할지 사용자에게 물어보세요.
- 저장 요청에는 Idempotency-Key 를 보내세요.
- 재고처럼 서버가 쥐고 있는 값은 클라이언트가 계산한 결과를 덮어쓰지 말고, "1개 줄여 줘" 같은 변경 요청으로 보내는 편이 안전해요.

## 정리 — 원자적 계산 · 충돌 응답 · 멱등 재시도

동시 저장에서 생기는 문제는 대부분 "누가 먼저 읽고, 누가 나중에 쓰는가"에서 나와요. 원자적 UPDATE 로 계산을 DB 에 맡기고, 충돌은 409 나 412 로 받아 화면에 알려 주세요. 재시도는 멱등성 키로 안전하게 만들어요.
