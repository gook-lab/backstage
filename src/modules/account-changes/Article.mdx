설정 화면에 이메일 변경 칸이 있어요. 새 이메일을 입력하고 저장을 누르면 `PATCH`로 바로 바뀌도록 만들었어요. 보안팀은 두 가지를 요구해요. 현재 비밀번호를 다시 받고, 옛 주소로 변경 알림을 보내 달라는 거예요. 이 글은 이 요구가 서버에서 무엇을 막고 무엇을 남기는지 따라가요.

글의 사건과 숫자는 예시예요. 아래 시뮬레이터의 기본값과 같은 가정이에요.

## 증상 — 이메일 한 줄이 계정 주인을 바꾸는 경로

이메일은 로그인 주소이고, 비밀번호를 잊었을 때 재설정 메일을 받는 주소이기도 해요. 그래서 이메일이 바뀌면 다음 로그인과 비밀번호 재설정이 모두 새 주소를 따라가요.

세션만 가진 사람이 이메일을 바꾸면 이런 순서가 생겨요.

1. 공격자가 훔친 세션으로 `PATCH`를 보내 자기 주소를 넣어요.
2. 사용자는 옛 주소로 로그인할 수 없어요.
3. 공격자는 새 주소로 비밀번호를 재설정해요.

OWASP 인증 치트시트는 이메일 주소나 비밀번호 같은 민감한 정보를 바꾸기 전에 현재 자격 증명을 요구하라고 설명해요. 이 조치가 없으면 공격자가 현재 비밀번호를 몰라도 CSRF나 XSS로 민감한 작업을 실행할 수 있다고 설명해요.

## 재인증 — 현재 비밀번호와 최근 재인증 시각 확인

재인증은 세션이 있다는 사실과 별개로, 지금 이 사람이 주인이라는 증거를 한 번 더 받아요. OWASP는 비밀번호 변경 기능에 현재 비밀번호 확인을 두라고 설명해요. 로그인한 채 자리를 뜬 공용 PC를 예로 들어요. 세션이 남아 있으면 다른 사람이 비밀번호를 바꿀 수 있다고 설명해요.

NIST SP 800-63B는 인증 뒤 세션에 전체 시간 제한(overall timeout)을 두고, 재인증이 성공하면 그 시간을 다시 센다고 설명해요. 그래서 서버는 세션마다 마지막 재인증 시각을 저장하고, 민감한 변경 전에 그 시각이 충분히 최근인지 확인하는 편이 좋아요. 기준 시간은 설계 판단이에요.

| 확인 방식        | 막는 것                        | 한계                                          |
| ---------------- | ------------------------------ | --------------------------------------------- |
| 세션만 확인      | 로그아웃한 요청                | 훔친 세션은 그대로 통과해요                   |
| 현재 비밀번호    | 세션만 훔친 공격자             | 비밀번호를 아는 공격자(예: 피싱)는 통과해요   |
| 최근 재인증 시각 | 자리를 비운 사이의 오래된 세션 | 기준 시간이 짧으면 사용자가 자주 입력해요     |
| 추가 인증 (MFA)  | 비밀번호만 빠진 공격자         | 두 번째 요소를 받을 수 없으면 사용자가 잠겨요 |

OWASP는 민감한 작업에 추가 인증 계층을 두라고 설명해요. 재인증에는 현재 비밀번호나 패스키처럼 계정에 이미 묶인 인증기를 쓰라고 설명해요. 보안 질문으로 대신하지 말라고도 설명해요.

FE는 서버가 재인증을 요구할 때만 비밀번호 입력칸을 띄우고, 입력이 끝나면 원래 요청을 한 번만 다시 보내요.

## 이메일 변경 — 대기 상태와 확인 링크

새 이메일을 받았다고 바로 바꾸면 그 주소를 실제로 가진 사람인지 확인하지 못해요. OWASP의 이메일 변경 절차는 새 주소를 대기 변경(pending change)으로 저장하고, 시간 제한이 있는 값(nonce)을 만들라고 설명해요. 확인 메일은 새 주소로, 알림 메일은 옛 주소로 보내라고 설명해요.

| 방식                     | 새 주소 소유 확인 | 옛 주소 알림 | 되돌리기         |
| ------------------------ | ----------------- | ------------ | ---------------- |
| 바로 적용                | 없음              | 없음         | 불가             |
| 확인 링크만              | 있음              | 없음         | 확정 뒤 불가     |
| 확인 링크 + 옛 주소 알림 | 있음              | 있음         | 알림 링크로 가능 |
| 옛 주소 알림만           | 없음              | 있음         | 알림 링크로 가능 |

OWASP는 비밀번호만 있는 계정에서 옛 주소 알림만 보내는 방식도 있다고 설명해요. 다만 이 방식은 위험이 따르고 사용자가 주의해야 한다고 설명해요. MFA가 있는 계정에서는 본인 확인이 더 강하므로 절차가 덜 엄격해도 된다고 설명해요.

대기 상태의 규칙은 간단해요. 확정 전에는 로그인 주소와 알림 주소를 바꾸지 않아요. 두 값은 확정 시점에 같이 바뀌어요.

## 옛 주소 알림 — 되돌리기 링크

옛 주소 알림은 "이 주소로 변경 요청이 들어왔어요"라는 사실을 알려요. 알림에는 예상하지 못한 활동을 신고하는 링크를 넣어요. OWASP의 절차도 같아요.

NIST SP 800-63B는 인증기 연결이나 계정 복구 같은 사건을 계정의 알림 주소로 알리라고 설명해요. 알림에는 받는 사람이 사건을 부인할 때 연락할 방법을 넣으라고 설명해요. 이메일 변경은 NIST가 든 예시에 없어요. 이 글이 이메일 변경을 알림 대상으로 두는 것은 설계 판단이에요.

되돌리기 링크도 확인 링크와 같은 토큰이에요. 일회성이고 만료 시간이 있어야 해요. 토큰 규칙은 아래 확인 토큰 절에서 다뤄요.

## 비밀번호 변경 뒤 — 세션 ID 재발급과 다른 세션 정리

OWASP 세션 관리 치트시트는 권한 수준이 바뀔 때 세션 ID를 다시 만들라고 설명해요. 비밀번호 변경이 그 예로 나와요. 같은 치트시트는 비밀번호 변경을 재인증이 필요한 고위험 사건으로 꼽아요. 동시 로그인을 사용자에게 알리고, 원격으로 세션을 끊는 기능도 두라고 권해요.

"다른 세션을 전부 끊는다"는 OWASP가 명시한 규칙이 아니라 설계 선택이에요. 시뮬레이터는 이 선택의 한계를 보여 줘요. 다른 세션을 끊어도, 바꾼 세션을 가진 공격자는 남아요. 그래서 세션 정리는 탈취 뒤의 피해를 줄이는 장치이고, 탈취를 막는 장치는 재인증이에요.

서버 세션은 서버에서 지우면 바로 끊겨요. OWASP는 로그아웃할 때 서버 쪽 세션을 무효화하라고 설명해요. 토큰은 발급한 뒤 지우기가 더 어려워요. 토큰의 한계는 [로그인 유지 — 세션과 토큰](/m/auth-session-token)에서 다뤄요.

## 같은 새 주소 요청 — 유일 제약은 확정 시점에

두 계정이 같은 새 주소를 요청하면 둘 다 대기 상태를 가질 수 있어요. 대기 상태는 로그인 주소를 바꾸지 않으니 겹쳐도 괜찮아요. 확정은 한 계정만 할 수 있어요. 유일 제약은 DB의 유일 인덱스로 두고, 확정 쓰기가 하나만 성공하게 해요. 동시에 들어온 쓰기를 다루는 방법은 [트랜잭션 · 락 · 데드락](/m/transactions)에서 다뤄요.

요청 때 "이미 쓰는 주소예요"라고 알려 주면 응답만으로 계정 존재가 드러나요. OWASP 비밀번호 찾기 치트시트는 계정이 있든 없든 같은 메시지를 주라고 설명해요. 응답 시간도 같게 하라고 설명해요. 그래서 요청 응답은 "확인 메일을 보냈어요"처럼 하나로 맞추고, 주소 사용 여부는 확정 시점에만 알려요. 이 판단은 설계 선택이에요.

## 확인 토큰 — 만료 · 일회성 · 계정에 묶기

OWASP 비밀번호 찾기 치트시트는 재설정 토큰을 암호학적으로 안전한 난수로 만들라고 설명해요. 토큰은 충분히 길고, 한 사용자에게 묶여 있어야 해요. 쓴 뒤에는 무효화하고, 적절한 기간이 지나면 만료되어야 해요. 유효한 토큰이 제출되기 전에는 계정을 바꾸지 않아야 해요.

토큰이 URL 쿼리에 실리면 로그와 Referer로 샐 수 있어요. OWASP는 재설정 페이지에 Referrer Policy를 `no-referrer`로 두라고 설명해요. 무차별 대입을 막는 요청 제한도 함께 두라고 설명해요.

번호 방식과 링크 방식의 차이는 [인증번호 (OTP)](/m/verification-codes)에서 비교해요. 링크 메일을 보내는 방법은 [트랜잭션 메일](/m/transactional-email)에서 다뤄요. URL에 남는 값이 로그에 남는 경로는 [민감 정보 누출](/m/sensitive-data)에서 다뤄요.

## 변경 이력 — 요청 · 대기 · 확정 · 되돌리기 기록

이메일 변경은 한 번에 끝나지 않아요. 요청, 대기 생성, 확정, 되돌리기, 비밀번호 변경, 세션 무효화가 각각 따로 일어나요. 각 단계를 행위자, 시각, 대상, 요청 id와 함께 남겨요.

OWASP 세션 관리 치트시트는 계정 활동 이력을 기록하고, IP 주소나 User-Agent 같은 클라이언트 정보를 함께 남기라고 권해요. 이메일 값은 개인정보예요. 이력 화면에서 주소를 가리는 방법과 보존 기간은 [변경 이력과 감사 로그](/m/audit-history)와 [민감 정보 누출](/m/sensitive-data)에서 다뤄요.

## FE 체크 포인트 — 대기 상태와 세션 끊김을 서버 값에 맞추기

- 새 주소를 입력하면 "확인 메일을 보냈어요. 링크를 누르기 전까지 로그인 주소는 그대로예요."처럼 상태를 알려 주세요.
- 대기 중인 주소와 만료 시각은 서버 응답으로 받아 보여 주세요. 확정됐다고 추측하지 마세요.
- 확정 뒤에는 설정 화면 값을 서버에서 다시 읽으세요. 낙관적으로 바꾼 값을 그대로 두면 확정 실패가 가려져요.
- 다른 기기에서 `401`을 받으면 로그인 화면으로 보내고, 다른 기기에서 로그아웃됐다고 알려 주세요. `401` 처리는 [로그인 유지 — 세션과 토큰](/m/auth-session-token)에서 다뤄요.
- 요청 응답 문구는 주소 사용 여부와 상관없이 같게 두세요. "사용 중"이라는 문구를 따로 만들지 마세요.
- 되돌리기 링크를 누른 화면은 서버 상태를 다시 읽어서 보여 주세요.

## 시뮬레이터 안내

시뮬레이터는 사건 하나를 고르고, 변경 방식을 켜고 끄면서 공격자 접근 · 되돌리기 · 남은 세션 · 계정 존재 노출을 보여 줘요.

- **세션 탈취**: 재인증, 대기, 옛 주소 알림, 세션 정리를 바꿔 보세요. 대기 상태만으로는 막히지 않는 점을 확인해 보세요.
- **오타 난 새 이메일**: 대기 상태와 알림에 따라 잠기는지 보세요.
- **다른 기기 세션**: 비밀번호를 바꾼 뒤 공격자 세션이 끊기는지 보세요.
- **같은 새 이메일 동시 요청**: 요청 때 미리 검사할 때와 확정 때만 검사할 때 응답이 어떻게 달라지는지 보세요.

계산은 단순화한 모델이에요. 세션 수는 가정이고, 확인 링크는 새 주소를 가진 사람만 누른다고 가정해요. 수치는 감을 잡기 위한 예시예요.

## 정리 — 재인증 · 대기 확정 · 옛 주소 알림 · 세션 정리 · 확정 시점 검사

- 민감한 변경 전에는 현재 비밀번호와 최근 재인증 시각을 확인해요.
- 새 주소는 확인 링크를 누르기 전까지 대기 상태로 두고, 로그인 · 알림 주소는 그대로 둬요.
- 옛 주소에 변경 알림과 되돌리기 링크를 보내요.
- 비밀번호를 바꾸면 세션 ID를 다시 만들고, 다른 세션을 끊을지 정책으로 정해요. 끊어도 바꾼 세션의 공격자는 남아요.
- 같은 주소 충돌은 DB 유일 제약으로 막고, 요청 응답은 확정 전까지 같게 둬요.
- 확인 토큰은 만료 시간을 두고, 한 번 쓰면 무효화해요.
- 변경 요청 · 확정 · 되돌리기를 이력으로 남겨요.

시뮬레이터에서 재인증과 옛 주소 알림을 하나씩 켜 보세요. 어느 쪽이 공격자 접근을 막고, 어느 쪽이 되돌릴 길을 여는지 비교해 보세요.
