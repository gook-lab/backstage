검색 결과의 순서는 "추천순" 같은 옵션 하나로 정해지지 않아요. 서버는 검색어와 맞는 상품을 찾고, 각 상품에 점수를 매기고, 판매나 최신 같은 신호를 섞어서 정렬해요. 이 글은 순위가 만들어지는 네 단계를 나눠 봐요. 단어로 후보를 찾는 역색인, 관련도 점수 식, 비즈니스 신호를 곱하는 방식, 그리고 점수가 같을 때 순서를 정하는 동점 처리예요. 마지막에는 페이지를 넘길 때 생기는 중복과 누락, 개인화 결과의 캐시 키를 짧게 다뤄요.

이 글은 [검색과 자동완성](/m/search-autocomplete) 글의 입력과 요청 쪽을 이어받아요. 여기서는 요청이 들어온 뒤 결과의 순서에 집중해요.

아래 시뮬레이터에서 점수 방식과 가중치를 바꾸고, 동점 처리를 끄고 켜 보세요. 같은 검색어인데 순위가 어떻게 달라지는지, 2페이지에서 같은 상품이 두 번 나오거나 빠지는지 직접 볼 수 있어요. 시뮬레이터의 상품 목록과 판매 수는 예시 데이터예요.

## 역색인 — 단어별 문서 목록을 미리 만든 색인

검색 엔진은 상품을 하나씩 읽어 단어가 있는지 확인하지 않아요. 단어에서 문서 목록으로 가는 색인을 미리 만들어 둬요. PostgreSQL 문서는 전문 검색에 쓰는 GIN 인덱스를 "Generalized Inverted Index" 기반 인덱스라고 설명하고, 전문 검색 인덱스로 가장 선호되는 종류라고 안내해요. Elasticsearch 도 같은 원리로 단어 목록을 바탕으로 점수 계산을 시작한다고 가정해요. 이 글은 이 부분을 공식 문서로 확인하지 않았어요.

그래서 점수를 계산하는 단위는 상품 전체가 아니라 검색어에 들어 있는 단어예요. "사과 주스" 를 검색하면 "사과" 의 문서 목록과 "주스" 의 문서 목록을 합쳐서 후보를 만들어요. 이 글의 시뮬레이터는 단어를 공백으로 나누는 것으로 단순화했어요. 한국어는 단어를 나누는 방식이 분석기 설정에 따라 달라서, 실제 서비스에서는 그 설정을 따로 확인해야 해요.

## 관련도 점수 — 단어 포함 수에서 BM25 까지

같은 후보라도 점수 식에 따라 순서가 달라져요. 이 글에서는 세 가지를 비교해요.

| 방식          | 점수 계산                                | 특징                                                      |
| ------------- | ---------------------------------------- | --------------------------------------------------------- |
| 단어 포함 수  | 검색 단어가 제목에 몇 개 있는지 세요     | 이해하기 쉬워요. 흔한 단어와 드문 단어를 구분하지 못해요  |
| TF-IDF (단순) | 단어 빈도에 `log(N / df)` 를 곱해 더해요 | 흔한 단어의 가중치를 낮춰요. 모든 문서에 있으면 0 이 돼요 |
| BM25          | idf 에 포화된 빈도 항을 곱해 더해요      | Elasticsearch 의 기본 similarity 예요                     |

BM25 의 두 가지 요소를 확인해 볼게요.

- **idf**: Lucene 의 BM25Similarity 문서는 `log(1 + (docCount - docFreq + 0.5) / (docFreq + 0.5))` 를 idf 식으로 밝혀요. 이 식은 모든 문서에 있는 단어에도 0 보다 큰 값을 줘요. 단순 TF-IDF 의 `log(N / df)` 가 그 경우 0 이 되는 것과 달라요.
- **tf 포화**: 같은 단어가 여러 번 나와도 점수는 조금씩만 늘어요. Elasticsearch 문서는 BM25 의 기본값을 `k1` 1.2, `b` 0.75 로 적고, `k1` 이 빈도 정규화의 비선형 포화를 조절한다고 설명해요. `b` 는 문서 길이가 빈도 값을 얼마나 정규화할지 조절해요.

tf 항의 정확한 식은 이 글에서 인용한 공식 페이지에 없어요. 시뮬레이터의 식은 포화 곡선을 보여 주는 표준 형태이고, 실제 구현과 맞는지는 Lucene 소스로 따로 확인해야 해요.

## 비즈니스 신호 — 판매 · 최신 가중치를 관련도에 곱하는 방식

관련도만으로 정렬하면 검색 결과가 "그럴듯하지만 안 팔리는" 상품으로 채워질 수 있어요. 그래서 판매량, 최신성, 재고 같은 신호를 함께 씁니다. Elasticsearch 의 function_score 쿼리는 이런 신호를 점수에 섞는 기능을 제공해요. 문서는 `boost_mode` 기본값이 `multiply` 라서 쿼리 점수와 함수 점수를 곱한다고 설명해요. `min_score` 를 쓰면 점수 기준 아래 문서를 걸러낼 수 있어요. 다만 이 문서는 `min_score` 를 쓰려면 모든 문서를 점수 매긴 뒤 하나씩 걸러야 한다고도 적어요. 큰 목록에서는 비용이 생긴다는 뜻이에요.

이 글의 시뮬레이터는 다음 식을 써요. 예시 식이고, 여기서는 function_score 의 `multiply` 와 같은 생각을 따라요.

```text
최종 점수 = 관련도 × (1 + 판매 가중치 × 판매 비율 + 최신 가중치 × 최신 비율)
```

가중치를 올리면 관련도가 낮아도 많이 팔린 상품이 위로 올라와요. 이것이 "추천순" 의 한 가지 모습이에요. 서버가 어떤 신호를 어떤 비율로 섞었는지는 API 응답만으로 알 수 없어요. 그래서 정렬 옵션 이름과 실제 식의 관계를 BE 에 물어야 해요.

PostgreSQL 의 `ts_rank` 는 단어가 몇 번 나오는지, 단어가 얼마나 가까운지, 문서의 어느 부분에 나오는지를 봐요. 문서는 ts_rank 계열이 전역 정보를 쓰지 않아서, 문서 집합 전체 기준의 정규화를 만들 수 없다고 설명해요. 문서는 함수 결과를 다른 요소와 합칠 수 있다고도 안내해요. 그러니 전문 검색만으로 판매나 재고를 다 맞추려 하면 한계가 있어요.

## 동점 처리 — 점수가 같을 때 순서를 정하는 기준

이 글에서 가장 중요한 부분이에요. 정렬 기준이 같은 상품이 여럿이면 그 순서는 정해지지 않아요. 시뮬레이터의 예시 데이터에서 "사과 주스" 를 BM25 로 돌리면 "사과 주스 1L", "사과 주스 2L", "사과 주스 500ml" 가 같은 점수를 받아요. 제목 단어 수와 검색 단어의 빈도가 같아서예요. 이 셋의 순서가 정해지지 않으면 페이지 나눔에서 문제가 생겨요.

Elasticsearch 의 페이지 나눔 문서는 정렬 값이 같은 문서들의 순서가 일관되지 않을 수 있다고 적어요. tiebreaker 필드가 없으면 페이지 결과에서 문서가 빠지거나 두 번 나올 수 있다고 설명해요. 권장되는 방법은 각 문서마다 고유한 값을 가진 tiebreaker 필드를 정렬에 넣는 것이에요.

| 동점 처리   | 같은 요청을 다시 보내면    | 2페이지에서                  |
| ----------- | -------------------------- | ---------------------------- |
| 없음        | 동점 순서가 바뀔 수 있어요 | 중복과 누락이 생길 수 있어요 |
| id 오름차순 | 항상 같은 순서가 나와요    | 중복과 누락이 없어요         |

시뮬레이터에서 동점 처리를 "없음" 으로 두면 이 현상을 볼 수 있어요. 한 번의 실행 예에서 `p05` 는 1페이지와 2페이지에 모두 나오고, `p04` 와 `p06` 은 두 페이지 어디에도 없었어요. 실행마다 다른 순서가 나오는 것은 실제 DB 가 동점 순서를 보장하지 않는다는 점을 흉내 낸 것이에요.

## 페이지 경계 — 요청마다 다시 정렬하는 offset 방식

offset 과 limit 으로 페이지를 나누면, 페이지마다 서버가 다시 정렬하고 자른다고 생각해 보세요. 1페이지와 2페이지가 같은 순서를 본다는 보장이 없어요. 동점 처리가 없으면 경계에서 같은 상품이 두 번 나오거나 빠질 수 있어요.

Elasticsearch 는 기본적으로 `from` 과 `size` 로 10,000 건을 넘어서 페이지를 넘길 수 없다고 문서에 적어요. 그보다 깊이 넘기려면 `search_after` 를 쓰라고 안내해요. `search_after` 는 이전 페이지 마지막 문서의 정렬 값 배열을 다음 요청에 넣는 방식이에요. 이때 같은 검색어와 같은 정렬 값이 필요하다고 설명해요. 정렬 값이 같은 문서끼리는 고유한 값이 필요하니, 정렬 키 끝에 고유 필드를 붙이는 것이 핵심이에요. 페이지 방식의 자세한 비교는 [페이지네이션](/m/pagination) 글에서 다뤘어요. 특히 동점 처리와 복합 인덱스를 함께 보면 이해가 쉬워요.

## 개인화 결과의 캐시 키 — 사용자와 정렬 옵션을 포함하는 방식

검색 결과를 캐시하면 같은 검색어에 같은 결과를 줄 수 있어요. 그런데 "나에게 맞춘 추천순" 이라면 결과는 사용자마다 달라요. 이때 캐시 키에 검색어만 넣으면 다른 손님의 결과가 섞여요. 키에 사용자 식별자와 정렬 옵션, 그리고 페이지 기준이 되는 값까지 넣어야 해요. 다만 사용자별로 키를 쪼개면 적중률이 떨어져요. 어떤 값을 키에 넣을지는 적중률과 잘못된 응답의 위험을 같이 보고 정해요.

캐시 키 설계의 원리는 [이미지 CDN](/m/image-cdn) 글의 캐시 키 절과 같아요. 요청의 어떤 값이 응답을 바꾸는지 먼저 찾고, 그 값만 키에 넣어요. 같은 캐시를 여러 사람이 쓰는 환경이라면 개인화 응답에 공유 캐시를 쓰면 안 돼요. 이 판단은 설계 원칙이에요. 실제 CDN 이 캐시 키와 `Vary` 를 어떻게 다루는지는 그 CDN 의 문서로 확인해야 해요.

## 0건과 오타 교정 — 사용자 확인 후 적용하는 방식

검색 결과가 0건이면 서버는 빈 목록을 돌려줘요. 여기서 오타 교정을 자동으로 적용하면 사용자가 찾는 것과 다른 상품을 보게 돼요. Elasticsearch 의 fuzzy 쿼리 문서는 편집 거리를 "글자를 바꾸기, 지우기, 넣기, 인접한 두 글자 자리 바꾸기" 로 정의하고, 그 거리 안에 드는 단어를 찾는다고 설명해요. 편집 거리가 가까운 단어가 여럿이면 엉뚱한 교정이 나올 수도 있어요.

그래서 FE 는 교정 후보를 따로 보여 주고, 사용자가 누르면 그때 다시 검색하는 흐름이 안전해요. 이 글의 시뮬레이터는 편집 거리 1 이내의 단어만 후보로 올려요. "쥬스" 를 "주스" 로 바꾸는 것이 예예요. 띄어쓰기가 없는 복합어 교정은 이 예시 범위 밖이에요.

## FE 가 할 일 — 정렬 옵션 계약과 커서 초기화

FE 는 정렬을 서버와의 약속으로 다뤄요. 아래 항목은 설계 제안이에요. 실제 파라미터 이름과 값은 팀의 API 문서로 정해요.

| 할 일                      | 무엇을 확인하나                                                                                               |
| -------------------------- | ------------------------------------------------------------------------------------------------------------- |
| 정렬 옵션 이름과 계약      | "추천순" 같은 화면 이름과 서버의 `sort` 값을 1:1 로 맞춰 문서로 남겨요. 모르는 값을 받았을 때의 응답도 정해요 |
| 하이라이트 응답 사용       | 서버가 준 강조 위치를 쓰고, 텍스트를 HTML 로 바로 넣지 않아요                                                 |
| 정렬을 바꿀 때 커서 초기화 | 페이지 번호나 커서는 정렬 기준에 묶여 있어요. 정렬을 바꾸면 1페이지부터 다시 받아요                           |
| 0건 응답의 교정 후보       | 자동 교정을 적용하지 않고, 사용자가 확인한 뒤 다시 요청해요                                                   |

정렬을 바꿀 때 커서를 그대로 두면 이전 정렬의 마지막 위치를 새 정렬에 넣게 돼요. 그러면 중복과 누락이 한꺼번에 생겨요. 커서는 정렬 옵션 값과 함께 묶어서 관리해 주세요.

## 시뮬레이터 — 점수 방식 · 가중치 · 동점 처리 비교

기본값은 BM25, 가중치 0, 동점 처리 없음이에요. 먼저 2페이지 결과 표에서 중복과 누락이 어떻게 생기는지 보세요. 그다음 동점 처리를 "id 오름차순" 으로 바꾸면 같은 데이터에서 중복과 누락이 사라져요. 판매 가중치를 올리면 점수 차이가 생겨서 동점이 깨지는 것도 확인할 수 있어요. 가중치로 순서가 바뀌는 것은 정렬 식이 바뀐 것이고, 동점 처리가 없어서 생기는 중복과 누락은 별개의 문제라는 점을 기억해 주세요.
