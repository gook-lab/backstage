사진 한 장은 API 서버로 보내도 크게 문제가 없어요. 영상 원본처럼 수 GB 짜리 파일도 같은 길로 보내도 될까요? 이 글은 올리는 길과 받는 길을 나누는 판단을 다뤄요. 아래 시뮬레이터에서 파일 크기와 끊김 확률을 바꿔 보면, 실패했을 때 다시 보내야 하는 양이 방식마다 어떻게 달라지는지 바로 확인할 수 있어요.

## 증상 — 큰 파일이 끝 근처에서 멈춤

진행률이 90%에서 멈추고 "네트워크 오류"가 떠요. 다시 누르면 처음부터 올라가요. 서버 로그에는 413이나 타임아웃이 남기도 해요. 이 증상은 파일이 크다는 사실과, 파일이 지나는 길이 하나라는 사실이 함께 만들어요.

## API 서버 경유 업로드 — 한도와 메모리 부담

요청 본문이 서버가 정한 한도를 넘으면 서버는 413 Content Too Large로 답해요. RFC 9110은 이 상태 코드를 요청 본문이 너무 커서 서버가 처리를 거부한다는 뜻으로 정의해요. MDN은 서버가 연결을 끊거나 Retry-After 헤더를 함께 줄 수 있다고 설명해요.

한도를 올리면 당장은 해결되지만, 서버가 파일 전체를 받아 메모리나 디스크에 두는 구조는 그대로예요. 동시에 올리는 사람이 많아지면 그 부담이 서버 인스턴스 수만큼 곱해져요. 이건 구조에서 나오는 판단이고, 실제 부담의 크기는 서비스와 서버 사양마다 달라요.

## 객체 저장소 직접 업로드 — presigned URL로 서버를 건너뛰기

흐름은 세 단계예요. FE가 서버에 "이 이름과 크기의 파일을 올릴게요"라고 요청하면, 서버는 저장소에 쓸 수 있는 URL을 만들어 돌려줘요. FE는 그 URL로 파일을 저장소에 직접 보내요. 끝나면 서버에 완료를 알려요.

AWS 문서에 따르면 presigned URL 에는 대상 객체, HTTP 메서드, 만료 시간이 들어가요. 업로드에는 PUT을 써요. 만료 전까지는 여러 번 쓸 수 있고, IAM 사용자 자격 증명으로 SigV4 서명을 하면 최대 7일까지 유효해요.

URL을 가진 사람은 그 권한을 그대로 쓸 수 있어요. 그래서 만료는 짧게 잡고 메서드와 객체 키는 좁게 정하는 편이 안전해요. 이 부분은 설계 판단이에요.

| 방식                             | 파일이 지나는 곳 | 실패 시 다시 보내는 양 | 서버에 남는 부담  |
| -------------------------------- | ---------------- | ---------------------- | ----------------- |
| API 서버 단일 요청               | API 서버         | 파일 전체              | 본문 한도, 메모리 |
| 저장소 단일 PUT (presigned)      | 저장소 직접      | 파일 전체              | 발급 요청만       |
| 저장소 멀티파트 (presigned 조각) | 저장소 직접      | 끊긴 조각만            | 발급과 완료 확인  |

## 멀티파트 업로드 — 조각 단위 전송과 재전송

멀티파트 업로드는 파일을 조각으로 나눠 올리는 방식이에요. AWS 문서의 순서는 이래요. 먼저 CreateMultipartUpload로 업로드를 시작하고 upload ID를 받아요. 그다음 조각마다 UploadPart를 보내고, 마지막에 CompleteMultipartUpload로 조각들을 한 객체로 묶어요.

지켜야 할 규칙이 몇 가지 있어요.

- 조각 번호는 1부터 10,000 까지예요. AWS 문서는 조각 크기를 5 MiB에서 5 GiB 사이로 정하고, 마지막 조각에만 최소 크기 제한이 없다고 설명해요.
- 조각을 올릴 때마다 응답의 ETag를 번호와 함께 기록해야 해요. 완료 요청에는 조각 번호와 ETag 목록을 함께 보내야 해요.
- 끊긴 조각만 다시 보내면 돼요. 처음부터 다시 올릴 필요가 없어요. AWS 문서가 이 방식의 이점으로 꼽는 내용이에요.
- 조각이 작을수록 한 번 끊겼을 때 잃는 양이 줄어요. AWS 문서도 작은 조각이 네트워크 오류 뒤 재시작의 영향을 줄인다고 설명해요. 대신 요청 수가 늘어나고, 조각 수에도 상한이 있어요.

업로드를 시작한 뒤 완료하거나 중단하지 않으면 그 업로드는 만료되지 않아요. AWS 문서는 미완료 업로드가 저장 비용을 만들므로 AbortIncompleteMultipartUpload를 쓰는 수명 주기 규칙을 권장해요.

시뮬레이터는 끊김을 MiB 단위로 다뤄요. 100 MiB를 보내는 동안 끊길 확률을 정하면, 조각 하나가 끝까지 갈 확률과 파일 전체가 끝까지 갈 확률이 크기에 따라 달라져요. 이 모델은 설명을 위한 예시예요.

## 완료 확인 — 조각을 다 올린 뒤 서버에 알리기

FE는 조각 번호와 ETag를 모아 서버의 완료 API로 보내요. 서버는 그 목록으로 저장소에 완료를 요청해요. 이 순서가 중요해요.

- 완료 응답을 받기 전에는 파일을 "업로드 중"으로 두고, 서버 DB에 사용 가능 상태(ready)로 된 행을 만들지 않아요.
- 완료 요청이 네트워크에서 실패해 FE가 다시 보내도 결과가 같아야 해요. 서버는 이미 끝난 업로드인지 확인하고 같은 응답을 돌려주는 쪽이 안전해요. 이것도 설계 판단이에요.
- 조각 업로드가 모두 끝났더라도 완료 요청이 빠지면 파일은 끝나지 않은 상태로 남아요. 그래서 미완료 업로드를 정리하는 규칙이 필요해요.

## 다운로드 — Range 요청과 206으로 이어받기

서버가 범위 요청을 지원하면 Accept-Ranges: bytes 헤더를 줘요. MDN은 이 헤더가 있으면 서버가 범위 요청을 지원한다는 뜻이라고 설명해요.

클라이언트가 `Range: bytes=500-` 같은 헤더를 보내면, 서버는 요청한 범위만 담아 206 Partial Content로 답하고, Content-Range 헤더로 전체에서 어느 위치인지 알려 줘요. 요청한 범위가 파일 밖이면 416 Range Not Satisfiable로 답해요. RFC 9110은 이 상태들을 이렇게 정의해요.

여기서 FE가 놓치기 쉬운 점이 있어요. RFC 9110은 서버가 Range 헤더를 무시할 수 있다고 정해요. 그래서 이어받기 코드는 응답 상태가 206 인지 확인해야 해요. 200으로 전체 본문이 오면 기존 조각 뒤에 붙이면 안 돼요. 처음부터 새로 받는 쪽으로 처리해야 파일이 깨지지 않아요.

## 다운로드 파일 이름 — Content-Disposition으로 저장 방식 정하기

Content-Disposition 헤더는 응답을 브라우저에서 보여 줄지(inline), 내려받을지(attachment) 정해요. MDN은 attachment를 받아서 저장하게 하는 값으로, 보통 "다른 이름으로 저장" 창을 띄운다고 설명해요.

파일 이름은 filename 파라미터로 줄 수 있어요. 한글 같은 non-ASCII 이름은 `filename*`에 UTF-8로 인코딩해서 넣어요. MDN 예시는 `filename*=UTF-8''file%20name.jpg` 형태예요. RFC 6266은 `filename`과 `filename*`을 둘 다 정의해요.

## 큰 응답 스트리밍 — 전체를 메모리에 모으지 않기

MDN은 스트리밍을 자원을 작은 조각으로 나눠서 조금씩 처리하는 방식이라고 설명해요. fetch 응답의 body는 ReadableStream이에요. 이걸 읽으면서 바로 파일이나 저장 스트림에 쓰면 전체를 메모리에 올리지 않아도 돼요.

서버도 같은 원칙을 따르는 편이 좋아요. 파일을 조각으로 읽어 응답에 흘려보내면 서버 메모리가 파일 크기와 무관해져요. 이것도 구조에서 나오는 판단이에요.

MDN의 Streams API는 쓰는 쪽이 따라오지 못할 때 역압(backpressure)으로 읽는 쪽 속도를 맞춘다고 설명해요. 다운로드를 저장할 때 이 개념을 기억해 두면 좋아요.

## FE 체크 포인트

- 진행률은 완료된 조각 수 기준으로 보여 줘도 충분해요. 조각 하나가 끝날 때마다 값을 올리면 돼요. 설계 판단이에요.
- 실패한 조각만 다시 시도하고, 시도 사이의 간격을 늘려요. 같은 조각을 계속 다시 보내면 서버와 네트워크에 부담이 커요.
- presigned URL 에는 만료 시간이 있어요. 만료된 URL로 조각을 보내면 실패하니, 그럴 때는 서버에서 URL을 다시 받아요.
- 같은 파일을 다시 골랐을 때 이어올릴 수 있게 upload ID와 완료된 조각 번호를 보관해 두면 좋아요.
- 다운로드는 응답 상태가 206 인지, Content-Range가 요청한 범위와 맞는지 확인한 뒤 이어받아요.

## 정리 — 저장소 직접 업로드와 조각 · 이어받기

큰 파일은 API 서버를 거치지 않고 저장소에 직접 올려요. 조각으로 나누면 끊겼을 때 잃는 양이 조각 하나로 줄어요. 서버는 발급과 완료 확인만 맡고, 파일 내용은 지나가지 않아요. 내려받을 때는 Range와 206으로 이어받고, 응답은 스트림으로 흘려보내요.

이 주제의 바탕은 HTTP의 요청 크기와 범위 규칙이에요. 파일을 올리고 내려받는 쪽의 상태 코드와 헤더를 먼저 익혀 두면 시뮬레이터의 결과도 쉽게 읽혀요.
