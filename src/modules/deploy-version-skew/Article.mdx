배포 직후에 "같은 화면인데 어떤 요청은 새 필드가 오고 어떤 요청은 안 와요"라는 제보가 들어와요. 어떤 사용자 화면에서는 청크를 불러오지 못해서 오류가 나요. 서버 배포는 한 번에 끝나지 않고, 열린 탭은 배포 전 번들을 계속 쓰기 때문이에요.

이 글은 그 차이가 생기는 원리와 막는 방법을 정리해요.

아래 시뮬레이터에서 배포 방식, 옛 자산 보존 여부, API 변경 방식을 바꿔 보면 옛 탭 요청이 칸마다 어떤 결과를 받는지 볼 수 있어요.

## 롤링 배포 — 옛 인스턴스와 새 인스턴스가 함께 응답하는 구간

Kubernetes Deployment의 롤링 업데이트는 새 Pod를 띄우고 옛 Pod를 줄이는 식으로 바꿔요. 문서는 maxUnavailable과 maxSurge의 기본값이 각각 25%라고 설명해요. 그래서 교체가 끝나기 전까지 옛 Pod와 새 Pod가 함께 응답해요.

로드밸런서는 버전을 구분하지 않아요. 같은 사용자의 연속된 요청도 옛 서버와 새 서버로 나뉘어 갈 수 있어요.

제보에서 본 "어떤 요청은 오고 어떤 요청은 안 와요"가 이 현상이에요. 준비 전 Pod에 트래픽이 가지 않게 하는 방법은 [로드 밸런싱과 연결 관리](/m/load-balancing) 글에서 이어 봐요.

## 열린 탭 — 옛 번들이 새 API를 부르는 경우

탭은 서버 배포와 상관없이 처음 받은 번들로 계속 동작해요. 사용자가 새로고침하지 않으면 옛 번들은 옛 필드 이름으로 API를 계속 불러요. 서버가 새 응답만 보내면 옛 번들은 그 값을 찾지 못해요.

이 문제는 서버를 먼저 올리든 FE를 먼저 올리든 생겨요. 같은 날 같이 올려도 롤링이 끝나기 전까지 두 조합이 함께 있어요. 응답을 옛 클라이언트가 읽을 수 있게 유지하는 규칙은 [API 버전 관리](/m/api-versioning) 글의 하위 호환 항목에서 다뤄요.

## 확장 → 이전 → 축소 — expand/contract 순서

필드 이름을 바꾸거나 지울 때는 한 번에 바꾸지 않고 세 단계로 나눠요.

- 확장: 새 필드를 더해서 옛 필드와 함께 보내요.
- 이전: FE가 새 필드를 읽도록 옮겨요.
- 축소: 옛 번들이 모두 사라진 뒤에 옛 필드를 빼요.

이번 배포에서 확장만 하면 옛 탭은 옛 필드를 계속 받아요. 축소는 옛 탭이 0이 된 뒤에 따로 하면 돼요. 단계별 표와 DB 칼럼 순서는 [스키마 마이그레이션](/m/schema-migration) 글에서 자세히 봐요.

## 청크 404 — 해시 파일이 배포 뒤 사라지는 경우

Vite는 빌드 결과물을 해시가 붙은 자산(JS, CSS, 이미지)으로 만들고, 기본 디렉터리를 `assets`로 써요. 파일 이름에 내용 해시가 들어가서 내용이 바뀌면 이름도 바뀌어요. 그래서 옛 탭은 옛 이름의 청크를 기억하고 있어요.

지연 로드하는 페이지는 탭에서 처음 열 때 청크를 요청해요. 새 배포 폴더에 그 옛 해시 파일이 없으면 요청이 404가 돼요.

동적 import가 실패하면 Vite는 `vite:preloadError` 이벤트를 내요. 문서는 이 이벤트에서 페이지를 새로고침하는 예시를 보여 줘요. 이벤트에서 `preventDefault()`를 호출하면 오류가 던져지지 않아요.

```ts
const KEY = 'last-preload-reload';

window.addEventListener('vite:preloadError', (event) => {
  const last = Number(sessionStorage.getItem(KEY) ?? 0);
  // 1분 안에 또 실패하면 새로고침하지 않고 오류를 그대로 둬요 (무한 새로고침 방지, 예시 값)
  if (Date.now() - last < 60_000) return;
  sessionStorage.setItem(KEY, String(Date.now()));
  event.preventDefault();
  window.location.reload();
});
```

자동 새로고침은 한 번의 응급 처리예요. 입력 중이던 값이 사라지니, 폼이 있는 화면에서는 안내 문구를 먼저 띄우는 편이 나아요.

## 옛 자산 보존 — 해시 파일을 기간 동안 남기기

옛 해시 파일을 배포 뒤에도 일정 기간 남겨 두면 청크 404가 줄어요. 해시 파일은 내용이 바뀌지 않으니 캐시도 오래 둘 수 있어요. MDN은 캐시 무효화 패턴을 쓰는 리소스에 긴 max-age를 주고 `immutable`을 붙이면 재검증 요청을 피할 수 있다고 설명해요.

보존 기간은 옛 탭이 남아 있을 것으로 보는 기간이에요. 기간은 팀이 정해요. 기간이 끝나면 옛 파일을 지우고, 그 뒤에 들어온 옛 탭은 새로고침 안내로 처리해요.

| 방식                          | 옛 탭의 청크 요청      | 비용                             |
| ----------------------------- | ---------------------- | -------------------------------- |
| 옛 해시 파일을 지움           | 새 배포에서 404가 돼요 | 저장 공간이 적게 들어요          |
| 옛 해시 파일을 기간 동안 남김 | 성공해요               | 저장 공간과 관리할 파일이 늘어요 |

## 버전 헤더 — 클라이언트 버전 차이 감지와 새로고침 안내

서버 응답에 빌드 버전을 담은 헤더를 붙이면 옛 탭이 스스로 차이를 알 수 있어요. 헤더 이름은 팀이 정하는 예시예요(예: `X-App-Version`). 빌드할 때 FE에 버전 상수를 넣고, API 응답의 헤더와 비교해요. 다르면 "새 버전이 나왔어요. 새로고침하세요" 같은 안내를 띄워요.

Martin Fowler는 카나리 배포 글에서 백엔드와 통신하는 소프트웨어는 두 버전을 함께 지원하고, 어떤 클라이언트 버전이 쓰이는지 모니터링할 수 있다고 설명해요. 버전 헤더는 그 모니터링의 입력으로도 쓸 수 있어요.

한계도 있어요. 탭이 API를 부르지 않으면 헤더를 볼 기회가 없어요. 그래서 헤더 감지는 청크 오류 처리와 함께 써야 해요.

## 블루-그린과 카나리 — 전환 방식 비교

Martin Fowler의 블루-그린 글은 운영 환경을 두 개 두고, 라우터를 바꿔 전환하는 방식을 설명해요. 옛 환경은 롤백을 위해 남겨 두고, 문제가 생기면 라우터를 되돌려요.

카나리 글은 새 버전을 일부 인프라에만 올리고, 일부 사용자에게만 보내는 방식을 설명해요. 문제가 생기면 그 사용자들을 옛 버전으로 되돌려요.

| 구분         | 블루-그린                           | 카나리                                       |
| ------------ | ----------------------------------- | -------------------------------------------- |
| 전환         | 라우터를 한 번에 바꿔요             | 비율을 올리며 나눠 보내요                    |
| 옛 탭 요청   | 전환 뒤에는 모두 새 환경으로 가요   | 비율만큼만 새 버전으로 가요                  |
| 롤백         | 라우터를 옛 환경으로 되돌려요       | 새 버전으로 가던 요청을 옛 버전으로 되돌려요 |
| 두 버전 관리 | 옛 환경을 롤백 기간 동안 대기시켜요 | 두 버전을 동시에 운영해요                    |

Vercel Skew Protection 문서는 지원 프레임워크에서 배포 ID를 요청에 실어 보내고, 연 탭의 정적 자산과 클라이언트 전환 요청을 그 탭이 처음 받은 배포로 보낸다고 설명해요. 새로고침과 주소창 입력은 최신 배포로 가요. 이 기능은 Vercel 플랫폼의 기능이라 다른 호스팅에서는 같은 방식으로 쓸 수 없어요.

## 헬스 체크와 연결 드레이닝 — 준비 전 트래픽 막기

Kubernetes readiness probe는 컨테이너가 트래픽을 받을 준비가 됐는지 알려요. 실패하면 EndpointSlice 컨트롤러가 그 Pod의 IP를 Service의 EndpointSlice에서 빼요.

종료할 때는 SIGTERM을 보내고, 유예 기간(기본 30초)이 지나면 KILL을 보내요. 앱은 SIGTERM을 받으면 새 요청을 멈추고 처리 중인 요청을 마치도록 만들어야 해요. 그래야 유예 기간 안에 옛 서버가 요청을 끊지 않고 내려가요.

자세한 설정은 [로드 밸런싱과 연결 관리](/m/load-balancing) 글에서 봐요.

## 피처 플래그 — 배포와 공개 분리

새 경로는 코드를 먼저 배포하고, 플래그로 나중에 켤 수 있어요. 옛 경로와 새 경로가 함께 있으면 두 버전이 섞이는 기간에도 화면 동작을 맞추기 쉬워요. 플래그 종류와 평가 위치는 [기능 플래그](/m/feature-flags) 글에서 다뤄요.

## FE 체크 포인트

- 청크 로드 오류를 전역에서 잡고, 새로고침 안내로 연결해요. 자동 새로고침은 한 번만 해요.
- API 응답의 버전 헤더를 빌드 버전과 비교해요. 차이가 있으면 입력 중인 값을 보존하는 안내를 먼저 띄워요.
- 옛 필드와 새 필드를 함께 읽는 함수를 두고, 둘 다 없을 때 기본값 대신 로그를 남겨요.
- 배포 직후 청크 404 비율과 버전 헤더 불일치 비율을 모니터링해요. 두 지표가 함께 오르면 자산 보존 기간을 되짚어요.

## 시뮬레이터 안내

아래 시뮬레이터는 배포 진행 단계를 칸으로 나눠 옛 탭 요청의 결과를 보여 줘요. 칸 1부터 새 버전 응답 비율이 늘어나고, 옛 탭 요청은 필드 누락 또는 청크 404를 받을 수 있어요.

1. 기본값인 롤링 · 바로 삭제 · 해시 미보존에서 깨진 칸 수를 확인해요.
2. 해시 파일을 남기면 청크 404 줄이 0이 되는지 봐요.
3. 확장 후 축소로 바꾸면 필드 누락이 사라지는지 봐요.
4. 블루-그린과 카나리를 고르고 칸 2와 칸 1의 비율을 비교해요.

비율과 칸 수는 예시예요. 실제 값은 트래픽과 배포 설정에 따라 달라요.

## 정리 — 전환 방식 · 자산 보존 · 버전 감지 · 축소 시점

- 롤링 배포는 옛 서버와 새 서버를 같은 시간에 세워요. 열린 탭도 옛 번들을 계속 써요.
- 블루-그린은 전환이 한 번에 일어나고, 카나리는 비율을 올리며 나눠 보내요. 롤백 방식도 달라요.
- 해시 파일은 배포 뒤에도 기간 동안 남겨요. 청크 404는 자산 보존 기간으로 줄여요.
- 필드 축소는 옛 탭이 사라진 뒤에 해요. 확장과 이전은 배포마다 나눠요.
- 버전 헤더로 차이를 감지하고 새로고침을 안내해요. 헤더는 API를 부르는 탭에서만 보여요.
