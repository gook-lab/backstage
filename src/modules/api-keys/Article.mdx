개발자 설정 화면에서 API 키를 만들면 "이 키는 지금 한 번만 보여요"라는 문구가 떠요. 그 뒤 목록에는 키의 앞 몇 글자만 남아요. 보통은 서버가 키 원문을 다시 보여 주지 않도록 설계해서 그래요. 이 글은 키 한 개의 일생을 따라가요. 저장, 표시, 생성, 권한, 회전, 유출 대응, 전달 위치 순서로 봐요.

아래 시뮬레이터에서 저장 방식과 회전 겹침 기간을 바꾸고 사건을 고르면, 공격자가 쓸 수 있는 키와 실패하는 정상 요청 수가 바로 바뀌어요. 모든 수치는 감을 잡기 위한 예시예요.

## 발급 직후 한 번 표시 — 원문을 다시 만들 수 없는 구조

Stripe 문서는 라이브 모드에서 직접 만든 비밀 키를 저장 전에 한 번만 보여 준다고 설명해요. 이후에는 키를 다시 볼 수 없어요. 잃어버린 키는 복구해 주지 않고, 회전하거나 삭제한 뒤 새로 만들라고 설명해요.

이 구조는 저장 방식과 맞아요. 서버가 해시만 가지고 있으면 원문을 다시 만들 수 없어요. 그래서 발급 화면에서만 전체 값을 보여 주고, 그 뒤에는 접두와 끝 몇 글자만 보여 주는 편이 좋아요.

## 저장 방식 — 해시 저장과 원문 폐기

OWASP 비밀번호 저장 글은 비밀번호를 평문으로 저장하면 안 된다고 설명해요. 같은 글은 SHA-256 같은 빠른 해시가 비밀번호 저장에 맞지 않는다고도 설명해요. 빠르게 많은 추측을 해 볼 수 있어서예요.

API 키는 사람이 고른 글자가 아니라 난수로 만들어요. 그래서 추측 공격의 대상이 비밀번호와 같지 않다고 보는 편이 자연스러워요. 이 판단은 출처 문장에서 직접 나온 것이 아니라 추론이에요. 그래서 키 길이와 난수 품질을 먼저 챙기는 편이 좋아요.

해시는 되돌릴 수 없어요. OWASP 글은 훔친 해시 값으로는 피해자처럼 로그인할 수 없다고 설명해요. 키도 같은 구조로 두면 서버가 요청의 키를 해시해서 저장된 값과 비교해요. DB에서 나온 해시 값을 헤더에 넣어 보내도 인증은 되지 않아요.

## 목록 표시 — 접두와 끝 글자 몇 개

GitHub 문서는 토큰이 종류를 알려 주는 접두로 시작한다고 설명해요. 클래식 개인 액세스 토큰은 `ghp_`, 세분화 토큰은 `github_pat_`로 시작해요. Stripe도 종류와 환경을 접두로 나눠요. 테스트 키는 `pk_test_`, 라이브 키는 `pk_live_`로 시작해요.

접두는 사람이 키 종류를 알아보기 쉽게 해요. GitHub 비밀 스캐닝 목록은 제공자 패턴을 정규식으로 탐지한다고 설명해요. 고정된 접두가 있으면 이런 탐지 규칙을 만들기 쉬워요. 이 부분은 출처 문장이 아니라 추론이에요.

목록에 끝 몇 글자만 보여 주는 것은 설계 선택이에요. 어떤 키인지 구분할 정도만 보여 주고, 나머지 값은 드러내지 않아요.

## 키 생성 — 암호학적 난수와 충분한 길이

키는 암호학적으로 강한 난수 API로 만드는 편이 좋아요. Node.js 문서는 `crypto.randomBytes`가 암호학적으로 강한 의사 난수 데이터를 만든다고 설명해요. 예시로 32바이트를 만들고 URL에 안전한 문자열로 인코딩할 수 있어요.

길이와 난수는 키가 추측되지 않게 하는 조건이에요. 사람이 고른 이름이나 시간으로 키를 만들면 이 조건이 깨져요.

## 권한 범위 — 키마다 최소 권한

Stripe 문서는 모든 권한을 가진 비밀 키보다 제한 키(restricted API key)를 쓰라고 권해요. 제한 키는 키마다 허용한 권한만 가져서, 키 하나가 새도 피해 범위가 줄어요. 같은 문서는 새 용도에 비밀 키를 쓰지 않는 편이 좋다고 설명해요.

OWASP 비밀 관리 글도 비밀에 접근할 수 있는 주체를 최소 권한으로 나누라고 설명해요. 범위는 키 레코드에 붙는 값이고, 서버는 요청마다 그 범위를 확인하는 편이 좋아요.

| 키 예시       | 허용 범위 (예시) | 샜을 때 피해             |
| ------------- | ---------------- | ------------------------ |
| 주문 조회용   | 주문 읽기        | 주문 내용이 보여요       |
| 재고 동기화용 | 재고 읽기 · 쓰기 | 재고 값이 바뀔 수 있어요 |
| 정산 배치용   | 정산 읽기        | 정산 내역이 보여요       |

## 회전 — 새 키 발급, 겹침, 옛 키 폐기

OWASP 비밀 관리 글은 새 키를 쓰기 작업에 먼저 도입하고, 읽기 작업에는 옛 키를 잠시 남겨 두는 점진 교체 방식을 설명해요. 키 회전이 한 번에 끊기지 않게 하는 방법이에요.

Stripe 문서는 대시보드에서 회전하면 옛 키와 새 키가 최대 7일 동안 함께 동작한다고 설명해요. 더 길게 겹쳐야 하면 새 키를 직접 만들고, 옮긴 뒤 옛 키를 폐기하라고 설명해요. 같은 문서는 옛 키의 요청이 몇 시간이나 며칠 동안 0이 된 뒤에 폐기하라고 권해요.

순서는 네 단계로 나눠요.

1. 새 키를 발급해요.
2. 서버와 배치를 하나씩 새 키로 옮겨요.
3. 옛 키의 요청 기록이 줄었는지 확인해요.
4. 요청이 0이 되면 옛 키를 폐기해요.

겹침 기간이 옮기는 기간보다 짧으면 옮기지 못한 쪽의 요청이 실패해요. 시뮬레이터의 `옮기는 3일` 수치가 이 차이를 보여 줘요.

## 유출 대응 — 즉시 폐기와 접두 기반 스캐닝

Stripe 문서는 비밀 키나 제한 키가 침해되면 악의적인 요청을 막으려고 회전해서 폐기하라고 설명해요. 폐기된 키는 더 이상 요청에 쓸 수 없어요.

OWASP 글은 비밀을 폐기할 수 있어야 하고, 폐기된 비밀을 쓰려는 시도도 기록할 수 있어야 한다고 설명해요. 그 기록은 침해 여부를 살필 단서가 돼요.

GitHub 문서는 비밀 스캐닝 알림 중 파트너 알림은 비밀 제공자에게 직접 보고된다고 설명해요. 노출 뒤 재빌드와 커밋 이력 정리는 [환경 설정과 비밀 값 글](/m/secrets-config)에서 이어 봐요.

## 마지막 사용 시각 — 옛 키 폐기 판단 기록

Stripe 문서는 옛 키를 폐기하기 전에 요청 로그를 확인하라고 설명해요. 마지막 사용 시각은 이 확인을 목록에서 바로 할 수 있게 해 줘요. 키가 언제 마지막으로 쓰였는지 보이면 옛 키를 끊어도 되는지 판단하기 쉬워요.

마지막 사용 시각은 요약이에요. 요청 로그 전체를 대신하지는 않아요. 기록할 때는 키 값을 함께 남기지 않는 편이 좋아요. OWASP 글은 비밀을 로그에 남기면 안 된다고 설명해요.

## 전달 위치 — Authorization 헤더 사용

RFC 6750은 액세스 토큰을 `Authorization` 헤더로 보내는 방식을 정해요. URI 쿼리 파라미터 방식은 URL이 로그에 남기 쉬워서 쓰지 말아야 한다고 설명해요(SHOULD NOT). RFC 6750은 OAuth 베어러 토큰 규약이라 API 키 자체의 규약은 아니에요. 그래도 OWASP REST 글은 키를 URL에 넣으면 웹 서버 로그에 남는다고 같은 이유를 들어요.

FE에서는 요청 설정 한 줄이에요. 키를 쿼리 문자열로 붙이는 코드가 보이면 로그에 키가 남을 수 있다고 의심해 보세요.

## 브라우저 코드 — 공개 키와 서버 키 구분

Stripe 문서는 publishable 키만 백엔드 밖에 노출해도 안전하다고 설명해요. 나머지 키는 백엔드 안에서 보호해야 해요. 공개 키는 프런트엔드 코드에 넣어도 된다고 설명해요.

그래서 키 종류를 발급 화면에 함께 보여 주고, 서버 키는 브라우저 번들에 들어가지 않게 해요. 번들에 값이 어떻게 들어가는지는 [환경 설정과 비밀 값 글](/m/secrets-config)에서 이어 봐요.

## FE 체크 포인트

- 발급 화면이 "지금만 보여요"라고 말하면, 키 목록 응답에 전체 값이 없는지 확인해요.
- 키를 요청에 붙이는 코드가 `Authorization` 헤더를 쓰는지 봐요. 쿼리 문자열이면 로그에 남을 수 있어요.
- 회전 화면에 새 키와 옛 키가 함께 동작하는 기간이 표시되는지 봐요. 기간이 없으면 옛 키를 언제 끊는지 알기 어려워요.
- 폐기된 키로 요청했을 때 응답 코드와 메시지를 확인해요. Stripe 문서는 만료된 키가 인증 오류를 돌려준다고 설명해요.
- 요청 제한에 걸린 키의 응답은 [레이트 리밋 글](/m/rate-limiting)에서 이어 봐요.

## 시뮬레이터 안내

아래 시뮬레이터에서 저장, 전달, 표시, 회전 겹침 기간을 바꿔 보세요. 사건을 고르면 공격자가 쓸 수 있는 키 값과 실패하는 정상 요청 수가 나와요. 먼저 `잘못된 예`에서 DB 유출을 고르고, 그다음 `권장`과 비교해 보세요. 회전 중 옛 키 유출과 폐기된 옛 키 사용에서는 겹침 기간에 따라 정상 요청이 어떻게 달라지는지도 보세요.

시뮬레이터는 실제 서비스가 아니에요. 배치가 새 키로 옮기는 데 3일 걸리고 하루 120회 요청한다는 값은 예시예요.

## 정리 — 해시 저장 · 한 번 표시 · 겹침 기간 · 헤더 전달

- 키 원문 대신 해시를 저장하고, 발급 때 한 번만 전체 값을 보여 줘요.
- 목록에는 접두와 끝 몇 글자만 보여 줘요.
- 키는 암호학적 난수로 만들고, 권한 범위를 키마다 나눠요.
- 회전은 새 키 발급, 겹침, 옛 키 폐기 순서로 해요. 옛 키의 요청이 0이 된 뒤 폐기해요.
- 키는 `Authorization` 헤더로 보내고, URL 쿼리에 넣지 않아요.
