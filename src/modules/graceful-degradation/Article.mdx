추천 목록 하나만 늦어요. 그런데 상품 상세 페이지는 통째로 비고, 서버 로그에는 추천 호출 실패가 쌓여요. 상품 정보는 DB에서 금방 가져오는데도 말이에요. 이 글은 느린 의존 서비스 하나가 페이지 전체로 번지는 경로를 따라가고, 서버가 그 전파를 끊는 방법을 정리해요.

이 글의 숫자는 설명을 위한 예시예요. 아래 시뮬레이터의 기본값과 같아요.

## 연쇄 장애 — 느린 의존 서비스가 칸을 붙잡는 구조

서버는 요청을 처리할 때 스레드, 커넥션 같은 칸을 빌려 써요. 칸 수는 한정돼 있어요. 추천 호출이 응답을 기다리는 동안에는 그 칸을 놓지 않아요.

Azure 아키텍처 센터의 Bulkhead 문서는 한 서비스의 과부하나 장애가 그 서비스를 쓰는 모든 소비자에게 영향을 준다고 설명해요. 소비자의 커넥션 풀이 고갈될 수 있다는 예도 들어요.

Google SRE 책은 연쇄 장애를 긍정적 피드백 때문에 시간이 갈수록 커지는 장애라고 설명해요. 가장 흔한 원인은 과부하라고 적어요. 같은 책은 용량이 모자라면 큐가 차고 지연이 늘어나며, 큐가 쓰는 메모리도 늘어난다고 설명해요.

예를 들어 추천 호출 시간 제한이 1000ms이고 초당 50건이 모두 추천을 기다리면, 칸 50개가 동시에 필요해요. 칸이 40개뿐이면 나머지 요청은 상품 정보 호출도 칸을 받지 못해요(예시). 추천은 느릴 뿐인데 상품 정보까지 실패하는 이유가 이 구조에 있어요.

시간 제한을 어떻게 정할지는 [타임아웃과 커넥션 풀](/m/timeouts-and-pools)에서 다뤘어요. 이 글은 칸을 지키는 쪽에 집중해요.

## 서킷 브레이커 상태 — 닫힘 · 열림 · 반열림

Azure 문서는 서킷 브레이커가 실패가 임계치에 닿으면 원격 서비스 접근을 잠시 막아서, 실패할 게 뻔한 작업을 계속 재시도하지 않게 한다고 설명해요. 상태는 세 가지예요.

| 상태               | 호출                             | 바뀌는 조건                            |
| ------------------ | -------------------------------- | -------------------------------------- |
| 닫힘 (closed)      | 그대로 보내고 실패를 세요        | 실패가 임계치에 닿으면 열려요          |
| 열림 (open)        | 보내지 않고 바로 실패로 돌려줘요 | 열림 시간이 지나면 반열림으로 바뀌어요 |
| 반열림 (half-open) | 제한된 시험 호출만 통과시켜요    | 성공하면 닫히고, 실패하면 다시 열려요  |

Azure 문서는 반열림 상태가 막 회복한 서비스에 요청이 한꺼번에 몰리는 일을 막아 준다고 설명해요. Azure 문서는 닫힘 상태의 실패 카운터를 시간 기준으로 센다고도 설명해요. 시뮬레이터는 이해를 쉽게 하려고 연속 실패 수로 세요.

AWS Builders' Library는 서킷 브레이커가 시스템을 모드처럼 바꿔 테스트하기 어렵게 만들고, 복구 시간을 상당히 늘릴 수 있다고 설명해요. 같은 글은 이 위험을 줄이려고 토큰 버킷으로 재시도를 제한한다고 적어요.

임계치는 정상 순간의 실패 몇 건으로 열리지 않을 만큼 높게, 칸이 다 차기 전에 열릴 만큼 낮게 잡는 편이 좋아요. 열림 시간은 추천 서비스가 회복되는 데 걸리는 시간에 맞춰 정해요. 설계 판단이에요.

## 재시도 예산 — 재시도 횟수와 양의 상한 두기

재시도는 일시적인 실패를 넘기게 도와줘요. 하지만 원인이 과부하일 때는 부하를 더 키워요. Azure Retry 문서는 간격이 짧고 재시도가 많은 정책이 이미 한계에 가까운 바쁜 서비스를 더 악화시킬 수 있다고 설명해요.

Google SRE 책은 요청 하나당 재시도 횟수를 제한하라고 권해요. 무한정 재시도하지 말라는 뜻이에요. 같은 책은 프로세스 전체에 재시도 예산을 두는 방법도 설명해요. 예를 들어 프로세스마다 분당 60번만 재시도하고, 예산을 넘기면 재시도 없이 요청을 실패로 끝내요. 이렇게 하면 재시도 효과가 한 곳에 갇혀서 전체 장애로 번지는 일을 막을 수 있다고 적어요.

Azure Retry 문서는 중요하지 않은 작업은 여러 번 재시도하기보다 빨리 실패하는 편이 낫다고 설명해요. 여러 번 재시도한 뒤에도 실패하면 같은 리소스로 가는 요청을 더 막고 바로 실패를 알리는 편이 낫다고도 설명해요.

| 제한 수단          | 막는 대상               | 정해야 할 값          |
| ------------------ | ----------------------- | --------------------- |
| 요청마다 횟수 상한 | 한 요청이 계속 도는 것  | 재시도 횟수           |
| 재시도 예산        | 프로세스 전체 재시도 양 | 분당 허용량           |
| 토큰 버킷          | 순간 폭주와 지속 재시도 | 토큰 크기와 보충 속도 |

재시도 전에는 그 호출이 멱등한지도 봐야 해요. AWS 글은 시간 초과나 실패가 부작용이 일어나지 않았다는 뜻은 아니라고 설명해요. 그래서 부작용이 있는 API는 멱등하게 설계하는 것이 모범 사례라고 적어요. 결제처럼 돈이 움직이는 요청은 [결제 — 이중 결제 막기](/m/payment-idempotency)의 멱등성 키로 막아요.

시뮬레이터의 재시도 횟수는 요청마다 상한이에요. 재시도 예산이나 토큰 버킷은 넣지 않았어요.

## 지터 — 같은 시각에 맞춘 재시도 흩기

AWS Builders' Library는 부하 때문에 실패하면 모든 클라이언트가 같은 시각에 재시도할 때 재시도가 효과를 잃을 수 있다고 설명해요. 그래서 지터를 넣는다고 적어요.

Azure Retry 문서는 여러 인스턴스의 재시도 간격을 요청이 최대한 고르게 퍼지도록 정하라고 설명해요. 바쁜 서비스가 과부하에서 벗어나지 못하는 위험을 줄이려는 목적이에요.

AWS Architecture Blog는 경쟁하는 클라이언트가 100개일 때, 지터를 넣은 백오프가 지터 없는 지수 백오프보다 호출 수를 절반 넘게 줄였다고 보여 줘요. 같은 글은 Full Jitter, Equal Jitter, Decorrelated Jitter를 비교해요. Equal Jitter는 백오프의 일부를 남기고 더 작은 폭만 흔드는 방식인데, 지터 방식 가운데 가장 나빴다고 설명해요. Full Jitter는 일이 적고 시간은 조금 걸린다고 설명해요.

시뮬레이터는 재시도 간격을 0과 백오프 사이에서 무작위로 고르는 방식을 써요. 요청을 10건씩 같은 순간에 도착시키고 재시도를 2번으로 두면, 지터가 없을 때 가장 몰린 10ms 호출이 20건, 지터를 켜면 11건이에요(예시).

## 벌크헤드 — 의존 서비스마다 칸 나누기

Azure Bulkhead 문서는 애플리케이션의 요소를 풀로 나눠서, 한 요소가 실패해도 다른 요소가 계속 돌아가게 한다고 설명해요. 이름은 배의 선체를 칸막이로 나눈 구조에서 왔다고 적어요. 소비자가 자원을 나눠서, 한 서비스를 부르는 데 쓰는 자원이 다른 서비스를 부르는 자원에 영향을 주지 않게 할 수 있다고도 설명해요.

| 방식                        | 막는 것                               | 대가                                          |
| --------------------------- | ------------------------------------- | --------------------------------------------- |
| 벌크헤드 (칸 나누기)        | 한 의존 서비스가 칸을 독점하는 것     | 추천 칸을 넘는 호출은 칸이 없어 보내지 못해요 |
| 서킷 브레이커 (호출 멈추기) | 실패가 계속되는 호출을 계속 보내는 것 | 열려 있는 동안 추천을 아예 받지 못해요        |

칸 크기는 호출량과 응답 시간을 곱해서 정하는 편이 좋아요. 초당 50건이 추천을 1초씩 기다리면 칸 50개가 필요해요. 칸을 10개로 나누면 40건 이상이 거절돼요(예시). 거절된 추천은 다음 절의 대체 응답으로 채워요. 설계 판단이에요.

시뮬레이터에서 벌크헤드만 켜면 상품 정보 실패가 0건이 돼요. 대신 추천 칸 10개를 넘는 호출은 보내지 못해요(예시).

## 대체 응답 — 빠진 추천 자리 채우기

Azure 문서는 서킷이 열린 상태에서 실패를 던지는 대신, 애플리케이션에 의미 있는 기본값을 돌려줄 수 있다고 설명해요. 다른 작업을 시도하거나 사용자에게 실패를 알리고 나중에 다시 하라고 안내하는 방법도 있다고 적어요. 열림 상태에서는 기본값이나 캐시 응답을 돌려주며 우아하게 기능을 줄이고, 사용자에게 일시적인 축소를 알린다고 설명해요.

| 대체 방식 | 예                        | 주의할 점                                                 |
| --------- | ------------------------- | --------------------------------------------------------- |
| 캐시 값   | 마지막으로 받은 추천 목록 | 옛 값이 섞이니 시각을 같이 보여 줘요                      |
| 기본값    | 빈 목록이나 기본 문구     | 빈 상태와 실패를 화면에서 구분해야 해요                   |
| 생략      | 추천 영역 숨기기          | 가장 단순하지만 이유를 알려 주지 않으면 사용자가 헷갈려요 |

Google SRE 책은 우아한 축소가 부하 차단의 개념을 한 걸음 더 나아가, 처리할 일의 양을 줄이는 것이라고 설명해요. 같은 책은 평소에는 쓰이지 않는 축소 모드가 운영 경험이 적어서 위험이 커진다고 설명해요. 그래서 과부하에 가까운 일부 서버에서 정기적으로 돌려 보라고 권해요.

추천이 빠진 응답은 이런 모양이 좋아요. 예시 응답이에요.

```json
{
  "product": { "id": "p_102", "name": "무선 키보드", "price": 32000 },
  "recommendations": null,
  "degraded": ["recommendations"]
}
```

빈 배열 대신 `null`과 `degraded` 목록을 주는 편이 좋아요. 빈 배열은 추천이 없는 상품과 구분되지 않아요. 설계 판단이에요.

## 부분 응답 — 영역별 필드 누락과 degraded 표시

여러 호출을 묶은 응답에서는 한 호출만 실패할 수 있어요. 그때 data와 errors를 함께 읽는 방법은 [API 조합(BFF)](/m/api-composition)에서 다뤘어요. 이 글은 실패한 영역을 응답에서 어떻게 표시할지에 집중해요.

부분 응답은 전체를 실패로 돌리지 않고, 살아 있는 영역만 채워서 보내는 응답이에요. 실패한 영역은 필드를 `null`로 두고 어떤 영역이 빠졌는지 목록으로 알려 줘요. 설계 판단이에요.

## FE 체크 포인트 — 영역별 상태와 재시도 버튼

- 영역마다 상태를 따로 그려요. 추천 영역만 빈 상태와 다시 시도 버튼을 보여 주고, 상품 정보 영역은 그대로 두세요.
- 스켈레톤은 로딩 중에만 보여 주세요. 실패한 영역에 스켈레톤을 계속 두면 로딩이 끝나지 않은 것처럼 보여요.
- 자동 재시도는 백오프와 횟수 상한을 두거나 하지 마세요. 사용자가 버튼을 연타하면 재시도가 쌓여요. 응답을 기다리는 동안에는 버튼을 잠가 두세요.
- `degraded` 목록을 읽어 문구를 나눠요. 추천이 빠졌다는 문구와 상품이 없다는 문구는 다른 문제예요.
- 429나 503을 받으면 헤더가 알려 주는 시각을 따르세요. 기준은 [레이트 리밋 알고리즘](/m/rate-limiting)과 [API 에러 모양](/m/api-errors)에 있어요.
- 추천 기능 자체를 끌 수 있으면 [기능 플래그](/m/feature-flags)의 킬 스위치로 호출을 멈추세요.

## 시뮬레이터 안내

아래 시뮬레이터에서 추천 장애의 응답 시간과 실패율, 호출 시간 제한, 재시도 횟수를 정하고, 서킷 브레이커, 벌크헤드, 대체 응답, 지터, 동기화를 하나씩 켜 볼 수 있어요.

기본값에서는 칸이 고갈돼서 상품 정보 호출도 많이 실패해요(예시). 대체 응답만 켜면 실패 수는 줄지만 상품 정보 실패는 그대로예요. 서킷 브레이커를 켜면 추천 호출이 약 절반으로 줄어요(예시). 벌크헤드를 켜면 상품 정보 실패가 0건이 돼요(예시).

## 정리 — 칸 나누기 · 서킷 상태 · 재시도 상한 · 대체 응답 기준

칸은 의존 서비스마다 나누고, 크기는 호출량과 응답 시간을 곱해서 정해요. 서킷 브레이커는 연속 실패가 쌓이면 열고, 반열림 시험으로 회복을 확인해요. 재시도는 요청마다 횟수 상한을 두고, 지터로 흩고, 멱등한 요청에만 해요. 대체 응답은 영역 단위로 주고, `degraded` 목록으로 빠진 영역을 알려요.
