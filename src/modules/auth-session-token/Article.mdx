로그인하고 십 분쯤 지나면 API가 `401`을 돌려줘요. 화면에서 요청 다섯 개가 한꺼번에 실패하고, 어떤 요청은 로그인 화면으로 밀려나요. 토큰을 어디에 두고 언제 갱신해야 하는지 정하지 않으면 이 장면이 계속 나와요.

이 글은 액세스 토큰을 어디에 저장할지, 만료되면 어떻게 갱신할지를 다뤄요. 아래 시뮬레이터에서 동시에 나간 요청이 갱신을 어떻게 처리하는지도 직접 돌려 볼 수 있어요.

## 서버 세션과 토큰 — 폐기 · 확장성 · 크기 비교

로그인 상태를 기억하는 방법은 크게 둘이에요. 서버가 세션을 들고 있으면 쿠키에는 세션 ID만 담아요. 토큰(JWT)을 쓰면 클라이언트가 내용이 든 토큰을 들고 다니고, 서버는 서명만 확인해요.

| 기준      | 서버 세션 + 쿠키                                                                                | 토큰 (JWT)                                                                                                               |
| --------- | ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 폐기      | 서버가 세션을 지우면 바로 끝나요. OWASP는 로그아웃할 때 서버에서 세션을 무효화해야 한다고 해요. | RFC 7519 본문에는 발급한 토큰을 폐기하는 방법이 없어요. 만료 시간을 짧게 두고, 폐기 목록 같은 장치는 따로 설계해야 해요. |
| 확장성    | 여러 서버가 같은 세션 저장소를 봐야 해요.                                                       | 서명 키만 있으면 검증할 수 있어요. 서버끼리 상태를 나눌 필요가 줄어요.                                                   |
| 크기      | 쿠키에는 짧은 세션 ID만 실려요.                                                                 | 클레임이 늘면 토큰이 커져요. 쿠키 하나는 최소 4096바이트까지 지원하도록 정해져 있어요(RFC 6265).                         |
| 내용 노출 | 내용은 서버에만 있어요.                                                                         | 서명만 한 JWT는 내용을 누구나 읽을 수 있어요. 서명(JWS)과 암호화(JWE)는 RFC 7519에서 따로 정의해요.                      |

브라우저 앱이라면 서버 세션과 HttpOnly 쿠키가 단순하고, 폐기가 확실해요. 토큰을 고른다면 수명을 짧게 두고, 리프레시 쪽은 서버가 상태를 쥐는 쪽이 안전해요. 이 판단은 설계 선택이에요.

## 쿠키 속성 — HttpOnly · Secure · SameSite가 막는 것

세션 쿠키에는 속성 세 가지를 같이 줘요. 각각 막는 위험이 달라요.

| 속성                               | 막는 것                                                    | 한계                                                                                                                                                                                                                                              |
| ---------------------------------- | ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `HttpOnly`                         | 스크립트가 `document.cookie`로 쿠키를 읽는 것을 막아요.    | XSS 자체를 막지는 않아요. OWASP는 쿠키 기밀성만 지킨다고 설명해요. HttpOnly 쿠키도 같은 origin으로 보내는 `fetch()` 요청에는 그대로 실려 가요(MDN). 그래서 XSS가 있으면 공격 스크립트가 쿠키를 읽지 못해도 사용자 이름으로 요청은 보낼 수 있어요. |
| `Secure`                           | HTTPS 연결에서만 쿠키를 보내요.                            | 민감한 정보를 쿠키에 넣어도 된다는 뜻은 아니에요. MDN은 Secure 만으로 모든 접근을 막지 못한다고 명시해요.                                                                                                                                         |
| `SameSite=Strict` · `Lax` · `None` | 다른 사이트에서 시작한 요청에 쿠키를 붙이는 범위를 정해요. | 값을 생략했을 때 기본 동작은 브라우저마다 달라요. CSRF를 완전히 막지는 못해요.                                                                                                                                                                    |

`__Host-` 접두사를 쓰면 Secure가 필수이고, `Path=/`이며, `Domain`이 없어야 해요. 쿠키가 발급한 호스트에만 묶여요(MDN).

## 저장 위치 — localStorage에 토큰을 두면 생기는 일

`localStorage`에 넣은 값은 같은 origin의 모든 스크립트가 읽을 수 있고, 브라우저를 닫아도 남아요(MDN Web Storage). OWASP는 인증 토큰, 세션 ID, JWT, 리프레시 토큰을 `localStorage`나 `sessionStorage`에 두지 말라고 해요. XSS 취약점이 하나라도 있으면 그 자리에서 모든 토큰이 빠져나가기 때문이에요.

그래서 FE가 할 일은 두 가지예요. 토큰 값을 JavaScript에서 읽을 필요가 없도록 HttpOnly 쿠키로 받고, 갱신 호출만 같은 origin으로 보내요. 액세스 토큰을 메모리 변수에만 두는 방법도 있지만, 새로고침하면 사라지니 갱신 흐름이 반드시 같이 있어야 해요.

## 짧은 액세스 토큰과 리프레시 토큰 — 수명 나누기

액세스 토큰은 수명을 짧게, 리프레시 토큰은 새 액세스 토큰을 받는 용도로만 써요. RFC 9700은 리프레시 토큰이 짧은 수명의 액세스 토큰을 가능하게 해서, 액세스 토큰이 새어도 피해를 줄인다고 설명해요.

다만 리프레시 토큰은 그 클라이언트가 쓸 수 있는 권한 전체를 대신해요. 그래서 노출되면 공격자가 액세스 토큰을 계속 발급받을 수 있어요.

RFC 9700은 이 위험을 막으려고 두 가지 중 하나를 요구해요.

- 토큰을 클라이언트에 묶는 방법 (발신자 제한)
- 갱신할 때마다 토큰을 바꾸는 방법 (회전)

브라우저 앱처럼 공개 클라이언트에는 이 요구가 그대로 적용돼요.

## 리프레시 토큰 회전 — 재사용 감지와 강제 로그아웃

회전은 갱신 응답마다 새 리프레시 토큰을 주고, 이전 토큰을 무효화해요. RFC 9700은 여기에 재사용 감지를 붙이는 그림을 설명해요.

1. 공격자와 정상 클라이언트가 같은 리프레시 토큰을 가지고 있어요.
2. 먼저 쓴 쪽이 새 토큰을 받고, 옛 토큰은 무효가 돼요.
3. 나중에 옛 토큰이 다시 오면 서버는 침해가 일어났다는 것을 알아요.
4. 서버는 누가 보냈는지는 알 수 없어요. 대신 활성 리프레시 토큰을 폐기해서 공격을 멈춰요.

대가도 있어요. 정상 클라이언트도 새로 인가를 받아야 해요. 보통은 다시 로그인하는 흐름이에요. 이 대가는 아래 시뮬레이터에서 가장 크게 보여요.

## 401 동시 갱신 — 갱신 요청을 하나로 묶기

만료된 토큰으로 요청 다섯 개가 동시에 나가면 401도 다섯 개가 와요. 각 요청이 "나만 갱신하면 되겠지" 하고 리프레시를 부르면 두 가지 문제가 생겨요.

- 갱신 요청이 여러 번 나가요. 회전을 쓰면 같은 옛 리프레시 토큰이 여러 번 제출돼요.
- 두 번째부터는 무효 토큰이라 거절돼요. 재사용 감지가 켜져 있으면 서버가 침해로 보고 세션을 끊어요.

그래서 설계는 이렇게 가요. 이 흐름은 FE가 짜는 설계 예시이고, 출처 명세가 정한 규칙은 아니에요.

- 첫 401이 갱신을 시작하고, 나머지 401은 그 결과를 기다려요.
- 갱신이 끝나면 기다린 요청을 새 액세스 토큰으로 한 번씩 다시 보내요.
- 이미 새 토큰이 있으면 갱신 없이 바로 재시도해요.

재시도는 한 번만 해요. RFC 9110은 새 자격 증명으로 다시 보냈는데도 같은 인증 요구(challenge)가 담긴 401이 오면, 클라이언트가 응답 내용을 사용자에게 보여 주는 것이 좋다고 권해요.

RFC 9110은 재시도 횟수를 정하지 않아요. 그래서 무한 재시도는 피하는 편이 좋아요. 이 부분은 설계 판단이에요.

## 401과 403 — 자격 증명 문제와 권한 문제

| 상태             | RFC 9110의 뜻                                                                               | 클라이언트가 할 일                                                                      |
| ---------------- | ------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| 401 Unauthorized | 요청에 유효한 자격 증명이 없어요. 응답은 `WWW-Authenticate` 헤더로 인증 방법을 알려야 해요. | 토큰을 갱신하고 한 번 재시도해요. 갱신도 실패하면 로그인으로 보내요.                    |
| 403 Forbidden    | 서버는 요청을 이해했지만 거부해요. 자격 증명이 있어도 권한이 부족하다는 뜻이에요.           | 같은 자격 증명으로 자동 재시도하지 않는 것이 좋아요(SHOULD NOT). 권한 안내를 보여 줘요. |

관리자 페이지에서 일반 회원이 `403`을 받았다면 토큰을 갱신할 이유가 없어요. `401`을 받았을 때만 갱신 흐름에 들어가요.

## CSRF — 쿠키로 인증할 때 남는 문제

쿠키로 인증하면 브라우저는 다른 사이트가 만든 요청에도 쿠키를 실어 보낼 수 있어요. 그래서 상태를 바꾸는 요청에는 CSRF 방어가 필요해요. OWASP는 쿠키로 인증하는 앱에는 CSRF 토큰이 여전히 필요하다고 해요. 동기화 토큰 패턴은 가장 널리 권장되는 방법 중 하나예요. SameSite는 이 방어를 보완하는 장치로 함께 써요.

API가 `<form>`을 쓰지 않는다면 OWASP는 사용자 지정 요청 헤더를 권해요. 다만 XSS가 있으면 어떤 CSRF 방어도 뚫린다는 점을 기억해야 해요.

## 시뮬레이터 안내 — 동시 401과 갱신 전략

시뮬레이터는 동시에 나간 요청 수, 갱신 방식, 회전, 재사용 감지를 바꿔 가며 결과를 보여 줘요. 시간 값은 설명을 위한 가정이에요. 같은 시드에서는 항상 같은 결과가 나와요. "다른 타이밍으로 보기"를 누르면 응답 지연이 바뀌어요.

- **각자 갱신 · 회전 없음**: 갱신 요청 수가 요청 수만큼 나가요. 회전이 없으니 모두 성공해요. 대신 갱신이 불필요하게 많아요.
- **각자 갱신 · 회전**: 같은 옛 토큰이 여러 번 제출돼 대부분 실패해요. 재사용 감지가 꺼져 있어서 세션은 살아 있어요.
- **각자 갱신 · 회전 · 재사용 감지**: 두 번째로 처리된 갱신에서 서버가 세션 전체를 폐기해요. 이후 갱신은 모두 실패해요.
- **하나로 묶어 갱신**: 갱신은 한 번만 나가고, 모든 요청이 새 토큰으로 성공해요.

재사용 감지로 세션이 끊긴 뒤에도 로그에 "재시도 성공"이 남을 수 있어요. 서버가 폐기한 것은 리프레시 토큰이고, 그 전에 먼저 갱신에 성공한 요청은 이미 새 액세스 토큰을 받았기 때문이에요.

그 액세스 토큰은 만료될 때까지 통과할 수 있어요. RFC 7519에는 발급한 토큰을 폐기하는 방법이 없어서, 이 공백은 액세스 토큰 수명을 짧게 두는 이유가 돼요.
