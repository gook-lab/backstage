장바구니에 담을 때는 재고가 충분했는데, 결제 버튼을 누르니 "품절이에요"가 뜨는 경험이 있을 거예요. 장바구니는 "나중에 살 목록"처럼 보이지만, 재고 입장에서는 그 순간에 무언가를 잡아 둘지 말지 정해야 하는 자리예요. 이 글에서는 언제 재고를 줄일지, 그 선택이 초과 판매와 포기한 손님 중 무엇을 만드는지, 그리고 프론트엔드가 가격과 재고 변화를 어떻게 받아야 하는지 정리해요.

아래 시뮬레이터에서 한정 판매 상황을 직접 돌려 볼 수 있어요. 글에서 말하는 세 가지 차감 시점과 원자적 차감 규칙을 그대로 따라요.

## 장바구니 — 담긴 목록과 재고 예약의 차이

장바구니에 담긴 상품은 "이 사람이 이걸 살 생각이 있다"는 기록일 뿐이에요. 재고를 잡았다는 뜻은 아니에요. 재고를 잡으려면 별도의 규칙이 필요하고, 그 규칙이 이 글의 중심이에요.

장바구니를 어디에 저장하는지에 따라 기기 간 동기화와 병합 방식이 달라져요.

| 저장 위치                         | 장점                                                                  | 주의                                                                              |
| --------------------------------- | --------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| 브라우저 저장소 (localStorage 등) | 로그인 없이 바로 담을 수 있어요                                       | MDN 문서대로 출처(origin)별로 브라우저 안에만 남아요. 다른 기기에는 보이지 않아요 |
| 서버 DB (회원 ID 기준)            | 기기가 바뀌어도 같은 목록을 봐요. 재고와 같은 DB에서 검사할 수 있어요 | 담을 때마다 요청이 가요. 같은 행을 두 기기가 동시에 고치면 충돌이 나요            |
| 캐시 (메모리 저장소 등)           | 응답이 빨라요                                                         | 만료나 유실을 어떻게 다룰지 정해야 해요. 장바구니의 기준 데이터로 쓰면 안 돼요    |

### 비회원 장바구니를 로그인 뒤에 합치기

비회원일 때 브라우저에 담은 목록은 로그인하는 순간 서버 장바구니와 합쳐야 해요. 합치는 규칙은 세 가지가 흔해요.

| 규칙           | 결과                                       | 주의                                         |
| -------------- | ------------------------------------------ | -------------------------------------------- |
| 수량 더하기    | 같은 상품은 두 수량을 더해요               | 두 번 담긴 것처럼 보여 수량이 부풀 수 있어요 |
| 최신 쪽 우선   | 마지막에 바꾼 쪽을 남겨요                  | 한쪽 담기 기록이 조용히 사라져요             |
| 재고 상한 적용 | 합친 수량을 현재 재고와 구매 한도로 잘라요 | 잘린 줄을 반드시 알려 줘야 해요              |

실무에서는 보통 "수량 더하기 뒤 재고 상한 적용"을 고르고, 잘린 줄은 줄 옆에 안내를 붙여요.

이 선택은 설계 판단이에요. 어떤 규칙이 맞는지는 서비스가 파는 상품과 손님이 기대하는 바에 따라 달라요.

### 여러 기기 · 탭의 동시 수정 — 절대값 요청

같은 장바구니를 두 탭에서 고치면 나중에 저장된 요청이 앞선 변경을 덮을 수 있어요. "수량을 3으로" 같은 절대값 요청은 여러 번 보내도 결과가 같아서 안전해요. 반대로 "수량을 1 더하기" 같은 상대값 요청은 재시도 때마다 값이 늘어요. RFC 9110은 여러 번 보내도 한 번 보낸 것과 같은 효과를 내는 메서드를 멱등하다고 정의해요. 그래서 수량 변경 API는 가능하면 절대값으로 설계하는 편이 안전해요.

## 재고를 줄이는 시점 — 언제 잡을지 고르기

재고를 줄이는 시점은 세 가지예요.

| 시점                      | 손님이 겪는 것                     | 대가                                                                              |
| ------------------------- | ---------------------------------- | --------------------------------------------------------------------------------- |
| 장바구니에 담을 때 잡기   | 담은 뒤에는 품절이 없어요          | 담기만 하고 떠난 손님이 보류 시간 동안 재고를 붙잡아요 (phantom hold)             |
| 결제를 시작할 때 잡기     | 결제 중에는 품절이 없어요          | 결제창에서 망설이다 떠난 손님이 재고를 잡아요                                     |
| 결제가 확정될 때 차감하기 | 보류가 없어서 가장 공정하게 보여요 | 결제 때 품절을 볼 수 있어요. 같은 재고를 동시에 확인하면 초과 판매가 날 수 있어요 |

핵심 트레이드오프는 **초과 판매**와 **포기한 보류**예요. 보류를 많이 잡으면 초과 판매는 줄지만, 떠난 손님의 보류가 재고를 묶어요. 보류를 적게 잡으면 판매는 빨라지지만, 결제 때 품절을 보는 손님이 늘어요.

한정 판매처럼 수요가 재고보다 훨씬 많은 상황은 보류를 택하는 편이 맞아요. 초과 판매 한 건의 비용이 크고, 보류가 묶는 재고는 TTL이 지나면 다시 풀리기 때문이에요.

일반 카탈로그처럼 재고가 넉넉한 상품은 결제 확정 때 차감하고 부족하면 바로 알려 주는 쪽이 간단하고 손님도 덜 불편해요. 이것도 설계 판단이에요.

예시로 재고 20개, 손님 60명, TTL 8틱, 포기율 30% 인 상황을 돌려 보면 이런 차이가 나요. 시뮬레이터의 값은 이 설정에서 나온 예시일 뿐이고, 실제 서비스의 수치가 아니에요.

- 담을 때 잡기: 구매 19명, 담을 때 품절 34명. 재고 20개 중 19개만 팔렸어요.
- 결제 시작할 때 잡기: 구매 20명, 결제 화면에서 품절 30명, 결제 중 품절 0명.
- 결제 확정 때 차감: 구매 20명, 결제 때 품절 24명. 보류가 없어서 결제 순간에야 품절을 알아요.

## 원자적 차감 — 확인과 차감을 한 문장으로

재고를 줄일 때 가장 흔한 실수는 "읽고, 앱에서 확인하고, 다시 쓰는" 패턴이에요. 두 손님이 같은 재고 1개를 동시에 읽으면 둘 다 "있어요"라고 판단해요. 자세한 과정은 [트랜잭션 · 락 · 데드락](/m/transactions) 글의 갱신 손실에서 다뤘어요.

조건과 차감을 한 문장으로 쓰면 이 문제를 막을 수 있어요.

```sql
UPDATE stock
SET qty = qty - $1
WHERE sku = $2 AND qty >= $1;
```

PostgreSQL 문서는 UPDATE가 갱신된 행 수를 알려 준다고 설명해요. 그 값이 0이면 아무 행도 갱신되지 않았다는 뜻이에요.

읽기 커밋 격리 수준에서 기다리던 UPDATE는 앞선 변경이 커밋된 뒤 갱신된 행에 WHERE 조건을 다시 적용해요. 재고가 이미 0이면 두 번째 UPDATE는 조건을 통과하지 못해요.

앱은 **영향받은 행 수를 반드시 확인**해야 해요. 0 행이면 품절로 응답하고, 1 행이면 다음 단계로 넘어가요. 행 수를 무시하면 실패가 조용히 지나가요.

### 예약 테이블과 만료 시간

보류를 두려면 예약을 별도 테이블에 남기고 만료 시간을 함께 적어요.

```sql
BEGIN;
UPDATE stock SET qty = qty - $1 WHERE sku = $2 AND qty >= $1;
INSERT INTO reservation (sku, qty, status, expires_at)
VALUES ($2, $1, 'held', now() + interval '10 minutes');
COMMIT;
```

만료된 예약은 두 방법 중 하나로 풀어요. 주기적인 작업이 만료된 예약을 찾아 재고를 되돌리거나, 재고를 읽을 때 만료된 예약을 빼고 계산해요. 어느 쪽이든 결제 확정 때는 "예약이 아직 살아 있는지"를 다시 확인해야 해요. 예약이 풀린 뒤 결제가 들어오면 원자적 차감을 한 번 더 해요.

결제 세션에도 시간 제한이 있어요. Stripe의 Checkout Session은 생성 뒤 30분에서 24시간 사이에서 만료 시각을 정할 수 있고, 기본값은 24시간이에요. 재고 보류와는 다른 개념이지만, 결제 흐름마다 얼마나 기다릴지 정해야 한다는 점은 같아요.

보류 시간을 얼마나 줄지는 손님이 결제를 끝내는 데 걸리는 시간으로 정해요. TTL이 짧으면 결제 중인 손님이 보류를 잃고, 길면 포기한 손님이 재고를 오래 붙잡아요. 아래 시뮬레이터에서 TTL을 바꿔 보면 두 쪽이 모두 보여요.

### 핫 SKU 행 — 버킷 분산과 샤드 트레이드오프

인기 상품 한 개의 재고 행에 모든 차감이 몰리면, 그 행의 락을 기다리는 요청이 줄을 서요. 처리량이 한 행의 쓰기 속도에 묶여요. 이 문제를 줄이는 방법은 설계 선택지예요. 특정 서비스가 이 방식을 쓴다는 뜻은 아니에요.

- 재고를 여러 버킷으로 나눠요. 예를 들어 같은 상품을 8개 행으로 쪼개고, 요청마다 무작위 버킷부터 차감해요.
- 버킷이 비면 다른 버킷에서 가져오는 재분배 작업이 필요해요. 모든 버킷이 아직 재고를 가지고 있는데 한 버킷만 비면 요청이 실패할 수 있어요.
- 카운터를 샤드로 나누면 쓰기는 가벼워지지만, 전체 재고가 0 인지 정확히 보려면 샤드를 모두 읽어야 해서 비싸고 복잡해요.

쪼갤수록 쓰기는 빨라지고, 재고가 "남았는데 팔 수 없는" 상황이 늘어나요. 이 균형을 정하는 것이 설계의 핵심이에요.

## 가격 변경 — 담을 때 가격과 결제할 때 가격

장바구니에 담을 때 본 가격과 결제할 때의 가격은 다를 수 있어요. 프로모션이 끝나거나 가격이 바뀌었을 수 있어요.

규칙은 세 가지예요.

- 장바구니 화면에는 담을 때 가격을 스냅샷으로 보여 주고, 현재 가격이 다르면 함께 알려 줘요.
- 결제할 때 서버가 현재 가격으로 줄별 금액과 합계를 다시 계산해요.
- 클라이언트가 보낸 가격이나 합계는 믿지 않아요. 요청에 들어 있는 금액은 참고용으로만 봐요.

가격이 바뀌었거나 재고가 부족하면 서버는 줄 단위로 어떤 문제인지 알려 줘야 해요. HTTP는 409를 "요청이 대상 리소스의 현재 상태와 충돌했다"는 뜻으로 정의해요(RFC 9110). 재고 부족이나 가격 변경은 현재 상태와 맞지 않는 요청이므로 409로 응답하는 방식을 고려할 만해요. 응답 본문에 줄별 코드를 담는 형식과 이 매핑은 설계 판단이에요.

결제 버튼을 누른 뒤 바뀐 가격으로 자동 진행하면 손님이 동의한 금액과 다른 금액이 결제될 수 있어요. 바뀐 가격을 화면에 보여 주고 다시 확인받은 뒤에 진행해야 해요.

## FE 체크 포인트

**결제 화면에 들어갈 때 장바구니를 다시 확인해요.** 목록을 받은 시점과 결제 시점 사이에 재고와 가격이 바뀔 수 있어요. 진입할 때 서버에 검증을 요청하고, 결과를 줄 단위로 보여 주세요.

**에러는 줄 옆에 붙여요.** 품절, 수량 부족, 가격 변경은 서로 다른 행동이 필요해요. 토스트 하나로 "오류가 났어요"라고 하면 손님이 무엇을 고쳐야 할지 몰라요. 줄 옆에 "품절이에요", "재고가 2개예요", "가격이 1,000원 올랐어요"처럼 구체적으로 적어 주세요.

**담기는 낙관적으로 반영하고, 실패하면 되돌려요.** 버튼을 누르자마자 장바구니 숫자를 올리고, 실패 응답이 오면 이전 값으로 되돌려요. 되돌릴 때는 조용히 바꾸지 말고 무슨 일이 있었는지 한 줄로 알려 주세요.

**재시도가 안전하도록 요청을 멱등하게 만들어요.** Stripe 문서는 API v1에서 같은 idempotency key로 다시 보낸 요청에 처음 저장된 응답을 돌려준다고 설명해요. 담기 요청에도 같은 원리를 쓸 수 있어요. IETF 초안도 Idempotency-Key 헤더로 POST를 재시도에 견디게 하는 방식을 다뤄요. 아직 표준 RFC는 아니라는 점을 기억해 두세요.

**수량 스테퍼는 연속 입력을 묶어요.** 버튼을 빠르게 여러 번 누르면 마지막 값 한 번만 보내요. 요청이 줄면 서버 부하도 줄고, 응답이 뒤섞이는 일도 줄어요.

**장바구니 숫자는 서버 응답을 기준으로 맞춰요.** 탭이 여러 개면 한 탭의 변경을 다른 탭에 알려야 해요. 배지 숫자는 로컬 계산보다 마지막 서버 응답을 따르게 하면 어긋남이 줄어요.

## 정리 — 차감 시점별 정확도와 품절 알림 시점

장바구니는 재고를 잡지 않아요. 재고를 언제 줄일지 정하는 것이 핵심 선택이에요. 담을 때 잡으면 품절을 늦게 알리고 포기한 손님이 재고를 묶어요. 결제 때 차감하면 보류가 없지만 결제 순간 품절을 볼 수 있어요.

어느 쪽이든 차감은 원자적으로 해야 해요. 조건과 차감을 한 문장으로 쓰고, 영향받은 행 수를 확인하세요. 가격과 합계는 서버가 다시 계산하고, 품절과 가격 변경은 줄 단위 응답으로 받아 화면에 구체적으로 보여 주세요.

더 깊이 보고 싶다면 같은 원리가 좌석 점유에서 어떻게 쓰이는지 [콘서트 좌석 점유](/m/concert-seats) 글을, 결제 재시도에서 멱등성 키가 어떻게 쓰이는지 [결제 멱등성](/m/payment-idempotency) 글을 이어서 읽어 보세요.
