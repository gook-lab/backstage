상품 상세 페이지를 서버에서 렌더링하면 요청마다 DB를 읽고 HTML을 새로 만들어요. 그런데 로그인 여부에 따라 헤더가 달라지면 같은 HTML을 모든 사람에게 줄 수 없어서, CDN 캐시도 쓰기 어려워 보여요. 이 글은 렌더링 결과를 언제 만들고, 어디에 두고, 어느 부분을 떼어 낼지 따라가요. 아래 시뮬레이터에서 방식을 바꾸면 원 서버 호출과 옛 가격이 어떻게 달라지는지 볼 수 있어요.

## 증상 — 로그인 헤더 때문에 공유 캐시를 못 쓰는 상품 페이지

FE에서는 같은 상품 주소인데 로그인하면 헤더가 바뀌어요. 응답은 매번 DB 조회만큼 걸리고, CDN은 hit 없이 원 서버로 요청을 넘겨요. 원인은 두 가지예요. 렌더링을 매 요청마다 하고 있고, 한 HTML 안에 사용자별 내용이 섞여 있어요.

공유 캐시는 요청 메서드와 대상 URI, 그리고 `Vary`가 고른 헤더로 캐시 키를 정한다고 RFC 9111은 설명해요. 같은 주소의 응답을 사용자마다 나눠 담으려면 설계 단계에서 부분을 나눠야 해요.

## 렌더링 시점 — 요청마다, 재검증 간격마다, 빌드 시 비교

서버가 HTML을 만드는 시점은 세 가지예요. 시점에 따라 원 서버 호출 수와 옛 가격이 남는 시간이 달라져요.

| 방식            | 원 서버 렌더링      | 옛 값이 남는 시간    | 맞는 상황                           |
| --------------- | ------------------- | -------------------- | ----------------------------------- |
| 요청마다        | 요청 수만큼         | 없어요               | 개인화가 크고 캐시할 부분이 없을 때 |
| 재검증 간격마다 | 간격당 많아야 한 번 | 간격 + 다음 요청까지 | 조금 낡아도 되는 공용 페이지        |
| 빌드 때만       | 배포 수만큼         | 다음 배포까지        | 내용이 거의 안 바뀌는 페이지        |

재검증 방식은 저장본을 만든 뒤 간격 동안은 원 서버에 묻지 않아요. Next.js ISR 가이드도 같은 흐름을 설명해요. 설정한 초가 지나면 다음 요청도 낡은 페이지를 받고, 새 페이지는 뒤에서 만들어져요. 그래서 옛 값은 적어도 간격만큼 남을 수 있고, 간격이 지난 뒤에도 다음 요청이 와서 새 페이지가 만들어질 때까지 더 남아요. 간격을 1시간으로 두면 가격을 바꾼 뒤 1시간 넘게 옛 가격이 나갈 수 있어요. 예시로 10분 간격이면 하루에 많아야 144번 렌더링해요.

빌드 때만 만드는 방식은 공용 HTML을 배포 때 한 번 만들고 정적 파일처럼 내보내요. 가격을 바꿔도 다음 배포 전까지 옛 값이 남아요. 자주 바뀌는 값을 여기에 넣으면 안 돼요.

## 공용과 개인 나누기 — 공용 HTML은 공유 캐시, 개인 부분은 따로 요청

로그인 헤더를 공용 HTML 안에 넣으면 페이지 전체가 개인 응답이 돼요. 공유 캐시에 둘 수 없으니 원 서버 부하가 사용자 수만큼 늘어요. 다른 방법은 공용 HTML에서 개인 부분을 떼어 내는 거예요.

- 공용 부분: 상품명, 이미지, 설명처럼 모든 사용자에게 같은 내용이에요. 공유 캐시에 저장해요.
- 개인 부분: 로그인 헤더, 장바구니 수량, 회원 혜택처럼 사용자마다 달라요. 클라이언트가 따로 요청해서 채워요.

Next.js 인증 가이드는 세션을 읽는 컴포넌트를 `Suspense` 경계 안에 두라고 설명해요. 경계 밖의 정적이거나 캐시된 부분은 정적 셸로 미리 렌더링돼 바로 나가고, 경계 안만 요청 시점에 채워져요. 이 구조가 공용과 개인을 나누는 방식과 같아요.

개인 부분을 공유 캐시에 두면 안 돼요. MDN은 개인화된 응답에 `private`을 빠뜨리면 공유 캐시에 저장돼 여러 사용자에게 재사용될 수 있고, 개인 정보가 새어 나갈 수 있다고 설명해요. 개인 부분 응답은 `private`이나 저장 금지로 표시하는 게 맞아요. 헤더 규칙 자체는 [API 응답 HTTP 캐시](/m/http-caching) 글에서 자세히 다뤄요.

## 쿠키가 붙은 요청 — 캐시 키와 저장 조건

RFC 9111의 캐시 키는 요청 메서드와 대상 URI로 정해지고, `Vary`가 고른 헤더가 더해져요. `Vary`에 쿠키를 넣지 않으면 쿠키 헤더는 캐시 키에 들어가지 않아요. 같은 URI에 쿠키만 다른 요청이 오면 캐시는 기본적으로 같은 저장본을 찾아요. 그래서 쿠키가 있는 요청을 공유 캐시에서 빼려면 설정으로 우회하거나 응답 헤더로 저장을 막아야 해요.

RFC 9111은 응답의 `Set-Cookie`가 캐싱을 막지 않는다고도 설명해요. 로그인 응답에 쿠키를 심었다고 저장이 안전하게 막히지 않아요. 시뮬레이터의 "공용 + 개인 섞임"은 쿠키 요청을 캐시에서 빼는 설정을 가정해요. 이 설정을 빠뜨리면 로그인한 사용자가 다른 사람의 헤더를 받을 수 있어요.

## 무효화 — 경로 · 태그 단위와 인스턴스 범위

가격이 바뀌었을 때 저장본을 지우는 방법은 범위에 따라 나뉘어요. Next.js 문서 기준으로 보면 이래요.

- 경로 단위: `revalidatePath`는 해당 경로의 캐시 항목을 무효화해요. 다시 만드는 일은 다음 요청에서 일어나요.
- 태그 단위: `revalidateTag`는 같은 태그가 붙은 캐시 항목을 모두 무효화해요. 태그는 데이터 호출이나 `cacheTag`로 붙여요.
- 인스턴스 범위: 여러 인스턴스를 쓸 때 기본 설정에서 무효화는 호출을 받은 인스턴스에만 적용돼요. 다른 인스턴스는 옛 값을 계속 줄 수 있어요.

CDN은 한 번 더 확인해야 해요. Next.js CDN 가이드는 `revalidateTag()`와 `revalidatePath()`가 서버 캐시만 지우고, CDN은 `s-maxage` 기간이 끝날 때까지 저장본을 준다고 설명해요. 그래서 무효화 호출과 함께 CDN 퍼지 호출을 같이 보내라고 권해요.

무효화 직후 옛 값이 다시 저장되는 경쟁은 [캐시와 캐시 스탬피드](/m/cache-stampede) 글에서 다뤄요.

## 옛 값 먼저 주기 — stale-while-revalidate를 렌더링 결과에 적용

RFC 5861은 `stale-while-revalidate`를 설명해요. 응답이 낡은 뒤에도 정해진 초 동안은 캐시가 낡은 응답을 줄 수 있고, 그 사이 뒤에서 재검증을 해요. 사용자는 기다리지 않아요.

렌더링 결과에 적용하면 이렇게 돼요. 낡은 HTML을 바로 주고, 새 HTML은 뒤에서 만들어요. 기다림은 줄어들지만, 새 HTML이 준비되기 전까지는 옛 가격이 나가요. 옛 값이 나가는 시간이 줄지는 않아요. 줄어드는 건 사용자가 기다리는 시간이에요.

Next.js ISR 가이드는 백그라운드 재생성이 재검증을 촉발한 요청을 받은 인스턴스에서 돈다고 설명해요. 요청별 과금을 쓰는 플랫폼에서는 이 작업이 추가 컴퓨트로 잡힌다고도 해요. `x-nextjs-cache` 응답 헤더에서 `HIT`, `STALE`, `MISS`, `REVALIDATED` 값을 볼 수 있어요. `STALE`은 옛 저장본을 주고 뒤에서 재검증 중이라는 뜻이에요.

## 데이터 캐시와 HTML 캐시 — 두 TTL이 겹치는 자리

캐시는 두 층에 있을 수 있어요. DB 결과나 API 응답을 저장하는 데이터 캐시, 그리고 완성된 HTML을 저장하는 HTML 캐시예요. 둘 다 옛 값을 담기 때문에 TTL을 따로 정하면 어긋나요.

데이터 캐시의 TTL이 60초이고 HTML 캐시도 60초라면, 최악의 경우 가격 변경 뒤 HTML이 다시 만들어질 때 데이터는 아직 옛 값일 수 있어요. 예시로 계산하면 옛 값은 두 TTL의 합만큼 남을 수 있어요. 이건 계산한 예시이고 실측이 아니에요.

Next.js 문서는 HTML 응답과 RSC 응답이 서로 다른 렌더링에서 나오면 화면이 어긋날 수 있다고 설명해요. 완화 방법으로 HTML과 RSC를 같은 TTL과 무효화 정책으로 함께 캐시하라고 권해요. 데이터 캐시를 쓴다면 HTML과 같은 무효화 태그를 붙이는 편이 나아요.

캐시 키와 태그에 개인 정보를 넣으면 안 돼요. Next.js 인증 가이드는 캐시 키와 태그가 평문으로 저장된다고 설명해요. 사용자 ID처럼 안정된 식별자로 키를 나누세요. 세션 토큰 자체는 키에 넣지 않아요. 세션 관리는 [인증 세션과 토큰](/m/auth-session-token) 글과 이어 봐요.

## 시뮬레이터 안내

아래 시뮬레이터는 하루(0시부터 24시간)를 1초씩 세는 순수 모델이에요. 같은 상품 페이지 하나만 보고, 캐시 노드는 한 개라고 가정해요. 실제 CDN과 여러 인스턴스의 분산 효과는 빠져 있어요.

1. 페이지 구성을 공용만으로 두고 렌더링 방식을 요청마다 바꿔 보세요. 적중률이 0%가 되는 걸 볼 수 있어요.
2. 재검증 간격을 1시간으로 두면 옛 가격이 나가는 최대 시간이 간격과 가까워지는 걸 볼 수 있어요.
3. 페이지 구성을 공용 + 개인 섞임으로 바꾸고 로그인 비율을 올려 보세요. 로그인 요청만큼 원 서버 렌더링이 늘어요.
4. 공용 HTML + 개인 부분 따로를 고르면 렌더링 횟수는 공용과 같고, 개인 부분 호출이 따로 집계돼요.

수치는 감을 잡기 위한 예시예요.

## FE 체크 포인트

- 응답의 `Cache-Control`과 `Age`를 보고 옛 값이 어느 층에서 왔는지 확인해요. 같은 페이지에서 공용 HTML은 캐시에서 오고 개인 부분만 새로 오는 게 정상이에요.
- 개인 부분 응답에 `private`이나 `no-store`가 붙는지 확인해요. 공유 캐시에 저장되면 다른 사용자에게 개인 정보가 섞여 나갈 수 있어요.
- 가격과 재고는 공용 HTML에 두더라도, 결제 직전에는 서버에 다시 확인해요. [서버 · 클라 처리 판단](/m/server-or-client) 글의 기준을 따라요.
- `x-nextjs-cache` 같은 신호가 있으면 `STALE`인지 `MISS`인지 보고 기다림과 옛 값을 나눠서 판단해요.

## 정리 — 공용 부분 캐시와 개인 부분 분리

페이지에서 로그인 헤더 같은 개인 부분을 떼어 내면 공용 HTML은 공유 캐시에 둘 수 있어요. 재검증 간격은 가격이 옛 값으로 남아도 되는 시간만큼 정해요. 가격처럼 바로 바뀌어야 하는 값은 간격 대신 태그 무효화와 결제 직전 확인으로 맞춰요. 캐시 키와 태그에는 개인 정보를 넣지 않아요.
