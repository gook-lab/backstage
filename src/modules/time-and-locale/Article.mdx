예시 응답 `2026-03-08T10:00:00`은 화면에 10시로 찍혀도, 그 값이 가리키는 순간은 사람마다 달라요. "3시간 전" 같은 상대 시간이나 다른 나라의 이벤트와 나란히 놓으면 차이가 드러나요.

이 글은 날짜와 시각을 어떤 형식으로 주고받을지, 시간대를 어디서 붙이고 어디서 표시할지 다뤄요. 아래 시뮬레이터에서 저장 방식과 보는 사람의 시간대를 바꿔 보면 차이를 바로 볼 수 있어요.

## 증상 — 오프셋 없는 문자열의 해석 차이

예시 응답 `2026-03-08T10:00:00`에는 오프셋이 없어요. 서울의 10시인지 뉴욕의 10시인지 문자열만으로는 알 수 없어요. 그래서 값을 받은 기기는 자기 시간대로 읽고, 기기마다 다른 순간을 만들어요.

RFC 3339는 ISO 8601을 인터넷 프로토콜에서 쓰도록 줄인 프로파일이에요. 이 문법에서 오프셋은 생략할 수 없어요. 오프셋은 `Z`나 `+hh:mm`, `-hh:mm` 중 하나로 써요.

## 시각과 벽시계 시간 — 저장 기준과 표시 기준 분리

같은 말이 두 가지 뜻으로 쓰여요. 설계할 때는 둘을 나눠 생각해요. 아래 표의 값은 예시예요.

| 개념                         | 뜻                                                             | 예                               |
| ---------------------------- | -------------------------------------------------------------- | -------------------------------- |
| 시각(instant)                | 지구에서 한 순간이에요. 누가 보든 같아요                       | UTC 01:00, 서울 10시와 같은 순간 |
| 벽시계 시간(wall clock time) | 달력과 시계에 찍히는 값이에요. 시간대가 있어야 시각이 정해져요 | 서울의 2026-03-08 10:00          |
| 날짜                         | 시각 없이 날짜만 뜻해요. 시간대와 상관없는 달력 날짜예요       | 생일 1990-05-01                  |

서버는 시각을 저장하고, 화면에서는 보는 사람의 시간대로 벽시계 값을 만드는 것을 기본으로 해요. 이 원칙을 지키면 "사용자마다 시간이 다르다"는 증상이 대부분 사라져요. 시간대가 없는 날짜는 따로 다뤄요.

## 주고받는 형식 — UTC와 오프셋 포함 RFC 3339

같은 순간을 네 가지 형식으로 적을 수 있어요. 예시 값은 서울 10시 이벤트예요.

| 형식        | 예                          | 가리키는 순간                      | 판단                           |
| ----------- | --------------------------- | ---------------------------------- | ------------------------------ |
| 오프셋 없음 | `2026-03-08T10:00:00`       | 정해지지 않아요                    | 시각으로 주고받지 않아요       |
| UTC (`Z`)   | `2026-03-08T01:00:00Z`      | 서울 10시, 뉴욕 전날 20시와 같아요 | 서버 저장과 전송의 기본        |
| 오프셋 포함 | `2026-03-08T10:00:00+09:00` | 서울 10시                          | 작성자 시간대를 남기고 싶을 때 |
| 날짜만      | `2026-03-08`                | 날짜 자체                          | 시간대가 없는 값 전용          |

RFC 3339는 `-00:00`을 `Z`나 `+00:00`과 다른 뜻으로 정해요(§4.3). `-00:00`은 UTC 시각은 알지만 현지 오프셋은 모른다는 뜻이에요. 주고받을 때는 `Z`나 실제 오프셋을 써요.

## JS Date 파싱 — 날짜만 있는 값과 시각이 있는 값 구분

MDN은 `Date.parse`의 ISO 형식 규칙을 이렇게 설명해요. 날짜만 있으면 UTC로 읽고, 날짜와 시각이 함께 있는데 오프셋이 없으면 시스템의 로컬 시간으로 읽어요.

- `new Date('2026-03-08')`은 UTC 3월 8일 0시예요. 뉴욕에서 보면 3월 7일 저녁 7시가 돼요.
- `new Date('2026-03-08T10:00:00')`은 보는 사람 기기의 시간대로 읽혀요.
- 표준이 아닌 문자열은 구현마다 다르게 읽을 수 있어요. MDN도 그렇게 설명해요.

파싱 규칙을 외우기보다, 주고받는 문자열에 `Z`나 오프셋을 붙이는 편이 안전해요.

## DB 타입 — timestamptz, timestamp, date 선택

PostgreSQL 문서는 세 타입이 시간대를 다루는 방식이 다르다고 설명해요.

- `timestamp with time zone`(timestamptz)은 입력에 시간대가 있으면 UTC로 바꿔 저장한다고 설명해요. 원래 시간대는 보존하지 않아요. 출력은 세션의 시간대로 바꿔 보여 줘요.
- `timestamp without time zone`은 입력의 시간대 표시를 무시하고 날짜와 시각 값만 저장해요. 시간대 변환이 없어요.
- `date`는 날짜만 저장해요.

| 데이터                               | 타입                                      | 이유                                              |
| ------------------------------------ | ----------------------------------------- | ------------------------------------------------- |
| 주문 · 결제 · 이벤트가 일어난 시각   | timestamptz                               | 같은 순간을 DB가 한 기준으로 비교하고 정렬해요    |
| 생일, 나이 계산의 기준 날짜          | date                                      | 시간대와 상관없는 달력 날짜예요                   |
| 매장 영업시간처럼 벽시계로 정한 규칙 | 벽시계 값과 시간대 이름(IANA)을 같이 저장 | 시간대 이름이 없으면 규칙을 다시 계산할 수 없어요 |

timestamptz는 원래 시간대를 남기지 않아요. 작성자 시간대가 필요하면 따로 열을 둬요.

## 시간대 표기 — IANA 이름과 고정 오프셋 구분

IANA 시간대 데이터베이스(tz database)는 지역마다 시간의 역사적 변경과 서머타임 규칙을 담는다고 설명해요. `Asia/Seoul`과 `America/New_York` 같은 이름은 규칙을 가진 값이에요. `+09:00`은 그 순간의 숫자라서 규칙이 없어요.

MDN은 `Intl.DateTimeFormat`의 `timeZone`이 IANA 이름을 받고, `+01:00` 같은 오프셋 식별자도 받는다고 설명해요. 두 값은 서로 다른 것이에요.

사람이 고른 지역은 IANA 이름으로 저장하고, 한 순간의 기록은 UTC나 오프셋 포함 문자열로 남겨요.

## 서머타임 — 23시간·25시간인 날과 매일 9시 예약

서머타임(daylight saving time, DST)이 바뀌는 날에는 로컬 시각이 없거나 두 번 있어요. MDN은 Date 문서에서 이 경우를 설명해요. 뉴욕에서 2시 30분은 봄 전환일에 존재하지 않아서 3시 30분으로 앞으로 밀려요. 두 번 있는 시각은 이른 쪽을 골라요.

그래서 봄 전환일은 하루가 23시간, 가을 전환일은 25시간이 돼요. 이 길이는 위 규칙에서 바로 나와요.

"매일 오전 9시" 예약은 두 방식으로 나뉘어요. 아래 표는 뉴욕 기준 3월 7일부터 9일까지를 예시로 계산한 결과예요.

| 날짜       | 시간대 이름으로 예약 (발송 UTC) | 처음 날 오프셋 고정 (뉴욕 시각) |
| ---------- | ------------------------------- | ------------------------------- |
| 2026-03-07 | 14:00Z (뉴욕 09:00)             | 09:00                           |
| 2026-03-08 | 13:00Z (뉴욕 09:00)             | 10:00                           |
| 2026-03-09 | 13:00Z (뉴욕 09:00)             | 10:00                           |

시간대 이름으로 예약하면 날마다 그 지역의 규칙을 다시 계산해서 9시를 지켜요. 고정 오프셋은 처음 계산한 값을 그대로 써서, 서머타임 전환일에 알림이 한 시간 늦게 나가요.

Vercel 문서는 Cron Jobs의 시간대가 항상 UTC라고 설명해요. 같은 문서는 Cron Jobs를 legacy 기능으로 보고 Schedules로 옮기는 중이며, Schedules에는 시간대가 있다고 설명해요.

한국의 9시는 UTC 00:00으로 맞추면 되지만, 뉴욕의 9시를 UTC로 고정하면 전환일마다 한 시간 어긋나요.

예약을 실제로 실행할 때의 재시도와 중복 실행 막기는 [배치 작업](/m/batch-jobs)에서 다뤄요.

## 집계 날짜 — 일별 통계의 "오늘" 기준 시간대

예시로, 서울에서 3월 8일 0시 30분에 일어난 이벤트를 생각해 봐요. 같은 이벤트도 기준에 따라 다른 날짜에 들어가요.

| 집계 기준        | 날짜                  | 맞는 경우                              |
| ---------------- | --------------------- | -------------------------------------- |
| 서버 UTC         | 3월 7일               | 여러 나라 데이터를 한 기준으로 합칠 때 |
| 작성자 시간대    | 3월 8일               | 매장이나 국가 단위 매출                |
| 보는 사람 시간대 | 뉴욕에서 보면 3월 7일 | 개인 화면의 "오늘" 기록                |

같은 데이터라도 집계표가 달라져요. 리포트에는 집계 기준 시간대를 함께 적어요. 보는 사람 시간대 기준은 서버가 사용자의 시간대를 알고 있어야 해요.

## 날짜만 있는 값 — 생일 같은 시간대 없는 날짜 저장

예를 들어 생일 `1990-05-01`을 `new Date`로 바꾸면 UTC 자정이 돼요. 뉴욕에서 보면 4월 30일로 보일 수 있어요.

그래서 생일은 `date` 열에 저장하고, 화면에는 문자열 그대로 보여 줘요. 날짜만 있는 값을 시각으로 바꾸는 순간 날짜가 밀려요.

## 표시 — Intl.DateTimeFormat과 Intl.NumberFormat

- `Intl.DateTimeFormat`은 `timeZone`으로 보여 줄 시간대를 골라요.
- `Intl.NumberFormat`의 `currency`는 ISO 4217 통화 코드를 받아요. MDN은 기본 소수 자릿수도 ISO 4217 목록을 따른다고 설명해요.
- 금액은 최소 단위 정수로 저장하고, 화면에 보일 때만 통화 형식으로 바꿔요.

## 언어 — Accept-Language 협상과 번역 위치

RFC 9110은 `Accept-Language`를 사용자 에이전트가 응답에서 선호하는 자연어 목록을 나타내는 헤더라고 설명해요(§12.5.4).

RFC 9110은 능동 협상(proactive negotiation)으로 응답을 고를 때 `Vary` 헤더를 보내는 경우가 많다고 설명해요. 이 헤더는 응답을 고를 때 어떤 요청 헤더를 썼는지 알려 줘요(§12.5.5).

RFC 9110은 사용자의 언어 선호를 모든 요청에 실어 보내는 것이 개인정보 기대와 어긋날 수 있다고 설명해요. 번역 위치는 용도에 따라 나눠요.

| 번역 위치  | 예                               | 이유                                                 |
| ---------- | -------------------------------- | ---------------------------------------------------- |
| 클라이언트 | 버튼 · 메뉴 · 날짜 표시          | 화면과 함께 바뀌고, 사용자 설정을 바로 반영해요      |
| 서버       | 이메일 · 알림 본문 · 저장된 약관 | 화면 없이 발송되거나 저장되므로 서버가 언어를 정해요 |

언어별로 다른 응답을 캐시한다면 캐시 키에 언어가 들어가는지 확인해요. 캐시 키 설계는 [캐시 스탬피드](/m/cache-stampede)에서 본 원칙과 이어져요.

## Temporal — 기본 선택을 보류하는 기준

MDN은 Temporal을 "Limited availability"로 표시하고, 일부 주요 브라우저에서 동작하지 않아서 Baseline이 아니라고 설명해요. 그래서 지금은 Date와 Intl을 기본으로 쓰고, Temporal을 쓰려면 대상 브라우저의 지원 상태를 MDN 호환성 표에서 직접 확인해요.

## FE 체크 포인트

응답에서 이런 신호를 보면 다음처럼 처리해요.

| 응답에서 보이는 것              | 뜻                          | FE가 할 일                                               |
| ------------------------------- | --------------------------- | -------------------------------------------------------- |
| 오프셋이 없는 날짜 시각         | 시간대 정보가 빠졌어요      | 서버에 형식을 확인해요. 임의로 로컬 시간대로 읽지 않아요 |
| `Z`나 `+09:00`이 붙은 값        | 한 순간이 정해져 있어요     | Date로 읽고, Intl로 보는 사람 시간대에 맞춰 표시해요     |
| `2026-03-08`처럼 날짜만 있는 값 | 시간대 없는 날짜예요        | `new Date`로 바꾸지 말고 문자열 그대로 표시해요          |
| `Vary: Accept-Language`         | 언어에 따라 응답이 달라져요 | 캐시를 쓰면 캐시 키에 언어가 들어가는지 확인해요         |

## 시뮬레이터 안내

아래 시뮬레이터에서 세 가지를 확인해요.

1. 작성자 시간대와 작성 날짜 · 시각을 고르고, 서버가 내려 주는 방식을 바꿔 보세요. 오프셋 없는 문자열은 보는 사람마다 다른 순간을 가리켜요.
2. 보는 사람 시간대를 바꿔서 일별 집계 날짜가 어떻게 달라지는지 보세요.
3. 예약 시간대를 뉴욕으로 두고 예약 방식을 바꾸면 3월 8일 발송 시각이 어떻게 달라지는지 보세요.

계산은 모두 브라우저의 Intl API로 해요. 그래서 같은 값을 여러 시간대에서 바로 비교할 수 있어요.

## 정리 — UTC 저장 · Intl 표시 · 시간대 이름 예약

- 주고받는 값은 UTC나 오프셋 포함 문자열로 정해요.
- 화면 표시는 보는 사람의 시간대로 Intl에 맡겨요.
- 매일 같은 시각의 예약은 시간대 이름으로 잡아서 서머타임 전환일에 맞춰요.
- 집계는 기준 시간대를 리포트에 함께 적어요.
- 시간대 없는 날짜는 `date`로 따로 저장해요.
