# 글쓰기 기준 — 학습 글 · 메타 · UI 문구

이 문서는 backstage 의 학습 글(`src/modules/*/Article.mdx`), 모듈 메타(`index.ts`), 시뮬레이터와 화면의 문구를 쓰거나 고칠 때 따르는 기준입니다. 기준은 새로 발명한 규칙이 아니라 main `2671c39` 시점 글들에서 가장 많이 쓰이던 관행을 문서화한 것입니다. 아래 수치는 그 시점의 실측입니다.

## 적용 범위 — 글 본문과 사용자에게 보이는 문구

| 대상                                                 | 어미                   | 기준                                           |
| ---------------------------------------------------- | ---------------------- | ---------------------------------------------- |
| `Article.mdx` 본문                                   | 해요체                 | 이 문서의 전 항목 적용                         |
| `index.ts` 의 title · question · summary · checklist | 해요체                 | 질문은 의문형, 체크리스트는 `~할 수 있어요`    |
| 시뮬레이터 · 화면 문구                               | 해요체, 짧은 동사 버튼 | 아래 UI 항목 적용                              |
| 이 문서 (`docs/`)                                    | 습니다체               | 저장소 문서 기준(`guk-lab-docs/STYLE.md`) 준수 |

## 어미 — 본문은 해요체로 통일

- 설명 문장은 `~해요 · ~이에요 · ~있어요 · ~돼요` 로 끝냅니다. 해요체 문장 끝이 본문 전체에서 800여 개인 반면 습니다체는 0개입니다.
- 독자에게 행동을 권할 때는 `~하세요` · `~마세요` 를 씁니다. main 에서 `하세요` 13회, `마세요` 8회, `해 주세요` 4회였습니다. `~해 주세요` 는 `~하세요` 로 바꿉니다. `~하라`, `~해라`, `~할 것`, `~하자` 같은 명령형은 쓰지 않습니다.
- 외부 자료의 권고를 옮길 때만 `~하라고 권해요`, `~하라고 설명해요` 처럼 간접 인용을 씁니다.
- 한 문장에는 한 가지 생각만 담습니다. 본문 문장의 중앙값은 35자이고, 90% 는 64자 안쪽입니다. 64자를 넘는 문장은 둘로 나눌 후보입니다.
- 한 단락은 3~4문장을 넘기지 않습니다. 긴 설명은 표나 목록으로 바꿉니다.

## 헤딩 — 대상 — 방식/결정

헤딩 형식은 `대상 — 방식/결정` 입니다. 대시 뒤는 명사구로 끝냅니다.

- 기준 형식이 205개 헤딩 중 173개(약 84%)입니다.
- 문장형 헤딩은 쓰지 않습니다. `~해요`, `~돼요`, `~다` 로 끝나는 헤딩은 명사구로 고칩니다.
  - ❌ `스탬피드 — 만료 순간 미스가 한꺼번에 나가요`
  - ⭕ `스탬피드 — 만료 순간 몰리는 미스`
  - ❌ `정리 — 재고는 나중에 줄일수록 정확하고 늦게 알려요`
  - ⭕ `정리 — 재고 차감 시점과 정확도 트레이드오프`
- 질문형과 구호형은 쓰지 않습니다. 구호가 설계 의도를 담으면 본문 첫 문장으로 내립니다.
- 고정 라벨은 대시 없이 씁니다. 다음은 모든 글에서 같은 이름을 씁니다. `FE 체크 포인트`, `시뮬레이터 안내`, `근거 문서`, `직접 돌려 보기`, `이제 판단할 수 있나요?`.
- 마지막 절은 `정리 — <결정 목록>` 형식입니다. 결정은 명사구로 씁니다.
- 레벨은 `##` 는 주제, `###` 는 주제 안의 방식 한 가지입니다.

- 표에 없는 용어는 처음 쓸 때 한 번 정하고, 같은 글에서는 표기를 바꾸지 않습니다.

## 띄어쓰기 — 영문 약어와 조사

- 영문 약어와 숫자 뒤의 조사는 띄어 씁니다. `API 를`, `DB 를`, `429 를`, `FE 가`, `TTL 을`.
- 근거: main 에서 `API 를`(35건, 붙여 쓴 `API를` 0건), `DB 를`(57건, 0건), `FE 가`(33건, 0건) 처럼 띄어 쓴 형태가 전부였습니다.
- 맞춤법 원칙은 조사를 앞말에 붙여 쓰는 것입니다. 그러나 이 저장소는 약어 뒤 조사를 띄우는 관행이 이미 굳어 있어 그대로 따릅니다. 맞춤법 기준으로 바꾸려면 전체 교체가 필요하므로 별도 결정으로 다룹니다.

## 영어 병기 — 첫 등장에만

- 처음 나오는 한국어 용어 뒤에 원어를 괄호로 씁니다. 예: `낙관적 락 (optimistic lock)`, `서버 전송 이벤트 (SSE)`.
- 같은 글 안에서 두 번째부터는 한국어 용어만 씁니다.
- SQL 키워드, HTTP 헤더, 상태 코드, 오류 코드(`40P01`), 함수명은 원문 그대로 씁니다.

## 출처 인용 — 확인한 범위만

- 출처를 인용할 때는 `문서명은 ~라고 설명해요` 형식을 씁니다. main 에서 `설명해요` 가 84회 쓰였고, 이 형식이 기본입니다.
  - ⭕ `PostgreSQL 문서는 FOR UPDATE 로 가져온 행이 트랜잭션이 끝날 때까지 잠긴다고 설명해요.`
  - ❌ `PostgreSQL 은 이 방식을 항상 보장해요.` (출처가 말하는 범위보다 넓음)
- 출처가 말하지 않은 것은 출처 문장 뒤에 덧붙이지 않습니다. 추정은 `~로 보여요` 처럼 추정임을 드러냅니다.
- 초안 · 비공식 문서는 자리를 밝힙니다. 예: `IETF 초안 (아직 RFC 가 아니에요)`.
- 출처를 확인하지 못했거나 회사 내부 수치는 쓰지 않습니다. 예시 숫자는 아래 예시 항목을 따릅니다.

## 설계 판단 — 선택과 이유를 같이

- 판단은 `~하는 편이 좋아요`, `~로 골라요`, `~해야 해요` 중 하나로 씁니다. 같은 글 안에서 같은 형식을 반복합니다.
- 판단에는 이유 한 문장을 붙입니다. 예: `재고를 원자적 UPDATE 로 줄이는 편이 좋아요. 확인과 차감이 한 문장이라 사이에 다른 요청이 끼지 않아요.`
- 장단점은 표로 비교합니다. 셀은 명사형이나 짧은 해요체로 씁니다.

## 예시 — 실측처럼 보이지 않게

- 실측이 아닌 숫자는 반드시 `예시` 라고 표시합니다. 본문 첫 문장이나 표 캡션에 씁니다.
- 예시 표기는 `예시`, `예를 들어`, `예시 응답은 이래요.` 셋 중 하나를 씁니다(`예시` 92회, `예를 들어` 13회).
- 화면 하단 문구는 `수치는 감을 잡기 위한 예시예요.` 로 고정합니다.

## 시뮬레이터와 UI 문구 — 짧은 해요체

- 버튼은 짧은 동사로 씁니다. 예: `재시도`, `저장`, `다시 보기`, `대기 순번 받기`.
- 결과 문구는 사실부터 씁니다. 예: `재고가 없어요`, `409 를 받았어요`. 원인과 다음 행동을 한 문장씩 붙입니다.
- 빈 상태와 오류는 원인 + 할 일 한 쌍으로 씁니다. 예: `찾는 글이 없어요` + `로드맵으로 돌아가기`.
- 로딩 문구는 `~을 불러오는 중이에요` 로 통일합니다.
- 감탄, 과장, 농담을 쓰지 않습니다.

## 체크리스트 — `~할 수 있어요` 로 끝내기

- 체크리스트는 5~7개입니다. 각 항목은 `~할 수 있어요` 로 끝냅니다. main 126개 중 107개(약 85%)가 이 형식이었습니다.
- 개념을 안다는 확인은 `~를 알아요` 를 허용합니다(14건).
- 항목은 한 판단만 확인합니다. `~할 수 있고, ~도 알아요` 처럼 두 판단을 잇지 않습니다.

## 질문과 요약 — 길이 기준

- `question` 은 FE 가 실제로 부딪히는 질문 한 문장입니다. 의문형 해요체(`~나요?`, `~까요?`)로 씁니다. main 20개의 중앙값은 33자입니다.
- `summary` 는 해요체 2~3문장입니다. main 20개의 중앙값은 132자입니다. 첫 문장은 현상이나 원리, 다음은 이 글이 다루는 방법, 마지막은 범위입니다.
- `summary` 가 `이 글은` 으로 시작하면 줄입니다. 본문과 같은 말을 되풀이하지 않습니다.

## 금지 표현

- 구호형 · 질문형 헤딩. 위 헤딩 항목을 따릅니다.
- 습니다체 · 반말 종결 (`~한다`, `~된다`, `~이다.`).
- 명령형 `~하라`, `~해라`, `~할 것`.
- 과장어. `완벽`, `확실히`, `반드시`, `절대`, `무조건`, `최고`. 근거로 말할 수 없으면 쓰지 않습니다. `항상` 은 출처가 실제로 그렇게 말할 때만 씁니다.
- 구어 군더더기. `그냥`, `진짜`, `되게`, `꽤`. 뜻이 달라지지 않으면 뺍니다.
- 추상 명사 세 개 이상을 한 문장에 겹치는 문장. 예: `효율성과 확장성과 사용자 경험을 향상했습니다`.

## 바꾸지 않는 범위 — 수치 · 링크 · 출처

- 수치, 날짜, 버전, 경로, 링크, 출처 제목, 표의 데이터, 코드 블록은 문장 다듬기 때문에 바꾸지 않습니다.
- 의미가 바뀔 수 있는 수정은 하지 않고, 리뷰 때 후보로만 남깁니다.
